## 1. 一条训练曲线究竟在测量什么

一条记录不能只有横坐标和数值。它至少对应运行身份、参数时刻、数据角色、损失定义、有效分母、模式和汇总方法。训练批次损失在参数更新前计算，各批次往往使用不同参数；验证损失通常在某个固定检查点上遍历验证集。把二者画在同一个 epoch 轴上便于观察，却不表示它们严格测量同一函数对两个集合的风险。解释曲线前先承认这些时刻差异。

对训练曲线，还要区分数据拟合项、显式惩罚和随机变换。训练损失包含增强、Dropout 或正则，验证只计算评估模式原始数据项时，训练高于验证并不自动说明泄漏。可另做固定参数、无随机增强、评估模式的训练集诊断，再与验证比较。不能先假定训练一定更低，再通过删除困难样本或调日志公式制造熟悉图形。

<a id="dl-project-4-detail-2"></a>
### 1.1 正确汇总可加分子和有效分母

批大小分别为六十四和十六，逐批均值再平均会让最后十六条占一半权重，而非五分之一。正确样本等权风险是所有逐样本损失和除总样本数。变长目标则可能按有效词元、像素或序列等权，必须先决定统计单位。记录分子与分母比只记录标量均值更稳妥，因为之后可以按合法方式合并，复算不同时间窗口。

若采用类别权重，分母又要说明是样本数、权重和还是其他约定。训练和日志必须针对同一目标，不能训练时按权重和归约、日志又按普通样本数拼接，却称它们同一损失。指标与训练目标可以不同，但名称应清楚。例如加权交叉熵、未加权准确率与宏平均召回描述不同偏好，没有哪一个名字能自动代表其余两个。

<a id="dl-project-4-detail-3"></a>
### 1.2 横坐标也有真实含义

更新数、已见样本、有效监督位置和墙钟时间都是可用横坐标，适合回答不同问题。梯度累积会改变微批到更新的关系，失败跳过会改变循环下标与真实更新数，数据过滤会改变每轮曝光。日志应同时保存关键计数，而不是把任何循环变量都叫 step。恢复之后从最近已完成更新继续计数，才能判断调度、曲线和状态是否接上。

时间应区分训练计算、验证、保存和数据准备，若只计设备计算就注明；若记录端到端，应包含相应等待。跨运行比较需固定计量边界，不能一个包含验证，另一个排除验证，再把耗时差全归于模型。时间戳用于定位事件，单调计时用于计算时长，两者用途也不同。时钟被校正或跨主机漂移时，直接相减墙上时间可能误导。

<a id="dl-project-4-detail-4"></a>
### 1.3 平滑只是展示，不能改写选择证据

移动平均或指数平均能帮助看趋势，但会混合多个参数时刻，并可能产生滞后。应保留原始点、窗口和边界处理，检查点选择使用事先定义的原始验证指标或明确的平滑规则。不能展示平滑后看起来更低的点，却保存另一时刻权重；也不能在看完曲线后选择最有利的平滑程度作为改进证据。

如果采用指数累计且从零初始化，早期数值可能有偏，需要说明是否做初值修正。缺测点应显示为缺失，而不是填零制造突然改善；中断后的新段也不能跨长空缺平滑成一条连续稳定曲线。图形用于解释真实记录，不能取代记录本身。保存原始分子、分母、运行与时刻，才能让别人重新画图和检查叙述。

<a id="dl-project-4-detail-5"></a>
### 1.4 实验一：批量汇总、选择身份和重复记录

下面用三个观察展示两种平均的差异，再用一组固定验证结果说明选择规则。运行身份与更新号构成记录键，重复键直接拒绝，避免恢复后将同一批结果计算两遍。人工数值只检验日志代数和状态身份，不模拟真实训练效果；它们应该能在纸上复算，再用代码确认。

```python
import math

batches = ([1., 3.], [10.])
numerator = sum(sum(b) for b in batches)
denominator = sum(len(b) for b in batches)
correct = numerator/denominator
wrong = sum(sum(b)/len(b) for b in batches)/len(batches)
assert correct == 14/3 and wrong == 6
history = [
    {'run': 'r1', 'step': 10, 'val_ce': .8, 'val_acc': .7},
    {'run': 'r1', 'step': 20, 'val_ce': .5, 'val_acc': .9},
    {'run': 'r1', 'step': 30, 'val_ce': .52, 'val_acc': .91},
    {'run': 'r1', 'step': 40, 'val_ce': .47, 'val_acc': .89}]
best_ce = min(history, key=lambda r: (r['val_ce'], r['step']))
best_acc = max(history, key=lambda r: (r['val_acc'], -r['step']))
assert best_ce['step'] == 40 and best_acc['step'] == 30

def validate(rows):
    keys = [(r['run'], r['step']) for r in rows]
    if len(keys) != len(set(keys)):
        raise ValueError('duplicate event identity')
    assert all(math.isfinite(r['val_ce']) for r in rows)
validate(history)
try:
    validate(history + [history[-1]])
except ValueError:
    pass
else:
    raise AssertionError('duplicate event accepted')
print('weighted / wrong batch means:', correct, wrong)
print('best CE / best accuracy steps:', best_ce['step'], best_acc['step'])
```

## 2. 把训练写成具有提交点的状态机

把每次更新分成取批、清梯度、前向、反向、更新参数、推进调度、记录状态几个阶段。保存点应该位于一个明确完成的边界，例如优化器和按更新调度都已完成，下一批尚未取出。检查点中的`next_step`表示下一次要执行的更新编号，而日志中的最后事件对应已完成更新。两种定义比只存一个含糊 epoch 数更不容易产生重复或跳过。

若在梯度累积中间保存，除了模型和优化器，还需要已累积梯度、有效分母、微批位置以及相关随机状态。教学与多数普通项目可以优先在完整更新边界保存，降低状态复杂性；若真实成本要求中途保存，则明确完整状态而非假装只多存一个计数器即可。数据预取、异步设备和分布式通信还可能有在途工作，保存前要确认边界含义。

<a id="sec-2-1"></a>
<a id="dl-project-4-detail-7"></a>
### 2.1 最近状态与最佳状态有不同任务

最近状态服务于故障恢复，应该包含当前完整训练轨迹所需信息。最佳状态由预先定义的验证规则选择，服务于最终评价和推理。最佳可能来自很早时刻，最近可能验证更差；二者并存没有冲突。不要用一个不断覆盖的含糊`best`文件同时承担两个角色，否则恢复时可能回退许多更新，报告又可能使用了最后权重。

选择还包括指标方向、严格改进、相同值时的先后政策和非有限值处理。验证交叉熵最小与准确率最大可能落在不同状态，实验一已经给出反例。应在开发前确定主要规则，不能最后从两者中挑更有利的测试结果。最佳值、最佳步和对应参数需要一起更新，避免其中一个变量更新失败而造成身份错配。

<a id="deep-dive-2"></a>
<a id="dl-project-4-detail-8"></a>
### 2.2 完整训练状态包含哪些对象

模型状态含可学习参数和持久缓冲，例如 BatchNorm 的运行统计；优化器状态含动量、二阶矩、步数和参数组设置；调度器包含进度及调度内部状态。还要保存随机流、采样位置、数据版本、预处理、结构配置和当前模式等必要条件。具体集合由执行图决定，使用 Python、NumPy、设备随机或独立生成器，就要分别考虑，不能只保存一个全局种子。

种子定义随机流的起点，随机状态定义当前流位置。训练到第六步后把种子重设为初值，会重新抽取最开始的随机掩码和批次，通常不是继续第七步。模型重建也可能消耗随机数，所以正确顺序通常是先构建对象、加载相关状态，再恢复随机流，最后开始下一次实际随机操作。若恢复后先随手运行一遍随机诊断，也可能推进了流位置。

<a id="dl-project-4-detail-9"></a>
### 2.3 状态一致性优先于文件数量

不能将第十步模型、第八步优化器和第九步调度器拼成一个所谓恢复点。它们分别有效，却不对应同一状态机时刻。保存清单应写明数据与配置身份、完成更新数和各对象时刻，并在重载时验证相容。参数组顺序、冻结参数和模型结构变化也影响优化器状态映射，不应只看键名能否载入。

如果修改架构或优化方法，有时可以迁移部分权重作为新实验起点，但应使用新的运行身份并声明哪些状态重置。它不是严格续接，也不能把两段曲线无标记拼成一条训练轨迹。清楚命名“恢复”“迁移”和“重新训练”，比让一个宽泛的成功标记掩盖差异更有用。不同恢复目标对应不同验收，不必为只需推理的交付保存所有训练内部对象。

## 3. 推理契约定义完整预测函数

图像项目的预测函数不仅由权重决定，还包含输入形状、通道顺序、数值单位、预处理、评估模式、输出类别映射和后处理。相同权重配另一种归一化，会形成另一函数。输入是原始零到十六强度还是已归一化零到一，必须由接口参数或清单明确，不能根据当前批次最大值临时猜测。低对比图本来也可能落在零到一，范围无法唯一识别单位。

<a id="dl-project-4-detail-11"></a>
### 3.1 明确允许形式，拒绝静默重排

本项目原始图像为单通道八乘八，推理入口接收批量、通道、高、宽四维浮点张量，并明确类别零到九的输出顺序。若支持单张图，可以提供单独适配入口补批维和通道维；不能把任意六十四个数随意 reshape 后就当同一张图，原通道顺序和空间排列可能已错。类型、有限性、非空批和范围检查都应先于实际模型计算。

错误输入要给出能定位问题的失败，例如缺少通道、非有限像素或单位不匹配。未知类别不是普通图像分类入口必然能识别的事实，最高 softmax 值也不是自动的分布外检测器。若另设拒绝或置信阈值，应纳入独立开发与评价。不要让接口输出一个数字，就无声承诺它能判断所有不属于十类的数据。

<a id="sec-1-1"></a>
<a id="dl-project-4-detail-12"></a>
### 3.2 单张与批量一致性的条件

如果网络在评估模式中逐样本计算，且前处理不依赖当前批内容，同一图像单独或与其他图像一起应在数值容差内一致。训练模式的 BatchNorm、随机 Dropout、按批估计归一化或显式跨样本模块会破坏该条件。发现差异应先检查模式与完整输入路径，再查加载或数值，不应无依据重新训练。

不同批形状可能选择不同浮点执行顺序，所以验收一般使用合理容差，并在接近类别并列时检查决策裕量。数学函数逐样本一致不必强求所有设备逐位相同；反过来，大幅差异也不能被一句“浮点不同正常”掩盖。要报告差异大小、触发形状和是否影响任务决策，再决定是否符合实际交付要求。

### 3.3 实验二：批量身份、单位和模式故障

这里构造一个未训练的卷积加 BatchNorm 分类器，只检验接口。先用人工批次更新运行统计，再比较评估模式的单张与批量结果。故意切换训练模式会看到同图受同批其他图影响；错误单位被拒绝。该随机网络没有数字识别能力，输出只作为函数一致性的参照，不参与前面项目的性能结论。

## 4. 新进程续训实验：比较完整后续轨迹

前面完整图像项目用于评价识别性能，本节另建四维输入、两维连续目标的小网络，以便隔离恢复机制。网络含 Dropout，优化器采用 Adam，学习率每四次更新衰减；每次更新用独立采样生成器抽八条记录。数据由另一个固定生成器构造，重建数据不会推进模型的随机流。这个设计故意同时包含参数、优化器、调度和两条动态随机流，让“只加载权重”不足以通过。

<a id="dl-project-4-detail-15"></a>
### 4.1 对照设计与保存边界

参考路径连续训练十二次更新。恢复路径从相同起点训练六次，在第六次参数更新和调度均完成后保存，记录下一步编号六；新进程重建对象、加载全部状态，再执行编号六到十一的更新。比较对象不仅是最终预测，还包括每步损失、抽样索引、实际使用学习率、下步学习率、所有参数、优化器矩、调度状态和随机流位置。若只比最终某个标量，许多错位可能被掩盖。

训练日志中每条损失来自更新前的当前模型，但事件里的`next_step`指向更新完成后的下一步。代码把`lr_used`和`lr_next`分开保存，避免调度之后的学习率被误当本次使用值。这里每次随机抽一个批次，不存在遍历整轮的游标；真实 DataLoader 若有当前排列、游标、预取和工作进程状态，需要额外设计，本实验不声称已验证多工作进程恢复。

<a id="dl-project-4-detail-16"></a>
### 4.2 独立可运行的父子进程演练

`core`只是当前代码块中的公共定义字符串，父子进程都在内存中执行，不产生脚本文件。临时目录自动删除检查点和最终对照产物。加载使用张量和基础容器组成的状态，不依赖自定义模型对象反序列化。子进程用当前解释器的同一默认包搜索环境启动并限制一条线程，加载时核对 Python 与 PyTorch 版本；这里的严格相等只作为本机确定性小实验目标，不推广到跨版本或不同设备。

```python
import copy
import subprocess
import sys
import tempfile
from pathlib import Path
import torch

core = r'''
import copy
import platform
import torch
from torch import nn

def setup():
    torch.set_num_threads(1)
    torch.manual_seed(52)
    net = nn.Sequential(nn.Linear(4, 8), nn.Tanh(), nn.Dropout(.25),
                        nn.Linear(8, 2)).double()
    opt = torch.optim.Adam(net.parameters(), lr=.02)
    sched = torch.optim.lr_scheduler.StepLR(opt, step_size=4, gamma=.7)
    sample = torch.Generator().manual_seed(53)
    data_rng = torch.Generator().manual_seed(54)
    x = torch.randn(32, 4, generator=data_rng, dtype=torch.float64)
    y = torch.stack((x[:, 0]+.5*x[:, 1], x[:, 2]-x[:, 3]), dim=1)
    return net, opt, sched, sample, x, y

def advance(net, opt, sched, sample, x, y, start, stop, history):
    net.train()
    for step in range(start, stop):
        ids = torch.randperm(len(x), generator=sample)[:8]
        opt.zero_grad(set_to_none=True)
        loss = (net(x[ids])-y[ids]).square().mean()
        assert torch.isfinite(loss)
        used = opt.param_groups[0]['lr']
        loss.backward()
        assert all(p.grad is not None and torch.isfinite(p.grad).all()
                   for p in net.parameters())
        opt.step(); sched.step()
        history.append({'step': step, 'next_step': step+1, 'loss': loss.item(),
                        'ids': ids.tolist(), 'lr_used': used,
                        'lr_next': opt.param_groups[0]['lr']})

def pack(net, opt, sched, sample, next_step, history):
    return copy.deepcopy({'format': 1, 'next_step': next_step,
        'torch_version': str(torch.__version__), 'python_version': platform.python_version(),
        'model': net.state_dict(), 'optimizer': opt.state_dict(),
        'scheduler': sched.state_dict(), 'sample_rng': sample.get_state(),
        'torch_rng': torch.get_rng_state(), 'history': history})

def restore(checkpoint, net, opt, sched, sample):
    assert checkpoint['format'] == 1
    assert checkpoint['torch_version'] == str(torch.__version__)
    assert checkpoint['python_version'] == platform.python_version()
    net.load_state_dict(checkpoint['model'])
    opt.load_state_dict(checkpoint['optimizer'])
    sched.load_state_dict(checkpoint['scheduler'])
    sample.set_state(checkpoint['sample_rng'])
    torch.set_rng_state(checkpoint['torch_rng'])
'''
exec(core)
old_threads = torch.get_num_threads()
try:
    net, opt, sched, sample, x, y = setup()
    reference_history = []
    advance(net, opt, sched, sample, x, y, 0, 12, reference_history)
    reference = pack(net, opt, sched, sample, 12, reference_history)
    net, opt, sched, sample, x, y = setup()
    partial = []
    advance(net, opt, sched, sample, x, y, 0, 6, partial)
    checkpoint = pack(net, opt, sched, sample, 6, partial)
    with tempfile.TemporaryDirectory() as temp:
        folder = Path(temp)
        torch.save(checkpoint, folder/'resume.pt')
        child = core + r'''
import sys
from pathlib import Path
folder = Path(sys.argv[1])
net, opt, sched, sample, x, y = setup()
saved = torch.load(folder/'resume.pt', weights_only=True, map_location='cpu')
restore(saved, net, opt, sched, sample)
history = copy.deepcopy(saved['history'])
advance(net, opt, sched, sample, x, y, saved['next_step'], 12, history)
torch.save(pack(net, opt, sched, sample, 12, history), folder/'resumed.pt')
'''
        result = subprocess.run([sys.executable, '-B', '-c', child, str(folder)],
                                capture_output=True, text=True, timeout=60)
        assert result.returncode == 0, result.stderr
        resumed = torch.load(folder/'resumed.pt', weights_only=True, map_location='cpu')
        def equal(a, b):
            if isinstance(a, torch.Tensor):
                return isinstance(b, torch.Tensor) and torch.equal(a, b)
            if isinstance(a, dict):
                return a.keys() == b.keys() and all(equal(a[k], b[k]) for k in a)
            if isinstance(a, (list, tuple)):
                return len(a) == len(b) and all(equal(x, y) for x, y in zip(a, b))
            return a == b
        assert equal(reference, resumed)
    # 完全恢复后故意推进 Dropout 的随机流，隔离随机状态错位。
    net, opt, sched, sample, x, y = setup()
    restore(checkpoint, net, opt, sched, sample)
    torch.rand(17)
    wrong_history = copy.deepcopy(checkpoint['history'])
    advance(net, opt, sched, sample, x, y, 6, 12, wrong_history)
    difference = max((net.state_dict()[k]-reference['model'][k]).abs().max().item()
                     for k in reference['model'])
    assert difference > 1e-8
    assert wrong_history[6]['ids'] == reference_history[6]['ids']
    print('all states and twelve event records match after fresh-process resume')
    print('same sampled batch but shifted Dropout RNG changes final parameters:', difference)
    print('step 6 used / next lr:', reference_history[6]['lr_used'],
          reference_history[6]['lr_next'])
finally:
    torch.set_num_threads(old_threads)
```

### 4.3 对照成功不等于所有恢复问题都已解决

同环境小网络逐项相等，说明保存集合和恢复顺序对当前执行足够。它没有验证 GPU、分布式、异步预取、混合精度缩放或其他随机库。若加入这些组件，状态机扩大，需增加对应状态与实测。不能因为一个 CPU 演练通过，就给任意硬件的严格复现承诺；也不应因此放弃机制核对，小对照正是发现具体缺失状态的有效方法。

故障路径在完整恢复后只推进模型随机流，采样索引仍保持相同，最终参数却改变。它隔离了 Dropout 随机位置，不把批次变化或优化器重置混入同一个反例。若只恢复权重并把其他一切都重设，观察到差异当然预期，却无法判断哪个状态最关键。设计恢复测试也需要控制变量，而不只是安排一次保存和加载。

<a id="dl-project-4-detail-18"></a>
## 5. 日志与检查点的事务边界

真实进程可能在写文件或写日志时失败，因此“调用过保存函数”不足以证明产物完整。可以先在同目录写候选文件，完成必要校验后再替换当前入口，使读取者看到旧完整版本或新完整版本。这个安排减少半写文件被当成有效状态的风险，但具体持久化与替换保证仍依赖文件系统和操作系统。本文演练同目录替换，不将它扩大成断电和所有网络存储下的保证。

<a id="dl-project-4-detail-19"></a>
### 5.1 两个文件不能无声当成一个原子事务

若模型和日志分别写入，进程可能在二者之间失败。解决思路是让检查点携带已提交事件位置与状态身份，外部日志只作为可重放记录；或先写版本化完整包，再更新一个小入口清单。恢复时核对事件与参数时刻，不直接相信文件修改时间。时间相近不等于因果上对应，文件名里写同一 epoch 也不能保证保存顺序没有错。

日志重放要明确幂等身份。一次已完成更新在重新输出后不应计两次，可以用运行身份、分支身份、更新号和事件类型构成键。严格恢复从同一检查点重演的事件若数值相同，可以按政策去重；同键却数值不同应报冲突，而不是静默保留最后一条。若是新配置分支，使用新身份，不要把它混入旧轨迹再靠排序拼接。

### 5.2 实验四：候选失败保留旧入口，成功后替换

以下使用 JSON 小清单和字节摘要演练提交流程，不保存真实大模型。先构造旧版本，再写一个缺少必需字段的候选，校验失败时不替换旧入口；最后合法候选完成替换，并核对摘要。所有文件在自动清理临时目录。摘要用于识别具体字节与检测意外改变，不自动证明发布者身份；教学目标是完整性和提交语义。

```python
import hashlib
import json
import os
import tempfile
from pathlib import Path

def validate(payload):
    if payload.get('format') != 1 or type(payload.get('next_step')) is not int:
        raise ValueError('invalid manifest')
    if payload['next_step'] < 0 or not payload.get('state_id'):
        raise ValueError('invalid state identity')

def publish(folder, payload):
    candidate = folder/'candidate.json'
    encoded = json.dumps(payload, sort_keys=True).encode('utf-8')
    with candidate.open('wb') as handle:
        handle.write(encoded); handle.flush(); os.fsync(handle.fileno())
    validate(json.loads(candidate.read_text(encoding='utf-8')))
    os.replace(candidate, folder/'current.json')
    return hashlib.sha256(encoded).hexdigest()

with tempfile.TemporaryDirectory() as temp:
    folder = Path(temp)
    old = {'format': 1, 'next_step': 6, 'state_id': 'run-a-step-6'}
    publish(folder, old)
    old_bytes = (folder/'current.json').read_bytes()
    try:
        publish(folder, {'format': 1, 'next_step': 7})
    except ValueError:
        pass
    else:
        raise AssertionError('bad candidate accepted')
    assert (folder/'current.json').read_bytes() == old_bytes
    try:
        publish(folder, {'format': 1, 'next_step': True, 'state_id': 'invalid-bool'})
    except ValueError:
        pass
    else:
        raise AssertionError('boolean step accepted')
    assert (folder/'current.json').read_bytes() == old_bytes
    new = {'format': 1, 'next_step': 8, 'state_id': 'run-a-step-8'}
    digest = publish(folder, new)
    assert json.loads((folder/'current.json').read_text()) == new
    assert hashlib.sha256((folder/'current.json').read_bytes()).hexdigest() == digest
print('failed candidate preserves previous entry; verified replacement passed')
```

### 5.3 校验范围应该能回答具体失败问题

字段与版本校验能发现格式不相容，参数形状与键校验能发现结构不匹配，固定样例预测能发现部分前处理或映射变化，新进程续训能发现训练状态缺失。它们不能相互替代。文件摘要完全一致，只证明读取的是相同字节，不证明原数据、标签或实现正确；固定样例通过，也不覆盖所有输入。应按故障模型安排组合检查，而不是堆一串没有对象的验收步骤。

还要区分意外损坏、配置漂移和人为修改。教学包由当前实验生成，加载时仍检查基础格式并使用明确序列化入口；实际交换产物则应按来源与组织政策选择加载方式。这里不把格式校验称作完整安全系统，也不为了讨论普通模型保存而引入无关的外部流程。关键是让读者知道各项证据证明了哪件事，避免把一个成功标记无限扩张。

<a id="dl-project-4-detail-22"></a>
## 6. 为什么当前预测相同，下一步却可以不同

把模型参数记为 $`\theta`$，优化器内部状态记为 $`u`$，随机与采样状态记为 $`r`$，训练转移写成 $`(\theta',u',r')=T(\theta,u,r;D)`$。当前预测只读取完整推理配置下的参数与模型缓冲，而下一步更新还读取后两类状态。因此两份产物可以实现相同当前函数，却具有不同未来轨迹。这不是恢复的悖论，而是两个验收问题要求的信息不同。

<a id="dl-project-4-detail-23"></a>
### 6.1 用 Adam 的更新公式定位缺失

Adam 的一阶矩累积梯度，二阶矩累积梯度平方，再根据步数做偏差修正，用修正矩和稳定项决定更新。相同参数与当前梯度，若历史矩或步数不同，更新仍一般不同。只恢复权重后重新初始化优化器，是从该参数启动一个新过程。它可能是有意义的微调起点，但不能用原连续训练日志解释它的后续路径。

学习率调度同样读取自己的进度，某些调度还读取验证指标历史。仅设置当前学习率，未必重建未来每一步应使用的值；仅载入调度状态又不核对优化器参数组，也可能错配。恢复测试最好比较实际下一步使用学习率和更新差值，再比较多步轨迹，这比只打印一个调度器对象更有辨识力。配置名称相同不是内部状态相同的证明。

<a id="dl-project-4-detail-24"></a>
### 6.2 模型缓冲不只是附属信息

BatchNorm 的运行均值、方差和已跟踪批次数影响评估函数，属于模型持久状态。只复制命名参数而遗漏缓冲，会得到看起来层形状完全相同、权重也一样的另一推理函数。相反，普通模块的训练或评估标志通常由调用者设置，不应假定加载参数字典会自动恢复正确推理模式。参数、缓冲和模式必须分别理解。

还有些缓存不是持久缓冲，例如某些增量状态或临时特征。是否需要保存取决于交付目标：重新从原输入预测可以重算，在线继续某个会话则可能必须恢复。保存集合不宜机械地越多越好，而应由函数与生命周期推导。无关缓存会增加体积和版本耦合，缺少必要缓存又会破坏继续语义；先明确下一次调用从哪里开始，再选择状态。

<a id="dl-project-4-detail-25"></a>
### 6.3 实验五：字典别名、独立快照和缓冲遗漏

下面用 BatchNorm 加线性层构造最小示例。保存浅引用与深复制之后，继续训练更新会使前者随原模块变化，后者保持。再让一份模型只接收参数、保留默认缓冲，评估输出会与完整状态恢复不同。所有对象在内存中，实验不写文件，也不将随机网络结果当分类性能。

```python
import copy
import torch
from torch import nn

torch.manual_seed(66)
net = nn.Sequential(nn.BatchNorm1d(3), nn.Linear(3, 2)).double()
net.train()
for _ in range(5):
    net(torch.randn(10, 3, dtype=torch.float64)+4)
alias = net.state_dict()
frozen = copy.deepcopy(net.state_dict())
old_mean = frozen['0.running_mean'].clone()
with torch.no_grad():
    net[1].weight.add_(1)
net(torch.randn(10, 3, dtype=torch.float64)-6)
assert torch.equal(alias['0.running_mean'], net[0].running_mean)
assert torch.equal(frozen['0.running_mean'], old_mean)
assert not torch.equal(alias['1.weight'], frozen['1.weight'])
complete = nn.Sequential(nn.BatchNorm1d(3), nn.Linear(3, 2)).double()
complete.load_state_dict(frozen); complete.eval()
parameters_only = nn.Sequential(nn.BatchNorm1d(3), nn.Linear(3, 2)).double()
with torch.no_grad():
    for (_, target), (_, source) in zip(parameters_only.named_parameters(),
                                         complete.named_parameters()):
        target.copy_(source)
parameters_only.eval()
x = torch.randn(4, 3, dtype=torch.float64)
with torch.no_grad():
    assert not torch.allclose(complete(x), parameters_only(x))
assert complete.training is False and parameters_only.training is False
print('independent snapshot stable; shallow alias and omitted buffers detected')
```

### 6.4 同解释器也要核对依赖搜索条件

本章新进程演练发现，本机默认解释器会从用户目录加载 PyTorch 2.10.0 CPU，而开启隔离模式可能转到系统目录的 PyTorch 2.5.1。解释器路径相同并不保证依赖集合相同，改变搜索环境就可能改变随机与优化实现。因此实验使用相同默认搜索条件，并把实际版本写进检查点，恢复前显式核对，而不是把进程启动成功视作环境一致。

这条观察不说明隔离模式不好，它说明隔离本身是环境变更，需要为目标环境准备正确依赖。跨环境迁移如果是任务目标，应另外定义兼容和容差测试，不能通过偷偷关闭版本校验来维持“严格续训”声明。固定依赖、记录包路径与版本、建立小参考，都是为了让失败能定位到具体条件，而不是为了要求所有未来系统永远不升级。

## 7. 训练异常的分层证据矩阵

当曲线或恢复结果异常，先定位是记录、输入、模式、梯度、更新还是选择。每一层选一个能区分竞争解释的小实验，而不是一次性换网络、优化器和随机种子。许多真实问题并不需要重新训练全项目：错误单位可在固定输入检查，旧优化器参数可通过身份集合发现，错位日志可用事件键复算。先缩小问题，再恢复完整流程。

<a id="dl-project-4-detail-28"></a>
### 7.1 曲线突然跳变：数据、状态与显示分别查

先检查是否恢复到另一检查点、学习率是否跨了调度边界、数据角色和有效分母是否改变。再核对增强和模式，最后查看是否只是汇总或平滑窗口切换。若日志中保存了原始分子和分母，可以直接复算；若只有截图，很多问题无法追踪。记录变化的那一次事件和参数身份，比观察整条漂亮曲线更能定位触发条件。

若跳变只发生于恢复后的第一批，应核对采样顺序、随机流、模型模式与优化器矩；若全体后续都错一个数量级，优先检查单位或归约。这样的模式只能提出优先假设，不能单凭图形确诊。用固定同批前向、梯度和更新分别对照，才能知道偏差最早出现在哪个阶段。诊断应找到第一个分叉，而不是只解释最后一个症状。

<a id="dl-project-4-detail-29"></a>
### 7.2 权重加载成功但预测不同：分阶段比中间量

先比较入口解析后的张量、缩放结果、通道与空间顺序，再比较模型缓冲、评估模式、逐层输出和最终类别映射。只看最后 argmax 可能掩盖大概率差异，也可能把极小近并列变化夸大为全模型失效。应同时保留数值差异和离散决策，报告最大绝对误差、典型尺度和决策裕量。

如果单张与批量不一致，先用相同图像复制构造控制批，再加入不同内容，观察变化是否来自跨样本统计。若只在输入拼接时出现，检查预处理是否按批最大值归一化或错误广播。若保存前后同一批都一致而服务仍不同，说明差异可能在服务入口或后处理，不应把序列化当默认罪魁。分层比较能避免无目的地重复保存或重训。

<a id="dl-project-4-detail-30"></a>
### 7.3 非有限损失之后的恢复政策

检测到非有限值时应明确是否已经更新参数或内部矩。若只在反向前发现，可以跳过并记录；若优化器已读入非有限梯度，状态可能已经污染。恢复旧权重却保留被污染矩，下一步可能继续异常。可信恢复点应由完整一致状态构成，修复后用固定下一批复验，不能只把 NaN 替换成零然后当作原训练没有发生变化。

混合精度系统还需考虑梯度缩放器是否跳过了更新，调度与计数应按实际政策推进。本文 CPU 双精度演练没有验证这个组件，所以只描述需要新增的检查对象。若正式训练允许跳过批次，报告跳过数量、原因和有效曝光；大量困难样本被无声跳过，会改变优化目标和评价覆盖。异常处理是学习流程的一部分，不是日志外无关细节。

<a id="dl-project-4-detail-31"></a>
## 8. 产物、日志与报告怎样形成可追溯闭环

一份最终报告应能从指标行追到预测文件身份、模型状态身份、数据划分与评价代码，再追到选择规则和训练记录。文件名只是入口，不足以表达这些关系。可以给每个版本一个不可混淆的身份，并保存用于核对的配置摘要、来源记录和固定样例。摘要证明字节对应，来源与生成记录证明流程关系，两者分工不同。

<a id="dl-project-4-detail-32"></a>
### 8.1 类别顺序与概率语义不可省略

输出十列 logits，必须明确第零列是否对应数字零、是否存在重排或缺失类别。softmax 只是将当前 logits 转为总和一的数值，不自动赋予目标总体校准含义。若加温度或拒绝阈值，校准和策略选择角色也应记录。把同一预测张量配错类别表，即使每列数值完全复现，也会产生错误业务结果。

预测记录应包含样本标识与模型版本，通过键连接标签复算指标，而非假设两文件排序永远一致。重复、漏行和覆盖变化应显式拒绝或按预设规则处理；不能静默丢掉失败样本，导致报告只剩最容易部分。第 2 章的固定测试结果可用于一次完整报告，第 3 章复用这些预测分析错误并不创造新独立测试，这个角色限制也应写清。

<a id="dl-project-4-detail-33"></a>
### 8.2 保存信息与清理中间文件的平衡

实验模型、清单与日志应按用途管理：教学演示可在临时目录完成保存与恢复验证，真实研究则应保留重建结果所需的配置、划分身份、参数、关键日志与评价记录。只剩一个分数而无法确认输入、模型和选择规则时，结果便失去可追溯性。清理前应检查依赖关系，确保没有删除恢复训练或重现推理所需的唯一证据。

清理前先从独立入口重载并核对结果，确认最终文档包含完整可执行代码和必要环境条件。若某个“临时”文件实际上是唯一词表或类别映射，它就是函数依赖，不能删后再说只保留最终模型。梳理依赖图可以识别这类隐藏必需品。完成标准是别人从保留结果能够理解并重建约定行为，而不是目录表面看起来很干净。

<a id="dl-project-4-detail-34"></a>
## 9. 二十四道练习与逐题详解

<a id="dl-project-4-detail-35"></a>
### 9.1 两个批次的均值为什么不能再平均

**问题：** 两条样本损失一、三，最后一个批次只有一条损失十，epoch 均值应是多少？

**解析：** 总损失十四，总样本三，所以均值十四除三；若先算两批均值二与十再平均，得到六，最后单样本被赋予一半总权重。应记录可加分子和有效分母，按所选统计单位汇总。若设计原本要求批次等权，也可采用后者，但它随如何分批改变，不是通常样本等权经验风险。用这个极小手算例核对日志，比只在整齐满批数据上观察曲线更容易发现错误。

<a id="dl-project-4-detail-36"></a>
### 9.2 为什么训练曲线不一定是某个固定模型的风险

**问题：** 一轮训练各批损失加权后，能否当作最后一步参数在整个训练集上的损失？

**解析：** 不能，因为各批计算时模型参数不断更新，汇总混合了多个参数时刻，且训练可能含随机增强和 Dropout。它可以作为过程统计，但若要固定最终模型的训练风险，应冻结状态、统一评估模式再遍历训练集。两者都可画图，却需要不同名称。不能把二者数值差直接解释为泛化差异，也不能用最后状态的验证风险无条件对应整个动态训练均值。

<a id="dl-project-4-detail-37"></a>
### 9.3 验证交叉熵与准确率最优步不同怎么办

**问题：** 实验一最小交叉熵在第四十步，最高准确率在第三十步，最终应保存哪个？

**解析：** 依照事先规定的选择目标；如果规则是最小验证交叉熵，就选择第四十步，并报告其准确率，不在测试后换成另一个状态。也可以保存两个带清楚身份的探索产物，但最终主结论要对应固定规则。概率分配和最高类别判断是不同评价，因此最优步不一致正常。把两个最优值拼成一行“最佳模型”指标，却没有任何一个实际状态同时达到它们，是不可复算的结果。

<a id="dl-project-4-detail-38"></a>
### 9.4 更新完成后的步号如何定义

**问题：** 从零编号，已经完成零到五六次更新，检查点的下一步应保存多少？

**解析：** 保存六，恢复执行六到十一得到十二次总更新。若把五误当下一步，会重放第六次；若存七又会漏掉一次。模型、优化器和调度器都要位于同一完成边界，事件记录明确本次与下一步编号。这个约定比含糊地写“第六步检查点”更精确，尤其当日志有更新前损失、更新后学习率和异步写入时。编号本身不重要，定义与所有调用一致才重要。

<a id="dl-project-4-detail-39"></a>
### 9.5 每次恢复都重新设置同一种子够吗

**问题：** 起初种子五十二，训练六步后重设五十二，是否延续原 Dropout 流？

**解析：** 不会，种子把流重置到起点，而不是第六步之后的位置。模型构造还会消耗随机数，使实际位置更加复杂。应在明确保存边界记录当前随机状态，重建与加载完成后再恢复，下一次随机操作才对应原流程。独立采样生成器也有自己的流，不能只恢复全局 Torch 状态。实验三特意保持批次索引相同、仅推进模型随机流，最终参数仍改变，说明这不是可忽略日志细节。

<a id="dl-project-4-detail-40"></a>
### 9.6 为什么恢复顺序里构造对象应在恢复随机流之前

**问题：** 先恢复随机状态，再初始化同结构模型和优化器有什么隐患？

**解析：** 初始化参数会消耗随机数，即使随后权重被覆盖，随机流已前进，下一次 Dropout 与连续训练不同。较清楚的顺序是先构造对象和加载状态，再设置采样及模型随机流，随后直接进入规定下一步。若中间诊断使用随机操作，也要控制或另用独立生成器。对象值最终一样不代表期间没有副作用，恢复测试要比较后续转移，而非仅观察加载后的当前参数。

<a id="dl-project-4-detail-41"></a>
### 9.7 新进程为何需要记录实际依赖版本

**问题：** 两次使用相同`sys.executable`，为什么仍可能不是相同软件条件？

**解析：** 用户目录、隔离启动、环境变量和包搜索路径可以改变导入位置，本机就存在不同搜索条件加载两份 PyTorch 的情况。应记录实际版本，必要时核对来源路径与配置，并为严格续训匹配相同条件。跨环境迁移是另一个目标，需要独立兼容测试，不能靠跳过校验冒充原轨迹。解释器路径是环境身份的一部分，却不是全部；保存一个路径字符串不足以证明数值与随机实现相同。

<a id="dl-project-4-detail-42"></a>
### 9.8 只恢复参数后预测相同，为什么下一步不同

**问题：** 参数、输入和当前梯度相同，优化器重建为何仍会改变更新？

**解析：** Adam 还读取一阶矩、二阶矩和步数，动量方法读取历史速度，调度读取进度。相同当前函数不限定这些内部状态，所以后续转移可不同。若目的为微调，重置优化器是合法新流程；若目的为中断续接，就应保存并恢复相容状态。不要把“训练能继续下降”当成续训等价证明，它最多说明新过程仍可优化。比较下一步参数差值和多步事件，才能验收目标。

<a id="dl-project-4-detail-43"></a>
### 9.9 学习率相同能否证明调度器已恢复

**问题：** 恢复时打印当前学习率与原来一致，未来调度一定一致吗？

**解析：** 不一定，调度器可能内部计数不同，下一次衰减发生时刻就会错；依赖验证的调度还可能缺最佳值或耐心计数。应核对调度状态、参数组和实际后续学习率序列。实验记录`lr_used`与`lr_next`，可以辨别更新前后错位。只设置一个当前标量可能暂时掩盖问题，到下一边界才分叉。验收应覆盖至少一个真实调度转折，而不只在平坦区间比较。

<a id="dl-project-4-detail-44"></a>
### 9.10 深复制最佳参数解决了什么

**问题：** 一个变量指向`state_dict()`，后续训练为何可能让所谓最佳值变化？

**解析：** 字典张量可与原模型存储共享，原地更新会改变其所引用内容；变量名不会冻结时间。深复制或独立序列化保留该时点数值。实验五同时改权重与运行统计，展示浅引用变化而独立快照保持。复制只是保存正确状态的一个条件，还需正确选择时刻、记录版本和验证指标。若复制的是下一轮已更新参数，却标成上一轮最佳，存储独立也无法修复语义错位。

<a id="dl-project-4-detail-45"></a>
### 9.11 参数相同为何评估函数还可能不同

**问题：** 两个 BatchNorm 模型全部命名参数一致，但输出不一致，哪里还需看？

**解析：** 持久运行均值、方差等缓冲也参与评估；训练或评估模式又决定使用什么统计。只复制参数遗漏缓冲，会形成另一函数。检查完整模型状态字典、模式与前处理，再对固定输入逐层比较。相同参数只是完整函数身份的部分条件。反过来，载入完整状态也不保证模块自动处于评估模式，调用者仍需明确切换，不能把序列化职责和执行模式混为一谈。

<a id="sec-7-1"></a>
<a id="dl-project-4-detail-46"></a>
### 9.12 单图与批量不一致一定是模型文件坏了吗

**问题：** 同图单独预测和放入其他图的批次预测差很多，应从哪开始？

**解析：** 先检查评估模式、BatchNorm、Dropout 和按批前处理，再检查张量布局与数值容差。实验二在训练模式中直接给出同图受批内容影响的反例，而没有任何文件损坏。若模型本来含跨样本机制，则一致性不是默认契约，需要另定义行为。诊断固定合法输入并逐阶段比中间量，找到第一个分叉，比盲目重复保存或重新训练更有效。序列化只是候选原因之一。

<a id="dl-project-4-detail-47"></a>
### 9.13 范围零到一为何不能自动判断已经归一化

**问题：** 输入最大值不到一，入口能否自行决定不再除十六？

**解析：** 不能，原始低强度图像也可能落在这一范围，数值无法唯一确定单位。按当前批最大值猜测还会让同图在不同批中采用不同路径。应明确单位或独立原始、归一化入口，并用固定样例核对。范围检查能拒绝明显越界，却不能识别所有语义错误。若交付要求原始零到十六，调用者必须声明并遵守，不能用一个启发式猜测替代数据契约。

<a id="dl-project-4-detail-48"></a>
### 9.14 六十四个数为何不一定可以随意 reshape

**问题：** 数量相同，转成一乘一乘八乘八是否保证图像正确？

**解析：** 不保证，原数据可能是不同通道顺序、列优先、转置或来自另一种空间排列。reshape 改形状不理解语义，不会自动恢复像素位置。接口应规定输入布局，单图适配只补约定维度，而不任意重排。可以用具有唯一位置编号的人工图检查每个像素映射，避免全零或对称图把错位隐藏。元素数一致是必要条件，空间身份正确还需要更强证据。

<a id="dl-project-4-detail-49"></a>
### 9.15 写出候选文件后为何不能立即宣布保存成功

**问题：** 写入没有报错，为什么还要校验与重载？

**解析：** 产物可能格式缺失、版本不匹配或对应错误时刻，进程失败还可能留下半写候选。可在同目录完整写入、校验，再更新可读入口，使旧有效版本在候选失败时仍可用。实验四只验证当前文件系统上的流程，不承诺所有断电和网络存储情形。文件存在不是有效状态证明，后续恢复与固定行为检查才对应实际功能。保存成功应有具体可核对定义。

<a id="dl-project-4-detail-50"></a>
### 9.16 模型和日志分别写入，怎样避免错配

**问题：** 进程在写模型后、写日志前失败，恢复应该信哪个？

**解析：** 需要预设提交协议，例如检查点携带已完成事件位置和状态身份，日志按该位置重放或核对；也可版本化完整包后更新入口。不能仅按修改时间较新决定，因为两文件承担不同对象，时钟也可能不可靠。恢复时明确哪些事件已提交、哪些可重复，遇同键不同值报冲突。两个文件各自完整，不代表它们一起形成同一训练时刻，事务关系必须设计。

<a id="dl-project-4-detail-51"></a>
### 9.17 重放日志怎样保持幂等

**问题：** 恢复后再次产生同运行、同更新的记录，是否简单追加即可？

**解析：** 如果同一事件被计两次，样本量、耗时与曲线都可能错误。应以运行、分支、更新及事件类型构成身份，按政策对一致重放去重，对同键不同内容拒绝或调查。配置变化后的分支用新身份，不伪装旧事件。幂等并不意味忽略所有重复，它要求同一操作重复执行不改变既定结果；数据冲突则应保留可诊断信息，而不是最后一条静默覆盖。

<a id="dl-project-4-detail-52"></a>
### 9.18 梯度累积中途能只保存普通检查点吗

**问题：** 已反向两个微批、尚未更新参数，此时保存模型和优化器够不够？

**解析：** 通常不够，还缺累积梯度、当前有效分母、微批位置及后续采样随机状态。若恢复后重新清梯度，会丢前两批；若重放却保留旧梯度，会重复贡献。可以优先在完整更新边界保存，减少复杂性；若成本要求中途保存，则将这些对象纳入状态机并演练。保存频率和状态完整性存在工程取舍，不能只增加调用次数就认为恢复更可靠。

<a id="dl-project-4-detail-53"></a>
### 9.19 非有限更新后只回退权重是否足够

**问题：** 参数恢复正常，下一步仍异常，最可能漏掉什么？

**解析：** 优化器矩、调度、随机或采样状态可能已经污染或错位。若非有限值在更新前检测并完全跳过，状态政策应明确；若更新已发生，需回到一致可信点，而非拼接旧参数与新矩。修复后比较固定下一批的前向、梯度与更新，确定恢复链正常。直接把异常数字替换为零可能改变目标并隐藏样本覆盖问题，不应无说明地当作原训练等价继续。

<a id="dl-project-4-detail-54"></a>
### 9.20 固定预测复现是否就是新泛化证据

**问题：** 保存加载前后测试 logits 完全一致，能否声称新增一次独立验证？

**解析：** 它证明函数恢复与原评价一致，没有创造新独立数据。重复对同一固定测试预测只是在复算既有结果，不能将次数当成统计样本或多次成功。前面项目的错误分析可合法复用既有预测，但用这些错误指导下一轮修改后，确认改进需要另行安排评价。实现验收、指标复算与泛化验证应分别命名，各自有价值，却不能相互冒充。

<a id="dl-project-4-detail-55"></a>
### 9.21 类别映射错误为什么数值检查也会漏过

**问题：** 十列 logits 数值完全一致，服务显示类别却不同，哪里出错？

**解析：** 列索引到类别的映射可能不同，输出张量只包含数值，没有自动附带语义。交付必须固定词表或类别顺序、后处理和版本；固定样例应检查数值与最终解释，而不只是数组形状。一个类别表的排列改变就是函数改变，尽管模型权重一字节没变。复算指标也要使用同映射，否则可能把正确预测误记为错误，或把错列在巧合样本中隐藏。

<a id="dl-project-4-detail-56"></a>
### 9.22 为什么当前项目不能承诺书写者独立泛化

**问题：** digits 图像随机分层测试表现不错，能直接推广到新书写者吗？

**解析：** 当前表没有用于划分的完整作者身份，图像级划分只支持相应图像总体的评价，不能确认训练测试书写者隔离。接口和检查点恢复正确不会弥补这个数据证据缺口。若任务关心新作者，应获取合法分组信息并重新建立协议，或明确限制。性能与恢复是两条证据轴，不能因为工程交付完整就把统计适用范围也随之扩大。

<a id="dl-project-4-detail-57"></a>
### 9.23 清理中间产物前必须确认什么

**问题：** 为保持目录整洁，可以只留权重删掉所有配置、词表与日志吗？

**解析：** 对正式研究不宜，因为其中可能包含函数与结果的必要依赖。先区分一次性临时文件和重建所需证据，独立重载核对后再清理。本文教材将完整代码和条件写进 Markdown，实验文件置于自动清理临时目录，因此资料目录不需留生成器。其他用途应按依赖图决定保留对象，不能照搬“删除全部”口号。整洁与可追溯可以兼顾，前提是知道最终结果依赖什么。

<a id="dl-project-4-detail-58"></a>
### 9.24 如何判断恢复验收是否覆盖了真实目标

**问题：** 一次测试通过，怎样说明它足够而非只是容易通过？

**解析：** 先列需要保证的行为和可能故障，再设计能让故障显现的对照。推理看输入与输出、模式和类别；续训看优化器、调度、随机及数据；事务看候选失败和事件提交。故意推进随机流、漏缓冲或使用浅别名，应被相应测试发现。没有故障敏感性的“通过”可能只是没有触发问题。最终报告同时写覆盖范围与未测组件，让后续实现者知道何时需要新增证据。

<a id="dl-project-4-detail-59"></a>
## 10. 进阶研究：建立一份可恢复的项目档案

<a id="dl-project-4-detail-60"></a>
### 10.1 五阶段综合验收

第一阶段把第 2 章实际选择的最佳状态、最后状态和验证历史对应起来，列出选择指标与两个时刻，确认报告使用的文件身份。第二阶段为原始图像入口写固定样例，覆盖单张、批量、缺通道、错误单位和非有限像素，比较预处理及最终 logits。

第三阶段独立复现本章新进程实验，解释每个保存对象，并分别去掉随机、优化器或调度状态，记录第一个分叉点。第四阶段演练候选写入失败与日志重放，确认旧有效入口和事件身份仍可用。第五阶段从最终保留产物重算一个报告表，检查类别、样本键和覆盖。

各阶段的产出是可复算证据，而不是只提交一句“测试通过”。写出原假设、输入、预期、实际、误差与限制；如果一个故障没有被当前测试发现，应修改测试设计而非将故障删掉。固定输入不变性、完整状态轨迹和事务完整性是不同层次，必须分别说明。综合验收结束后，才能知道项目到底交付了当前函数、可继续训练过程，还是两者都已具备。

<a id="dl-project-4-detail-61"></a>
### 10.2 在恢复与迁移之间作明确选择

将新设备、依赖升级、结构修改或数据清洗加入项目时，先判断目标是延续旧轨迹还是开始新版本。前者需要匹配执行状态并核对连续性，后者可以重置部分对象，但应保留迁移来源、新运行身份和重新评价。不要为了让代码运行而不断宽松加载，最后仍沿用旧报告数字；结构可载入与统计结果可继承是两个不同条件。

迁移后可以先用固定回归集合检查短期功能，再在目标分布做独立评价。若只验证 CPU 推理，就如实标明；若未来增加 GPU 或并行，继续补环境、算子与状态测试。教材提供的是能扩展的思考方式，不是一份对所有系统永久足够的保存字段清单。每新增一个影响计算的组件，都追问它的状态、生命周期、身份和验收，才能把求知转化成可靠工程能力。

<a id="dl-project-4-detail-62"></a>
### 10.3 用状态充分性证明恢复目标

可以把恢复要求写成一个有限步归纳命题：若保存的状态足以决定下一次取批、随机计算、更新和记录，恢复得到相同状态，且后续外部输入与转移实现相同，那么下一完整更新也相同；继续归纳，规定范围内所有后续状态都相同。这个证明的关键不在“保存了很多东西”，而在保存集合是否对未来转移充分。若某个未保存的游标或随机流仍影响下一步，归纳的第一步就不成立。

充分并不要求复制进程内每一个对象。实验三没有保存上一步残留梯度，因为下一步先按固定政策清空，旧值在被读取前已覆盖；也没有保存数据张量，因为固定独立生成器可以重建相同数据。这些省略都有明确理由。若改成跨微批累积，残留梯度变成必要状态；若数据来自会变化的外部文件，生成规则也不再足够。状态集合随执行协议改变，不能机械照抄字段清单。

同理，保存前后的诊断可能改变未来。训练模式验证会更新运行统计，随机可视化会消耗随机流，抽样检查会移动数据游标。若它们属于规定流程，就应将相应变化纳入状态时刻；若只用于观测，应隔离或恢复副作用。观察程序不是天然透明的，尤其当日志函数顺便调用模型时。将记录职责与训练转移分开，能够减少“加一句调试代码就无法复现”的隐蔽耦合。

<a id="dl-project-4-detail-63"></a>
### 10.4 给每一种等价选择适当验收

参数逐项相等比当前预测相等更强，但仍不自动包含优化器和未来输入；当前预测在有限样例上相等，又弱于对所有合法输入函数相同。跨设备若只能保证容差，应说明数值和任务行为要求；重复种子得到相近统计质量，则是另一种分布性复现。层次之间不能直接推出更强命题，也不必为了只需推理的用途强求恢复全部研究轨迹。

一个可审阅结论应写出对象、条件、比较集合和误差政策，例如“同软件 CPU、同下一批和随机状态、十二次更新的全部已列状态逐项相同”。这句话范围有限，却能被别人实际检验。只写“完全可复现”虽然简短，反而隐藏了设备、数据和状态假设。把等价拆清楚之后，读者才能知道如何扩展实验、哪些新组件会破坏已有证明，以及下一轮需要补什么证据。

若保存点后的外部数据顺序允许变化，验收目标也要相应调整。相同模型状态但接收另一批输入，本来就可能更新不同，不应把正常输入变化误报为加载失败。先用固定下一批隔离恢复，再用实际管线检验端到端顺序与覆盖；两个步骤逐层增加条件，才能定位首个分叉。实验中即便最终准确率偶然一样，也不能反推全部内部轨迹一致，因为不同参数完全可能在有限样本上给出同样离散判断。
