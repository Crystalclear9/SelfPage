## 1. 聚合必须说明统计单位

<a id="pd2-unit"></a>

### 1.1 行、订单、用户与群体是不同分母

`groupby`将记录按键划分，再对组内值执行聚合。语法上只是几行代码，统计上却在重新定义样本单位。订单表按用户求和后，一行从一笔订单变成一位用户；按用户与月份分组后，一行变成一个用户月份。相同的金额列，在不同粒度下求平均，会得到不同权重体系，因此必须先写出要估计的量。

假设用户甲有两笔订单，金额十元和三十元；用户乙只有一笔五十元。按订单平均金额为九十除以三，即三十元。先算用户内平均再对用户平均，结果为二十与五十的均值，即三十五元。两个结果并不矛盾：前者随机抽一笔订单，后者随机抽一位用户再在其订单中平均。活跃用户在前者权重更高，在后者每人权重相同。

用户总消费的平均又是另一种量：两位用户总额分别四十和五十，均值四十五元。把“人均消费”“单均金额”“用户平均单价”都简称为平均消费，程序就可能计算出正确数字却回答错误问题。指标定义应包括事实粒度、筛选范围、分子、分母、缺失处理和时间口径，不能只留下一个聚合函数名称。

如果订单表只包含发生交易的用户，按用户平均描述的是活跃交易用户，不是所有注册用户。要估计全体注册用户的人均消费，需要先定义用户全集，再把无交易用户的消费按业务含义补零。没有记录与记录金额未知仍是不同状态，不能仅因连接后出现空值就自动认为零消费。

<a id="sec-1-1"></a>

### 1.2 基础算例：连接后核对金额为什么翻倍
用户甲有两笔订单十元和二十元，属性表里甲有两条不同记录。按用户键连接时，每笔订单各匹配两次，得到四行十、十、二十、二十，总额由三十变成六十。程序没有算错加法，连接也没有违背多对多关系的定义，真正的问题是你把原本订单级金额当成展开后每行独立金额。

若目标是一行一订单的训练表，右侧应先成为每用户唯一的合法属性映射，再执行多对一连接。若右表两行表示两个兴趣类别，展开可能是有意的，但输出粒度变成订单与兴趣的配对；后续金额统计与训练权重都需要重新设计。不能只删除重复金额，因为不同订单可能恰好同金额，也不能用最终行数等于原始行数作为唯一验收。

还要问属性的版本是否正确。右表保留最新一条可以让键唯一，却可能把用户今天的等级写到去年样本。连接基数与时间合法性是两个独立维度；`validate`能检查前者的一部分，不能判断后者。先把本章的基数关系弄清，再进入后续章节的时点匹配，才能避免“键对了所以一切正确”的误解。

<a id="pd2-size-count"></a>

### 1.3 size、count、sum 与全缺失组

`size`计算组内行数，不因某个值列缺失而减少；`count`对指定列计算非缺失数量。三条订单金额为十、缺失、零，行数为三，金额有效数为二。均值默认以有效金额数为分母，不能把`count`不加解释地命名为订单数，否则遇到缺失时指标就悄悄从订单数变成已知金额订单数。

求和还有一个重要边界：一个组金额全部缺失时，默认求和可能得到零。这适合某些代数约定，却可能把“完全未知”误当“确实没有金额”。通过`sum(min_count=1)`可以要求至少一个有效值，否则保留缺失。要区分没有订单、订单全未知与已知零订单，通常需要同时保留行数、有效数和金额和三个统计量。

组内缺失如何进入指标还取决于定义。金额总和可以只对已知部分计算并报告覆盖率；总订单平均金额若要包含未知订单，就需要额外缺失假设，不能只换个分母。用已知金额和除以全部订单数，实际上把未知贡献按零处理，即使你从未显式调用`fillna(0)`，也隐含实施了补零。

同理，计数与唯一计数也不同。`nunique`统计不同值的数量，并有缺失是否计入的选项；它不是判断主键完全正确的替代。某个组里一百行只有九十个订单号，可能有重复导出，也可能是一单多商品。必须知道输入粒度，才能决定该用行数、订单唯一数还是先聚合后的订单数。

[打开原图放大](images/02-merge-valid-count-and-sum-before-dividing.webp)

图中两组原始记录分别是 A 的一条 10 与 B 的三条 20。箭头先把每组压缩为“有效计数、总和”，分别得到 $`(1,10)`$ 与 $`(3,60)`$；合并时两项各自相加，得到 $`(4,70)`$，最后才计算 $`\frac{70}{4}=17.5`$。组均值十和二十虽然足以描述各组中心，却没有保存 B 的三条记录这一权重，直接再平均得到十五。

这不是某个函数的精度差异，而是两种抽样单位：每组等权与每条原记录等权。若分区 B 再拆成三份，保存计数与总和仍得到相同总体均值；只平均分区均值却可能随拆分方式变化。这里的计数必须与总和使用同一有效集合，金额缺失时不能用总行数替代有效金额数；全组无有效值时应保留零计数并明确均值未定义。若统计目标本来就是等权的组平均，十五可以正确，但它不能被称为原记录总体均值。

### 1.4 缺失分组键、类别全集与输出顺序

Pandas 分组默认可能排除分组键缺失的行；若需要保留未知群体，显式使用`dropna=False`。金额总和从原表汇总后突然变小，可能不是金额计算错误，而是缺失键的记录根本没进入任何输出组。分组前后对账时应把这项筛选写进条件，而不能默认 groupby 覆盖了全部输入。

类别型分组还需要明确只输出实际观察到的组合，还是输出允许类别的全集。`observed=True`表达只考虑观察组合，`False`可以包含未观察类别；不同版本默认可能变化，本章显式传参。未观察类别的输出可能有零计数或不同聚合结果，不能把它与真实观察到但金额为零的群体混同。

`sort`控制组键的输出排列，不等同于组内时间排序。关闭排序可以避免无关的键排序成本，但不会自动保证每组记录已按业务时间排列。`first`、`last`等依赖顺序的操作，必须先定义顺序；其中某些聚合还会按列跳过缺失，得到的多个字段未必来自同一原始行。需要完整首条记录时，应先排序，再用保留整行的规则选择。

![逐列取首个非缺失值时，两个字段分别来自第二行与第一行](images/02-groupby-first-picks-values-from-different-rows.webp)

[打开原图放大](images/02-groupby-first-picks-values-from-different-rows.webp)

**完整记录与字段拼接的最小反例。** 同一用户的两条记录按时间为 $`(a,b)=(\mathrm{NA},3)`$、$`(1,\mathrm{NA})`$。按列选择首个非缺失值会得到 $`(1,3)`$，两个字段分别来自第二行与第一行。排序正确仍不足以把这个结果解释为“第一条实际观测”。需要保留整行时，可在明确排序后按组取首条行，例如选择相应的 `head(1)`；是否保留空分组、索引及并列次序仍要显式约定。若确实需要字段级最近可见值，应另保留每个字段的来源时刻，不能只给拼接记录盖一个统一时间戳。接口的逐列选择与 skipna 规则见 Pandas GroupBy.first。

输出索引也需要约定。`as_index=False`常适合后续连接的普通列结果，`as_index=True`则把分组键放入索引；两者可表达同样的关系，但下游赋值和对齐方式不同。不要为了让代码跑通不断调用重置索引，应先确认输出的键、唯一性与预期粒度。

```python
import pandas as pd
orders = pd.DataFrame({
    "user": pd.Series(["A", "A", "B", "B", pd.NA], dtype="string"),
    "amount": pd.Series([10, pd.NA, pd.NA, pd.NA, 7], dtype="Int64"),
})
g = orders.groupby("user", dropna=False, sort=False, observed=True)
summary = g.agg(rows=("amount", "size"), valid=("amount", "count"))
summary["known_sum"] = g["amount"].sum(min_count=1)
assert summary.loc["A", "rows"] == 2 and summary.loc["A", "valid"] == 1
assert pd.isna(summary.loc["B", "known_sum"])
assert int(summary["rows"].sum()) == 5
assert int(summary["known_sum"].sum()) == 17
assert int(orders.groupby("user", dropna=True)["amount"].sum().sum()) == 10
print(summary)
```

### 图解：一对多连接使金额重复

连接后为什么每笔订单还在，总金额却翻倍？先给订单保留身份，再枚举它与属性记录形成的每一对。

![同一用户的两笔订单与两条属性记录产生四个匹配对](images/02-two-orders-and-two-attributes-form-four-pairs.webp)

[打开原图放大](images/02-two-orders-and-two-attributes-form-four-pairs.webp)

**先固定行、列的来源身份，再数格子。** 行轴是两笔不同订单 O1、O2，列轴是同一用户 u 的两条属性 A、B。一个格子对应一个合法匹配对，所以 O1 生成 `(O1,A,10)`、`(O1,B,10)`，O2 生成 `(O2,A,20)`、`(O2,B,20)`。两行乘两列得到四条输出；每个来源金额沿所在行出现两次，合计由三十变成六十。它没有生成四笔真实订单，只展开了四个关系配对。

这个画法借鉴 Pandas 官方多对多连接示例图中保留左右来源和结果重数的方法，再把输出摊成笛卡尔网格，使每一份金额从哪里重复直接可见。对一般键 k，左右重数为 $`a_k,b_k`$ 时，内连接产生 $`a_kb_k`$ 行。左连接只为无匹配的左行补空，不会把成功匹配的多条右行自动合成一条。

**改变左表粒度，仍可能保留右表放大。** 先把 O1、O2 聚成用户总额三十，再连接 A、B，仍然输出三十、三十，总和六十。因此预聚合只有在输出粒度、连接基数与所需统计量一致时才合法，不能代替选择正确属性版本。若 A、B 是历史记录，应按预测时点和可见性选定版本；若业务确实允许多标签展开，则须明确展开后的计分权重。

验收时先写身份不变量，例如“每笔订单恰有一个有效属性”，核对右键唯一性并采用 `validate="many_to_one"`，再共同检查覆盖、行数和金额。按金额去重可能误删金额相同的不同订单；仅检查总和又可能被其他误差抵消。图中的 u 键相同且字段非空，未展开空键匹配、类型转换与时间版本边界，它们应按实际数据协议另行核对。

## 2. 连接为什么会突然增加行数

<a id="pd2-cardinality"></a>

### 2.1 从匹配计数推导连接行数

对某个连接键值 k，设左表有 n 个匹配行，右表有 m 个匹配行。等值内连接输出 n 乘 m 行，因为每个左行都与每个右行配对。把所有键的这个乘积求和，就得到总行数；它说明多对多膨胀不是偶发 bug，而是关系连接的基本组合结构。表越大，越应该在真正连接前用键频数估计潜在输出规模。

![一笔一百元订单匹配两条标签后，同一金额出现在两个结果行](images/02-one-order-matches-two-rows-and-repeats-its-amount.webp)

[打开原图放大](images/02-one-order-matches-two-rows-and-repeats-its-amount.webp)

一条金额一百的订单匹配两条标签，因此输出两行都带着同一笔金额。直接对连接后的金额求和会得到二百，增加的是匹配重数而非真实交易。连接前应声明左右粒度和键唯一性，需要多对一时用验证约束拒绝重复键，而不是连接后随意去重掩盖问题。

把左、右键频数分别记作 $`n_L(k)`$ 与 $`n_R(k)`$，则行数公式为

```math
\begin{aligned}
N_{\mathrm{inner}} &=\sum_k n_L(k)n_R(k),\\[6pt]
N_{\mathrm{left}} &=\sum_{k:n_L(k)>0}n_L(k)\max\{1,n_R(k)\}.
\end{aligned}
```

证明可按键分割配对集合：不同键的输出互不重叠，同键内是两个行集合的笛卡尔积，大小为频数乘积；左连接对右侧空集合补一个缺失占位。公式适用于这里讨论的普通等值匹配，并把 Pandas 实际能匹配的缺失键纳入相应键组。它不是非等值范围连接的通用行数公式。

对左连接，若某个左键在右表没有匹配，每个左行仍保留一行，右侧字段为空；若有匹配，则复制 m 次。因此该键贡献 n 乘以 m 与一的较大者。只要右键唯一，m 不超过一，左连接就保持左行数；如果右键重复，即使部分左行不匹配，也仍可能增加总量。行数不变也不保证身份正确，因为复制与后续删除可能相互抵消。

复合键的推理完全相同，只是 k 变成字段元组。例如用户与月份唯一，不意味着用户单列唯一；只按用户连接，会把不同月份组合起来。键应根据目标关系完整选择，不能看哪个字段名字相同就拿来连接。`on`应显式声明，避免默认使用所有同名列导致连接条件随表模式变化。

对极端热点键，输出可以远大于两张表行数。例如左右各十万条未知身份，若未知键可匹配，将产生一百亿组合。不能把机器内存不足简单当作计算资源问题；应先检查是否定义了错误关系。合理的规模预估既是性能优化，也是数据语义检查。

<a id="sec-2-1"></a>

### 2.2 机制展开：多对一验证检查的是键关系

`validate="many_to_one"`要求右表连接键唯一，允许左表重复；`one_to_many`相反；`one_to_one`要求两边唯一；`many_to_many`允许多对多，并不会帮你拒绝膨胀。关系应从业务定义推出来，不应在验证报错后逐步放宽直到程序通过。报错意味着输入与声明冲突，需要调查原因。

右键唯一与左表业务键唯一是不同要求。订单表可有多单对应一个用户，所以按用户连接属性时左连接键不唯一是合理的；但订单编号作为输出样本键仍应唯一。连接验证只围绕传入的连接键，不知道哪个字段才是你的样本身份，因此还需独立检查样本键集合、顺序和列值来源。

`indicator=True`会添加匹配状态，便于统计左侧独有、右侧独有与匹配行。左连接看不到纯右侧独有的行，因为它们没有进入输出；若要做双向键对账，可以对键集合做外连接。匹配率的分母也要注明：按输出行计算会被重复匹配影响，按原始样本键计算更适合回答多少样本取得属性。

验证不检查字段内容可信度。唯一的用户属性也可能来自错误来源、具有非法类别或过期版本；全部匹配也可能是编号规范化把不同用户合并了。因此，基数验证应与第一章的数据契约衔接，把键类型、规范化碰撞、值域和时间含义一起检查。

<a id="deep-dive-2"></a>

### 2.3 深入讲解：连接基数如何改变样本权重与聚合结果

假设原始训练损失是每个样本损失之和除以样本数。连接后第 i 个左样本复制了 m_i 次，若每个复制行使用相同特征和标签，新的经验损失等于按 m_i 加权的旧损失，再除以总复制数。也就是说，连接偷偷实施了样本重加权；某些用户属性版本多，就在训练里获得更大影响。

令原始损失为 $`\ell_i(\theta)`$，复制次数为正整数 $`m_i`$，则复制后的平均经验风险是

```math
\widehat R_{\mathrm{expanded}}(\theta)
=\frac{\sum_{i=1}^{n}m_i\ell_i(\theta)}{\sum_{i=1}^{n}m_i}.
```

将所有 $`m_i`$ 同时乘一个常数不会改变这个平均，但不同样本的相对倍数会改变优化目标。即使每个样本统一复制，若训练目标另外包含一个未按同样归约调整的正则项，使用求和损失的实现也可能改变数据项与正则项的相对强度。因此，讨论复制是否无影响时，还要说明求和还是均值以及正则系数的约定。

这个等价要求复制行的损失相同。如果不同右侧记录带来不同属性，复制后的特征也不同，此时不只是重加权，而是构造了多个可能矛盾的样本。对树、线性模型和概率校准的影响都不能用一个简单倍率修正。应回到属性关系，决定是多值特征、合法展开还是错误历史版本，而不是事后把训练损失除回原行数。

金额统计同样如此。若所有左行被相同倍数复制，平均值可能保持不变，总和会放大；若复制倍数与金额相关，平均值也改变。一个平均数看起来正常，不能说明连接没问题。某些评价指标对整体重复不变，但交叉验证若把同一事实的复制行拆到训练与验证，还可能形成身份泄漏，导致更深的问题。

若有意展开为商品或兴趣配对，可以为同一左样本的复制行分配总和为一的权重，保留某些总量。但这也不是通用修复：不同特征的训练目标、相关性结构与有效样本量仍改变。权重守恒只解决你明确声明的加总问题，不自动恢复原始任务的统计独立性。

<a id="pd2-join-experiment"></a>

### 2.4 连接实验：让错误基数先失败

代码依赖 pandas。第一轮故意让右表存在重复键，观察连接后行数和金额怎样膨胀。第二轮用符合业务规则的唯一键维表和 `validate` 约束核对结果，最后通过连接标志检查右表还有哪些键没有订单。

```python
import pandas as pd
orders = pd.DataFrame({"order": [1, 2, 3], "user": ["A", "A", "B"],
                       "amount": [10, 20, 50]})
bad_users = pd.DataFrame({"user": ["A", "A", "B"], "tier": ["old", "new", "basic"]})
expanded = orders.merge(bad_users, on="user", how="left", validate="many_to_many")
assert len(expanded) == 5 and expanded["amount"].sum() == 110
try:
    orders.merge(bad_users, on="user", how="left", validate="many_to_one")
except pd.errors.MergeError:
    pass
else:
    raise AssertionError("重复右键必须违背多对一契约")
# 这里直接给出一个经过业务确认的属性快照，不用任意删重制造快照。
users = pd.DataFrame({"user": ["A", "B", "C"], "tier": ["new", "basic", "basic"]})
joined = orders.merge(users, on="user", how="left", validate="many_to_one", indicator=True)
assert len(joined) == 3 and joined["order"].is_unique
assert joined["amount"].sum() == 80 and joined["_merge"].eq("both").all()
keys = orders[["user"]].drop_duplicates().merge(
    users[["user"]], on="user", how="outer", validate="one_to_one", indicator=True)
assert keys["_merge"].eq("right_only").sum() == 1
print("原始3行80元；错误连接5行110元；合法快照连接保持事实")
```

## 3. 时间特征只能使用当时已知的信息

<a id="pd2-information"></a>

### 3.1 键匹配、数据划分与信息可见性是三种约束

一张训练表至少需要同时满足身份正确、划分合法、信息可见三类约束。身份正确意味着特征和标签属于同一个预测对象；划分合法意味着验证方案模拟部署时面对的新时间、新实体或新来源；信息可见意味着特征在预测时已经可获得。通过其中一项，不能推导另外两项。

用户今天的总消费与用户明天是否购买，键可以完美匹配，但如果总消费包含明天订单，特征就使用了未来信息。某个字段记录的是事件发生时间，实际数据两天后才入库，按事件时间过滤仍可能在历史回放中使用当时不可见的记录。后续章节会展开时间窗口与可用时间，本章先把这种边界纳入分组与连接的思考。

静态数据也有泄漏。先对全表按用户算标签均值，再随机分行训练测试，每个测试标签可能进入自己的特征，训练标签还可能进入同用户测试特征。即使只算输入均值，若部署面对完全新用户，使用测试用户的整批记录也改变了任务设定。是否允许批量无标签信息，应明确为归纳或允许传导的评价协议。

因此，不要把“没有直接连接标签列”当作无泄漏证明。应追踪每个统计量的来源行、参数拟合范围、事件时间、可用时间和划分归属。这个追踪可称为信息依赖图：最终特征依赖哪些输入与拟合参数，每条依赖在预测时是否可访问。复杂流程里，这比只审查最终列名更有力量。

<a id="pd2-target-encoding"></a>

### 3.2 目标统计：留一法不等于完整的折外方案

类别目标均值常被用作编码。若某个类别只有一个训练样本，直接使用组标签均值就等于把它自己的标签写入特征。留一法排除当前标签可以减轻直接自引用，但它仍可能与模型选择、时间顺序或其他相关样本形成依赖，不能把“去掉自己”当作所有评价设计都安全的通行证。

折外编码在训练部分再划分若干内部折，每个内部验证折的编码只用其他内部训练折标签估计；最终外部验证或测试编码只用整个外部训练集拟合的统计。若存在用户相关性，内部折也应按用户分组；若是预测未来，内部计算还应符合时间方向。编码规则需要跟随任务划分，不能机械套用随机折。

平滑编码把类别均值向全训练均值收缩，以减少小组方差。常见形式是类别标签和加上平滑强度乘全局均值，再除以类别样本数加平滑强度。这个形式需要明确全局均值来自哪部分数据，平滑强度如何选择，未知类别如何回退。参数选择本身也要处于合法的内部验证边界。

这里只建立编码的信息边界，不要求立即实现完整目标编码器。读者应能画出某条训练样本编码与哪些标签相连，并指出外部测试标签没有进入任何拟合参数。如果做不到这一点，代码即使只有一个漂亮的`transform`调用，也不应被视为可靠。

<a id="sec-4"></a>

## 4. 聚合前后核对守恒量

<a id="pd2-invariants"></a>

### 4.1 行数、身份、金额与覆盖分别约束什么

聚合通常减少行数，所以不能要求输出行数等于输入行数；可以要求各组行数之和等于进入聚合的输入行数，要求组键唯一，要求可加指标在相同缺失与筛选口径下守恒。连接若声明多对一左连接，则可要求左样本身份集合和数量不变；内连接允许丢行，但必须解释被排除身份及其特征。

金额守恒并不能替代身份守恒。漏掉一笔十元、复制另一笔十元，总金额不变但事实错误；身份集合正确也不能排除金额赋错人。因此，验收应组合多个不变量：样本标识唯一、集合覆盖、关键数值和、非缺失数量、类别分布和来源匹配。每一个不变量都对应一种可能错误，而不是为了堆更多断言。

浮点加总需要允许合理舍入误差，整数最小货币单位可以使用精确比较。不同求和顺序可能带来微小差异，但百分之几十的金额变化不应被“浮点误差”解释。容差应根据数量级和算法给出，而不是发现断言失败后不断放宽。对财务类数据，表示与舍入协议应该在第一章清洗阶段就确定。

过滤也要进入账本。若删除退款订单、缺失用户键或非法金额，就把它们作为单独分区统计，说明原始总量如何分解为保留、排除与未知部分。只报告最终金额和最终行数无法解释流程，质量问题发生时也难以定位是哪一步改变了口径。

<a id="pd2-coverage"></a>

### 4.2 匹配率、事实覆盖率与属性完整率

连接后的`_merge`显示是否找到右键，但匹配不代表每个属性都有值。用户记录存在而地区字段缺失，与用户根本没有属性记录不同；两者应分别统计。样本匹配率、用户匹配率和金额覆盖率也可能不同：高价值用户属性缺失时，行级匹配率很高，金额覆盖却可能很低。

例如一百笔订单中只有一笔没有用户属性，但该单占总金额一半。按订单匹配率为百分之九十九，按金额覆盖率仅百分之五十。报告哪一个更合适取决于任务，应尽量并列展示而不是选择最漂亮的指标。若缺失与目标、来源或价值相关，直接删除未匹配记录会改变研究总体。

右侧还有多少用户未被订单使用，也值得检查，但那是另一个问题。左连接输出不会呈现右侧独有键，所以不能从`_merge`没有`right_only`推出右表没有多余用户。需要双向覆盖时，对去重后的键集合做外连接，分别统计两个方向；如果右表本来就是注册用户全集，未交易用户通常是合法存在。

<a id="sec-5"></a>

## 5. transform 与 agg 的输出粒度

<a id="pd2-agg-transform"></a>

### 5.1 聚合表与行级广播各自回答什么

`agg`把每组压缩成统计结果，通常每组一行；`transform`把组统计或同形变换映射回原行，结果与原输入行索引对应。用户金额均值可用两者计算，但前者得到用户表，后者得到每笔订单附带用户均值。输出粒度不同，所以随后继续求和或平均时，权重也不同。

对前面的两用户例子，用户均值二十与五十的简单平均是三十五；把均值广播回订单后得到二十、二十、五十，再平均是三十。广播并不是无害的显示便利，它把用户统计重复了用户订单数次。若目标是用户均值的平均，应在用户表上计算，或显式使用每用户总权重一致的权重，而不是在广播表上直接平均。

训练特征常需要保持原行粒度，`transform`很合适，但仍要验证信息边界。对全部历史按用户计算均值再回填每个历史样本，会包含未来记录；对标签求均值还会包含自身标签。API 保持行数并不等于任务合法。应先明确可用记录范围，再选择以`agg`后连接还是`transform`输出。

`agg`后连接与`transform`的等价需要组定义、缺失键处理、排序和对齐一致，并且聚合结果对组键唯一。若一个流程默认排除缺失键，另一个保留，结果就不等价；若连接使用了不完整的复合键，也可能膨胀。可在小样本上按稳定行标识比较结果，但不能只比较平均值相同。

<a id="pd2-apply"></a>

### 5.2 apply 的灵活性与更强的输出责任

`apply`允许对每个组运行更一般的函数，输出形状可以复杂得多，因此也更难自动推理。能用内置聚合或变换表达的任务，通常优先使用那些有明确输出契约的接口；这有利于性能和可审计性。`apply`并不是更高级就更正确，它只是把更多结构责任交给函数作者。

Pandas 2.3.3 中，DataFrame 分组`apply`对分组列是否传入函数涉及迁移行为；需要使用时显式考虑`include_groups=False`等版本参数，并在固定版本测试。不要把不同版本里的警告简单屏蔽掉，因为它可能提示函数输入列集合即将改变。还要明确`group_keys`、返回索引以及最终是否形成多级索引。

自定义函数应返回约定字段、类型与行关系，不要在组内修改共享外部状态。组处理顺序通常不应该影响统计结果；若函数通过全局列表累计状态或依赖调用次数，就难以验证并行化与重排后的等价性。尽量让函数只依赖当前组与显式固定参数，输出可单独检查的结果。

对复杂任务，可以先写一个容易理解的参考实现，再用向量化或内置运算优化，并逐行对照。性能优化应保持语义契约，而不只是最终数值接近。尤其是缺失、全空组、单元素组和重复键，往往是优化版与参考版不等价的地方，应该进入小型反例集。

<a id="pd2-transform-code"></a>

### 5.3 广播实验：相同均值为何产生不同平均

在安装 pandas 的环境中运行。先用聚合得到每个用户一个均值，再用 `transform` 把均值广播回订单。输出的 35 对用户等权，30 对订单等权，两者的权重差来自各用户拥有的订单数。

```python
import pandas as pd
from pandas.testing import assert_series_equal
orders = pd.DataFrame({"user": ["A", "A", "B"], "amount": [10., 30., 50.]}, index=[8, 2, 5])
mean_per_user = orders.groupby("user", sort=False, dropna=False, observed=True)["amount"].mean()
broadcast = orders.groupby("user", sort=False, dropna=False, observed=True)["amount"].transform("mean")
assert mean_per_user.mean() == 35 and broadcast.mean() == 30
assert broadcast.index.equals(orders.index)
reference = orders[["user"]].assign(row_id=orders.index).merge(
    mean_per_user.rename("user_mean"), left_on="user", right_index=True,
    how="left", validate="many_to_one").set_index("row_id")["user_mean"]
assert_series_equal(broadcast.rename("user_mean"), reference.rename_axis(None))
print("用户均值平均35，广播后订单权重平均30")
```

### 图解：agg 与 transform 的输出粒度不同

![组汇总按用户输出，回填则按订单输出并重复同组汇总值](images/02-group-aggregate-and-broadcast-back-to-order-rows.webp)

[打开原图放大](images/02-group-aggregate-and-broadcast-back-to-order-rows.webp)

**沿图右三条订单追踪回填的结果。** `transform` 将 u 的组总额三十回填到两条 u 订单，v 的五回填一次，所以新列之和为 $`2\times30+1\times5=65`$，不是原金额和三十五。一般地，第 g 组有 $`n_g`$ 条记录、组总量为 $`S_g`$，回填列总和为 $`\sum_g n_gS_g`$；这不是重复计算实现错误，而是输出粒度从组回到了行。

如果目标是用户总额之和，应在用户粒度合计一次，或按明确用户身份去重后再求和；若目标是每条订单附带用户上下文，回填则合理。不要把同名的 sum 当作跨粒度的守恒证据。聚合与同形变换的输出约定可核对 Pandas GroupBy transform。

三笔订单分属 u、u、v，金额为 10、20、5。agg 生成两条用户级记录 u=30、v=5；transform 将同一组总额回填到每条原始订单，得到 30、30、5，因此仍有三行。相同用户的订单连到同一个汇总值，用户 u 的三十来自十和二十。两条回填箭头从同一个三十出发，分别回到 O1 与 O2；它们增加的是附带统计的出现次数，没有增加真实交易。图中的箭头说明同一分组统计的两种输出组织，不能把 transform 回填列再按订单求和当作原始总额。

transform 列若再跨订单直接求和，会把 u 的 30 计算两次，得到 65 而非原始金额 35。图中的重复是按契约广播，不代表重复订单。

## 6. Pandas 与 SQL 对空连接键的差异

<a id="pd2-null-key"></a>

### 6.1 未知身份不能凭空变成同一身份

Pandas `merge`可以把两侧为空的键匹配起来；常见 SQL 普通等值连接不会把两个 NULL 判为相等。这里讨论普通等值连接，数据库还可能提供专门的空值安全比较，不能笼统声称所有 SQL 操作都禁止空匹配。跨系统翻译时应把这种语义差别作为显式测试，而不是只对正常键样本比较结果。

业务上两个未知用户编号通常不表示同一位用户。若左侧有两条空键、右侧有三条空键，空键组就可能产生六个匹配。空值带来的膨胀既影响资源，也可能把不相关人的属性或标签混在一起。即使右侧仅一条空键而多对一验证通过，也不说明这种身份映射合理。

一种常见规则是右表空键不参与匹配，左表空键保留但属性未知；这可以通过先排除右侧空键再左连接实现。另一种规则是两侧空键都不应进入事实表，应先隔离。如果业务确实把一个特殊空键表示“全局默认配置”，则可以允许匹配，但这已是不同的键协议，需要避免与真正未知身份混用。

把缺失键统一填成同一个字符串哨兵并不能自动解决问题，因为它仍会把所有未知身份连到一起，还可能与合法编号冲突。若只是需要临时区分输入行，可以生成不冲突的行标识，但这种标识不能用于跨表识别同一真实实体。身份缺失的问题需要数据来源或任务规则解决，不能靠换一个表示就消失。

```python
import pandas as pd
left = pd.DataFrame({"key": pd.Series(["A", pd.NA, pd.NA], dtype="string"), "v": [1, 2, 3]})
right = pd.DataFrame({"key": pd.Series(["A", pd.NA, pd.NA], dtype="string"), "tag": ["known", "x", "y"]})
expanded = left.merge(right, on="key", how="left")
assert len(expanded) == 5
safe = left.merge(right.loc[right["key"].notna()], on="key", how="left",
                  validate="many_to_one", indicator=True)
assert len(safe) == 3
assert safe.loc[safe["key"].isna(), "tag"].isna().all()
assert safe["_merge"].eq("left_only").sum() == 2
print("空键默认匹配产生5行；右侧空键不匹配保留3行")
```

<a id="pd2-composite-null"></a>

### 6.2 复合键、类型转换与缺失集合

复合键中部分字段缺失时，同样需要明确是否允许匹配。用户编号已知但月份缺失，不应自动理解为该用户所有月份；用户编号缺失但地区已知，也不能说明同地区的未知用户是同一人。普通等值匹配与通配规则是不同关系，若需要默认值或层级回退，应作为独立步骤设计，不能靠缺失值自然实现。

连接键的类型也应一致。字符串编号“零零一”和整数一在业务上可能相同，也可能不同；应先根据协议规范化，验证碰撞，再连接。临时将两边都转字符串虽然可能绕过类型报错，却会生成诸如缺失字面量字符串等新问题。更可靠的是在入口建立相同的键类型与缺失表示，并对标准化后的唯一性重新检查。

空键组的统计也不要只看数量。若某个来源大量丢失关键字段，删除空键可能让该来源在训练中消失。隔离后仍需按来源记录覆盖，必要时修复上游或限制结果适用范围。拒绝错误匹配是必要步骤，但它并不能独自消除由于缺失身份而产生的选择偏差。

## 7. 进阶：连接基数与聚合交换的条件

<a id="sec-7-1"></a>

### 7.1 连接基数决定特征表是否仍是一行一个样本

可以把样本表视为一个以样本标识为主键的关系。向它附加用户特征时，右表必须对用户连接键提供至多一行，才能保持原主键唯一；若样本按用户与预测日期定义，右表仅按用户唯一也未必表达正确版本。关系约束告诉我们输出是否仍是同样的样本集合，时间约束告诉我们附加信息是否合法。

有意的一对多展开需要重新定义样本。例如一笔订单展开为多个商品，订单标签可能复制到商品行，但预测任务已经从订单风险变成带有商品上下文的样本问题。若模型最终仍对订单决策，需要说明商品级输出如何汇总、训练如何分配权重、评价如何按订单计算。展开后的行数不是独立事件数，不能直接拿来宣称数据规模增加。

同一实体的重复快照也会产生相关性。即使样本键由用户与日期组成而保持唯一，随机按行划分仍可能让同一用户的相邻快照跨训练测试出现。是否错误取决于部署对象；如果部署会遇到已知用户的未来状态，时间划分比完全按用户隔离更贴近任务；如果部署面对新用户，则需要按用户划分。粒度、划分与信息边界要共同定义。

<a id="pd2-commutation"></a>

### 7.2 什么条件下可以先聚合再连接

设事实表每行是一笔订单，属性表对用户键唯一，且属性值在本次分析范围固定。若先按用户求订单金额和，再附加用户地区，与先把地区附到每笔订单、再按用户及地区求和，可以得到相同的每用户金额。关键条件是属性不复制事实、分组保留足够键、筛选口径相同、缺失组处理相同，聚合函数也具有可组合结构。

若最终只要地区金额和，也可以先算用户和，再按地区求和，因为加法可结合。但如果要地区订单平均，不能简单平均用户平均；必须保留每用户金额和及有效订单数，再用总和除以总有效数。先聚合并没有错，错在丢掉了合成最终统计所需的充分信息。

方差也类似。单靠组均值与组内方差不足以不加条件地拼出总体方差，还需要组样本数和均值差异。一个常见稳定合并公式包含组内离差平方和与组间均值偏移项；若仅平均各组方差，会丢失群体间差异。中位数和分位数一般不能由各组中位数及计数精确合成，需要保留更多分布信息或使用有误差保证的摘要结构。

方差的合成可以精确写出。第 j 组有有效数 $`n_j`$、均值 $`\mu_j`$ 和离差平方和 $`M_{2,j}`$，总体有效数为 $`N=\sum_jn_j`$，总体均值为 $`\mu=\sum_j\frac{n_j\mu_j}{N}`$，则

```math
M_2=\sum_j\left[M_{2,j}+n_j(\mu_j-\mu)^2\right].
```

推导只需把组内每个偏差写成 $`(x-\mu_j)+(\mu_j-\mu)`$，平方展开后交叉项之和为零，因为组内偏差和为零。总体方差可按目标分别除以 N 或在适用样本设定下除以 N 减一。这个证明说明，组间项不是可选修饰，而是由平方展开必然出现；只平均组内方差就把群体均值差异删掉了。

筛选也可能破坏交换。先按用户汇总后只保留总额大于一百的用户，与先删除单笔金额不超过一百的订单再汇总，显然是不同规则。属性随订单变化、连接本身有未匹配、聚合丢失了所需连接键时，交换更不能默认成立。优化之前应写出两条流程的等价条件，再用反例验证条件缺失时确实会失败。

<a id="pd2-functional"></a>

### 7.3 函数依赖与可加指标提供一种证明语言

“用户决定地区”是一种函数依赖：在给定快照中，同一用户键对应唯一地区。它允许把地区视作用户的属性，并帮助证明某些聚合与连接的交换。若同一用户同时属于多个地区，依赖不成立，必须决定是多值关系、不同时间版本还是数据错误。证明里不能把需要验证的依赖偷偷当成事实。

对可加指标，事实层的每一项只要被保留一次，分组总和就守恒。对半可加指标，例如账户余额，沿账户可以求和，沿时间通常不能直接求和，因为余额是存量而非流量。对不可加指标，例如比率和分位数，需要保留相应分子分母或分布信息。字段是数字不意味着它在任意维度上可加。

连接维度表之前，可以列出函数依赖与指标归属：订单决定用户及订单金额，用户在某一有效版本决定地区，商品行决定数量及明细金额。这个小型关系说明比一段复杂代码更容易暴露重复计数。如果一个指标没有明确归属层级，就应先停止汇总，补全它的业务定义。

<a id="pd2-weighted"></a>

### 7.4 加权统计：权重究竟代表频数、重要性还是抽样设计

加权均值的形式是各值乘权重的和除以权重和，但形式相同不表示解释相同。订单数作为权重可以把用户均值还原为订单均值；抽样概率倒数作为权重试图恢复目标总体；业务价值权重则定义另一种偏重高价值对象的目标。应注明权重来源、单位、是否允许负值、如何处理缺失以及归一化口径。

若值缺失，分子与分母必须使用一致的有效集合。一个错误实现对缺失值乘积跳过求和，却把全部权重加进分母，相当于把缺失值贡献当零。正确实现通常先筛选值与权重均有效且满足权重条件的记录，再同时计算两部分；若你的任务确实要求未知值按零处理，也应明示这一假设。

权重和为零时均值未定义，不应随意返回零。负权重可以出现在某些估计器中，但它们不再是普通概率权重，均值可能超出原值范围；普通消费平均通常应拒绝负权重。极端权重会使有效信息集中在少数样本，名义行数很大也可能估计不稳定，应报告权重分布并做敏感性分析。

常见的权重集中度指标是权重和平方除以平方和，独立同方差且固定权重等简化设定下可以用作有效样本量直觉；它不是复杂抽样或相关重复样本的一般方差公式。不能看到这个指标接近一千，就宣称有一千个独立样本。复制同一事实增加行数，却不创造同等数量的新信息。

### 7.5 分组趋势与总体趋势为什么可以反转

假设甲方案在容易组通过九十人中的八十一人，通过率百分之九十；在困难组通过十人中的三人，通过率百分之三十。乙方案在容易组通过十人中的九人，同为百分之九十；困难组通过九十人中的二十七人，同为百分之三十。两方案组内表现完全相同，总体通过率却分别为百分之八十四和百分之三十六，因为群体组成不同。

要构造“每组甲都优于乙、总体甲却更差”，还必须让群体组成与组内率的组合满足反转条件，不能仅在上述固定组成中把甲的两组通过率都略微提高。一个可手算的反例是：甲的容易组十人全部通过，困难组一百人中三十一人通过；乙的容易组一百人中九十人通过，困难组十人中三人通过。甲在容易组为 $`100\%>90\%`$，困难组为 $`31\%>30\%`$，但总体为 $`\frac{41}{110}\approx37.27\%`$，乙为 $`\frac{93}{110}\approx84.55\%`$，方向相反。

反转来自两方案的组权重不同。若用同一组非负目标权重 $`w_g`$（总和为一）标准化，且每组 $`r_{A,g}\ge r_{B,g}`$，则

```math
\begin{aligned}
&\sum_gw_gr_{A,g}-\sum_gw_gr_{B,g}\\
&\quad =\sum_gw_g(r_{A,g}-r_{B,g})\ge0
\end{aligned}
```

由这个非负差值可知，统一权重后不会再出现这种方向反转。这里没有算术矛盾，原总体比率按各方案自身群体权重混合，而组内比较固定了群体。评价时要判断目标是部署总体表现、固定人群下的比较，还是因果效应；不同目标需要不同权重与假设，不能单凭分组或总体哪个结果更顺眼就选择。

表处理在这里承担透明计算责任：保留每组分子分母，明确缺失与筛选，能够按统一目标分布重新加权。它不自动提供因果识别。是否应控制某个变量，还取决于变量在生成机制中的角色；把所有字段都分组并不能保证公平比较，有时反而引入新的偏差。

### 8.1 实验契约与需要保留的未知状态

输入订单表以订单编号为主键，每行一笔订单，金额以分为可空整数。用户键可以缺失，但这部分订单要保留在未知群体，不能悄悄消失。用户属性表对非空用户键唯一，未知键不参与匹配。统计输出要区分订单数、已知金额订单数、已知金额和以及金额完全未知的用户。

本实验只验证关系与聚合逻辑，不生成预测特征。属性表被明确视为当前分析合法的固定快照，不能拿本代码直接回放历史预测；那需要后续章节补充有效期与可用时间。这样限定目标，可以把一个完整实验做透，而不是让少量代码承担没有实现的时间语义。

样本包括用户甲两笔订单十元与二十元，用户乙一笔金额缺失，用户丙一笔五元但无属性，另有未知用户一笔七元。属性表包含甲、乙和无订单的用户丁。实验将证明：事实行保留、已知金额四千二百分守恒、未知金额不变成已知零、未知用户不被错误匹配，右侧未使用用户丁也能被报告。

### 8.2 自足实现与手算结果

代码依赖 pandas。先以订单身份核对连接前后是否仍一单一行，再按用户对账已知金额，同时保留未知用户和未知金额。验收时将五笔订单、四笔已知金额和 4,200 分的合计分开核对。

```python
import pandas as pd
from pandas.testing import assert_frame_equal
orders = pd.DataFrame({
    "order_id": [101, 102, 103, 104, 105],
    "user_id": pd.Series(["A", "A", "B", "C", pd.NA], dtype="string"),
    "amount_cents": pd.Series([1000, 2000, pd.NA, 500, 700], dtype="Int64"),
})
users = pd.DataFrame({"user_id": pd.Series(["A", "B", "D"], dtype="string"),
                      "region": pd.Series(["N", "S", "N"], dtype="string")})
original = orders.copy(deep=True)
assert orders["order_id"].is_unique and users["user_id"].is_unique
assert users["user_id"].notna().all()
joined = orders.merge(users, on="user_id", how="left", validate="many_to_one", indicator=True)
assert joined["order_id"].is_unique
assert set(joined["order_id"]) == set(orders["order_id"])
assert len(joined) == len(orders) == 5
assert joined["amount_cents"].sum() == orders["amount_cents"].sum() == 4200
assert joined["amount_cents"].count() == orders["amount_cents"].count() == 4
assert joined["_merge"].eq("left_only").sum() == 2

def summarize(frame, keys):
    g = frame.groupby(keys, dropna=False, observed=True, sort=False)
    out = g.agg(order_count=("order_id", "size"), known_count=("amount_cents", "count"))
    out["known_cents"] = g["amount_cents"].sum(min_count=1)
    return out.reset_index()

by_user = summarize(orders, ["user_id"])
assert int(by_user["order_count"].sum()) == 5
assert int(by_user["known_count"].sum()) == 4
assert int(by_user["known_cents"].sum()) == 4200
assert pd.isna(by_user.loc[by_user["user_id"].eq("B").fillna(False), "known_cents"].iloc[0])
user_with_region = by_user.merge(users, on="user_id", how="left", validate="one_to_one")
first_join = summarize(joined, ["user_id", "region"])
columns = ["user_id", "region", "order_count", "known_count", "known_cents"]
left = user_with_region[columns].sort_values("user_id", na_position="last").reset_index(drop=True)
right = first_join[columns].sort_values("user_id", na_position="last").reset_index(drop=True)
assert_frame_equal(left, right)
key_audit = orders.loc[orders["user_id"].notna(), ["user_id"]].drop_duplicates().merge(
    users[["user_id"]], on="user_id", how="outer", validate="one_to_one", indicator=True)
assert key_audit["_merge"].eq("left_only").sum() == 1  # C
assert key_audit["_merge"].eq("right_only").sum() == 1  # D
assert_frame_equal(orders, original)
print(by_user)
print("5单，4单金额已知，已知合计4200分；C未匹配，D无订单，未知用户独立保留")
```

<a id="pd2-full-analysis"></a>

### 8.3 为什么这些断言比看输出前五行更强

对用户甲，订单数二、有效金额数二、金额和三千分；用户乙订单数一、有效金额数零、金额和缺失；用户丙订单数一、有效金额数一、金额和五百分；未知用户组订单数一、有效金额数一、金额和七百分。四个组的行数和为五，已知金额数和为四，金额和为四千二百分，这三项分别核对不同层次。

先聚合后连接与先连接后按用户地区聚合结果相同，是在本实验右键唯一、属性固定、无筛选且缺失组保留的条件下成立。对两条结果按相同键排序再比较，是为了消除纯显示顺序差异，不是为了掩盖身份问题。输入订单标识和金额来源仍单独验证；只比较两条流程一致还不够，因为它们可能共享同一个错误假设。

这里把未知用户组保留为一个统计桶，不表示这些订单属于同一个真实用户。若要计算用户数或人均消费，不能把这个桶当作一位用户；应单独报告无法识别的订单，或在有额外证据时恢复身份。分组中的缺失桶是一种汇总表示，不能反过来被解释为实体同一性。

用户乙全金额缺失与一个真实消费零元用户不同。若把`min_count=1`去掉，乙的金额和可能显示零，但有效金额数仍为零；两个指标一起看可以发现这个边界。若后续只保留金额和而丢弃有效数，未知与零的区别就很容易永久消失。因此，指标表的字段选择也属于信息保留设计。

<a id="pd2-exchange-counter"></a>

### 8.4 交换失败与加权合成的反例实验

在安装 pandas 的 Python 环境中运行。三组对照分别检查组均值的分母、缺失值对应的权重，以及一对多连接导致的重复计账。每一组都单独设置断言，方便定位是哪一步改变了统计对象。

```python
import pandas as pd
orders = pd.DataFrame({"user": ["A", "A", "B"], "amount": [10., 30., 50.]})
by_user = orders.groupby("user", observed=True, dropna=False).agg(
    total=("amount", "sum"), valid=("amount", "count"), avg=("amount", "mean"))
assert by_user["avg"].mean() == 35
assert by_user["total"].sum() / by_user["valid"].sum() == orders["amount"].mean() == 30
# 加权时只用值与权重同时合法的记录；未知值不能只从分子移除。
values = pd.Series([10., float("nan"), 30.])
weights = pd.Series([1., 100., 3.])
valid = values.notna() & weights.notna() & weights.ge(0)
weighted_mean = (values[valid] * weights[valid]).sum() / weights[valid].sum()
wrong_mean = (values * weights).sum() / weights.sum()
assert weighted_mean == 25 and wrong_mean < 1
# 同一用户的两个属性造成事实复制，先聚合也不会神奇修复关系。
attributes = pd.DataFrame({"user": ["A", "A", "B"], "category": ["x", "y", "x"]})
expanded = orders.merge(attributes, on="user", how="left")
assert expanded["amount"].sum() == 130
aggregated_expanded = by_user.reset_index().merge(attributes, on="user", how="left")
assert aggregated_expanded["total"].sum() == 130
print("订单均值30，用户均值平均35；合法加权25；多值属性使总额90变130")
```

<a id="pd2-experiment-lessons"></a>

### 8.5 反例给出的工程启示

两个流程都产生一百三十元并不能证明它们都正确，只能说明错误关系下的复制同样作用在订单事实或用户总额上。先聚合可以减少计算量，却不能把多值属性变成函数依赖。若类别关系本来合法，应明确每个用户金额如何分配到类别，是全额归属、按比例分配还是只统计用户覆盖，不能随便要求总额守恒。

加权反例里，缺失值对应权重一百。错误分母保留这项权重，分子只剩一百，结果约零点九六；合法有效集合的分子一百、分母四，结果二十五。这个错误说明“求和默认忽略缺失”不一定让组合公式正确，分子和分母需要同一观测集合。许多比率、加权损失和转化率都存在同类问题。

实现大型管道时，可以把这类极小反例作为契约示例随文档保留。它们不需要复杂测试框架，也不应成为每次批次运行都重复的昂贵实验；真正的生产检查应围绕关键约束。教材代码运行验证表达式行为，实际数据审计则验证输入满足假设，两者作用不同。
