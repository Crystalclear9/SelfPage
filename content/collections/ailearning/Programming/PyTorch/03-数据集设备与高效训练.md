## 1. 数据管道首先是一份统计契约

高效训练需要同时回答两个问题：每次更新究竟利用了哪些信息，以及这些信息经过怎样的路径到达计算设备。前一个问题决定实验是否正确，后一个问题决定实验是否高效。把两者混在一起，常会出现一种隐蔽的错误：训练看起来更快，实际上只是漏掉了难样本、改变了长度权重，或者让验证集参与了预处理。本章把样本身份、目标归一化、随机状态、设备语义与性能测量放在同一条可核对的链路中。

先明确训练目标。若数据集有有限的有效样本，均匀经验风险是各样本损失的算术平均；若任务按有效词元计分，分母就应当是词元数；若业务规定每份文档等权，长文档不能仅因词元多就获得更大权重。这三种目标都可能合理，却不能互相替换。数据加载器提供的是批次结构，不会自动替研究者决定统计单位。要让优化结果可解释，必须把分子、分母、样本权重和排除规则写清楚。

设第一个微批有两个有效词元，第二个微批有八个。两个微批损失均值的平均，给两个词元组成的小批分配了一半权重；把十个词元损失相加再除以十，才是词元等权。设备、并发和混合精度都不会修正这个差异。所有性能实验开始之前，应先用极小数据手算一个更新，确认程序优化的确实是所声明的目标。

<a id="torch-3-detail-2"></a>
### 1.1 从样本身份到批次字段

一个样本最好同时具有稳定标识、输入、目标，以及解释输入所必需的元数据。稳定标识不一定送进模型，却能追踪重复、丢失、错配和跨集合泄漏。对于图像分类，可以是文件相对路径的规范化标识；对于文本窗口，可以是文档标识与起止位置；对于表格，可以是业务主键及时间戳。若预处理拆分了一个样本，也应保留拆分前后的对应关系。

批次契约应说明每个字段的形状和含义。例如输入是批次乘时间乘特征，掩码是真表示有效位置，长度是原始有效长度，类别是从零开始的整数索引。形状吻合只是必要条件：长度等于输入第二维，并不能证明填充值没有被当成真实输入；标签和输入数量相同，也不能证明打乱时保持了配对。因此调试时应打印少量标识与标签，并建立能够预测输出的人工样本。

应当区分“读取失败”和“任务允许排除”。在读取失败时静默返回另一个样本，会改变采样分布，同时使一个标识对应多个随机替身。直接返回空值并让组批函数跳过，也会改变有效批量与归一化分母。更合理的策略是预先记录有效样本清单，或明确记录跳过事件并按实际有效数计分。对于必须容错的流式任务，应把排除规则作为数据版本的一部分。

<a id="torch-3-detail-3"></a>
### 1.2 映射式数据集与可迭代数据集

映射式数据集实现按键读取，常见键是整数索引。它适合有限样本和需要随机访问的场景。采样器生成键，数据集把键映射为样本，组批函数把多个样本组成批次。这个分工让采样分布可以独立检查：只运行采样器便能知道某一轮将访问哪些样本，而不必真的解码大文件。

可迭代数据集直接产生样本流，适合顺序读取、持续日志和无法廉价随机访问的来源。它没有通用的索引空间，因此不能把映射式采样器原样套上去。有限长度可能只是估计，数据源也可能随时间变化。此时“一个轮次”往往应定义为固定更新数、固定有效记录数或固定时间区间，而不是假定遍历一次就对应不变的完整数据集。

两者的分界不是磁盘与内存。内存数组可以做成可迭代数据集，磁盘文件也可以做成映射式数据集。真正重要的是访问协议、身份稳定性和可恢复性。映射式方案容易保存一个排列与游标；流式方案通常还需要源分片、偏移、水位和重放约定。若后续要求故障恢复，需要在选择数据接口时就考虑状态如何表示，而不是训练中断后才寻找不存在的索引。

<a id="torch-3-detail-4"></a>
### 1.3 基础算例：先估算批数据字节再增加并发

一批三十二张、三通道、二百二十四乘二百二十四的单精度图像，原始输入约占十九点三兆字节。这个数字只包含输入张量，不包含解码前的压缩文件、增强中间结果、目标、队列、模型激活与设备副本。若四个工作进程各预取两个批次，排队中的输入量级就可能达到八批；再加主进程当前批、传输中的批次和工作进程各自的临时对象，主机内存消耗明显高于一批。

这种估算不应被当成精确峰值公式。实际队列和生命周期会让部分对象重叠，张量共享机制又可能减少某些复制；反过来，复制大量由 Python 对象构成的文件索引，也可能引入更大的常驻开销。估算的价值是识别量级与风险，然后用目标机器的内存观测验证，而不是凭显存还有余量就无限提高预取。

若图像尚未归一化时以八位整数保存，把转换推迟到合适阶段可以减少传输量，但这会改变预处理所在设备。必须验证数值范围、增强顺序和舍入是否保持预期。若 CPU 解码已经是瓶颈，减少传输字节未必提升吞吐；若设备等待传输，减少字节才可能有效。每个改动应有明确的瓶颈假设。

<a id="deep-dive-1"></a>
<a id="torch-3-detail-5"></a>
### 1.4 深入讲解：流水线中的吞吐与延迟

把一批处理分成读取解码、主机变换、传输和设备计算，串行执行时每批延迟接近各阶段时间之和。若资源独立且调度允许充分重叠，稳定吞吐可能接近最慢阶段的处理速率。这是理想化模型，实际还受队列空满、带宽竞争、批次大小波动和同步点影响。它解释了为什么仅把一个已非瓶颈的阶段加速十倍，端到端仍可能几乎不变。

吞吐和单批延迟也不是同一个目标。更深的队列可能让设备持续工作，却增加样本从读取到使用的等待时间；对在线学习，这还意味着数据更新更滞后。较大的批次可能提高每秒样本数，却改变每轮更新数以及优化轨迹。如果比较固定训练时间的模型质量，应同时记录吞吐、实际更新数和最终质量，不能只展示一个最快的批次时间。

队列可以吸收短暂抖动，却不能创造长期处理能力。若读取阶段平均比计算阶段慢，继续增大队列只能延后设备开始等待的时刻；若读取偶尔抖动但平均足够快，适度预取才可能有明显价值。通过时间分布而非一个均值分析等待，能够区分持续瓶颈与偶发停顿。报告中应说明是否包含首轮缓存、进程启动和文件系统冷启动。

## 2. 采样器决定了训练看见的分布

<a id="torch-3-detail-7"></a>
### 2.1 打乱不是增加新信息

无放回随机排列让每个样本在一轮中通常出现一次，但更新先后顺序改变了随机优化轨迹。带放回采样则允许重复与遗漏，两者并不等价。对存在类别不平衡的数据，按类别调整抽样概率可能改善少数类梯度信号，却也改变了隐含目标。若希望仍估计原始总体的均匀风险，就需要考虑与抽样概率匹配的重要性权重，并检查方差代价。

例如两类分别有九十个与十个样本，按类别等概率抽样后，每个少数类样本被抽中的概率更高。若训练损失仍不加权，优化的是近似类别等权目标，而不是原始九比一总体目标。这不是代码错误，但评价解释必须一致。若训练又使用逆频率类别权重，相当于在采样调整外再次倾斜，可能过度放大小类。应先写出期望梯度，再决定是否需要这两种机制同时存在。

这里需要把“修正权重”真正算出来。固定当前参数，记训练集大小为 $N$、第 $i$ 条样本的梯度为 $g_i$，原目标梯度是 $N^{-1}\sum_i g_i$。若独立有放回抽样的每次索引分布为 $q_i>0$，则

$$
\mathbb E_q\!\left[\frac{g_I}{Nq_I}\right]
=\sum_iq_i\frac{g_i}{Nq_i}
=\frac1N\sum_i g_i.
$$

这里的 $q_i$ 是每条记录的抽样概率，不是把未归一采样分数直接代入。对于九十条甲类、十条乙类且类内均匀的平衡抽样，甲类每条概率为 $1/180$，乙类为 $1/20$；恢复原始经验目标的乘数分别为 $1.8$ 与 $0.2$。若两类平均梯度分别为 $2$ 与 $-1$，原目标梯度为 $1.7$，平衡采样未加权的期望却为 $0.5$。校正后是 $0.5\times1.8\times2+0.5\times0.2\times(-1)=1.7$。这一步说明修正的方向：已经过采样的少数类需要减轻单次贡献。

若平衡采样以后又给乙类九倍损失权重，期望数据梯度变成 $0.5\times2+0.5\times9\times(-1)=-3.5$；若再按总体平均权重五归一，则为 $-0.7$，对应甲乙约一比九的类别风险，而不是原来的九比一。这个目标可以出于代价偏好有意采用，但不能当作“纠正类别不平衡后仍估计原总体”的自动结果。抽样与损失权重必须一起进入期望计算。

还要区分两种批内归约。对 $B$ 次独立抽样，以 $B^{-1}\sum_b g_{I_b}/(Nq_{I_b})$ 归约，分母固定，保留上述条件无偏性；若改除以本批随机权重和，就成为自归一化比值，一般不再有限样本无偏。最小反例是 $B=1$，权重在分子分母中完全抵消，期望又回到 $0.5$。本段推导还假定每样本损失可以独立相加；若损失含批内负样本、批统计或样本交互，改变抽样也改变联合批分布，不能只靠单条记录的权重恢复全部行为。无放回不等概率抽样则应分析纳入概率与对应估计器，不能直接沿用这里的独立有放回公式。

打乱也不应破坏任务依赖。时间序列预测不能先把整个时间轴随机分成窗口再宣称未来独立测试，重叠窗口可能泄漏相邻目标。用户行为数据若同一用户出现在训练与测试，也可能高估跨用户泛化。数据集划分的独立单位通常高于批次单位；采样器只控制训练内部顺序，不能补救划分层面的泄漏。

分布式采样器只负责输入分片，数据并行包装器本身不自动切分数据。采用按轮次打乱的分布式采样器时，应在每轮开始前调用其 `set_epoch(epoch)`，让不同轮次使用受控而变化的排列；遗漏该调用可能让每轮顺序重复。各进程必须使用兼容的数据清单、种子与轮次，才能共同形成预期分片。

<a id="torch-3-detail-8"></a>
### 2.2 尾批、重复填充与评价分母

丢弃尾批可以保证部分批内算法的形状条件，却会减少样本覆盖。若样本排列固定，尾部总被丢弃，某些样本可能长期没有参与更新；若每轮随机排列，被丢弃的身份随轮次变化，但每轮有效样本仍少于全部。训练可以接受明确的丢弃约定，评价通常更适合保留所有有效样本并按真实数量归约。

分布式采样为了让各进程样本数一致，可能重复某些索引，也可能按配置丢弃尾部。训练中的少量重复与评价中的重复含义不同：评价重复会使某些样本权重增加。若必须用填充索引保证同步，可携带有效标记，让指标只计真正样本；也可以采用适合不等长评价的独立汇总方案。不能仅通过全进程平均准确率就假定每个原始样本恰好计数一次。

批采样器可以按长度组桶，减少填充浪费。它同时改变批内长度组成，因此应注意批内归一化、负样本构造和难度相关性。全局完全排序可能使前期总见短样本、后期总见长样本，形成隐含课程。较稳妥的策略是在随机的大块内排序或随机组桶，并记录算法。性能收益来自减少无效填充，学习行为变化则应另行解释。

## 3. 工作进程、随机源与跨平台启动

<a id="torch-3-detail-10"></a>
### 3.1 工作进程中到底复制了什么

多进程加载把读取、增强和组批中的一部分工作移到子进程。它适合某些计算或读取密集任务，却需要进程启动、对象传递与队列维护。对于已经位于内存的小张量，主进程直接索引可能更快。工作进程数也不是只由 CPU 核数决定：解码库内部线程、存储随机访问能力和主机带宽都可能先达到上限。

在 Windows 的生成式启动协议下，新进程会导入入口模块，相关类与函数需要能够被定位和序列化。把训练主体放在模块顶层，可能导致子进程重新执行训练入口；把数据集定义在临时交互局部作用域，可能使子进程无法找到定义。可移植程序应将数据集类、组批函数和初始化函数定义在模块顶层，并用主入口保护启动训练。

本章的可执行实验使用零工作进程，因此可以直接在内存中运行，不依赖额外脚本文件。下面的入口模板仅展示独立程序组织方式，不应在本章环境中据此宣称已经测试了多进程性能。实际项目应在真正的模块入口验证工作进程退出、异常传播和资源回收，尤其检查程序被中断后是否留下持有文件句柄的子进程。

```text
模块顶层：Dataset 类、collate 函数、worker 初始化函数
main 函数：读取配置、构建 DataLoader、创建模型、启动训练
if __name__ == "__main__": main()
```

<a id="torch-3-detail-11"></a>
### 3.2 种子、随机流与可重复增强

固定全局种子只规定某个随机流的初始状态，不保证所有模块消费随机数的次数都相同。模型初始化、采样排列、数据增强和日志可视化若共享同一个流，新增一次随机绘图就可能改变之后的数据顺序。将独立职责分配给独立生成器，能够减少这种隐式耦合。生成器的当前状态也需要在严格续训时保存，只有初始种子不足以知道已经消费了多少随机数。

工作进程会获得各自的随机状态；若增强还使用 NumPy 或 Python 的随机模块，应按框架约定从工作进程种子派生并初始化相关源。这里应避免“所有工作进程使用同一个常数种子”的简单写法，否则不同进程可能产生相同增强序列。又要避免把生成器对象的共享误认为状态自动同步：跨进程复制之后，它们的状态演化往往独立。

持续工作进程减少了每轮重新启动成本，但其内部状态也持续存在。主进程修改数据集对象的某个普通属性，不代表子进程副本会自动看到同样变化。若增强依赖轮次，需要显式传递可见状态，或把轮次编码进可重建的样本键。不能假定每次进入外层循环，工作进程初始化函数都会重新运行。

一种更容易审计的方案是以基础种子、轮次、样本身份与增强次数生成局部随机键。这样同一样本在指定轮次的增强由身份决定，而不依赖它恰好被哪个工作进程处理。实现时应使用稳定的整数映射或稳定摘要，避免依赖跨进程可能变化的 Python 字符串哈希。这个方案仍需定义重复采样时的增强编号，否则同一轮重复样本可能得到完全相同的增强。

<a id="torch-3-detail-12"></a>
### 3.3 可迭代数据集的进程与设备分片

多个工作进程若各自从同一流的开头读取，最直接的结果是重复数据。应当把总消费者标识定义为设备进程与工作进程的组合，再用互斥分片分配记录。例如全局消费者数为设备进程数乘每进程工作数，可用记录序号对消费者数取余决定归属。这个方案容易验证覆盖与互斥，但每个消费者若仍必须扫描全部记录，读取成本可能很高；按物理文件分片通常更高效。

每个消费者内部再独立丢弃尾批，可能比全局只丢弃一个尾批损失更多记录。若各分片长度不同，还会导致不同设备进程的迭代次数不同。同步训练需要明确处理这种不平衡，不能让一个进程继续进入梯度通信，而其他进程已经退出。对于无界流，可以按固定更新预算训练；对于有限流，应预先设计等长分配或采用明确支持不均匀输入的协议。

流式系统还需区分“读取成功”和“更新已提交”。预取可能已经从外部来源读取未来记录，但这些记录尚未进入参数更新。若检查点只保存读取偏移，恢复可能跳过未训练记录；若保存过早的偏移，又可能重复使用已训练记录。正确的游标应对应已提交更新的消费边界，或采用允许重放并能审计重复的协议。这也是下一章讨论检查点时，不能只保存模型权重的原因。

<a id="torch-3-detail-13"></a>
## 4. 设备、精度与状态共同构成运算接口

<a id="torch-3-detail-14"></a>
### 4.1 参数、缓冲区与新建张量

模型的设备迁移会处理注册参数与注册缓冲区，但普通 Python 属性中保存的张量未必随模型自动迁移。因此长期状态应根据语义注册为参数或缓冲区，临时张量则尽量依据已有张量的设备和类型创建。比如掩码通常应是布尔型，类别索引通常应是整数型，浮点输入则与所选算子的要求相容。不能为了消除设备报错，把所有字段统一转换为同一种浮点类型。

将模型移到目标设备之后再创建优化器，是清晰且易检查的默认组织方式。优化器持有参数引用及其状态，加载检查点时还要检查历史状态与当前参数的设备和精度是否兼容。不同优化器可能对计数器等状态采取不同存放策略，所以也不能无条件把状态字典中的所有张量递归转成参数精度。应按当前优化器接口与实际状态结构核对。

新建常量的常见风险来自隐式默认。一个在函数内部通过默认构造创建的 CPU 张量，可能直到第一次 GPU 前向才触发错误；一个无意创建的双精度张量，可能导致额外转换或运算不被支持。将这些约束写进输入检查，能够把失败定位在边界，而不是在很深的算子栈中追踪。检查应在调试阶段充分，在稳定阶段按成本调整。

<a id="sec-2-1"></a>
<a id="torch-3-detail-15"></a>
### 4.2 同设备仍可能有错误的任务语义

单标签分类的硬标签是类别编号，多标签分类的目标通常是各类独立的零一值或概率。二者即使形状经过强制变换后可以送入某个函数，也不意味着目标相同。位置掩码、采样权重和类别权重又是不同概念：掩码排除不参与目标的位置，采样权重决定样本贡献，类别权重改变不同类别的误差代价。

索引张量还必须满足取值范围。使用负数表示忽略标签时，必须在损失函数明确支持忽略语义，或在手动索引之前过滤，而不是先用无效索引取值再乘零。类似地，填充位置若先参与无定义运算，再被掩码乘零，仍可能产生非有限结果，因为零乘非数并不能还原一个有效值。掩码应在数学定义和程序访问层面都正确。

从设备迁移排错时，可先固定一批样本，在 CPU 上记录输入范围、目标、输出与损失，再仅改变设备重算。若同时改增强、批大小、随机种子和精度，差异就失去归因依据。要求逐位相同通常过强，但可要求任务语义一致、数值有限、输出在声明容差内接近。之后再逐项打开混合精度与并行选项。

<a id="torch-3-detail-16"></a>
### 4.3 内存布局、视图与复制

张量的逻辑形状和物理布局不是同一个对象。转置可能只创建共享存储的视图，某些后续操作却需要连续布局而产生复制。频繁在通道顺序之间转换，可能让传输或算子准备时间超过预期。查看形状之外，还应理解步幅、连续性和共享关系；不能把所有慢操作都归因于模型乘法。

切片也可能保留对大存储的引用。一个很小的视图若被长期缓存，可能让整块原始存储无法释放；显式复制会增加当下开销，却可能减少长期驻留。反过来，无必要的复制会提高峰值内存和带宽消耗。应围绕对象生命周期判断，而不是把“视图总好”或“连续总快”当成普遍规则。

零梯度时把梯度设为空与写成全零，在内存与部分优化器行为上可能有区别。未得到梯度的参数和得到零梯度的参数并不总能混为一谈，特别是带权重衰减或条件分支的模型。训练代码应明确哪些参数本步参与目标，不能只观察损失下降就忽略长期未更新的分支。

<a id="torch-3-detail-17"></a>
## 5. 混合精度：范围、舍入与算子策略

<a id="torch-3-detail-18"></a>
### 5.1 低精度为什么既可能快也可能失败

浮点表示需要在指数范围和有效位数之间分配有限比特。半精度与脑浮点格式的范围和相对分辨率不同，因此不能仅按“十六位”判断数值行为。一个格式可能容纳较大的数，却对相邻数的细小差别更不敏感；另一个格式可能在小梯度上更容易下溢。求和、指数、归一化和方差计算对此具有不同敏感性。

计算误差也不只来自单个乘法。长链相乘会累积舍入，接近的两个大数相减可能损失有效位，许多小数相加可能被较大的累加器吞没。保留主参数或部分累加为较高精度，能够缓解某些风险，却不会使整个训练与全精度完全相同。评价混合精度时，应检查稳定性、最终质量与资源收益，而不是要求每一步参数逐位一致。

更低精度也不保证提速。若任务受数据读取或主机调度限制，减少设备运算时间可能没有端到端收益；若硬件对该精度缺少高效路径，转换开销甚至可能更大。对于小矩阵，启动与内存搬运可能占主导；对于大矩阵，专门计算单元才更可能发挥优势。因此应在目标形状和硬件上测量，而不能根据理论峰值直接推算训练速度。

<a id="torch-3-detail-19"></a>
### 5.2 autocast 与梯度缩放解决不同问题

自动混合精度上下文按算子与设备策略选择合适的执行精度，它不是对所有参数和输入统一强制转换。前向与损失计算通常放在上下文中，反向通常在上下文外触发，让自动求导沿前向所建立的类型路径工作。不要为追求低精度，把类别索引和布尔掩码也转换为浮点。

梯度缩放则对损失乘以尺度，使一些本来可能下溢的中间梯度进入可表示范围，然后在更新前恢复相应尺度。它不能修复输入本来就是无穷、损失公式无定义或索引越界。若放大后产生非有限梯度，缩放器可能跳过优化器更新并调整尺度。于是“处理了一个批次”和“真正完成一次参数更新”成为不同事件。

对于适合脑浮点格式的 CPU 路径，常见用法是自动转换而不使用面向半精度下溢的缩放策略；是否需要缩放必须依据格式、设备及具体问题。不要把一个设备上的经验强行推广到另一个设备。本章的实验只验证本地 CPU 支持与数值有限性，不声称验证了 GPU 混合精度的吞吐或显存收益。接口应按所用版本的官方文档核对。

在本章对应版本中，可用 `torch.autocast(device_type="cuda", dtype=torch.float16)` 声明适合的 CUDA 前向上下文，并用 `torch.amp.GradScaler("cuda")` 管理缩放。典型有效组边界是依次执行 `scaler.scale(loss).backward()`、`scaler.unscale_(optimizer)`、裁剪、`scaler.step(optimizer)` 和 `scaler.update()`；累积时前一项按微批执行，后面各项在组末执行。这里是设备条件说明，当前 CPU 实验没有运行此 CUDA 路径。

<a id="torch-3-detail-20"></a>
### 5.3 梯度缩放与裁剪不交换

设真实梯度为梯度向量，裁剪阈值为固定常数。若先把梯度乘上尺度再按同一个阈值裁剪，最后除回尺度，实际阈值相当于被缩小，更新可能过度受限。应在有效更新需要的全部微批反向完成后，对相应优化器解除缩放，再计算真实梯度范数并裁剪。每次更新只在正确边界处理一次，不能在尚未完成累积时反复解除缩放。

多优化器场景还涉及共享参数和不同更新频率。一个损失对两个优化器的参数产生梯度，并不意味着可以随意交叉解除缩放与更新。应明确每个优化器负责的参数集合、每次更新所见的梯度，以及缩放器的使用协议。初学时宜先建立一个优化器的正确闭环，再扩展到交替更新，避免把数值流程隐藏在通用训练器中。

调度器步数也要对应声明的时钟。按轮次调整、按批次调整和按真实更新调整是三种协议。缩放器跳过更新时，是否推进调度器会改变训练定义；应按照所选协议记录并验证，不能只根据调用位置推断。检查点需要保存这种时钟及缩放状态，否则恢复后可能改变更新频率与学习率对应关系。

<a id="torch-3-detail-21"></a>
## 6. 梯度累积、变长目标与分布式归约

<a id="torch-3-detail-22"></a>
### 6.1 先推导权重，再写反向代码

设一个有效更新组包含若干微批，每个微批有有效损失和与有效单位数。若目标是所有有效单位等权，则组损失等于各微批损失和之和，再除以总有效数。因求导线性，可以先按同一个总分母分别反向，最后只更新一次。若总分母事先未知，可先累计未归一化梯度，更新前按最终总数缩放，但需同时正确处理混合精度与分布式归约。

当所有微批大小相等且每批损失都是同一种单位的均值时，除以微批数量是该公式的特例。最后一个累积组少于预设微批数量时，仍除以预设数量会缩小梯度。若每批词元数变化，简单除以微批数量也会改变目标。应通过一个极不平衡的例子验证实现，例如一批只有一个有效词元，另一批有九个，手算两者权重是否一比九。

累积等价还有前向条件。没有跨样本操作、随机路径一致且参数在累积期间不变时，损失梯度能够对应大批目标；批归一化、批内对比负样本和某些跨样本正则会改变前向函数。即使数学目标相同，浮点求和顺序不同也可能造成小误差。因此应区分“目标相同”“梯度在容差内相同”和“逐位相同”，不能只用有效批大小一个数字替代这些条件。

<a id="torch-3-detail-23"></a>
### 6.2 分布式平均中的隐藏分母

考虑有多个设备进程，各进程独立处理本地微批。若默认同步通信把梯度在设备进程间平均，而每个进程先对本地有效单位取均值，那么最终得到的是本地均值的等权平均。只有各进程有效数相同，这才等于全局有效单位均值。对于变长文本、过滤样本或不同掩码，本地有效数往往不同。

若希望得到全局均值，可先通信汇总全局有效数。对每个进程的本地损失和乘以设备进程数，再除以全局有效数；默认梯度平均中的设备进程数因子恰好抵消。这里假设通信确实执行默认平均，并且没有自定义通信钩子改变归约语义。若框架已经在上层处理了归一化，再手动乘一次会重复修正，因此必须核对实际训练栈。

梯度累积时还可以在前几个微批使用不立即同步的上下文，在最后一个微批执行通信，降低重复通信开销。但该上下文需要覆盖相应前向与反向，并保证所有设备进程以兼容顺序参与最终同步。若某个进程没有有效样本，也不能简单跳过所有通信，让其他进程永久等待；应按明确协议处理零贡献并避免除零。

<a id="torch-3-detail-24"></a>
### 6.3 学习率与有效批量不能机械互换

把有效批量扩大后按比例增大学习率，是某些训练方案中的经验规则，不是任意模型和优化器的定理。批量影响梯度噪声、更新次数与正则化效果，动量和自适应优化器的历史也随更新频率改变。固定轮数时，大批量通常意味着更少的更新；固定更新数时，又意味着处理更多样本。两种预算下的比较回答不同问题。

梯度裁剪进一步引入非线性。分别裁剪每个微批梯度再相加，一般不等于先相加再裁剪。权重衰减若按每次更新执行，减少更新次数也改变累计收缩。因此“累积四次就完全等价于大四倍批量”必须附带前向、归约、裁剪、随机性与更新时钟条件。对实际工程，更有价值的是准确记录这些条件，而非追求一句过度简化的等价描述。

<a id="torch-3-detail-25"></a>
### 6.4 用公式核对本地与全局目标

令第 $r$ 个进程拥有 $n_r$ 个有效单位，本地损失和记为 $A_r(\theta)$，总有效数 $N=\sum_r n_r$。希望优化的全局目标是

$$
L(\theta)=\frac{\sum_{r=1}^{R}A_r(\theta)}{N}.
$$

默认梯度平均给出 $\frac1R\sum_r\nabla_\theta L_r$，所以令本地反向目标为 $L_r=R A_r/N$，便得到所需的 $\nabla_\theta L$。相反，若令 $L_r=A_r/n_r$，则每个进程等权，而非每个有效单位等权。当某个进程有效数为零，后者甚至无定义；前者在全局有效数非零且通信路径正确时允许零贡献。这也说明计数必须与实际掩码对应。

如果数据项之外还有每次更新执行一次的正则项 $J(\theta)$，可以让每个进程都加入同一个 $J$，默认平均后正则系数保持一次。若同时把该正则项也乘上 $R/N$，就改变了正则强度。对分布式归约的推导必须分别处理数据和、分母与非数据正则，不能把整个损失盲目乘上同一个修正系数。

<a id="torch-3-detail-26"></a>
## 7. 主机传输、锁页与异步执行

<a id="torch-3-detail-27"></a>
### 7.1 锁页内存解决的是传输路径

可分页主机内存与设备直接传输之间可能需要额外准备。锁页内存让主机页面在传输期间具有所需稳定性，常被用来改善某些主机到设备的传输路径。数据加载器的锁页选项提供了便利，但它占用的主机资源有限，而且给自定义批次结构锁页需要相应支持。不能以为启用一个布尔参数，就保证任意嵌套对象都自动获得最佳传输行为。

非阻塞复制允许程序在某些条件下避免立即等待复制完成，但“主机调用更快返回”不等于“复制与计算已经重叠”。重叠还取决于源内存、设备能力、流依赖、操作顺序以及是否存在独立工作。若在同一执行流中先复制再计算同一批，计算仍要等待该批复制完成；只有在正确安排不同批次与依赖时，才可能把下一批传输藏在当前批计算后面。

异步也带来生命周期要求。若源缓冲在复制完成前被修改或复用，结果可能错误；若把设备数据异步复制到主机后立即读取，而没有等待必要完成事件，也可能读取未就绪内容。性能优化必须保证使用时刻与完成时刻的先后关系。先验证同步版本正确，再引入异步协议，能够显著缩小排错范围。

<a id="torch-3-detail-28"></a>
### 7.2 为什么日志会改变计时

设备上的计算通常异步提交，主机读取一个标量可能需要等待相关设备工作结束。每步都提取损失、逐层打印梯度范数或频繁把输出搬回主机，可能把本可重叠的流水线切成串行片段。日志本身还包含格式化、文件写入和可视化开销。因此应当区分诊断模式与性能模式，并在性能报告中说明日志频率。

这不意味着完全不检查数值。可以在诊断阶段频繁验证有限性、样本与梯度，在稳定测量阶段降低频率，并对设备侧统计做批量归约。若训练已经出现不稳定，就应优先恢复足够诊断信息，不能为了吞吐掩盖非有限值。测量系统必须服务于正确训练，性能指标才有意义。

内存统计也需解释。设备分配器可能保留已经释放给缓存池的内存，以减少未来申请成本；操作系统或工具显示的占用，不必然等于当前活跃张量量。频繁清空缓存通常会引入代价，也不能修复仍被 Python 引用持有的张量。若怀疑泄漏，应观察相同迭代阶段的活跃量、峰值与对象引用，而不是只看任务管理器的一个总数。

<a id="torch-3-detail-29"></a>
## 8. 性能实验必须能回答一个具体问题

<a id="torch-3-detail-30"></a>
### 8.1 端到端吞吐与算子延迟分开测

端到端吞吐包含读取、排队、传输、计算和必要记录，适合回答固定时间内处理多少有效单位。算子延迟则试图隔离某段设备工作，适合定位局部瓶颈。对异步设备，主机起止时间可能只测到提交；需要在适当边界同步或使用设备事件，并说明事件覆盖哪些执行流。同步会改变流水线，因此不能把隔离延迟简单相加当成真实端到端时间。

预热是为了让初始化、缓存、算子选择和可能的编译完成，但预热本身也代表真实启动成本。短任务应报告包括启动的总时间，长期服务可以另报稳定阶段。若形状动态变化，新形状可能引入新的准备成本；只挑一个最容易缓存的固定形状，会高估实际收益。结果至少应包括代表性输入分布、重复次数及波动范围。

每秒样本数适合等规模样本，每秒有效词元更适合变长文本，每秒像素有时更能解释分辨率变化。无效填充的处理量也可辅助定位浪费，但不能和有效工作量混在一起。若一种方法吞吐提高只是因为平均样本变短，应当如实记录，而不是把数据组成变化算成框架优化收益。

<a id="sec-6-1"></a>
<a id="torch-3-detail-31"></a>
### 8.2 数据加载与混合精度的瓶颈要分别测量

一种实用顺序是先用预先生成的设备内批次估计计算上限，再加入主机传输，再加入真实读取与增强。每一步增加的差异提供线索，但它们不一定可线性相加，因为阶段之间可能重叠，也可能竞争同一资源。应进一步用分析工具观察等待与执行分布，确认假设后再修改参数。

比较工作进程数时，固定模型、数据清单、批大小和增强规则。比较精度时，固定采样与评价，并检查误差和最终质量。比较编译时，分别记录首次与稳定阶段，同时验证动态形状和图断点。一次改变多个因素，或只报告最顺利的一次运行，都难以支持可复核的结论。

性能研究还要关注总成本。一个更快配置如果频繁触发内存不足、需要更高主机内存，或让恢复复杂到容易丢失训练进度，未必是整体最优。可以用固定质量阈值所需时间与资源衡量，而不是只看单步峰值。这里的质量阈值、早停规则与失败重试也应事先定义，避免比较过程中的选择偏差。

<a id="torch-3-detail-32"></a>
## 9. 实验一：变长批次、随机排列与覆盖核对

<a id="torch-3-detail-33"></a>
### 9.1 自足实验代码

下面只使用合成整数序列和零工作进程，在 CPU 上检查组批契约、掩码及相同种子的排列。每个样本保留身份，填充值不参与均值。实验不用下载数据，也不创建持久文件。它能证明当前合成任务的数据语义，却不证明真实文件解码或多进程吞吐已经验证。

```python
import torch
from torch.utils.data import Dataset, DataLoader
from torch.nn.utils.rnn import pad_sequence

class TinySequences(Dataset):
    def __init__(self):
        self.rows = [torch.arange(1, n + 1) for n in [1, 4, 2, 5, 3, 6, 2]]
    def __len__(self):
        return len(self.rows)
    def __getitem__(self, index):
        x = self.rows[index]
        return {"id": index, "x": x, "target": x.float().mean()}

def collate(rows):
    lengths = torch.tensor([len(r["x"]) for r in rows])
    x = pad_sequence([r["x"] for r in rows], batch_first=True)
    mask = torch.arange(x.shape[1])[None, :] < lengths[:, None]
    return {
        "id": torch.tensor([r["id"] for r in rows]),
        "x": x, "mask": mask, "length": lengths,
        "target": torch.stack([r["target"] for r in rows])
    }

def one_pass(seed):
    generator = torch.Generator().manual_seed(seed)
    loader = DataLoader(TinySequences(), batch_size=3, shuffle=True,
                        generator=generator, collate_fn=collate, num_workers=0)
    ids = []
    for batch in loader:
        value = (batch["x"] * batch["mask"]).sum(1) / batch["length"]
        assert torch.allclose(value, batch["target"])
        assert torch.equal(batch["mask"].sum(1), batch["length"])
        ids.extend(batch["id"].tolist())
    assert sorted(ids) == list(range(7))
    return ids

assert one_pass(19) == one_pass(19)
assert one_pass(19) != one_pass(23)
print("coverage, masks, and isolated shuffle generator: passed")
```

<a id="torch-3-detail-34"></a>
### 9.2 如何把实验扩展为真实数据验收

实验中用种子构建新的生成器，因此每次调用从相同状态开始。若复用同一个生成器重复迭代，状态已经推进，排列通常不同，这是正常行为。若希望恢复某轮中间位置，需要保存已经生成的排列及已提交游标，或者保存足够重建它的协议与状态，不能只重新设置最初种子就认定自动回到中途。

真实项目还应检查同一个身份是否始终对应相同原始内容、训练与验证是否共享相同业务实体，以及增强是否只在允许的集合中应用。对于随机增强，测试重点不是每次像素相同，而是给定随机键时变换可重现、目标同步变换、范围和形状符合契约。例如分割掩码需要与图像共同几何变换，却不能随意使用连续插值制造不存在的类别编号。

覆盖核对应在小规模完整清单上进行。一个批次看起来正常，无法发现整轮重复与缺失。对于带放回采样，覆盖不应被强制为恰好一次，而应检查实际频率是否符合设计，并把抽样种子固定以便诊断。测试断言必须对应采样协议，不能为了让测试通过偷偷把合法的带放回采样改成无放回。

<a id="torch-3-detail-35"></a>
## 10. 实验二：不等大小微批的精确归一化

<a id="torch-3-detail-36"></a>
### 10.1 以双精度建立梯度基准

下面比较一次完整批次与大小为二、三、二的三个微批。模型没有批内统计与随机层，均方误差以输出元素为单位，因此各微批损失和除以全部目标元素数。只比较梯度，不在中间更新参数。双精度用来降低舍入影响，并不代表实际训练必须采用双精度。

```python
import copy
import torch
from torch import nn

torch.manual_seed(31)
x = torch.randn(7, 3, dtype=torch.float64)
y = torch.randn(7, 2, dtype=torch.float64)
whole = nn.Linear(3, 2).double()
micro = copy.deepcopy(whole)
wrong = copy.deepcopy(whole)

((whole(x) - y).square().sum() / y.numel()).backward()
parts = [(0, 2), (2, 5), (5, 7)]
for begin, end in parts:
    ((micro(x[begin:end]) - y[begin:end]).square().sum() / y.numel()).backward()
    ((wrong(x[begin:end]) - y[begin:end]).square().mean() / len(parts)).backward()

good = max((a.grad - b.grad).abs().max().item()
           for a, b in zip(whole.parameters(), micro.parameters()))
bad = max((a.grad - b.grad).abs().max().item()
          for a, b in zip(whole.parameters(), wrong.parameters()))
assert good < 1e-12
assert bad > 1e-6
print("correct maximum gradient error:", good)
print("equal microbatch weighting error:", bad)
```

<a id="torch-3-detail-37"></a>
### 10.2 从实验结果反推错误机制

错误方案不是“累积失效”，而是优化了另一个目标：三个微批各占三分之一。中间那个三样本微批中，每个样本的权重低于两个二样本微批中的单样本。若数据恰好在批次间均匀、梯度相近，误差可能看起来很小，所以应使用不平衡大小与不同目标建立敏感反例。测试应主动放大可能错误，而非依赖随机情况下刚好接近。

将同样逻辑迁移到词元时，分母应是所有有效目标词元数，而不是输入词元数，更不是填充后的张量元素总数。自回归任务还可能移位，输入与目标可评分位置并不相同。若按样本等权，则先对各样本有效位置求均值，再按样本权重汇总。程序中的两个均值位置不同，表达的统计对象也不同。

若加入正则项，需要明确每次有效更新只计一次，或按微批权重分摊成总和恰好一次。把完整正则项加到每个微批再累计，会把正则强度放大为微批数量倍。解耦权重衰减又由优化器更新执行，应按真实更新次数解释。归一化测试应同时覆盖数据项与正则项，才能防止只在损失主体上正确。

<a id="torch-3-detail-38"></a>
## 11. 实验三：CPU 自动混合精度与边界检查

<a id="torch-3-detail-39"></a>
### 11.1 可执行的数值检查

代码固定同一模型和输入，比较单精度参考与 CPU 脑浮点自动转换的输出，验证损失和梯度有限。输出差异只作观测，不把一次小模型结果当作通用误差界。这里不测速度，没有 GPU 同步与显存实验。若读者更换硬件或版本，应重新核对算子支持与实际精度。

```python
import torch
from torch import nn

torch.manual_seed(41)
model = nn.Sequential(nn.Linear(8, 16), nn.GELU(), nn.Linear(16, 3))
x = torch.randn(12, 8)
target = torch.randint(0, 3, (12,))
reference = model(x).detach()
model.zero_grad(set_to_none=True)
with torch.autocast(device_type="cpu", dtype=torch.bfloat16):
    logits = model(x)
    loss = nn.functional.cross_entropy(logits, target)
loss.backward()
assert torch.isfinite(loss)
assert all(p.grad is not None and torch.isfinite(p.grad).all()
           for p in model.parameters())
error = (reference - logits.float().detach()).abs().max().item()
print("CPU autocast output dtype:", logits.dtype)
print("maximum observed output difference:", error)
print("finite CPU loss and gradients: passed")
```

<a id="torch-3-detail-40"></a>
### 11.2 结果如何用于后续决策

若这个实验失败，先检查当前构建是否支持所用上下文与算子，再检查输入是否已经非有限。若实验通过，只能说明这一组模型和输入的路径可执行且有限；长时间训练还可能因为梯度范围、优化器历史或困难样本出现问题。因此采用混合精度前应有短程训练对照，并在相同评价协议下比较最终质量。

如果输出差异集中在很接近决策边界的样本上，分类结果可能发生变化，而损失差异仍较小。应检查任务指标及其不确定性，而不是以最大元素误差一个数字决定一切。对于对数概率、概率校准或科学回归，绝对误差与相对误差的意义不同；误差准则需要与用途相匹配。

同样不能从“低精度输出更接近某次标签”推断数值方法更准确。标签本身含噪声，训练随机性也会影响结果。严谨比较应固定数据协议，运行足够种子，并区分数值误差、优化差异和统计波动。教学实验的作用是暴露机制、建立可检查接口，为真实任务的测量提供起点。

## 12. 练习与逐步解析

<a id="torch-3-detail-42"></a>
### 12.1 练习一：同设备是否已经满足接口

<a id="sec-7-1"></a>
问题：输出与标签都在同一设备，标签是浮点数组，数值依次为零、一、二，能否直接断定分类接口正确？

解析：先确定任务是单标签、多标签还是软目标分布。硬类别编号通常需要整数语义与正确范围；软目标需要与类别轴对应，并满足损失定义。再检查批次与类别维，确认不是把位置维误当类别维。设备一致只排除了一个错误来源，不能替代任务契约。验收应构造一个明显高置信正确预测和一个错误预测，检查损失排序符合预期。

<a id="torch-3-detail-43"></a>
### 12.2 练习二：为什么四个工作进程更慢

问题：小型内存张量从零工作进程改为四个，吞吐下降，是否说明多进程机制有缺陷？

解析：先看每个样本处理成本与进程通信成本的相对大小。若读取只是数组索引，进程启动、队列和对象传递可能占主导。再检查内部数值库线程是否与多进程相乘导致过量竞争。用固定模型和相同数据分别测启动总时间与稳定吞吐，并观察 CPU 使用率和内存。结论应限定在当前任务与硬件，不能推广成任何数据加载都不需要工作进程。

<a id="torch-3-detail-44"></a>
### 12.3 练习三：如何计算尾组的归一化

问题：预设每四个微批更新一次，最后只剩两个等大小微批，仍各除以四有什么后果？

解析：两个微批梯度的和被缩小到所需均值的一半，等价于这一步数据项使用更小系数。若正则项没有同比缩小，二者比例还会改变。应按最后组实际有效数归一化，或明确丢弃最后组。若两批大小不同，仅把四改成二仍不够，应采用总损失和除以总有效数。用本章双精度实验替换最后组大小，可直接验证。

<a id="torch-3-detail-45"></a>
### 12.4 练习四：填充为何会污染均值

问题：长度一和长度九的序列都填充到九，直接对填充后的误差取均值，会优化什么？

解析：若填充目标与输出均参与损失，模型同时被训练去拟合人为填充值；即使填充误差恰为零，除以十八而不是十，也会缩小数据项梯度。若希望词元等权，应掩码后求误差和除以十；若希望序列等权，应先分别除以各自长度，再对两序列平均。两种正确目标也不同，必须先声明。不能仅在日志里改分母，反向仍使用另一个目标。

<a id="torch-3-detail-46"></a>
### 12.5 练习五：类别重采样与损失权重

问题：按类别等概率采样后，又使用逆原始类别频率的损失权重，是否必然更公平？

解析：两种机制都提高少数类贡献，同时使用会进一步倾斜。先写出每类被抽取概率与条件损失权重的乘积，得到实际期望目标。公平性的定义可能涉及召回、误报成本或群体约束，不能由少数类权重单独决定。应选择目标分布，在独立验证集上报告各类指标及总体代价，并避免对同一验证结果反复调参后仍称其为无偏测试。

<a id="torch-3-detail-47"></a>
### 12.6 练习六：固定种子为什么还不相同

问题：训练种子不变，新增一个随机诊断样本后数据顺序改变，原因是什么？

解析：模型、诊断和采样可能共享全局随机流。新增调用消耗状态，后续排列使用了不同位置。可为采样器与诊断使用独立生成器，并记录各自状态。若有工作进程，还需管理外部随机模块与持续进程内部状态。固定种子不是一个脱离消费顺序的魔法常量；可重复性需要控制状态转移以及调用协议。

<a id="torch-3-detail-48"></a>
### 12.7 练习七：预取偏移为何不能直接恢复

问题：流已经预读到第一百二十条，但仅前一百条完成更新，检查点保存哪个偏移？

解析：若保存一百二十，恢复会跳过尚未训练的二十条；若保存一百，又必须保证来源允许重放这些预读记录。应保存与已提交更新对应的逻辑游标，并在恢复时重建预取队列，或者把队列内容纳入状态协议。外部来源若不可重放，需要持久缓冲或明确容许丢失的语义。这个问题属于消费事务边界，不能仅靠重新设置随机种子解决。

<a id="torch-3-detail-49"></a>
### 12.8 练习八：非阻塞为什么没有加速

问题：所有复制都设置非阻塞，端到端时间几乎不变，是否参数没有生效？

解析：主机返回方式和设备工作重叠不同。当前批计算依赖当前批复制，若没有独立下一批工作，依赖链仍串行；源内存路径和硬件也影响收益。再检查读取或计算是否才是瓶颈。通过时间线观察复制与计算，确认是否存在可重叠区域，并在保持生命周期正确的前提下优化。不能只根据调用耗时判断传输已经结束。

<a id="torch-3-detail-50"></a>
### 12.9 练习九：为何裁剪必须在解除缩放之后

问题：真实梯度范数为二，阈值为一，缩放尺度为一千，先裁剪缩放梯度再还原会怎样？

解析：缩放梯度范数为两千，按一裁剪后再除一千，得到范数零点零零一；正确对真实梯度裁剪应得到范数一。两者相差一千倍。这里差异来自裁剪的非线性而不是舍入。实际实现需按缩放器协议在有效组边界解除缩放一次，再裁剪并更新；不能为消除差异随意扩大阈值而失去尺度含义。

<a id="torch-3-detail-51"></a>
### 12.10 练习十：分布式本地均值为什么不够

问题：两个进程分别有一个和三个有效词元，默认平均梯度，本地均值是否给每个词元相同权重？

解析：第一个词元获得总权重二分之一，另外三个各获得六分之一，因此不等权。全局目标应让四个词元各占四分之一。可先汇总全局计数，再对本地损失和按默认梯度平均规则修正。若系统还包含梯度累积，应把整个有效更新组的计数纳入，而不是只看最后微批。通过手工指定四个不同梯度即可验证，不需要先启动大型训练。

<a id="torch-3-detail-52"></a>
### 12.11 练习十一：吞吐提高是否等于训练更好

问题：批量翻四倍后每秒样本提高一倍，固定轮数验证质量下降，如何解释？

解析：每轮样本数近似相同，但更新数减少到约四分之一；梯度噪声、学习率与正则化累计也改变。吞吐是系统指标，质量是优化与统计结果，两者需要联合比较。可以报告达到预定质量所需时间，并按合理协议重新选择学习率等超参数。不能把低质量配置的吞吐优势直接当作训练任务完成速度的优势。

<a id="torch-3-detail-53"></a>
### 12.12 练习十二：连续批次与批归一化

问题：四个微批累积得到同样有效样本数，为何批归一化模型与大批训练不同？

解析：每个微批前向使用自己的均值与方差，而大批前向使用所有样本统计，计算图中的归一化函数已经不同。反向梯度线性无法弥补前向目标差异，运行统计的更新次数也不同。可在无随机层的极小模型比较两者输出与缓冲区，再解释差异。选择其他归一化或同步统计可能改变条件，但不能因此声称任意累积都完全等价。

<a id="torch-3-detail-54"></a>
### 12.13 练习十三：可迭代分片如何验收

问题：两台设备、每台两个工作进程读取十二条记录，怎样证明既无重复又无遗漏？

解析：为四个全局消费者分配互斥标识，按序号取余分配，收集各自记录身份。核对任意两集合交集为空，集合并恰为全部十二条，总计数也为十二。然后再加入尾批规则重新计算，因为每个工作进程独立丢弃可能破坏覆盖。若数据源会变动，需固定快照或水位，否则无法在同一个集合上证明覆盖。

<a id="torch-3-detail-55"></a>
### 12.14 练习十四：为什么编译首轮不能混入稳定均值

问题：第一轮耗时十秒，后九轮各一秒，报告平均一点九秒是否足够？

解析：平均值对总计十轮的任务是真实描述，却掩盖启动与稳定阶段差别。应同时报告总时间、首轮准备和稳定分布，并说明实际任务预计运行多久。若形状不断变化，后续还会发生新的准备成本，固定形状的九次均值不能代表动态任务。质量和数值检查也应在编译路径上重复，性能变快不自动证明计算语义完整。

<a id="torch-3-detail-56"></a>
## 13. 研究拓展：把优化变成受控实验

<a id="torch-3-detail-57"></a>
### 13.1 用消融表隔离系统与统计变化

一个可读的性能研究应以基线配置为起点，每次只改变一个主要因素，并给出选择这个因素的瓶颈证据。表中记录有效工作量、真实更新数、精度、数据规则、峰值内存和质量。若某项变化不得不连带修改其他设置，应把这种耦合写清楚，而不是把多因素组合的收益归给一个开关。

研究结论也应描述适用区间。小数据集全部位于缓存时，读取策略可能看不出差异；数据超过内存后，随机读取与顺序分片可能完全不同。短序列与长序列、单机与多机、稠密与稀疏输入都有不同瓶颈。比起寻找一个“最佳工作进程数”，更值得学习的是如何测量、形成解释并预测在新规模下会怎样变化。

<a id="torch-3-detail-58"></a>
### 13.2 从性能故障回到最小反例

当吞吐突然下降，先固定一批设备内数据，排除读取；再恢复主机传输；最后恢复真实增强。若只有真实输入触发慢路径，检查形状分布、异常长样本和隐藏同步。若逐步内存上升，检查日志是否保留带计算图张量、缓存是否无界、循环是否保存完整输出。每个假设都应对应一个能使现象出现或消失的小实验。

若数值突然非有限，先恢复全精度，检查输入、损失分母与目标范围，再追踪梯度和优化器状态。性能优化不应成为错误归因的替罪羊：同一个错误可能在全精度下只是暂时未爆发。最终记录应说明触发条件、定位证据、修改及复验，而不是仅说“换个精度好了”。这种研究习惯能让训练代码在规模扩大后仍然可理解。
