## 1. 检查点保存的是哪一种状态

训练程序可以看作状态机：给定当前状态、下一份输入以及随机数，程序产生新状态和输出。模型权重只是这个状态机的一部分。一次中断之后，若只恢复权重，当前预测可能相同，但下一次更新可能已经不同。理解这个差别，才能正确区分推理发布、迁移学习、故障恢复与严格复现实验。

设训练状态由参数、优化器历史、调度阶段、随机流和数据位置共同组成。更新函数把当前状态映射到下一状态。只有恢复了更新函数实际依赖的全部信息，并且未来输入与执行规则兼容，才能期待未来轨迹一致。这是一个状态充分性问题，不是“文件能否被读取”的问题。保存格式再复杂，若漏掉数据游标，也可能重读或跳过一批。

实际项目并非都需要逐位一致。有些任务只需恢复同一个预测函数，有些需要保持学习率与动量继续优化，有些需要在固定环境中逐步复现实验，还有些只能要求统计质量接近。应该先声明所需层级，再设计检查点与验收。把无法满足的精确复现承诺藏在“已恢复成功”四个字里，会让后续研究结论难以解释。

<a id="sec-1-1"></a>
<a id="torch-4-detail-2"></a>
### 1.1 基础算例：相同权重不代表相同下一步

考虑一维带动量更新。动量由旧动量乘衰减系数再加当前梯度得到，参数再沿新动量更新。两个运行当前参数都是一，当前梯度也都是零点二，但一个运行的旧动量是零，另一个是一，取动量系数零点九和学习率零点一，下一参数分别是零点九八与零点八九。当前函数完全相同，下一步却不同。

自适应优化器还维护梯度一阶矩、二阶矩及步数。它们影响预条件与偏差校正，因此只恢复参数后重新创建空优化器，相当于从这些权重开始一个新的优化阶段。这个做法可以用于微调，但不能称为原轨迹的严格继续。若研究的问题就是优化器重启，应把它当成明确的实验干预，而不是恢复时的无意遗漏。

模型缓冲区同样影响预测。例如批归一化的运行均值、方差和计数，通常不是可学习参数，却属于模型状态。类别映射、输入标准化统计和分词词表甚至可能保存在模型外部。若这些对象改变，相同参数张量也可能表示不同函数。推理验收必须覆盖输入到输出的完整契约，而不只比较参数数量。

<a id="deep-dive-1"></a>
<a id="torch-4-detail-3"></a>
### 1.2 深入讲解：恢复未来轨迹的条件

能够影响下一次更新的对象都应被纳入审计。除了常见优化器与调度器，随机层使用的随机状态、数据采样顺序、混合精度缩放器、梯度累积位置、指数移动平均权重、回放缓冲和课程学习阶段，都可能属于训练状态。哪些必须保存，取决于实际算法，而不是检查点模板里通常有哪些字段。

恢复也依赖代码与运行环境。模型结构定义、算子语义、精度策略、设备类型和确定性选项都会影响状态转移。保存一个代码版本标识能够解释来源，却不能自动保证代码仍可用；保存依赖版本能够约束环境，却不能保证不同硬件逐位一致。因此检查点应同时记录配置和环境，并提供实测过的恢复层级。

一种可操作的分类是：参数恢复验证键与数值；函数恢复验证固定输入输出；更新恢复验证下一步参数与历史；轨迹恢复验证后续多个更新和数据身份；统计恢复验证在允许非确定性的情况下质量分布接近。每层都比前一层多提出条件。验收报告应说明通过了哪一层，而不能把一次前向比较提升为整个未来训练的证明。

<a id="torch-4-detail-4"></a>
### 1.3 推理包、最近状态与最佳模型

推理产物关注部署所需函数，可以只包含模型状态、结构配置、预处理、类别映射与版本。最近检查点关注中断后的最小损失恢复，应对应最近一次完整提交的更新。最佳验证检查点关注模型选择，应对应特定评价指标及选择时刻。这三者可能共享部分内容，却承担不同职责。

最容易出现的混搭是把最佳权重和最后一步优化器拼在一起。二者来自不同时间，历史动量不再对应当前参数。若仅用于推理，优化器无关；若继续训练，这是一种新的初始化组合，应明确命名与评估。保存完整最佳状态能继续最佳时刻的训练，但不意味着已经保留之后所有实验进度。

“最佳”本身也需要定义：指标越大越好还是越小越好，多个指标如何排序，平局如何处理，是否使用平滑值，验证频率是什么。若改变这些规则，最佳时刻可能变化。应保存用于选择的指标值、有效样本数和评价配置，避免后续只看到一个文件名却无法解释它为何被选中。

### 图解：恢复训练需要一致状态集合

![恢复训练需要一致状态集合](images/04-concept.svg)

上半图用同一动量刻度拆开历史贡献与当前梯度贡献。两条分支都从 $`w=1`$ 出发，下一梯度同为一；区别只是旧动量为 $`0.5`$ 还是零。采用 $`v'=0.9v+g`$，完整恢复产生 $`0.45+1=1.45`$，清空历史只得到一。下半图再把这两个动量乘以学习率 $`0.1`$，映射为同一参数轴上的两段位移：$`1-0.145=0.855`$ 与 $`1-0.1=0.9`$。箭头长度来自数值比例，不能由相同起点推出相同下一点。

这幅图固定数据与当前梯度，单独隔离了历史状态的影响。它采用无权重衰减、无阻尼、非 Nesterov 的 SGD 约定，并假定历史动量已经存在；其他优化器应按自己的状态转移式重新分析。该接口的具体更新约定见 [PyTorch SGD](https://docs.pytorch.org/docs/2.10/generated/torch.optim.SGD.html)。

检查点应在清楚的更新边界捕获一致状态。模型参数决定当前预测，优化器和调度器决定后续更新，随机源与数据位置决定接下来读到什么。这些仍不是对所有训练程序都完备的通用清单：微批中途保存、工作进程预取、混合精度缩放及其他算法记忆会增加状态，应以连续训练与恢复训练的实际对照验证具体范围。

<a id="torch-4-detail-5"></a>
## 2. 为检查点设计明确的数据契约

<a id="torch-4-detail-6"></a>
### 2.1 状态字典是有版本的接口

检查点应有顶层格式版本与训练任务标识，加载器据此判断哪些字段存在、如何解释。模型配置最好保存足够重建结构的基本类型，而不是直接保存整个任意对象。数据配置应记录切分标识、特征顺序、标签映射、标准化统计或其受控引用。更新配置则记录优化器类别、参数分组及调度协议。

格式版本用于表示字段语义变化，不只是代码版本变化。例如原来进度字段表示“刚完成的轮次”，后来改为“下一轮索引”，若不升级格式，就可能多训或少训一轮。迁移函数应输入旧结构，输出新结构，并明确哪些字段无法恢复。不能在捕获所有异常后随意给默认值，然后仍声称恢复完全。

可读配置与张量状态最好分清。字符串、数字、布尔值、列表和字典通常容易审计；自定义类和闭包难以跨版本重建，也扩大反序列化依赖。状态并不是越少越好，而是应该尽可能显式、稳定、可验证。对复杂对象，优先设计它的状态接口，而不是把整个活动对象直接塞进文件。

<a id="torch-4-detail-7"></a>
### 2.2 参数名称、形状与优化器映射

模型加载通常能检查参数键与形状，但同样形状仍可能对应不同语义。比如类别顺序变化后，最后一层每行的意义改变，形状完全相同却不能原样解释。特征列重新排序也会让输入层权重失去对应关系。因此结构兼容检查必须包含任务语义，而不能只依赖张量维度。

优化器状态还依赖参数组的组织和顺序。参数组数量、每组参数及超参数必须与当前算法兼容；名称相同并不意味着框架会自动按业务含义重新匹配所有历史状态。若重构代码改变参数注册顺序，应该检查映射，或实施明确且可测试的迁移。盲目忽略警告可能把某个参数的历史矩配给另一个形状相同的参数。

部分加载是合法操作，但应作为迁移学习处理。明确列出成功加载、缺失、额外和形状不匹配的字段，解释哪些层重新初始化，哪些优化器状态丢弃。验收也应按新任务定义，而不是要求原训练轨迹一致。严格加载失败时，首先诊断版本或结构问题，而不是立刻改成宽松加载来消除报错。

<a id="torch-4-detail-8"></a>
### 2.3 进度字段必须对应一个确定边界

只保存轮次通常不足以恢复轮次中途。至少需要说明当前轮次、已提交更新数、已消费样本位置、当前排列以及下一次读取位置。若有梯度累积，还要记录当前有效组是否结束。最容易实现的可靠策略是在完整更新结束、梯度清空、调度状态已推进的边界保存，此时无需恢复半成品计算图。

若业务要求在任意微批后保存，则可能需要保存各参数已累积梯度、当前累积分母、已处理微批数、缩放尺度和随机状态。计算图通常不应被当成通用持久状态；已经完成反向的梯度可以序列化，但尚未完成的前向图和激活需要另行设计重算协议。把普通状态字典当成任意时刻暂停整个进程的镜像，是不现实的。

进度应以“下一动作”解释清楚。例如游标表示下一个尚未提交样本的位置，更新数表示已经成功执行优化器更新的次数。混合精度可能跳过更新，所以读取批次数、反向次数与成功更新数不一定相同。调度器依据哪个时钟推进，也应写入契约。否则恢复后即使没有数据重复，学习率仍可能错位。

<a id="torch-4-detail-9"></a>
### 2.4 状态充分性的归纳证明

为了使“状态完整”不只是一份经验清单，可以把训练形式化。令 $`S_t`$ 表示更新边界处的全部算法状态，$`B_t`$ 表示下一组数据，$`U_t`$ 表示本次使用的随机输入，确定的更新程序记为 $`F`$，则有

$$
S_{t+1}=F(S_t,B_t,U_t).
$$

假设恢复后的状态满足 $`\widetilde S_t=S_t`$，未来输入满足 $`\widetilde B_t=B_t`$ 与 $`\widetilde U_t=U_t`$，执行的更新函数也完全相同，那么代入相同函数就得到 $`\widetilde S_{t+1}=S_{t+1}`$。对后续每一步重复这个论证，便得到整个未来轨迹相同。这是一个简单归纳证明，却清楚列出了承诺所依赖的条件：状态相等、输入相等、随机输入相等、执行规则相同。缺少其中任何一项，都不能直接使用结论。

随机生成器可以被纳入状态，此时随机输入由生成器状态确定产生，更新函数同时推进生成器。数据排列与游标也可纳入状态，使下一数据组由状态生成。这样系统可以进一步写成只依赖外部不可控输入的状态机。但真实流式数据可能包含未来才到达的记录，不能提前保存在检查点中，因此证明只能条件于相同未来输入，或转为统计分布层面的要求。

为什么模型权重不足以构成状态？从反证角度看，只要存在两个历史，它们当前权重相同，但面对同样数据产生不同下一参数，权重就不是充分状态。前文动量例子已经构造了这样的两个历史。类似地，若当前权重与动量相同而数据游标不同，下一样本不同仍会产生不同更新。状态充分性应通过这些可区分的历史审查，而不是按对象是否方便序列化决定。

有限精度执行也属于更新函数定义的一部分。相同数学公式在不同归约顺序下可能产生不同浮点结果，因此数学层面的同一函数不自动等于实现层面的逐位同一。若只要求容差内相近，需要进一步分析误差如何传播：非线性更新可能放大小差异，长期轨迹不应仅根据一步误差很小就断言一直接近。实践中通常同时采用短程精确测试和长期统计质量测试，分别回答状态遗漏与任务表现问题。

保存成本则可以用另一个简化模型理解。假设每隔固定训练时长保存一次，保存本身耗时固定，故障以很低且近似恒定的频率发生，中断时刻在间隔内近似均匀，那么每次故障平均损失约半个间隔。单位时间的额外成本由保存频率造成的开销与故障重算开销相加。这个近似说明间隔太小与太大各有代价，却没有考虑相关故障、恢复耗时、异步争用和存储限额，不能直接套成所有系统的最优策略。

实际选择时，应先测完整快照与写出的耗时，再估计可接受重复计算预算，并通过恢复演练检查保存真的可用。对短教学实验，几乎没有必要做复杂最优化；对数周任务，保存协议与数据可重放性可能比单步快几个百分点更影响总成本。把这些假设写清楚，能够让系统决策具有可审查的依据，而不只是凭习惯设置保存频率。

## 3. 实验一：连续训练与完整恢复的轨迹对照

<a id="torch-4-detail-11"></a>
### 3.1 实验设计与可证明的范围

下面构造一个小型 CPU 回归任务，使用带动量的随机梯度下降、学习率调度、丢弃层、随机输入扰动和按轮次排列的数据。样本数不是批大小整数倍，因此会自然跨过尾批。检查点保存在内存中，不创建持久文件。恢复分支重建模型和优化器，再恢复状态，并在最后恢复随机流，防止重建过程消耗随机数影响下一步。

实验比较后续每一步的样本身份、损失、学习率、最终参数与动量。再建立一个对照分支：保留同样权重、数据状态和随机流，只清除优化器历史。这样差异可以归因于动量遗漏，而不是同时改变多个因素。实验限定在同一个本地 CPU 环境，不宣称跨硬件或任意算子都能逐位复现。

```python
import copy
import io
import random
import torch
from torch import nn

torch.set_num_threads(1)
data_rng = torch.Generator().manual_seed(101)
x = torch.randn(13, 3, generator=data_rng, dtype=torch.float64)
y = (x[:, :1] * 0.8 - x[:, 1:2] * 0.3).clone()

def build():
    model = nn.Sequential(nn.Linear(3, 7), nn.Tanh(),
                          nn.Dropout(0.25), nn.Linear(7, 1)).double()
    optimizer = torch.optim.SGD(model.parameters(), lr=0.03, momentum=0.8)
    scheduler = torch.optim.lr_scheduler.StepLR(optimizer, step_size=3, gamma=0.7)
    return model, optimizer, scheduler

class Cursor:
    def __init__(self):
        self.generator = torch.Generator().manual_seed(202)
        self.order = torch.randperm(len(x), generator=self.generator)
        self.position = 0
        self.epoch = 0
    def next_indices(self):
        if self.position == len(x):
            self.epoch += 1
            self.order = torch.randperm(len(x), generator=self.generator)
            self.position = 0
        end = min(self.position + 4, len(x))
        result = self.order[self.position:end].clone()
        self.position = end
        return result
    def state_dict(self):
        return {"generator": self.generator.get_state(), "order": self.order,
                "position": self.position, "epoch": self.epoch}
    def load_state_dict(self, state):
        self.generator.set_state(state["generator"])
        self.order = state["order"].clone()
        self.position, self.epoch = state["position"], state["epoch"]

def advance(model, optimizer, scheduler, cursor, steps):
    log = []
    model.train()
    for _ in range(steps):
        ids = cursor.next_indices()
        jitter = (random.random() - 0.5) * 0.01
        optimizer.zero_grad(set_to_none=True)
        loss = (model(x[ids] + jitter) - y[ids]).square().mean()
        loss.backward()
        optimizer.step()
        scheduler.step()
        optimizer.zero_grad(set_to_none=True)
        log.append((ids.tolist(), loss.item(), optimizer.param_groups[0]["lr"]))
    return log

random.seed(303)
torch.manual_seed(404)
model, optimizer, scheduler = build()
cursor = Cursor()
advance(model, optimizer, scheduler, cursor, 5)
payload = {
    "format_version": 1, "completed_updates": 5,
    "config": {"input_dim": 3, "hidden_dim": 7, "dropout": 0.25},
    "model": model.state_dict(), "optimizer": optimizer.state_dict(),
    "scheduler": scheduler.state_dict(), "cursor": cursor.state_dict(),
    "torch_rng": torch.get_rng_state(), "python_rng": random.getstate()
}
buffer = io.BytesIO()
torch.save(payload, buffer)
frozen_bytes = buffer.getvalue()
reference_log = advance(model, optimizer, scheduler, cursor, 7)
reference_parameters = [p.detach().clone() for p in model.parameters()]
reference_momentum = [optimizer.state[p]["momentum_buffer"].clone()
                      for p in model.parameters()]

def restore(clear_momentum=False):
    state = torch.load(io.BytesIO(frozen_bytes), map_location="cpu",
                       weights_only=True)
    restored_model, restored_optimizer, restored_scheduler = build()
    restored_cursor = Cursor()
    restored_model.load_state_dict(state["model"], strict=True)
    saved_optimizer = copy.deepcopy(state["optimizer"])
    if clear_momentum:
        saved_optimizer["state"] = {}
    restored_optimizer.load_state_dict(saved_optimizer)
    restored_scheduler.load_state_dict(state["scheduler"])
    restored_cursor.load_state_dict(state["cursor"])
    random.setstate(state["python_rng"])
    torch.set_rng_state(state["torch_rng"])
    return restored_model, restored_optimizer, restored_scheduler, restored_cursor

restored = restore()
restored_log = advance(*restored, steps=7)
assert reference_log == restored_log
for expected, actual in zip(reference_parameters, restored[0].parameters()):
    assert torch.equal(expected, actual)
for expected, parameter in zip(reference_momentum, restored[0].parameters()):
    assert torch.equal(expected, restored[1].state[parameter]["momentum_buffer"])
without_momentum = restore(clear_momentum=True)
advance(*without_momentum, steps=7)
difference = max((a - b).abs().max().item()
                 for a, b in zip(reference_parameters, without_momentum[0].parameters()))
assert difference > 1e-8
print("continuous versus restored: exact CPU match")
print("omitting momentum, maximum parameter difference:", difference)
```

<a id="torch-4-detail-12"></a>
### 3.2 内存检查点仍需冻结当时的值

实验把字典立刻序列化为字节，因此后续训练不会修改已经保存的字节。若只是把模型状态字典赋给一个变量，里面的张量可能仍与模型共享存储，所谓旧状态会随更新改变。要在内存中保留快照，应深拷贝所需状态或立刻完成序列化。模型状态和优化器状态都要按各自共享关系审计，不能只复制最外层字典。

在异步保存中，这个问题更重要。若后台线程正在读取张量，前台优化器又修改同一存储，文件可能混合多个时刻的值。要么先得到一致且独立的快照，再让后台写入；要么采用框架明确支持的同步与快照协议。后台写入返回之前，还不能把该状态标为已发布。异步减少主线程等待，并不会自动提供一致性。

内存缓冲实验也不测试磁盘可靠性。字节已经完整存在，不涉及写入中断、磁盘空间不足、路径权限和文件替换。它的价值是把算法状态恢复与文件系统故障分离。第二个实验再单独处理发布流程，这样出现错误时能知道是状态遗漏还是存储协议问题。

<a id="torch-4-detail-13"></a>
### 3.3 为什么随机状态必须最后恢复

构建新模型通常会随机初始化权重，即使马上加载旧权重，这些初始化也已经消耗随机流。若先恢复随机状态再构建模型，下一次丢弃层就会使用偏移后的随机数。实验先完成所有对象重建，再恢复随机流，从而保证下一动作看到保存时刻之后的正确状态。

![对象重建可能消费随机流，恢复顺序会改变轨迹](images/04-rng-restore-order.svg)

R 表示已保存的随机生成器状态，a、b、c 只是该状态之后的三个输出标记。为看清顺序，假设模型构造恰好消费同一个随机流中的两个值：先恢复再构造，下一动作将看到 c；先完成对象重建再恢复，下一动作才重新看到 a，与连续执行对应。真实模型消费次数由实现决定，若构造使用其他独立流，则应按实际依赖分别分析；所有可能消费待恢复随机流的准备工作都应纳入恢复协议。

数据采样使用独立生成器，当前排列与游标也被保存。仅保存采样生成器状态不一定足够：随机排列可能已经整体生成，生成器已处于排列生成之后，而尚未消费的排列仍有大量元素。保存排列和已提交游标，能够直接表示这些未来元素。对于真实大型数据，也可以用可重建排列算法与种子、轮次、位置表示，但必须验证其版本稳定性。

实验中的 Python 随机扰动说明，仅恢复框架随机流也不够。真实任务若使用 NumPy、自定义生成器或多个设备随机流，应分别保存。NumPy 的某些状态对象不能原样通过受限加载协议，需要转换成受支持的张量和基本类型，再按显式版本重建。不要因为一个随机源恰好没有参与小实验，就省略真实训练中的其他随机源。

<a id="torch-4-detail-14"></a>
### 3.4 相等断言的意义与局限

本实验要求每步记录逐项相等，并比较最终参数和动量逐位相等，这比只比较一次预测更严格。它证明在当前受控 CPU 路径中，所保存状态足以恢复未来七次更新；它不是对任意模型、数据加载器和硬件的形式化证明。新增随机增强、工作进程或分布式算子后，应重新建立对应实验。

故意去掉动量的分支保留其他条件，让反例具有解释力。若同时不恢复随机数、重置学习率并重新打乱数据，即使发生差异也无法判断各因素贡献。研究时可逐项遗漏，观察第一步开始出现差异的位置，并核对理论预期。这样的故障注入能检验状态清单，而不是只验证理想路径。

完全相同也不等于算法正确。两个分支可能复现同一个错误目标，例如都把词元分母算错。恢复测试保证状态转移一致，目标正确性仍需独立的手算、梯度与数据验收。高质量训练工程把这些证明义务分开：数学目标、单步实现、状态恢复和统计评价各自有证据。

<a id="torch-4-detail-15"></a>
## 4. 训练器应该组织职责而不是隐藏语义

<a id="torch-4-detail-16"></a>
### 4.1 单步接口需要返回什么

一个训练步骤应明确输入批次、损失分子与分母、是否更新、成功更新计数和诊断指标。若梯度累积跨多个调用，接口必须说明当前是否处于有效组边界；若混合精度可能跳过更新，返回值应区分处理批次与真正更新。日志层不能靠猜测某函数调用次数来重建这些信息。

验证步骤应明确模式和无梯度上下文，按实际有效单位汇总指标。它不应修改参数、推进优化器或消耗训练专用采样器。若验证中使用随机增强，应有独立且可记录的随机协议。结束后是否恢复训练模式也要有约定，避免验证完忘记切回训练，导致丢弃层与归一化行为改变。

检查点函数负责收集一致状态、写入暂存、验收与发布，训练主循环负责决定何时调用。把这些职责拆开，能够单独测试保存失败不会破坏旧检查点，验证不会改变训练参数，日志不会推进随机采样。一个巨大类本身并不错误，但若把这些副作用隐蔽起来，复现与排错会更加困难。

<a id="torch-4-detail-17"></a>
### 4.2 配置区分结构、算法与运行资源

结构配置决定模型函数，例如隐藏层宽度和类别映射；算法配置决定更新规则，例如优化器、损失权重和调度时钟；资源配置决定设备、工作进程和日志路径。恢复时有些资源可安全改变，有些算法改变会产生新实验。按语义分类能够避免把所有配置都简单判为“必须完全相同”或“都可以覆盖”。

例如把日志输出目录改到新位置，通常不改变数学训练；把类别数改掉，显然不是同一任务；把每设备批大小改变但保持有效目标，也仍可能因为批归一化或随机性改变轨迹。配置兼容性应由具体字段规则决定，加载器可以报告允许变化与禁止变化，而不是只比较一个整段字符串哈希。

配置需要记录解析后的最终值。只保存命令行参数而不保存配置文件默认值，未来默认值改变就无法重建原实验；只保存配置文件又忽略环境变量覆盖，也会不完整。可以同时记录原始来源和最终规范化配置，后者用于实际重建，前者用于解释。敏感凭据不应作为训练语义状态写进发布产物。

<a id="torch-4-detail-18"></a>
### 4.3 指标与日志必须能指向同一状态

日志中的更新编号应与检查点进度一致。若先打印“第十步完成”，实际优化器尚未更新就保存，日志与权重会错位。若验证指标对应更新一百，但最佳文件存的是之后更新一百零一的权重，也会使模型选择证据失效。应规定事件顺序，并让每个指标附带状态标识。

失败重试也会让日志重复。可以用运行标识、已提交更新数和事件类型构成可去重键，区分重复写入与真正重复训练。不要只用墙上时间判断先后，恢复后时区或机器时钟可能变化。对于分布式任务，还需要决定哪个进程负责发布全局事件，避免各进程把本地指标误当全局指标写入同一个文件。

观察性代码不应改变实验关键状态。随机可视化使用独立生成器，模型快照需要冻结数值，指标累加器应存脱离计算图的统计。保存完整损失张量列表可能保留计算图并造成内存增长；在日志中额外前向又可能消耗随机状态。训练器组织的核心是让这些副作用可见、可控，而不是追求最少代码行。

<a id="sec-4"></a>
<a id="torch-4-detail-19"></a>
## 5. 状态清单与容易遗漏的边界

<a id="torch-4-detail-20"></a>
### 5.1 模型之外的算法状态

指数移动平均模型维护另一套历史权重，用于评价时需要保存其值与更新次数。早停策略维护最佳值和耐心计数，恢复时丢失会改变停止时刻。自适应损失权重、课程学习难度、教师模型、记忆队列和强化学习回放缓冲也可能影响未来梯度，不能因为它们不属于优化器就不保存。

混合精度缩放器的尺度与增长跟踪会影响后续是否跳过更新，应保存其状态。调度器则需与优化器真实学习率同步。创建优化器和调度器的次序以及加载顺序应按当前接口核对，避免初始化调度器覆盖刚恢复的学习率。实验采用先创建两者、再加载优化器和调度器，最后核对下一次实际使用的学习率。

冻结参数与参数组也属于算法配置。恢复时若误把原先冻结的参数解冻，或遗漏某组权重衰减，当前预测可能仍相同，之后训练就会改变。可在恢复后打印或验证每组参数名称、学习率、衰减和可训练标记。不要只检查总参数量，因为两个错误分组可能拥有相同总量。

<a id="torch-4-detail-21"></a>
### 5.2 模式、梯度与非持久状态

模型状态字典并不自动等于完整活动对象状态。训练模式标志、某些非持久缓冲、自定义缓存和普通属性可能不在常规字典中。恢复后应根据当前阶段显式设置训练或评价模式，必要时重建缓存。自定义模块若有额外状态，应提供清楚的状态接口并测试保存与加载。

参数梯度通常不由模型状态字典保存。若在完整更新边界保存并清空梯度，这不构成遗漏；若在梯度累积中途保存，它就是关键状态。还要记录累计目标分母与当前微批数，特别是最后一个不完整有效组。只保存梯度却忘记归一化阶段，恢复后可能再次缩放或提前更新。

优化器加载也不会自动证明各状态张量设备正确。迁移设备时，应检查参数引用、历史矩、计数器和当前精度策略。不同优化器对某些状态有特殊要求，因此不要把所有状态无条件转成同一种类型。先在目标设备做一个受控更新，检查有限性与预期行为，再恢复长训练。

<a id="torch-4-detail-22"></a>
### 5.3 数据版本比文件路径更重要

一个路径可能在不同时间指向不同文件，远程数据源也可能被更新。因此检查点应记录稳定数据版本、清单摘要或受控快照标识。划分规则、排除清单、预处理统计和特征顺序同样重要。模型状态完全恢复，但数据内容变化，后续轨迹就不再有相同输入基础。

摘要能检测内容变化，却不能自动说明变化是否合法，也不能独立证明来源可信。若数据太大，可记录文件清单、大小和受控版本服务引用，并根据风险选择更强校验。关键是定义可接受的一致性层级，而不是只增加一个看起来专业的哈希字段。任何摘要都必须与被校验的实际字节和规范化协议对应。

预处理代码版本也要纳入解释。相同原始文件经过不同插值、分词或缺失值策略，得到的训练张量可能不同。若这些转换具有随机性，还需要对应状态。恢复系统能够加载文件，并不等于恢复了数据生成过程；完整实验复现应从原始输入到最终张量逐层核对。

<a id="visual-04-advanced"></a>

### 图解：只恢复参数，随机轨迹仍可能改变

![只恢复参数，随机轨迹仍可能改变](images/04-advanced.svg)

## 6. 实验二：暂存、验收与原子发布

<a id="torch-4-detail-24"></a>
### 6.1 文件存在不代表可用

直接覆盖唯一检查点时，进程中断可能留下截断文件，旧状态也已被破坏。更可靠的发布协议是在目标目录创建独立暂存文件，完成写入与必要刷新，重新加载核对，再用同文件系统的替换操作发布。这样读者看到的正式路径尽量对应完整旧版本或完整新版本，而非写到一半的内容。

原子替换与断电持久性不同。替换操作的可见性保证，不自动涵盖所有文件系统、远程存储、缓存与目录项落盘行为。对象存储也可能没有普通本地文件重命名语义。应按实际存储协议设计，并在故障模型下测试。教学代码说明本地发布思路，不能被当成任意平台上的完整事务系统。

<a id="torch-4-detail-25"></a>
### 6.2 自动清理的本地发布实验

下面用临时目录测试正常发布与模拟失败。失败发生在暂存写入之后、替换之前，正式文件应仍保持旧版本。所有文件由上下文自动清理，不在学习资料文件夹留下脚本或模型。实验只读取本程序生成的状态，不演示不可信文件加载。

```python
import os
import tempfile
from pathlib import Path
import torch

def publish(target, payload, fail_before_replace=False):
    handle, temporary_name = tempfile.mkstemp(
        prefix=target.name + ".", suffix=".staging", dir=target.parent)
    temporary = Path(temporary_name)
    try:
        with os.fdopen(handle, "wb") as stream:
            torch.save(payload, stream)
            stream.flush()
            os.fsync(stream.fileno())
        check = torch.load(temporary, map_location="cpu", weights_only=True)
        assert check["format_version"] == 1
        assert torch.isfinite(check["weight"]).all()
        if fail_before_replace:
            raise RuntimeError("simulated interruption before publication")
        os.replace(temporary, target)
    finally:
        if temporary.exists():
            temporary.unlink()

with tempfile.TemporaryDirectory(prefix="ai-checkpoint-lesson-") as name:
    directory = Path(name)
    target = directory / "latest.pt"
    publish(target, {"format_version": 1, "step": 1,
                     "weight": torch.tensor([1.0, 2.0])})
    previous = target.read_bytes()
    try:
        publish(target, {"format_version": 1, "step": 2,
                         "weight": torch.tensor([3.0, 4.0])},
                fail_before_replace=True)
    except RuntimeError:
        pass
    assert target.read_bytes() == previous
    assert list(directory.iterdir()) == [target]
    publish(target, {"format_version": 1, "step": 2,
                     "weight": torch.tensor([3.0, 4.0])})
    loaded = torch.load(target, map_location="cpu", weights_only=True)
    assert loaded["step"] == 2
    assert torch.equal(loaded["weight"], torch.tensor([3.0, 4.0]))
    assert list(directory.iterdir()) == [target]
print("local publication and pre-replace failure preservation: passed")
```

<a id="torch-4-detail-26"></a>
### 6.3 发布与保留策略也是状态管理

最近检查点可以按固定更新间隔保存，最佳检查点按验证事件保存，还可以保留少量历史版本用于回退。保存太频繁增加暂停与存储成本，太稀疏则增加故障后的重复计算。应依据保存耗时、故障概率与可接受恢复损失选择间隔，而不是每个批次都无条件保存完整状态。

发布最新指针应发生在新状态验证完成之后。若先更新指针再上传实际对象，消费者可能读到不存在或未完成的版本。异步分布式保存还需要等待所有必要分片可用，再发布清单。清理旧版本既要确认新版本可恢复，也要遵守读取者的版本保留协议，避免保存失败后失去恢复点，或让尚在读取旧分片的进程中途失去文件。

读取多分片检查点时，一次恢复应先固定一份清单，再按其中不可变的版本引用读取全部分片，不能逐片重查“最新”入口。每片单独校验成功仍可能拼出跨版本状态；清单应同时约束分片身份、参数布局和更新边界。版本回收必须考虑还未打开所有分片的读者，仅有新版本已发布不能推出旧版本可立即移除；具体交错反例见[Python 文件发布中的读取快照](../Python/03-文件异常环境与脚本组织.md#python-publication-snapshot)。

最好定期做真正的恢复演练。文件大小正常、键齐全和校验和一致，仍不能证明能重建模型并执行下一步。一次小规模冷启动恢复，比长期积累未验收的文件更有价值。演练应使用独立新对象，避免由于原进程仍保有未保存状态而掩盖遗漏。

<a id="torch-4-detail-27"></a>
## 7. 安全加载与兼容迁移

<a id="torch-4-detail-28"></a>
### 7.1 受限加载能做什么

反序列化是一段程序边界。对自己生成且来源可控的检查点，优先保存张量与基本类型，并显式采用受限加载模式。它减少任意对象反序列化带来的执行风险，但并不把任意文件变成可信数据，也不提供来源认证、资源耗尽防护或语义正确性保证。文件扩展名只是约定，不能决定内容安全。

若加载器报告不受支持的对象，不应习惯性关闭限制。先确认文件来源和预期结构，检查为何保存了该对象，能否改用显式基本类型状态。为兼容历史可信产物而实施迁移时，应在受控环境进行，生成新的清晰格式，并记录迁移过程。不要把“能加载”作为唯一目标而扩大执行面。

校验和能帮助发现传输损坏，但如果攻击者可以同时替换文件与校验和，它不能证明真实性。来源认证需要独立可信渠道或签名等机制，这与训练恢复状态完整性是不同问题。教学实验没有引入外来文件，因此只验证本地格式与数值，不模拟安全对抗。真实发布流程应依据来源和使用环境选择适当边界。

<a id="torch-4-detail-29"></a>
### 7.2 设备映射与内存预算

加载时指定先映射到 CPU，可以减少在恢复对象尚未重建时意外占满目标设备内存的风险，之后再按计划放置模型与状态。它不会消除主机内存需求，文件中张量大小仍可能很大；内存映射等选项也有特定格式与生命周期条件。应预先估算模型、优化器历史、快照副本和加载峰值，而不是只看参数文件大小。

严格轨迹恢复通常要求兼容硬件与运算路径。把检查点从 GPU 迁到 CPU，可以验证函数或继续优化，却不应承诺之后逐位相同。不同精度、并行归约顺序和算子实现会引入差异。应重新规定容差与验收层级，并在报告中把迁移与原地恢复区分开。

模型并行或分片优化器把状态分散在多个进程，单个文件可能只包含一部分。改变设备进程数需要重新分片协议，普通单机字典加载不能自动解决。可使用框架提供的分布式检查点接口，但仍需审计全局步骤、各进程随机状态、数据位置和发布清单。封装工具减少实现工作，不替代语义检查。

<a id="torch-4-detail-30"></a>
### 7.3 兼容迁移应产生可解释的新状态

模型结构升级后，某些权重可以映射，某些必须重新初始化。迁移函数应明确名称映射、形状规则和初始化来源，并对关键输入验证新输出。若类别扩展，新行初始化和旧行保持需要单独检查；若特征重排，应按字段身份重排对应权重，而不是仅保持相同形状。

优化器历史未必能与模型迁移同样处理。参数维度变化后，历史矩是否扩展、重置或局部映射会改变算法。最诚实的做法是声明这是从已有权重开始的新训练阶段，并记录继承了哪些状态。只有迁移规则与算法语义经过验证，才应称其为某种受定义的连续训练。

配置迁移应尽可能纯粹：读入旧结构，验证版本，输出新结构，不偷偷依赖当前默认值或外部可变文件。迁移后的状态可以保存为新版本，并保留来源摘要。测试应包含合法旧状态、缺字段状态、非法维度和未知版本，保证失败是清晰的，而不是在长时间训练之后才暴露。

## 8. 进阶：微步边界、预取与分布式一致性

<a id="sec-6-1"></a>
<a id="torch-4-detail-32"></a>
### 8.1 完整状态不止是对象清单

状态清单列齐并不等于快照一致。模型在更新一百步、优化器在更新一百零一步、游标在已预读一百二十批时，各字段单独都有效，组合却没有对应的真实训练时刻。应先定义提交边界，再在边界捕获相互一致的字段。必要时短暂停止更新与数据提交，冻结快照后再异步写出。

分布式场景还要区分全局状态与进程局部状态。模型参数可能同步，但每个进程的随机流、数据分片位置与某些局部缓冲不同。只让主进程保存自己的随机状态，无法恢复其他进程的未来随机路径。保存协议应覆盖所需局部状态，并让所有分片引用同一个全局更新标识。

同步点本身也要谨慎安排。若某些进程在保存时进入通信，其他进程仍在不同计算阶段，可能出现等待甚至死锁。应使用框架支持的集体保存协议或明确协调流程，而不是随意在任意异常处理分支中加一个同步。异常恢复需要考虑哪些进程仍存活、哪些通信已经失败，不能把正常路径的同步照搬过去。

<a id="torch-4-detail-33"></a>
### 8.2 预取意味着读取位置领先于训练位置

工作进程通常提前获取下一批，因此采样器的“已发出索引”可能领先于优化器真正使用的数据。若检查点保存这个领先游标，恢复会漏掉队列里尚未训练的批次。若保存已提交游标并重建队列，则需要保证预处理可重放或按身份确定随机增强。这个差别在单进程、零预取的小实验中不会出现，必须在真实管道中单独测试。

持续工作进程还保存自己的随机状态与缓存。主进程重新设置种子，未必能恢复它们。精确中途恢复可以采用更简单的策略：只在轮次边界保存，并约定重建工作进程；或者采用显式可状态化的数据管道；或者允许重放最近一段并把这种语义记录下来。选择取决于恢复精度要求与工程成本。

外部流如果不可重放，数据状态还涉及消息确认、水位与持久缓冲。模型检查点与消息确认若不是同一事务，故障可能导致重复或遗漏。通常需要明确至少一次、至多一次或更强的消费语义，并检查学习算法能否容忍重复。不能因为模型文件使用原子替换，就宣称整个数据与训练系统已经端到端原子化。

<a id="torch-4-detail-34"></a>
### 8.3 非确定性下怎样验收

确定性设置可以减少某些差异，但可能影响性能，也不保证跨版本、跨设备完全一致。应先明确是否真的需要逐位相等。调试状态遗漏时，受控 CPU 小实验非常有效；生产训练如果包含不保证确定性的算子，可以使用预先规定的数值容差与统计验收，并记录环境条件。

容差不能成为掩盖系统错误的工具。若恢复后的第一步使用了不同样本，参数差异不是简单数值噪声；若学习率错位，差异会有系统方向。应先比较离散元数据，如样本身份、更新计数和调度阶段，再比较损失、梯度与参数。只有离散契约一致后，才有理由把小差异归于浮点与执行顺序。

统计验收需要足够独立重复与合适指标。单次最终准确率相近，可能只是巧合，也可能掩盖校准或少数类质量差异。应按照任务预设质量标准，比较均值、波动和必要分组指标，同时说明样本量限制。复现层级越宽松，解释应越具体，而不是用“差不多”替代证据。

<a id="visual-04-mechanism"></a>

### 图解：更新边界与微批中途恢复的差别

![更新边界与微批中途恢复的差别](images/04-mechanism.svg)

图用一个标量回归例子显示“参数未变”为什么不能推出“没有新状态”。取 $`w=2`$，三个输入为 $`1,2,3`$，目标均为零，逻辑批目标固定为

$$
L(w)=\frac16\sum_{i=1}^{3}(wx_i)^2,
\qquad
\frac{\partial L_i}{\partial w}=\frac{w x_i^2}{3}.
$$

每个单样本微批都使用同一个分母六，且组内不更新参数，因此导数贡献依次为 $`\frac23,\frac83,6`$。第二个微批反向完成时，参数仍为二，但梯度字段已经存有 $`\frac{10}{3}`$。完整恢复再处理第三批，梯度成为 $`\frac{28}{3}`$；学习率 $`0.1`$ 的普通 SGD 更新后，参数为 $`2-0.1\times\frac{28}{3}=\frac{16}{15}`$。若只恢复参数与指向第三批的游标，前两批梯度消失，参数会误变成 $`1.4`$。

这说明微批中途可以恢复，但必须增加保存内容，而不是绝对禁止在中途取检查点。本图只采用无动量、无衰减、无混合精度的 SGD；现实训练还要把累计分母、缩放阶段、微步位置和随机状态一起对齐。反过来，约定只在一次完整更新、调度和清梯度之后保存，能够省去半组梯度，从而简化状态协议。

还可选择回退到前一个完整组边界重放三个微批，此时应恢复该边界的参数、随机与数据状态，并确保没有同时恢复前两批梯度，否则会重复计入。选择“保留部分结果”还是“回退重放”，必须贯穿同一份恢复协议，不能只在模型权重层面决定。

## 9. 练习与逐步解析

<a id="torch-4-detail-36"></a>
### 9.1 练习一：只加载权重属于哪种操作

问题：从训练二十轮的模型加载权重，重新创建空的自适应优化器，继续训练，是否属于完整恢复？

解析：当前函数可能恢复，但历史一阶矩、二阶矩和步数缺失，下一步预条件与偏差校正改变。这是从已有权重开始的新训练阶段。若目标是微调，可以这样做，但应记录优化器重启与新调度。若目标是故障恢复，需要加载对应优化器状态并验证后续更新，而不是仅比较固定输入输出。

<a id="sec-8-2"></a>
<a id="torch-4-detail-37"></a>
### 9.2 练习二：加载成功是否证明继续训练等价

问题：键与形状全部匹配，也没有异常，是否可以宣布轨迹恢复成功？

解析：这只证明格式层面的部分兼容。先检查输入预处理与类别映射，再比较固定模式的预测；然后检查优化器、调度、随机状态和数据游标，并比较后续若干更新。若模式或采样不同，当前预测甚至也可能不一致。加载器不理解全部业务语义，因此不报错不能代替恢复实验。

<a id="torch-4-detail-38"></a>
### 9.3 练习三：最佳权重搭配最后动量

问题：把验证最好的一轮权重与最后一轮动量组合后继续训练，为什么值得单独命名？

解析：动量总结的是另一条参数历史，当前权重与历史方向不再对应同一状态。下一步可能产生不符合任一原轨迹的更新。可以把它作为有意干预研究，但不能称为从最佳轮次严格继续。若要继续最佳时刻，应保存该时刻完整状态；若只发布推理模型，优化器则可以省略。

<a id="torch-4-detail-39"></a>
### 9.4 练习四：字典副本为何不是张量快照

问题：用普通字典复制保存参数状态，继续更新后发现“旧权重”也变了，如何解释？

解析：外层容器复制不保证内部张量存储独立。模型更新修改共享存储，旧字典看到的值同步变化。应对所需状态深拷贝，或立即序列化成独立字节。验收时先记录固定参数值，继续训练，再加载快照确认回到旧值。异步保存还需保证拷贝过程与更新不会并发混合多个时刻。

<a id="torch-4-detail-40"></a>
### 9.5 练习五：为什么只有种子不够

问题：保存初始种子后训练五千步，中断时重新设同一种子，是否回到中断位置？

解析：种子规定流的起点，五千步已消费大量随机数。重新设置会回到开头，不会自动跳到中途。可以保存当前随机状态，或严格重放全部消费，但后者通常昂贵且脆弱。采样器还可能提前生成排列，因此需要保存当前排列与已提交位置。多个随机源应分别处理，不能假设框架种子控制所有库。

<a id="torch-4-detail-41"></a>
### 9.6 练习六：恢复随机状态为何放在重建之后

问题：先恢复随机状态，再创建模型并加载权重，下一步丢弃层与原运行不一致，原因是什么？

解析：模型构造中的随机初始化消耗了恢复后的随机流，即使权重随后覆盖，消费已经发生。应先完成对象重建与状态加载，再恢复未来计算需要的随机状态，且之后避免额外随机诊断调用。若某些对象构造必须依赖独立随机源，可显式隔离生成器。实验应比较下一步随机输出，而不是只检查加载权重相等。

<a id="torch-4-detail-42"></a>
### 9.7 练习七：调度器应该保存哪个时钟

问题：混合精度跳过一次优化器更新，程序仍推进学习率调度，恢复时只记录批次数会怎样？

解析：批次、反向和成功更新已经不再一一对应。若算法规定按成功更新调度，原程序就存在时钟错误；若规定按处理批次调度，则要完整记录该协议。恢复系统必须保存相应计数及调度内部状态，并核对下一步实际学习率。不能只根据某个轮次字段猜测调度阶段，更不能在恢复时无说明地换成另一协议。

<a id="torch-4-detail-43"></a>
### 9.8 练习八：微批中途保存需要什么

问题：累计四个微批更新一次，第二个微批反向后保存，只保存参数与优化器够不够？

解析：参数尚未更新，前两个微批的梯度存在参数梯度字段中，常规模型状态字典不包含它们。还需保存累计梯度、有效分母、微步位置、缩放状态和后续数据游标，或选择回退到完整组边界重放。若直接清空后继续第三个微批，前两批贡献丢失；若重新处理前两批又恢复了梯度，则会重复累计。

<a id="torch-4-detail-44"></a>
### 9.9 练习九：预取游标领先导致什么

问题：采样器已发出十个批次，实际只更新八个，保存位置十并恢复会漏掉什么？

解析：队列中的第九和第十批尚未参与更新，却被恢复游标当成已消费，因此遗漏。应以已提交更新对应的数据位置为准，重建未来队列，或者保存队列及其增强状态。若数据源可重复读取，重放较容易；若不可重复，就需要持久缓冲或更强事务设计。把工作进程数量设为零只是简化测试，不能自动修复生产协议。

<a id="torch-4-detail-45"></a>
### 9.10 练习十：原子替换是否等于永不丢失

问题：使用同目录暂存并替换，是否可以保证任意断电与远程存储故障后都有最新文件？

解析：原子可见性与持久化是不同保证，文件与目录项的落盘、存储缓存和远程协议都会影响结果。教学实验只证明替换之前的模拟失败不会破坏旧正式文件。需要根据目标文件系统制定刷新、备份和恢复策略，并做相应故障测试。应避免把一个本地成功实验推广为所有存储系统的完整事务证明。

<a id="torch-4-detail-46"></a>
### 9.11 练习十一：校验和能证明来源吗

问题：下载文件和同目录校验和完全匹配，是否可以直接信任任意反序列化对象？

解析：校验和说明文件与所给摘要一致，但如果两者都被替换，真实性仍无保证。来源信任需要独立可信渠道等机制。即使来源可信，也应优先用受限格式与显式状态，避免无必要的任意对象加载。恢复正确性还需要结构和数值验收，摘要正确不能证明优化器状态与权重属于同一步。

<a id="torch-4-detail-47"></a>
### 9.12 练习十二：类别顺序改变但形状相同

问题：分类器仍有十个输出，类别列表交换了两项，严格加载没有报错，预测是否仍正确？

解析：权重每行对应的语义已经变化，形状检查无法发现。应恢复原类别映射，或显式重排输出层权重、偏置及相关优化器历史，并验证已知样本。若映射无法确认，应拒绝宣称原函数已恢复。类似问题也出现在表格特征顺序与文本词表索引，说明业务契约比张量形状更强。

<a id="torch-4-detail-48"></a>
### 9.13 练习十三：验证如何污染训练状态

问题：每次验证都随机抽取训练样本画图，恢复后训练轨迹不同，可能有哪些原因？

解析：可视化若使用训练随机流，会改变后续采样或丢弃层；若额外前向处于训练模式，还可能更新归一化缓冲。应使用独立生成器与明确评价模式，并在完成后恢复阶段约定。保存日志张量时应脱离计算图，避免内存累积。验证函数也应有独立测试，确认参数与不该改变的训练状态保持不变。

<a id="torch-4-detail-49"></a>
### 9.14 练习十四：改变设备数量如何解释

问题：从四进程检查点改为两进程继续训练，只要总批量不变，就能逐位延续吗？

解析：数据分片、随机流归属、归约顺序和批内操作都可能改变，即使总样本数一样也不保证轨迹相同。分片优化器还需重新分片状态。可以定义保持目标与大致训练阶段的迁移恢复，但应重新声明验收层级。若研究要求严格轨迹，应保持兼容执行条件，并用真实跨进程恢复测试证明所需性质。

<a id="sec-8"></a>
<a id="torch-4-detail-50"></a>
## 10. 进阶研究：把恢复当成可验证的状态转移

<a id="sec-8-1"></a>
<a id="torch-4-detail-51"></a>
### 10.1 综合练习：恢复后从哪一层证明正确

问题：为一个包含随机增强、混合精度和梯度累积的训练系统设计验收，如何避免只测试文件读写？

逐步解析：先建立固定合成数据上的数学目标基准，核对完整批与累计梯度。再验证模型快照的键、参数、缓冲和固定输入输出。随后固定更新边界，比较连续运行与中断恢复后的数据身份、随机增强、学习率、缩放状态、梯度和参数。最后逐项加入工作进程、设备与分布式执行，明确每次放宽的确定性条件。

验收应包含故障注入：遗漏动量、恢复错误游标、在替换前失败、篡改格式版本和改变类别映射，确认系统能够发现或产生预期反例。只有成功路径测试，可能因为实验没有真正依赖某字段而掩盖遗漏。故障注入的重点是每种失败都有解释清楚的观测，不是简单增加异常数量。

还应测试轮次边界、尾批、不完整累计组和验证恰好发生在保存前后的情况。边界最容易出现进度偏一，因为不同字段可能分别采用已完成数与下一索引。定义统一事件时序后，将每个检查点还原为“下一动作应该是什么”，能显著简化推理。恢复系统的最终产品是可预测的行为，而不仅是一个序列化文件。

<a id="torch-4-detail-52"></a>
### 10.2 用状态机不变量审查训练主循环

可以为每个更新边界建立不变量：所有参与本步的梯度已经消费，成功更新计数与调度阶段匹配，数据提交游标对应已用样本，日志指标引用同一状态，下一组梯度尚未开始。保存只在这些不变量成立时执行，便能减少必须持久化的半完成状态。若需要更细粒度中断，再显式增加状态与不变量。

把训练循环写成事件序列也便于检查异常。读取、前向、反向、更新、调度、清梯度、提交游标、验证、保存等事件各自可能失败，应定义失败后从哪里重放。某些事件可重复执行，某些事件会产生不可逆外部副作用。对日志可用幂等键，对外部消息确认则需要更强协议；不要假设所有操作都能无代价重试。

对于研究项目，完整事务系统可能过重，但清楚定义更新边界通常成本很低。先做到小模型可恢复、状态可解释，再逐步扩展并行与异步，比一开始引入复杂训练框架却无法解释一步更新更可靠。框架的价值应是实现已理解的协议，而不是用抽象层替代对算法状态的理解。

<a id="torch-4-detail-53"></a>
### 10.3 恢复精度与工程成本的取舍

逐位轨迹恢复有利于调试和精细消融，但可能要求固定硬件、确定性算子、可重放数据与严格状态捕获，成本很高。统计恢复允许更多资源调整，却需要更强的评价设计和更多重复实验。两者都可以合理，关键是需求与声明一致。对于长任务，保持优化器和调度状态的可靠恢复通常已经能减少大量重复计算。

如果决定只在轮次边界保存，应估算最坏重复训练量，并明确这不是任意微步恢复。若允许重放最近若干批，应说明日志、数据来源和随机性如何处理重复。若只发布权重用于推理，应保留完整输入输出契约，并且不要让使用者误以为可以从这个包严格续训。简洁来自准确限定能力，而不是隐去必需状态。

最终交付应包含可读配置、明确状态版本、恢复入口说明和至少一个实测对照。对于本章资料，代码保留为 Markdown 中可复制的学习实验，所有暂存由内存或自动清理目录承载。读者应把这里的状态分析迁移到自己的算法，列出真正影响未来更新的对象，并通过连续与恢复对照验证，而不是机械复制一份永远不完整的字段列表。
