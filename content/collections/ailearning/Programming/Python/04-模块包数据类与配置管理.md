## 1. 模块是可导入的职责边界

模块提供独立命名空间，也可以成为一个职责边界。普通项目里一个 Python 文件常对应一个模块，相关模块可以组成包。模块让函数有稳定位置，避免所有名字堆在同一脚本；更重要的是，它决定哪些逻辑依赖哪些逻辑。合理拆分能让计算不依赖命令行、数据结构不依赖训练入口、展示不干扰核心算法。

导入不是纯粹的文本粘贴。模块初始化时顶层语句会执行，之后模块通常被缓存到进程的模块表。反复导入相同模块通常复用同一个模块对象，因此模块里的可变状态可能持续存在。把训练放在顶层，会让仅仅想复用一个函数的人也触发训练；把实验列表放在全局并不断追加，会让同一进程中的多个任务共享历史。

命名空间帮助避免冲突。使用模块名前缀可以清楚显示函数来自哪里；大范围星号导入则容易覆盖已有名字，让读者难以追踪来源。别名适合约定俗成的数值库或明显冗长名字，但不应把多个含义不同的模块都缩成随意单字母。代码越依赖隐式来源，重构与调试越困难。

包内相对导入表达同一包中的关系，绝对导入表达从顶层包起的定位。两者都有合理用途，关键是保持一致并按正确方式启动。一个文件直接按路径执行时，包上下文可能与用模块方式启动不同，所以相对导入失败不一定表示文件缺失。不要每次遇到问题就临时插入搜索路径，这可能让同名模块解析到意外位置。

模块命名也影响导入。若项目文件取名与常用标准库模块相同，当前搜索位置可能让你的文件遮蔽原模块，导致看似莫名其妙的属性缺失。发现“明明装了却导入错了”时，可以查看实际模块位置，而不是反复安装。包名、文件名与公开接口一起构成项目可理解性，不只是外观整理。

拆分尺度要根据变化边界。一个几十行工具无需十几个层级；数据解析、模型结构与训练调度增长到各自需要独立测试时，分模块很自然。不要为了追求文件数量，把一个连续逻辑切成每个只有一行且互相循环调用的片段。好的模块边界减少读者同时需要记住的信息，而不是增加跳转次数。

<a id="sec-1-1"></a>
### 基础算例：模块导入与主入口的最小分工

设有一个成绩汇总程序。数据模块负责读取并验证记录，计算模块接收合法记录并汇总，入口模块解析路径与选项，然后调用前两者。计算模块不应反过来导入入口，只为了读取一个全局阈值；阈值应作为参数传入，或放在独立的稳定配置结构里。这样计算可以用三条内存记录验证，不需要构造命令行环境。

导入入口模块本身也不应立即创建结果目录。主入口判断下调用主函数，明确执行时才产生外部动作。测试可以导入 main 并传入参数列表，或者通过子进程验证真正命令行。两种层级提供不同证据，不能只用“import 没报错”代替完整运行，也不能每次测试一个函数都启动全流程。

当默认阈值变化时，只有配置来源应改变，数据与计算模块仍消费同一有效配置。若阈值分别写在三个文件里，就会出现局部更新。模块拆分本身不能解决重复事实，必须让参数有唯一来源，并沿明确方向传递。第八节会把这个原则写成完整可运行配置解析器。

## 2. 数据类表达稳定配置

数据类减少字段定义、初始化和表示等重复代码，适合表达字段相对固定的配置或结果。它的主要价值是结构清楚，不是自动让数据合法。注解为整数的字段仍可能被传入字符串；学习率即使是浮点数，也可能为负或非有限；两个单独合法字段也可能互相冲突。业务验证仍需要显式执行。

初始化后检查适合把单个对象的不变式集中起来。创建成功意味着配置已经满足约定，而不是要求每个使用者记得再调用 validate。但不要让这种检查顺便读大文件、启动设备或创建输出目录，否则普通对象构造会变得昂贵且有副作用。路径是否存在属于运行环境验证，可以在入口另一步执行，结构与资源检查不必混在一起。

冻结数据类限制普通字段重新赋值，有助于防止执行中悄悄改配置。它不会递归冻结内部列表或字典，也不构成防恶意访问的安全边界。若需要稳定配置，可以优先使用元组、不可变标量和嵌套冻结结构，或在规范化阶段建立独立快照。不能看到 frozen 标记就断言整个对象图永远不变。

默认可变字段应通过工厂建立每个实例自己的容器。即使工具会拒绝某些明显危险默认值，也不能把这种检查当作全部共享风险的证明。工厂若每次返回同一个全局列表，实例仍会共享；传入的外部列表也可能被保存引用。真正的独立性来自创建与所有权规则，不是某个参数名字。

```python
from dataclasses import dataclass, field, FrozenInstanceError

@dataclass
class MutableNotes:
    notes: list[str] = field(default_factory=list)

@dataclass(frozen=True)
class FrozenEnvelope:
    labels: list[str]

first, second = MutableNotes(), MutableNotes()
first.notes.append("one")
assert second.notes == []
envelope = FrozenEnvelope(labels=["A"])
envelope.labels.append("B")
assert envelope.labels == ["A", "B"]
try:
    envelope.labels = ["C"]
except FrozenInstanceError:
    pass
else:
    raise AssertionError("ordinary field assignment should fail")
```

这个例子故意展示冻结外层与可变内部之间的差异。它不是推荐用冻结对象保存会变化的配置标签，而是让你知道工具究竟保证什么。若字段应不可变，构造前转为元组并验证每个元素更直接；若字段本来代表运行日志，则它也许不应属于稳定配置对象，而应放在独立运行状态中。

<a id="sec-2-1"></a>
### 机制展开：配置的数据结构不等于配置校验

配置验证可以分为形状、类型、单字段范围、交叉关系与环境条件。形状检查必需字段和未知字段；类型检查防止字符串冒充数值；范围检查批量正数；交叉关系检查验证比例与切分方式是否一致；环境检查数据路径和设备。分层之后，错误能更准确定位，也能避免每次构造配置都重复昂贵外部检查。

布尔值是一个典型边界。某些语言关系允许它按整数表现，但业务上批量大小为 True 通常不是合理表达。若接受自动转换，必须规定转换规则；若采用严格模式，应显式排除。对命令行和 JSON 文件，数字、字符串与布尔来源不同，不能靠 Python 的真假转换统一处理。

<a id="deep-dive-2"></a>
### 深入讲解：配置对象如何变成可复现执行

有效配置应是所有来源按规则合并、转换并验证后的结果。训练函数、日志和产物保存读取同一对象，可以避免记录与实际行为脱节。若运行中需要改变学习率调度状态，应把它视为算法状态，而不是修改最初配置来伪装原始输入从未变化。输入配置与动态状态各有角色。

保存配置时还要把不能直接 JSON 表示的值转成明确形式，例如 Path 变成规范路径字符串，元组变成约定数组。通用序列化不一定保留所有 Python 类型身份，因此加载后仍需模式化重建。数据类转字典可以方便输出，但它不是自动生成稳定外部协议，更不替代版本字段和迁移规则。

配置对象的相等也有边界。默认字段比较可能包含输出目录或备注，导致科学参数相同而配置不相等；反过来，如果排除数据版本字段，两个语义不同实验可能被错误归为相同。要为比较目的定义身份范围，例如科学参数、资源预算和运行位置分别比较，不要盲目把整个对象默认相等当作实验等价。

## 3. 命令行与配置优先级

命令行适合指定本次运行的少量覆盖，文件适合保存可审阅的参数集合，代码默认值提供基础行为。常见规则是默认值先、文件其次、命令行最后。规则本身不唯一，但必须明确且稳定。未知字段应尽早报错，否则学习率拼写错了可能被忽略，实验仍按默认值运行，用户却以为比较了新参数。

最容易犯的错误是让命令行解析器预先给每个选项填默认值，再把整个命令行字典覆盖配置文件。即使用户没有写该选项，解析器默认值也会冲掉文件值。正确做法之一是只收集显式提供的命令行字段，例如采用抑制缺省字段机制，再按层合并。缺省与显式设置成某个值，必须可区分。

布尔开关不能用对任意字符串取布尔值的方式解析，因为非空字符串 False 仍为真。可以用明确正负开关或专门文本解析器。若想让命令行能够覆盖文件里的 true 为 false，就必须提供表达关闭的方式，只有一个开启标志可能不够。设计选项时要考虑双向覆盖，而不只是从默认关闭到开启。

路径的来源决定相对基准。文件配置中的相对路径可以按该配置文件父目录解释，命令行相对路径可以按启动目录解释，但如果选择这种分层规则，合并后应立即解析并保存来源，避免把两种相对字符串混在一起再用同一基准解释。也可以统一要求数据根目录，重点是不能隐式变化。

参数帮助信息属于接口。说明单位、合法范围、默认来源和互斥关系，比只写“设置参数”更有用。参数很多时可以按职责分组或子命令组织，但不必一开始引入复杂框架。命令行是把外部意图映射到内部配置的边界，保持可读与可预测比支持所有花哨缩写更重要。

## 4. 可维护性的判断

可维护性可以通过具体问题判断：能否从入口看出输入与输出，能否单独运行一个计算函数，修改图表是否无需加载模型，新增字段是否有统一校验位置，错误是否能定位到来源。文件数量、类数量和设计模式名字都只是手段。一个小而清楚的脚本可能比层层转发的框架更容易维护，一个职责混乱的大文件则可能需要拆分。

边界应降低理解成本。如果数据模块为了读取标签映射，反过来导入训练入口，入口又导入数据模块，依赖已经不合理。可以把稳定类型或常量下沉到不依赖上层的模块，或者通过参数传入。推迟导入有时能解决特定初始化问题，但若根本原因是职责互相拥有，长期只会让调用顺序更隐蔽。

重复不全是坏事，错误抽象也有成本。两段代码表面相似，却可能因未来业务方向不同而不宜强行合并；反复出现的同一配置解析规则，则应集中维护，避免错误修复只落到某一处。抽象的依据是共同语义和变化原因，不是几行字符长得一样。

公开接口与内部实现应该区分。调用者不应依赖某个内部缓存字段或文件组织细节，否则简单重构也会变成破坏性变更。对于学习项目，可以用命名约定和简短文档说明稳定入口，不必建立复杂访问控制。稳定接口越小，越容易测试和演化；但过小到只能靠读取内部状态才能使用，也说明设计不完整。

配置对象也要避免成为“上帝对象”。数据读取器通常只需要路径与解析规则，不必接收优化器、绘图颜色与远程上传凭证。传入整个大配置虽然省参数，但会扩大隐式依赖，也让单独测试需要构造许多无关字段。可以传入小型子配置或明确参数，让使用者知道每个组件真正依赖什么。

<a id="sec-5"></a>
## 5. 配置从默认值到结果的传递

配置处理可以按读取、合并、转换、验证、冻结、传递、保存七步理解。读取把不同来源变成原始字段；合并按优先级选值；转换把文本与路径变成内部类型；验证检查契约；冻结减少运行中误改；传递让各组件消费同一事实；保存为结果解释留下证据。不是每一步都必须是一个函数，但概念上分清有助于定位问题。

转换与验证的顺序不能一概而论。字符串转数值前要确认文本格式，转成数值后要检查有限性与范围；未知字段应在丢弃或重命名前检查；路径基准应在来源信息还在时解析。若先把所有值强制转成字符串，原有类型差异就丢失；若先用集合处理字段，又可能抹去重复。每次转换都要知道会损失什么。

字段间一致性校验应基于最终值，而不是分别验证各来源。默认模型宽度与文件注意力头数可能单独合法，合并后却不整除；文件启用恢复，命令行换了类别数量，也可能冲突。应在完整合并之后统一检查关系。否则“每份输入都验证过了”仍不能保证最终组合合法。

配置传入组件后，组件不应再悄悄读取另一个同名环境变量覆盖它。若某些参数必须在运行时决定，比如自动设备选择，应将解析结果记录为派生事实，并说明选择依据。这样用户请求与实际执行可以同时保存，不需要把自动解析结果伪装成用户原始输入。

结果目录中的配置最好能够重新加载得到等价有效配置，但等价范围应明确。临时运行路径、时间戳和凭证可能不属于科学参数；数据身份、模型结构与预处理规则通常属于。可以分别保存请求配置、有效科学配置和运行元信息，避免一个字段集合同时承担全部角色。小项目也可以用一个结构化文件分区表达，不必拆成许多碎片。

<a id="sec-6"></a>
## 6. 进阶：模块依赖与配置可追溯性

把模块视为有向图，边表示导入或调用依赖，可以直观看到结构。入口依赖组装组件，训练逻辑依赖模型与数据接口，稳定类型模块位于较底层。理想并不是图上没有任何共享节点，而是高层政策不被低层反向依赖。循环有时可以运行，但它让初始化与使用顺序变成隐藏前提，增加维护风险。

配置追溯则是一张来源图。最终学习率来自命令行，批量来自文件，种子来自默认值，每项都有来源。只保存最终值可以重现部分行为，保存来源还能解释为什么覆盖发生。对复杂团队实验，来源信息有助于排查“我明明改了文件却没生效”，因为可能存在更高优先级覆盖。

来源记录不等于把所有原始内容永久存储。可以保存层名、字段名与必要来源标识，凭证只保留引用，巨大环境不必全量复制。追溯信息要服务于解释与重建，不是无差别采集。来源表也需要与最终配置同步生成，手工另写一份容易再次发生偏差。

<a id="sec-6-1"></a>
### 配置优先级怎样形成一个确定实验

默认学习率零点零一，文件设成零点零零三，命令行显式给零点零零一，则最后应为命令行值；用户未写命令行学习率时，应保留文件值。这个两行推理足以暴露常见解析默认值错误。测试至少覆盖“显式覆盖”和“没有覆盖”两种情况，不能只检查最终值是某个合法正数。

若命令行显式设置关闭，不能把假值当作未提供；若合法设置为零，也不能用真假判断决定是否覆盖。来源缺失与值为假是不同事实。使用键是否存在或专用缺省标记来判断，可以保留这个差异。第一章讨论的零、空值与假值语义，在配置系统里会再次出现。

恢复实验还需要比较兼容性。日志显示频率变化可能允许严格续接，模型结构或特征顺序变化通常不允许，预算增加则要明确是否属于允许扩展。可以为字段定义兼容策略，给出差异清单，而不是仅比较整个配置是否完全相等。过严会阻止合理恢复，过宽会把新实验伪装成续接。

<a id="sec-7"></a>
## 7. 练习与逐步解析

**练习一：重复事实。** 三个函数内部都写随机种子四十二，为什么入口再设一次并不足以解决？解析：每个函数再次重置全局状态，可能让不同阶段重复同一序列，也让调用顺序和期望随机性脱节。应设计统一初始化或独立随机源，并明确哪些组件推进哪一条状态。配置集中只是开始，执行代码也必须遵守。

**练习二：冻结对象的边界。** 冻结数据类的字段是一个列表，外部追加是否必然失败？不会，冻结主要限制普通属性重新绑定，不递归冻结内部对象。若希望配置稳定，转为不可变元素组成的元组，并检查传入对象是否仍有可变内部。不能只把外层换成元组就宣布任意嵌套状态只读。

**练习三：循环导入。** 数据模块导入训练模块获取常量，训练模块导入数据模块获取读取器。解析路线是找出真正稳定事实，把它下沉到不依赖两者的模块，或者让调用者传入。不要先添加一堆函数内部导入，因为这可能只是把初始化错误推迟成调用时错误。

<a id="sec-7-1"></a>
### 边界追问：配置文件相同是否保证实验参数相同

不保证。命令行、环境、默认版本和自动解析都可能不同。即使最终参数完全相同，数据路径内容、代码版本和硬件数值环境仍可能不同。精确复现需要说明身份范围，逐层核对实际事实，不能仅凭文件名或文件文本相同就下结论。

反过来，配置文本不同也可能产生相同有效参数，例如字段顺序不同、显式写默认值与省略默认值、路径别名解析到同一版本。应比较规范化后的语义对象，并保留足够来源解释。规范化不是任意删字段，而是对已定义等价关系建立统一表示。

<a id="sec-8"></a>
## 8. 完整案例：分层合并、来源记录与严格验证

下面实现一个小型实验配置。固定字段为批量、学习率、种子和是否打乱。默认值提供完整基础，文件层只包含部分覆盖，命令行层只包含用户显式选项。每层未知字段都立即拒绝，防止拼写错误；每个最终字段保存最后来源。这个例子不读取真实文件，文件层用内存字典模拟，便于把合并逻辑与文件语法解耦验证。

配置对象在创建后检查类型与范围。学习率接受有限内置整数或浮点数，批量与种子严格要求内置整数，因此布尔值不会混入；打乱严格要求布尔。种子限定非负是本项目契约，并非所有随机库统一要求。命令行支持显式开启或关闭打乱，未提供时不会产生对应键。

```python
import argparse
import math
from dataclasses import dataclass, asdict

@dataclass(frozen=True, kw_only=True)
class Config:
    batch_size: int = 32
    learning_rate: float = 0.01
    seed: int = 42
    shuffle: bool = True

    def __post_init__(self):
        if type(self.batch_size) is not int or self.batch_size <= 0:
            raise ValueError("batch_size must be a positive integer")
        if type(self.seed) is not int or self.seed < 0:
            raise ValueError("seed must be a nonnegative integer")
        if type(self.shuffle) is not bool:
            raise ValueError("shuffle must be a boolean")
        if type(self.learning_rate) not in (int, float):
            raise ValueError("learning_rate must be numeric")
        try:
            valid = math.isfinite(self.learning_rate) and self.learning_rate > 0
        except OverflowError:
            valid = False
        if not valid:
            raise ValueError("learning_rate must be finite and positive")

def parse_explicit_cli(arguments):
    parser = argparse.ArgumentParser(argument_default=argparse.SUPPRESS)
    parser.add_argument("--batch-size", type=int)
    parser.add_argument("--learning-rate", type=float)
    parser.add_argument("--seed", type=int)
    parser.add_argument("--shuffle", action=argparse.BooleanOptionalAction)
    return vars(parser.parse_args(arguments))

def resolve_config(file_values, cli_values):
    values = asdict(Config())
    sources = {name: "default" for name in values}
    known = set(values)
    for label, layer in [("file", file_values), ("cli", cli_values)]:
        unknown = set(layer) - known
        if unknown:
            raise ValueError(f"unknown {label} fields: {sorted(unknown)}")
        values.update(layer)
        sources.update({name: label for name in layer})
    return Config(**values), sources

file_values = {"learning_rate": 0.003, "shuffle": True}
cli = parse_explicit_cli(["--no-shuffle", "--batch-size", "16"])
config, sources = resolve_config(file_values, cli)
assert config.learning_rate == 0.003
assert config.batch_size == 16
assert config.shuffle is False
assert sources == {
    "batch_size": "cli", "learning_rate": "file",
    "seed": "default", "shuffle": "cli",
}
assert parse_explicit_cli([]) == {}
try:
    resolve_config({"learn_rate": 0.1}, {})
except ValueError:
    pass
else:
    raise AssertionError("unknown field should fail")
try:
    resolve_config({"batch_size": True}, {})
except ValueError:
    pass
else:
    raise AssertionError("boolean batch size should fail")
```

手工核对合并过程：默认建立四个字段；文件只改变学习率并明确设置打乱；命令行只改变批量和打乱；种子始终来自默认。没有提供命令行学习率，所以文件值不会被解析器默认值覆盖。显式关闭保留为假，而不是被当作缺省。来源表与值在同一循环更新，减少两份记录脱节的可能。

这个实现采用浅层字段合并。若以后配置变成嵌套模型结构，不能直接宣称同样 update 就符合需求。某个嵌套字典覆盖时，是整体替换，还是递归合并子字段，列表是追加还是替换，都需要模式定义。盲目递归合并可能保留用户本想删除的旧字段，盲目整体替换又可能丢失必需默认。合并不是通用字符串技巧，而是数据语义。

错误报告可以进一步聚合多个配置问题，但要避免在结构无效时继续触发无关异常。比如根对象不是映射，应先失败，再谈字段。对于交叉约束，可以在最终对象检查后集中给出差异。大配置系统还应把来源定位到具体文件与字段路径，本例来源标签只是最小教学实现，没有冒充完整配置框架。

规范化时要有意决定数值表示。当前学习率传整数一也被接受，内部仍可能保存整数而非浮点。若需要统一序列化与哈希，可以在创建前规范成浮点，并验证转换不会溢出。不要直接修改冻结对象来补救散落转换，最好在进入稳定对象之前完成。规范化规则本身也应有测试，因为它决定哪些原始配置被视为等价。

## 9. 包入口与导入安全的最小实验

模块导入是否具有副作用，最好用独立进程验证。当前交互环境可能已经导入过模块，缓存会掩盖首次初始化行为。下面在临时目录建立一个最小包：核心模块只定义计算函数，命令行模块组织调用，包入口负责明确执行。先导入核心与命令行模块，要求没有标准输出；再按模块方式运行包，核对结果与退出状态。

这个演示创建的脚本只存在于临时目录，退出后自动清除。它不是要求你把学习资料目录改成同样布局，而是给出可以实际检验导入语义的方法。子进程使用当前解释器，避免误用系统另一个 Python；工作目录显式指定，让搜索路径与相对位置可解释。

```python
import subprocess
import sys
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as temporary:
    root = Path(temporary)
    package = root / "tinyexperiment"
    package.mkdir()
    (package / "__init__.py").write_text("", encoding="utf-8")
    (package / "core.py").write_text(
        "def total(values):\n    return sum(values)\n",
        encoding="utf-8",
    )
    (package / "cli.py").write_text(
        "from .core import total\n"
        "def main():\n"
        "    print(total([2, 3, 5]))\n"
        "    return 0\n",
        encoding="utf-8",
    )
    (package / "__main__.py").write_text(
        "from .cli import main\nraise SystemExit(main())\n",
        encoding="utf-8",
    )
    imported = subprocess.run(
        [sys.executable, "-B", "-c",
         "import tinyexperiment.core; import tinyexperiment.cli"],
        cwd=root, text=True, capture_output=True, check=True,
    )
    assert imported.stdout == ""
    executed = subprocess.run(
        [sys.executable, "-B", "-m", "tinyexperiment"],
        cwd=root, text=True, capture_output=True, check=True,
    )
    assert executed.stdout.strip() == "10"
    assert executed.returncode == 0
```

包入口文件只负责调用命令行主函数，核心计算没有读取命令行、输出路径或全局设备。这个方向允许核心在测试、笔记本和其他程序中复用。导入安静并不代表绝无副作用，定义类、注册某些对象和导入依赖仍会执行；本例只验证没有意外打印。若要求不得创建文件或访问网络，还需要相应额外检查。

命令行模块可以被导入而不执行主函数，包入口则在用户明确运行包时触发。若你直接执行包内部某个文件路径，包相对导入上下文可能不同，因此推荐给用户一个稳定启动方式，而不是列出许多未经检查的入口。启动方式本身属于项目接口，应在文档与自动化中一致使用。

大项目还可能采用源目录布局，把可导入包放在 src 下，减少当前工作目录偶然遮蔽安装结果的问题。学习阶段不必立即使用所有打包工具，但应理解它解决的是导入来源与发布一致性，而不是让文件树看起来专业。任何布局都需要在干净环境验证实际导入位置，否则本地成功可能依赖未提交文件。

<a id="sec-10"></a>
## 10. 配置模式演化：迁移、兼容与未知字段

配置格式会随项目发展变化。旧字段可能重命名，单位可能调整，默认策略可能变更。如果没有模式版本，加载器难以判断一份历史配置应该按哪套规则解释。增加 schema_version 能把变化显式化，但版本号本身不完成迁移，还需要从旧结构到新结构的确定转换与验证。

迁移应尽量单向、可测试，并保留原始来源。比如旧版字段 lr 改名为 learning_rate，可以在明确旧版本时转换；若新旧字段同时出现且值不同，应该报冲突，而不是任意挑一个。若单位从秒改为毫秒，要显式乘相应系数；仅改字段名会让参数语义错误。迁移后再次运行当前完整验证，不能假定转换永远产生合法对象。

未知字段策略取决于用途。训练配置通常应拒绝拼写错误，防止用户以为参数生效；允许扩展的插件配置可以给特定命名空间保留额外字段。不能把所有未知字段静默丢弃，也不能为了严格而拒绝专门设计的扩展区。模式要说明哪些部分固定，哪些由其他组件解释，责任边界清晰才方便协作。

弃用与删除也应区分。弃用期可以接受旧字段并给明确警告，同时输出新规范形式；真正删除后应解释替代方案。若每次加载都同时支持所有历史别名，却不处理冲突与来源，配置系统会逐渐难以预测。迁移层可以集中历史兼容逻辑，核心计算只接受当前规范对象，减少到处写版本分支。

默认值变化是一种容易忽略的模式变化。用户省略某字段时，旧版和新版可能得到不同有效配置。若希望历史实验可重建，保存有效配置而非仅保存稀疏请求；若必须重新解析旧请求，应按当时模式默认解释。否则同一个文件在新代码中运行，结果变了却看不出参数变化。

验证兼容性也要按恢复目标区分。精确续接可能要求模型结构、数据身份、优化器规则相同；仅做旧模型推理可能不需要保存训练预算；迁移到新任务则本来就是新实验。不要用一个粗糙的“版本相同”判断全部兼容，也不要只要版本不同就拒绝一切。列出具体差异和政策，更利于审阅。

模式测试可包含往返、迁移和冲突。当前对象保存后加载，应得到规定意义上的等价对象；旧样例迁移后应匹配手工预期；新旧别名冲突必须失败；未知模式版本应明确拒绝或进入经过设计的兼容路径。测试不需要保留大量中间脚本，固定小型内存配置就能表达大部分规则。

<a id="sec-11"></a>
## 11. 实验身份：规范化、哈希与外部依赖

实验身份是为某个目的定义的等价关系。比较模型方法时，输出目录和备注可能无关；恢复训练时，数据切分和参数顺序很重要；缓存预处理时，绘图颜色无关而清洗规则版本重要。不能指望一个默认对象比较或一个全部字段哈希同时回答所有问题。应先确定身份用途，再决定纳入哪些事实。

规范化让语义相同输入得到统一表示，例如固定键排序、明确数值类型、统一路径基准和单位。但不能把有意义顺序随意排序：类别列表顺序决定输出轴含义，增强步骤顺序影响结果，特征顺序影响矩阵乘法。只有在已经证明顺序无关的字段上，排序才是合理规范化。

哈希可以把规范表示映射成紧凑标识，便于目录命名与查找，但它不是数学上的绝对唯一证明。实际项目可以保存完整规范配置和强摘要，遇到冲突或可疑情况核对原文。更常见风险不是加密哈希碰撞，而是遗漏依赖：数据路径字符串相同但内容改变，模型代码变了而版本没纳入，导致相同标识对应不同执行。

路径不适合无条件作为内容身份。把文件从一个目录移动到另一个目录，字节可能相同；同一路径覆盖新文件，字节可能不同。可以同时记录逻辑数据标识、内容摘要与运行解析路径，分别回答“是什么数据”和“本次从哪里读取”。巨量数据全量计算摘要有成本，可以使用受信版本清单，但要说明依据。

数值规范化还应处理特殊表示。正零与负零在许多计算中相等，但在某些底层表示和特殊函数里可区分；整数一与浮点一是否视为相同，也取决于字段契约。非有限值通常不适合作为普通超参数，应在身份计算前拒绝。不要依赖通用序列化器恰好输出的字符串来暗中决定科学等价关系。

另一个容易遗漏的是派生默认值：批量未提供时按设备显存自动选择，两台机器可能得到不同有效批量。此时请求配置相同，执行配置不同，应同时记录自动选择规则与最终值。若缓存只用请求配置，可能复用不兼容结果。区分请求、解析与执行层，能让这类变化成为可见事实，而不是难以复现的偶然差异。

参数网格搜索还要避免身份混杂。种子、数据划分和超参数组合构成一个运行实例；同一方法多个种子的汇总又是更高层结果。若把种子从所有身份中删掉，可能覆盖单次运行；若把时间戳放进科学比较键，每次运行都被视为全新方法。可以分开定义方法键、运行键和汇总键，使层级清楚。

复现实验也不应把敏感信息纳入普通可公开配置。凭证通常不影响算法定义，应以安全引用和访问环境管理；服务版本与返回数据身份若影响结果，则需要记录。把访问令牌作为哈希输入也不能替代安全设计，因为日志、调试和原配置可能仍泄露。区分科学事实、资源定位与秘密值，更利于共享结果。

配置导出还要注意对象遍历成本。数据类转换为普通字典时会递归处理某些嵌套结构，并对其他对象采用复制行为，因此它并不总是一个廉价的字段视图。把大型数组、模型或活动资源塞进配置，再直接转字典，可能造成意外内存开销或转换失败。稳定配置最好保存构建这些对象所需的描述，而不是对象本身。

循环引用也不适合普通树形配置格式。若两个配置节点互相引用，通用递归展开可能无法得到有限的 JSON 表示。应改用明确标识表达关系，或重新设计为无环结构；不能认为数据类工具会自动把任意对象图转换成可移植协议。序列化格式能够表示的结构应当成为配置契约的一部分。

导出时还需区分请求值与派生对象。用户选择某个优化器名称与参数，运行时构造出优化器实例；保存前者通常足以解释配置，保存后者属于算法状态或检查点范畴。把两者混在同一字段里，会让重载、哈希和迁移都变复杂。保持描述与执行资源分离，既减少依赖，也让历史配置更容易审阅。

配置身份还可以帮助发现不可见变化。运行前输出一份差异摘要，显示与基准相比哪些字段改变，能让审阅者快速识别实验是否只改了目标因素。差异应基于规范对象，而不是文本行，否则字段重排会制造噪声。对于重要研究比较，明确的变化清单比一个看不懂的长哈希更有解释力。

<a id="sec-12"></a>
## 12. 依赖注入、插件与测试替身

依赖注入的朴素含义，是把组件需要的协作者显式交给它，而不是让它在内部寻找全局对象。一个评估函数接收预测器和数据，就可以用小型假预测器验证指标；若它内部固定加载巨大权重并读取某个文件，测试就会依赖许多无关条件。这个原则不要求使用专门容器框架，普通函数参数已经可以实现。

接口应说明所需能力而非具体实现。需要读取记录时，可接收返回记录的函数；需要多次操作同一状态时，可以定义协议或小型对象接口。第六章会深入结构类型，这里先从使用者需要哪些方法反推。过宽接口把无关能力带进来，过窄但没有必要结果则迫使调用者偷看内部状态，都不理想。

测试替身是用可控对象代替真实依赖。它可以记录调用参数、返回预定小结果或模拟失败，让你检验上层如何应对。替身不应随意模仿真实实现内部细节，否则实现重构会使测试大量失效。更重要的是替身可能与真实服务契约漂移，因此还需要少量真实接口验证，不能只靠假对象通过就宣称集成无误。

插件系统则把替换能力开放给外部实现。需要稳定的输入输出、版本兼容、发现方式和错误边界。注册名字重复、插件初始化失败、返回类型不符，都应该有明确行为。不要让导入任意插件时自动启动昂贵任务；初始化可以显式执行，并在失败时保留插件身份与原因。

动态导入带来灵活性，也扩大排查范围。配置里一个字符串指定类路径，可能因安装版本、搜索路径或模块重名解析到不同对象。可以限制在明确注册表中选择，并记录最终实现标识。学习项目若只有两种算法，普通字典映射名称到工厂函数往往比任意字符串求值更清楚，也更容易检验未知名称。

可替换不等于任意替换都科学公平。两个数据读取器即使返回同结构，也可能采用不同缺失政策；两个模型接口一致，也可能默认训练预算不同。接口兼容只解决调用关系，方法比较仍需控制数据、预算和评估口径。模块化让比较更容易实施，却不会自动替你设计合理实验。

依赖生命周期也要明确。一个对象由入口创建并传给多个组件，谁负责关闭？若每个使用者都关闭它，其他组件可能失败；若没人关闭，则资源泄漏。可以由最外层上下文拥有，内部只借用，或通过明确转移所有权。类型与参数列表可以显示关系，但关闭政策仍要写入契约。

## 13. 项目布局、发布边界与协作

项目布局应该服务于可发现性。读者应容易找到入口、核心实现、配置模式、测试与示例，不需要在多个同名 train 文件间猜测。可以先保持浅层目录，随着职责增长再拆分。深目录本身不提供模块化，如果上层到处跨层访问内部对象，结构仍然紧耦合。命名与依赖方向比树形外观重要。

导入包与安装分发包不是同一概念。用户安装一个分发项目后，可能导入一个或多个不同名字的包；包版本元数据也通常由分发系统提供。诊断时既要知道实际导入模块来自哪里，也要知道安装的分发版本。不要把某个模块没有版本属性就理解成无法记录版本，也不要假设安装名与导入名永远相同。

项目元数据可以声明解释器范围、依赖与入口，但声明不证明代码真正兼容所有范围。若你只在某个版本执行过，就应按实际验证范围表述。依赖范围过窄会增加安装冲突，过宽可能接受未验证的大版本变化。根据使用接口与测试证据设定约束，再定期检验，比盲目固定一切或完全不约束都更有依据。

相对资源加载也需要设计。代码安装到其他位置后，源码旁边的数据文件是否仍包含在分发包里？工作目录可能不是包目录，直接打开一个短文件名就会失败。小型静态资源可以使用包资源接口；大型训练数据通常不应嵌入代码包，而应由显式数据路径或版本管理。区分代码资源与用户数据，能减少部署后的路径惊喜。

公开接口应有稳定名称与最小示例。一个函数从内部模块迁移时，可以暂时保留兼容入口；若直接删除，会让使用者不易定位升级方法。配置模式变化同样需要迁移说明。学习项目不必承诺永不破坏兼容，但应该让变更可审查，明确新旧行为，而不是让用户通过错误消息猜测。

协作中要避免每个人都创建自己的全局配置模块。可以约定入口统一解析，小配置按职责传递，公共数据结构放在稳定位置。代码评审时重点看新依赖是否合理、是否引入导入副作用、配置是否保存实际值、错误是否足够具体。无需为了形式统一所有函数写法，但事实来源与边界应一致。

文档也属于接口。示例命令应能在干净环境执行，参数名称要与解析器一致，默认值变化应同步说明。一个经常过时的 README 会让用户绕过正式入口，转而复制内部代码，增加维护负担。可以用小型集成验证检查关键示例，而不是要求所有文档片段都变成复杂测试套件。

依赖图与配置图还可以指导重构。若改一个模型字段需要修改五个模块中的默认值，说明唯一来源没有建立；若新增数据格式要修改训练算法，说明解析与计算耦合；若绘图模块一导入就初始化加速设备，说明资源边界不合理。先依据这些具体症状重构，比为了“更专业”全面改架构更有效。

发布前可以做一次消费者视角检查：从一个不包含源工作目录的独立位置，使用声明方式安装并运行最小例子，确认导入来自目标版本，资源可定位，配置与产物匹配。这样容易发现本机路径、未声明依赖和未打包资源。测试通过只支持实际环境中的结论，不应扩展成所有平台绝对兼容。

结果文件组织也应区分代码版本与实验实例。一个安装包可以运行许多实验，每个实验保存自己的有效配置和数据身份；代码包不应在安装目录写训练结果。否则只读安装环境、多个用户和并行运行都可能出问题。入口接受输出根目录并创建独立运行位置，职责更清楚。

## 14. 综合研究练习与参考资料

**任务一：配置覆盖真值表。** 对默认、文件与命令行三个来源，列出未提供、显式真、显式假和数值边界。至少验证命令行缺省不覆盖文件，显式假覆盖文件真，未知字段失败，非法最终组合失败。解析时先写每一格的预期来源和值，再运行实现；不能只检查对象能创建，因为它可能采用了错误来源的合法值。

接着把学习率字段重命名，设计旧版迁移。若旧字段单独存在，转换为新字段；若新旧字段同时出现，按明确政策拒绝或要求相等；未知模式版本不得静默按最新版本解释。验收需要保留迁移前请求与迁移后有效配置，使历史行为可以解释。迁移代码应集中在入口边界，计算函数不应该到处检查旧字段名。

**任务二：冻结边界实验。** 创建含标签列表的冻结配置，把它传给两个组件，令一个组件追加标签，观察另一个组件是否看到。再改成不可变标量组成的元组，并验证普通使用下不再存在相同修改路径。解析必须指出外层冻结与深层不可变的区别，也要说明不可变表示不能自动保证字段语义正确，例如重复类别仍可能不合法。

进一步比较复制与冻结。复制可以让两份可变对象独立，冻结则限制某些修改入口；两者解决的问题不同。若每个实验需要可变运行状态，可以各自复制必要数据；若配置应稳定，优先建立不可变规范对象。不要为了避免一次共享错误就把所有运行状态都深复制，也不要冻结后继续把可变缓存藏在同一配置里。

**任务三：导入副作用检测。** 在临时包中故意加入顶层打印、文件创建或主函数调用，然后用独立子进程导入，观察哪些证据暴露问题。修复后导入只建立定义，明确模块执行才产生输出。解析中说明为什么在当前交互进程重复导入可能看不到第一次副作用，因为模块缓存改变了实验条件。若要验证首次导入，使用新进程比随意删除模块缓存更容易解释。

同时检查包入口与直接文件执行的差异。给出一个唯一推荐启动命令，并说明它如何建立包上下文。不要通过在每个文件开头追加搜索路径来让所有启动方式勉强工作，那会增加同名解析风险。项目可以提供多个正式入口，但每个都应有清楚用途与验证。

**任务四：依赖图重构。** 画出入口、配置、数据、模型、训练与展示的依赖箭头，标记循环。选择一个循环，找出被共享的真实概念，把稳定结构下沉或把依赖作为参数传入。重构之后用小输入分别调用数据与计算模块，确认不再需要导入训练入口。验收不是箭头少了就成功，还应保持公开行为和错误信息。

**任务五：定义三种身份。** 为方法比较、单次运行和缓存分别列字段。方法比较可以排除时间戳但必须控制预算，运行身份包含种子与实例标识，缓存身份包含所有影响变换结果的依赖。构造两个文本不同但规范后等价的配置，再构造同路径内容不同的数据，解释为什么规范配置哈希仍不足以定义完整实验。

这个任务还应测试有意义顺序。交换类别列表顺序通常改变模型输出含义，不应被规范化成同一对象；重排普通映射键则可能不影响含义。规范化的每个动作都需要依据字段语义，不能一律排序所有容器。写出这些反例，会比只实现一个排序 JSON 哈希更能说明你理解身份设计。

**进阶研究：配置系统应当多强？** 比较简单数据类、手写字典合并与成熟配置框架在未知字段、嵌套覆盖、来源追踪、插值和模式迁移上的能力。先定义项目需求，再评估复杂度，不必立即引入新依赖。一个四字段项目可能不需要插件式配置引擎，几十个组件的团队项目则可能从统一框架获得收益。结论应基于具体功能与失败场景，而非工具流行度。

**进阶研究：如何防止配置与执行脱节？** 可以让组件只接收已经验证的子配置，在启动时保存规范快照，运行结束记录派生事实与状态，再对关键参数做一致性断言。还可以用依赖注入使全局环境不再成为隐式覆盖来源。不能只靠“大家约定不要改”而无任何接口支持，也不必把所有运行变化禁止掉；应区分输入、派生事实与动态状态。

本章完成标准是：能够从入口追踪参数来源，解释模块依赖方向，设计可验证的数据类，正确处理显式覆盖与缺省，给历史配置建立迁移路径，并说明哈希能证明与不能证明什么。下一章把这些契约变成调试方法和自动验证，检查项目在正常、边界和故障路径上是否都遵守承诺。
