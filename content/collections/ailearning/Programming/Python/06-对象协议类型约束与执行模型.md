## 1. 对象协议：从语法糖还原行为契约

协议可以理解成一组操作约定：某种使用者需要对象提供哪些行为，以及这些行为应具有什么语义。可迭代协议让循环可以逐项读取对象；可调用协议让对象能够像函数一样接受参数；上下文管理协议负责进入和退出一段资源使用过程。这里的重点是“使用者需要什么能力”，而不是“对象是否属于某个特定内置类”。这种能力导向的接口使数据源可以来自列表、文件或自定义批次流。

语法通常会触发特定协议。调用一个对象涉及其类型提供的调用行为；用方括号索引涉及取项行为；内置长度操作涉及长度行为。实际解释过程并非总能机械地替换成对实例同名方法的普通属性调用，因为某些特殊方法查找在类型层进行。你可以先把协议视为解释语法的入口，再逐渐学习特殊方法查找的精确规则，而不要把“所有语法都是普通方法调用”当成无条件等价式。

可迭代对象与迭代器应分别理解。可迭代对象能提供一个迭代器；迭代器维护当前位置，逐次产生元素，并在结束时发出停止信号。容器往往每次产生一个新迭代器，因此可以重新从头遍历；迭代器本身通常返回自己，第一次遍历耗尽后，再遍历不会自动回到开头。数据加载代码若把一次性的生成器当作可重复容器，可能第一轮有数据、第二轮突然为空。

下面的对象不继承列表，却能被循环和列表构造函数消费。它保存不可变元组作为底层样本，每次迭代都返回独立的元组迭代器，因此两次遍历不会共享当前位置。长度与索引也明确委托给底层表示。它是协议组合的例子，并没有宣称实现所有列表方法。

```python
class SampleView:
    def __init__(self, values):
        self._values = tuple(values)

    def __len__(self):
        return len(self._values)

    def __iter__(self):
        return iter(self._values)

    def __getitem__(self, index):
        return self._values[index]

view = SampleView([4, 7, 9])
left = iter(view)
right = iter(view)
assert next(left) == 4
assert next(left) == 7
assert next(right) == 4
assert len(view) == 3
assert list(view) == list(view) == [4, 7, 9]
assert view[1:] == (7, 9)
```

接口完整性需要检查语义，不只是方法名字。例如某对象虽然有长度方法，却返回负数，内置长度操作不会接受；某迭代器达到结尾后又突然产生元素，会违背通常的迭代器约定。实际框架依赖这些性质进行预取、进度估计和批次合并。所谓鸭子类型不等于随意返回任何值，而是按行为契约接受对象，验证责任并没有消失。

相等与哈希协议同样需要合作。两个对象比较相等时，它们的哈希值应一致，否则字典与集合的查找假设会被破坏。若对象的相等含义依赖可变字段，修改字段可能使它不再适合作为稳定键。为研究记录建立身份时，可以选择不可变编号作为键，而把可变指标放在值里。不要把整个可变实验状态对象直接作为键，然后期望缓存永远正确。

协议还有成本与副作用层面。一个取项操作可能只是访问内存，也可能触发磁盘读取、解压和数据增强；一个属性访问可能触发远程请求。它们在语法上都很短，却不代表运行成本很低。接口文档应该说明重复读取是否确定、是否缓存、是否改变内部状态。后续讨论属性描述符时，这种“看起来像字段却可能执行计算”的情况会更明显。

## 2. 属性查找：实例、类与描述符的合作

初学者常把`obj.name`想成从一个字典取值。普通对象确实常有实例字典，但属性访问还可能涉及类及其基类、描述符、定制查找方法。理解这个机制，能解释为什么实例方法自动获得对象参数，为什么属性可以只读，为什么缓存属性第一次读取与后续读取行为不同，也能帮助排查被某个实例字段意外遮蔽的方法。

在普通实例属性查找的典型默认机制中，先沿类的方法解析顺序寻找同名类属性；若找到具有相关读取行为的数据描述符，它优先于实例字典。否则检查实例字典；若实例里没有，再处理类里的非数据描述符或普通类属性；若常规查找最终失败，外层属性访问机制可以调用定义的后备查找方法。这里说的是默认机制，主动改写底层查找入口可能改变行为，也可能轻易破坏描述符协作。

数据描述符通常具有设置或删除入口，非数据描述符只有读取入口。这个区分影响优先级：数据描述符可以控制实例赋值和读取，不容易被实例同名字段遮蔽；非数据描述符允许实例字典同名值优先。普通用户定义函数放在类上，会表现为非数据描述符；通过实例访问后得到绑定方法，因此调用时自动把实例作为第一个参数传入。直接从类字典取原始函数，就不会经过同样的绑定步骤。

属性查找优先级并非抽象细节，它能解释真实现象。只读 property 即使没有公开设置函数，也有描述符层的设置处理，会在不允许时抛出异常；不应该认为“没有设置函数所以只是普通字段”。而一种常见缓存属性实现是非数据描述符：首次访问计算结果，写入实例字典，之后同名实例值遮蔽描述符，从而直接返回缓存。两者选择了不同的修改与失效语义。

```python
class NonData:
    def __get__(self, obj, owner=None):
        if obj is None:
            return self
        return "computed"

class Data:
    def __get__(self, obj, owner=None):
        if obj is None:
            return self
        return "controlled"

    def __set__(self, obj, value):
        raise AttributeError("read only")

class Example:
    loose = NonData()
    strict = Data()

x = Example()
x.__dict__["loose"] = "instance"
x.__dict__["strict"] = "attempted shadow"
assert x.loose == "instance"
assert x.strict == "controlled"
try:
    x.strict = "new"
except AttributeError:
    pass
else:
    raise AssertionError("assignment should fail")
```

这个例子有意直接写实例字典，用来把优先级现象分离出来，不代表日常程序应绕过接口这么操作。即使实例字典里存在 strict 键，读取仍由数据描述符控制；loose 则被实例值遮蔽。描述符一般要放在类属性上才能参与这个默认过程，把描述符对象放进实例字典，通常只会得到那个对象本身，而不会自动变成受管理字段。

定制属性查找时，常见错误是在方法内部再次写普通属性访问，导致同一查找逻辑递归调用自己。需要时应使用父级的基础实现访问必要状态，但不要因为知道这个技巧，就把所有接口都改成全局拦截。只有少数字段需要验证时，property 或描述符通常更局部、更容易测试。广泛动态属性还可能让静态分析、自动补全和错误定位变得困难。

属性读取也会抛出异常，甚至改变状态。所以`hasattr`不是完全无副作用的结构检查，它可能触发实际查找过程，并把某些属性错误解释为不存在。如果底层计算错误地抛出了属性错误，调用者可能误以为字段缺失。设计动态接口时要选择恰当的异常类型，把“没有这个属性”与“计算这个属性失败”区分开。调试框架时，也应留意查看对象的操作本身可能执行用户代码。

## 3. 完整案例：用描述符实现受约束参数

现在实现一个有限正数参数。应用场景是某个实验配置具有学习率和温度，它们都必须是大于零、且能通过浮点有限性检查的内置数值；超出浮点范围的巨大整数明确拒绝。最简单的做法是在构造函数里检查，但如果后续允许赋值，构造时合法不代表对象生命周期内永远合法。我们希望把检查放在同一个属性写入入口，让初始化和后续修改使用同一规则。

描述符对象属于类，因此不能把每个实例的当前值直接存进描述符自身的同一个字段，否则不同实验实例会共享值。描述符应该保存字段元信息，而把实际值保存在目标实例上。这里通过类创建时收到字段名，生成专用存储名。这个名字仅是约定式内部名字，并非防止恶意修改的安全边界；外部若直接访问实例字典，仍可能绕过它。

```python
import math

class PositiveFinite:
    def __set_name__(self, owner, name):
        self.public_name = name
        self.storage_name = "_parameter_" + name

    def __get__(self, obj, owner=None):
        if obj is None:
            return self
        try:
            return obj.__dict__[self.storage_name]
        except KeyError:
            raise AttributeError(self.public_name) from None

    def __set__(self, obj, value):
        if type(value) not in (int, float):
            raise TypeError(self.public_name + " must be an int or float")
        try:
            valid = math.isfinite(value) and value > 0
        except OverflowError:
            valid = False
        if not valid:
            raise ValueError(self.public_name + " must be finite and positive within float range")
        obj.__dict__[self.storage_name] = value

class Experiment:
    learning_rate = PositiveFinite()
    temperature = PositiveFinite()

    def __init__(self, learning_rate, temperature):
        self.learning_rate = learning_rate
        self.temperature = temperature

first = Experiment(0.01, 0.7)
second = Experiment(0.02, 1.0)
first.learning_rate = 0.005
assert first.learning_rate == 0.005
assert second.learning_rate == 0.02
for value in [0, -1, float("inf"), float("nan"), 10 ** 400]:
    try:
        first.temperature = value
    except ValueError:
        pass
    else:
        raise AssertionError("invalid value accepted")
assert first.temperature == 0.7
assert Experiment.learning_rate.public_name == "learning_rate"
```

逐步解释一次合法写入：属性赋值找到类上的数据描述符，调用它的设置入口；先验证类型，布尔值因此不会作为整数被接受；再验证有限性和正值；全部通过后才写实例字典。非法赋值会在写入之前抛出异常，所以原先合法值保留。这是局部的“先验证后提交”原则，但只保证这个单字段操作的逻辑，并不让整个对象初始化自动具备事务性。

类访问与实例访问也应分开。读取`Experiment.learning_rate`时，示例返回描述符本身，便于检查字段元信息；读取某个实例的属性时才返回该实例值。不同描述符完全可以定义其他类访问行为，但要明确，而不是让没有实例时意外报错。对于通用库，继承、同一描述符实例重复挂载、存储名冲突和无实例字典的对象都需要进一步考虑，本例没有声称覆盖这些扩展需求。

使用这种方案是否一定比 property 好？如果只有一个字段、规则很特殊，property 的局部清晰性可能更好；多个类的多个字段共享相同规则，描述符能减少重复，并集中测试；如果配置只允许初始化后不变，冻结的数据结构加构造验证也可能更简单。选择取决于修改模型与复用需求，不应因为机制进阶就到处使用它。

还要区分字段级与整体级约束。学习率为正、温度为正分别是局部条件；若还要求最小温度不超过最大温度，就涉及两个字段之间的关系。逐个赋值检查可能让合法的成对更新难以完成，需要设计批量更新接口或创建新配置对象，在验证整体之后再替换。这个问题反映约束的原子边界，而不是多写一个描述符方法就自动解决。

## 4. 继承与组合：方法解析顺序及协作调用

继承允许一个类复用并扩展另一个类的行为，但“复用实现”和“可以替换使用”是不同的目标。一个子类可能继承了方法，却收紧输入条件、改变异常类型或破坏返回值约定，结果无法安全替代父类。把训练数据集设计成某个框架数据集的子类时，除了方法名字相同，还要保证长度、索引和随机性语义符合框架的预期。

多重继承引入一个核心问题：同名方法应该按什么顺序查找？Python 用一致的方法解析顺序组织类及其基类。对常见菱形继承，公共祖先不会简单地在两个分支中各执行一次；解析顺序需要同时尊重局部基类先后关系和继承结构的一致性。某些互相矛盾的继承要求无法形成合法顺序，类创建会失败，而不是随意挑一个结果继续。

`super()`不能简单理解成“调用代码中写出来的直接父类”。在协作式多重继承中，它沿实际对象类型的方法解析顺序，寻找当前位置之后的实现。因而同一段定义在某个类中的方法，在不同最终子类结构下，下一站可能不同。若把协作链某处改成硬编码调用特定父类，就可能跳过其他分支，或者让公共祖先重复初始化。

```python
class Root:
    def trace(self):
        return ["Root"]

class Left(Root):
    def trace(self):
        return ["Left"] + super().trace()

class Right(Root):
    def trace(self):
        return ["Right"] + super().trace()

class Combined(Left, Right):
    def trace(self):
        return ["Combined"] + super().trace()

assert [c.__name__ for c in Combined.__mro__] == [
    "Combined", "Left", "Right", "Root", "object"
]
assert Combined().trace() == ["Combined", "Left", "Right", "Root"]
```

从结果可以看到，Left 的下一站是 Right，而不是定义 Left 时写出的 Root。这不是违背继承关系，而是协作查找按最终解析顺序推进。要让这种设计可靠，各参与方法通常需要统一调用约定，并把未消费的参数继续传递；链上某个方法提前停止，会截断后续处理。这个约定并非语言强制，团队需要通过接口说明与测试维护。

多重继承适合少量正交能力的组合，例如某个功能明确只负责日志包装；但如果多个基类都拥有复杂可变状态、都依赖初始化顺序，组合对象往往更清楚。组合是把依赖作为字段交给对象，例如数据加载器持有读取器、解码器和增强器。这样可以独立替换与测试各组件，也容易看出状态属于谁；代价是需要显式转发调用，不像继承那样自动获得整个方法集。

“优先组合”也不是不需要分析的万能规则。如果框架明确要求继承某个基类，遵循它可能是合理的；如果多个实现共享严格的生命周期契约，抽象基类可以提供有价值的统一入口。判断时问三个问题：使用者需要的是共同类型身份还是共同能力，复用的是纯算法还是状态管理，替换组件时需要保持哪些不变式。回答这些问题比追求某种设计风格更有指导作用。

研究代码常有一个隐蔽问题：为了改动很小的一步，继承一个巨大训练器并覆盖内部私有方法。短期很方便，但上游实现一改，覆盖点就可能失效，而且类型检查未必能发现行为变化。若框架提供稳定回调或策略接口，优先使用公开扩展点；若不得不覆盖内部方法，应固定版本并为关键行为写小型契约验证。继承深度越大，隐含依赖越难审查。

## 5. 类型提示：静态约束与动态事实的边界

类型提示让你在运行前表达和检查部分接口约定。它可以帮助发现把字符串传给数值函数、遗漏可能为空的分支、误用返回值等问题，但普通解释器不会因为参数写了整数注解，就自动拒绝字符串。静态检查器与运行时验证是两个系统：前者依据代码和标注推理，后者面对真实对象执行规则。一个系统中表达清楚的事实，不会自动完整转移到另一个系统。

以`float | None`为例，它表示值可能是浮点数，也可能为空。调用者在参与算术之前，应先处理空值分支；检查器通常能从明确的身份判断中缩小可能类型。这里的类型缩小是基于控制流的逻辑推断，而不是把对象从一种类型转换成另一种。只有经过实际转换操作，字符串才会变成数值；加注解并不会改变内存中的数据。

不要把宽泛类型当成解决报错的办法。把所有参数都标成`Any`可以让许多静态错误消失，但它同时把相应推理义务交还给程序员。`object`则表达任意对象，但在没有进一步检查时，只能安全进行所有对象共有的有限操作。前者更像暂时关闭部分静态检查，后者是保守地承认信息不足。这两种标注的含义差别，比它们看上去“都很宽泛”重要得多。

结构化协议允许接口按能力描述，不要求实现者继承同一个具体基类。下面的评分器只需要接收一组数值并返回一个数值。均值评分器没有显式继承协议，但只要它的接口满足约定，就可以交给按该协议标注的使用者。示例在普通 Python 中可运行；是否完全通过某个静态检查器，还取决于所用检查器及其设置，因此运行结果与静态检查结果需要分别报告。

```python
from typing import Protocol
from collections.abc import Sequence

class Scorer(Protocol):
    def __call__(self, values: Sequence[float]) -> float:
        ...

class MeanScorer:
    def __call__(self, values: Sequence[float]) -> float:
        if not values:
            raise ValueError("values must not be empty")
        return sum(values) / len(values)

def evaluate(values: Sequence[float], scorer: Scorer) -> float:
    return scorer(values)

assert evaluate([1.0, 3.0, 5.0], MeanScorer()) == 3.0
```

协议没有表达空输入时抛出什么，也没有自动保证评分结果有限，更没有约束函数是否修改外部状态。这些仍需要文档、数据契约和测试。类型系统擅长表达一部分结构关系，却不是完整的数学规格语言。一个函数标注返回浮点数，实际却返回非数值特殊浮点，也可能在类型层完全合法，但对你的指标计算无效。

标注还能帮助表达不同阶段的数据结构。原始记录中的分数也许是字符串或空值，验证后的记录则保证是有限数值。与其在所有函数中传同一个宽泛字典，不如建立两个明确结构，并让清洗函数成为转换边界。不过普通类型提示通常无法直接表达“数值有限且介于零与一之间”这类全部语义，仍要在构造处验证并维持对象不变式。

运行时可检查协议也有边界。即使启用了相应机制，运行时检查主要关注属性是否存在，不能替代对完整参数类型、返回值语义和副作用的验证。一个对象拥有同名方法，不保证调用时接受所需参数，也不保证工作正确。插件系统中可以结合结构检查、一次小型试运行与清晰错误信息，但不要宣称一个存在性检查就证明插件完全兼容。

类型标注的收益还依赖维护纪律。如果真实接口改变了，标注却停留在旧版本，它会制造虚假的安全感。对于数值研究代码，最有价值的标注通常位于模块边界、配置、数据阶段和公共调用接口，局部短小变量未必需要逐个加长注解。目标是保留关键关系，而不是让每行代码都被类型语法淹没。

## 6. 泛型与变型：为什么可变列表不能随意替换

泛型用于表达输入输出之间的类型关系，而不只是给一个位置贴上“任意类型”。例如一个返回序列首项的函数，无论输入元素是什么类型，返回值都应该与元素类型一致。若把输入和输出都写成宽泛任意类型，这种联系就消失了；使用类型变量则把“同一种类型”作为约束传播。这样调用者使用结果时，仍保留具体信息。

```python
from typing import TypeVar
from collections.abc import Sequence

T = TypeVar("T")

def first(values: Sequence[T]) -> T:
    if not values:
        raise ValueError("empty sequence")
    return values[0]

assert first([3, 5]) == 3
assert first(("cat", "dog")) == "cat"
```

这里返回类型不是“所有可能类型的混合”，而是由本次输入约束决定。仍然要检查空输入，因为类型系统并没有证明序列非空。你也可以让返回值为可空类型，但那会改变接口：每个调用者都必须处理空值。让错误显式抛出还是返回空值，应由业务需求决定，不应只为了让类型签名看起来简单。

为什么整数列表通常不能当作任意对象列表随意替换？考虑某个函数接收“可追加任意对象的列表”，并向其中追加字符串。若允许把只应包含整数的列表交进去，调用后整数列表就混入字符串，原有类型约定被破坏。这是可写容器的经典风险：既从容器读取，也能向容器写入，使得元素类型之间不能简单按继承关系提升。

只读视图则不同。如果使用者只需要读取元素，接收较一般元素类型的只读序列，可能安全地使用更具体元素类型的序列。这对应协变直觉：读取到子类对象时，它也能按父类能力使用。回调的参数方向又相反：若你需要一个能处理某种特定对象的函数，一个能够处理更一般对象的函数通常足够，因为它当然也能接收该特定对象。这是逆变的核心理由。

这些词容易背，真正需要掌握的是替换后会不会允许原对象无法承受的操作。可以每次构造一个反例：替换后，使用者是否能写入更宽类型？是否期待返回更窄类型？如果能由此破坏约定，替换就不安全。变型规则是从可替换性推出的结果，不是类型检查器故意刁难某种容器。

对于训练流水线，接口尽量声明真正需要的最小能力会更灵活。若只要逐项读取，不必强制要求列表；若需要多次遍历，单次迭代器又不足够；若需要随机索引和长度，可使用相应序列能力。类型提示与运行时协议在这里汇合：越准确地描述操作需求，越容易接入新的数据源，也越容易发现某个看似相似的对象其实不满足契约。

泛型也不能表达全部数组形状。一个二维数值数组与一个三维数组，可能共享相同的 Python 外层类型；批次大小、特征维度、设备和数值类型往往需要额外工具或运行时检查。应把静态标注、形状断言和具体例子结合使用。单靠一个宽泛的数组类名，不能证明矩阵乘法轴一定对应，也不能证明标签顺序与样本一致。

## 7. 生成器：暂停、恢复与双向通信

普通函数调用从入口执行到返回，把结果交给调用者；生成器函数包含产生值并暂停的表达式，调用它首先获得生成器对象，函数体尚未按普通调用那样完整执行。之后每次请求下一个值，才从上次暂停位置继续。局部变量和当前位置被保留下来，因此能够把一个较长的处理流程写成逐项推进的状态机。

惰性求值首先改变执行时机。你调用一个生成器函数，看似已经“处理了数据”，实际可能一条数据都没读；真正读取与验证发生在消费者迭代时。因而异常出现的位置可能远离生成器创建处。文件打开、计数更新和日志输出也会随着迭代推进才发生。调试时要区分创建数据流、消费数据流与完整耗尽数据流，三者不是同一动作。

生成器通常节省的是同时保留的中间结果，而不是自动让所有内存成本消失。如果上游已经把全部输入放进列表，生成器不会释放那个列表；如果下游立刻把生成器转成列表，输出仍会全部物化；如果生成器内部保留一个不断增长的缓存，它也可能占用大量内存。分析惰性流水线时，应该追踪每个阶段持有哪些对象，而不是看到生成器语法就断言常数空间。

下面的累加器还展示双向通信。第一次推进到暂停点，产生初始总和；之后通过发送操作把一个数交回暂停表达式，它更新状态并再次产生结果。发送空值让它返回最终总和，返回值出现在停止异常中，而不是被当作又一个普通元素产生。

```python
def running_total():
    total = 0
    while True:
        incoming = yield total
        if incoming is None:
            return total
        total += incoming

g = running_total()
assert next(g) == 0
assert g.send(3) == 3
assert g.send(4) == 7
try:
    g.send(None)
except StopIteration as stop:
    assert stop.value == 7
else:
    raise AssertionError("generator should have returned")
assert list(g) == []
```

为什么需要先推进一次？因为在生成器尚未开始执行时，没有一个已暂停的产生值表达式可以接收普通发送值。先调用下一项操作，或发送空值完成启动，才进入双向协作阶段。多数数据管线只使用单向迭代，完全不必为此引入发送协议；了解机制是为了阅读更复杂代码，而不是把简单循环全部改成协程风格。

生成器的清理行为同样重要。若它在暂停前获取了资源，消费者提前停止迭代，资源并不必然在你希望的时刻释放。可以设计显式关闭、上下文管理或把资源所有权放在外层清晰作用域中。关闭生成器会在暂停处注入相应终止信号，使最终清理块有机会执行；清理代码不应试图继续向外产生普通值。不能把垃圾回收时机当成确定的资源管理协议。

委托产生语法会把一系列交互转发给子迭代器或子生成器，包括逐项取值，以及在适当情况下传递发送、异常与关闭。它不只是缩短一层循环，还能接收子生成器结束时的返回值。对于分层解析器或分阶段状态机，这可以让控制流更自然；对于普通列表展开，一个清楚的循环已经足够。选择机制时，应看是否需要保留交互语义。

有一种细节值得记住：在生成器内部直接错误地抛出停止迭代异常，不应被当成正常结束写法。现代 Python 会把某些从生成器体意外逃出的停止异常转换为运行时错误，避免深层错误被静默解释为数据正常结束。正常结束应使用返回语句。这个区别保护了消费者：文件解析出错与文件真的耗尽，不应该只因异常类型相同就变得无法区分。

如果一个训练循环需要每轮重新读取数据，最好传入能够创建新迭代器的数据源或工厂，而不是把某个已经创建的生成器对象永久保存并反复使用。重建迭代器不等于重置随机状态，数据增强随机性还需独立管理。由此可以把数据集、采样顺序和迭代器状态拆开理解，这为后续 PyTorch 数据加载机制建立了直接基础。

## 8. 协程与任务：等待、调度与取消

异步协程把“当前操作尚未完成，可以先让出执行机会”表达为显式等待。它适合协调许多等待网络、磁盘接口或外部服务的任务，但不会自动让纯 Python 的高强度计算并行完成。一个协程若长时间只执行普通计算，不遇到真正让出控制的等待点，就可能阻塞同一个事件循环里的其他协程。异步的核心是合作调度与等待组织，而不是在函数前加关键词就获得更多处理器。

调用异步函数会创建协程对象，函数体并非立即完整执行。要让它推进，需要等待它，或把它交给调度器包装为任务。任务拥有调度状态，事件循环负责在可运行任务之间推进；遇到尚未完成的等待对象时，当前任务暂停，其他任务可以运行。协程对象、任务和最终结果因此是三个层次，不能把“创建了协程”误当成“工作已经完成”。

下面例子使用标准库的异步睡眠模拟等待，不访问网络，也不依赖真实服务。两个工作任务都先记录开始，再等待，最后记录结束。我们只验证每个任务内部的先后关系和任务分组完成后的清理，不验证精确耗时或两个任务结束的相对顺序，因为调度与时钟环境不应成为这个例子的脆弱前提。

```python
import asyncio

async def worker(name, events):
    events.append((name, "start"))
    try:
        await asyncio.sleep(0)
        events.append((name, "done"))
    finally:
        events.append((name, "cleanup"))

async def main():
    events = []
    async with asyncio.TaskGroup() as group:
        group.create_task(worker("A", events))
        group.create_task(worker("B", events))
    for name in ["A", "B"]:
        own = [event for who, event in events if who == name]
        assert own == ["start", "done", "cleanup"]
    assert len(events) == 6

asyncio.run(main())
```

任务组建立一个清晰生命周期边界：退出分组时，组内任务的完成与异常传播按对应规则处理。相比随处创建后不追踪的后台任务，这更容易说明“本次操作究竟等待了谁”。但结构化组织不替代业务补偿：一个任务已经向外部系统提交数据，另一个任务失败，任务组并不会自动撤销外部写入。异步异常边界与数据库事务边界仍是不同问题。

取消是合作式请求，通常在任务推进到可取消等待点时以取消异常体现。清理应放在最终清理块或可靠的上下文管理中。若捕捉到取消信号只是为了释放资源，通常应继续传播，使上层知道任务并未正常完成。无意吞掉取消，可能使超时和任务组无法按预期结束。反过来，取消也不是保证任意底层阻塞调用立刻停止，外部接口可能有自己的不可中断阶段。

超时应以整个操作的需求为基准。每一步都给相同超时时间，连续若干步后总耗时可能远超用户等待预算；共享一个总体截止期限则更接近“这个请求必须在某时刻前结束”。重试还要考虑幂等性与剩余时间：网络超时可能表示结果未知，而不是对方没有执行。虽然本章不编写真实请求系统，这些约束能防止把异步接口理解成简单的并发发射器。

共享可变状态在异步环境中仍可能发生逻辑竞争。即使只有一个事件循环线程，只要读取状态后等待，恢复时其他任务就可能改过状态。典型错误是读取余额、等待远程响应、再按旧余额写回。若一段业务步骤需要不可交错，可以使用适当异步锁或重新设计数据流；但持锁等待慢速外部操作也会降低并发并制造死锁风险，必须明确临界区范围。

计算密集任务与阻塞接口需要另一种处理方式，例如把适当的阻塞工作交给线程接口，把需要真正并行的计算交给进程或释放解释器锁的数值库。具体性能依赖实现、版本与任务性质。本章以 Python 3.11 常见 CPython 环境作语义背景，不对新版本所有构建模式的线程机制做统一断言。选择异步、线程或进程时，先分析等待来源与状态共享需求，再做测量。

## 9. 执行模型：名字、闭包、导入与字节码

理解执行模型，是为了知道代码何时被求值、状态何时建立、错误何时出现。源代码先经过解析与编译等处理，再由具体实现执行；普通 CPython 会使用字节码与解释器执行机制。但语言语义不是某一份字节码清单。不同版本可能调整指令、优化和内部缓存，即使指令不同，只要可观察语义符合规范，程序仍可以是正确的 Python 实现。

函数定义执行时建立函数对象，它关联代码与定义环境中的相关信息；函数体通常在调用时才执行。默认参数表达式则在定义语句执行时求值，所以默认可变列表可能跨多次调用共享。装饰器也在定义阶段参与函数对象的变换，而不是等到每次调用才重新执行定义本身。区分定义时与调用时，是解释许多缓存、注册表和配置行为的基础。

闭包会保留对外层变量绑定所在单元的访问，而不是自动为每次创建复制变量当时的值。因而在循环里创建多个引用同一循环变量的函数，之后调用时常常都观察到循环结束后的值。如果你需要创建时的快照，可以通过默认参数、工厂函数或明确对象状态建立独立绑定。哪种更清楚取决于接口，不应把某种技巧当作唯一正确写法。

```python
late = []
snapshot = []
for index in range(3):
    late.append(lambda: index)
    snapshot.append(lambda index=index: index)

assert [f() for f in late] == [2, 2, 2]
assert [f() for f in snapshot] == [0, 1, 2]
```

这段例子中的默认参数保存的是当时求值所得对象引用。若捕获的是可变列表，而之后继续修改同一列表，默认参数不会自动获得深层快照。它只解决某种名字后绑定问题，不解决所有可变对象共享问题。把第一个章节的对象图模型与这里的求值时机结合，才能完整解释行为。

局部变量的判定也可能先于具体运行分支。若函数体中某处给名字赋值，该名字通常会被当作局部名字，除非有相应声明。于是你在赋值前读取它，可能得到未绑定局部变量错误，即使模块里存在同名对象。不要通过随意添加全局声明来“修好”这种报错；更清楚的做法通常是通过参数显式传入依赖，并返回需要更新的值。

导入不仅是把文本贴到当前文件。模块通常有独立命名空间，导入机制会查找并执行模块初始化，然后缓存模块对象。重复导入通常复用已有模块，因此模块顶层的可变状态也可能在整个进程中持续存在。循环导入时，一方可能观察到另一方尚未初始化完成的状态，形成“单独导入没问题，换个入口就报错”的现象。解决方法优先是重新划分依赖方向，而不是到处延迟导入掩盖设计问题。

字节码反汇编适合检验你对某个解释器版本行为的猜测，例如某段语句包含哪些大致步骤。但它不能证明线程下复合操作具备事务性，也不能代替语言层契约。一个高级语句可能对应多步，某个底层操作也可能在执行中调用用户代码。并发正确性应依赖明确同步与接口保证，而不是依赖“反汇编看起来很短”。

性能分析也应遵守层次边界。给局部名字换写法、手工合并语句，收益可能远小于减少一次磁盘读取或避免平方级扫描；微基准还可能受缓存、解释器预热和输入规模影响。先测量端到端热点，再针对稳定瓶颈验证优化，并确保输出契约保持不变。解释执行机制能帮助形成假设，但最终性能判断需要数据。

## 10. 框架接口设计：状态、缓存与可序列化边界

对象协议、类型约束和执行模型最后都服务于接口设计。一个数据变换器可以是普通函数，也可以是带参数的可调用对象。普通函数适合无状态变换；对象适合保存明确配置或必要状态。关键是让调用者知道同一输入是否得到相同输出，调用是否推进内部状态，以及是否能够安全地在多个任务或进程之间复用。不能仅根据“它能被调用”推断它就是纯函数。

缓存是最典型的状态来源。缓存键必须覆盖决定结果的全部依赖：输入、配置、预处理版本，有时还包括模型权重或外部文件内容。如果键只有文件路径，而文件内容被替换，旧结果可能继续被误用；如果键引用一个之后会变化的配置对象，同样的表面调用也可能对应不同语义。缓存正确性首先是依赖建模问题，然后才是选择字典还是专门缓存库。

用属性缓存结果，还需要定义失效机制。假设归一化统计量从训练数据计算并缓存，后来替换训练数据而未清缓存，模型会使用过时统计量。可以设计对象初始化后配置不变，或者在修改入口显式使缓存失效；也可以把结果与不可变数据版本绑定。没有一种方案对所有场景最优，但必须有一项明确策略。单纯观察“第二次访问快了”不能证明缓存正确。

序列化则要求区分数据状态和执行资源。数值配置、样本编号与明确版本信息通常适合保存；打开的文件、线程锁、活动生成器和事件循环任务往往不适合被当作普通配置直接迁移。即使某种序列化工具能够保存复杂对象，也不代表恢复后其外部依赖仍有效。研究复现更可靠的做法常是保存构建对象所需的配置与状态，再按清晰步骤重建资源。

多进程数据加载尤其需要关注这些边界。子进程如何启动、哪些对象被继承或序列化、随机状态如何初始化，都可能影响行为。把文件连接在主进程构造器中提前打开，然后假设所有工作进程都能安全共享，并不稳妥。更合理的设计通常让每个工作上下文创建自己拥有的资源，记录初始化与关闭规则。具体机制应结合操作系统和框架文档核对，不要从一次本机运行推广到所有平台。

插件接口可以结合本章机制逐层验证：静态协议帮助开发者编写兼容实现，运行时配置验证保证输入范围，小型契约用例验证实际行为，版本信息说明兼容边界。每层检查针对不同风险，不应互相冒充。例如类型检查通过不能证明输出无非数值，配置合法不能证明某个数据源可重复遍历，小样本测试通过也不能证明任意输入都正确。

接口演化时，新增可选参数通常比静默改变已有参数含义更容易管理，但仍可能影响子类覆盖和回调签名。引入新的返回字段看似兼容，若调用者依赖固定元组拆包，也会破坏旧代码。因此公开接口最好有明确的参数方式、结果结构和弃用策略。研究代码也会成为别人项目的依赖，简洁说明这些边界能节省大量后续沟通。

设计中最值得追求的不是“动态能力越多越好”，而是关键依赖可见。描述符适合统一属性规则，不适合掩盖昂贵远程调用；协议适合声明最小能力，不适合假装已经验证全部语义；生成器适合渐进处理，不适合隐藏难以管理的资源；异步适合组织等待，不适合掩盖阻塞计算。知道机制能做什么之后，还要知道什么时候选择更普通、更明确的结构。

## 11. 分层习题与逐步解析

**习题一：实例方法为什么少传一个参数？** 定义一个类，其普通方法接收实例与数值两个参数，通过实例调用时只传数值。解释哪个阶段提供实例。解析：函数作为类属性参与描述符读取，经实例访问后得到绑定方法；绑定方法保存相关实例与函数，调用时把实例放在约定位置。通过类访问后显式传实例也能调用同一函数，但不能据此把所有可调用类属性都当成普通实例方法，静态方法与类方法的绑定规则不同。

进一步验证时，可以比较方法对象中关联的实例与底层函数，不必依赖打印地址。再尝试给实例写一个同名普通字段，观察普通方法的非数据描述符如何被遮蔽。这个实验把第二区分的数据描述符优先级与实际方法调用连接起来。错误结论是“类里有方法，所以实例永远不能同名覆盖”，正确结论要带上属性类型与查找规则。

**习题二：为什么两个对象的受约束属性不能共享存储？** 将第三节描述符改成在描述符自身保存一个 value 字段，创建两个实验对象并分别赋值。预测第二次赋值之后第一个对象读取什么。解析：两个实例通过同一类属性找到同一个描述符，因此单个 value 被覆盖，两个实例观察相同最终值。修复方向是按目标实例保存值，而不是在读取时临时复制，后者只是复制已经错误共享的结果。

还应考虑描述符对象被同一个类的两个字段重复使用的情况。自动名称通知会反复更新同一元信息，可能导致两个公开字段使用同一个最后存储名。最简单的使用契约是每个字段创建一个独立描述符；通用工具也可以检测重复挂载并拒绝。这里体现可复用组件的边界：如果使用前提没有写出来，日后合理-looking 的复用就可能造成难找的错误。

**习题三：把一个耗尽迭代器传入两次评估。** 第一次计算总和后，第二次计算元素数，为什么可能得到零？解析：消费改变了迭代器当前位置，第二次从结束位置开始。修复可以一次循环同时计算总和与计数，或者先物化为容器，或者让调用方提供可重新创建的迭代器工厂。三种方法在内存、读取成本与数据一致性上不同，应按真实需求选择。

若数据来自外部持续变化的流，两次重新读取还未必得到相同内容。因而“重新创建迭代器”只解决当前位置问题，并没有自动提供快照一致性。设计评估程序时，最好明确数据版本，避免一个统计量来自早先数据、另一个来自后来数据。这个延伸把语言层迭代行为连接到实验方法。

**习题四：类型标注是否证明数值有效？** 某函数标注返回浮点数，却返回正无穷。静态结构上为什么可能不报错？因为无穷大仍是浮点对象，标注没有表达有限性。解题时应在计算边界验证有限值，必要时提供明确失败类型或结果状态；不要把返回类型改成任意类型来消除疑问。更进阶的设计可以构造已验证数值包装，但仍需在构造处执行检查。

**习题五：只读序列与可写列表的替换关系。** 用一个向容器追加字符串的函数构造反例，解释为何不能把整数列表直接视作允许写任意对象的列表。再改为只读取并打印元素的函数，说明为什么较窄元素类型可安全满足较宽读取需求。解析重点是允许操作集合，而非背协变或不变术语。若接口只读，却不必要地要求具体可写列表，会把本来可接受的数据源排除在外。

**习题六：闭包快照与对象快照。** 在循环中用默认参数保存一个列表，然后每轮继续向同一列表追加。预测多个函数调用时看到的内容。解析：默认参数保存当时的列表引用，而不是复制内容；若全都指向同一列表，它们仍观察后续修改。要保留内容快照，可在创建时构造适当独立表示；若列表元素还有可变内部对象，还需继续分析复制深度。

**习题七：异步取消是否等于事务回滚？** 一个任务先把结果写入文件，再等待确认；等待时被取消。问文件是否必然恢复原样。解析：不会自动恢复。取消影响控制流，文件修改是已经发生的外部副作用。需要时设计临时文件与原子替换、显式补偿或业务事务。这里不能仅在最终清理块删除所有文件，因为那可能删除此前已存在的合法结果；清理必须知道资源的所有权与创建阶段。

**习题八：协作继承链被截断。** 在多重继承例子中，令 Left 直接返回自己的结果，不再调用后继。解释 Combined 的结果为什么不再包含 Right 与 Root。解析：方法解析顺序只决定查找顺序，不会强制所有类的同名方法都自动执行。协作式链依赖各参与实现继续委托。若某个类设计上应当是终点，应把这个契约说明白，而不是让调用方误以为所有混入能力都会生效。

## 12. 综合研究项目、验收标准与参考资料

综合项目是构建一个可重复评估的流式评分组件。输入是可重复建立的样本源，组件包含已经验证的有限正数缩放参数，评分接口按协议接收数值序列。要求分批处理输入、逐批产生结果、保留样本数量与总分，并允许调用者提前结束。项目不要求训练神经网络，重点是把本章机制组织成一个能解释的系统。

第一步，先决定样本源是可重复容器还是一次性流。如果需要多轮实验，最好显式接收一个工厂，每次调用工厂建立新的迭代器。工厂应当绑定明确数据版本。不要把“这个对象有迭代方法”直接理解成“每轮都会从头且内容相同”，这两个额外性质必须独立说明。对只能消费一次的外部流，应把限制写进接口并避免伪装成普通数据集。

第二步，为缩放参数选择验证方式。一个字段可以用 property，多种共享规则字段可以使用描述符；若整个配置不可变，则构造验证加不可变表示也合理。验证应在更新状态之前完成，非法更新保留原先合法状态。验收不仅检查能接收正数，还应检查零、负数、布尔值、非有限值和错误类型。无需规定所有实现必须使用同一种机制，只要行为契约一致。

第三步，让批次评分器依赖协议而不是具体均值类。至少实现均值与最大值两种评分器，它们对空批次的处理必须一致或有明确差异说明。最后一批可能较短，因此总体均值不能无权平均各批均值，应按批次数量加权，或者直接累计总分与计数。这个要求把语言接口与统计口径结合，防止接口设计正确而统计计算错误。

第四步，使用生成器逐批产出结果，并设计提前结束的资源处理。若样本源由外层上下文拥有，生成器结束不能擅自关闭不属于自己的共享资源；若生成器自行创建资源，就要确保提前关闭时能够释放。验收包括完整耗尽、只消费第一批后显式关闭、数据源中途抛出错误、空数据源和批次大小大于样本数。每个用例都应有可观测的清理证据，而不是只看程序最终退出。

第五步，如果加入异步读取，要把阻塞评分与等待分开。可以先保持评分同步，仅让数据获取使用可等待接口。建立任务组或其他清晰生命周期边界，确保失败能够传播并清理。不要为了演示并发而添加没有意义的后台任务；只有读取等待确实可以重叠时，异步才有明确收益。性能评估应比较相同数据、相同处理规则与相同资源预算，不能把减少检查误认为并发优化。

项目完成后的说明文档应回答六个具体问题：输入何时读取，哪些对象被修改，哪些状态被缓存，迭代能否重建，异常如何传播，结果怎样追溯到数据版本。写出答案比列出用了哪些高级语法更重要。若其中某个答案依赖特定解释器或框架版本，应明确固定范围，并提供最小复现实验。

你还可以提出一个研究延伸：能否用更少动态机制保持同样契约？把描述符换成构造验证，把继承换成组合，把自定义迭代器换成生成器，逐项比较代码量、错误定位、测试难度和运行开销。机制越复杂不等于方案越先进。真正的进阶能力，是在理解机制之后选择最容易维护正确性的方案，并能够用具体反例解释取舍。

本章机制的权威定义可按问题查阅以下资料。示例与项目是本章独立构造的教学内容，不要求逐页阅读参考手册才开始练习：

- [Python 3.11 数据模型](https://docs.python.org/3.11/reference/datamodel.html)：特殊方法与对象语义。
- [Python 3.11 描述符指南](https://docs.python.org/3.11/howto/descriptor.html)：属性管理与绑定机制。
- [Python 3.11 类型提示模块](https://docs.python.org/3.11/library/typing.html)：协议、泛型与类型辅助接口。
- [Python 3.11 生成器表达式与产生值表达式](https://docs.python.org/3.11/reference/expressions.html#yield-expressions)：暂停、恢复与委托。
- [Python 3.11 asyncio 任务文档](https://docs.python.org/3.11/library/asyncio-task.html)：任务组、取消与等待。
- [Python 3.11 执行模型](https://docs.python.org/3.11/reference/executionmodel.html)：名字解析、作用域及异常传播。
- [Python 3.11 dis 模块](https://docs.python.org/3.11/library/dis.html)：观察特定解释器版本的字节码；不要把指令细节当语言保证。
