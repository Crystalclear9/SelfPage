# 第 3 章 文件、异常、环境与脚本组织

[主题目录](README.md) · [分类目录](../README.md) · [总目录](../../README.md) · [上一章](02-函数类与迭代器.md) · [下一章](04-模块包数据类与配置管理.md)

一个程序在内存小样本上计算正确，只完成了实际学习项目的一部分。它还必须找到正确文件，按正确编码解释字节，识别缺失字段，在失败时保留原因，把结果完整地发布出去，并让另一台机器知道该使用什么解释器和依赖。本章围绕“输入怎样成为可信数据，执行怎样成为可追溯结果”组织这些问题。

示例面向 Python 3.11 及以上版本。所有涉及写入的完整代码都在临时目录中运行，不会修改学习目录或真实数据。操作系统与文件系统有关的保证会明确限定范围；本地文件替换、远程对象存储发布、断电持久性和多文件事务不是同一件事，不能由某一次运行成功推出全部保证。

## 1. 明确文件格式和编码

文件在底层保存字节，文本读取负责按编码把字节解释成字符，格式解析再把字符组织成字段或对象，业务验证最后判断这些字段是否可用。四个层次分别可能失败：路径不可访问、字节无法解码、文本不符合格式语法、字段违反业务约定。把它们都叫“数据读错了”，会失去判断能否重试、是否应修复源文件以及责任属于哪一层的线索。

文本文件应该明确编码。本章统一使用 UTF-8，并在读取和写入两端显式指定，而不依赖某台机器的默认地区设置。中文在一台电脑上正常、另一台出现乱码，往往是编码约定不一致。用忽略解码错误的选项让程序继续，可能直接删除无法解释的字节，使编号或标签发生变化。除非任务明确允许有损恢复并记录损失，否则解码错误应作为输入质量问题暴露。

文本模式与二进制模式用途不同。模型权重、压缩文件和图片不能靠文本解码读取；文本文件也不应因为乱码就随意换成二进制后假装已经理解内容。二进制读取只是保留原始字节，后续仍需要对应格式解析器。扩展名能提示意图，却不证明内容真实符合格式，下载失败的网页也可能被保存成看似正确的文件名。

换行同样属于解释层。不同系统可能用不同换行表示，文本接口会按相应规则处理。CSV 解析需要特别注意文件打开时的换行设置，以便让解析器正确处理字段内换行与记录边界。不要用普通的逐行逗号切割替代 CSV 解析，因为引号中可能合法包含逗号，甚至包含换行。一条业务记录不必对应一个物理文本行。

JSON 适合保存有限层级的配置与摘要，但其数据模型并不等于任意 Python 对象。字典键、元组、集合、自定义类和特殊浮点值都可能涉及转换或兼容问题。为了输出更接近严格 JSON 的结果，可以拒绝非有限浮点序列化；读取外部 JSON 时还要检查实际根对象类型和字段。解析成功只说明语法可被解释，不说明配置已合法。

路径使用 Path 对象组合，有助于表达目录与文件关系，而不是手工拼接斜杠。相对路径基于进程当前工作目录，通常不自动基于脚本位置。脚本在编辑器、终端和任务调度器中启动，工作目录可能不同。入口应明确数据根目录或配置基准，再把解析后的路径传给底层函数，避免每个模块自行猜测。

<a id="sec-1-1"></a>
### 基础算例：一份 CSV 从路径到字段的处理顺序

设输入要求列名为 sample_id、group 和 score。先确定路径基准，实际打开文件，再进行严格解码，随后使用 CSV 解析器读取表头，检查缺失列与重复列，最后转换每条分数。文件存在只解决第一层问题；表头正确也不代表每一行都合格。按层处理能让错误消息准确指向“找不到文件”“编码错误”“缺列”或“某条分数非法”。

假设其中一条分数是“缺考”。如果契约把它定义为缺失，可以保留该记录的缺失状态和原因；如果契约只接受数字，则应隔离或终止。不能默认把它转成零，因为零分与没有测量具有不同统计意义。处理完成后应核对总记录数、有效数和隔离数，同时保证每条输入有且只有一个最终分类。

CSV 的记录位置可以使用解析器消费位置和业务记录序号共同描述。字段内换行时，物理行号与记录序号不一致，所以错误报告中的“行”必须说清楚。对小文件可以报告记录序号；对复杂数据源可以同时保存源文件、记录编号和解析位置。研究复现需要能找到原始事实，而不只是知道发生过多少次错误。

<a id="deep-dive-1"></a>
### 深入讲解：分清字节、文本、语法和业务记录

每一层转换都应该说明是否保真。UTF-8 解码在输入合法时可以恢复文本，但有损替换可能改变字符；CSV 解析把引号语法转成字段值，但不应改变字段内合法逗号；分数转换把文本变成数值，会丢掉某些表面形式，例如前导零；清洗又可能统一空白或分类标签。不是所有变化都错误，但必须知道变化发生在哪一层。

这种分层还能指导测试。坏编码输入不应被拿来验证数值范围错误；缺表头输入不应继续进入模型训练；数值转换测试最好直接使用内存字段，以免文件解析干扰结论。分别建立小型失败样例，能更准确地区分格式接口的问题与业务规则的问题。第五章会进一步讨论独立判据与最小反例。

同一批输入包含多个文件时，还要考虑快照一致性。先读样本表，再读标签表，若两者之间上游发布了新版本，读者可能把旧样本与新标签配在一起。分别检查两个文件都存在、都能解析，并不能排除这种组合错误。更可靠的输入约定是由版本清单明确列出同一批文件身份，读者按该清单读取并核对，不自行混用目录中最新时间的对象。

文件修改时间与文件大小可以作为快速线索，但通常不足以证明内容身份相同。同样长度的文本可以改变标签，时间戳也可能受复制与存储粒度影响。若使用这些元信息避免重复处理，应把它理解成带假设的优化；重要结果仍需要受信版本或内容证据。不要把方便取得的属性直接提升成科学数据版本。

对持续写入的日志，则可能有意接受非快照读取。此时必须说明未完成末行如何处理、读取位置如何保存，以及文件轮转后怎样识别新对象。不能把适用于不可变训练文件的规则无条件套到增长日志，也不能把日志的宽松末行策略带入必须完整的配置文件。输入生命周期决定合理协议，解析器只是其中一层工具。

文件读取也涉及时间。先检查存在，再打开，期间文件可能被删除或权限改变；先读一个文件的元信息，再读内容，内容也可能被替换。因此事先检查有助于给出友好提示，却不能代替实际操作中的异常处理。对强一致性要求更高的系统，需要版本化、快照或其他存储保证，而不是增加更多 exists 判断。

<a id="sec-2"></a>
## 2. 异常是错误信息的载体

异常不仅表示“程序停了”，还携带类型、消息和调用链。类型帮助调用者区分缺文件、权限、格式与数值错误；消息提供输入位置与期待条件；调用链展示失败怎样穿过层级。完整保留这些信息，往往比输出一长串没有结构的提示更有助于定位。不要只保留最后一句“运行失败”，把最有价值的上下文丢掉。

异常应与不能满足的契约对应。文件找不到不是合法空数据，分数文本解析失败不是合法零值，模型参数缺失也不是默认成功。若某些情况确实允许降级，降级结果应带状态，让调用方知道实际使用了何种替代。静默吞错会让程序表面稳定，结果却建立在无法解释的输入上。

捕获范围尽量小，只围住可能出现且你能处理的操作。若想处理某个可选配置文件缺失，只包住读取动作并捕获相应异常，不要把模型构建与训练也放进同一个宽泛捕获中。否则程序内部真正的变量拼写错误、数据形状错误，也可能被误判成“配置可选所以继续”，在更远处造成难以理解的结果。

异常重新抛出可以保留原调用链；如果转换为更贴近领域的错误，应该连接原始原因。例如底层浮点转换失败，上层可以抛出“文件中第几条记录的 score 不合法”，并保留原始转换异常。这样使用者得到业务上下文，开发者仍能看见真实原因。随意从空白开始抛一个不相关错误，会使排查路径断裂。

finally 适合无论成功失败都需要执行的清理，但清理代码本身也可能失败。若清理又抛出异常，最初错误可能在展示上被新错误覆盖；应该避免不必要的清理复杂度，并谨慎保留原始原因。更不要在最终清理块中返回一个默认值，这可能覆盖原来的返回或异常，让调用者误以为操作正常完成。

<a id="sec-2-1"></a>
### 机制展开：异常应捕获在能够作出决策的层

数值解析器知道字段不能转成数值，但未必知道一条坏记录能否跳过；批处理层知道质量政策，可以决定隔离；命令行入口知道用户请求和退出状态，可以决定终止并显示说明。这种分工让每层只作自己有信息支持的决策，而不是底层统一返回零，把所有选择提前封死。

可恢复与不可恢复还依赖上下文。必需数据文件缺失通常应失败，可选说明文件缺失可能使用空说明；临时网络超时可能重试，确定的格式错误重复请求通常没有用。错误类型是线索，不是完整政策。同一个异常在不同业务位置可能需要不同处理，应该结合操作身份与数据契约判断。

错误消息最好包含操作、对象标识和期望条件，例如“解析输入成绩文件的第三条记录时，score 应为零到一百的有限数值”。消息不必把整份原始数据打印出来，尤其是大文本或敏感字段。足够定位与控制信息规模可以同时做到。日志层再决定是否保留完整调用链，避免用户提示与调试输出互相混杂。

<a id="visual-03-advanced"></a>

### 图解：异常链保留底层原因与上层语义

![异常链保留底层原因与上层语义](images/03-advanced.svg)

底层解析失败只说明某个局部转换无法完成，上层还知道这是哪条记录、哪个阶段或哪个输入文件。封装领域异常时保留原始原因，可以同时说明业务失败和技术原因，减少只有“处理失败”四个字的信息损失。

<a id="sec-3"></a>
## 3. 隔离环境与组织入口

虚拟环境的目标是让一个项目使用自己的 Python 包集合，减少项目间依赖冲突。创建环境时使用明确解释器，安装依赖时用该解释器执行包管理模块，能降低命令行上的 pip 与 Python 指向不同位置的问题。环境激活主要改变当前终端命令解析路径，不是程序获得隔离能力的唯一入口；直接调用虚拟环境解释器同样可以运行。

在 Windows PowerShell 中，环境里的解释器通常位于 Scripts 目录；在类 Unix 系统中通常位于 bin 目录。教材中的路径例子应该按系统区分，而不是让所有人复制同一条斜杠混杂命令。若不想依赖激活脚本，可以明确调用解释器完整路径，再使用其模块安装命令。实际版本与依赖内容还需要记录，环境目录名字本身不说明装了什么。

虚拟环境不是操作系统容器，也不隔离所有文件、网络和系统库。程序仍可以访问它有权限访问的数据，数值包还可能依赖底层驱动与共享库。把项目放进虚拟环境，不会自动解决显卡驱动、不同硬件指令或外部工具版本问题。复现范围越严格，环境说明越需要覆盖这些依赖层次。

程序入口负责把外部参数变成内部调用。常见的主入口判断让模块被导入时主要定义函数与类，而明确执行时才读取文件、创建输出和启动计算。这样测试或其他脚本可以复用工具函数，不会因为导入而突然开始训练。入口逻辑应尽量短，把实际工作放在可独立调用的函数中。

命令行调用还有退出状态。正常完成返回成功状态；参数错误或执行失败应返回非成功状态，方便外层脚本和调度器判断。只打印“失败”但进程仍报告成功，会使自动化流程继续消费不存在或过时结果。后文会把日志、产物和退出状态共同作为运行证据，避免仅靠屏幕上一句话判断成功。

<a id="sec-4"></a>
## 4. 把脚本组织成可重复流程

可重复流程首先有明确阶段：解析参数、确定输入、验证配置、读取数据、计算、校验输出、发布结果。阶段之间传递清楚对象，而不是通过任意全局变量与固定当前目录交换。对一个小项目，不必建立庞大框架；几个职责明确的函数和一个入口就足够。组织的价值在于可以单独检查，也能从入口看出执行顺序。

阶段还应有成功条件。例如读取成功意味着得到符合结构约定的数据，而不是文件句柄打开了；计算成功意味着所有必需结果已产生且满足有限性与数量检查；发布成功意味着最终路径可读取且对应本次运行。若阶段名只是一些打印语句，内部状态没有约束，它们并不能提供可靠恢复依据。

不要让底层计算函数自己选择输出目录、覆盖固定文件或临时改变工作目录。把路径作为显式参数，入口统一决定。这能让同一计算在临时目录测试，在真实目录运行，也能避免多个实验互相覆盖。输出目录命名应有冲突策略：拒绝已存在目录、生成新运行标识，或明确允许受控覆盖，而不是每次默默复用。

对长任务，先做启动预检：配置类型与范围、必需输入是否可读、输出父目录是否合理、样本结构是否匹配。预检不能保证后续不会出错，但能把明显问题提前暴露。也不要让预检完整重复昂贵计算，否则“先检查一下”可能本身消耗大半预算。合理预检针对可便宜验证的必要条件。

流程结束时应输出能解释结果的摘要：实际输入记录数、有效数、隔离数、阶段完成状态和结果路径。摘要应与程序内部实际计数一致，而不是依据用户期待值填写。计算函数可以返回这些统计，入口负责展示和保存；这样同一份事实不会在多个地方各算一遍，产生彼此矛盾的日志。

<a id="sec-5"></a>
## 5. 配置与运行结果相互对应

结果必须能追溯到实际使用的配置，而不是用户最初写下的配置文件。默认值、文件参数、环境变量和命令行覆盖都可能影响最终行为。应在启动后形成唯一有效配置，验证后传给各阶段，并把这一份保存到结果目录。否则日志记录学习率为一个数，训练代码却从另一个全局变量读取，后续比较没有可信基础。

配置快照还应说明单位与解释规则。相同的数值一百可能表示训练步数、样本数或毫秒，字段名字和模式版本决定其含义。若旧版本使用秒、新版本改成毫秒，只保存数值而不迁移单位，会让看似相同配置产生完全不同执行。规范化时把单位转换到唯一内部表示，并把原始来源与转换规则记入必要证据，比反复猜测历史参数更可靠。

输入路径也属于配置，但路径字符串不是数据版本。同一路径今天和明天可能指向不同内容；相同文件名在不同机器也可能是不同数据。可以记录内容摘要、数据集版本或来源清单，必要时保存不可变副本。内容哈希帮助确认字节相同，却不会告诉你标签是否正确、数据是否代表目标总体，技术身份与科学有效性仍要分开。

运行结果目录最好包含清晰清单：有效配置、输入身份、环境摘要、阶段状态以及产物列表。不是每个项目都需要保存完整软件包镜像，但至少要让读者知道哪些证据存在、哪些假设依赖外部环境。只保存一个模型文件，通常难以解释它如何产生，更难判断可否继续训练。

状态文件需要区分计划、进行中、失败与完成。程序一启动就创建名为 success 的文件，会误导后来检查；只有全部必需产物校验通过后才能写完成标记。失败记录也不应覆盖成空白成功摘要。运行是否完成是一个可验证状态，而不是某段代码顺利执行到了最后一个打印语句。

配置中还可能有敏感值，如访问令牌或内部服务地址。学习项目也应区分需要保存的科学参数与不宜直接写入普通日志的凭证。可以记录凭证来源标识而非明文内容。这里不是要求复杂安全系统，而是避免“为了复现就把所有环境变量完整保存”这种不加区分的做法。

<a id="sec-6"></a>
## 6. 进阶：原子写入与实验恢复

直接打开最终文件写入，通常会先截断已有内容。若程序中途失败，旧结果已经丢失，新结果又不完整。更稳妥的发布模式是在目标目录建立独立临时文件，完整写入并关闭，必要时校验，然后用替换操作把它发布到最终路径。这样把“计算过程中逐渐形成的内容”与“读者应看到的正式版本”分开。

替换的保证要精确理解。对支持相应语义的本地文件系统，同一文件系统上的成功原子替换可以让读者看到旧版本或新版本，避免中间半文件；它不等于跨多文件事务，也不自动保证突然断电后全部数据与目录项持久保存。跨文件系统移动可能不是同样机制，远程存储又有自己的接口与一致性契约。

临时文件应具有唯一名字，避免多个运行写到同一个中间路径。关闭句柄后再替换，在某些平台尤其重要，因为打开文件的共享规则可能阻止替换。失败后清理只删除本次创建且仍存在的临时文件，不应扫描并删除整个目录里所有看起来像临时文件的东西。清理也需要所有权边界，不能把其他运行的数据当垃圾。

恢复训练比重新执行复杂。除了模型参数，还可能需要优化器状态、学习率调度进度、随机源、数据采样位置和已经提交的结果记录。只加载权重并从第一批重新开始，不一定是精确续接。对于普通数据处理，也要说明哪些记录已提交、哪些仅在内存，避免恢复后遗漏或重复。

<a id="sec-6-1"></a>
### 文件写入的成功需要怎样的证据

写函数没有抛异常，只说明相关调用没有报告失败，还应检查最终文件是否存在、能否按格式读取、关键字段是否与预期一致。对重要产物可以验证字节数或内容摘要。不能只检查“文件大小大于零”，因为错误页、截断 JSON 或旧结果也可能非空。证据应对应产物语义，而不是一个方便的外观指标。

成功标记最好指向本次运行标识与产物清单。若只写一个固定的 done 文件，后一次运行失败但旧标记仍在，检查程序可能误判。可以给每次运行独立目录，或让标记明确包含版本与摘要，再由读取者核对。发布协议的两端都需要参与：写入者按规则提交，读取者按规则识别完成。

单文件原子替换是有用积木，但当摘要与数据必须一起更新时，两次替换之间仍存在不一致窗口。可以先把所有版本化产物写入新目录，最后替换一个小型清单或指针，让读取者只按该清单消费。这个模式把提交点集中到一个对象，虽然仍需处理持久性与并发规则，却比假设多文件“写得很快所以相当于原子”更可靠。

<a id="sec-7"></a>
## 7. 练习与逐步解析

**练习一：区分四层错误。** 一个文件能打开，但读文本失败；另一个文本能读，但 JSON 解析失败；第三个解析成功却缺学习率。分别属于编码、语法和业务结构层。解析时应给不同原因，而不是都返回空字典。空字典可能是合法输入，也可能触发默认值，若用它代表所有失败，错误就被转化成另一场未被授权的实验。

**练习二：工作目录改变。** 同一个脚本从两个目录启动，相对路径分别指向哪里？解析：基于各自进程工作目录，而非默认跟随脚本位置。修复可以要求显式数据根目录，或明确以配置文件父目录为基准。采用哪种都要记录解析后的实际路径。不要靠程序内部随处改目录来补救，否则其他相对路径会随之改变。

**练习三：清理失败。** 主计算抛出格式错误，清理临时文件时又因权限失败。应该保留什么？解析：最初格式错误仍是主要原因，清理错误应作为附加信息处理，而不是无声覆盖。更好的实现减少清理资源数量、限定所有权，并让日志能区分主失败与清理失败。没有必要把所有情况都变成单一泛化异常。

<a id="sec-7-1"></a>
### 边界追问：捕获异常后返回零是否更健壮

合法零与解析失败在业务上不同。把后者强制变成零会改变均值、通过率和缺失分布，可能引入系统偏差。健壮处理应定义缺失、隔离、修复或终止策略，记录发生了什么，并保证下游知道实际样本口径。程序不报错不意味着数据可信，更不意味着研究结论可靠。

如果任务确实要求无法读取时使用默认零，也应返回或记录状态，并说明为什么零是合理替代。比如某个可选计数未出现被定义为零，与一个本应存在的测量值解析失败是两种情况。关键不是禁止默认值，而是不能让默认值抹去来源差异。

<a id="sec-8"></a>
## 8. 完整案例：严格 CSV 读取与行级隔离

下面实现成绩文件读取器。契约为固定列名，拒绝重复表头与未知结构，允许字段内逗号，分数字符串在去除两端空白后解析为有限且位于零到一百的浮点数。空分数归为缺失；业务字段不合格的记录进入隔离列表；整个文件缺列或结构异常则失败。这样区分文件级错误与记录级错误，不让缺表头被误当成大量普通坏行。

样本编号必须非空，但本步骤不去重，因为重复可能代表多次测量。分组限定为 A 或 B。记录序号从一开始，不包含表头；它是业务记录编号，不保证等于物理行号。输出保留该序号，便于追踪。完整代码在临时目录写入一份测试文件，运行结束自动清理，只演示输入输出规则。

```python
import csv
import math
from pathlib import Path
from tempfile import TemporaryDirectory

def read_scores(path):
    accepted, rejected = [], []
    with Path(path).open("r", encoding="utf-8", newline="") as handle:
        reader = csv.DictReader(handle, strict=True)
        required = ["sample_id", "group", "score"]
        if reader.fieldnames is None:
            raise ValueError("header is required")
        if len(reader.fieldnames) != len(set(reader.fieldnames)):
            raise ValueError("duplicate header")
        if set(reader.fieldnames) != set(required):
            raise ValueError("unexpected columns")
        for number, row in enumerate(reader, start=1):
            if None in row or any(value is None for value in row.values()):
                raise ValueError(f"record {number} has inconsistent field count")
            sample_id = row["sample_id"].strip()
            group = row["group"].strip()
            raw = row["score"].strip()
            reason = None
            value = None
            if not sample_id:
                reason = "empty_id"
            elif group not in {"A", "B"}:
                reason = "invalid_group"
            elif raw == "":
                reason = "missing_score"
            else:
                try:
                    value = float(raw)
                except ValueError:
                    reason = "invalid_number"
                else:
                    if not math.isfinite(value):
                        reason = "non_finite"
                    elif not 0 <= value <= 100:
                        reason = "out_of_range"
            if reason is not None:
                rejected.append({"record": number, "reason": reason})
            else:
                accepted.append({
                    "record": number, "sample_id": sample_id,
                    "group": group, "score": value,
                })
    return accepted, rejected

with TemporaryDirectory() as temporary:
    path = Path(temporary) / "scores.csv"
    with path.open("w", encoding="utf-8", newline="") as handle:
        writer = csv.writer(handle)
        writer.writerow(["sample_id", "group", "score"])
        writer.writerows([
            ["sample,one", "A", "0"],
            ["second", "A", "60"],
            ["third", "B", ""],
            ["fourth", "B", "nan"],
            ["fifth", "B", "bad"],
            ["sixth", "B", "101"],
            ["seventh", "B", "90"],
        ])
    accepted, rejected = read_scores(path)
    assert [row["score"] for row in accepted] == [0.0, 60.0, 90.0]
    assert accepted[0]["sample_id"] == "sample,one"
    assert [row["reason"] for row in rejected] == [
        "missing_score", "non_finite", "invalid_number", "out_of_range",
    ]
    positions = [row["record"] for row in accepted + rejected]
    assert sorted(positions) == list(range(1, 8))
```

代码使用解析器而非字符串切分，因此编号中的逗号不会制造额外字段。对于字段数不一致，我们选择文件级失败，因为它可能表示格式解析已偏离预期。若任务希望逐行隔离结构错误，也可以重新设计，但对字段内换行文件必须谨慎，不能随意按物理行恢复解析而破坏记录边界。

为什么先检查表头重复，再比较列集合？集合会去掉重复，若先转集合，重复列名的信息已经丢失。字典读取重复表头时可能覆盖值，造成数据静默损失。这个例子体现输入验证顺序：在有损转换之前检查会被转换抹去的信息。类似地，编号是否允许前导零，也必须在数值转换之前决定。

对每条记录只记录一个首要原因，是为了形成互斥分类。若同时有空编号和非法分数，代码优先报告空编号；如果想收集全部原因，应改为原因列表并区分拒绝记录数与问题条数。计数对账不能只看总量，还要保证原始序号完整且不重复。本例最后一个断言正是覆盖检查。

读取器只处理数据解析，不决定输出位置，也不训练模型。上层可以根据拒绝比例决定是否继续，例如隔离比例超过阈值就终止。阈值属于项目质量政策，不应藏在底层读取器里。读取器也不把异常统一打印后继续，而是保留文件级失败，让有能力决定的入口处理。

<a id="sec-9"></a>
## 9. 路径、资源与上下文管理的边界

路径对象表达的是位置，不是打开的资源。构造一个 Path 不会证明对应文件存在，也不会读取文件；调用读取方法时才实际请求系统操作。把位置解析、权限检查和内容读取分开理解，能避免以为创建路径变量就已经完成预检。相对路径还依赖当前目录，而绝对路径虽然消除这层歧义，仍可能指向会变化的文件或符号链接。

路径规范化与业务授权也不是一回事。解析路径可以帮助显示真实位置、检查预期目录关系，但在并发修改或恶意链接环境中，仅靠事先字符串判断未必构成完整安全保证。一般学习项目的重点是避免误读误写：入口展示或保存最终路径，输出限制在明确运行目录，清理仅针对自己创建的文件。不需要把普通脚本写成通用沙箱，也不能完全忽略路径来源。

资源生命周期应由明确拥有者管理。打开文件得到句柄，它在使用期间占用系统资源；with 表达在进入与退出时执行相应管理协议，即使块内抛异常，也会走退出逻辑。但上下文管理器可以选择抑制某些异常，退出逻辑本身也可能失败，所以“用了 with”不等于所有错误都自动解决。它让生命周期结构清晰，仍需正确实现协议。

多个资源可以按嵌套上下文组织，后获得的通常先释放。数量动态变化时，可以使用 ExitStack 集中注册清理，避免手写复杂的成功标记。关键仍然是资源所有权：调用者传入的已打开文件是否由函数关闭，必须说明。常见原则是创建者负责关闭，除非接口明确转移所有权；随便关闭别人的句柄会破坏外部流程。

生成器与上下文组合尤其需要小心。若函数内部打开文件并逐条产生记录，文件会随生成器暂停而保持打开；消费者提前停止却不关闭生成器，资源可能迟迟不释放。可以让外层 with 管理文件，把迭代放在其中，或者给数据源提供显式上下文接口。不能依赖某个解释器当前恰好立即回收对象来实现跨环境正确性。

下面展示异常发生后文件仍会关闭，且错误被保留。这里检查的是可见句柄状态，而不是推断系统缓存已持久保存。文件位于临时目录，异常是故意产生的局部数值转换错误，没有吞掉其他不相关故障。

```python
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as temporary:
    path = Path(temporary) / "sample.txt"
    handle = None
    try:
        with path.open("w", encoding="utf-8") as handle:
            handle.write("before error")
            int("not-an-integer")
    except ValueError:
        assert handle is not None and handle.closed
    else:
        raise AssertionError("conversion should fail")
    assert path.read_text(encoding="utf-8") == "before error"
```

最后的文件仍有已写内容，说明资源关闭与业务回滚不同。with 没有撤销写入，更没有让整段计算原子化。若要求只有全部成功才让读者看到结果，应采用下一节的发布协议，而不是期待上下文管理自动删除半成品。把生命周期、完整性与持久性分开，是可靠文件处理的基础。

<a id="sec-10"></a>
## 10. 可靠发布：临时文件、清单和提交点

我们实现一个原子发布 JSON 的教学函数。它先把待保存对象序列化为文本，明确拒绝非有限数值；再在目标父目录创建独立临时文件，写入、刷新并关闭；之后替换正式路径。序列化放在创建临时文件之前，能让明显的数据错误更早失败。函数假设父目录已存在，不偷偷建立任意目录树。

刷新 Python 缓冲与调用系统同步请求属于不同层。示例执行 flush 后调用 fsync，尽力将文件内容交给系统持久化接口；这仍不构成对所有硬件、网络文件系统或目录项持久性的统一保证。教材必须明确这一限制，而不是把代码中出现同步函数就等同于“绝对不会丢数据”。高可靠存储需要结合具体系统设计与故障测试。

```python
import json
import os
from pathlib import Path
from tempfile import NamedTemporaryFile, TemporaryDirectory

def publish_json(path, value):
    target = Path(path)
    payload = json.dumps(
        value, ensure_ascii=False, sort_keys=True,
        allow_nan=False, indent=2,
    ) + "\n"
    temporary_path = None
    try:
        with NamedTemporaryFile(
            mode="w", encoding="utf-8", newline="\n",
            dir=target.parent, prefix=target.name + ".",
            suffix=".tmp", delete=False,
        ) as handle:
            temporary_path = Path(handle.name)
            handle.write(payload)
            handle.flush()
            os.fsync(handle.fileno())
        os.replace(temporary_path, target)
        temporary_path = None
    finally:
        if temporary_path is not None:
            temporary_path.unlink(missing_ok=True)

with TemporaryDirectory() as temporary:
    target = Path(temporary) / "result.json"
    publish_json(target, {"count": 2, "mean": 3.0})
    loaded = json.loads(target.read_text(encoding="utf-8"))
    assert loaded == {"count": 2, "mean": 3.0}
    before = target.read_bytes()
    try:
        publish_json(target, {"mean": float("nan")})
    except ValueError:
        pass
    else:
        raise AssertionError("non-finite JSON should fail")
    assert target.read_bytes() == before
    assert sorted(item.name for item in Path(temporary).iterdir()) == ["result.json"]
```

示例的清理逻辑仍有值得讨论的边界：如果临时文件删除本身失败，它可能抛出新的异常。在需要更完整异常保留的生产工具中，可以单独记录清理失败，并让主失败继续传播。本例没有把清理错误悄悄吞掉，但也没有声称已提供全部故障组合的最佳报告。读代码时要能够区分核心发布逻辑与错误报告策略。

并发写入同一目标也是另一项需求。两个运行各自正确替换文件，最后仍只有某一版本保留，这可能是合法“最后写入者胜出”，也可能是不可接受的覆盖。单文件原子性不提供自动冲突检测。可以采用每次运行独立路径、版本比较或明确锁协议。不要在写入前仅检查“目标不存在”，就以为消除了检查之后其他进程创建文件的竞态。

多产物发布可以采用版本目录加清单：先把数据、指标和配置写入新版本位置，验证完成后发布一个指向该版本的清单。读取者只消费清单中的对象，并核对摘要。若写到一半失败，未提交版本可以留待受控清理，不会被当作正式结果。清单本身是提交点，但仍需定义旧版本保留、并发提交和恢复策略。

清单还可以记录产物之间的语义关系。比如指标使用哪个模型和数据切分，预测文件有多少行，类别顺序是什么。字节摘要只能证明文件身份，不能表达这些关系。一个完整发布协议不只是安全写文件，还要让消费者知道这些文件属于同一次计算，并且满足相互兼容的约定。

<a id="sec-11"></a>
## 11. 日志、退出状态与可观察性

日志记录运行过程中发生了什么，指标描述任务结果，状态文件说明生命周期，它们承担不同职责。把所有内容都打印成没有结构的字符串，短任务尚可，长实验很难查询。至少保留时间、级别、运行标识、阶段和具体消息，让读者能区分正常进展、可恢复问题与终止失败。详细调用链适合错误日志，不必在每个正常样本都输出。

日志不是数据本体的替代。只记录“读取成功”不足以说明读取了哪份文件、多少条记录；只记录“丢弃了一些数据”不足以解释偏差来源。可以保存摘要计数与排除原因分布，必要时另存隔离清单。记录规模应与风险匹配：不能打印整个大数组试图证明形状正确，也不能因为日志怕太多就删除所有关键证据。

错误层级应一致。某条允许隔离的坏记录可以记为警告，整个必需输入缺失则应使运行失败。不要把每条坏行都记录成致命错误，却仍报告整个任务成功；也不要把数据全被隔离仅记成普通信息，最后得到空结果。质量门槛需要明确，例如有效记录至少一条或拒绝比例不得超过预定阈值。

退出状态给外部自动化提供一个简洁信号。内部主函数可以返回整数，再由真正入口把它作为退出码。测试时直接调用主函数，检查返回值与产物；在子进程集成测试中再核对进程状态。这样不需要在每个底层函数里直接终止进程，工具函数也能被其他程序复用。

运行时间与性能日志也要解释口径。总耗时、读取耗时和计算耗时可能包含重叠或缓存影响，不能简单相加；只测训练循环而忽略数据准备，也许不能代表用户等待时间。先定义要回答的问题，再选择计时范围。时钟测量用于观察相对表现，不能作为确定性单元测试的唯一判据。

可观察性还包括失败后的证据是否可用。运行异常时应保留失败阶段、有效配置身份和原始原因；已经完整发布的旧结果不应被半成品覆盖；未提交临时产物应该能够辨识。不是要求永远保存所有中间文件，而是让生命周期信息与最终产物保持一致。本学习资料自身只需要最终 Markdown，但教材中的项目可以有明确设计的必要运行证据。

## 12. 恢复协议：幂等、检查点与重放

恢复的核心问题是确定哪些工作已经生效。假设处理一千条记录，每一百条写一次汇总，程序在六百五十条时中断。内存进度可能到六百五十，正式输出只包含六百，日志又可能已打印到六百四十九。恢复应以明确提交记录为准，而不是挑最大数字。否则重跑可能漏掉未提交数据，或把已经提交部分重复计入。

幂等操作重复执行仍产生相同最终效果，例如把某个版本结果写到确定键下；累加操作则通常不幂等，重复加一次会改变总量。若使用“处理后追加一条结果”的协议，需要记录唯一输入身份与提交状态，避免重放产生重复。不能仅凭样本位置去重而忽略输入文件版本，另一份文件的同位置不是同一事实。

检查点应记录可恢复的充分状态。对纯数据聚合，可能需要输入版本、已提交记录位置和累计统计；对随机抽样，还需要随机状态；对模型训练，还可能需要优化器、调度器和采样器进度。检查点太少无法续接，太多则增加存储与兼容成本。应从恢复后下一步需要哪些信息反推字段，而不是把整个进程对象随意序列化。

检查点与输出之间需要一致关系。先更新进度再写结果，失败可能跳过尚未写出的结果；先写结果再更新进度，重试可能重复写。解决方式依赖存储能力，可以使用事务，或版本化提交记录把两者关联，也可以设计可幂等重放。对于本地单机小项目，最容易解释的方案往往是每个批次保存独立版本结果与一个明确清单。

恢复还要核对兼容性。旧检查点使用的配置、特征顺序或代码规则变化后，继续运行可能成为新实验。可以区分严格续接与有意迁移，记录差异并拒绝不兼容变更。只要文件名相同就加载，可能把旧类别映射应用到新模型，得到不会立即报错却语义错误的结果。

重试必须有界，并针对可能瞬时恢复的故障。格式确定错误不会因为等一秒就变合法，权限配置错误反复重试也通常无益。网络超时则可能结果未知：对方也许已经完成写入，只是确认丢失。对有副作用操作，先设计幂等标识与查询机制，再谈自动重试。一个简单 for 循环重试五次，不足以构成可靠协议。

研究练习可以模拟三个中断点：产物写入前、产物写完但未提交清单、清单提交之后。分别解释恢复时读者应看到什么，哪些文件可忽略，哪些工作应重做。故障注入最好在临时目录用明确异常完成，不必真的断电。这个实验会迫使你把“应该没问题”的直觉转成可检查状态。

<a id="visual-03-mechanism"></a>

### 图解：幂等恢复：重放已提交批次不再重复计数

![幂等恢复：重放已提交批次不再重复计数](images/03-mechanism.svg)

恢复后再次收到批次 k，程序先核对该批次的提交身份。已经提交的结果直接复用；尚未提交的批次才进入计算与发布。这样重复执行输入不会必然造成重复累加。

这是一项协议设计：提交记录与结果发布若不一致仍可能重复或遗漏。非事务外部副作用还需要幂等键、原子机制或补偿，单靠异常捕获无法获得保证。

## 13. 环境证据与跨机器复现

“使用同一个环境”需要具体解释。解释器主次版本、依赖包版本、操作系统、硬件、驱动与底层数值库都可能影响行为。普通文本汇总项目对硬件差异不敏感，深度学习训练则可能涉及不同内核与归约顺序。复现要求应按任务分级：能重新执行、结果在容差内一致、指标统计相近、逐位相同，不是同一标准。

依赖声明与锁定文件也承担不同角色。声明表达项目需要哪些功能与允许范围，锁定记录某次解析出的具体版本及相关身份。只保存当前安装列表，可能混入许多与项目无关的包；只写宽泛最小版本，又可能在未来安装不同组合。小项目可以先记录明确直接依赖和实际运行版本，再按复现要求增加更严格约束。

虚拟环境通常适合重新创建，不适合把整个环境目录拷到另一台不同路径或系统机器后直接假设可用。可执行脚本、路径和二进制包可能依赖原环境。更可靠的交付是提供依赖信息、解释器要求和启动命令，让目标环境按规则建立，再执行小型验收。环境目录本身是运行产物，不必成为学习资料中的长期结果。

还要确认实际启动的是哪个解释器。终端、编辑器与笔记本内核可能各自指向不同环境。可以在诊断摘要记录解释器路径与版本，导入关键包后记录其版本。不要仅凭终端前面的环境名字就判断所有工具都使用它；更不要在一个解释器中安装包，却在另一个内核里反复尝试导入。

随机种子只控制某些随机过程的起点。数据源顺序、工作线程调度、硬件数值实现和非确定性内核不一定由同一个种子控制。程序也可能在多个位置反复重置种子，导致批次间意外重复。复现策略应说明随机源划分与初始化时机，而不是在所有函数开头复制一行设置种子。

数据版本往往比小数末位更重要。输入多了一批样本、标签映射顺序变化或时间切分边界移动，都可能显著影响结果。环境完全相同但数据不同，不是同一实验；数据相同但清洗规则变更，也不是相同输入语义。有效配置、数据身份和代码版本共同描述执行，不能只记录其中一项。

跨机器路径不应硬编码个人桌面目录。可以让配置保存逻辑数据标识与相对布局，由入口接受实际根目录映射，再记录解析后的运行路径。这样既有可迁移性，也有本次运行的追溯信息。不能为了“跨机器”把所有绝对路径都删掉而不给映射规则，也不能为了“可追溯”要求每个人建立一模一样的用户目录。

离线复现还涉及外部服务。若数据来自会更新的接口，只记录请求地址不够；需要保存响应版本、快照或能够重取同版数据的标识。依赖远程模型服务时，服务行为也可能随时间变化。对不可冻结依赖，应诚实说明复现边界，并尽量把关键中间结果作为正式数据证据保存，而不是声称只要脚本相同就绝对一致。

最终验收可以从最小环境开始：创建干净虚拟环境，安装声明依赖，用一份小型固定输入执行入口，核对退出状态、输出结构与手算结果。这个过程比在长期使用的个人环境中成功一次更能发现隐式依赖。验收通过也不证明所有平台兼容，只证明你实际检查的环境满足约定，应把范围写清楚。

## 14. 综合研究任务与参考资料

**任务一：建立输入失败矩阵。** 为同一个读取入口准备不存在路径、空文件、坏编码、重复表头、缺字段、多余字段、合法零、空分数和非有限值。先不运行程序，逐项写出应当是文件级失败、记录隔离还是合法输入，再对照实际行为。解析重点是把政策写在代码之外，避免测试只是重复实现者当时的临时决定。

然后检查错误定位信息。不存在路径应指明操作对象，坏编码应保留解码原因，结构错误应尽可能给出记录位置，隔离项应保留稳定序号。若某类错误只有“失败”两个字，问自己接手者需要怎样定位。若错误消息包含整份大文件，又问哪些信息真正必要。信息不足与信息过载都会降低排查效率。

**任务二：模拟发布中断。** 在临时目录先放一个合法旧结果，尝试发布一个不能序列化的新对象，确认旧结果字节未变；再在写临时文件之后、正式替换之前故意抛异常，确认最终路径仍指向旧结果。最后正常发布并检查新结果能解析，临时文件没有残留。验收应同时包含成功与失败路径，不能只观察最后文件非空。

如果要验证多产物，分别模拟数据写完但指标未写完、全部写完但清单未提交、清单已提交三个状态。读取者应只接受已提交且清单一致的版本。这个任务说明“每个文件都原子写”与“整组结果一致”有差别。回答中应明确提交点，而不是泛泛地说加锁或加日志。

**任务三：设计可恢复聚合。** 输入按固定版本和记录序号识别，每批保存局部计数与总和，提交清单标记已完成批次。中断后读取清单，重新计算尚未提交批次，最后合并各批统计。解析时应说明为什么不能直接相加批均值，为什么批次身份需要包含输入版本，以及重新执行已完成批次如何避免重复计入。

进一步加入隔离记录计数与原因分布。恢复后既要核对总体数值，也要核对输入覆盖：有效与隔离序号互斥且完整。只比较最终总和可能漏掉“一条重复、另一条遗漏但金额相抵”的错误。恢复验证不仅是结果近似一致，还要保证处理了正确事实集合。

**任务四：环境迁移实验。** 在独立临时环境中运行同一小输入，记录解释器、直接依赖、启动命令与有效配置。比较两次结果时，先确认输入字节与业务规则一致，再比较数值。若结果不同，按输入、代码、配置、依赖与硬件层次逐项排查，不要第一反应就把所有问题归结为随机种子。

**进阶追问：如何确定实验归档的最小集合？** 从结果反向列出依赖：预测需要模型、前处理与词表，重训需要数据身份、划分、有效配置和代码，续训还需要优化器、调度器与随机状态。只有不再被这些过程引用、也无独立诊断价值的临时产物才适合清理。先明确归档目标，再判断文件用途，才能在控制存储成本的同时保留结果解释与重建所需的证据。

另一个进阶方向是把发布协议与存储系统联系起来。本地文件替换、数据库事务和对象存储版本化提供不同能力。尝试用同一组故障场景比较它们：单对象写入中断、并发覆盖、多个对象一致提交、读取旧版本以及突然断电。没有必要马上实现全部系统，但应能够指出本章单机方案不能解决哪些更广泛问题。

掌握本章后，你应该能解释一次运行从路径到正式产物的每个阶段，在错误时保留有效证据，在成功时证明结果属于本次执行，并明确复现边界。下一章进一步把模块、配置对象和命令行覆盖组织成稳定项目结构；第五章则把本章的故障场景转成可持续验证的测试。
