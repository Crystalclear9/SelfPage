## 1. 从最小失败输入开始

调试是用证据缩小错误原因的过程，不是随机改代码直到程序跑通。首先固定失败条件：输入版本、实际配置、启动方式和完整错误信息。若某次运行失败后马上覆盖数据、重启环境并改动多个模块，往往会失去解释原问题的机会。保留可重现的小样例，能让每个后续修改都有可比较依据。

读取异常调用链时，先找到直接触发错误的位置，再向上追踪调用路径和输入来源。最底层报错可能只是前面问题的表现，例如矩阵乘法形状错误来自更早的数据列顺序变化；不能只在报错处随便转置，直到尺寸凑上。要问每个轴代表什么，以及这个对象是在哪个阶段偏离契约的。

最小失败输入是仍能重现问题、同时删掉尽可能多无关因素的样本。一个百万行连接错误可能只需要两个左键、一个重复右键和一个缺失匹配；一个共享引用问题可能只需要一个嵌套列表与两个名字。缩小不是忽略真实复杂度，而是让因果链变得可见。修复后，这个样例还可以成为有独立意义的回归检查。

缩小可以从规模、结构和环境三方面进行。先减少记录数量，再减少字段，再替换昂贵外部依赖；保持每一步仍能重现。若问题消失，说明被删除因素可能相关，但不一定是唯一原因。不要只保留最后一个成功缩小动作而忘记输入假设，最小样例仍必须属于原函数承诺支持的输入域。

日志与断点解决不同问题。日志适合长任务和跨阶段历史，断点适合观察当前局部状态。一次打印整个数组常常信息太多，类型、形状、有限性、少量代表值和关键计数更有效。观察也可能改变程序，例如把生成器转成列表会消费它，所以调试操作本身需要理解语义。

修复时尽量一次改变一个相关因素，并写下预测。如果你怀疑过滤步骤导致标签错位，应先检查保留编号与标签编号，而不是同时改模型、随机种子和损失。每个假设对应一个能支持或反驳的观察，调试才会逐步收敛。程序偶然不再失败，并不等于你知道根因已经解决。

<a id="sec-1-1"></a>
### 基础算例：从正常样例扩展到边界样例

一个平均函数对二和四返回三，说明普通样例正确，但没有检查空输入、单元素、非数值和非有限值。先写清契约：空输入明确失败，单元素返回自身，非法元素不被悄悄忽略。再选择每个边界的最小样例。这样每个检查都对应一个独立行为，而不是随意增加许多相似数字。

若平均值错误，观察累计和与计数。错误可能是分母用了全部记录数但分子只累加合法值，也可能计数初始化成一。把输入缩成一个合法值和一个缺失值，往往就能区分。这个例子说明，边界不只是极端数字，还包括不同类别数据的交互。

修复后应保留原失败行为的检查，而不是只保留“现在没有异常”。若错误原来是缺失被当成零，检查应该明确合法样本数与均值口径；如果只断言结果是浮点数，错误实现仍会通过。回归检查应解释被保护的契约。

<a id="sec-2"></a>
## 2. 验证行为而非复制实现

测试需要独立判据，也称预期行为来源。手算小例子、数学不变式、可信独立实现或外部规范都可以提供判据。把实现中的同一公式原样写到测试里，再比较两者，可能只是复制同一个错误。独立性不是绝对隔离，而是尽量避免两边共享同一处未经验证的假设。

正常结果、异常类型与状态变化都属于可观察行为。测试一个不修改输入的函数，既要比较返回值，也要检查输入；测试失败后保留旧模型，就要先拟合成功，再触发失败并比较状态。只验证“抛了某个异常”，可能漏掉异常之前已经污染对象的事实。

一个好测试通常有清楚准备、动作和检查。准备建立最小且有含义的数据，动作只执行需要验证的行为，检查指出具体承诺。把十几个不相关步骤放在一个巨型测试里，失败后难以知道哪项契约破坏；把每个内部赋值都单独测试，又会把实现锁死。边界应围绕行为而不是语句。

下面用标准库测试框架验证非空均值的三个行为。测试方法使用框架断言，而不是把主程序里的输入验证当作测试；运行结果对象可供自动化判断。示例只是展示组织方式，后续完整项目会同时检查更丰富的状态和输入分类。

```python
import io
import unittest

def mean_nonempty(values):
    if not values:
        raise ValueError("empty input")
    return sum(values) / len(values)

class MeanTests(unittest.TestCase):
    def test_hand_computed(self):
        self.assertEqual(mean_nonempty([2, 4]), 3)

    def test_single_value(self):
        self.assertEqual(mean_nonempty([7]), 7)

    def test_empty_rejected(self):
        with self.assertRaises(ValueError):
            mean_nonempty([])

suite = unittest.defaultTestLoader.loadTestsFromTestCase(MeanTests)
result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
assert result.wasSuccessful()
assert result.testsRun == 3
```

测试中的断言失败表示预期行为没有满足；程序中的运行时验证则面对外部输入。普通 assert 可能在优化运行模式被移除，因此不适合作为必须一直生效的用户输入检查。测试框架的断言方法与语言 assert 也不能混淆，前者是明确方法调用。选择工具时应知道每一层在什么时候执行。

<a id="sec-2-1"></a>
### 机制展开：测试需要独立于实现的判据

以排序为例，只检查结果有序不够，因为返回空列表也有序；只检查长度不变不够，因为可以把所有元素替换成同一个值。应共同检查有序、多重集合保留和具体小样例。不同性质覆盖不同错误，组合起来才接近任务要求。测试设计就是寻找错误实现仍能通过哪些薄弱条件。

对分组总额，只检查各组加起来等于总额，也可能漏掉组标签互换；还需要手算每组结果。对预测损失，只检查非负，返回常数零也能通过；还需要已知预测与标签。性质强但不是万能，具体答案与通用关系互补，避免任何一类检查独自承担全部证明。

<a id="deep-dive-2"></a>
### 深入讲解：从示例断言上升到性质检查

示例覆盖你事先想到的输入，性质约束覆盖一类关系。稳定去重重复执行应不改变结果；聚合把数据分块后按正确规则合并应与全量相同；概率输出应非负且和为一。每条性质都需要前提，不能看到名字熟悉就套用。比如去重保留最后记录与保留第一记录，对追加重复项的响应不同。

性质检查可以穷举小域，也可以随机生成结构。小域穷举能系统覆盖短序列与边界组合，随机生成适合更大空间但可能漏掉罕见结构。不能用一个普通均匀随机分布替代所有边界，因为重复键、空组和极端值未必经常出现。生成策略应服务于错误模型。

当性质失败，保留具体反例与生成条件，而不只是种子。种子在相同生成算法下有助复现，但代码或库改变后生成序列可能变化；直接保存最小输入更稳定。可以尝试删除元素、缩小数字或减少字段，逐步得到仍失败的样例。自动缩小也必须保持输入合法性，否则可能制造与原契约无关的失败。

<a id="sec-3"></a>
## 3. 综合项目步骤

本章项目是一个订单汇总器：输入包含订单编号、分组与整数金额，验证后按订单编号去重，汇总各组总额，输出有效记录、排除原因和统计。金额使用最小货币单位整数，避免把浮点表示误差混入最初的业务验证。这里只讨论非负订单金额，退款需要另外扩展契约。

先定义重复策略。本项目保留每个订单编号的第一条合法记录；非法记录不占用编号，所以后来合法记录仍可接收。重复合法记录归为单独排除原因。这个细节必须写清楚，否则先把所有编号加入已见集合，会让一条坏记录阻断后来正确记录，形成隐蔽数据损失。

接着把纯计算与文件边界分开。汇总函数接收内存记录，不自己寻找 CSV，也不决定结果目录；入口负责读取、调用和发布。这样可以先用四五条手工记录验证业务，再用临时文件做集成。若纯计算正确但文件结果错误，就集中检查解析与字段转换，不必怀疑整个系统。

验收不只看总金额。输入位置应被有效与排除集合完整覆盖，分组结果应匹配手算，输入不应被修改，返回数据的可变独立性应符合约定。空输入与全非法输入的结果也要说明。每个输出字段都是承诺的一部分，不能只挑最容易通过的一项。

最后补运行证据：有效配置、输入身份、处理计数、退出状态和最终产物。第三章已经讨论发布与恢复，第五章把这些行为变成故障场景验证。项目规模保持小，但要能解释失败后的状态，而不是只演示成功时打印一个表格。

<a id="sec-4"></a>
## 4. 如何挑选有意义的检查

从风险出发选择检查，比从代码行数出发更有效。订单汇总的主要风险包括重复导致多算、合法零被过滤、非法编号占用去重键、分组错置和输入被修改。每项风险都可以用很小样例暴露。若只是反复用十个不同正金额测试总和，数量很多，却没有覆盖这些关键分支。

边界值应围绕规则变化点。例如金额必须非负，负一、零和一比随机取十几个大正数更有针对性；组别限定 A、B，就需要合法两组与未知组；订单编号去除空白后不能为空，就需要空字符串、纯空白和带两端空白的正常编号。边界不是随便找极大数，而是寻找行为切换的位置。

交互条件常比单字段更难。非法记录与后续同编号合法记录，重复记录分组冲突，缺字段与非法金额同时出现，都能检验检查顺序。测试不必穷举无限组合，但应有意识覆盖会影响状态的交互。若某项策略不确定，先修订需求，不能让测试随机选择一个实现行为作为标准。

检查错误信息时关注稳定语义，不必锁定每个标点与内部函数名。异常类型、字段名和记录位置通常有用；完整堆栈文本可能随重构变化。若用户界面明确承诺固定错误码，则应严格检查该码。测试对外契约，而不是对所有偶然输出逐字快照。

大数据成功运行可以提供性能与集成证据，却不一定提供强正确性证据。十万条记录没有报错，仍可能每组都多算一次；一个三条记录手算样例反而能直接证明该情况的总额。合理证据组合是小样例解释、性质扩展、接口集成与代表规模性能，不是让某一类取代全部。

<a id="sec-5"></a>
## 5. 进阶：基于性质的验证与变形测试

变形测试利用输入变化与输出变化之间的关系。例如不带去重的金额总和，复制全部数据后应翻倍；本项目带按订单去重，复制同样合法订单后总额应不变。两个性质都合理，但对应不同任务。若不先看契约，就把“重复后翻倍”套到去重聚合，会迫使正确实现变成错误实现。

共同置换预测与标签，不改变按样本平均的独立损失，因为保留了配对且加法顺序在精确算术下无关；只置换标签则通常改变结果。时间序列处理、保留首条重复以及有状态在线算法，可能对顺序敏感。应把允许变换的条件写在性质旁边，避免读者误以为一切数据程序都应排列不变。

分块等价也是有条件的。纯总和可以分别计算后相加；均值需要同时传计数；本项目去重需要跨块合并已见键与保留策略。若各块独立去重再直接相加，跨块重复会多算。性质检查能暴露合并状态不足，也能指导你设计正确的中间表示。

<a id="sec-5-1"></a>
### 用性质检查补充具体答案检查

一个系统的性质集合应避免明显漏洞。去重结果没有重复，但可能漏项；输入输出总额相同，但可能把组别弄错；计数守恒，但可能一条重复与另一条遗漏抵消。可以组合成员覆盖、身份唯一、分组手算和位置对账，使不同检查相互补充。没有任何单条短断言能替代认真定义行为。

性质还能用于测试测试本身。故意构造一个总返回空列表的坏实现，看看你的检查能否拒绝；再构造一个只把 A、B 互换的坏实现，检查手算分组是否发现。这样的思路称为变异测试的基本直觉：如果显然错误的程序仍通过，说明验收判据可能太弱。后文会具体讨论哪些变异有意义。

<a id="sec-6"></a>
## 6. 练习与逐步解析

**练习一：两小时训练前怎样检查新指标？** 构造少量答案已知的预测与标签，覆盖完美预测、明显错误、单样本、空输入和长度不等，再接入短训练。解析重点是把指标公式与训练效果分开。一次长训练准确率合理，不证明新指标正确；局部指标通过，也不证明整个训练数据没有泄漏。

**练习二：为什么固定种子仍失败？** 可能存在独立随机源、不同调用顺序、外部数据变化或并行归约差异。先保存具体失败输入与状态，再判断问题是随机生成还是数值比较。不要不断换种子直到通过，也不要把所有随机测试都改成宽泛容差。随机性应当成为可解释依赖。

**练习三：测试为何不应依赖运行顺序？** 如果一个测试留下共享全局缓存，下一个测试可能只在前者先运行时通过。每个测试应准备自己需要的状态，并清理自己创建的资源；必要共享应明确且只读。把测试顺序随机化有时能暴露污染，但根本修复是边界清晰，而不是固定一个幸运顺序。

<a id="sec-7-2"></a>
### 边界追问：测试通过是否说明任意重排都合法

不能。排列不变性取决于任务。保留第一条同编号记录时，重排可能改变保留对象；时间预测中顺序包含信息；浮点归约顺序可能改变末位。正确性质应限定为不改变业务语义的变换，数值比较也要按需要使用容差。错误测试通过再多，也只是把错误前提反复确认。

如果希望某个程序与顺序无关，应先设计相应规则，例如按明确时间戳选择最新记录，并规定并列冲突，再验证排列关系。不能直接要求当前“保留第一条”实现排列不变。测试是检查契约的工具，不是凭空改变契约的命令。

<a id="sec-7"></a>
## 7. 进阶研究练习与解析

有随机性且可恢复的程序需要多层证据。纯变换用手算小例子，随机源用状态或明确种子复现，恢复用提交位置与输入版本，最终结果用记录覆盖与汇总核对。只固定种子不能恢复已经消费的迭代器位置；只保存位置不能复现被其他代码推进的随机状态。

一个可操作练习是先处理前半批，保存必要状态，再继续；另一路从同一初始状态完整处理，比较结果与记录集合。中断点应覆盖提交前后，不只在循环自然结束处停。若浮点求和顺序不同，允许合理容差，但记录身份与计数仍应严格一致，不能把语义错误藏进数值容差。

<a id="sec-7-1"></a>
### 综合练习：验证数据变换是否有副作用

要求返回嵌套成绩表的有效记录，调用不改输入，独立修改结果的内层字段也不污染原表。验收分两步：调用后比较输入原值，再修改返回记录的内部标签列表并检查原表。仅复制最外层列表通常只能满足第一步的一部分，不能保证第二步。测试必须实际触发那条共享修改路径。

如果项目有意使用共享只读记录，应改变契约并解释使用方式，而不是强制所有场景深复制。比较两种设计的时间、内存与误用风险，可以形成有价值研究练习。关键是让实现、接口和测试三者一致，不能测试要求完全独立，文档却说可能共享，代码又无声混用。

## 8. 完整案例：整数金额汇总与独立验收

现在实现项目核心。每条记录必须是字典，包含非空字符串订单编号、合法分组和非负内置整数金额。编号去除两端空白后用于去重；非法记录不占用编号。输出记录是新字典，字段只有不可变标量，因此独立修改结果字段不会修改输入。返回排除列表保存原始位置和原因，保证输入可对账。

示例将正常、重复、非法和边界放在同一个手算样本里。第一条 A 组金额一百，第二条同编号重复不计，第三条 B 组零金额合法，第四条负金额不合法但不占编号，第五条相同编号的合法金额二百五十仍被接收。因此 A 组一百，B 组二百五十，总额三百五十，三条有效、两条排除。

```python
from copy import deepcopy

def summarize_orders(records):
    seen = set()
    accepted, rejected = [], []
    totals = {"A": 0, "B": 0}
    for position, row in enumerate(records):
        reason = None
        order_id = None
        if not isinstance(row, dict):
            reason = "not_record"
        elif not {"order_id", "group", "amount"} <= row.keys():
            reason = "missing_field"
        elif not isinstance(row["order_id"], str) or not row["order_id"].strip():
            reason = "invalid_id"
        elif row["group"] not in ("A", "B"):
            reason = "invalid_group"
        elif type(row["amount"]) is not int or row["amount"] < 0:
            reason = "invalid_amount"
        else:
            order_id = row["order_id"].strip()
            if order_id in seen:
                reason = "duplicate"
        if reason is not None:
            rejected.append({"position": position, "reason": reason})
            continue
        seen.add(order_id)
        item = {
            "position": position, "order_id": order_id,
            "group": row["group"], "amount": row["amount"],
        }
        accepted.append(item)
        totals[item["group"]] += item["amount"]
    return {"accepted": accepted, "rejected": rejected, "totals": totals}

records = [
    {"order_id": " one ", "group": "A", "amount": 100},
    {"order_id": "one", "group": "B", "amount": 999},
    {"order_id": "two", "group": "B", "amount": 0},
    {"order_id": "three", "group": "B", "amount": -1},
    {"order_id": "three", "group": "B", "amount": 250},
]
original = deepcopy(records)
result = summarize_orders(records)
assert result["totals"] == {"A": 100, "B": 250}
assert [row["order_id"] for row in result["accepted"]] == ["one", "two", "three"]
assert [row["reason"] for row in result["rejected"]] == ["duplicate", "invalid_amount"]
positions = [row["position"] for row in result["accepted"] + result["rejected"]]
assert sorted(positions) == list(range(len(records)))
assert records == original
result["accepted"][0]["amount"] = 7
assert records == original
assert summarize_orders([]) == {
    "accepted": [], "rejected": [], "totals": {"A": 0, "B": 0},
}
```

结果记录后来被修改，汇总不会自动重算，这也是接口边界。输出是一次计算的快照，不是联动电子表格。若调用者修改 accepted 金额后还继续使用旧 totals，就会自己制造内部不一致。可以把结果转成只读结构，或明确视为不可变使用，或者提供重新汇总接口；不要假设返回新对象就保证之后所有使用都正确。

接下来设计独立验收。手算总额不调用 summarize_orders 内部逻辑；位置覆盖检查不重新按同一条件筛选，而是检查输出位置分割；输入不变与结果独立检查直接触发修改。三类证据来自不同关系，降低共同复制同一错误的风险。它们仍不构成对所有输入的形式化证明，但比只断言结果字典存在强得多。

如果业务允许同订单不同分组冲突，本例保留首条合法并把后者归为重复。另一种合理策略是冲突时报错或隔离全部相关记录，但那会改变算法状态需求，可能需要先收集全部记录再判断。测试应该让这种政策明确，而不是用一个模糊 duplicate 名称遮住业务选择。

## 9. 系统调试：假设、观测与最小反例

当项目给出错误汇总，不要从所有可能原因同时开始。先确认输入身份与有效配置，再定位最早偏离预期的阶段。原始记录数正确、清洗后数量错误，优先检查过滤；数量正确但组额错误，检查分组键与金额；纯计算正确但文件输出错误，检查序列化与发布。阶段摘要像一组路标，帮助缩小搜索空间。

每个调试假设应该能被某项观测反驳。例如“重复订单被多算”可以检查 accepted 中编号唯一性；“零金额被当缺失”可以用只有零金额的一条记录；“非法记录占用了编号”可以用坏记录加同编号好记录。比起打印整个大型结果，这些最小样例更能直接判断。若观测不支持假设，就更新判断，而不是继续围绕原猜测修补。

断点可以放在状态首次变错之前，逐步执行一个最小样例。观察分支条件、当前值与累加器，不必每次进入标准库内部。条件断点适合只在特定编号或计数异常时停，事后调试适合检查异常现场。交互调试会暂停程序，可能改变并发时序，因此并发问题还需要日志、事件追踪与受控调度等其他证据。

二分定位适用于有序阶段或已知版本历史。若某个处理中间状态可保存，可以比较前半流程是否仍正常，再缩到后半；若是代码回归，可在明确通过与失败版本之间定位变化。二分依赖判据稳定，若测试本身随机失败或输入持续变化，结论会被噪声干扰。先建立可靠复现条件，再使用加速定位工具。

删减反例时需要保护语义。一个函数只承诺非空输入，删到空列表后报错不再代表原问题；一个时间序列模型要求按时间排序，任意重排后失败也可能是非法输入。缩小过程应该持续检查前提，而不是只追求更短。最小反例是对某个性质的最小合法反例，不是任意让程序崩溃的最短对象。

调试也应注意观察者效应。日志格式化可能调用对象的动态表示方法，属性检查可能触发计算，遍历生成器会推进状态，打印 GPU 张量可能引入同步。普通 Python 例子规模小，但这种意识在训练框架中很重要。先选择轻量、明确的观测，再判断是否需要更深入工具，避免调试行为掩盖原始性能或顺序问题。

修复验证需要两部分：原反例现在满足契约，周边正常与边界行为没有破坏。不要只把异常捕获扩大，让原反例“不再报错”，却返回空结果；也不要为通过一个样例而写特殊编号分支。根因修复应能由一般规则解释，再用相关性质检查支持。回归测试记录的是这个一般承诺在具体关键输入上的表现。

记录根因时，用“什么条件触发、哪里违反了契约、改动怎样恢复”三项说明，比描述每次尝试更有用。例如“非法首条记录提前占用去重键，导致后续合法记录被排除；改为验证成功后登记编号”。这个解释让未来维护者明白检查顺序为何重要，避免重构时把错误重新引入。

还要识别需求不明确造成的所谓错误。一个实现保留首条，另一个保留最后条，如果需求从未规定，单靠代码调试不能决定哪种正确。应先澄清业务口径，再调整实现与测试。程序缺陷、数据缺陷和规格缺口常同时出现，成熟调试会分清它们，而不是把所有问题都归到某一行代码。

## 10. 浮点、随机与时间：避免脆弱测试

浮点结果比较应根据任务误差尺度选择绝对与相对容差。接近零时，仅靠相对误差可能无法接受合理微小差异；数值很大时，仅用极小绝对误差又可能过严。容差要来自数值分析或应用需求，而不是在测试失败后不断放宽到通过。一个错误倍数通常远大于舍入误差，不能用宽容差掩盖。

对整数计数、编号与布尔分类，通常应严格比较。把所有断言都改成近似，会让真实漏项和重复逃过检查。数组比较还要检查形状与轴语义，广播可能让不同形状在数值比较中产生误导。标量近似相等不能代替结构正确，也不能证明元素配对正确。

随机程序至少有两类测试。回归测试固定独立随机源或输入，检查某个稳定行为；统计测试重复试验，检查分布或估计性质。前者便于定位，后者接近随机算法承诺。固定一个种子不是统计正确性的证明，而让每次随机运行都必须产生某个精确比例也不合理，因为真实随机波动本来存在。

如果要测试随机采样，先检查确定性结构：输出范围、长度、是否允许重复、相同初始状态能否重现。再决定是否需要统计检验。统计检验要考虑误报概率、样本量和多次执行，不能随便设一个很窄区间，导致持续集成偶发失败。高代价随机算法的统计评估可以作为单独实验，不必每次小改动都运行。

下面不检查某个具体随机数，而验证状态保存与恢复。它使用独立随机源，不受模块全局随机调用干扰。恢复同一状态后得到相同后续序列，是这里的精确契约；这不意味着所有版本的所有随机接口都承诺完全相同序列，也不验证均匀性。

```python
import random

generator = random.Random(2026)
prefix = [generator.random() for _ in range(3)]
state = generator.getstate()
continuation = [generator.random() for _ in range(5)]
generator.setstate(state)
restored = [generator.random() for _ in range(5)]
assert continuation == restored
assert all(0.0 <= value < 1.0 for value in prefix + restored)
other = random.Random(2026)
assert [other.random() for _ in range(3)] == prefix
```

时间也是外部依赖。测试若断言某个函数必须在极小固定毫秒内完成，可能因机器负载失败；如果函数逻辑依赖当前日期，过几天同样测试也可能变。可以把时钟作为依赖传入，用固定时间验证逻辑，把性能基准放在受控环境独立测量。功能正确与性能预算应分别报告，不能互相替代。

超时测试需要验证行为而不是精确经过多少微秒。可以用可控等待对象模拟达到期限，检查取消、清理和状态，而非真的等待很久。若必须验证真实并发接口，使用合理余量并记录环境，避免把调度抖动当产品错误。测试越接近外部系统，越要说明证据范围。

数值稳定性测试可以使用多个尺度与对照公式。对于方差，常数数据应为零，整体平移理论上不改变方差，整体缩放使方差按平方改变；但极端浮点输入的容差要与表示误差对应。先在温和数值上确认代数关系，再研究极端尺度失效。不要把一项数学性质无条件强加给已丢失精度的机器输入。

随机失败发生后，保留种子、具体输入、库版本和失败条件。不要简单重跑直到绿色，因为这删除了证据而没有修复问题。若确认是测试过度敏感，应调整统计设计并说明依据；若是实现状态污染，应修复隔离。偶发性意味着需要更多解释，不意味着错误可以忽略。

## 11. 故障注入、恢复与隔离外部依赖

正常路径测试无法验证失败后的状态。故障注入是在可控位置制造明确失败，观察程序是否保留契约。可以让读取器在第三条记录抛异常，让序列化拒绝非法对象，让发布前一步失败，或让外部调用返回规定错误。故障应围绕真实风险选择，不需要模拟所有想象中的灾难。

依赖替身让故障可重复。一个记录调用次数并在指定调用失败的读取器，比真实等待网络断开更适合局部测试。替身必须符合真实接口的基本约定，不能因为写得方便就返回现实中不可能的结构。少量真实集成验证仍有必要，否则上层可能只适配了自己造的假对象。

文件测试使用临时目录，每个测试拥有独立路径，结束后清理自己创建的资源。不要在真实数据目录测试删除或覆盖，也不要假设当前目录为空。临时目录并非万无一失，程序若错误地忽略传入路径仍可能写到别处，因此入口路径参数与受控工作目录也值得检查。测试环境隔离与实现边界共同降低风险。

下面演示一个提交函数的失败行为：先完成序列化，再写临时文件，允许在替换之前注入故障。测试检查旧正式文件不变、临时文件清理和正常发布。这不是断电模拟，也不证明任意文件系统持久性，只验证本地逻辑的关键状态转移。

```python
import json
import os
from pathlib import Path
from tempfile import NamedTemporaryFile, TemporaryDirectory

def commit_json(path, value, *, before_replace=None):
    path = Path(path)
    text = json.dumps(value, allow_nan=False, sort_keys=True)
    pending = None
    try:
        with NamedTemporaryFile(
            mode="w", encoding="utf-8", dir=path.parent,
            prefix="pending-", delete=False,
        ) as handle:
            pending = Path(handle.name)
            handle.write(text)
        if before_replace is not None:
            before_replace()
        os.replace(pending, path)
        pending = None
    finally:
        if pending is not None:
            pending.unlink(missing_ok=True)

def fail_before_replace():
    raise RuntimeError("injected failure")

with TemporaryDirectory() as temporary:
    root = Path(temporary)
    path = root / "result.json"
    path.write_text('{"version": 1}', encoding="utf-8")
    old = path.read_bytes()
    try:
        commit_json(path, {"version": 2}, before_replace=fail_before_replace)
    except RuntimeError:
        pass
    else:
        raise AssertionError("injected failure should propagate")
    assert path.read_bytes() == old
    assert sorted(item.name for item in root.iterdir()) == ["result.json"]
    commit_json(path, {"version": 2})
    assert json.loads(path.read_text(encoding="utf-8")) == {"version": 2}
```

代码中的故障钩子是教学依赖点，不意味着正式接口必须对所有内部语句暴露钩子。也可以把存储操作封装为可注入协作者。选择应看测试是否需要控制某个稳定边界，而不是为了覆盖率把每行都参数化。测试可观察行为，内部实现仍应保有重构空间。

恢复测试需要比较记录集合与提交状态，不只是最终数值。一次完整运行与一次中断恢复运行应处理同一输入版本，使用同一规则，最终没有遗漏或重复。若随机状态参与处理，还应保存并恢复；若重新分批改变浮点归约顺序，可以按明确容差比较，但身份与计数仍严格核对。

失败后是否允许保留部分产物，应由协议决定。有些批处理允许已提交批次继续有效，有些任务要求整组结果一致发布。测试要确认读取者不会把未提交半成品当正式结果。只检查写入者报错，而不检查读取者随后看到什么，可能漏掉最重要的数据污染路径。

清理同样可能失败。测试可以模拟删除权限问题，检查主要错误是否仍可定位，并记录清理残留。不要为了让测试永远干净就宽泛吞掉所有异常，也不要递归删除未知目录。资源属于谁、哪些路径可清理，应该在实现与测试中共同保持清晰。

## 12. 覆盖率、变异与测试有效性

代码覆盖率描述测试执行到了哪些位置，不等于这些位置被正确检查。一个函数每行都执行，测试却只断言返回值不是空值，许多错误仍会通过。分支覆盖比行覆盖更关注条件路径，但也无法证明输入组合与数值边界完整。覆盖率适合发现明显没碰到的区域，不适合作为正确性的单一分数。

高覆盖率也可能由无意义测试获得。例如调用每个函数一次，不检查结果；或者把所有异常都捕获后仍判成功。这样的测试消耗执行时间，却不能帮助审查。应该问每个检查能拒绝什么错误实现，以及失败时能告诉你什么。少量有独立判据的测试，通常比大量“能跑一下”的测试更有价值。

变异测试的思想是有意制造小型错误，观察测试能否发现。把大于等于改成大于，可能暴露边界遗漏；把计数初始化一，可能暴露空输入；删除去重步骤，可能暴露重复处理。变异不是要求随机破坏所有代码，而是把常见错误假设转成具体挑战。若显然有害变异仍通过，应补强判据。

不是每个变异都代表真实语义变化。有些改动在当前输入域完全等价，无法也无需被测试区分；有些改动只影响内部实现，不属于公开契约。分析变异结果时应人工判断，不能机械追求百分之百拒绝。目标是发现薄弱验收，不是把实现每个字符都锁住。

下面穷举长度零到四、元素取零一二的短序列，验证稳定去重。独立参考使用字典保序机制，实际实现使用列表加集合；再加入一个总返回空列表的坏实现，说明“无重复”这条性质单独不足。小域穷举不证明所有长度正确，却系统覆盖了空输入、重复与多种顺序。

```python
from itertools import product

def stable_unique(values):
    seen, result = set(), []
    for value in values:
        if value not in seen:
            seen.add(value)
            result.append(value)
    return result

checked = 0
for size in range(5):
    for values in product(range(3), repeat=size):
        expected = list(dict.fromkeys(values))
        actual = stable_unique(values)
        assert actual == expected
        assert stable_unique(actual) == actual
        assert set(actual) == set(values)
        checked += 1
assert checked == 121

def broken_unique(values):
    return []

bad = broken_unique([1, 2, 1])
assert len(bad) == len(set(bad))
assert set(bad) != {1, 2}
```

最后两行展示一个坏实现满足“结果无重复”，却不满足成员覆盖。即使把无重复性质随机检查一百万次，空实现也全部通过。因此增加测试次数不能修复错误判据，先检查性质集合是否足够强。类似地，概率总和为一不能证明类别轴正确，均值有限不能证明分母正确。

测试成本也需要管理。局部纯函数检查通常快，真实网络与长训练慢且不稳定。可以把快速契约检查作为日常反馈，集成与性能实验按适合频率运行。不要每次修改一处文档都执行两小时训练，也不要因为训练昂贵就完全不验证新指标。选择最便宜但能覆盖当前风险的证据。

测试结果的可读性也是质量的一部分。断言失败时若只显示一个真假值，维护者仍要重新构造现场；可以在框架消息中附输入标识、实际值与期待性质。信息应精简到足够解释，不必打印全部数据。特别是自动生成用例，保留最小反例比只输出第几轮失败更方便长期复现。

测试维护失败有时是契约变化，有时只是过度耦合内部。重构算法后输出不变，但测试因为私有函数调用次数变了而失败，应判断调用次数是否真的属于约定。如果它代表避免重复网络收费，可能有价值；若只是实现细节，就应改为结果与必要副作用检查。测试本身也需要设计审查。

另一个检验有效性的办法是区分覆盖输入和覆盖结论。一个样例可以同时经过合法分支与重复分支，但若只断言有效数量，没有检查保留的是哪条记录，保留末条的错误实现也许通过。把结果字段逐项对应到契约，能发现“执行到了但没有观察”的空洞。对于本章项目，编号列表、分组金额、排除原因、原始位置和输入状态分别保护不同语义，不是冗余地把同一数再比较五遍。

参考实现也需要审查。若用另一个库作为答案来源，应确认它的默认去重、缺失与排序规则一致；否则差异可能来自任务定义，而非实现错误。对于复杂模型，用高精度或慢速实现作为小规模对照很有价值，但仍应保留手算特殊情形，防止两套代码共享轴方向或分母假设。独立性是逐步增强的证据，不是一贴上“参考”标签就自动成立。

测试失败还应有分类流程：首先确认测试输入符合契约，其次确认预期关系成立，再检查实现，最后排除环境与测试污染。这个顺序不是让开发者优先怀疑测试，而是防止为了变绿而盲目改任何一边。若需求本身改变，应同时更新说明、实现与检查，并留下变化理由；若只是内部重构，外部预期通常不应变化。清楚分类能减少把真实回归误当作测试过时的风险。

代码审查与测试互补。审查可以发现测试未覆盖的假设、危险路径和规格缺口，测试可以实际执行验证并防止回归。不能因为“有测试”就不读逻辑，也不能因为“看起来没问题”就跳过关键运行证据。对数值研究，公式推导、手算、自动验证与实验结果共同提供可信度。

<a id="sec-13"></a>
## 13. 可复现交付与分层验收

交付应让接手者知道怎样从明确输入得到结果，而不是只收到一张截图。最低限度包括运行入口、依赖要求、有效配置、数据身份和结果说明。学习项目可以保持文件少，但不能删去解释结果所必需的信息。整理时可清除失去用途的临时日志与过时草稿；训练入口、正式配置与数据版本若参与结果重建，则应随项目归档。

验收可以分四层。局部层检查函数公式、状态和边界；接口层检查读取与计算之间的字段和形状；流程层检查退出状态、发布、失败与恢复；任务层检查评估协议与效果是否合理。每层有不同判据，不能用高准确率证明文件解析正确，也不能用单元测试通过证明不存在数据泄漏。

端到端小例子应有独立预期。对于本章汇总器，准备已知总额与去重结果的小文件，按真正入口运行，检查最终 JSON、有效配置和退出状态。再给缺列文件，要求失败且不产生误导成功标记。这个测试不需要真实大数据，却覆盖多个边界的配合。代表规模运行再补性能和内存证据。

测试隔离还包括进程环境。一个测试临时设置环境变量或改变工作目录，若结束时未恢复，后续测试可能读取不同配置或写到错误位置。应优先通过显式参数消除这种依赖；必须修改时，用有界上下文保存旧值并恢复。恢复也要区分原本不存在的变量与原本为空的变量，不能统一写回空字符串。

并行运行测试会放大共享路径问题。两个用例都使用固定 result.json，即使单独执行都通过，也可能互相覆盖或抢先删除。每个用例拥有独立临时目录，能同时提供隔离与清理边界；需要验证并发写入时，则有意共享目标并明确冲突契约，不能把意外竞争当成随机噪声忽略。

最后检查测试是否真的执行。发现规则、文件命名或入口配置错误，可能让测试工具报告零个用例却仍退出成功。持续验证应核对预期测试集合，至少关注异常的数量变化与跳过原因。绿色状态只有在相关检查实际被运行时才有意义，不能只看最后一个成功退出码。

测试数据应该固定且可说明来源。手工构造数据便于解释，真实数据抽样便于接近实际，但可能包含敏感信息或不可公开内容。可以保存经过合适处理的最小反例，明确变更是否保留故障性质。不要为了复现一个解析错误，把整份不必要的私人数据复制进项目。

复现记录要区分代码提交、运行配置和环境。只写“最新版”不可追溯；只保存随机种子也不充分。若无法固定某个外部服务版本，应说明这一限制，并保存必要响应身份。结果比较时，先核对这些事实，再讨论模型方法差异，避免把数据变动误解成算法改进。

持续验证可以按风险分级。修改纯指标函数，运行其小样例、性质与相关集成；修改文件发布逻辑，运行失败注入和旧结果保留；修改配置覆盖，运行来源真值表；修改训练算法，运行数学检查与短实验，再按需要进行正式评估。验证范围应与改动相称，不必每次无差别执行全部昂贵任务。

对外说明应诚实报告实际做过什么。代码能编译不等于执行过，执行一个局部块不等于完整项目训练成功；使用模拟数据不等于真实部署验证。把证据范围说清楚，反而更方便他人继续验证。不要把教材示例的运行结果包装成某种科学结论或生产保证。

整理实验目录时，先区分源代码、配置、数据引用、正式结果与临时材料。根据引用关系列出清理候选，确认路径位于项目范围内，再执行受控清理；不要按扩展名全盘删除，因为 Python 文件可能是训练入口，日志也可能是定位数值故障的唯一记录。自动清理的临时目录适合短期演示，正式项目则应预先规定归档与恢复策略。

验收完成也应记录未覆盖范围。例如只在 Windows 与 Python 某版本执行，未验证所有系统；数值例子只覆盖温和规模，极端条件另有讨论；故障注入验证逻辑中断，未模拟真实断电。范围清楚不是降低标准，而是避免接手者误用证据。下一步验证可以据此针对真正风险，而不是重复已知检查。

<a id="sec-14"></a>
## 14. 综合研究路线与参考资料

**研究任务一：为汇总器建立错误模型。** 至少写出六个可能错误：把零金额丢掉、重复订单多算、非法首条占编号、组别互换、输入被原地改写、坏记录被悄悄转换成零。对每个错误设计最小输入和独立预期，说明为什么普通正金额总和样例发现不了。然后故意实现其中两种变异，确认测试能够拒绝。

进一步比较测试集的冗余。有些样例都只验证普通求和，可以合并；一个特别小的交互样例却可能保护关键状态顺序，应保留。测试优化不是机械减少数量，而是让每项检查有明确风险目标。说明删除某个检查后，哪种错误会重新逃过，能帮助判断其价值。

**研究任务二：逐步缩小失败。** 从一个包含多条记录的错误结果开始，每次尝试删除一条输入，若仍违反同一性质就保留删除。直到再删任一条都不失败，得到局部最小反例。解析中区分局部最小与全局最短，说明缩小顺序可能影响结果。还应保持业务前提，不能缩到非法输入后换成另一种错误。

给最终反例写逐步状态表，记录已见编号、当前分类和组额。找出第一次与手工契约不一致的位置。修复后保留这一具体例子，再用性质检查周边输入。这个流程把自动探索与人工解释结合，比只保存一个随机种子更容易长期维护。

**研究任务三：证明合法变形。** 为三种任务分别选择关系：普通总和、保留首条去重、时间序列预测。说明复制、重排和分块各是否保持结果，以及需要哪些前提。对普通总和，复制翻倍；对去重，复制整份合法数据不改变已保留集合；对时间序列，任意重排通常不合法。每个结论给一个小反例或推理。

然后检查浮点边界。整数金额严格守恒，浮点归约可以允许尺度合理的末位差异，但不能允许记录丢失。把结构断言与数值断言分开，避免用一项近似比较代替全部语义检查。这个任务帮助你不再把“变形测试”当作一组无条件口号。

**研究任务四：恢复验收。** 在临时目录模拟正常完整运行与中断恢复运行，保存输入身份和提交位置。比较最终记录编号集合、重复数、隔离原因和组额。故意让中断发生在写产物之后、提交状态之前，观察是否重复计入。修复可以使用幂等键、版本清单或明确事务，但必须解释为何不会遗漏与重复。

如果加入随机处理，应保存独立随机源状态；若恢复时重新读取源文件，应确认内容身份一致。仅仅最终总额一样，可能存在两条错误抵消，所以编号覆盖仍严格核对。报告中说明模拟故障与真实系统故障的差别，不把异常注入结果夸大为断电可靠性证明。

**研究任务五：设计最小交付包。** 只保留能解释并重现项目的正式文件，给出一条入口命令、一份小型输入、一份有效配置和结果说明。生成过程中使用的脚本与临时文件可以删除，但被测正式源代码不能误删。让另一人从独立目录运行，观察是否依赖你的工作目录、缓存或未声明包，再依据证据修正。

**进阶追问：测试是否能证明学习系统正确？** 对有限程序与有限域，可以穷举覆盖；对一般算法可以结合形式化推理；对数据驱动系统，还涉及分布假设、标签质量和目标定义。自动测试能发现实现违反契约，却不能单独证明训练数据代表未来部署，也不能保证模型在所有群体与变化下表现稳定。需要把实现验证与统计评估共同纳入研究。

本章最终能力是提出可反驳假设、构造独立判据、保存最小反例、选择与风险相称的检查，并诚实界定证据。后续学习训练框架时，这些方法会用于检查张量形状、梯度、数据切分和恢复状态。高级模型并不会减少基础验证的重要性，反而让清楚的边界与小型独立实验更有价值。
