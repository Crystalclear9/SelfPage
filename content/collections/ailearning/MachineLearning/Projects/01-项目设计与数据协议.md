## 1. 从一个愿望写到一个可以失败的项目

“用机器学习识别故障”还不是可以执行的项目。识别的是已发生的故障还是未来故障，预测发生在哪个时刻，允许观察哪些信息，错误后采取什么行动，都会改变数据结构和模型评价。

一个算法在某张随机划分的表格上取得高分，只说明它在那个实验中完成了一次统计拟合；若项目问题没有锁定，高分可能回答了另一个问题。本章先把问题变成数据和实验协议，下一章才运行分类项目。第三章转向连续目标的损失和报告，第四章运行按设备分组的回归，第五章审查可交付接口。

本主题贯穿一个人工设备场景：每台设备在一次巡检时提供若干传感器读数，系统判断本次记录属于哪一种运行状态，或预测下一次维护所需工时。人工数据使生成机制、独立单位和可用时间可核查，避免把领域含义不明的公开表格当作完整生产证据。分类章还保留内置葡萄酒数据作为接口迁移练习；它不承担设备来源、未来时间或生产收益的证明。

项目的最小定义包括预测对象、输入、输出、作用时点、评价总体和行动规则。以“在巡检完成后的十秒内，根据当时已进入系统的读数，预测这台设备本次的状态类别”为例，输入边界很明确。如果改成“提前七天预测故障”，当天维修结论和未来传感器峰值就不再合法；如果改成“新设备第一次上线”，过去同设备的历史表现也可能不可得。模型名称相同，问题仍然已经改变。

### 1.1 项目问题需要包含可核查的名词

把任务写成一句可以由他人逐项检查的话：在指定来源和时间范围内，对满足纳入规则的巡检记录，利用预测时刻已经可得的字段，估计一个明确目标，按照预先指定的损失与约束，与指定基线比较。这里每一个限定都对应一项数据检查。来源对应表和采样框，时间对应快照，纳入规则对应过滤条件，可得字段对应特征字典，目标对应标签生成程序，约束对应最终验收表。

不要把“提升准确率”直接写成成功标准。若有三个类别且一个占九成，恒预测大类已经可以达到九成准确率。若真实行动要求每台设备每周最多触发一次复检，那么逐行准确率还不是行动层面的收益。项目可以同时规定主要质量指标、关键类别召回下界和计算成本上界，但应明确哪个用于排序、哪个属于不可违反的约束。没有一条方法能从纯统计数据自动推出所有这些偏好。

可证伪问题允许答案为没有证据支持改善。例如：“在未见设备的留出数据上，折内标准化逻辑回归相对训练多数类基线改善宏平均 F1，且任何关键类别的召回没有低于预定要求。”如果结果不满足约束，正确结论是当前流程未通过验收，接着研究原因；不是更换一组测试设备直到出现理想数字。失败标准在训练前就能写出来，才使项目有边界。

<a id="project-1-detail-3"></a>
### 1.2 三层目标：统计量、决策和证据

统计目标回答要估计什么，例如类别条件概率；决策目标回答如何由概率采取行动；证据目标回答本次实验足以支持多大范围的结论。三个层次不能互相代替。模型给出较好的概率排序，不保证在特定阈值下漏检更少；在某批新设备上漏检较少，也不保证换季后依旧如此。报告应沿着三个层次逐步限定，而非从一个宏平均分数跳到“可以投入所有场景”。

假设漏检代价是误报代价的五倍，二分类且概率准确、两类决策无其他成本时，预测正类的条件为 $`5p>1-p`$，即 $`p>\frac{1}{6}`$。这里阈值来自代价和概率语义。若概率未经校准或复检容量固定，这个推导的前提便不满足，需要用开发数据估计相应规则，或者把容量作为排序截断约束。规则的选择本身也是学习流程的一部分，必须有独立的信息来源。

更深一层，评价样本需要与希望作用的对象一致。随机抽一条记录得到的风险、随机抽一台设备再抽一条记录得到的风险、以及按真实流量加权的风险，通常是三个不同参数。决定要估计哪个参数，比把同一模型的正则强度再细调十倍更影响结论。下面先把这些单位拆开。

<a id="visual-projects-01"></a>
### 图解：实体隔离：单一字段与关联图

![实体隔离：单一字段与关联图](images/01-concept.svg)

四条预测记录分别是 $`r_1=(A,X)`$、$`r_2=(A,Y)`$、$`r_3=(B,Y)`$、$`r_4=(C,Z)`$，括号内为设备与现场身份。左图用关联矩阵逐行列出记录涉及的实体，右图把同一关系画成二部图。每条边代表一条记录，线的长短和角度没有时间或距离含义。若把设备 A 放入训练，设备 B、C 放入测试，设备编号确实不相交；但现场 Y 同时连接训练记录 $`r_2`$ 和测试记录 $`r_3`$，若现场环境或采集格式可被模型识别，这份评价仍未隔离现场。

若目标要求测试设备与现场均未见过，应把所有共享任一被隔离实体的记录视为相连。记录 $`r_1`$ 与 $`r_2`$ 因设备 A 相连，$`r_2`$ 与 $`r_3`$ 因现场 Y 相连；传递性迫使前三条留在同一个集合。右图因此以蓝色表示 $`\{r_1,r_2,r_3\}`$ 所在分量，以橙色表示 $`\{r_4\}`$ 所在分量，再按完整分量分配角色。左图前三行并非任意两行都直接共享实体：第一行与第三行就没有共同的一列；它们仍因第二行形成的路径而不能拆开。只检查每行的复合身份是否重复，会漏掉这种传递约束。单纯将设备号和现场号拼成复合键并不解决问题：四个设备—现场组合都不同，复合键分组仍可把有关联的边拆开。

这里有一个可证明的最小性结论：任何满足“共享实体绝不跨集合”的划分，都必须把同一条关联路径上的记录放在一起；反复沿边应用这个条件，每个连通分量便不可再拆。反过来，按完整连通分量划分，就不会有图中已定义的共享实体跨集合。这个保证只覆盖已建模的身份关系，不会自动排除未记录的来源、时间依赖或近重复。

本例只有两个连通分量，因此不能再声称从这四条数据中得到训练、验证、测试三个非空且同时满足两种实体隔离的角色。若真实数据形成一个巨大分量，正确行动是调整目标、补采独立来源或明确保留的迁移限制；反复换随机种子不能制造不存在的独立结构。[scikit-learn 的交叉验证说明](https://scikit-learn.org/stable/modules/cross_validation.html#cross-validation-iterators-for-grouped-data)强调分组需对应样本依赖，本图进一步把多种交叉实体落实为一组明确的图约束。特征发生与可见时间则由后面的[历史信息时间图](#visual-insight-projects-01)单独说明，实体隔离不能替代时间合法性。

## 2. 预测单位、采样单位和决策单位

预测单位是一条输入对应什么输出，采样单位是随机进入评价的基本对象，决策单位是动作实际作用于谁。设备可能每天产生一百条窗口记录，但每天只允许一次维修建议。若把窗口都当作独立样本，记录多的设备会获得更大权重；若按设备分组留出，评价的是未见设备，而非同设备下一条窗口。协议应该把三个单位并排写下，不能只记录总行数。

设设备 $`g`$ 有 $`n_g`$ 条记录，逐行损失为 $`\ell_{gi}`$。按记录风险的经验估计为 $`\hat R_r=\frac{\sum_g\sum_i\ell_{gi}}{\sum_g n_g}`$，等权设备风险为 $`\hat R_g=G^{-1}\sum_g n_g^{-1}\sum_i\ell_{gi}`$。当每台设备记录数相同，两者相等；记录数不同且难度相关时会有显著差异。这个差异不是指标实现出错，而是抽样分布改变。若目标是设备公平覆盖，不能只报告流量加权平均。

例如设备甲有九十条记录、平均损失为一，设备乙有十条、平均损失为九。按行平均为一点八，等权设备平均为五。若部署面对设备数量均衡的新客户，后者可能更贴近目标；若按实际记录消耗资源，前者可能更贴近负荷。两项都可以报告，但主结论必须对应预先定义的总体。用一个模糊的“平均误差”掩盖权重，会使后续模型比较失去共同尺度。

<a id="project-1-detail-5"></a>
### 2.1 实体关联不止一个分组字段

同一设备的多个窗口显然相关，但同一批次、同一现场、同一采集软件版本也可能共享误差。只按设备分组，不代表完全隔离了现场信息。若要检验新现场，训练和测试必须在现场层面隔离；若同一设备跨现场，则分组关系形成图，简单挑一个字段可能仍存在连接。可以把共享实体视作图中的边，再以连通分量作为不能拆开的最小组，但这样可能得到一个巨大的组，暴露数据本身不足以支持目标评价。

重复记录也是关联的一种。完全相同的内容跨训练和测试，可能让模型记住模板或来源指纹。去重应基于可解释的键和业务语义，不能仅因为两行数值一样就认定它们是误采样；两台不同设备可能恰好拥有相同读数。保留原始记录标识、采集事件标识和内容指纹，分别用于唯一性检查、事件级去重和近重复诊断，能避免把三个问题混成一次`drop_duplicates`。

<a id="project-1-detail-6"></a>
### 2.2 重复采样为何减少独立信息

对同一设备的 $`m`$ 条等方差损失，若任意两条的相关系数近似为 $`\rho`$，组均值的方差为 $`\frac{\sigma^2[1+(m-1)\rho]}{m}`$。推导来自方差展开：共有 $`m`$ 个方差项与 $`m(m-1)`$ 个协方差项，再除以 $`m^2`$。当 $`\rho=0`$，恢复独立平均；当 $`\rho`$ 接近一，增加记录几乎不增加信息。常见的设计效应 $`1+(m-1)\rho`$ 是在这个简化条件下得到的近似，不能机械套到任意不等组和异方差数据。

这个推导解释了为什么“十万行”可能只代表几十个独立来源。增加每台设备的采样频率，未必能回答未见设备的泛化问题。数据计划应同时记录设备数、每组行数分布、来源数量、观察跨度和有效标签数。统计推断、交叉验证以及重采样通常都应尊重这些依赖，而非在最后的报告里补一句“样本可能相关”。

## 3. 时间协议：发生、可见、预测和成熟

一条事件至少可能拥有发生时间和进入系统的可见时间。发生于昨天的维修记录，若今天午后才上传，就不能被今天上午的历史预测使用。另有预测时刻、目标窗口结束时刻、标签确认时刻和数据提取时刻。它们回答不同问题，不能用一个名为`date`的字段替代。协议应明确时间单位、时区、区间端点和迟到处理规则。

对预测时刻 $`t`$，特征合法性的一个基本条件是组成特征的每条记录都满足可见时间不晚于 $`t`$。如果特征定义为过去七天事件数，还需发生时间落在约定窗口，例如 $`[t-7\text{天},t)`$。同一事件有多个修订版本时，应先在可见信息中挑选当时最新版本，再检查修订后的发生时间和删除状态；先按旧发生时间过滤，可能错误地恢复一个已被更正的版本。数据库主题给出了这种版本查询的可运行实现，这里把它纳入项目合同。

<a id="project-1-detail-8"></a>
### 3.1 成熟标签与右删失

预测未来七天是否故障，并不意味着七天后标签一定可用。若故障还需两天人工确认，则在训练截止时刻 $`T`$，只有目标窗口结束且确认完成的样本才可作为完整标签。简单写成 $`t+7\text{天}+2\text{天}\le T`$ 只适用于确认延迟固定的教学情形；真实系统需要实际可见时间、延迟分布及修订政策。把尚未观察到故障的样本标成零，会把未成熟与无故障混淆。

更棘手的是设备退出观察。样本未来七天内没有故障记录，可能是确实没有故障，也可能是第二天设备断联。若任务坚持完整七天二分类，需要明确最小跟踪要求和排除规则；若希望利用不完整随访，则需要相应的删失建模和额外假设。不能在普通分类代码中悄悄把所有缺失未来都当负类，再声称预测了完整窗口。

标签本身也可能修订。维修工单最初标为故障，事后改为传感器误报。训练历史模型时使用哪一版，评估当前事实时使用哪一版，是两个可以不同但必须声明的目标。可复现的训练快照应记录其提取时刻与版本选择规则，不能只留下一个最终标签列。否则三个月后重跑同一代码，改变的可能不是算法，而是过去被覆盖的事实。

<a id="project-1-detail-9"></a>
### 3.2 时间隔离和实体隔离组合起来看

若部署在已见设备的未来，可以使用过去同设备记录，时间划分比设备完全隔离更贴近目标。若部署在未来的新设备，既要隔离实体又要隔离时间。若设备在切分边界附近拥有重叠目标窗口，还要审查训练标签是否引用了验证期内的事件。清除重叠或设置间隔是一种信息边界设计，间隔长度应来自观察与目标生成范围，不能仅凭经验加一个任意天数。

随机分层划分适合近似同分布、样本独立且类别足够的情形；分组划分检验组外迁移；时间前推检验未来部署。没有一种划分天然最严格或普遍最好，因为它们估计不同的风险。错误做法是为了分数好看而在三种协议中挑一个；正确做法是从部署问题推出协议，然后接受由此带来的更大不确定性或更低分数。

### 3.3 实验一：可见时间、成熟标签和排除原因

下面不用外部文件，直接构造四个预测样本。合法特征必须同时满足过去窗口和可见时间；标签只有在截止日前完整成熟才进入训练。断言验证迟到记录未泄漏、边界事件未误计、成熟数量可对账。代码是一份最小逻辑证据，不声称模拟了全部生产延迟。

```python
from collections import Counter

samples = [
    {"id": "a", "t": 10, "follow_end": 17},
    {"id": "b", "t": 12, "follow_end": 19},
    {"id": "c", "t": 15, "follow_end": 22},
    {"id": "d", "t": 18, "follow_end": 20},
]
events = [(7, 8), (9, 13), (10, 10), (14, 14)]
cutoff, horizon, confirmation = 22, 7, 2
accepted, excluded = [], Counter()
for row in samples:
    t = row["t"]
    feature = sum(t - 5 <= happened < t and visible <= t
                  for happened, visible in events)
    if row["follow_end"] < t + horizon:
        excluded["incomplete_followup"] += 1
    elif t + horizon + confirmation > cutoff:
        excluded["immature_label"] += 1
    else:
        accepted.append((row["id"], feature))
assert accepted == [("a", 1), ("b", 2)]
assert excluded == {"immature_label": 1, "incomplete_followup": 1}
assert len(accepted) + sum(excluded.values()) == len(samples)
print(accepted, dict(excluded))
```

在时刻十，发生于九但到十三才上传的事件不可用；发生于十的事件因历史窗口右开也不可用。时刻十二的窗口从七开始，发生于七和十且已经可见的两条记录均计入，所以样本乙的特征数为二。样本丙虽然跟踪覆盖完整七天，标签确认却晚于训练截止；样本丁连完整跟踪都没有，排除原因按代码规定的优先顺序计入一次。排除计数总和必须与原始样本数对账，不能因为一个样本同时触发多个条件而重复扣减。

如果在第十五天只拿已确认标签训练或评价，早到阳性会过度代表整批预测对象，哪怕每条已收到标签本身都没有错。统一成熟队列、描述阳性提前确认机制或显式建模到达过程，才能说明评价总体。到达余量也不能保证所有标签最终齐全：若仍有非随机迟报、漏报或更正，需要另报缺失与版本机制。特征合法性和标签成熟性属于两个不同过滤，任何一个都不能替代另一个。

## 4. 评价协议是流程的一部分

评价协议规定哪些数据可以用于拟合、哪些用于比较、哪些用于最终确认。它不仅是一个训练测试比例，还包括划分键、候选范围、主要指标、并列处理、缺失策略、随机性、阈值选择、资源预算和停止规则。改动其中任何一项，都可能改变被评价的系统。第二章会把这些职责落实为不同数据区域和明确的`fit`调用。

开发集允许形成和比较方案，确认集回答冻结后的方案在未参与决策样本上的表现。最终测试只评一次是易于执行的纪律，但关键原则是它不能被用于影响本次所称独立的选择。即使只运行一次测试，若先查看它的标签分布再定主要指标，也已经使用了信息；相反，固定规则生成全部预测后一次性计算多个预定指标，并不会因指标数量大于一而自动破坏独立性。

<a id="sec-2-1"></a>
<a id="project-1-detail-12"></a>
### 4.1 在哪一层选择，就在哪一层隔离

一个项目可分为特征构造、预处理估计、模型参数拟合、超参数选择、概率校准和行动阈值选择。每一层都可能消耗标签或输入分布信息。标准化只使用输入，依旧应在训练折拟合；校准使用标签，需要与基础模型的拟合数据区分或采用合适交叉拟合；阈值依赖代价或验证表现，不能在最终测试上选择后再报告同一测试的最佳结果。

如果搜索的目标是估计完整选择流程的泛化性能，外层验证必须包住内层搜索。外层每一折都要重新执行内层选择，不能先用所有开发标签找出一个参数再声称外层是嵌套评估。固定测试可承担最终外部确认，嵌套开发评价则帮助比较流程和观察不稳定性。二者不是同一张数据表换一个名称。

<a id="project-1-detail-13"></a>
### 4.2 指标、约束和最小有意义差异

指标应来自任务，而非来自某个模型恰好擅长什么。多分类宏平均 F1 将每类等权，适合检查小类，但它是由混淆矩阵非线性得到的统计量，不能把每条记录的 F1 再简单平均。总体准确率可写成逐样本零一损失平均，概率对数损失衡量整个概率分布，二者关注的对象不同。先在模型评估主题掌握定义，再在项目协议中选择主次。

“有统计差异”也不等于值得替换系统。若一个新模型平均少错一条记录，却慢二十倍且维护复杂度增加，项目可能选择保留简单方案。最小有意义差异可按损失单位、每千次决策减少的错误数或可接受成本表达。样本不足以排除这个差异时，结论应是证据尚不足；不能把未显著解释成两者完全等价。等效、非劣和优越问题具有不同的假设方向，需另行设计。

<a id="deep-dive-2"></a>
<a id="project-1-detail-14"></a>
### 4.3 把协议写成别人可以执行的合同

一份简明协议至少应回答：输入记录如何生成，哪类对象进入目标总体，何时输出预测，目标如何成熟，数据如何隔离，哪一步使用哪些标签，如何选择候选，失败怎样记录，最终以什么证据验收。它无需使用复杂格式，但必须消除关键歧义。协议里写“随机划分”时，还需要明确随机对象是行还是组、是否分层、种子与索引保存位置，以及是否先按时间排除过某些记录。

建议同时保留自然语言说明与机器可检查字段。自然语言表达业务含义，结构化字段表达可执行的约束，如目标窗口长度、分组列名、类别顺序、主要评分、候选数和预算。二者应相互校验：文档说按设备隔离而程序传入行号，属于协议实现错误；程序确实隔离设备但报告声称未来时间泛化，则属于证据解释错误。两种错误都不会被单一高分自动发现。

协议不是永远不能修改。数据审查可能发现标签定义不可实施，早期试验可能暴露计算预算不足。合理做法是给修改分配新版本，说明修改原因、使用过的信息以及需要重新评价的部分。探索期与确认期的边界可以移动，但移动必须可追溯，不能把所有探索历史擦去，只留下最终看起来从未变过的计划。

<a id="project-1-detail-15"></a>
## 5. 数据契约：把一张表拆成可核查的声明

数据字典不只是列名和类型的列表。每一列至少要交代物理或业务含义、单位、生成程序、可见时间、缺失原因、允许范围以及变更方式。温度的一列可能来自传感器即时值，也可能是维修结束后的人工校正值，二者数值类型相同却具有不同预测合法性。字符串设备号可能仅用于分组，也可能被错误地当成可泛化特征。字段的角色应单独标记，而不是让模型自动猜测。

数据类型也有语义层次。整数可能是类别编码、计数、日期偏移或有序等级；浮点缺失可能表示未测量、不适用、设备断联或解析失败。把这些原因全部填零，会把不同过程压成一个数值关系。可以设计缺失指示，但仍需检查该指示在预测时可得且未来生成机制稳定。若缺失由事后人工审查决定，它本身也可能泄漏结果。任何看似技术性的填补都要回到生成机制。

<a id="project-1-detail-16"></a>
### 5.1 主键、外键和连接后的数量守恒

项目常从多张表提取数据。一个预测样本对应多条传感器事件，若直接连接维修表与事件表，可能产生乘法式重复。假设一个样本有三条传感器记录、两条工单，连接后形成六行；直接求和会把传感器金额重复两次、工单金额重复三次。模型能正常训练，损失也能下降，但训练单位已经被悄悄改变。应先确定每张子表的聚合粒度，再连接到唯一预测键。

每一步提取都应报告行数、唯一预测键数、重复键数与标签支持数。过滤缺失标签后减少多少行，按成熟条件排除多少行，连接后是否仍一键一行，这些都是可核查的守恒关系。若预期一个样本一行，就在边界直接断言唯一性；若本来需要一对多表示，则明确如何池化或加权，不能同时把它当成平坦独立样本。数据库主题的连接重数知识在这里直接决定统计对象。

<a id="project-1-detail-17"></a>
### 5.2 缺失、越界和异常的不同处理

缺失是没有值，越界是存在一个不满足契约的值，异常是相对某种分布或规则较少见的值。三者不能统一为“脏数据”。负维护工时可能是单位或录入错误；极高但真实的工时可能是最重要的困难样本；传感器缺失可能具有合法状态含义。清洗规则应先根据来源证据确定，再记录适用范围。按全数据目标值删去最难的百分之一，会直接改变评价总体。

训练集中估计的分位数截断、均值填补、尺度变换和类别词表，都是拟合参数，需要在折内学习。无需数据拟合的固定单位转换可以在划分前执行，但应确保转换规则来自外部契约而非观察最终测试后制定。判断边界的关键不是函数名是否叫`fit`，而是规则是否从被隔离的数据中提取了信息。一个手写的全局均值和一个库对象的`fit`在信息意义上并无区别。

<a id="project-1-detail-18"></a>
### 5.3 实验二：分组隔离与权重确实改变对象

这段代码同时检查分组集合互斥、样本覆盖完整，以及逐行风险与等权组风险的差异。它不依赖任何机器学习模型，因此一旦失败，应先修复数据协议。把这些断言放在训练入口附近，比等到报告时回忆划分逻辑更可靠。

```python
import numpy as np
from sklearn.model_selection import GroupShuffleSplit

groups = np.repeat(np.arange(12), [3, 4, 5, 3, 4, 5, 3, 4, 5, 3, 4, 5])
X = np.arange(len(groups), dtype=float).reshape(-1, 1)
split = GroupShuffleSplit(n_splits=1, test_size=0.25, random_state=23)
train, test = next(split.split(X, groups=groups))
assert set(groups[train]).isdisjoint(groups[test])
assert set(train).isdisjoint(test)
assert sorted(np.r_[train, test].tolist()) == list(range(len(groups)))
loss = np.r_[np.ones(90), np.full(10, 9.0)]
g = np.r_[np.zeros(90, dtype=int), np.ones(10, dtype=int)]
row_risk = loss.mean()
group_risk = np.mean([loss[g == key].mean() for key in np.unique(g)])
assert np.isclose(row_risk, 1.8)
assert np.isclose(group_risk, 5.0)
print("rows:", len(train), len(test), "risks:", row_risk, group_risk)
```

这里分组打散的比例针对组数，实际训练与测试的行数比例不必精确等于四分之三和四分之一。若某台设备拥有一半数据，三台测试设备也可能贡献大多数行。应报告组数与行数两组统计，而不是只验证一个近似比例。若还要求类别支持充足，必须在协议设计时检查组与类别关系；不能在看到最终性能后反复重抽分组以挑选容易的测试集。

## 6. 实验身份：一行结果到底属于哪一个系统

一行结果至少由数据快照、样本键集合、划分映射、特征定义、前处理、模型、超参数、随机状态、选择规则、环境与评价程序共同确定。只记录“随机森林，种子四十二”不足以重建实验。数据行序改变后，即使随机种子相同，索引划分也可能对应不同样本；库版本改变默认值，模型名称相同也可能得到不同流程。身份应该建立在稳定样本键和完整配置上。

适合教学项目的记录可以很精简：一个协议对象、一份带稳定键的内存数据、显式的划分映射、一张候选结果表和一份冻结报告。正式数据无法随资料发布时，要说明可复现到哪一层：是否能重建提取逻辑，是否能核验私有快照标识，是否只能复现人工示例。内容哈希可以检验给定字节是否一致，但不能证明这些字节真实、合法、代表目标总体，也不能证明处理无泄漏。

<a id="project-1-detail-20"></a>
### 6.1 哈希、版本与规范化

同一配置在不同键顺序下不应无意产生不同身份，因此通常先将键排序并使用明确的序列化规则。数据中的时间、浮点、缺失和类别顺序也需要规范化约定。文本哈希对换行和编码敏感；数据结构哈希若忽略行序，则必须另有规则表达训练顺序。不要把“哈希相同”与“所有有意义的执行行为相同”混为一谈。

版本可以分成数据版本、协议版本和实现版本。数据新增一批样本属于数据变化；把主要指标从准确率改为宏 F1 属于协议变化；修复一个特征窗口右端点错误属于实现变化，并可能使旧结论失效。三者分别记录，能回答结果为什么变化。一个统一的任意运行编号方便检索，但无法独自解释变化来源。

<a id="project-1-detail-21"></a>
### 6.2 实验三：规范化身份与单因素变更

以下例子只为明确的纯数据配置构造哈希，不哈希任意 Python 对象。它验证字典键排列不会改变身份，而阈值变化会改变身份。断言还检查候选表中的选择仅依赖开发分数，最终结果不参与排序。真实项目应进一步绑定稳定样本键、数据快照与依赖版本，本例没有假装一个短哈希就能替代全部审计。

```python
import hashlib
import json


def identity(config):
    payload = json.dumps(config, sort_keys=True, ensure_ascii=False,
                         separators=(",", ":"), allow_nan=False)
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()


protocol = {"metric": "f1_macro", "groups": "device", "threshold": 0.5}
reordered = {"threshold": 0.5, "groups": "device", "metric": "f1_macro"}
changed = dict(protocol, threshold=0.4)
assert identity(protocol) == identity(reordered)
assert identity(protocol) != identity(changed)
candidates = [
    {"name": "small", "cv": 0.76, "cost": 1},
    {"name": "large", "cv": 0.75, "cost": 4},
]
best = sorted(candidates, key=lambda row: (-row["cv"], row["cost"], row["name"]))[0]
assert best["name"] == "small"
assert all("test" not in row for row in candidates)
print(identity(protocol)[:12], best["name"])
```

在本例中，成本只作为验证分数完全相等时的并列规则。若想把“相差不足某个有意义幅度时选简单方案”写成选择规则，也可以预先定义，但必须实际编码；不能看见大模型恰好落后后才发明该规则。复杂度、可解释性和运行成本都是合理偏好，问题在于它们是否事先明确并一致执行。

<a id="project-1-detail-22"></a>
### 6.3 随机种子不等于重复证据

固定种子使一个随机过程可重演，却不使结果免于抽样波动。换种子得到不同划分或不同初始化，评估的是不同层面的不稳定性。若固定同一测试集，只重复训练随机森林，观察到的是条件于这批测试对象的训练随机性；若重抽测试设备，又包含评价样本变化。把这两类标准差合成一个数字而不说明来源，会使误差条没有清晰含义。

项目可以预先指定多个训练种子，报告平均表现和最差表现；不能只保留最好种子作为最终模型而仍把搜索视作单次训练。若部署实际只训练一个模型，研究种子波动的目的是理解这种运行风险；若部署会集成多个种子，则集成本身应作为完整候选接受同一协议。训练预算要记录实际尝试数，不能仅记录最后留下来的模型数。

<a id="project-1-detail-23"></a>
### 6.4 数据审查与测试隔离并非互相矛盾

项目开始就需要知道数据能否使用，但又不能根据最终测试的结果选择方案。可以把审查分成预定的完整性检查和会影响建模决策的探索分析。前者如确认文件可读取、键不重复、目标没有缺失、字段满足外部模式，通常属于执行预先规则；后者如观察测试中特定类别与特征的关系，再专门增加交互项，会把测试纳入开发。边界应围绕信息如何改变选择来判断，而非简单规定测试文件绝不能打开。

一种清晰做法是由固定程序在全部数据上执行只读的契约断言，失败时停止，而将模型相关的分布探索限制在开发区域。最终测试的类别支持和分组统计可以在冻结方案后随报告给出。若数据规模太小，无法在不探索测试的情况下判定任务是否可行，就应承认当前阶段是先导研究，目标是建立下一轮协议，不能同时宣称完成独立确认。先导研究本身可以有价值，无须伪装成最终结论。

<a id="project-1-detail-24"></a>
### 6.5 训练快照与评价快照为何可能不同

模拟过去某天训练时，训练快照应只含当时已经成熟并可见的标签；评价后来实际发生的结果时，可以等待更完整的事实确认。这两个快照服务于不同环节。若把后来更正的训练标签送回过去模型，得到的是一种拥有事后知识的反事实训练，不再是当时系统可实现的回放。它可以用于分析数据修订的价值，但名称、信息假设和结论范围应与真实回放区分。

同样，模型上线后的新标签到达会不断改变累计评价。每次报告需要说明评估截止时刻、尚未成熟的样本数和修订政策。若早期容易样本成熟更快，只报告已确认部分可能高估总体质量。项目可以按预测批次等待固定成熟条件，或者对延迟过程进行明确建模；不能把当前已到达标签的样本默认看成原始预测总体的随机子样本。

时间协议因此贯穿提取、训练和报告，而不是只在划分步骤出现一次。还应保留评价样本进入报告的资格原因，例如已完成观察窗口、已确认且没有后续未决修订。若同一批预测的累计分数随时间改变，应先对账新增成熟标签和被修订标签，再分析模型漂移。只有在样本范围、标签版本与统计权重一致时，两次报告之间的差值才可以直接解释为同一目标上的表现变化。

## 7. 基线、假设与对照：从跑分进入研究

基线的价值不只是提供一条低分线，它还帮助检验任务定义和数据处理。多数类分类器解释类别比例，均值或中位数回归器解释损失下的无输入预测，持久性或季节基线解释时间结构，简单线性模型检验可加关系是否已经足够。若复杂模型没有超过强而合法的基线，可能是输入无信息、模型失配、标签噪声太大，也可能是评价单位或提取实现出错。不能仅凭一次失败判断机器学习不适用。

一个可检验假设应该连接机制、改动和预期现象。例如“不同传感器量纲使正则惩罚不均衡，因此折内标准化应提高逻辑回归的稳定性”；这里可比较有无标准化，观察开发指标、参数和收敛状态。再如“来源缺失机制导致某类漏检，加入预测时可见的缺失指示应改善该类召回”；这里需要检查缺失指示合法性，并比较总体与目标子群体的取舍。

<a id="project-1-detail-26"></a>
### 7.1 单因素对照与联合方案

若同时更换特征、模型和搜索预算，最终分数改善只能归于整个方案，不能单独归功于某个组件。消融实验固定其他部分，逐个去除或替换组件，能够提供更局部的证据，但组件存在交互时，独立贡献仍不唯一。标准化与正则化的作用可能互相依赖，去掉标准化后保持同一正则参数并不公平；需要明确比较的是固定参数组件效应，还是允许各方案重新调参后的流程效应。

两种问题都可以研究，但不能混用解释。前者测量一个系统中局部改动的敏感性，后者测量在相同开发预算下各流程的可达到表现。若对复杂方案开放一百次搜索，对简单方案只试默认值，比较结果也包含预算差异。研究报告应把候选数、训练次数和资源条件作为实验的一部分，而非仅在性能表下面写一个模糊的“已调参”。

<a id="project-1-detail-27"></a>
### 7.2 可证伪性需要容许不漂亮的结果

把“改进模型”写成目标容易导致所有结果都被解释为成功。更好的假设带有失败情形：若标准化只减少训练迭代却不改善验证指标，则只能支持计算稳定性的部分；若缺失指示仅改善一个开发分组而损害另一个重要分组，应报告权衡；若复杂模型均值提高但波动显著增加，需要检查部署能否接受这种风险。证据不充分时保留不确定性，是研究结论的一部分。

提前设计一个反例也很有用。若某个设备编号特征在行随机划分中极强，却在未见设备上失效，反例提示它可能记住身份；如果使用打乱标签仍得到高验证分数，优先检查泄漏和重复对象；若所有候选都完美分类，也要检查目标是否直接编码在输入中。反例不会证明一切错误，但可以迅速推翻过强的解释。

<a id="project-1-detail-28"></a>
## 8. 预算、停止和验收如何共同工作

资源预算至少包括训练时间、搜索次数、内存、预测延迟和人工分析成本。延迟需要说明输入批量、预处理是否计入、冷启动还是稳定运行、设备和并发条件。一个模型在一千行批量上的平均每行时间，不能直接当成单条在线请求延迟。教学项目可以只记录粗粒度 CPU 耗时，明确它用于排查异常慢的流程，不承担生产服务承诺。

停止规则可以是完成预先列出的候选、预算达到上限，或开发指标在若干合理尝试后没有实质改善。不要让停止取决于最终测试是否足够好看。模型搜索可以因数值失败停止某个候选，但应保留失败参数、错误类型和处理方式。悄悄删除所有失败候选后只报告成功均值，会低估流程的工程风险。

<a id="project-1-detail-29"></a>
### 8.1 验收从数据完整性到结论范围

验收可分成四层。第一层数据验收检查唯一键、时间合法性、标签成熟、组隔离和排除对账；第二层流程验收检查每个拟合对象的信息来源、候选预算与冻结配置；第三层统计验收检查指标重算、基线一致、支持数和不确定性；第四层交付验收检查输入契约、依赖、固定样例和限制。每层都服务于同一个问题：别人能否确定当前数字究竟来自什么系统。

这不是要求每个学习项目建设庞大的平台。三个简洁、可运行的断言往往比几十行口号有用。对内置小数据，记录样本索引、折内处理和评分已经能解释许多关键问题；对多表时间数据，必须增加版本和可见时间；对设备重复观测，必须增加组隔离。验收深度应与任务结构匹配，而非机械复制另一项目的检查清单。

<a id="project-1-detail-30"></a>
### 8.2 修改协议后的证据恢复

如果最终测试暴露输入单位错误，修复错误是必要的，但修复后的结果不应被叙述为从未参考过测试的新独立证据。可以保留旧测试作为回归检查，再获取新确认数据；也可以明确承认当前报告是探索性重分析，限制结论。无法立即获得新数据时，诚实说明证据边界比将原测试改名更有价值。

若只是修正打印格式而预测完全相同，通常不必重新获得评价样本；若改变特征、标签、阈值或样本纳入规则，则影响统计对象，需要重新审查。判断依据是改变是否能影响被报告的预测、损失或选择，而不是修改文件行数。实验日志应记录变更的具体作用，使复核者不必凭作者的“只是小改动”来判断。

## 9. 十六道练习与逐题解析

<a id="project-1-detail-32"></a>
### 9.1 一台设备有一千条记录，另一台只有十条，如何报告平均质量

**问题：** 项目称面向新设备，但只给全部记录的准确率，是否足够？

**解析：** 不足。逐行平均把记录多的设备赋予更高权重，估计的是抽到一条记录时的表现。面向新设备时，应先确定设备抽样分布，再计算等权设备或目标权重风险，并报告组数和每组支持。若两种风险差异大，应检查采样频率与难度是否相关，而不是选择较高的一个。仍可同时给流量加权结果，用于说明运行负荷下的实际总错误量，但主结论应对应原定总体。

<a id="project-1-detail-33"></a>
### 9.2 数据发生在昨天，为什么今天上午仍不能使用

**问题：** 一个故障事件昨天发生，今天下午上传，上午的历史预测能否使用它？

**解析：** 不能。历史回放必须限制可见时间，事件时间仅决定它是否属于统计窗口。若只按事件时间筛选，回放会拥有当时系统不知道的信息。应保存进入系统或版本可见的时间，先恢复当时可见的事实版本，再计算窗口。若源系统没有可见时间记录，就无法完全重建这种历史合法性，报告要明确限制，不能靠后处理猜出真实到达顺序。

<a id="project-1-detail-34"></a>
### 9.3 七天内没有故障记录，是否等于负标签

**问题：** 设备第二天断联，此后没有故障记录，是否可标记未来七天无故障？

**解析：** 不可直接这样处理。未来观察不完整，缺少记录不能区分未发生与未被观察。若二分类任务要求完整七天标签，应按预定跟踪规则排除并记录数量；若保留不完整样本，需要相应删失建模假设。还应审查退出是否与故障相关，否则只研究完整随访对象也可能改变目标总体。不能把排除写成单纯技术清洗而忽略它的选择含义。

<a id="project-1-detail-35"></a>
### 9.4 固定种子能否修复先后多次挑选测试集

**问题：** 作者试了二十个种子，留下测试分数最高的一次，并记录了种子，结论是否可靠？

**解析：** 该结果可复现，但测试已经参与选择，不能当作一次独立评价。种子记录只保存了获胜路径，没有消除二十次比较产生的乐观性。应记录全部尝试，将这些样本视为开发证据，并使用未参与选择的数据确认；如果无法获取新数据，承认探索性质。不能从“任何人能重现高分”推导出“高分无选择偏差”。

<a id="project-1-detail-36"></a>
### 9.5 基线和候选能否使用不同样本

**问题：** 基线在全测试集上计算，候选因为部分输入缺失而只在剩余样本上计算，可以直接比较吗？

**解析：** 不能。两者差异同时包含模型和样本范围变化。应在共同可评价集合上给配对比较，另行报告覆盖率及被拒绝样本的特征；或者事先定义含回退策略的完整系统，使所有目标样本都有可评价动作。若复杂模型通过拒绝最难样本提高分数，覆盖率必须进入验收，不能只展示条件于成功预测的质量。

<a id="project-1-detail-37"></a>
### 9.6 标准化没有使用标签，为何仍要折内拟合

**问题：** 全表均值只来自输入，是否不会影响独立评价？

**解析：** 全表均值包含验证或测试分布信息，改变了训练变换，违反通常的归纳式评价协议。应在每个训练折估计均值和尺度，再应用到对应验证。某些任务明确允许利用一批未标记目标数据做转导适配，那属于另一种合法但不同的协议，需要从开始就声明，并用一致的部署可用信息评价，不能事后把普通泄漏重命名为适配。

<a id="project-1-detail-38"></a>
### 9.7 两个方案同时改变四个模块，应如何归因

**问题：** 新方案换了特征、填补、模型和搜索范围，分数提高，是否证明新模型结构更好？

**解析：** 只证明整个流程在当前协议下表现不同，不能识别某一个模块的贡献。若要局部归因，需要固定其他部分做消融或因子设计，并明确各方案是否允许重新调参。还要考虑交互作用：某种特征可能只对某种模型有用。报告应区分完整流程优劣与组件机制证据，而不是将所有改善归到最显眼的模型名称上。

<a id="project-1-detail-39"></a>
### 9.8 小类召回下降但宏平均提高，能否通过验收

**问题：** 主要指标提升，某个关键故障类召回从八成降到六成，该如何判断？

**解析：** 先检查协议是否为该类别设定下界或代价约束。若有硬约束，则平均指标改善不能抵消违约；若没有，应报告明确取舍并在下一版本重新界定目标，不能假装所有方面改善。小类支持数少时还要报告原始错例数量与不确定性，避免两个样本的变化被叙述为稳定机制。阈值调整属于新方案，需在开发数据完成。

<a id="project-1-detail-40"></a>
### 9.9 模型效果比基线差，项目是否没有成果

**问题：** 严格分组后复杂模型不如简单基线，应怎样写报告？

**解析：** 这是有效结果，说明当前输入、算法与预算未提供足够证据支持替换。检查流程错误、基线合法性、组间分布和容量后，区分可解释失败与未知原因。可以提出收集更多独立设备、改进合法特征或缩小适用范围等下一步，但不能把未经运行的改进当成果。项目成果也包括确定某种常见做法在当前设定下不能泛化。

<a id="project-1-detail-41"></a>
### 9.10 哈希一致，是否证明数据正确

**问题：** 两次数据哈希相同，是否意味着没有泄漏、标签真实且来源可靠？

**解析：** 不意味着。哈希只在给定规范化规则下检查字节或结构一致；错误数据同样可以稳定地拥有同一个哈希。合法性需要时间与字段来源，真实性需要数据生成证据，代表性需要采样说明。哈希应与这些语义检查配合，而非代替它们。也要记录哈希到底覆盖原始文件、清洗表还是划分映射，避免不同对象共享一个模糊的“数据指纹”。

<a id="project-1-detail-42"></a>
### 9.11 组数比例正确，行数比例为何不正确

**问题：** 留出四分之一设备，却留出了一半记录，是否说明分组器失效？

**解析：** 不一定。设备记录数不等时，组比例与行比例自然不同。检查组集合互斥和覆盖完整，再报告实际行数。若任务还要求总计算量受控，可以设计预定的组抽样方案，但不能为了改善测试表现反复挑组合。若设备数很少，一台大设备会主导风险，应该同时报告组层面的表现和支持，明确估计的不稳定性。

<a id="project-1-detail-43"></a>
### 9.12 以行号保存划分是否足够

**问题：** 作者保存训练行号，数据重排序后直接使用，会发生什么？

**解析：** 行号对应不同实体，原划分身份被破坏，即使种子和行号文件都没变。应使用稳定预测键保存角色映射，并在加载时检查键唯一、覆盖完整、数据快照匹配。行号可以是内存实现细节，但不能独自承担跨版本身份。若新增样本，协议还要说明它们是追加开发、未来确认还是全部重新划分，不能默认为原测试仍保持相同统计意义。

<a id="project-1-detail-44"></a>
### 9.13 新数据标签更正后，旧报告是否必须删除

**问题：** 旧标签发现系统性错误，如何处理历史结果？

**解析：** 保留可追溯的旧版本和更正说明，标记旧结论的适用限制，再在更正数据上重建流程。标签更正可能改变选择结果，不能只重新计算最终测试分数而保持旧的最优参数解释不变。若更正规则来自查看测试错例，也要说明信息使用过程。历史结果不需要被抹去，但不能继续被引用为未受错误影响的证据。

<a id="project-1-detail-45"></a>
### 9.14 什么样的最小差异值得实际替换

**问题：** 候选平均提升千分之一，训练成本增加十倍，应如何决策？

**解析：** 先把差异换成目标总体中的错误数量或损失，再与实际成本和不确定性比较。若差异小于事先定义的有意义幅度，可优先简单方案；如果任务对极少数高代价事件极敏感，则需要看相关约束而非只看平均。数据不够时不能宣称等价，只能说无法可靠区分。选择规则若在看见结果后才制定，应标记为探索决定并寻求后续确认。

<a id="project-1-detail-46"></a>
### 9.15 测试后修复单位错误，还能叫独立结果吗

**问题：** 测试发现温度单位不一致，修正后分数大幅提高，怎样报告？

**解析：** 修复必要且应记录，但原测试已经帮助识别问题并改变系统。可以将修复结果作为透明的重分析或回归检查，再用新确认样本评价；如果没有新样本，应限制独立性声明。还要检查训练与部署的单位契约，防止仅对这批测试写特殊修复。第五章将把单位检查变成输入验收，使同类错误在预测前被发现。

<a id="sec-7-1"></a>
<a id="project-1-detail-47"></a>
### 9.16 先看测试再决定主要指标是否公平

**问题：** 两个候选各有优势，作者挑新模型领先最多的指标作为主要结果，这是否只是报告方式？

**解析：** 这已经让测试参与选择了评价标准。主要指标应来自任务代价和事前协议，其他指标可以完整补充并注明探索性质。若确有理由修改任务目标，应给协议新版本，解释修改使用过哪些信息，再获取相应独立证据。结果表可以展示多项取舍，但不能把事后挑选的优势写成原定成功标准。即使训练过程完全没有接触测试，这种报告选择仍会产生偏差。

<a id="project-1-detail-48"></a>
## 10. 综合研究：把一页协议变成可执行证据链

现在尝试为人工设备分类项目写一页协议。首先声明每台设备的多条巡检相关，目标是未见设备的状态识别，输入是巡检时可见的数值和类别字段，设备号仅用于分组。随后固定一组外部设备作确认，其余设备用于训练、搜索和开发诊断；若需要概率校准与阈值选择，另设合法区域或交叉拟合策略。主要指标为宏平均 F1，辅助指标包括每类召回、混淆矩阵、概率质量与运行成本。

接着列出基线和少量有机制理由的候选，例如训练先验基线、折内填补标准化逻辑回归和一个受限树模型。规定候选预算和并列规则，保存所有失败。最后列出验收：组不相交、预测键唯一、支持数可重算、预处理在正确范围拟合、候选身份冻结、概率列与类别顺序一致、最终表只评价冻结流程。第二章的完整实验会展示怎样实现其中最重要的边界。

研究扩展可以比较行随机划分与设备分组划分，但应把它们明确视作两个不同泛化问题。若行随机分数显著更高，进一步检查设备指纹和组间分布，而不是宣布其中一个协议“错误”。可以再生成具有不同组相关强度的人工数据，观察差距如何变化，并分别报告独立设备数与行数。通过控制生成机制，才能把分数变化与一个具体假设关联起来，而不是把每次高低差都称为数据泄漏。

另一个扩展是固定总记录数，改变设备数与每台设备记录数。预期在组相关较强时，更多独立设备比同设备更密集采样更有助于组外泛化。应重复生成不同数据集，区分生成随机性、划分随机性和训练随机性，给每个层面的汇总。这个实验将本章的单位选择、设计效应和预算分配连在一起，也为以后研究主动采样与数据收集价值打下基础。
