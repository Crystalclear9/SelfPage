## 1. 从任务规格到计算模型

<a id="algo-one-2"></a>

### 1.1 先规定答案，再讨论速度

算法分析的起点不是选择容器，而是明确输入、输出与允许的错误。对一批用户记录做去重，究竟按数据库编号、邮箱还是姓名判定同一用户？是否保留第一条、最后一条，或者合并字段？结果是否维持输入顺序？这些要求改变需要维护的状态，也改变正确性的含义。把姓名放入集合可能运行很快，却会错误合并同名的人；这样的程序不能因为复杂度低就被称为更好的算法。

设输入包含记录序列，程序输出去重序列。可以将规格拆成三个可以检查的性质：输出中的每条记录来自输入；每个业务主键恰好出现一次；保留的代表符合约定的选择规则。若还要求稳定顺序，就需要第四个性质：保留代表之间的相对顺序与输入一致。明确这些性质后，才有资格比较使用列表扫描、哈希集合或排序的方案。复杂度分析回答的是完成同一任务所需的资源，而不是把不同任务的程序并列计时。

再看保留最高分候选。仅返回前十个分数，返回前十个完整对象，以及返回按分数降序排列且并列时按时间升序的前十条记录，是三个不同规格。第一个问题可以只保存数值，第二个需要引用原记录，第三个需要完整的比较规则。分数为非数值、出现空缺、候选不足十个时如何处理，也属于输入契约。边界条件写在任务层，可以避免在容器内部不断补丁式地猜测需求。

<a id="algo-one-3"></a>

### 1.2 输入规模不是永远只有一个字母

对长度为一百万的整数数组，元素个数是自然规模；对字符串集合，总字符数往往比字符串条数更能解释成本。若有十万个文档，每个平均长十个字符，与每个平均长十万个字符，仅用文档数描述复杂度会隐藏主要差异。可以同时记文档数为 $`n`$、总字符数为 $`L`$、不同词数为 $`u`$。于是读取文档至少需要与 $`L`$ 成正比的工作，词频表的条目数量则由 $`u`$ 决定。

机器学习中的数据常是 $`n`$ 个样本、每个 $`d`$ 维。完整读入密集矩阵需要处理 $`nd`$ 个标量。若算法声称线性时间，必须说明是关于样本数线性、特征数线性，还是关于输入编码长度线性。构造全部样本对的距离，输出本身包含约 $`n^2`$ 个数；如果还把每对样本的逐维差保存下来，中间状态可能达到 $`n^2d`$。把这些方案都写成“遍历一次数据”会掩盖完全不同的内存风险。

图输入需要至少区分顶点数 $`V`$ 和边数 $`E`$。稀疏图中两者可能同阶，稠密图的边数却可能接近平方。邻接表遍历的 $`O(V+E)`$ 与邻接矩阵逐行扫描的 $`O(V^2)`$，不能只用顶点数代入一个固定结论。若顶点名字是长字符串，还应考虑构建编号映射与字符串哈希的成本。问题中的数学对象与存储对象不是天然相同的，需要明确映射过程。

<a id="algo-one-4"></a>

### 1.3 单位代价模型与位复杂度

在常见的字长随机访问模型中，可以在常数时间访问一个机器字、比较适当大小的整数并执行基本算术。这是推导数组下标、计数器和指针操作的方便起点。它不是说任何 Python 语句都只花一个单位时间。复制长度为一万的切片、拼接长字符串、比较长元组，都可能执行与对象长度有关的工作。复杂度必须跟着实际操作展开，而不能按源代码行数计数。

任意精度整数尤其值得注意。两个具有 $`b`$ 位的整数相加，至少要处理相应的机器字；乘法的成本则取决于算法及规模。计算第 $`n`$ 个斐波那契数时，如果把大整数加法视为常数，迭代次数是线性的；如果研究精确整数计算的位操作成本，就必须计入数值位数随 $`n`$ 增长的事实。两种分析可以同时正确，但它们回答不同模型中的问题。

字符串键的哈希也不应无条件当作常数。如果一个新字符串尚未计算过哈希，通常需要检查其内容；某些实现会缓存不可变对象的哈希值，使后续对同一对象的哈希较便宜。不能把实现优化误写成“所有长度字符串首次查询都严格常数”。本章在讨论哈希表操作时，若没有特别说明，默认键的哈希与相等比较各自为有界成本；涉及文档时另把字符处理量列出。

<a id="algo-one-5"></a>

### 1.4 从求和式读出增长规律

设第 $`i`$ 轮执行 $`i`$ 次基本工作，总量为 $`1+2+\cdots+n=\frac{n(n+1)}{2}`$。这是平方增长，不是因为“有两层循环”而是因为累积操作量如此。相反，若内层指针在全部外层迭代之间只向前移动，每个元素最多进入和离开一次，即使代码视觉上有两层循环，总工作仍可能是线性的。单调队列与双指针算法经常使用这一结构。

若每次把正整数规模除以二，经过 $`k`$ 步后规模约为 $`\frac{n}{2^k}`$，直到不超过一，因此步数与 $`\log_2 n`$ 同阶。若每次仅减少一，则需要线性步数。把“规模如何变化”写成关系式，能解释二分查找、堆高度和递归深度，也能帮助发现那些看似对数、实际却在每一层复制大数组的实现。递归树的高度只是总成本的一部分，每层的工作还需要相加。

<a id="algo-one-6"></a>

### 1.5 基础算例：累计移动次数解释二次复杂度

动态数组需要维持逻辑元素在连续槽位上的顺序。从头删除一个元素后，后面的引用必须向前移动。长度为四时，连续清空需要移动三次、两次、一次与零次，共六次。推广为 $`\frac{n(n-1)}{2}`$。这一结论与每个元素所指向的对象是否很大没有直接关系，因为移动的通常是引用；但即使只移动引用，平方增长也会使规模扩大后成本迅速上升。

如果任务仅要求依次处理元素，甚至不必真的删除。可以直接遍历原列表，让一个游标向前移动；若需要及时释放已处理对象的引用，游标方案可能仍让原列表持有全部对象，此时就要比较队列、分块读取或清空槽位的选择。时间复杂度改进与内存生命周期是两个相关但不同的问题。不能只把头删改成游标，就自动声称所有资源瓶颈都得到解决。

## 2. 渐近符号与四种成本保证

<a id="algo-one-8"></a>

### 2.1 大 O、紧确界与比较范围

$`T(n)=O(g(n))`$ 表示存在正常数与足够大的规模，使 $`T(n)`$ 不超过常数倍的 $`g(n)`$。它给出上界，未必是最紧上界。线性函数也属于平方的大 O；因此若已经知道上下界一致，更精确的写法是 $`\Theta(n)`$。下界符号 $`\Omega`$ 则表达至少具有某个增长阶。把三个符号分清，才能理解“比较排序的下界”与“某个算法的最坏上界”如何共同说明最优性。

省略常数有助于跨机器研究增长趋势，但不意味着常数不存在。顺序扫描一次连续数组，与遍历同样多的独立 Python 对象，在相同量级下可能具有很不一样的运行时间。对于小规模问题，启动、函数调用、对象分配等固定开销甚至可能主导结果。渐近分析适合排除增长明显不合适的方案，最终实现仍需在实际输入分布上测量。

多参数表达不能随意消去。例如 $`O(n\log k)`$ 在 $`k`$ 固定时可视为关于 $`n`$ 的线性，但若 $`k`$ 也随输入增长，必须保留其影响。算法返回全部有序记录与仅返回一个固定大小候选集，输出要求不同，不能直接声称其中一个“永远更快”。比较时应该列出参数的变化范围，并说明预处理是否在多次查询间复用。

<a id="algo-one-9"></a>

### 2.2 最坏、平均、随机期望与摊还

最坏成本在同一规模的所有合法输入中取最大值，可以给出不依赖输入分布的保证。平均成本则需要为输入规定分布，再对成本求期望。若不说明分布，“平均情况”常常只是经验印象。例如随机排列与几乎有序的排列对排序算法具有不同意义；线上业务中的热门键分布也很少等同于均匀选择键。

随机算法的期望分析可以固定输入，只对算法内部随机选择取期望。随机选取枢轴的快速排序就是典型情形：其期望性质不是假设用户提交随机排列。若输入还会根据已观察到的随机行为自适应改变，需要更明确的对手模型。不要把“内部随机”与“输入随机”合并成一句模糊的平均复杂度。

摊还分析研究一整串操作的总成本，再把总成本分配到各步。它不必依赖概率。动态数组偶尔扩容，虽然一次追加可能搬迁全部旧元素，但从空状态开始的一连串追加总工作可以被线性界住。相同序列在任何输入值上都满足这个界；这与哈希表在一定散列假设下的期望查找成本不同。

这些概念还可以组合。哈希表既可能有扩容导致的摊还成本，又可能因碰撞分布具有期望成本。于是严谨表述可能是“在相应哈希假设下，插入的期望摊还成本为常数”。如果只剩一句“插入常数”，就把两层前提都删掉了。工程上通常可以使用简洁表格，但在理解和设计关键路径时必须恢复被省略的条件。

<a id="algo-one-10"></a>

### 2.3 预处理与查询的收支平衡

设原列表有 $`m`$ 个元素，需要做 $`q`$ 次成员查询。逐次扫描最坏要做 $`qm`$ 次比较；先建立集合再查询，在键成本有界且散列行为合适时，预期总工作约为 $`m+q`$。但是集合需要额外空间，构建过程也不是免费的。当只查询一次、列表很短时，扫描可能更简单且更快。建立索引本质上是用一次投入换取重复访问收益。

还必须考虑数据是否变化。如果集合需要持续跟随原列表更新，维护成本应该加入总账。若列表中的可变对象修改了参与主键的字段，之前构建的外部索引可能不再反映真实状态；若业务允许旧版本快照，则需要明确查询针对哪个版本。复杂度公式没有替你定义一致性，但一致性会决定要执行多少工作。

在训练数据管线中，常见做法是先构建词表、编号映射和偏移索引，再重复多个训练轮次。分析一次训练时，预处理是否已经完成会影响计时解释。论文若把索引构建排除在查询成本之外，应同时报告构建时间、存储量以及预期复用次数，读者才能判断收益在自己的任务规模下是否成立。

<a id="algo-one-11"></a>

### 2.4 机制展开：哈希键的相等语义影响去重

对于遵守哈希协议的对象，相等的键必须具有相同哈希值；具有相同哈希值的键不必相等。因此哈希值不能单独作为可靠身份。字典先根据哈希定位候选位置，再通过适当的相等判断区分碰撞。把哈希输出直接存入集合做“绝对去重”，忽略了碰撞可能，会改变精确去重任务的语义。

可哈希对象还需要在作为键期间维持与哈希、相等相关的稳定行为。若自定义对象的哈希取决于一个后来会修改的字段，它可能仍能写出哈希函数，却不满足安全作为键的使用契约。更稳妥的办法是采用不可变业务编号或明确构造不可变快照。不可变容器也不必然可哈希：元组内部如果包含列表，整体仍不能作为普通字典键。

Python 中某些跨类型数值可能比较相等，例如布尔真值与整数一。因此若数据系统要求区分“布尔标签真”和“整数编号一”，仅凭原始对象作为键可能合并本应不同的实体。可考虑带类型标签的复合键，但也要说明类型规范化政策。数据结构设计中的身份问题，本质上是领域建模问题，不能通过换一个更快的散列函数自动解决。

<a id="algo-one-12"></a>

### 2.5 访问模式、操作数量与状态规模

判断一个方案是否可用，可以按三个轴审查：每种操作执行多少次；每种操作在当前表示上需要多少成本；这些操作过程中有多少状态同时驻留。只看其中一个轴容易产生误判。一次全量复制的次数可能很少，却制造巨大的内存峰值；一个常数时间操作重复数十亿次，也可能成为主要时间开销。

例如为每条样本查询类别权重，若先构造哈希映射，再扫描样本，预期查找次数线性。若每次都重新从类别表构造字典，重复预处理就会乘上样本数。又如循环里不断使用不可变字符串拼接，逻辑上每次只添加一段，底层却可能不断复制已有前缀；应根据实际语言与实现分析，不能把每个加号当作恒定工作。

状态规模也不等于最终输出大小。流式求平均只需要计数和累计值，但如果程序先把全部解析对象放入列表，再计算平均，就承担了不必要的驻留空间。反过来，精确去重通常需要保存已见身份；仅输出一个计数，并不意味着内部状态也能保持常数。输出很小的任务，仍然可能具有不可忽略的信息存储需求。

<a id="algo-one-13"></a>

## 3. 动态数组与摊还证明

<a id="algo-one-14"></a>

### 3.1 长度、容量与操作边界

动态数组在逻辑上保存长度为 $`n`$ 的序列，在物理上分配容量为 $`c`$ 的槽位，满足 $`n\le c`$。尾部追加在空余容量存在时只需写一个引用；容量不足时，要获得更大的存储区并保留原有顺序。实际实现可能原地扩展，也可能重新分配，因此教科书通常采用“扩容时复制现有元素”的保守模型分析。

随机下标访问能够直接计算位置，这是数组的主要优势。中间插入或删除为了保持顺序，一般需要移动后缀。若业务允许打乱顺序，可以用末尾元素覆盖待删除位置，再尾部弹出，改变操作代价；但此时实现的是无序集合式删除，不能拿它替代要求稳定顺序的序列删除。修改规格有时确实带来巨大收益，前提是业务允许并且文档清楚说明。

Python 列表保存对象引用，不等同于连续存放相同数值类型的密集数组。即使引用槽位连续，被引用的整数或用户对象仍可能分散在堆上。复制列表通常复制这一层引用，嵌套可变对象仍共享。内存局部性、数值向量化和对象生命周期，都需要区分容器自身与元素对象。不能从“列表是动态数组”推导出它和密集浮点张量具有相同的布局。

<a id="algo-one-15"></a>

### 3.2 聚合法：几何扩容为什么有效

为便于证明，假设容量从一开始，每次满时翻倍。最终长度为 $`n`$，历史扩容复制量不超过 $`1+2+4+\cdots+2^r`$，其中最后一次复制的规模小于 $`n`$。几何级数的和小于 $`2n`$。加上每次追加本身的一次写入，总工作小于常数倍的 $`n`$，因此前 $`n`$ 次追加的摊还成本为常数。

这不是声称每一步都均匀。容量从一千零二十四变成两千零四十八的那一步，可以复制一千多个引用；紧接着许多追加又很便宜。总量证明适合吞吐量评估，却不能单独提供严格的单请求延迟上界。若系统要求每次请求都在固定时限内完成，需要考虑预分配、分块结构、渐进迁移或其他能够限制单步工作量的设计。

若每次只增加一个槽位，复制量变为 $`1+2+\cdots+(n-1)`$，总成本是平方量级。由此可见，动态数组的摊还性质来自增长策略，不是“数组”这个名字自带的保证。实际 Python 实现采用的过量分配细节与版本有关，本章的翻倍模型只用于证明几何增长的原理，不能当作对 CPython 具体容量序列的承诺。

<a id="algo-one-16"></a>

### 3.3 势能法：把昂贵操作的账提前保存

势能法为状态定义非负数 $`\Phi`$，把第 $`i`$ 次操作的摊还成本定义为实际成本加势能变化，即 $`\widehat c_i=c_i+\Phi_i-\Phi_{i-1}`$。对整串操作求和，中间势能相消，得到实际总成本等于摊还总成本减去最终势能再加初始势能。如果初始势能为零、之后势能非负，实际总成本就不会超过摊还总成本。

在只追加、容量翻倍的模型中，可以对非空数组使用 $`\Phi=2n-c`$，并令空状态势能为零。由于扩容后使用率至少约为一半，该势能在可达非空状态上非负。普通追加花一次写入，势能增加二，所以摊还成本为三。满容量为 $`c`$ 时追加，实际成本是复制 $`c`$ 次加写入一次；扩容前势能为 $`c`$，扩容后长度为 $`c+1`$、容量为 $`2c`$，势能为二，因此摊还成本仍为三。

第一次从空状态创建容量一时，实际成本一、势能变为一，摊还成本二，也满足统一常数上界。证明中的势能不是机器真实存储的钱，而是分析工具。它必须对所有分析覆盖的状态满足条件，不能只在扩容前后挑几个好看的点。若允许删除使使用率很低，原势能可能变为负数，需要更换势能或改变分析范围。

<a id="algo-one-17"></a>

### 3.4 扩缩容抖动与迟滞

若数组一满就翻倍，刚降到半满就立刻减半，会发生什么？先在临界位置插入触发扩容，再删除触发缩容，反复交替就可能每两步都搬迁大量元素。原本希望的常数摊还操作被边界抖动破坏。问题不在单次复制，而在两次昂贵事件之间没有足够多的便宜操作来积累支付成本。

一种常见原则是在不同阈值触发增长与收缩，例如满时翻倍、使用率降至四分之一时容量减半。收缩后大约半满，离下一次增长和下一次收缩都还有线性数量的操作。可以用分段势能正式证明总成本；直觉上，迟滞使昂贵迁移之间隔开足够距离。这种设计思想也出现在缓存淘汰、负载扩展和数值迭代的阈值控制中。

但收缩并非免费且并非总值得。某些实现宁愿保留容量，以避免反复分配，并提高未来增长时的速度。于是峰值过后容器长度明显变小，进程占用却未必立刻下降。逻辑删除、容器释放、分配器把内存归还系统，是不同层次的事件。分析空间复杂度时可以讨论渐近上界，解释实际常驻内存时则需要进一步观察实现和分配行为。

## 4. 哈希表：期望效率建立在什么条件上

<a id="algo-one-19"></a>

### 4.1 散列、碰撞与装载因子

哈希表把键映射到有限位置，碰撞不可避免。链式散列在桶中保存多个条目，开放寻址在表内继续探测空位；两类方案具有不同的缓存行为、删除处理和负载限制。设条目数为 $`n`$、桶或槽位数量为 $`m`$，装载因子为 $`\alpha=\frac{n}{m}`$。讨论期望成本时，必须说明散列假设以及装载因子是否受控。

在简单均匀散列的链式模型中，一个查询需要检查的预期桶长度与 $`\alpha`$ 同阶，所以预期查找工作可以写为 $`O(1+\alpha)`$。如果通过扩容让 $`\alpha`$ 保持常数量级，才得到常见的预期常数结论。开放寻址在表接近填满时探测代价会迅速增加，不能直接把链式模型的公式照搬过去。实现细节不同，具体期望公式也不同。

在最坏情况下，许多不同键可以碰撞到同一位置，查询就可能退化为线性比较。字符串哈希随机化等机制能缓解特定攻击方式，但不能把任意自定义哈希对象的最坏成本变成数学上保证的常数。工程上可以合理依赖标准容器的常见表现，同时仍应知道性能结论在哪些输入下会失效。

<a id="algo-one-20"></a>

### 4.2 删除、墓碑与重建

开放寻址不能简单把删除位置视为空白，因为后面的碰撞键可能沿探测路径越过该位置。若查询遇到这个空白就停止，会错误地认为后面的键不存在。一种处理办法是保留墓碑标记，让查询继续探测，插入则在合适条件下复用。墓碑积累后，即使有效条目不多，探测路径也可能变长，因此需要重建或清理策略。

这说明表的逻辑大小并不能完全描述成本。历史插入删除序列、容量、空槽与墓碑数量都可能影响实际工作。对反复更新的在线特征表，只测量一次性插入后查询的性能，未必能代表长期运行的状态。基准测试需要包含具有代表性的更新模式，而不是只生成一个静态随机字典。

删除语义也可能影响迭代。边遍历字典边改变其大小，通常不是可以随意依赖的操作方式；更稳妥的是收集待删除键后统一处理，或者明确迭代的是快照。快照又会产生额外线性空间。这里没有脱离规格的万能选择，容器操作、迭代协议与资源代价需要一起考虑。

<a id="algo-one-21"></a>

### 4.3 词频、去重与复合索引

词频统计的基本状态是从词到计数的映射。若输入总词数为 $`N`$、不同词数为 $`u`$，在有界键成本和合适散列假设下，处理通常需要期望线性次数的字典操作，状态条目为 $`O(u)`$。如果还要保存每个词的全部出现位置，则空间会增加到与总出现次数有关，不能继续只写不同词数级别。

精确去重可以用已见键集合加输出列表：首次遇到键时加入集合并保留记录，之后忽略。这样既提供成员查询，也保留首次出现的输入顺序。若改成先构造集合再遍历集合输出，就不再得到相同的顺序规格。顺序是算法输出的一部分，而不是读者应自行猜测的附带现象。

复合索引适合具有多个筛选维度的任务，但每个附加索引都要付出存储与维护成本。按用户建字典、用户内部再按日期建字典，可以快速定位某类查询，却可能在纯时间范围扫描时不理想。设计之前应该列出主要查询形态、更新频率、键的基数和结果大小。索引无法让输出一百万条结果变成常数时间，因为写出结果本身已经需要线性工作。

## 5. 栈、队列、链表与堆

<a id="algo-one-23"></a>

### 5.1 抽象操作与具体表示

栈只规定后进先出的访问规则，队列只规定先进先出的访问规则；它们是抽象数据类型，不是某一种唯一内存布局。动态数组尾部可以实现栈，链表也可以实现栈。队列可以由环形数组、分块双端队列或链表实现。分析时先看任务需要哪些操作，再讨论具体表示支持这些操作的成本。

链表经常被描述为插入删除常数时间，这个说法隐含已经拿到合适节点及必要前驱信息。若只有目标值而没有位置，需要先遍历查找，成本可能线性。单链表删除某个节点通常还需要前驱，双链表则为额外链接支付空间。遍历链表还可能缺乏数组式的局部性；在高级语言中每个节点的对象开销可能远大于保存的数值。

如果程序既要求按下标随机访问，又要求频繁在任意中间位置插入，简单数组与简单链表都难以同时满足全部理想成本。可以研究平衡树、跳表或分块序列，但结构更复杂、常数更大、实现负担也更重。学习数据结构不应演变成“越高级越好”，而应该建立一张由操作约束推导表示选择的地图。

<a id="algo-one-24"></a>

### 5.2 双端队列与滑动窗口

双端队列支持从两端加入和移除，适合广度优先搜索、流式缓冲和固定窗口。Python 的`deque`对两端操作提供合适的实现；中间位置随机访问并不是它的优势。若把一个以两端操作见长的结构当成密集数组逐下标读取，可能再次产生线性访问累积。数据结构的强项总是相对于某组操作而言。

固定窗口还涉及过期语义。长度窗口保留最近若干条，时间窗口保留时间阈值内的记录，两者不同。时间戳若乱序到达，仅从队头移除旧记录可能不正确，因为过期元素未必集中在头部；需要排序、缓冲或事件时间水位等额外约定。教科书中的队列窗口通常默认输入顺序与过期顺序一致，移植到日志系统前必须检查这一前提。

维护窗口和时，每条记录入队加上其值，出队减去其值，在单位算术模型下可实现每步常数工作。如果每一步重新求整个队列的和，窗口宽为 $`w`$ 时总量是 $`O(nw)`$。两种代码可能都只有一层显式外循环，区别在于是否维护可更新摘要。数值计算中，长时间加减还可能积累浮点误差，需要根据精度要求考虑周期性重算或稳定求和。

<a id="algo-one-25"></a>

### 5.3 二叉堆的局部有序

最小堆要求每个父节点的键不大于其子节点，因而根是全局最小值；它不要求同一层有序，也不要求整个数组排序。用零开始的数组表示，节点 $`i`$ 的子节点位置为 $`2i+1`$ 与 $`2i+2`$。完全二叉树的高度是对数级，插入上浮与删除根后的下沉最多跨越这一高度，所以单次主要调整工作为对数级。

为什么批量建堆可以线性，而逐个插入的简单上界是 $`n\log n`$？从最后的非叶节点开始下沉时，大多数节点离叶子很近。高度至少为 $`h`$ 的节点数量至多与 $`\frac{n}{2^h}`$ 同阶，因此总代价可由 $`n\sum_{h\ge1}\frac{h}{2^h}`$ 控制，级数收敛，得到线性界。关键是按节点高度累计，不能把每个节点都错误地按最大高度收费。

堆不适合快速搜索任意键。除根的极值性质外，大部分位置之间没有足够顺序信息，查找指定对象通常仍可能线性。若需要频繁更新某条记录的优先级，可以维护位置索引并同步堆交换，也可以使用惰性删除，把旧条目标记过期，新条目重新入堆。后者简化实现但使堆条目数可能超过活跃任务数，必须核算积累和清理。

<a id="algo-one-26"></a>

### 5.4 流式前若干名与并列规则

想保留最大 $`k`$ 条候选，可维护容量至多为 $`k`$ 的最小堆。堆根是当前保留集合中最差的一条；新条目若不优于堆根即可丢弃，优于堆根则替换。归纳证明很直接：处理前缀后，堆保存该前缀按既定全序排列的最大若干条；新条目只可能替代其中最小者，其他条目的相对优劣不变。

最坏情况下每条记录都引起调整，处理 $`n`$ 条的时间为 $`O(n\log(k+1))`$，额外状态为 $`O(k)`$；最终若要求有序输出，还需 $`O(k\log k)`$。这里用 $`k+1`$ 避免 $`k=1`$ 时把表达式误读成零工作。若 $`k=0`$，应直接返回空结果。若 $`k\ge n`$，返回全部候选的有序结果与全排序相近，不能期待截断结构带来显著收益。

并列分数时，应在键中加入确定的次级顺序。例如希望早到记录优先，可以用分数与负到达序号组成键。不要把完整业务对象放在无法比较的并列位置，否则元组比较可能意外尝试比较字典并报错。还应禁止或定义非有限分数，尤其是浮点 NaN（Not a Number）会破坏直观的顺序性质。正确的前若干名算法首先需要一个一致的比较规则。

## 6. 空间、图表示与 AI 数据负载

<a id="algo-one-28"></a>

### 6.1 总空间、辅助空间与峰值

空间复杂度应该说明是否包括输入和输出。就地排序通常讨论额外工作区，而程序的总驻留状态仍包含原数组。返回一个长度为 $`n`$ 的新列表，即使内部计算只用常数几个计数器，也至少需要输出空间。若输出可以逐条交给下游，峰值空间又可能不同，但前提是下游不把所有条目重新收集起来。

峰值尤其容易被隐藏。表达式先构造新副本再替换旧引用时，新旧对象可能同时存在；多进程工作者也可能复制或持有独立缓存。即使最终状态只有一份数据，转换期间也可能出现两份以上。训练管线中，从文本到分词列表、再到数组、再到批张量的多阶段表示，可以让同一信息以多种形式同时驻留。

浅层对象大小不能直接当作完整内存占用。某个列表自身的字节数可能不包含被引用字符串的内容；递归相加又可能对共享对象重复计数。解释内存测量时必须说明测的是容器浅层大小、可达对象估计、分配器追踪，还是进程常驻内存。不同指标反映不同层次，不能把一个数字当作所有内存问题的唯一答案。

<a id="algo-one-29"></a>

### 6.2 邻接表、矩阵与压缩行格式

邻接矩阵为每个顶点对保留位置，判断某条边是否存在可以直接索引，但存储通常需要平方空间。邻接表只保存实际边及必要的顶点条目，稀疏图更节省空间，遍历某个顶点的邻居与其度数相关。如果需要频繁判断任意边是否存在，可以把邻接集合用于成员查询，但集合的对象开销和散列成本也应列入比较。

无向图通常把一条边保存为两个方向，因此邻接项总数约为两倍边数；自环和重边则要根据定义处理。图算法中 $`E`$ 有时指数学边数，有时指实际存储的弧数量，写代码分析时应统一口径。没有边的孤立顶点也应保留，否则由邻接键集合推断顶点集合会遗漏它们，导致连通分量或拓扑处理不完整。

压缩稀疏行格式把邻居连续存放，用偏移数组标记每个顶点邻接段的起止位置。它通常适合静态图的扫描与批量处理，却不适合随意在中间插入边，因为插入可能移动大量后续元素。可更新图与训练期间重复读取的静态图，适合的表示不必相同。预处理一次压缩布局、随后重复扫描多轮，就是用构建成本换局部性与较低表示开销。

<a id="algo-one-30"></a>

### 6.3 特征表、检索候选与批处理

词表映射适合哈希查找，但映射后的稠密编号通常应进入连续数值表示。若每个浮点特征都包在独立 Python 对象和字典里，解释器与对象开销可能主导。另一方面，极稀疏特征若强行展开为完整密集矩阵，也可能浪费绝大多数空间。应以非零项数、维度和访问模式决定稀疏或密集表示，而不是机械地坚持某一种容器。

检索系统经常先从多个来源得到候选，再去重、打分和保留前若干名。去重放在打分前可以减少重复计算，但若重复候选携带不同来源证据，需要先合并而不能任意丢弃。保留前若干名若放在特征计算前，使用的是初级分数而不是最终分数，可能改变召回结果。数据结构可以降低执行代价，流程顺序则决定算法实际优化的目标。

批处理也存在交换。逐条读取的峰值状态小，但函数调用与设备传输可能频繁；批量扩大能摊薄固定成本，却增加驻留内存并可能增加等待延迟。适合训练吞吐的批量不一定适合在线请求。用复杂度比较时，可以引入批大小 $`b`$、每批固定成本与每条计算成本，区分吞吐量、单请求等待和最大内存，而不是只报告一个总耗时。

<a id="sec-6-1"></a>

<a id="algo-one-31"></a>

### 6.4 从单步成本推导完整流程成本

设读取 $`n`$ 条记录，每条含 $`d`$ 个数值，按用户聚合并保留每个用户最高 $`k`$ 条。至少要处理输入的 $`nd`$ 个标量；若用户键哈希成本有界，分组定位具有常见的期望常数成本；堆更新的上界与 $`\log(k+1)`$ 有关。于是核心工作可表达为输入读取成本加 $`O(n\log(k+1))`$ 的候选维护。若最终要为每个用户输出有序列表，还要累计各组结果的排序成本。

空间上，若用户数为 $`u`$，仅保留候选所需条目至多为 $`uk`$，但前提是没有同时把全部原始记录留在另一个列表里。若每条候选仍引用整份巨型原始文档，按“候选数”计算会低估对象保留。可以只存索引或必要字段，延迟读取完整内容，不过这又增加后续随机访问成本。时间与空间之间的交换应该明确列出来。

如果数据天然按用户分组，可以完成一个用户后立即输出并释放状态，状态可能从所有用户的候选降为当前组候选。如果数据无序，则要么保留多个用户的状态，要么先排序或使用外部存储。输入顺序本身就是一种可利用的结构。分析算法时，把“已按键分组”当作额外前提，比在结果中悄悄假定它存在更可靠。

## 7. 可复现实验：数操作而不是迷信一次计时

<a id="algo-one-33"></a>

### 7.1 扩容复制量与头删移动量

下面使用抽象模型统计复制次数，不试图猜测当前 Python 列表的真实容量策略。几何增长和每次加一的增长处理相同数量的追加；实验检查几何策略的累计界，以及线性增长的精确平方求和。它提供对证明的有限验证，也让昂贵单步与低总量同时可见。断言通过不能替代对任意规模的证明，证明也不能代替实际实现的基准测量。

```python
def copies_for_appends(n, geometric):
    size = capacity = copied = worst = 0
    for _ in range(n):
        cost = 1
        if size == capacity:
            copied += size
            cost += size
            capacity = max(1, capacity * 2) if geometric else capacity + 1
        size += 1
        worst = max(worst, cost)
    return copied, worst

for n in range(1, 300):
    geometric, worst = copies_for_appends(n, True)
    linear, _ = copies_for_appends(n, False)
    assert geometric < 2 * n
    assert linear == n * (n - 1) // 2
assert copies_for_appends(257, True)[1] == 257
assert sum(range(50)) == 50 * 49 // 2
print('growth and movement checks passed')
```

容量达到二百五十六时，再追加一个元素会产生复制二百五十六个旧引用的昂贵步骤。此前许多低成本追加让总成本仍然受线性界控制。这个现象清楚说明摊还分析允许单步尖峰。若你只看平均每次移动数量，就会忽略时延；若只盯着最慢一步，又会错过长序列的总效率。

<a id="algo-one-34"></a>

### 7.2 碰撞反例与身份规则

下面构造所有键哈希值相同的对象，但按编号判断相等。该对象故意暴露碰撞影响，不代表通常业务数据。查找一个不存在的键需要排除大量相等哈希候选，而已存在的键仍能正确查到。断言只要求比较次数至少达到条目数量级，不依赖某个 CPython 版本精确的探测次序，因此实验检查的是实质性质。

```python
class CollisionKey:
    comparisons = 0
    def __init__(self, value):
        self.value = value
    def __hash__(self):
        return 0
    def __eq__(self, other):
        type(self).comparisons += 1
        return isinstance(other, CollisionKey) and self.value == other.value

n = 80
table = {CollisionKey(i): i * i for i in range(n)}
assert table[CollisionKey(7)] == 49
CollisionKey.comparisons = 0
assert CollisionKey(-1) not in table
assert CollisionKey.comparisons >= n
assert len({True, 1, 1.0}) == 1
rows = [('same-name', 101), ('same-name', 102)]
assert len({name for name, uid in rows}) == 1
assert len({uid for name, uid in rows}) == 2
print('collision and identity checks passed')
```

最后两个集合分别按姓名与编号去重，结果数量不同，却没有任何一个容器出错。错误只能相对于任务规格讨论。碰撞实验则说明，只要相等判断正确，碰撞主要影响效率而不应改变映射含义。将哈希值直接当身份与让哈希表处理碰撞，是两种截然不同的操作；后者保留精确相等语义，前者未必保留。

<a id="algo-one-35"></a>

### 7.3 稳定前若干名与滑动窗口

以下实验把“分数越高越好，同分越早越好”写成明确的全序键。维护堆后再按同一个键输出，与完整排序的参考结果逐项比较。输入包含大量并列分数、负分和不同候选数量，覆盖最容易被忽略的边界。另一个窗口例子比较增量和与直接求和，验证过期和更新的顺序。全部数据在内存生成，无需下载或创建文件。

```python
from collections import deque
from heapq import heappush, heapreplace
import random

def top_k(records, k):
    if k < 0:
        raise ValueError('negative k')
    if k == 0:
        return []
    heap = []
    for index, score in enumerate(records):
        item = (score, -index)
        if len(heap) < k:
            heappush(heap, item)
        elif item > heap[0]:
            heapreplace(heap, item)
    return [(score, -neg_index) for score, neg_index in sorted(heap, reverse=True)]

rng = random.Random(31)
for n in range(40):
    records = [rng.randrange(-3, 4) for _ in range(n)]
    expected = sorted(((s, i) for i, s in enumerate(records)),
                      key=lambda item: (-item[0], item[1]))
    for k in (0, 1, 5, 50):
        assert top_k(records, k) == expected[:k]

values = [rng.randrange(-10, 11) for _ in range(70)]
window, total, width = deque(), 0, 7
for i, value in enumerate(values):
    window.append(value)
    total += value
    if len(window) > width:
        total -= window.popleft()
    assert total == sum(values[max(0, i - width + 1): i + 1])
print('top-k and window checks passed')
```

参考排序只用于小规模验证，不参与流式堆的正式复杂度。测试中循环多次构造参考结果，是为了交叉检查，不是建议在生产中同时执行两个算法。验证代码与被验证算法应有不同思路：前者用完整排序表达规格，后者用有界堆维护状态，这样比复制同一个实现再比较更容易发现错误。

<a id="algo-one-36"></a>

### 7.4 如何设计有解释力的性能测量

如果要补充计时，应把数据生成、预处理和主体执行分别测量，记录 Python 版本与机器环境，并重复多次。对会修改输入的操作，每次运行需要独立输入；否则第二次可能测到已清空或已排序的数据。对极短操作，计时器分辨率和函数调度开销可能占比很大，需要批量执行并报告分布，而不是拿一个偶然数字证明理论。

比较列表成员查询与集合时，可分别报告构建集合成本、单次查询成本和重复查询总成本，包含命中与不命中两类请求。比较队列时，应在输入规模递增时观察增长趋势，且避免把随机数生成放入计时主体。即便结果与理论一致，也应写成“在该环境和输入下支持预期趋势”，不要把有限测量上升为所有规模的数学证明。

内存实验也应该预先规定指标。若只使用浅层大小，说明它不包含全部引用对象；若使用分配追踪，说明它的覆盖范围；若观察进程常驻内存，考虑分配器缓存、后台工作和垃圾回收。只有把测量对象讲清楚，读者才能复现结论，或者理解为什么自己的机器出现不同数字。

## 8. 进阶练习与完整解析

<a id="algo-one-38"></a>

### 8.1 练习一：建立集合何时有意义

**题目。** 有长度为 $`m`$ 的成员列表，需要对 $`q`$ 条记录判断成员关系。分别给出逐次扫描与先建集合的时间、额外空间及适用条件。如果只查询一次，是否仍应直接选集合？

**解析。** 逐次扫描最坏检查 $`qm`$ 个候选，额外状态可为常数；建立集合在键哈希与比较成本有界、散列行为合适时需要期望 $`O(m)`$，随后查询需要期望 $`O(q)`$，集合条目空间为 $`O(u)`$，其中 $`u`$ 是不同键数。查询一次时，两者都可能需要处理与 $`m`$ 同阶的数据，集合还承担分配和哈希成本，所以不能仅凭查询表中的常数符号决定。

进一步应问列表是否已经排序、查询是否可批量排序、集合是否可以在后续任务复用。如果已有有序数组且内存紧张，二分查询可以避免建立哈希索引。如果成员判断关系不是精确相等，而是某种近似匹配，普通集合并不直接实现规格。选择方法之前，先确认比较语义和预处理的复用范围。

<a id="sec-7-1"></a>

<a id="algo-one-39"></a>

### 8.2 练习二：均摊常数是否排除单次线性开销

**题目。** 动态数组尾部追加均摊常数，为什么某次追加可能明显变慢？若服务要求每次请求都有严格时限，仅靠这一结论是否足够？

**解析。** 容量耗尽时需要搬迁已有引用，个别追加可以与当前长度成正比。几何扩容证明的是一串操作的总成本，不是每一步的独立上界，因此总吞吐较好与单步出现尖峰并不矛盾。严格时限需要更强的单步保证，可以预先分配上限容量，或者采用分块存储、渐进迁移等方案，但这些方案又具有不同的访问与空间代价。

还要区分算法步骤与真实时钟时间。即使基本步骤数量有界，内存分配、操作系统调度、缓存失效和垃圾回收也可能影响时延。教材中的复杂度保证是设计依据，实际实时系统仍需在所采用的执行环境中分析更具体的资源和调度条件。

<a id="algo-one-40"></a>

### 8.3 练习三：改变扩容增长率

**题目。** 理想模型中容量每次乘以固定 $`r>1`$，忽略取整，证明追加复制总量为线性。若 $`r`$ 非常接近一，渐近结论为何仍不足以保证快？

**解析。** 历次复制量构成几何级数，若最后一次复制规模小于 $`n`$，其和至多是常数倍 $`\frac{n}{(1-\frac{1}{r})}`$。对固定 $`r`$，系数有限，所以总量线性。但 $`r`$ 趋近一时系数增大，扩容更频繁，复制总量和分配次数都可能显著增加。渐近符号允许依赖固定设计参数的常数，因此没有暴露这项工程交换。

较大的增长率通常减少搬迁次数，却可能保留较多未使用容量。具体选择还受到分配器、内存上限和预期增长模式影响。若增长率本身随输入变化，不能继续把它当成固定常数消去，需要重新分析。整数取整与最小容量也应在实际实现中处理，否则很小容量乘以略大于一后取整可能根本不增长。

<a id="algo-one-41"></a>

### 8.4 练习四：双栈队列的势能

**题目。** 一个栈接收新元素，另一个栈负责弹出。仅当输出栈为空时，把输入栈全部倒入输出栈。证明从空队列开始的一串入队出队操作总成本线性。

**解析。** 每个元素最多被压入输入栈一次，从输入栈弹出并压入输出栈一次，最后从输出栈弹出一次。用每个栈操作单位成本计，总工作不超过每个入队元素四次栈操作，加上常数次状态检查，因此线性。一次出队可能搬迁很多元素，但不能对同一个元素反复支付同样的搬迁费用。

也可以令势能为输入栈元素数的两倍。入队实际成本一、势能增加二，摊还成本三。若搬迁 $`k`$ 个再出队，实际成本 $`2k+1`$，势能下降 $`2k`$，摊还成本一。证明依赖输出栈非空时不随意重新搬迁；改变这一策略就可能破坏“每元素只迁移一次”的关键性质。

<a id="algo-one-42"></a>

### 8.5 练习五：为什么不能只存哈希值

**题目。** 为节省内存，程序将每篇文档的有限长度哈希值存入集合，看到相同哈希就丢弃。它是否仍是严格精确去重？如何表达更合理的任务说明？

**解析。** 有限哈希空间不可能对任意多的不同文档保持一一对应，碰撞会使不同文档被错误合并，所以不能无条件称为精确去重。若要求精确，需要在哈希相同的候选中进一步验证内容或使用能唯一标识业务对象的可靠编号。哈希可以减少候选比较范围，却不能自行创造唯一性。

如果接受极小碰撞概率，应明确这是带概率风险的指纹去重，并说明哈希选择、输入规模和风险假设。安全哈希、普通散列和业务主键具有不同目的，不应混称。某些场景的错误丢弃代价很高，单纯报告平均节省空间不足以说明方案适用。

<a id="algo-one-43"></a>

### 8.6 练习六：精确计数与状态下界

**题目。** 数据流只要求输出不同用户数量，输出是一个整数。能否因此断定存在常数内存的单遍精确算法，且对任意大的用户域都成立？

**解析。** 不能。输出尺寸小，不代表中间需要区分的历史状态少。对来自有限用户域的精确不同计数，已经见过哪些用户会影响未来某个用户是否增加计数。不同的已见集合可能需要被算法区分，否则构造一个后续元素就能让两个历史产生不同正确答案，而算法状态却相同，形成矛盾。

若用户域大小固定，可以用位图，空间与域大小有关；若域巨大且稀疏，可以用集合，空间与不同用户数及键表示有关；若允许近似，可以研究概率草图，但需要误差与失败概率说明。近似算法改变了答案规格，不应拿它的低空间直接反驳精确任务的存储需求。

<a id="algo-one-44"></a>

### 8.7 练习七：堆为什么没有全部排序

**题目。** 最小堆的根最小，是否能直接按堆数组顺序输出升序结果？如果不行，怎样获得有序结果，成本如何？

**解析。** 堆只要求父节点不大于其子节点，左右子树之间以及同层节点之间不必有序。因此判断一个数组是否为堆，需要检查每条父子关系，不能凭树形图想象整层排序。合法堆`[1, 4, 2, 7, 5, 3]`的数组序列显然不是升序。因此直接输出内部表示不满足全排序规格。

可以重复弹出根，获得有序序列，总代价通常为 $`O(n\log n)`$，但会破坏原堆；也可以对副本使用排序，付出副本空间与排序成本。如果只需要最小的一个元素，则根已经足够，强行全排序是在解决更强问题。结构中的局部顺序保证应与任务需要的全局顺序分开。

<a id="algo-one-45"></a>

### 8.8 练习八：前若干名的并列与稳定性

**题目。** 两个候选分数相同，但业务要求先到者优先。为什么仅用分数入堆不够？为何使用到达序号时要注意符号？

**解析。** 容量受限时，堆需要确定谁是当前最差候选。若同分没有次级比较规则，就可能任意淘汰早到者。对保留最大键的最小堆，应该让更优者拥有更大的键；分数相同时，较小序号更优，所以第二关键字使用负序号。这样晚到者键更小，更可能位于被替换的边界。

最终输出也必须使用同一规则，否则保留集合虽然正确，呈现顺序仍可能不满足规格。若只把序号加入最终排序，却没有在维护堆时使用，已经错误淘汰的候选无法恢复。这体现了在线剪枝必须遵守最终比较标准，而不是等到输出阶段才补充规则。

<a id="algo-one-46"></a>

### 8.9 练习九：图密度改变表示选择

**题目。** 一个图有百万顶点、数百万条边；另一个图只有数千顶点，但几乎每对顶点都有边。解释邻接表与邻接矩阵的时间空间交换，不要求给出某台机器的精确字节数。

**解析。** 第一个图相对稀疏，平方矩阵位置数量极大，而邻接表与实际边数同阶，通常更适合扫描邻居与遍历。第二个图本来就有平方数量级边，邻接表的边条目并不能在量级上节省多少，矩阵可能提供更紧凑的规则布局和直接查边能力。实际字节数还取决于元素编码、对象开销与是否使用位图。

如果主要操作是列出某个低度顶点的邻居，邻接表可以只访问存在的边；矩阵往往需要扫描整行。若主要操作是反复判断任意顶点对是否相连，矩阵具有直接索引优势。图是否变化、能否预先编号、是否保留重边，也会影响选择，不能仅用“稀疏用表、稠密用矩阵”一句口号结束设计。

<a id="algo-one-47"></a>

### 8.10 练习十：视图、浅复制与峰值

**题目。** 一份包含嵌套可变记录的列表做浅复制后，是否已经拥有完全独立的数据？为何新副本建立时的峰值内存不能只按最终列表大小估计？

**解析。** 浅复制通常创建新的外层引用序列，内部记录仍被共享；修改共享记录的字段会被两边观察到，而替换某个外层位置则不必影响另一边。是否需要深复制应由独立性需求决定，不能为了消除共享就无条件复制所有内容，尤其是在大型训练数据上。

建立副本的过程中旧外层与新外层会同时存在，共享元素或新建元素也有各自生命周期。后续再转为数组、序列化或传给工作进程，可能出现额外缓冲区。峰值需要按同时存活的对象计算，最终变量只指向一份数据并不说明转换过程只用了一份内存。

<a id="algo-one-48"></a>

### 8.11 练习十一：滑动窗口的输入前提

**题目。** 用双端队列保存最近十分钟事件，每次从队头删除过期事件。若到达顺序与事件时间不同，为什么算法可能保留已经过期的记录？

**解析。** 仅检查队头隐含队列按事件时间单调。若一个较新的事件先到，较旧且已经过期的事件随后进入队尾，队头不过期时程序停止删除，队尾旧事件便被错误保留。容器按到达时间排序，不等同于按业务事件时间排序，二者不能混用。

解决方式取决于允许的延迟与正确性：可以要求输入有序；可以在一定迟到范围内缓冲重排；可以使用按时间组织的优先结构并维护身份；也可以明确定义窗口按到达时间计算。每一种选择改变资源或业务语义，需要写在接口契约中，而不是在发现个别异常后随意删数据。

<a id="algo-one-49"></a>

### 8.12 练习十二：为什么计时不能证明复杂度

**题目。** 某次长度一千的列表查询比集合查询更快，能否据此证明列表成员判断是常数复杂度，或者集合没有价值？怎样改进实验？

**解析。** 单个规模、单次运行只说明那次执行的时间，无法决定随输入规模增长的函数。固定开销、命中位置、数据生成、缓存和噪声都可能影响结果。列表查询若目标总在第一个位置，实验也没有测试最坏扫描；集合若在每次查询前重建，则测量的是另一种流程。

应选择多个递增规模，控制命中位置与不命中比例，分别测量预处理和查询，多次重复并保留稳定统计。实验用于检验实现是否符合分析、定位常数与瓶颈，复杂度证明则需要对全部合法输入或明确分布建立数学界。两类证据互补，不应互相替代。

<a id="algo-one-50"></a>

### 8.13 练习十三：缓存命中率不是全部成本

**题目。** 一项特征查询加入缓存后命中率很高，是否一定更快且更省内存？请列出完整成本，并说明容量限制为何重要。

**解析。** 缓存每次查询仍要计算键、查表、维护替换顺序，并占用对象与索引空间；未命中还要执行原始计算和插入。若原计算本来极便宜，缓存维护反而可能更贵。命中率相同的两个工作负载，也可能具有不同的键长度、对象大小和并发争用，因此单个百分比不足以预测收益。

没有容量上限的缓存可能随不同键数持续增长，让长时间运行的程序失去内存可控性。有上限则需要定义淘汰策略，并考虑对象引用是否阻止其他资源释放。还应规定缓存键是否包含模型版本与全部相关参数，否则高命中可能只是反复返回过期结果。性能优化首先要保持正确性。

<a id="algo-one-51"></a>

### 8.14 练习十四：全流程模型审查

**题目。** 给定十亿条候选记录，要求按用户精确去重、保留每用户最高十条并稳定处理并列。内存有限，不能一次读完。请提出可审查的设计，不要求写完整系统。

**解析。** 先明确去重主键、重复记录的合并规则以及分数和并列次序。若同一候选在多处出现，不能先各自裁剪再随意去重，因为局部结果可能无法重建全局要求。可以按用户或业务键进行外部分区，使同一需要合并的实体进入可一致处理的分区；必要时采用外部排序或分阶段聚合，避免把全部身份放入单机内存。

每个分区完成精确合并后，使用确定比较键的有界堆维护候选，最终有序输出。需要报告读取字节量、分区写入与读取次数、最大分区规模、候选状态和临时外部空间。若用户分布极偏斜，单个分区仍可能超限，要有再分区或外部处理策略。这里只给算法设计原则，真实实现还需处理失败恢复与一致性，但不能用这些系统细节掩盖任务语义尚未定义的问题。

<a id="algo-one-52"></a>

## 9. 继续研究：从渐近结论走向可验证设计

<a id="algo-one-53"></a>

### 9.1 设计文档应该保留哪些证据

一个有价值的算法说明至少包括任务规格、输入规模定义、核心不变量、成本求和、假设与失败反例。复杂度表格适合查阅，却不能替代这些证据。对于哈希表，要写键成本与散列假设；对于动态数组，要区分摊还总量与单步延迟；对于流式方案，要说明哪些状态能释放，哪些历史信息必须保存。这样读者遇到新任务时才能修改分析，而不是机械套表。

同样应该解释为什么没有选择看起来更强的结构。若请求只需一次线性扫描，复杂索引可能没有回本；若查询很多且数据稳定，预处理的投入可能很划算；若内存上限严格，紧凑排序数组的对数查询可能比对象较重的哈希表更合适。这些判断可以用参数化成本模型表达，再通过代表性实验确认常数，而不必诉诸模糊经验。

<a id="algo-one-54"></a>

### 9.2 可继续探索的三个方向

第一个方向是外存与缓存复杂度。数据大到无法完全驻留时，磁盘或网络传输次数往往比算术操作更关键。顺序扫描虽然执行许多步骤，却可能比大量随机访问更快；分块、归并和压缩布局因此具有重要作用。研究时应为块大小和传输成本建立模型，不要继续用所有内存访问完全等价的简化模型解释现象。

第二个方向是近似数据结构。布隆过滤器、不同元素计数草图和近似近邻索引以允许受控错误换取空间或时间收益。学习它们前，应先掌握精确任务的语义与成本，随后明确误报、漏报、估计偏差和失败概率各指什么。一个方向上允许错误，并不意味着其他方向可以随意错误；概率保证也需要对输入和随机性的条件作出说明。

第三个方向是并发与持久化表示。一个顺序容器的操作复杂度，并不能直接推出多个线程同时修改时的正确性和扩展能力。锁、复制、不可变快照与版本索引分别付出不同代价。读写一致性要求会反过来决定数据结构选择。继续阅读系统章节时，可以持续追问同一个问题：为了提供目前的语义，每一步究竟移动、保存和同步了什么信息？
