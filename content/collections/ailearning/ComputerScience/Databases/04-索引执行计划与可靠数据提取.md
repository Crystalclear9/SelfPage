## 1. 优化前先定义必须保持的结果

数据库优化不是让某段 SQL 更短，也不是让计划里出现索引，而是在相同数据与语义下减少完成同一任务所需的资源。对于训练数据提取，这个任务还包含样本身份、重复次数、时间范围、缺失值和版本条件。一个漏掉困难样本的查询可能非常快，却不是原查询的性能改进。

本章把索引、计划和提取恢复放在同一条证据链中：先固定逻辑结果，再理解访问路径，随后检查快照与分页，最后设计可重试、可验收的产物。实验使用本地 SQLite 3.42.0 与 Python 标准库；PostgreSQL 的计划概念明确作为官方文档说明，不声称在本机运行该数据库。

<a id="sec-1-1"></a>

<a id="db-4-detail-2"></a>

### 1.1 相同行数不是相同数据

两份结果都一万行，仍可能一份遗漏某用户，另一用户重复两次；同样总金额也可能由正负误差抵消。应先确定业务键和预期重复规则，再比较每个键的记录与字段。对 SQL 多重集，重复次数也是语义，不能只比较集合。

如果输出有明确顺序，比较还要包括排序键与同分规则；如果顺序无意义，应避免把物理扫描变化误判为结果变化。通常先按稳定键规范化，再比较完整行或多重集，浮点字段采用符合任务尺度的容差，离散键与计数则精确核对。

源数据、参数、隔离条件和执行时点也应一致。优化前后分别在变化数据库中运行，差异可能来自底表更新，不能直接归因于改写。性能和语义对照最好使用同一冻结副本或明确一致性方案。

<a id="db-4-detail-3"></a>

### 1.2 逻辑问题与物理问题分别诊断

若一对多连接被误当一对一，输出膨胀首先是建模与连接语义问题。加索引可以让错误连接更快，却不能恢复正确样本。若连接本来合法但中间结果很大，则可以研究聚合下推、访问路径与计算顺序。

同样，全表扫描不代表错误。当读取表的大部分行时，顺序访问可能比许多索引定位和回表更便宜。看到 SEARCH 也不证明高效，索引可能只筛掉少量行，随后仍产生大量随机读取和排序。

建立清楚的诊断顺序能节省时间：先问结果是否是目标，再问哪里产生不必要工作，最后问索引、统计信息或改写能否减少它。不能用优化器给出的某个路径标签代替整个分析。

<a id="db-4-detail-4"></a>

### 1.3 吞吐、延迟与提取完成时间

交互查询通常关心首行响应时间，以及 P95、P99 等高分位延迟，批量训练集提取更关心全部结果完成、客户端接收与写出时间。一个查询很快返回游标，不表示全部行已经被计算和传输。测量若只包围 execute 而不消费结果，可能错过主要成本。

应定义完成条件：所有行已读取、必要变换完成、输出校验通过，还是只完成数据库端执行。网络、解码、压缩和磁盘写出可能主导端到端时间，单纯优化 SQL 核心不一定明显改善总耗时。

还要记录冷暖缓存、并发负载和参数分布。一次空闲环境中的最好时间，不能代表高并发服务或长时间批处理的稳定性能。系统性能建模章节提供了更广泛方法，本章重点说明它们怎样应用到数据库提取。

<a id="visual-04-concept"></a>

### 图解：键集分页与移动的 OFFSET

![键集分页与移动的 OFFSET](images/04-concept.svg)

**图解。** 首次分页已读取键 1、2，随后插入 0。偏移两行会重新读到 2；以最后读取键 2 继续查询则返回 3、4。该例解释位置漂移，并不把键游标等同于跨页快照隔离。

分页游标保存的是最后成功键，而不是已经跳过多少行。若前缀插入新记录，OFFSET 所指的位置发生移动，可能重复或漏读；稳定键边界更容易表达进度。

键集分页也不是任意可变源的不重不漏证明。排序键必须稳定且能形成全序，跨页还需要明确快照或变更日志协议；写出结果与确认进度也要有一致提交边界。

## 2. B 树、复合索引与访问范围

<a id="db-4-detail-6"></a>

### 2.1 索引把查找变成有序定位

常见有序索引将键组织成多层结构，使定位不必逐行检查整个表。理想化页模型中，高扇出让层数随记录数对数增长，但实际成本还包含缓存命中、叶页扫描和访问原表。不能只写一个对数复杂度就认为返回一百万行也几乎免费。

索引记录可能包含键和行定位信息；查询需要的字段不在索引中时，还要访问表数据。若命中很多分散记录，这些访问可能比一次顺序扫描更昂贵。覆盖索引可以减少某些回表，但会增加索引宽度、存储与写入维护。

具体实现随数据库和表组织不同。SQLite 普通 rowid 表、无 rowid 表和其他数据库的聚簇或二级索引不是完全同一结构。本章用通用有序查找模型解释趋势，具体计划以产品与版本为准，不把一种结构的细节当普遍定义。

<a id="db-4-detail-7"></a>

### 2.2 复合键是字典序，不是多个独立排序

索引键为用户、事件时间、事件号时，先按用户分段，同一用户内再按时间，同一时间内再按编号。查询固定一个用户并给时间范围，通常能对应一个连续的键区间，后续可按时间和编号读取。

如果不固定用户，只要求全体按事件时间排序，这个索引的整体顺序一般不能直接满足，因为它先按用户排列。多个用户条件也不自动等于一个全局时间有序流，可能需要额外合并或排序。应从字典序结构推导，而不是看到包含所需字段就认为排序一定免费。

传统前缀分析是重要起点，但不能把它写成优化器绝无例外的限制。某些产品与数据分布可以采用跳跃扫描、多个区间或其他路径。教材应该说明常见可利用范围，并通过计划验证实际选择，而不是用一句最左规则代替全部查询规划。

<a id="db-4-detail-8"></a>

### 2.3 等值、范围与后续过滤的角色

复合索引前部的等值条件能缩小到某个分段，接下来的范围条件确定扫描区间；更后面的条件仍可能用于索引内过滤，却不一定继续把扫描变成单个更窄连续区间。这些作用应分别理解。

例如按用户等值、时间范围、金额阈值筛选，金额可能减少输出行，但不一定减少需要检查的时间范围索引项。若金额条件选择率极高，另一种索引顺序可能更有利；若还要按时间输出，又会产生排序取舍。

不存在脱离负载的万能列序。应结合常见筛选、连接、排序、返回字段与写入频率选择，使用代表性参数测量。只为一条小样本查询定制一个很宽索引，可能损害其他查询与更新成本。

<a id="db-4-detail-9"></a>

### 2.4 表达式、类型与部分索引

对列应用函数或隐式转换，可能让普通索引无法直接提供原本预期的范围定位。可以研究等价的原值范围表达式，或产品支持的表达式索引，但需要保持日期、时区与类型语义，不能为利用索引而改变边界。

部分索引只覆盖满足某条件的行，查询必须能在产品规则下证明其所需记录位于该范围内。一个看似相近条件不一定被规划器识别为蕴含，NULL 与参数化还会影响判断。应检查实际计划，而不是只看索引创建成功。

类型也会影响比较。文本数字按字典序与数值顺序不同，时间字符串与统一整数时间可能不同；改变类型转换位置还可能改变错误或 NULL 行的去留。索引优化必须从同一个数据契约出发。

<a id="visual-04-mechanism"></a>

### 图解：复合索引是字典序，不是两个独立排序

![复合索引是字典序，不是两个独立排序](images/04-mechanism.svg)

索引 (user_id,event_time) 先按用户，再在同一用户内按时间排列。因此用户 2 且时间至少为 3 的记录形成连续后缀范围；所有用户中“时间至少为 3”的记录却不一定形成单一连续区间。

表为升序且无 NULL 的最小示例，说明访问范围而非保证数据库必选此索引。实际选择还受选择性、覆盖列、排序需求与代价估计影响。

## 3. 怎样读计划而不被计划误导

<a id="db-4-detail-11"></a>

### 3.1 估计与实际执行是不同证据

普通解释计划描述优化器选择的路径与估计，不一定真正运行完整查询。带实际执行的分析则会执行并测量，具体语法与副作用随产品而异。不能把只看计划当作已经证实真实耗时，也不能忘记某种分析命令会真正执行工作。

PostgreSQL 的估计成本是优化器内部相对单位，不是直接的毫秒；实际时间、实际行数与循环次数又属于运行证据。父子节点时间常有包含关系，不能把所有节点时间简单相加当总耗时。需要核对产品对每循环统计的具体展示方式。

SQLite 的 EXPLAIN QUERY PLAN 输出主要帮助观察扫描、搜索、覆盖索引和临时结构，不等于 PostgreSQL 的完整实际执行报告。文本展示格式也不是稳定程序接口，教学实验会打印供人观察，但不以精确字符串断言绑定某个计划。

<a id="db-4-detail-12"></a>

### 3.2 从基数误差追到多余工作

估计某步只有一百行，实际却有十万，可能导致不合适的连接顺序或执行方式。原因包括统计信息陈旧、数据倾斜、列相关性、复杂表达式或参数分布。应先定位误差最早出现的位置，再看它怎样放大后续循环和排序。

但实际行数大不自动意味着查询错。如果业务本来要求所有匹配配对，输出可能就很大。应该同时检查键约束和目标粒度，区分真实多对多输出与意外重复。性能分析与语义审计互相帮助，却不能互相替代。

统计更新可能改变计划，应在受控环境记录前后条件。生产统计维护有权限和资源成本，本章只在内存教学库中运行；读者实际系统应按维护流程操作，而不是看到慢查询就随意改全局设置。

<a id="db-4-detail-13"></a>

### 3.3 排序、覆盖与读取规模

计划中出现临时排序，可以问是否有合适顺序、是否必须返回该排序，以及是否在连接或聚合后破坏原顺序。删除 ORDER BY 能提速，但若输出分页依赖该顺序，就改变了接口，不能称纯优化。

覆盖索引意味着所需字段可能直接从索引取得，但实际收益仍依赖产品读取一致性机制、索引宽度和缓存。不要把一个路径名等同完全没有其他读取，也不要根据一个小库计划推断大库必定使用同样方式。

对于 LIMIT 查询，首批速度可能很好，却不能代表完整扫描性能；对于分页查询，不同游标位置也会影响访问成本。性能实验应根据真实消费模式选择参数和读取量，避免把只取前十行的成绩推广到全量导出。

## 4. 实验一：访问路径改变，结果必须守恒

<a id="db-4-detail-15"></a>

### 4.1 在内存数据库中建立可控对照

下面生成五千条事件，每个用户在整数时间轴上有规律记录。查询固定用户和时间区间，返回按时间与事件号有序的明细。先无额外索引运行，再建立覆盖所需字段的复合索引并重新运行。

实验同时比较有序列表和多重集，确认索引没有改变逻辑结果。计划打印用于观察，不断言某个固定文本或承诺速度倍数；数据库版本、统计和数据规模变化可能改变路径。性能测量若要扩展，需消费全部结果并记录缓存与重复条件。

```python
import sqlite3
from collections import Counter

con = sqlite3.connect(":memory:")
con.execute('''
CREATE TABLE events(
 id INTEGER PRIMARY KEY,user_id INTEGER NOT NULL,
 event_time INTEGER NOT NULL,amount INTEGER NOT NULL
)
''')
data = [(i, i % 50, i // 50, (17*i) % 1000) for i in range(5000)]
con.executemany("INSERT INTO events VALUES(?,?,?,?)", data)
query = '''
SELECT id,event_time,amount FROM events
WHERE user_id=? AND event_time>=? AND event_time<?
ORDER BY event_time,id
'''
params = (7,20,60)
plan_before = con.execute("EXPLAIN QUERY PLAN "+query,params).fetchall()
before = con.execute(query,params).fetchall()
con.execute("CREATE INDEX events_lookup ON events(user_id,event_time,id,amount)")
con.execute("ANALYZE")
plan_after = con.execute("EXPLAIN QUERY PLAN "+query,params).fetchall()
after = con.execute(query,params).fetchall()
reference = sorted([(i,t,a) for i,u,t,a in data if u==7 and 20<=t<60],
                   key=lambda r:(r[1],r[0]))
assert before == after == reference
assert Counter(before) == Counter(after)
assert len(after) == 40
print("plan before:",plan_before)
print("plan after:",plan_after)
print("rows / amount sum:",len(after),sum(row[2] for row in after))
con.close()
```

<a id="db-4-detail-16"></a>

### 4.2 为什么这个实验不宣称索引总更快

小内存数据库没有真实网络与磁盘压力，初始化、查询编译和 Python 调用可能占较大比例。即使观察到某个耗时比，也不能直接推广到大型服务器。实验目的首先是核对访问路径和结果契约，再为真实环境测量建立参考。

还应改变参数选择率。固定一个用户和窄时间窗，与读取全部用户多年历史，是不同负载；覆盖索引的存储和写入成本也没有在本例中完整衡量。实际选择应覆盖典型与困难参数，而不只测试最有利条件。

索引创建本身也有成本。若只提取一次小表，构建可能不值得；若长期重复查询，收益可以摊销。训练数据管线应把构建、维护和查询一起纳入生命周期预算，而不是只计算最终 SELECT 的时间。

## 5. 查询改写的等价证明与反例

<a id="db-4-detail-18"></a>

### 5.1 预聚合能够减少连接，但必须保留充分量

如果每个用户有很多事件，而目标只是每用户计数与总和，可以先在事件表按用户聚合，再左连接用户主表。这样可能减少中间行，但需要保留空用户和 NULL 语义，不能把所有聚合都任意提前。

例如原查询的 COUNT(event_id) 对没有事件的用户为零，预聚合后左连接得到的计数字段为 NULL，需要按目标填零；SUM(amount) 对无已知金额可能仍为 NULL，是否填零应另行定义。一个 COALESCE 不能同时替所有字段决定缺失含义。

如果后续筛选依赖事件属性、明细时间或样本时点，先按用户聚合可能丢掉必要信息。前一章已经给出时间桶等价条件，本章强调：改写应有关系粒度和可合并统计量的理由，不能仅因为中间结果变小就认为正确。

<a id="db-4-detail-19"></a>

### 5.2 EXISTS、连接与 DISTINCT 不可随意互换

只需要判断是否存在合格事件时，用存在性表达避免明细展开通常更符合目标。把它改成普通连接可能复制用户；再加 DISTINCT 虽可能恢复用户键，却未必恢复附带字段和其他聚合语义。

反过来，原目标如果需要每个匹配对，改成 EXISTS 就会删掉输出。一个更快的查询可能只回答了更弱问题。应明确输出行的身份究竟是用户、事件还是匹配对，再选择半连接、普通连接或聚合。

集合差比较也有边界。某些 SQL 差集运算会去重，两个重复次数不同的结果可能在双向差集上都为空。对于多重集目标，应比较每种完整行的出现次数，或使用支持相应多重集差的产品功能，并核对 NULL 与类型规则。

<a id="db-4-detail-20"></a>

### 5.3 完整预聚合对照

下面对有两笔相同金额事件、全空金额事件以及无事件用户同时验收。两笔金额十必须贡献二十，不能用金额 DISTINCT 偷偷变十。空用户计数为零，而原金额和保留 NULL。

```python
import sqlite3
from collections import Counter

con = sqlite3.connect(":memory:")
con.executescript('''
CREATE TABLE users(id INTEGER PRIMARY KEY);
CREATE TABLE facts(id INTEGER PRIMARY KEY,user_id INTEGER,amount INTEGER);
INSERT INTO users VALUES(1),(2),(3);
INSERT INTO facts VALUES(1,1,10),(2,1,10),(3,2,NULL);
''')
original = con.execute('''
SELECT u.id,COUNT(f.id),SUM(f.amount)
FROM users u LEFT JOIN facts f ON f.user_id=u.id
GROUP BY u.id ORDER BY u.id
''').fetchall()
rewritten = con.execute('''
WITH totals AS(
 SELECT user_id,COUNT(*) AS n,SUM(amount) AS total
 FROM facts GROUP BY user_id
)
SELECT u.id,COALESCE(t.n,0),t.total
FROM users u LEFT JOIN totals t ON t.user_id=u.id
ORDER BY u.id
''').fetchall()
assert Counter(original)==Counter(rewritten)
assert original==[(1,2,20),(2,1,None),(3,0,None)]
wrong_count = con.execute('''
SELECT u.id,COUNT(*)
FROM users u LEFT JOIN facts f ON f.user_id=u.id
GROUP BY u.id ORDER BY u.id
''').fetchall()
assert wrong_count[-1]==(3,1)
a=[(1,"x"),(1,"x"),(2,None)]
b=[(1,"x"),(2,None)]
assert set(a)==set(b) and Counter(a)!=Counter(b)
print("equivalent results:",original)
print("outer COUNT(*) counterexample:",wrong_count)
con.close()
```

<a id="db-4-detail-21"></a>

### 5.4 数值等价、类型等价与业务等价

整数金额和计数适合严格比较；浮点 SUM 在不同执行顺序下可能产生小差异，需要根据量级与风险定义容差。容差不能用于掩盖键丢失或重复，离散结构应先精确核对，再处理数值字段。

类型变化也可能影响下游。整数除法、定点精度、文本编码和日期表示即使打印类似，也不一定具有相同含义。提取模式应包括字段名、类型、单位和允许缺失，而不是只比几行文本是否相似。

业务等价还要求信息可用性相同。最新版本查询与历史 as-of 查询可能对大多数样本值相同，却在少数后来修订者上不同；这种差异不是可以按低比例忽略的普通浮点噪声。应定位边界个体并判断是否改变预测合法性。

## 6. 一致快照、长事务与可重提取

<a id="sec-2-1"></a>

<a id="db-4-detail-23"></a>

### 6.1 一个查询、多个查询与多个连接

一个查询读取的关系是否一致，取决于产品与隔离机制；多条语句是否共享相同快照，也取决于事务和隔离级别。不能只说用了事务，就断言所有产品的所有读取都固定在同一时点。

同样，一个连接上的读事务不自动让其他连接共享其快照。并行提取多个分区时，需要产品支持的共享快照、统一版本数据源或其他明确协议。仅让所有工作进程大致同时开始，无法证明它们看见完全相同状态。

本章 SQLite 实验选择 WAL 模式来展示一个读事务持有旧视图、另一个连接提交更新后读者仍继续读取旧状态的情况。它只说明这一具体机制，不把 SQLite 的单写者与快照行为推广成所有数据库的隔离定义。

<a id="db-4-detail-24"></a>

### 6.2 快照稳定不等于历史无泄漏

今天的稳定快照可能包含去年之后的会员升级、修订金额与补录事件。把它连接去年预测样本，数据库读取完全一致，特征仍可能使用未来信息。快照解决提取期间的状态漂移，业务可用时间约束解决预测时允许的信息，两者缺一不可。

也要区分可重复读取与长期可重建。一个事务里稳定，不代表下周还能打开同一个历史状态。若需要长期重提取，应保存版本化数据、可恢复快照或不可变事件日志，并记录查询与参数。只记事务开始时间通常不够。

长事务可能占用版本保留、日志或维护资源，具体表现依产品而异。不能为了追求一致性就无限保持连接。应按提取规模选择快照导出、冻结分区或合理事务边界，并在保持目标定义的前提下控制运行成本。

<a id="db-4-detail-25"></a>

### 6.3 WAL 快照的真实双连接实验

下面只在自动清理的临时目录创建教学数据库，不启动服务。读者先建立快照并读取前两行，写者更新后续行并插入新行，读者继续读取时仍见旧值；结束读事务后才看到新状态。连接在清理前关闭，避免残留数据库与日志文件。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import sqlite3

with TemporaryDirectory(prefix="ai_sql_snapshot_") as folder:
    path = str(Path(folder)/"demo.sqlite")
    writer = sqlite3.connect(path,isolation_level=None)
    reader = None
    try:
        mode = writer.execute("PRAGMA journal_mode=WAL").fetchone()[0]
        assert mode.lower()=="wal"
        writer.execute("CREATE TABLE records(id INTEGER PRIMARY KEY,value TEXT)")
        writer.executemany("INSERT INTO records VALUES(?,?)",
                           [(i,f"v{i}") for i in range(1,7)])
        reader = sqlite3.connect(path,isolation_level=None)
        reader.execute("BEGIN")
        first = reader.execute(
            "SELECT id,value FROM records ORDER BY id LIMIT 2").fetchall()
        writer.execute("BEGIN IMMEDIATE")
        writer.execute("UPDATE records SET value=? WHERE id=4",("changed",))
        writer.execute("INSERT INTO records VALUES(7,'v7')")
        writer.execute("COMMIT")
        rest = reader.execute(
            "SELECT id,value FROM records WHERE id>? ORDER BY id",
            (first[-1][0],)).fetchall()
        assert first+rest == [(i,f"v{i}") for i in range(1,7)]
        reader.execute("COMMIT")
        fresh = reader.execute("SELECT id,value FROM records ORDER BY id").fetchall()
        assert len(fresh)==7 and fresh[3]==(4,"changed")
        print("snapshot rows:",first+rest)
        print("fresh rows:",fresh)
    finally:
        if reader is not None:
            reader.close()
        writer.close()
```

## 7. 稳定分页与覆盖范围

<a id="db-4-detail-27"></a>

### 7.1 OFFSET 的位置会随数据变化漂移

分页用 LIMIT 与 OFFSET 表示跳过当前排序中的若干行。如果前面插入或删除记录，下一页的位置就会移动，可能重复或漏读。即使 ORDER BY 唯一，排序位置在变化表中也不是稳定身份。

在固定快照中，OFFSET 可以产生正确结果，但深页可能需要处理越来越多前缀，具体代价取决于执行路径。不能把它一律称为错误，也不能把它当作任何规模都等价于直接定位第若干页。

对批量提取，更常用的是基于最后一个完整排序键继续读取。它把进度绑定到键范围，而非当前位置，但仍需要考虑键是否可变、是否有新记录插入已越过范围，以及多个批次是否共享相同快照。

<a id="db-4-detail-28"></a>

### 7.2 键集分页需要完整且不变的次序

按时间、唯一编号排序时，游标也要同时保存时间和编号。只保存时间，下一页使用严格大于会漏掉同时间其他记录；使用大于等于又可能重复。复合比较或等价的分支条件能表达完整字典序。

排序字段若可为 NULL，需要明确 NULL 顺序与游标编码；字符串排序还依赖 collation 与规范化，不能在恢复时换一种比较规则。业务键更新会让记录跨越游标，可能重复或漏读，稳定编号不能自动修复可变首排序字段。

限制最大编号可以帮助冻结追加型、编号单调且其他内容不变的数据范围，但不能冻结字段更新、删除或回填较小编号。所谓高水位需要写出源数据不变性假设，而不是把一个 MAX(id) 当作通用快照替代品。

<a id="db-4-detail-29"></a>

### 7.3 分页漂移的可运行反例

下面先取两行，再在排序前端插入一条。OFFSET 下一页重复旧页末尾；键集分页不会重复已经越过的稳定键，但也不包含新插入的前端记录。这说明它解决位置漂移的一部分，而不自动提供一个新旧数据混合下的完整快照。

```python
import sqlite3

con=sqlite3.connect(":memory:")
con.execute("CREATE TABLE source(id INTEGER PRIMARY KEY,t INTEGER NOT NULL)")
con.executemany("INSERT INTO source VALUES(?,?)",
                [(1,1),(2,1),(3,2),(4,2),(5,3),(6,3)])
first=con.execute("SELECT id,t FROM source ORDER BY t,id LIMIT 2").fetchall()
con.execute("INSERT INTO source VALUES(0,0)")
offset_page=con.execute(
 "SELECT id,t FROM source ORDER BY t,id LIMIT 2 OFFSET 2").fetchall()
assert first==[(1,1),(2,1)] and offset_page==[(2,1),(3,2)]
cursor=(first[-1][1],first[-1][0])
rest=[]
while True:
    page=con.execute('''
      SELECT id,t FROM source
      WHERE (t,id)>(?,?) ORDER BY t,id LIMIT 2
    ''',cursor).fetchall()
    if not page:
        break
    rest.extend(page)
    cursor=(page[-1][1],page[-1][0])
assert [r[0] for r in first+rest]==[1,2,3,4,5,6]
assert 0 not in [r[0] for r in first+rest]
print("offset repeated ID:",offset_page[0][0])
print("keyset IDs, excluding late insertion before cursor:",
      [r[0] for r in first+rest])
con.close()
```

<a id="db-4-detail-30"></a>

### 7.4 分区并行也要证明不重不漏

按键范围分任务时，应使用一致闭开边界，并证明所有分区覆盖目标域且不重叠。按哈希分区时，需要相同哈希与稳定键；简单取模还要明确负数、类型和产品运算规则。分区数量改变时，旧游标不能直接解释为新分区进度。

多个并行任务必须读取同一版本条件，或在结果中显式保留不同来源版本。若某分区失败后从更新后的表恢复，拼接结果可能混入两个时间状态。每分区完成清单应包含范围、版本、查询参数和输出摘要。

最终还要核对跨分区唯一键。局部每个任务都无重复，不代表边界没有重叠；每个任务行数合理，也不代表某个分区被漏掉。全局覆盖验证是并行提取协议的一部分，不能由任务状态显示全部成功来替代。

## 8. 可重试提取与提交边界

<a id="db-4-detail-32"></a>

### 8.1 检查点应描述已确认完成的工作

只记录读到了哪一行不够，还要知道对应输出是否已经可靠写入。若先推进游标再写输出，中断后会跳过缺失数据；若先写输出再推进游标，中断后重试可能重复写。需要让两者原子提交，或用幂等输出与明确恢复规则处理间隙。

同一数据库事务内的目标表写入与进度更新可以共同提交，这是一个较简单模型。若源、目标与对象存储分别属于不同系统，单个本地事务不能覆盖全部，需要分块不可变产物、发布清单、幂等键或其他协议。不能只使用一次 upsert 就宣称端到端任何情况下都恰好一次。

检查点还应保存查询与变换身份、快照或数据版本、分区键和完整游标。换了特征逻辑后继续旧游标，会生成混合模式产物；换了源快照后继续，也可能不再代表同一提取。恢复首先是状态一致性问题，再是继续执行命令的问题。

<a id="db-4-detail-33"></a>

### 8.2 幂等性依赖稳定输入和变换

对同一键 upsert 相同结果，可以让重复提交不产生多份记录，但前提是结果由固定输入与确定规则生成。若每次随机变换不同、调用外部当前状态或使用不稳定时间戳，重复同一个键可能覆盖为另一结果，不能简单称重试完全无影响。

还要说明删除和修订政策。固定快照批次可以把源看成不变；增量同步则需要事件版本与删除状态，单纯按最大编号只能发现新增，不能发现旧记录变更。两种任务应使用不同协议，不要用同一个游标字段假装全部涵盖。

即使数据库提交成功，客户端也可能在收到确认前断开，恢复时无法仅凭本地异常判断提交是否发生。幂等键与可查询提交记录能处理这种不确定性，比盲目重跑或盲目跳过更可靠。本章实验使用事务回滚模拟一种边界，不声称覆盖全部分布式故障。

<a id="db-4-detail-34"></a>

### 8.3 故障注入与原子进度实验

下例源数据固定、编号为正且递增，变换为整数平方。输出与进度位于同一 SQLite 数据库事务。故意在写输出之后、更新游标之前抛异常，回滚后两者都未提交；再次运行得到完整九条，无重复或遗漏。

```python
import sqlite3

con=sqlite3.connect(":memory:",isolation_level=None)
con.executescript('''
CREATE TABLE source(id INTEGER PRIMARY KEY CHECK(id>0),value INTEGER NOT NULL);
CREATE TABLE output(
 id INTEGER PRIMARY KEY,value INTEGER NOT NULL,transform_version TEXT NOT NULL
);
CREATE TABLE progress(
 singleton INTEGER PRIMARY KEY CHECK(singleton=1),
 last_id INTEGER NOT NULL,transform_version TEXT NOT NULL
);
INSERT INTO progress VALUES(1,0,'square-v1');
''')
con.executemany("INSERT INTO source VALUES(?,?)",[(i,i) for i in range(1,10)])

def step(fail=False):
    con.execute("BEGIN IMMEDIATE")
    try:
        last,version=con.execute(
          "SELECT last_id,transform_version FROM progress WHERE singleton=1"
        ).fetchone()
        if version!="square-v1":
            raise ValueError("checkpoint transform mismatch")
        rows=con.execute(
          "SELECT id,value FROM source WHERE id>? ORDER BY id LIMIT 3",(last,)
        ).fetchall()
        for ident,value in rows:
            con.execute('''
             INSERT INTO output VALUES(?,?,'square-v1')
             ON CONFLICT(id) DO UPDATE SET
               value=excluded.value,transform_version=excluded.transform_version
            ''',(ident,value*value))
        if fail and rows:
            raise RuntimeError("injected after output writes")
        if rows:
            con.execute("UPDATE progress SET last_id=? WHERE singleton=1",
                        (rows[-1][0],))
        con.execute("COMMIT")
        return bool(rows)
    except BaseException:
        con.execute("ROLLBACK")
        raise

try:
    step(fail=True)
except RuntimeError:
    pass
else:
    raise AssertionError("failure injection missing")
assert con.execute("SELECT COUNT(*) FROM output").fetchone()[0]==0
assert con.execute("SELECT last_id FROM progress").fetchone()[0]==0
while step():
    pass
actual=con.execute("SELECT id,value FROM output ORDER BY id").fetchall()
assert actual==[(i,i*i) for i in range(1,10)]
assert con.execute("SELECT last_id FROM progress").fetchone()[0]==9
assert step() is False
print("recovered output:",actual)
con.close()
```

<a id="db-4-detail-35"></a>

### 8.4 从教学事务到真实文件产物

若每批写一个文件，可以先写独立暂存对象，校验内容，再发布不可变块并更新清单。恢复时按清单识别已确认块，对未确认暂存物选择校验重用或删除。文件存在不等于内容完整，文件名也不等于样本范围已经正确覆盖。

发布机制的原子范围与持久性需要按文件系统或存储服务核对。重命名在某些条件下可提供可见性切换，但跨文件系统、远程对象存储或断电持久性不是同一个保证。应把状态机与实际接口条件写清，不把一句原子保存当作完整故障协议。

最终完成标志应在全部分区提交并通过全局验收后产生，而不是最后一个工作进程退出时立即生成。这样下游能区分可消费产物与仍在写入的目录。可靠提取不仅要求能重跑，还要求消费者知道何时可以相信结果完整。

## 9. 结果验收、摘要与数据身份

<a id="db-4-detail-37"></a>

### 9.1 结构检查与业务检查分层

结构层先检查模式、类型、唯一键与约束；记录层检查完整键集合、重复次数与缺失；统计层检查分组计数、金额、标签分布和时间范围；业务层抽查版本与可见性。每层覆盖不同错误，不能用一个总行数替代。

对训练数据，还要检查标签成熟、实体跨划分重复和特征来源版本。一个数据库提取完全成功，仍可能生成有泄漏或不适合部署的数据集。数据库一致性、查询语义、机器学习信息边界应作为独立验收维度。

验收规则应在观察结果前尽量固定。事后发现某组样本导致质量下降就把它从查询删掉，会改变研究总体；可以探索，但应记录并重新定义实验，而不是悄悄称作清洗后同一个测试集。

<a id="db-4-detail-38"></a>

### 9.2 内容摘要需要规范化序列化

想比较两次结果摘要，必须固定行序、列序、类型、NULL 表示、文本编码与浮点格式。相同关系的不同物理顺序，若直接按流计算摘要，会产生不同值；反过来，简单把行哈希相加也可能丢掉顺序与碰撞信息。

规范化摘要可以辅助检查与版本管理，但不提供数学上的无碰撞证明，也不证明数据语义正确。已知错误数据同样能得到稳定摘要。应保留键和统计验收，并在关键差异时能定位到具体记录。

对于超大结果，可以按稳定键范围生成分块摘要与清单，先定位变化分区，再做细粒度比较。分块边界与摘要算法版本也需要保存，否则两次清单难以解释。不要把最终一个字符串当作所有质量证据的替代品。

<a id="db-4-detail-39"></a>

### 9.3 提取清单应保存什么

一份可重建清单应包含查询文本或稳定代码版本、绑定参数、源模式与快照身份、业务时间协议、分区规则、输出模式、变换版本和验收结果。环境与驱动版本影响类型和行为时，也应记录。

只有 SQL 文件与提取日期通常不足以重建持续变化的表。日期不是数据库快照，代码提交也不包含外部数据与运行状态。相反，也不必把所有临时日志都当成最终产物；应保留足以解释和恢复结果的必要信息。

当团队修改查询时，清单能够说明结果变化来自数据、逻辑还是执行环境。把这些维度分开，比只给训练集起一个新文件名更可审查。下一轮模型实验才能明确自己到底改变了哪一个输入条件。

## 10. 进阶：代价估计、约束与计划稳定性

<a id="db-4-detail-41"></a>

### 10.1 列相关会怎样放大选择率误差

假设一万行中，条件甲命中一千，条件乙也命中一千。如果优化器按独立近似估计两者同时成立，可能得到一百行；若两条件实际上完全重合，真实为一千，差十倍；若互斥，真实为零。单列频率都正确，也不能确定联合选择率。

这说明统计信息更新不总能解决所有估计问题。需要理解产品支持哪些联合统计、约束与表达式信息，以及实际参数是否与统计样本相符。不能把任何慢计划都归因于统计过时，数据本身的相关与倾斜同样重要。

估计误差还会沿连接传播。一个早期中间关系被低估十倍，后续按它选择的嵌套访问可能多执行很多次；排序与内存预算也会受到影响。分析应从最早偏差处追踪，而不是只责怪最后那个耗时最长的节点。

<a id="db-4-detail-42"></a>

### 10.2 键约束既保护语义，也提供推理信息

若右表连接键唯一，左表每行最多命中一条；若不唯一，输出上界就不同。业务口头说唯一，不等于数据库或验证程序已经建立该事实。应使用适合的约束，并在历史版本表中注意唯一的是实体还是实体加版本。

约束还会影响空值和连接边界。某个外键存在，不自动表示所有记录在业务时点都有合法版本；时间区间表即使键加版本唯一，也可能有重叠有效区间。静态关系完整性与时间唯一性需要分别检查。

优化器能利用什么约束依实现而异，但对研究者而言，约束至少使等价证明更清楚。比如先聚合再连接能否保留一行一个样本，就取决于聚合键是否与样本身份关系匹配。不能仅看字段名字相同就假设函数依赖成立。

<a id="db-4-detail-43"></a>

### 10.3 不同连接算法对应不同资源结构

概念上，嵌套循环对外层每行寻找内层匹配，适合外层小且内层访问高效的场景；哈希连接需要构建与探查状态，可能受内存和溢写影响；归并连接利用有序输入，但排序本身可能有成本。这是分析模型，不代表每个数据库都提供全部路径。

SQLite 的计划阅读应按它实际展示的执行方式解释，不能在没有相应证据时套用另一服务器数据库的算子名称。查询文本相同，在不同产品中可能采用不同算法和资源配置，比较结果时应记录环境。

连接算法也不能消除输出规模。如果某键左侧一千条、右侧一千条且要输出全部配对，就有一百万结果。换更快索引只减少查找，无法把必须输出的配对变成一千。需要减少输出时，应重新定义任务或采用合法聚合，而不是期待优化器自动改变关系语义。

<a id="db-4-detail-44"></a>

### 10.4 参数分布与缓存计划的边界

一个稀有用户只返回几行，一个热点用户可能返回几百万行，最佳访问路径未必相同。只测平均参数会掩盖尾部负载。应使用代表性参数组，记录返回规模与资源，检查慢查询是否集中在特定分区、值域或时间跨度。

有些系统会复用已准备的执行计划，计划对参数分布的处理方式需要按产品核对。即使查询文本相同，版本、统计、缓存和配置变化也可能改变计划。稳定复现应保存这些条件，而不是把某次计划文本当永久保证。

强制路径或提示有时能规避特定问题，但也可能在数据增长后变差。应保留不强制的基线和结果等价检查，说明为何选择该控制。性能改进需要可回退与可观察的依据，不能只把一个经验开关写成通用最佳实践。


<a id="db-4-detail-45"></a>

### 10.5 客户端批量与结果消费也属于负载

每次 fetch 一行会产生很多客户端调用，一次取全部又可能超出内存。适当批量读取能在调用开销和工作集之间折中，但数据库游标、驱动预取与网络缓冲可能使请求批量不等于实际传输块。应测端到端完成时间和峰值内存，而不是只根据 fetchmany 参数推算吞吐。

如果下游变换比数据库慢，提取端会积压结果。提高查询速度可能只让队列更快填满，最后受写出限制。可以把读取、变换、写出分阶段观测，并使用有限缓冲限制在途状态；若涉及并行变换，还要保证结果身份和最终排序。数据库优化应与整个管线的瓶颈匹配。

测量时应保持输出消费相同。一个方案只数行、另一个方案还序列化全部字段，不能直接比较总时间；一个方案丢弃失败记录，也没有完成同一任务。可以分别报告纯查询、客户端转换与完整交付，清楚说明每个边界，而不是把不同层面的最好数字拼成一个结论。

<a id="db-4-detail-46"></a>

### 10.6 多重集参考也需要类型契约

本章 Counter 实验中的行由整数和 NULL 组成，适合直接用 Python 元组核对。真实数据跨驱动比较时，还要注意类型相等规则：某些宿主语言会把整数一与浮点一视为相等，而提取模式可能要求区分；NaN、自定义数值与时区对象的比较也可能不同。

可以先固定输出模式，再把每个值规范成带类型的表示，明确 NULL、字节、文本、时区与数值精度。不要只按打印文本比较，因为字符串一与数字一可能打印相似，却代表不同字段含义。对浮点允许容差时，也需要保持行键与重复次数的精确对应，不能先把所有值四舍五入后就假定业务等价。

差分测试还应该避免共享同一个错误实现。可以让参考查询采用直接明细关系，让优化方案采用预聚合或范围访问，再用手工小表和独立逐行程序核对。随机输入能扩展覆盖，但若两种实现都错误处理同一边界，仅仅相互一致仍不能证明正确。

<a id="db-4-detail-47"></a>

### 10.7 参数化回归表让性能改动可审查

为重要查询保留一套小型语义回归表，包含空匹配、重复键、NULL、相同金额、时间边界、版本修订和热点分组。每次改索引或 SQL，先运行这些有明确答案的输入，再在代表规模测性能。小表不用于预测服务器秒数，而用于阻止悄悄改变任务。

另外保存一组代表性参数，覆盖窄窗、宽窗、稀有键与热点键。报告各类返回规模与资源变化，避免平均提速掩盖最重要请求退化。如果没有新的改动或风险，已经通过的语义实验不必机械反复运行；保留结果和版本，再把验证精力用在变化的部分。

还要先修复本来未充分定义的查询：没有确定排序却使用 LIMIT 时，不同访问路径可能返回不同合法子集；不能据此断言索引破坏了数据库语义，也不能把任意子集当作稳定训练样本。若研究需要固定样本，应先增加完整排序或其他明确抽样规则，再比较优化。

## 11. 进阶：增量提取与完成性证明

<a id="db-4-detail-49"></a>

### 11.1 追加、高水位与变更日志是不同模型

固定快照提取可以把源视为不变，单调追加源可以用稳定高水位限定范围；支持更新删除的源，则需要能够识别旧键变化的机制。按主键大于上次最大值只覆盖新增，不会发现一条老记录金额被修订或已经删除。

增量同步常借助变更日志或版本列，但应明确顺序、事务边界与保留期。一个简单更新时间可能有并列、精度和回填问题；不同表的时钟也未必完全一致。不能用墙钟字符串替代产品提供的可靠提交坐标而不分析条件。

如果日志过期，恢复游标可能已不可用，需要重新建立一致基线或其他恢复路径。检查点文件仍然存在，不代表源系统仍能重放它之后的完整变化。恢复演练应该验证从数据来源到目标提交的整条链。

<a id="db-4-detail-50"></a>

### 11.2 初始快照与后续变化之间不能有缝隙

想先扫描全表，再消费更新日志，需要保证扫描期间发生的变更不会漏掉或被错误重复。正确协议必须关联快照边界与日志坐标，并定义如何合并同一实体的快照值和后续变更。具体接口依数据库，不应通过分别记录两个近似时间来假装建立原子边界。

例如扫描早期读到旧值，稍后更新已经发生，但日志消费却从更新之后开始，就会漏修订；若消费更早日志而不做版本判定，又可能把较旧值覆盖到较新快照值。幂等键能去除部分重复，不能自动判断哪个版本应获胜。

可以用小型状态机模拟插入、更新、删除在扫描前后交错，检查最终目标是否等于某个明确定义状态。正式系统仍要用产品支持的快照与日志协议验证。教学模型用于暴露问题，不是专用同步引擎的完整替代实现。

<a id="db-4-detail-51"></a>

### 11.3 用不变量证明前面的恢复实验

在固定正整数主键源中，令游标为 c，不变量是目标表恰好包含源中键不大于 c 的记录对应变换，且每个键一行。初始 c 为零，源键全为正，目标为空，所以成立。

每一步按键读取 c 之后的下一批，把这些结果写入目标，并在同一事务中把游标推进到该批最大键。成功提交后，目标新增部分恰好覆盖被跨过的源范围；失败回滚时，目标和游标共同回到旧状态。因此归纳得到全部成功步骤都保持不变量。

证明使用源固定、键有序且不变、变换确定、目标唯一键和共同原子事务。只要换成可变源、两个独立存储或不确定外部调用，就必须补相应协议。一个通过了故障注入的教学程序，不应被解释成已经证明所有分布式场景完全相同。

<a id="db-4-detail-52"></a>

### 11.4 消费者确认与生产者进度

数据管线可能有读取、变换、写出多个阶段，内存队列里已经读取的记录不等于已提交输出。检查点应根据最后确认提交的边界推进，不能根据预取器读到的位置推进。否则中断后队列内容丢失，恢复会跳过尚未完成的工作。

有限队列与背压能限制在途内存，但也需要异常传播。写出失败后，前端不能无限继续读，消费者等待也要能结束。提取完成条件应同时包含生产结束、在途任务清空、错误处理和最终清单发布，而不是某个线程退出。

这些系统机制与 SQL 本身相互连接。数据库查询返回游标，只完成了流程的一部分；训练集真正可消费，需要整个生产与提交协议完成。把完成性写成状态机，可以让重试、取消与恢复具有一致解释。

## 12. 进阶练习与完整解析

<a id="db-4-detail-54"></a>

### 12.1 练习一：相同行数为何不够

**题目。** 原结果用户甲两行、乙一行，优化后甲一行、丙两行，总数都三。若金额也碰巧相同，可以认定等价吗？

**解析。** 不能，键覆盖与重复次数都变了，聚合总量相同只是抵消。应按业务键和完整行的多重集比较，并检查相关字段。若目标是一用户一行，原查询本身也要审查。等价验收必须先明确目标粒度，而不是选择最容易相等的几个汇总数字。

<a id="db-4-detail-55"></a>

### 12.2 练习二：为什么全扫描可能合理

**题目。** 查询要读取表中百分之九十五记录及多数宽字段，为什么索引定位不一定更快？计划中出现扫描是否说明结果错误？

**解析。** 大量索引定位和回表可能引入额外访问，顺序扫描有机会更高效；还取决于缓存、覆盖与表组织。访问路径是实现选择，不能据此判断逻辑结果错误。应在相同数据和消费条件下测量，并把输出规模计入分析，不把索引出现与否当成成功标准。

<a id="db-4-detail-56"></a>

### 12.3 练习三：复合索引的顺序

**题目。** 索引按用户、时间、编号排序，固定一个用户并按时间输出通常有什么帮助？若查询所有用户按时间输出，为什么不同？

**解析。** 固定用户后，剩余索引次序就是该用户内的时间、编号，可同时支持范围与顺序读取。全体索引先按用户分段，不是全局时间次序，可能需要额外排序或其他路径。应从字典序推导，不是只检查索引是否包含时间列。

<a id="db-4-detail-57"></a>

### 12.4 练习四：计划成本和实测时间

**题目。** 某产品 EXPLAIN 成本为一百，另一个版本实测一百毫秒，能否说两者相等？为什么不能把所有父子节点时间直接加总？

**解析。** 估计成本常是优化器内部单位，与实际毫秒不是同一量；具体需按产品解释。父节点可能包含子节点工作，简单相加会重复。还应结合循环次数与完整查询耗时，不能仅根据一个看似相同数字得出性能结论。

<a id="db-4-detail-58"></a>

### 12.5 练习五：COUNT 的左连接反例

**题目。** 用户无事件，左连接后 COUNT(*) 为什么可能为一，而 COUNT(event_id) 为零？预聚合改写应保留哪种语义？

**解析。** 左连接为无匹配用户生成一条右侧空扩展行，COUNT(*) 数这条结果行，COUNT 非空事件号不数它。若目标是事件数，应保留后者或等价预聚合加零填充。不能为了减少 SQL 字符把两个计数替换，空用户正是能暴露错误的必要反例。

<a id="db-4-detail-59"></a>

### 12.6 练习六：相同金额的去重陷阱

**题目。** 两笔不同订单金额都十，连接膨胀后想用 SUM(DISTINCT amount) 修复，为什么不可靠？

**解析。** 金额不是订单身份，去重数值会把真实两笔也合成一笔，得到十而非二十。应修复连接粒度，或按明确订单键恢复唯一贡献，再求和。DISTINCT 只能实现其定义的等值去重，不能理解哪些重复来自错误连接，哪些是合法业务记录。

<a id="db-4-detail-60"></a>

### 12.7 练习七：OFFSET 漂移

**题目。** 排序记录一到六，读完前两条后在最前插入零，再按 OFFSET 二读取两条，会发生什么？固定快照中是否也必然发生？

**解析。** 新位置二从旧记录二开始，重复上一页末条；固定快照中插入不可见，就没有这一漂移。问题来自位置分页与变化数据组合，不能把 OFFSET 一律说错。若规模较大，固定快照仍需评估深页读取成本。

<a id="db-4-detail-61"></a>

### 12.8 练习八：复合游标

**题目。** 三条记录时间相同，第一页只取其中两条，只保存最后时间并用下一页时间大于游标，会怎样？

**解析。** 第三条同时间记录会被漏掉。应保存时间加唯一编号，并按相同字典序继续，或采用等价分支条件。若排序字段可为 NULL 或使用特殊字符排序，游标编码还需完整表达这些规则；恢复时不能换成另一种顺序。

<a id="sec-7-2"></a>

<a id="db-4-detail-62"></a>

### 12.9 练习九：同一 SQL 能否重建同一结果

**题目。** 保存了 SQL、绑定日期和代码提交，底表持续修订，下周重跑是否保证相同训练集？还缺什么？

**解析。** 不保证，还需可重建的数据版本或快照、模式与时间协议。代码身份没有固定外部表状态，日期参数也不是数据库版本。可以保存不可变数据源或可靠历史日志及重放规则，再配验收摘要。摘要能帮助核对，不能凭空恢复已经丢失的数据。

<a id="db-4-detail-63"></a>

### 12.10 练习十：高水位的假设

**题目。** 保存最大主键一千，后续只取更大键，能否发现主键十的金额修改？若只想冻结追加范围，这个办法何时合理？

**解析。** 不能发现旧键更新或删除。它适合键稳定、严格按协议追加且范围内内容不再改变的源，并需处理并列或回填规则。可变源需要版本或变更日志。一个方便游标只在明确数据模型下充分，不能自动提供通用同步保证。

<a id="db-4-detail-64"></a>

### 12.11 练习十一：游标提交顺序

**题目。** 先保存游标再写输出，与先写输出再保存游标，分别有什么中断风险？教学实验怎样避免？

**解析。** 前者可能跳过未写数据，后者可能重试重复写。示例把输出与进度放在同一数据库事务共同提交，并使用唯一输出键。跨文件和不同服务则需要幂等与发布协议，不能把本地事务范围外的动作也当作原子完成。

<a id="db-4-detail-65"></a>

### 12.12 练习十二：估计独立性

**题目。** 一万行中甲条件与乙条件各命中一千，独立估计联合一百，但实际完全重合。误差来自什么？更新单列频率一定能修复吗？

**解析。** 联合相关性没有被独立近似表达，真实一千，差十倍。单列频率已经正确，单独更新它们不保证修复，需要合适联合信息或其他规划依据。应查具体产品能力，并定位偏差传播，不把所有估计问题都简化成统计过时。

<a id="db-4-detail-66"></a>

### 12.13 练习十三：多重集差异

**题目。** 两结果分别为甲、甲、乙和甲、乙，用去重集合比较是否相等？为什么有些双向差集验收仍会漏掉问题？

**解析。** 去重集合相等，但重复次数不同。某些差集运算按集合语义去重，所以两方向都为空仍不能证明多重集等价。应比较完整行计数或使用明确支持多重集的操作，并核对 NULL 与类型。验收算法本身也有语义契约。

<a id="db-4-detail-67"></a>

### 12.14 练习十四：测量只包围 execute

**题目。** 查询返回十万行，代码只记录 execute 调用耗时，不 fetch 结果。这个数字能否代表完整导出耗时？

**解析。** 不能，数据库或驱动可能延迟执行与传输，后续取数、解码和写出尚未完成。应定义完成条件并消费全部目标结果，同时可另外报告数据库核心时间。把首行延迟与全量提取时间混为一个指标，会导致错误优化方向。

<a id="db-4-detail-68"></a>

### 12.15 练习十五：快照与业务可用时间

**题目。** 一个长事务保证多批都看到今天同一状态，能否直接把今天最新资料用作去年每个样本的特征？

**解析。** 不能，事务快照解决批次状态一致，历史特征还要按当时有效和可用版本选择。今天统一看见未来升级仍是泄漏。应在查询中表达样本时点，并用前一章的延迟、修订与删除反例核对，不能用隔离级别名称代替业务合法性。

<a id="db-4-detail-69"></a>

### 12.16 练习十六：规范化摘要

**题目。** 同一关系按不同物理顺序输出，逐行累积内容哈希不同，是否证明数据内容变了？如何改进？

**解析。** 不一定，可能只改变行序。若顺序非目标语义，应先按稳定完整键规范化，并固定列序、类型和 NULL 表示再摘要。若顺序本来重要，则应保留其差异。摘要只能在明确序列化协议下解释，也不能替代具体键与业务验收。

## 13. 综合研究任务与验收

<a id="sec-7-1"></a>

<a id="db-4-detail-71"></a>

### 13.1 快照一致但特征仍泄漏的完整诊断

构造一个后来升级会员、迟到交易和金额修订的小库，用今天一致快照生成去年样本。先展示无时间约束的最新表连接，再按预测可用时间选择版本。比较每个样本的版本身份与特征差异，解释哪个环节属于数据库一致性，哪个属于历史信息条件。

然后为正确参考查询建立索引或合法预聚合，比较结果多重集与执行计划。验收要求优化不改变样本覆盖、版本与缺失规则，再讨论运行资源。若查询更快但悄悄使用今天最新状态，应明确判为目标改变，而不是有效优化。

<a id="db-4-detail-72"></a>

### 13.2 对提取器做中断与重试研究

在固定源中选择几个故障点：读完未写、写完未确认、部分分区完成、客户端未收到提交确认。对每种情况说明已有持久状态、恢复依据与重复风险。可以先用教学事务验证，再在项目实际存储上核对原子范围。

最终从源定义、游标、输出唯一键和完成清单证明不重不漏，或准确说明只能获得哪种保证。记录一次演练成功很有价值，但不代表全部故障都已覆盖；应让结论与已验证状态机匹配。
