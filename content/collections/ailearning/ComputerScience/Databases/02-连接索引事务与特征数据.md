## 1. 连接先算基数，再写字段

<a id="database-2-detail-2"></a>

### 1.1 用每个键的重数推导结果

等值内连接可以理解为枚举左右行对，只保留连接条件为真的组合。对于某个非空键，若左侧有两行、右侧有三行，结果有六对。整个内连接的结果数等于各键左重数与右重数乘积之和；这个表达式假设简单等值、比较规则明确，并单独处理空值，因为普通空值等号不会成为真。条件更复杂时，应直接定义匹配集合，不能继续机械套键计数。

左连接对每条左行生成全部匹配；若一个匹配也没有，补出一行右列为空的结果。所以每条左行贡献匹配数与一中的较大值。左连接保留左行的存在，却不保证左行仅出现一次。数据工程中常有人以为“左连接不丢数据”就表示安全，实际上保留键集合和保持样本重数是两条独立要求，一对多匹配完全可能使样本权重失控。

如果左表是一行一预测样本，右表是一行一订单，把订单直接连接上来会让高频购买用户拥有更多训练行。模型可能因此偏向高活跃群体，而整体样本数增加被误认为训练数据变丰富。正确做法常是先在合法时间范围内把订单聚合到样本粒度，再连接；如果确实要一行一订单训练，就应该重新定义目标与样本单位，而非沿用用户级标签说明。

<a id="database-2-detail-3"></a>

### 1.2 唯一约束如何变成基数保证

右表连接键唯一时，每条左行最多匹配一次；若还存在有效外键，且引用非空，内连接通常不会因无匹配而删除左行。这里的“通常”不是模糊推理，而是提醒比较字段、约束范围和额外筛选必须一致。例如外键保证用户存在，却不保证用户满足当前状态筛选；额外要求用户为活跃状态，仍可能删除合法订单。

复合键不能省略部分列。假设订单编号仅在租户内部唯一，连接只用订单编号会把不同租户混在一起。每侧单看编号都可能有合理重复，但组合键才表达对象身份。跨时间版本表也类似：用户号只能标识实体，用户号与有效区间才说明某个状态版本。把版本表误当唯一维表，是特征宽表复制的常见根源。

在查询之前先统计右键重复，并检查约束是否真实启用。对于应该唯一却不唯一的来源，应修复或明确版本选择，不要通过随意取最小值隐藏冲突。最小值能让结果变成一行，却不证明被选记录正确。若规则确实是“取最新合法版本”，需要明确最新的时间字段、可见性边界和并列次序，这些都属于逻辑定义。

<a id="sec-1-1"></a>

<a id="database-2-detail-4"></a>

### 1.3 基础算例：ON 与 WHERE 逐行展开

用户甲有一笔有效订单和一笔取消订单，用户乙没有订单，用户丙只有取消订单。如果把有效状态条件放在连接条件中，甲匹配有效订单，乙和丙都得到空扩展行；如果先连接全部订单再在筛选中要求有效状态，只有甲保留。丙尤其重要：他不是没有任何订单，而是没有合格订单，这能揭示某些看似补救的改写仍然错误。

有人在后置筛选中加入“或者订单号为空”，以为能恢复左连接。它能保留乙，因为乙产生空扩展行；却不能保留丙，因为丙已经匹配到取消订单，没有空扩展行可保留。因此“有效状态或者未匹配”并不等价于“只匹配有效订单且保留全部用户”。最小反例需要包含只有不合格右行的用户，只有有单与无单两类还不够。

<a id="database-2-detail-5"></a>

### 1.4 半连接、反连接与缺失陷阱

若只需判断用户是否存在合格订单，不需要把每笔订单铺开，存在子查询表达更接近问题。半连接保留有匹配的左行，右侧有一笔或一百笔都不会额外复制该左行；但左表自己若有重复行，重复仍保留。它解决的是右侧匹配造成的放大，不是自动对左侧去重。

不存在子查询表达“没有匹配”。用不属于某个子查询的写法时，如果子查询包含空值，三值逻辑可能使预期的真变成未知。例如候选用户三既不等于一，也无法确认不等于未知编号，因此筛选可能没有结果。不是说不属于永远不能用，而是必须证明右侧非空及预期比较语义。不存在通常更直接地表达按条件找不到匹配的事实。

左连接后检查右侧某列为空也可表达反连接，但应选择匹配时保证非空的标识列；如果检查一个本来就可空的业务字段，就会把“匹配成功但字段未知”误判为“没有匹配”。这种错误在统计缺少订单、缺少地址或缺少标签时尤其常见。检查列的约束是证明的一部分，不应仅凭列名猜测。

<a id="visual-02-concept"></a>

### 图解：左连接保留存在不保留重数

![左连接保留存在不保留重数](images/02-concept.svg)

**图解。** 沿每条匹配边生成一条输出记录。订单 O1 匹配右表的两个版本，所以金额 100 出现两次；LEFT JOIN 的“保留左行”不意味着“每个左行只出现一次”。

左连接保证每条左记录至少在结果中出现一次，但不是恰好一次。匹配数量决定输出重数，因此不能把保留左键集合与保留样本权重混为一谈。

应先定义属性表的业务有效版本和唯一键，再验证连接基数。若本来需要展开，则应改变输出粒度与汇总政策；事务快照正确也不能替代历史信息合法性。

## 2. 连接重写与聚合粒度的证明

<a id="database-2-detail-7"></a>

### 2.1 先聚合再连接何时有效

设每笔订单有金额，订单还连接商品标签。直接连接后求订单金额，会让多标签订单被反复累计。若目标是用户订单总额，可以先在订单粒度确认唯一，再按用户聚合，不把标签维度引入金额路径；若目标是各标签归因金额，则必须说明多标签如何分配权重。每标签都算全额是多重归因，不等于互斥分配，合计可能超过总额。

先聚合右侧到连接键能控制基数，但聚合条件仍需和样本一致。若每个样本有不同预测时点，简单把所有历史按用户聚成一行，会把未来订单混入早期样本。此时聚合键可能需要样本号，或通过时点条件关联后按样本聚合。不能只关注一行一用户的形状，而忽略那一行摘要对应哪个时间范围。

过滤与聚合的交换也需要注意。若要保留全部用户并计算有效订单数，先在右侧筛有效订单并分组，再左连接是清晰方案；未匹配计数可显示零。若聚合输出金额未知，是否填零要依业务决定；没有合格订单与有合格订单但金额全部未知应区分，最好同时携带订单数和已知金额数，而不是只导出一个总额。

<a id="database-2-detail-8"></a>

### 2.2 用输出契约审查优化改写

一个优化如果保留键集合却改变重数，仍可能改变训练目标；如果保留行数却换了用户，仍然错误；如果保留均值但改变缺失分布，也可能影响模型。因此等价验收至少比较键集合、逐键重数、字段值和缺失状态，必要时再比较确定排序。对于浮点聚合，应设有依据的容差并检查误差来源，不能把大差异一律归为舍入。

连接算法可以变化而语义保持。嵌套循环逐左行找右匹配，哈希连接按键组织一侧，归并连接利用有序输入；它们的适用条件、内存与排序成本不同。学习时应区分“连接类型”与“连接算法”：左连接属于结果定义，哈希连接属于实现策略。某个产品不提供某种算法，不会使左连接的概念消失。

## 3. 索引与执行计划：访问路径怎样影响成本

<a id="database-2-detail-10"></a>

### 3.1 从扫描到有序搜索结构

无索引时，为找一个少见键可能需要检查整张表。树形索引把有序键组织成多层结构，先定位范围再读取匹配项，理想化成本可以写成对数级定位加返回记录成本。但真实代价还包括页读取、缓存命中、回表、锁、可见性判断和结果传输。只写一个渐近式无法判断具体数据库里两毫秒与两秒的区别。

索引的键顺序与表行顺序也不是普遍相同。某些索引叶子存行引用，取非覆盖列还要访问表；覆盖索引包含所需列，可以减少额外读取，但会更大且写入维护更贵。索引是否覆盖必须相对于具体查询定义。把所有列塞进一个索引可能降低某个查询的读取，却提高每次更新成本，也可能挤占缓存。

对于很低选择性的条件，例如大部分用户都活跃，逐条通过索引回表可能比顺序扫描更贵。优化器决定不用索引不一定是故障。先看匹配比例、输出列与数据布局，再分析计划估计是否合理。如果计划基数估错，可能需要更新统计或改善相关性描述；不能只通过强制索引掩盖数据分布问题。

<a id="database-2-detail-11"></a>

### 3.2 复合索引的顺序与查询形状

复合索引可以按用户、时间排列。同一用户的记录相邻，用户等值之后可在其时间区间内查找，因此适合查询某用户最近订单。反过来只按全局时间筛选，不一定能像以时间为首列的索引那样直接定位。所谓最左前缀是重要工作模型，但不同引擎可能有跳跃扫描等优化，不能把简化规则当作所有计划的绝对边界。

范围条件之后的列仍可能用于过滤或覆盖，但未必进一步缩小连续搜索区间。索引还可能帮助排序，不过排序方向、缺失位置、排序规则和多个范围都会影响适配。正确设计方法是从实际查询的等值条件、范围条件、输出字段和排序要求出发，再用计划和测量验证，不是把高频出现的列随意排列。

在时间列上套函数有时会阻止使用普通索引范围，例如先提取月份再比较；改成原时间列的左闭右开范围，通常更容易表达访问区间，但前提是时区与日期含义一致。表达式索引也可能支持函数形式，具体依产品而异。任何为了性能的改写都必须先证明统计范围不变，否则只是更快地回答另一个问题。

<a id="sec-2-1"></a>

<a id="database-2-detail-12"></a>

### 3.3 索引不改变业务含义，也不是免费午餐

索引增加存储与维护，每次插入、删除和相关列更新可能需要修改多个结构。过多索引会放大写入、占用缓存并增加维护复杂度。训练特征场景往往既有批量写入又有大范围扫描，不能仅凭一次交互查询很快就给所有字段建索引。应根据主要工作负载选择，定期检查索引是否仍服务真实查询。

执行计划描述引擎打算或实际如何访问数据。不同产品的估计计划与带执行统计计划形式不同；SQLite 的查询计划输出适合观察扫描和索引使用，但文本格式不是稳定业务接口。本章不对完整计划字符串作断言，而只展示它，并用结果断言确认索引前后语义一致。性能测量则需要更大数据、重复运行和明确缓存条件。

一个查询变快但行数减少，不一定是优化成功。增加截断、改变连接类型、删除空值用户都可能使任务更轻，却改变目标总体。性能报告应同时展示等价验收与资源指标；对训练抽取，还应比较键、时间范围和覆盖率。逻辑正确性是性能优化的约束，而非一个可随意牺牲的指标。

## 4. 事务、并发与快照：三个层次分开理解

<a id="database-2-detail-14"></a>

### 4.1 原子性、一致性、隔离性、持久性

原子性要求一组事务修改整体成功或整体失败，例如转账的扣款与入账不应只保留一半。一致性常被概括为约束保持，但业务正确性还需要程序本身符合规则；数据库不会从两个金额字段猜出应保持怎样的总额。隔离性描述并发事务的可见性与相互影响，持久性描述已确认提交后的保存承诺，实际还受系统配置与故障模型影响。

回滚可以撤销尚未提交的数据库修改，却不能自动撤回已经发出的邮件或外部调用。因此将数据库操作和外部副作用放在同一段代码，并不使它们获得一个跨系统原子事务。可以采用事务内记录待发送事件、事务外可靠投递等协议，但需要处理重试和幂等。本章先建立边界，避免把事务上下文误当成包治所有并发与分布式问题的工具。

<a id="transaction-concurrency"></a>

<a id="database-2-detail-15"></a>

### 4.2 原子性不自动修复读取再写回

计数初值十，两个会话都读十，再各自把十一写回，在允许这种交错的协议里可能丢失一次增加。每个会话自身整体提交，也不意味着两个业务操作有正确串行效果。对于单行增量，直接让数据库执行基于当前值的增加，通常比应用读值后计算绝对新值更容易获得正确并发语义，但仍应核对数据库的锁和冲突规则。

另一种方式是乐观条件更新：读取值和版本，更新时同时要求版本仍是旧值，受影响行数为零就表示发生竞争，需要重新读取并重试完整业务决策。版本字段比只比较旧金额更可靠，因为金额可能变化后又回到原值。重试必须有边界、退避与幂等设计，不能在无限循环里假定最终总会成功。

涉及多行约束时，单行原子更新未必足够。例如两个值班医生都读取另一人仍在岗，于是分别离岗，每次只更新自己那行；最终无人值班。即使没有传统丢失更新，也可能违反跨行规则。这类写偏差需要更强隔离、锁定共同资源、约束重构或其他可证明协议。选择方法要围绕不变量，而不是只围绕某个异常名称。

<a id="database-2-detail-16"></a>

### 4.3 隔离级别名称不等于完整行为

在 PostgreSQL 的读已提交模式下，普通查询通常以语句开始时的可见状态为基础；同一事务中两次查询可能看到其他事务在两次之间提交的改变。可重复读提供更稳定的读取视图，但仍不应直接等同所有业务操作可序列化。可序列化要求结果可以对应某个串行顺序，冲突可能以事务失败呈现，应用必须准备回滚并重试整个事务。

SQLite 的并发结构与服务器数据库不同，写入者调度、日志模式和读快照都有具体规则。普通独立连接默认不会看到其他连接未提交修改；回滚日志与预写日志模式对读写共存方式也不同。不能把 SQLite 的串行写入机制描述成 PostgreSQL 的行锁模型，也不能用单连接演示声称验证了并发隔离。实验只对实际使用的连接、日志模式和语句作结论。

读取一致快照能使多张表来自同一个数据库视图，但并不保证它们在业务时间上同步。某个上游可能延迟半小时才更新状态，另一个实时写入，数据库视图内部仍可一致。快照一致性解决存储版本可见性，业务管道延迟与历史可用性仍需单独定义。不要把“同一事务读出”简化为“历史特征必然正确”。

<a id="deep-dive-2"></a>

<a id="database-2-detail-17"></a>

### 4.4 索引、事务、历史时点分别解决什么

索引回答从哪里和以什么代价找到行，事务回答哪些修改共同成功以及并发中能看到什么，历史时点规则回答当时模型能够知道什么。三者相互影响实现，却不能互相替代。对一年以前的样本使用今天最新会员等级，即使查询有索引、处于一致快照并且结果无重复，仍然可能泄漏未来。

审查时可分三张清单：结果语义检查身份、重数、缺失和范围；数据库协议检查提交、回滚、竞争、快照和重试；特征合法性检查事件时间、可用时间、版本和标签窗口。这里只是思考框架，不要求机械生成额外文档。关键是遇到异常时能定位哪一层失败，而不是把所有问题都归为数据库不稳定。

<a id="visual-02-advanced"></a>

### 图解：事务中的读改写也需要并发协议

![事务中的读改写也需要并发协议](images/02-advanced.svg)

假设两个操作分别扣减 10 和 20，却都先读取旧余额 100，再分别写回计算结果。在允许这类交错且缺乏正确并发保护的模型中，最终余额可能为 80，丢失了扣减 10 的影响。

这不是对所有数据库或隔离级别的行为断言。原子更新、行锁、乐观版本检查或可串行化协议会改变允许的执行；必须按实际引擎与事务语义验证。

## 5. 特征可用时间：当时发生与当时知道不同

<a id="database-2-detail-19"></a>

### 5.1 至少需要区分三条时间轴

事件时间说明事实何时发生，到达或可用时间说明系统何时能够使用它，抽取时间说明本次查询何时运行。一个一月三日的订单可能一月五日才补录；对一月四日的预测，它属于过去事件，却还不可用。仅筛事件早于预测时点，会让训练模型提前看到尚未到达的信息，线上无法复现这种优势。

标签则从预测之后的目标窗口定义，例如预测未来七天购买。特征窗口与标签窗口应明确边界，防止同一事件既影响标签又被错误当作预测前特征。还需考虑标签成熟时间：七天窗口结束不表示数据已经全部到齐，若来源延迟，应为评估等待足够时间，或明确未成熟样本如何处理。标签可见性与特征可见性是相关但不同的问题。

时间戳相等时采用严格小于还是小于等于，取决于预测调用发生在事件处理之前还是之后。统一写小于不一定总是业务正确，但它是常见安全边界；如果部署允许同刻已提交事件参与，就要保存足够精度或处理顺序。不能用粗粒度日期强行判断毫秒级先后，否则边界泄漏与重复计数难以诊断。

<a id="database-2-detail-20"></a>

### 5.2 补录、撤销与修订的历史重放

某条订单最初金额一百，后来更正为一千。历史训练如果只保留当前行，会把后来修订金额带回过去。除了事件时间与首次可用时间，还需要版本的可用区间，或一份可重建当时状态的变更日志。选择版本时应先限制到预测时点已知，再按版本规则选择最新，而不是先选今天最新版本再判断事件时间。

撤销和删除同样需要历史表达。今天记录不存在，不代表过去模型也看不到；今天状态已取消，不代表过去预测时已经知道会取消。若无法重建历史，只能承认历史回测的信息条件受限，或采用后续新采集的前瞻验证。重新运行一个完全正确的 SQL 也不能恢复从未保存过的旧状态。

可用时间的定义应贴近实际部署链。事件写进仓库但在线特征服务尚未刷新，模型仍不能使用；反之某项实时特征在线可用却没有回流仓库，离线重放可能缺失。离线与在线不仅要字段名相同，还要时间范围、更新频率、缺失规则和聚合代码一致。评估应检验这种条件一致性，而不是只比较两份表的列数。

<a id="database-2-detail-21"></a>

## 6. 历史维表与版本选择

<a id="database-2-detail-22"></a>

### 6.1 有效区间与可见区间

会员等级有效区间说明业务上哪段时间属于某等级，可见区间说明系统从何时开始知道这个版本。两者可能不同：三月十日补录“二月一日起升级”，业务有效时间是二月，但二月中旬模型尚不知道。若只按业务有效时间回连，便在历史训练中提前获知三月才收到的事实。需要根据研究目标选择事后真实状态分析还是当时可部署预测，两者不能混为一谈。

一种双时间设计同时保存有效起止和记录版本的可见起止，使用左闭右开区间减少相邻版本边界重复。一个样本只能选择在其预测时点业务适用且当时已知的版本；若多个满足，说明版本规则还需要优先级或约束。若一个都不满足，应保留缺失或定义回退，不能任意选择未来记录凑满。

历史表还应检查区间重叠、倒置、空隙和并列版本。简单要求同一用户起始时间唯一，不足以禁止区间重叠；简单取最大起始时间，也不证明前一个版本正确结束。产品可能提供范围约束等能力，通用流水线也可做显式检查。版本唯一性是保证一行一样本的关键，不应在最终宽表中用无条件去重隐藏。

<a id="database-2-detail-23"></a>

### 6.2 先合法，再最新，最后聚合

版本选择的顺序可以概括为先限制合法候选，再在候选中确定唯一版本，最后参与特征聚合。若先取最新再过滤可见时间，可能把旧合法版本一起丢掉，错误显示未知；若先聚合全部版本再筛时间，未来信息已经混入。顺序不仅决定效率，更决定能否得到当时真实可用的值。

这里的“合法候选”首先是按预测时点可见的版本，不能把所有业务条件都提前下推。若修订可以改变事件时间或删除状态，应先在可见版本中选出该事件的最新版本，再按所选版本的事件时间判断窗口、按删除状态决定是否贡献。

否则新版本已把事件移出窗口或标为删除，提前筛选却会留下旧版本，使事件错误复活。只有能证明某条件在同一事件的全部版本间保持不变时，才可提前用它限制候选；第 3 章将用完整样本重放实验验证这一顺序。

对同一事件的修订，也应按预测样本选择版本。一个事件可以对早期样本贡献旧金额，对后期样本贡献修订金额，这不是重复计算错误，而是不同预测时点拥有不同知识。实现时保留稳定事件号、版本可用时间和确定性版本号，才能区分“同一事件多版本”与“多个真实事件”。如果源头把版本身份丢失，后续很难正确重建。

<a id="visual-02-mechanism"></a>

### 图解：双时间约束：版本生效早不等于当时已知

![双时间约束：版本生效早不等于当时已知](images/02-mechanism.svg)

预测时刻 5 的版本选择同时受两个时间条件限制：版本已经生效，并且系统当时已经收到。v2 虽追溯到时刻 4 生效，但到 7 才到达；回放预测时不能把它作为当时已知事实。

这是双时间视角的最小例子。多个满足条件版本之间仍需定义取最新的排序和确定性裁决，删除、撤销与完整快照也需要单独约定。

## 7. 参数、并发协议与可复现抽取

<a id="database-2-detail-25"></a>

### 7.1 参数化只解决明确的一层问题

值参数绑定避免把字符串内容解释为语法，同时保留驱动对类型的处理。它不会自动验证时间范围合理、用户拥有访问权限或统计口径正确。表名和排序方向等结构选择应由受控映射产生，而阈值、状态与时间使用参数。实验中所有外部值都采用占位符，读者无需手写转义规则。

大规模分页抽取还需要稳定顺序和快照策略。若按偏移翻页，期间发生插入或删除，记录可能重复或遗漏；使用基于唯一有序键的游标式分页通常更容易保持进度，但如果排序字段会更新，仍可能发生跨页移动。快照能固定数据视图，却有资源成本。选择抽取协议要同时考虑一致性、可恢复性与数据库负担。

<a id="database-2-detail-26"></a>

### 7.2 提交成功、确认丢失与幂等

应用遇到连接中断时，可能不知道事务是否已经提交。如果盲目重试一次扣款或事件写入，就可能重复执行。业务操作应尽量有稳定幂等键，数据库在同一事务中检查或约束该键，重试时能识别已经完成的操作。仅在客户端生成一个新随机号再重试，反而会把同一业务行动变成两个不同操作。

训练抽取通常主要读取，但保存样本、写入特征快照和回填状态仍可能遇到相同问题。可以让输出批次有明确身份，采用完整批次替换或可验证追加协议，并在提交边界记录完成状态。不要把程序日志中打印了完成当作数据已经可用的唯一证据，也不要把没有打印完成当作数据库没有提交的证明。

## 8. 三组完整实验

<a id="sec-6-1"></a>

<a id="database-2-detail-28"></a>

### 8.1 左连接过滤与反连接的最小反例

以下程序同时包含有效订单用户、无订单用户、只有取消订单用户，以及具有空引用的脏数据。它不建立外键约束，目的就是让空引用进入反连接案例；与上一章受约束生产风格模式不同，这里是刻意构造的反例环境。所有预期输出都通过断言核对，连接在结束时关闭。

```python
import sqlite3
from contextlib import closing

with closing(sqlite3.connect(":memory:")) as db:
    db.executescript("""
    CREATE TABLE users(id INTEGER PRIMARY KEY);
    CREATE TABLE orders(id INTEGER PRIMARY KEY, user_id INTEGER, state TEXT);
    INSERT INTO users VALUES (1),(2),(3);
    INSERT INTO orders VALUES
        (10,1,'done'),(11,1,'cancelled'),(12,3,'cancelled'),(13,NULL,'done');
    """)
    on_rows = db.execute("""
        SELECT u.id, o.id FROM users u
        LEFT JOIN orders o ON o.user_id=u.id AND o.state='done'
        ORDER BY u.id
    """).fetchall()
    where_rows = db.execute("""
        SELECT u.id, o.id FROM users u
        LEFT JOIN orders o ON o.user_id=u.id
        WHERE o.state='done' ORDER BY u.id
    """).fetchall()
    patch_rows = db.execute("""
        SELECT u.id, o.id FROM users u
        LEFT JOIN orders o ON o.user_id=u.id
        WHERE o.state='done' OR o.id IS NULL ORDER BY u.id
    """).fetchall()
    assert on_rows == [(1,10),(2,None),(3,None)]
    assert where_rows == [(1,10)]
    assert patch_rows == [(1,10),(2,None)]
    has_order = db.execute("""
        SELECT u.id FROM users u
        WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id=u.id)
        ORDER BY u.id
    """).fetchall()
    no_order = db.execute("""
        SELECT u.id FROM users u
        WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id=u.id)
        ORDER BY u.id
    """).fetchall()
    bad_anti = db.execute("""
        SELECT id FROM users WHERE id NOT IN (SELECT user_id FROM orders)
    """).fetchall()
    assert has_order == [(1,), (3,)]
    assert no_order == [(2,)] and bad_anti == []
    db.executescript("""
    CREATE TABLE l(k INTEGER);
    CREATE TABLE r(k INTEGER);
    INSERT INTO l VALUES (7),(7);
    INSERT INTO r VALUES (7),(7),(7);
    """)
    assert db.execute(
        "SELECT COUNT(*) FROM l JOIN r ON l.k=r.k"
    ).fetchone()[0] == 6
    print("ON:", on_rows, "WHERE:", where_rows, "patch:", patch_rows)
    print("EXISTS:", has_order, "NOT EXISTS:", no_order, "NOT IN:", bad_anti)
```

结果展示三个不同总体，而不仅是不同空值布局。反连接中，不属于查询返回空结果，是因为子查询存在空值；不存在查询正确保留没有订单的用户二。注意本例有订单用户与有有效订单用户不同，存在子查询如果需要后者，应在子查询内加入有效条件。精确条件仍由问题决定，选择存在语法不会自动补足业务要求。

<a id="database-2-detail-29"></a>

### 8.2 索引前后同一结果与乐观更新

程序创建一万行数据，比较复合索引前后的计划和结果，并演示失败的多步业务修改如何回滚，以及版本条件如何发现过期写入。这里的版本冲突由顺序执行模拟，不声称运行了两个并发事务；它验证条件更新协议的核心判据，而不是某个服务器隔离级别。

```python
import sqlite3
from contextlib import closing

with closing(sqlite3.connect(":memory:", isolation_level=None)) as db:
    db.execute("CREATE TABLE events(id INTEGER PRIMARY KEY, uid INTEGER, t INTEGER)")
    db.executemany("INSERT INTO events VALUES (?,?,?)",
                   [(i, i % 100, i) for i in range(10000)])
    query = "SELECT id FROM events WHERE uid=? AND t>=? AND t<? ORDER BY t"
    params = (7, 2000, 5000)
    before = db.execute(query, params).fetchall()
    plan_before = db.execute("EXPLAIN QUERY PLAN " + query, params).fetchall()
    db.execute("CREATE INDEX idx_events_uid_t ON events(uid,t)")
    after = db.execute(query, params).fetchall()
    plan_after = db.execute("EXPLAIN QUERY PLAN " + query, params).fetchall()
    assert before == after and len(after) == 30

    db.executescript("""
    CREATE TABLE accounts(id INTEGER PRIMARY KEY, balance INTEGER NOT NULL);
    INSERT INTO accounts VALUES (1,100),(2,50);
    CREATE TABLE counter(id INTEGER PRIMARY KEY, value INTEGER, version INTEGER);
    INSERT INTO counter VALUES (1,10,0);
    """)
    try:
        db.execute("BEGIN")
        db.execute("UPDATE accounts SET balance=balance-30 WHERE id=1")
        raise RuntimeError("simulate failure before credit")
    except RuntimeError:
        db.execute("ROLLBACK")
    assert db.execute("SELECT balance FROM accounts ORDER BY id").fetchall() == [(100,),(50,)]

    old_value, old_version = db.execute(
        "SELECT value,version FROM counter WHERE id=1"
    ).fetchone()
    db.execute("UPDATE counter SET value=value+1,version=version+1 WHERE id=1")
    cursor = db.execute("""
        UPDATE counter SET value=?, version=version+1 WHERE id=1 AND version=?
    """, (old_value + 1, old_version))
    assert cursor.rowcount == 0
    value, version = db.execute("SELECT value,version FROM counter WHERE id=1").fetchone()
    assert (value,version) == (11,1)
    cursor = db.execute("""
        UPDATE counter SET value=?,version=version+1 WHERE id=1 AND version=?
    """, (value+1,version))
    assert cursor.rowcount == 1
    assert db.execute("SELECT value,version FROM counter").fetchone() == (12,2)
    print("rows:", len(after), "counter:", (12,2))
    print("before plan:", plan_before)
    print("after plan:", plan_after)
```

计划通常会从表扫描及排序转向索引范围访问，但具体文本依 SQLite 版本变化。这里不把某个计划字符串当正确答案，也没有对毫秒时间作夸大结论。程序运行在内存且数据很小，真实索引收益必须在代表性规模、字段宽度、并发和缓存条件下测量。唯一严格保证是本例索引前后结果完全一致。

回滚实验中账户余额保持一百和五十，说明尚未提交的扣款被撤销；它没有模拟断电持久性。版本实验先制造一次更新，再用旧版本条件写入，受影响行数为零，表示旧决策不能提交。随后重读并重算得到十二。实际并发协议还应把相关操作放进完整事务，并在冲突时重做全部决策，而不是只机械重复最后一句。

<a id="database-2-detail-30"></a>

### 8.3 事件时间与当时可见版本

最后一个实验以整数表示时间，避免日期解析干扰。样本时点为十，事件甲在五发生、六可用，后来在十二修订；事件乙在七发生、十一才到达；事件丙在十发生。采用事件与可用时间都严格早于十的协议，只有事件甲旧版本可用。程序对比当前值、仅按事件时间和完整时点规则的差异。

```python
import sqlite3
from contextlib import closing

with closing(sqlite3.connect(":memory:")) as db:
    db.executescript("""
    CREATE TABLE versions(
        event_id TEXT, version INTEGER, user_id INTEGER,
        event_t INTEGER, available_t INTEGER, amount INTEGER,
        PRIMARY KEY(event_id,version)
    );
    INSERT INTO versions VALUES
        ('A',1,1,5,6,100),
        ('A',2,1,5,12,900),
        ('B',1,1,7,11,200),
        ('C',1,1,10,10,300);
    """)
    cutoff = 10
    valid = db.execute("""
        SELECT v.event_id,v.amount
        FROM versions v
        WHERE v.user_id=? AND v.event_t<? AND v.available_t<?
          AND NOT EXISTS (
            SELECT 1 FROM versions n
            WHERE n.event_id=v.event_id AND n.available_t<?
              AND (n.available_t>v.available_t
                   OR (n.available_t=v.available_t AND n.version>v.version))
          )
        ORDER BY v.event_id
    """, (1,cutoff,cutoff,cutoff)).fetchall()
    assert valid == [('A',100)]
    current_past = db.execute("""
        SELECT v.event_id,v.amount FROM versions v
        WHERE v.user_id=? AND v.event_t<?
          AND v.version=(SELECT MAX(n.version) FROM versions n
                         WHERE n.event_id=v.event_id)
        ORDER BY v.event_id
    """, (1,cutoff)).fetchall()
    assert current_past == [('A',900),('B',200)]
    assert sum(x[1] for x in valid) == 100
    assert sum(x[1] for x in current_past) == 1100
    print("available at prediction:", valid, "sum:", 100)
    print("current rows with past event time:", current_past, "sum:", 1100)
```

这里把事件发生时间设为版本间不变，是实验的明确假设；如果事件时间也能修订，就需先按可见版本重建整条事件，再对该版本的事件时间筛范围，否则旧版本可能被错误保留。修订可以删除事件、改变用户归属或金额，真正版本系统需要把这些情况写入协议，不能把本例简化表视作完整生产设计。

第一种正确结果为一百，第二种错误历史重放为一千一百。差异不是模型更聪明，而是提前得知后来修订和补录。即使使用同一个数据库事务读取这张表，错误结果仍然错误；即使给所有时间列增加索引，也只会更快得到错误结果。这正是本章把访问路径、数据库视图和业务可用性分开验证的原因。

## 9. 快照实验与抽取协议

<a id="database-2-detail-32"></a>

### 9.1 两连接观察同一行的不同版本

下面确实使用两个独立连接，在临时目录中创建一个预写日志模式的 SQLite 数据库。读连接先开始事务并读取零，写连接提交一，再读连接在原事务内仍读零；读事务结束后重新查询得到一。临时数据库及日志在关闭连接后由临时目录自动清理，不会留在学习目录。若环境不支持指定日志模式，程序会明确失败而非假装验证成功。

```python
import sqlite3
import tempfile
from pathlib import Path
from contextlib import closing

with tempfile.TemporaryDirectory() as directory:
    path = Path(directory) / "snapshot.sqlite"
    with closing(sqlite3.connect(path, isolation_level=None)) as reader, \
         closing(sqlite3.connect(path, isolation_level=None)) as writer:
        mode = reader.execute("PRAGMA journal_mode=WAL").fetchone()[0]
        assert mode.lower() == "wal"
        reader.execute("CREATE TABLE value_store(id INTEGER PRIMARY KEY, value INTEGER)")
        reader.execute("INSERT INTO value_store VALUES (1,0)")
        reader.execute("BEGIN")
        first = reader.execute("SELECT value FROM value_store").fetchone()[0]
        writer.execute("BEGIN IMMEDIATE")
        writer.execute("UPDATE value_store SET value=1 WHERE id=1")
        writer.execute("COMMIT")
        second = reader.execute("SELECT value FROM value_store").fetchone()[0]
        reader.execute("COMMIT")
        third = reader.execute("SELECT value FROM value_store").fetchone()[0]
        assert (first,second,third) == (0,0,1)
        print("reader values:", (first,second,third))
```

这个实验验证指定 SQLite 模式下，一个已建立读取视图的事务保持该视图。它不证明任何读写混合业务都能成功，也不证明两个写入者可以无阻塞并行。读事务若试图基于旧视图升级为写事务，可能需要处理冲突；长时间读事务还会影响日志回收。把一个清晰实验限定在它实际观察的现象，才能避免从一个三元组推导出过强系统结论。

与 PostgreSQL 文档中的语句快照、事务快照和序列化冲突对照时，应把实验条件逐一列出：产品、日志或隔离设置、连接数、事务开始位置、第一条读取位置、写入提交位置与读取结果。这种时间线比笼统说“数据库支持隔离”更有信息。移植到新产品时重新实验，而不是只替换驱动名称后继续相信旧结论。

<a id="database-2-detail-33"></a>

### 9.2 一致快照与历史可用性如何组合

假设要抽取一百万条历史样本，数据库快照固定为今天中午。快照保证抽取期间对今天数据库状态的读取一致；每个样本仍需以自己的预测时间选择历史可见事件与版本。因此存在两个独立切点：抽取快照切点和样本信息切点。前者避免边读边变造成内部不一致，后者防止历史泄漏，二者不能互相取代。

如果来源不保存可见历史，固定今天快照最多保证今天可复现，不能保证去年可部署。此时可以把研究表述为使用事后校正数据的关联分析，或在未来启动前瞻数据采集，不能把缺乏记录的部分默认为正确。研究结论应匹配证据条件；精确时间戳和复杂查询都无法创造已经丢失的信息。

<a id="database-2-detail-34"></a>

### 9.3 大规模抽取的可恢复边界

一次长事务有助于视图稳定，却可能保持旧版本、占用资源或影响清理。分批抽取减少单次负担，但跨批次视图可能不同。可以选择固定数据快照、导出版本、稳定分区或适当的游标协议，具体依据产品能力和业务要求。重要的是说明所选择的一致性承诺，而非只报告任务最终跑完。

恢复时应知道哪些批次完整提交，哪些只是部分写出。若输出文件和数据库状态不在同一事务里，要采用可验证协议，例如先写临时目标再原子发布，或用批次清单说明完整性。此处不要求读者建立复杂平台，但即使一个简单练习，也应该避免把半份样本当作完整数据继续训练。可恢复性与逻辑正确性共同决定结果可信度。

## 10. 高阶方法比较与研究问题

<a id="database-2-detail-36"></a>

### 10.1 预聚合、相关查询与时点连接

预聚合适合多个样本共享固定时间范围的情况，可减少右侧行数；相关查询按每条样本应用不同时间条件，语义直接但成本可能高；历史时点连接可利用排序或索引批量处理版本选择，但实现与边界更复杂。比较方法时应让输出契约一致，再测量，不要因为一种方法天然容易写出未来信息，就误判它更高效。

如果样本时点密集，还可使用增量状态维护，但迟到事件和修订会使维护复杂。新增事件只需增加统计，撤销事件可能需要减去，求最大值在撤销当前最大元素后还需找次大值，去重计数则需保留频次。聚合函数是否可逆，决定增量特征能否仅保存一个标量。算法选择必须考虑更新模型，不只是首次批量计算。

<a id="database-2-detail-37"></a>

### 10.2 精确历史与事后真实状态

预测研究关心当时能知道什么，因果或业务核算研究有时关心后来确认真实发生什么。相同事件可能在两类研究中采用不同时间口径，这并非必然矛盾，但需要清楚命名。将“当时已知订单额”与“事后修订订单额”分成不同变量，可以避免一个方便的宽表被无意用于错误任务。

对标签而言，事后修订可能是更可靠真值；对特征而言，同一修订却是未来信息。因此不能简单禁止所有后来信息，也不能把全部后来信息都当作正确。先区分输入与目标，再定义各自的成熟和可见规则。评估报告应说明标签何时冻结，训练输入如何历史重放，才能让读者判断预测性能是否可部署。

<a id="database-2-detail-38"></a>

### 10.3 自动化检查应该覆盖哪些失效模式

一套有价值的检查应至少包含样本键唯一、目标总体覆盖、连接前后重数、版本候选数、事件及可见时间边界、标签窗口和基础数值范围。每项检查要能给出异常样本，而不是只返回失败。若一个样本匹配三个历史版本，应展示三个候选和时间区间，方便判断是数据重叠还是查询条件遗漏。

还可以加入反事实式输入扰动：在预测时点之后插入新订单，不应改变此前样本特征；在时点之前插入已知事件，应按定义改变对应样本；添加一个无关用户，不应改变其他用户的局部摘要。这样的变形测试直接检验信息依赖，比只比较某次固定结果更能发现泄漏路径，但仍需处理全局归一化等明确允许跨用户影响的特征。

## 11. 进阶练习与详细解析

<a id="sec-7-1"></a>

<a id="database-2-detail-40"></a>

### 11.1 题一：更快但用户更少是否是优化

**题目：** 将右表有效状态条件从连接条件移到后置筛选，查询更快且用户减少，能称为同一任务优化吗？

**解析：** 一般不能。原左连接保留无合格订单用户，后置筛选只保留至少有合格匹配的用户，统计总体发生变化。应包含有有效订单、无订单、只有取消订单三种用户做最小反例，再比较键集合、逐键重数和字段值。只有原任务本来就要求有有效订单用户，且其他语义也一致时，才可能把这种改写视为等价。性能比较应建立在已证明或充分验证的同一输出契约上，而不是只看运行时间下降。

<a id="database-2-detail-41"></a>

### 11.2 题二：左连接为什么仍会增加样本

**题目：** 左表每用户一条样本，右表每用户三条地址，左连接后样本数变三倍。为何保留全部左行仍不安全？

**解析：** 保留左行只保证每个左键至少出现，不保证只出现一次。每条左行匹配三条右行，训练损失会把它计算三次。需要按业务角色和预测时点选择唯一地址，或把多个地址聚合成定义明确的特征，再连接。如果任务确实要每地址一条样本，则应重写样本单位与标签含义。不能在最终表无条件去重，因为地址字段不同，去重可能不起作用；随意删列又会隐藏业务差异。

<a id="database-2-detail-42"></a>

### 11.3 题三：或者空值为何不能修复外连接

**题目：** 筛选条件写为有效订单或者订单号为空，是否等价于只连接有效订单并保留所有用户？

**解析：** 不等价。只有取消订单的用户先成功匹配取消订单，因此不会产生空扩展行；后置条件既非有效也非空，于是用户消失。只在连接条件中限定有效订单，取消订单不构成匹配，该用户才得到空扩展行并保留。这个反例说明外连接的补空发生在匹配判断之后，不能假设后置筛选会重新为被删匹配补一行。推理时逐行画出中间结果，比只看最终行数更清晰。

<a id="database-2-detail-43"></a>

### 11.4 题四：NOT IN 为什么可能全空

**题目：** 用户编号为一、二、三，订单引用为一、三、空值。不属于订单用户的查询为何找不到二？

**解析：** 对二而言，不等于一和不等于三都为真，但与空值的不等比较未知，合取不是肯定真，因此被筛掉。按用户条件寻找不存在匹配，能正确表达没有订单的用户二。也可在证明右侧引用非空后使用相应写法，但若未来模式允许缺失，证明前提就失效。代码审阅应检查这种约束，而不是把一种语法永久列为正确或错误；关键在具体输入域与三值逻辑。

<a id="database-2-detail-44"></a>

### 11.5 题五：反连接检查哪一列

**题目：** 左连接订单后检查金额为空，能找出没有订单的用户吗？

**解析：** 不能，因为有订单但金额未知的用户也满足。应检查匹配成功时保证非空的订单标识，例如非空主键；或者直接使用不存在子查询。若右表键本身可空，必须重新选择可靠匹配标志。一般原则是区分记录存在性和属性可观察性，两者不应由同一可空业务字段代替。模型特征中“没有订单”与“订单金额未结算”也有不同解释，应分别编码并检查覆盖率。

<a id="database-2-detail-45"></a>

### 11.6 题六：复合索引为什么顺序重要

**题目：** 用户与时间的复合索引适合某用户最近订单，是否同样适合查全部用户某一分钟订单？

**解析：** 不一定。前者用户等值固定后，时间区间在该用户范围内连续；后者没有固定首列，不同用户的时间段分散在索引中。引擎可能仍利用覆盖或其他优化，但不能假定成本与时间首列索引相同。应比较实际计划、匹配比例、输出字段和写入成本。索引选择来自工作负载，而非一个列排序口诀；如果两种查询都重要，也要考虑是否值得维护两个索引及其资源代价。

<a id="database-2-detail-46"></a>

### 11.7 题七：原子更新解决哪些问题

**题目：** 将应用读取计数后写回，改为数据库原地加一，是否保证所有并发业务正确？

**解析：** 对单行增量，它通常避免基于过期值覆盖的新问题，但不能自动保证跨行约束、外部副作用或整个业务可序列化。两个医生分别离岗仍可能破坏至少一人值班规则，邮件发送也不随数据库回滚。应先写出业务不变量，再选择锁、条件更新、隔离或协议。数据库支持原子算术表达式是有用构件，不是完整并发证明。测试也要覆盖多行交错，而不只检查最后计数。

<a id="database-2-detail-47"></a>

### 11.8 题八：版本条件失败应该重试哪里

**题目：** 乐观更新受影响行数为零，只重复最后一条更新直到成功是否合理？

**解析：** 若继续使用旧决策和旧版本，可能一直失败；若只替换版本但不重算业务，又可能提交不再合法的决定。应重新读取相关状态，重做完整决策，并在必要事务边界内执行，控制重试次数和退避。若操作包含外部副作用，还需幂等键或可靠投递协议。冲突意味着原先依据已经变化，应当重新验证依据，而不是把失败当作暂时语法问题机械重放。

<a id="database-2-detail-48"></a>

### 11.9 题九：可重复读是否等于可序列化

**题目：** 事务中两次读取同一行不变，能否证明业务结果可对应某个串行执行？

**解析：** 不能。稳定读取只描述部分可见性，跨行写偏差等仍可能使联合结果无法满足预期串行语义。产品的隔离实现和异常检测各有规则，必须查官方文档并设计具体交错。可序列化也可能通过使部分事务失败来实现，应用要处理整体回滚重试。不能只以事务没有报错、两次读相同作为充分证据。应明确不变量、冲突对象和失败处理，才能评价协议正确性。

<a id="database-2-detail-49"></a>

### 11.10 题十：过去事件为什么仍可能泄漏

**题目：** 事件在五发生、十一可用，样本时点为十。筛事件早于十为何不够？

**解析：** 它满足过去发生，却不满足当时可知。训练使用该事件会提前获得部署无法使用的信息。应按照实际部署链的可用时间限制，并考虑仓库到在线服务的刷新延迟。若只保存事件时间而没有可用历史，就无法严格重放这种条件，应补采或收缩结论。记录一个叫历史订单的字段不意味着它自动合法，历史性必须由信息时间关系证明，而不是由命名证明。

<a id="database-2-detail-50"></a>

### 11.11 题十一：先选最新再筛可见为什么错误

**题目：** 事件版本一在六可用，版本二在十二可用，预测时点十。先取最新版本再筛可用时间会怎样？

**解析：** 最新版本二被选中后因十二不早于十被删除，版本一已在前一步丢失，结果错误地显示没有事件。正确顺序是先限制可见版本，再在其中选择最新，得到版本一。若事件时间也能修订，应重建整条可见版本再筛事件范围，不能让旧版本因字段条件不同而漏入。版本选择与范围筛选的顺序取决于哪些字段可变化，必须写进数据模型假设。

<a id="database-2-detail-51"></a>

### 11.12 题十二：一致快照能否防止未来会员等级

**题目：** 在同一事务中读取去年样本和今天用户等级，是否已经避免泄漏？

**解析：** 没有。同一数据库快照仅保证今天读取视图一致，今天等级仍可能来自去年预测之后的升级。要按样本时点连接当时适用且当时已知的历史版本。若表只保留最新状态，快照无法恢复旧等级。应明确抽取时点与样本信息时点是两个独立概念，并分别验证；索引与隔离无论多完善，都不能修复缺失的历史语义。

<a id="database-2-detail-52"></a>

### 11.13 题十三：标签为什么可以使用后来信息

**题目：** 未来七天购买是标签，为何可以使用预测后的订单，而同样订单不能作为特征？

**解析：** 标签定义预测要回答的未来结果，特征定义作答时可用信息，两者角色不同。预测之后的事件正是标签材料，却不能提前进入输入。标签还需要成熟时间和修订规则，避免把尚未到齐记录误认为未购买。训练数据应分别保存预测时点、特征窗口、标签窗口与标签冻结时点。禁止全部未来数据会让监督目标无法构造，允许未来信息进入所有列又会造成泄漏，必须按角色判断。

<a id="database-2-detail-53"></a>

### 11.14 题十四：怎样测试未来数据不会改变过去特征

**题目：** 不知道完整正确特征表，怎样用扰动测试发现时间泄漏？

**解析：** 先固定过去样本结果，再插入预测之后发生或之后才可用的事件，重新抽取，过去特征应不变；再插入预测之前发生且可用的合法事件，特征应按定义变化。对版本表，还可新增未来修订，检查早期样本仍使用旧版本。测试需控制全局统计等允许跨样本依赖的特征，不能机械要求所有列永远不变。把变化范围作为契约，能更直接地验证信息依赖路径。

<a id="database-2-detail-54"></a>

### 11.15 题十五：为什么查询快照也需要资源设计

**题目：** 为保证抽取稳定，让读事务持续一天是否总是最好？

**解析：** 不一定。长事务可能保持旧版本、影响日志回收或占用其他资源，具体影响依产品。应根据一致性要求选择固定导出、版本化快照、分区或可恢复分批方案。分批方案又要处理跨批视图变化与游标移动，不能只把事务拆小便宣布正确。工程设计需要明确承诺和代价，并在代表性规模测量。逻辑一致与系统可承受共同决定可用方案，单一指标最优不等于完整任务最优。

<a id="database-2-detail-55"></a>

## 12. 章节验收与后续学习

完成本章后，应能对一个宽表生成任务同时回答四个问题：最终键是什么，连接是否复制它，数据库读取视图怎样固定，每条输入何时可用。只要其中一个无法回答，就不宜仅凭模型分数高或查询运行快判断流程可靠。对最小反例的解释应在性能优化之前完成，之后再用执行计划、索引和批处理改善成本。

进一步研究可从可串行化历史、增量视图维护和双时间数据模型进入。每个方向都先写明确不变量，再设计两个或三个操作的交错，最后验证实现。数据库学习的深入不在于记住更多隔离名词，而在于能够说明某个协议为何在给定故障、并发和时间条件下保持业务事实；条件变化时，也能准确指出原结论失效的位置。

<a id="database-2-detail-56"></a>

### 12.1 批量回填与在线计算的同构检查

离线回填常用 SQL 扫描整段历史，在线服务可能按事件增量维护。两者即使字段名相同，也可能在迟到事件、取消订单和时区边界上不同。应给两条路径输入相同的小事件流，按每个预测时点比较输出，而不是只比较最后一天总额。中间状态不同却最终总额相同，仍会影响历史样本与真实预测。

测试流应包含正常到达、迟到、重复投递、金额修订、取消和同刻多事件。对重复投递，稳定事件键应使状态只增加一次；对修订，应按版本规则替换旧贡献；对过期窗口事件，应正确移出统计。如果在线协议根本不回溯处理迟到事件，离线训练也不能默默使用更完整历史，除非明确接受这种信息条件差异并在验证中测量其影响。

<a id="database-2-detail-57"></a>

### 12.2 将时间边界作为数据类型思考

一个时间戳只有数值还不够，必须知道它代表事件发生、首次到达、版本可见还是业务有效时间。可以把这些角色看作不同的语义类型，即使底层都存同一种时间格式，也不允许随意替代。代码审查时检查参数名称和连接条件是否使用正确角色，能发现许多语法上完全合法的泄漏。数据字典若只写日期类型而不写时间角色，信息仍然不足。

时间区间也应带清楚的闭开规则。相邻窗口使用左闭右开能避免同一边界事件被两窗重复纳入，但前提是各路径采用同一时区和精度。对于按本地日历定义的一天，夏令时变化可能使实际时长不同，不能总用固定秒数代替日历边界。学习时先用整数时间隔离概念，再在真实系统中显式处理日历、时区和精度，是更稳健的推进方式。

<a id="database-2-detail-58"></a>

### 12.3 证据范围与研究结论保持一致

本章实验能够验证小表的确定性连接结果、索引前后相同输出、顺序版本冲突判据，以及指定日志模式下的双连接读取视图。它没有测量高并发吞吐、故障恢复或大型时点连接的复杂性能。要研究这些问题，应扩大实验设计并控制变量，而不是从现有程序的成功运行直接外推。清楚列出证据边界，能让后续研究逐步增加可信度，也使读者知道还应补充哪些实验。
