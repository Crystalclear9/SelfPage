## 1. 表、关系与键：先确定一行代表什么

<a id="database-1-detail-2"></a>

### 1.1 从现实对象到关系模式

数据库中的表并非随意排列的电子表格。它表达一种关于世界的陈述，例如订单表的一行可以表示“某个订单属于某位用户，发生于某时，金额为某数”。列的名字和类型规定陈述的结构，约束规定哪些陈述允许出现，行则给出某次观察或某个对象的具体事实。先确定这层含义，再考虑查询语法，才能避免把用户、会话、商品和交易等不同单位混成一个样本。

关系模式描述属性及其约束，关系实例描述某一时刻已有的元组。数学关系通常作为集合处理，元组没有位置，属性通过名称或约定位置识别，完全相同的元组不会出现两次。实际 SQL 查询默认采用多重集语义，允许输出重复行；实际表还允许缺失标记，并有数据类型、排序规则和事务版本等实现因素。因此，关系代数提供推理工具，但必须明确哪些集合定理仍适用于当前 SQL 表达式。

例如，一个用户可以有十笔订单，一个订单可以有三个商品明细。如果建表时把“一行一个订单”写清楚，订单号应当唯一；若实际一行一个明细，订单号重复就是正常结构，此时主键需要明细号，或者订单号与行号的组合。不能看到重复订单号便立即删除，也不能看到一个新编号便相信它对应独立业务事件。数据粒度是业务事实，数据库编号只是表达和检查事实的手段。

训练样本也有独立粒度。预测用户下周是否购买时，样本可能是一对“用户、预测日期”，并非用户本人。一个用户在不同周出现多次可以合理，但同一天因订单连接产生五份同样样本，通常会意外改变权重。将最终样本键写在查询设计的第一页，后续每次投影、筛选、分组和连接都要回答：这个键还存在吗，还是已经被聚合成另一种单位？

<a id="database-1-detail-3"></a>

### 1.2 超键、候选键与主键的区别

超键是一组能唯一识别元组的属性，候选键是去掉任何属性后就不再能保证唯一的最小超键。主键是在候选键中选定的主要标识。例如，若学号唯一且学校内部邮箱也唯一，它们可能各自构成候选键；把学号和姓名一起使用仍然唯一，却不是最小的，因为姓名可以删掉。键的最小性是逻辑属性，并不意味着字符串长度最短或存储开销最小。

唯一性应来自所有合法数据的规则，而不是当前小样本恰好没有重复。今天用户姓名没有重名，不证明姓名可以当用户键。反过来，某个外部系统承诺事件编号唯一，导入后出现重复，可能说明重试、数据损坏或版本规则未处理，应先调查规则。把“目前观察到的唯一”当作“永远必须唯一”，容易使系统在数据增长后突然失败。

主键通常要求唯一且非空；外键表达引用完整性，即非空引用应能找到被引用对象。唯一约束与缺失标记的交互、复合外键中部分空值的处理等细节具有产品差异，因此不能只记一个抽象口号。SQLite 实验会显式打开外键检查，并把业务必需的列标为非空；这样反例失败是因为约束真的执行，而不是只在建表文本里写了一个漂亮声明。

自然键由业务属性组成，例如有稳定定义的证件编号；代理键由系统产生，例如整数编号。代理键能使引用更短、减少业务字段变化的影响，却不能自动阻止同一对象被重复导入。若每次导入都生成新编号，同一个真实事件仍会出现两次。可靠设计往往同时需要代理主键与业务唯一约束，并记录外部来源、来源编号和版本等去重依据。

<a id="database-1-detail-4"></a>

### 1.3 基础算例：同一张表中计行与计已知值

金额为十、缺失、二十的三条记录，行数为三，已知金额数为二，已知金额的均值为十五。这三个数的分母不同。若把缺失解释为零，平均变成十；如果缺失意味着尚未结算，零就不是事实，而是人为填补。查询结果不应只给一个均值，应同时展示总体规模和观测覆盖率，否则读者不知道该数描述多少对象。

假设两座城市的已知均值分别是十与二十，却分别只有一笔和九笔已知订单。直接平均城市均值得到十五，逐订单平均得到十九。两者都能计算，区别在于每座城市等权还是每笔订单等权。数据库不会替你选择科学问题。先给出总体、观测单位、可用值规则和权重，再决定聚合表达式，能避免后续建模将不同问题误认为一个指标。

<a id="database-1-detail-5"></a>

### 1.4 约束既是防线，也是推理的前提

非空约束表达必需信息，检查约束表达域内规则，唯一约束表达标识规则，外键表达跨表引用。它们能把错误尽早暴露，但不能表达全部业务含义。例如金额非负并不保证币种一致，时间格式合法并不保证时区正确，用户编号存在也不保证订单属于正确的人。数据库约束负责可精确执行的部分，其他规则需要导入校验、审计和业务定义共同完成。

检查约束遇到未知值时的规则容易被误解。若只声明金额大于等于零，空值可能不被拒绝，因为条件并未成为假；若金额必须出现，应另外加非空约束。不要让读者以为“合法区间”自动包括“必须有值”。在概念模型中分别列出“是否允许缺失”和“出现时允许什么取值”，再映射到实际数据库声明，表达会清楚得多。

约束还支持查询证明。如果订单号唯一且外键有效，订单连接用户表时，每笔非空用户引用最多匹配一行；没有这种前提，连接可能复制订单。优化器也可能利用部分约束改写查询，但学习时先从逻辑上证明基数，不要假定所有引擎都执行相同优化。约束是否启用、是否验证历史数据、是否允许延迟检查，都应属于运行环境说明。

### 图解：WHERE 与 HAVING 的统计对象

![WHERE 与 HAVING 的统计对象](images/01-concept.svg)

**图解。** 比较同一组金额 40、160 的两条执行路径：先过滤金额大于 100 的行再平均，结果为 160；先求组平均得到 100，再要求平均严格大于 100，则整组消失。

## 2. 从自然语言到查询的逻辑流水线

<a id="database-1-detail-7"></a>

### 2.1 写查询前先写统计契约

考虑需求：“找出一月已完成订单至少两笔的用户，按已知订单金额总和降序排列。”其中最终单位是用户，原始单位是订单，月份用订单发生时间定义，合格条件是已完成，计数包括金额未知的合格订单，总额则只累计已知金额。最后一句若未明确，就有人会以为金额未知订单不计入两笔门槛。精确的自然语言能提前消除这种分歧。

一个简洁的统计契约应写明输出键、输入范围、事件时间字段、状态口径、缺失规则、分母、并列排序规则，以及结果为空时如何解释。它不需要变成冗长行政文档，可以只有一段话。但这些信息必须在某处存在，否则同一段 SQL 被另一个人复用时，变量名看起来一致，实际含义已经改变。训练数据的标签口径也应采用同样方式明确。

```sql
SELECT
    user_id,
    COUNT(*) AS completed_orders,
    COUNT(amount_cents) AS known_amount_orders,
    SUM(amount_cents) AS known_total_cents
FROM orders
WHERE created_at >= :start_time
  AND created_at < :end_time
  AND status = :completed_status
GROUP BY user_id
HAVING COUNT(*) >= 2
ORDER BY known_total_cents DESC, user_id ASC;
```

这里的参数写法对应本章 Python 驱动示例，其他驱动的占位符可能不同。日期条件使用左闭右开区间，避免把月底写成某天午夜而漏掉当天其余时间。文本日期只有在统一格式、统一时区并保留足够精度时才适合直接按字典序比较；真实数据库宜选明确的时间类型和时区约定，不能从这个简化示例推出任意日期字符串都能比较。

### 2.2 WHERE 与 HAVING 分别过滤什么

可把查询理解为先形成输入行，再筛选行，随后形成分组、计算聚合并筛选组，最后生成输出列、处理去重和排序等。这个顺序是解释语义的模型，不是数据库必须逐步物化的程序。优化器可以利用索引、谓词下推和不同连接算法，只要保留规定结果；实际执行快慢与逻辑处理顺序不是同一个问题。

订单为四十、一百六十的用户，先保留金额大于一百的订单再平均，得到一百六十；先对全部订单平均再要求均值大于一百，均值恰好一百，严格大于条件不通过。一个查询回答“大额订单自身有多大”，另一个回答“哪些用户的整体均值较大”。把条件从筛行移动到筛组，相当于换了问题，不能作为语法美化处理。

分组条件有时能合法提前，例如按城市分组后只保留某座城市，在城市字段不被其他表达式改变的前提下，可以先筛这座城市再聚合。但是按组总额筛选不能通常化成逐行金额筛选。证明改写是否正确时，要逐项检查条件依赖哪些列、聚合是否会看到不同输入，以及未知值如何传播，不能凭条件文本相似就认为等价。

<a id="database-1-detail-9"></a>

### 2.3 逻辑阶段怎样决定统计总体

从输入行集合开始，筛选决定纳入总体，分组决定统计单位，聚合决定每个单位的摘要，组筛选决定报告对象，排序决定呈现次序。每一个阶段都能让某些信息不可恢复。订单号在分组时被丢弃后，外层通常无法再准确统计原始订单；先去掉未知金额用户后，无法从剩余行恢复所有原始用户的覆盖率。

一个实用方法是为中间结果写“小型模式”。例如第一步为合格订单，键是订单号；第二步为用户订单摘要，键是用户号，包含合格行数和已知金额数；第三步为达到门槛的用户摘要。这样每一步都有可检查的唯一键和行数上界。公用表表达式可以帮助表达这些阶段，但语法上的分块不保证引擎真的按块保存，也不自动保证逻辑正确。

<a id="database-1-detail-10"></a>

### 2.4 别把 SELECT 别名当成任意阶段变量

不同产品对输出别名在筛选、分组和排序中的可用范围有差异。为避免依赖扩展语法，复杂派生列可以先放入子查询或公用表表达式，再在外层引用。例如先算每用户总额，再在外层筛总额，这既明确阶段，也减少把聚合别名错误放入原始行筛选的机会。可移植性来自明确语义与验证，而不是只使用看起来常见的词。

聚合查询中选择一个既未分组也未聚合的普通列尤其危险。部分数据库拒绝，部分在特定函数依赖成立时允许，SQLite 还有其自身对裸列的处理规则。本章不使用这类模糊写法。若要“总额最高订单的发生时间”，不能简单同时选择最大金额与发生时间并期待它们自动来自同一条确定记录；应该明确挑选整行，并定义并列情况。

## 3. NULL 与三值逻辑：缺失如何穿过查询

<a id="database-1-detail-12"></a>

### 3.1 UNKNOWN 的真值运算

普通比较遇到空值通常得到未知。例如未知金额是否大于十，既无法肯定也无法否定。筛选只保留真，因此未知行会被过滤。逻辑否定不会把未知变成真，所以“大于十”和“不大于十”不能共同覆盖包含缺失的全部记录。若要完整划分，应另设缺失分支，而不是假设两个条件互为补集。

三值逻辑的合取与析取可以从信息解释得到：假与未知的合取必为假，因为已有一个假足够否定整体；真与未知的析取必为真，因为已有一个真足够肯定整体；真与未知的合取仍未知，假与未知的析取仍未知。这个规律解释了条件组合为什么有时保留未知行，有时不保留，但不保证表达式按从左到右短路执行。

例如条件“金额大于十，或者金额为空”会保留大额记录和缺失记录；条件“金额不等于十”不会保留缺失记录。业务说“不是已取消订单”时，状态未知是否也要纳入，必须明确。写成不等于已取消往往只保留已知且不同的状态。状态未知与已知未取消是两个事实，若部署时处理方式不同，训练查询也应分别表达。

<a id="database-1-detail-13"></a>

### 3.2 比较相等、去重相同与分组相同

空值与空值使用普通等号比较仍不产生真，但分组和去重会按相应规则把缺失放入共同类别。不要由此得出数据库自相矛盾：等号在回答两个未知事实是否相等，分组需要决定缺失记录如何归类，这是不同操作的约定。在需要把缺失视为相同键进行比较时，某些数据库提供专门的空值安全比较语法；使用前应核对具体实现。

若分组列是城市，城市未知的用户可能汇入一个缺失组。这个组不代表真实世界存在一座“未知城”，只是当前资料无法区分它们。把缺失组当作普通地理类别训练，可能学习到采集流程或来源差异。可以把缺失指示作为独立信号，但应通过验证判断其稳定性，并在数据字典中说明该列的实际含义。

空字符串、数字零、字符串零和空值也不是同一概念。某些产品对空字符串有特殊规则，SQLite 中空字符串与空值不同。跨系统导入时，文本文件中的空白字段还可能由解析器改成缺失。排查时应沿着原文件、解析结果、数据库存储和模型输入四个阶段检查，而不是只在最后一张表里看展示出来的空白。

<a id="database-1-detail-14"></a>

### 3.3 缺失的统计含义比语法更重要

假设高额交易更容易因人工审核而暂时缺失金额，那么已知金额平均值可能系统性偏低；若低额交易更容易漏报，则可能偏高。数据库给出的十五只是已观察值的算术平均，不能自动推断完整总体均值。即使完全掌握三值逻辑，也仍需理解缺失机制，并考虑补采、分层分析或明确的不确定性说明。

把缺失填成零可能适合“没有发生购买”这种结构性零，却不适合“购买发生但金额未知”。二者都可能在导入表中表示为空，但正确处理方式不同。最好在数据模式中将状态拆清楚，例如是否发生、金额是否已知、金额数值和缺失原因，避免一个空值承担多种无法区分的业务含义。后续特征处理才有可解释的依据。

<a id="visual-01-mechanism"></a>

### 算例：NULL 的三值逻辑会改变筛选结果

| x | x > 0 | NOT(x > 0) | WHERE 保留条件 |
| --- | --- | --- | --- |
| 2 | TRUE | FALSE | 第一列条件保留 |
| −1 | FALSE | TRUE | 取反条件保留 |
| NULL | UNKNOWN | UNKNOWN | 两个条件都不保留 |

WHERE 只保留结果为 TRUE 的行。NULL 的比较得到 UNKNOWN，取反后仍然是 UNKNOWN；因此用“正数条件的取反”并不能自动得到包含缺失值的全部补集。

需要纳入缺失值时，应明确写出 IS NULL 等分支。这里展示标准三值逻辑，不把 NULL 当成零、空字符串或一个普通可比较数值。

## 4. 聚合、权重与分母：每个指标必须解释对象

<a id="database-1-detail-16"></a>

### 4.1 COUNT、SUM 与 AVG 的边界

数行、数非空值、数不同非空值，分别回答记录数量、可观察数量和已知不同取值数量。若订单号重复，数行可能是明细数；若金额重复，数不同金额更不是订单数。聚合前先标记单位，再读函数名，否则同一个“数量”字段在报表、训练和实验评估中会被赋予不同含义。

对一个没有输入行、且没有分组的聚合查询，计数通常仍返回零，而求和与均值返回空值；有分组而不存在相应组时，结果可能根本没有那一行。这三种情况分别是“存在一个总体，观测数为零”“总体摘要不可计算”“根本没有生成该组”。要给所有用户输出零订单，必须先有用户总体再连接摘要，不能期待订单表自己产生从未出现的用户。

数学上已知金额均值可写成已知值之和除以已知个数。分母为零时均值未定义；业务若要求显示零，应把“计算值未定义”和“展示缺省值”分开记录。尤其不要先填零再平均，却在文档里仍称其为已知金额平均。命名可以长一点，因为列名承担了统计解释的一部分，例如已知订单金额均值就比平均值更清楚。

<a id="database-1-detail-17"></a>

### 4.2 条件聚合与指标覆盖率

同一用户需要同时统计全部订单、已完成订单、已知金额订单时，分别查询再拼接容易产生口径差异。条件聚合能在同一输入范围内表达多项计数。例如满足条件时贡献一，否则贡献零，可以计算合格行数；满足条件时贡献金额，否则贡献空值，可以计算合格且已知的金额均值。这里的否则值会直接决定分母，不能随手替换。

条件成立时金额仍可能为空，因此“满足条件的行数”与“条件成立且金额已知的行数”依然不同。若计算合格率，应先定义分母是否包含状态未知记录。假设十条记录中四条合格、四条不合格、两条未知，四除以十表示全体中已确认合格比例，四除以八表示已知状态中的合格比例；它们不能在同一图表中无说明地比较。

覆盖率也应与指标一起输出。均值变化可能来自金额变化，也可能来自已知比例下降；若只看均值，两种机制难以分辨。可以同时报告行数、已知数、缺失数、已知和及已知均值，必要时按来源或日期分层。这样数据库输出已经包含基本诊断信息，后续模型监控不会被一个孤立数字误导。

<a id="database-1-detail-18"></a>

### 4.3 平均的平均与合并统计

设第一个组有一个已知值十，第二个组有九个已知值二十。组均值等权平均为十五，按样本数加权的整体均值为十九。要合并分片均值，必须同时保存有效个数；只保存均值无法辨认一个组有一行还是一万行。若各分片还对空值采用不同规则，即使保存行数，也可能不是正确权重。

求和与计数容易进行分布式合并，均值则应通过和与计数合并。不同值计数更复杂：两个分片分别有同一个用户，直接加不同用户数会重复计算；需要合并集合或采用带误差说明的近似算法。数据库函数能否拆分，与它输出一个标量无关，而与是否存在足够的可合并中间状态有关。这也连接到大规模特征流水线的设计。

比率合并同理。各城市的转化率平均，给城市等权；总转化人数除以总曝光人数，给曝光等权。如果用户在一天多次曝光，分母又可能是曝光次数而非用户数。选择哪一种取决于业务目标，不能因为某个查询更短就选它。先写出分子和分母对应的事件或对象，再考虑查询可以有效减少语义漂移。

<a id="visual-01-advanced"></a>

### 图解：AVG 的分母不包含 NULL

## 5. 类型、规范化与数据契约

<a id="database-1-detail-20"></a>

### 5.1 类型是语义的一部分

金额建议用最小货币单位的整数，或精确定义精度的小数类型表达，避免用二进制浮点承担精确记账义务。整数也有范围限制，长期累计或错误单位可能溢出；不同币种更不能直接求和。数值列应同时有单位定义，必要时保留币种与换算时间，模型特征也要记录转换规则，不能只在列名中写金额而省掉这些背景。

文本标识符不应因为看起来像数字就转成整数。邮政编码可能有前导零，账户编号可能超过常见整数范围，商品编号可能包含大小写有意义的字母。排序规则还会影响字符串比较、分组与唯一约束。若两个系统对大小写或重音的处理不同，表面相同的连接条件可能得到不同匹配，跨库迁移应加入专门测试。

SQLite 采用其自身的类型亲和及存储规则，不能把它当作严格类型数据库的普遍替身。本章实验使用明确的整数和文本输入，避免借助隐式转换“刚好得到结果”。在生产系统中，应查清类型声明是否严格执行、算术如何转换、除法是否截断，以及无效日期如何处理。将错误字符自动转成数值零，会比直接报错更难发现。

<a id="database-1-detail-21"></a>

### 5.2 函数依赖与更新异常

若用户号决定城市，却在每条订单记录里重复当前城市，用户搬家时要更新多行；漏改一行就出现同一用户多个当前城市。没有订单的新用户也可能无处保存，删除最后一笔订单又可能丢失用户信息。这分别体现更新、插入和删除异常。把用户实体与订单事件分开，是让每项事实有明确归属。

函数依赖表示某组属性相同就应决定另一组属性相同。它来自业务规则，并受时间范围限制。“用户决定城市”若指当前地址可能成立，若用户可以保留多地址或需要历史城市就不成立。规范化设计必须先把有效时间、地址角色等因素纳入键，不能用当前报表的偶然规律代替完整业务规则。

规范化不是把表拆得越碎越好，而是消除不应由多处独立维护的重复事实。分析宽表则为特定样本单位组织可读取特征。来源层可以规范化，分析层可以有意反规范化，但宽表应能追溯来源、转换和时间口径。只保留最终宽表会丢失解释错误所需的信息，只保留来源表又无法直接表达训练样本，两层各有职责。

<a id="database-1-detail-22"></a>

### 5.3 模式演化不能悄悄改变指标

新增列、改变状态枚举、扩大数值范围、调整时区或把空值改成默认值，都可能改变查询含义。使用星号选择所有列便于临时探索，但固定训练数据应显式选择字段，避免新列无意进入特征或改变导出顺序。标签字段尤其要在列清单中被明确控制，否则一次模式变化就可能把答案直接带入输入。

数据契约应记录列类型、单位、允许值、缺失含义、键、时间字段和版本。变更时先判断是向后兼容扩展，还是需要新版本。若状态从“完成”拆成“支付完成”和“交付完成”，旧查询不能只靠字符串替换继续运行，因为原业务含义可能已不再对应某个单一状态。需要用旧新样本对照检查统计口径。

## 6. 关系代数、多重集与等价改写

<a id="database-1-detail-24"></a>

### 6.1 用重数而不只是集合想问题

可把一个 SQL 中间结果看成“元组到出现次数”的映射。筛选保留满足条件元组的重数；不带去重的投影把映射到同一输出元组的重数相加；连接把每对匹配行的重数相乘，再对相同输出求和。这样就能解释为什么只删掉一列，行数通常不变，而去重可能使其下降。

假设两条不同订单金额都为一百，只投影金额会得到两行一百；加去重后只剩一行。若接着求和，从两百变成一百。投影后金额相同不意味着订单相同，去重消除的是输出表示相同的行，而不是自动识别业务重复。正确去重应在保留业务键和版本规则的阶段完成，不能在信息已经丢失后凭数值补救。

合并两个时间区间的数据也要区分保留重复与集合并。如果两个区间本来互斥且记录唯一，直接合并便合理；若边界重叠或数据有重放，去重集合并可能消除部分重复，却也可能合并真实不同事件。选择操作前先知道每条记录的身份，不要把集合操作当作数据清洗的通用替代品。

<a id="sec-6-1"></a>

<a id="database-1-detail-25"></a>

### 6.2 哪些变换需要证明前提

两个确定性、无副作用的筛选通常可以交换，因为最终都要求同时满足条件；但表达式可能报错、依赖易变函数或具有产品特定求值行为时，不能依赖某个筛选先执行来保护另一个。比如先筛分母非零，再做除法，不应只靠文本顺序保证安全，可以在表达式内部用明确的零分母处理来表达定义。

筛选可以穿过投影的前提是投影保留了所需信息，或条件可以被正确改写。按城市筛选后只取用户号，与先只取用户号再按城市筛选，后者已经没有城市列。聚合下推则需要更强条件：求和可以先在互斥分片内求和再相加，均值必须携带计数，去重计数必须保留重叠信息。查询优化本质上包含带前提的代数推理。

对外连接、窗口函数和前若干行截取的改写尤其需要谨慎。先截取十笔订单再聚合与先聚合再取十个用户显然不同；把城市筛选从窗口之后移到之前，可能改变排名参照总体。这里先建立一般原则，后续章节用完整窗口与连接实验细化。遇到新语法时，仍然先问它改变哪一种单位、哪些记录能影响最终输出。

<a id="database-1-detail-26"></a>

### 6.3 排序、并列与可重复结果

没有明确排序时，数据库返回行的顺序不构成可依赖契约。索引增加、统计信息变化或执行计划变化，都可能让同样内容以另一顺序出现。训练代码如果按返回顺序切分训练与测试，便可能在没有改动 SQL 文字时产生不同样本。稳定切分应由明确键、时间规则或可复现散列定义，而不是偶然位置。

只按总金额降序还不足以确定并列用户的次序。若需要稳定导出，可以追加唯一键作为次排序键；若希望表达业务并列，则应在指标含义上保留并列，而不是把唯一键误认为业务优劣。数值缺失的排序位置也有产品差异，跨产品复现时可以显式建立缺失排序标志。可重复性应当是查询设计的一部分。

## 7. 完整实验：从受约束原表到可解释用户摘要

<a id="database-1-detail-28"></a>

### 7.1 可独立运行的内存数据库

下面的程序建立用户和订单，金额以分为单位，订单时间采用统一格式文本。它验证外键、缺失、条件聚合、筛选阶段、参数绑定和空输入行为。实验不是性能基准，不需要安装服务；连接明确关闭，内存内容随之释放，不会在资料目录产生数据库或脚本。

```python
import sqlite3
from contextlib import closing

with closing(sqlite3.connect(":memory:")) as conn:
    conn.execute("PRAGMA foreign_keys = ON")
    assert conn.execute("PRAGMA foreign_keys").fetchone()[0] == 1
    conn.executescript("""
    CREATE TABLE users(user_id INTEGER PRIMARY KEY, city TEXT);
    CREATE TABLE orders(
        order_id INTEGER PRIMARY KEY,
        user_id INTEGER NOT NULL REFERENCES users(user_id),
        amount_cents INTEGER CHECK(amount_cents >= 0),
        status TEXT NOT NULL CHECK(status IN ('done', 'cancelled')),
        created_at TEXT NOT NULL
    );
    """)
    conn.executemany("INSERT INTO users VALUES (?, ?)",
                     [(1, "甲城"), (2, "乙城"), (3, None)])
    conn.executemany("INSERT INTO orders VALUES (?, ?, ?, ?, ?)", [
        (101, 1, 1000, "done", "2026-01-02T10:00:00"),
        (102, 1, None, "done", "2026-01-03T10:00:00"),
        (103, 1, 2000, "done", "2026-01-04T10:00:00"),
        (104, 2, 4000, "done", "2026-01-05T10:00:00"),
        (105, 2, 16000, "done", "2026-01-06T10:00:00"),
        (106, 2, 9000, "cancelled", "2026-01-07T10:00:00"),
        (107, 3, 6000, "done", "2026-02-01T00:00:00"),
    ])
    for row in [
        (101, 1, 2, "done", "2026-01-01"),
        (108, 99, 2, "done", "2026-01-01"),
        (108, 1, -2, "done", "2026-01-01"),
    ]:
        try:
            conn.execute("INSERT INTO orders VALUES (?, ?, ?, ?, ?)", row)
        except sqlite3.IntegrityError:
            pass
        else:
            raise AssertionError("constraint was not enforced")
    args = {"start": "2026-01-01T00:00:00",
            "end": "2026-02-01T00:00:00", "state": "done"}
    summary = conn.execute("""
        SELECT user_id, COUNT(*), COUNT(amount_cents),
               SUM(amount_cents), AVG(amount_cents)
        FROM orders
        WHERE created_at >= :start AND created_at < :end
          AND status = :state
        GROUP BY user_id HAVING COUNT(*) >= 2 ORDER BY user_id
    """, args).fetchall()
    assert summary == [(1, 3, 2, 3000, 1500.0),
                       (2, 2, 2, 20000, 10000.0)]
    assert conn.execute(
        "SELECT COUNT(*) FROM orders WHERE amount_cents = NULL"
    ).fetchone()[0] == 0
    assert conn.execute(
        "SELECT COUNT(*) FROM orders WHERE amount_cents IS NULL"
    ).fetchone()[0] == 1
    empty = conn.execute("""
        SELECT COUNT(*), COUNT(amount_cents), SUM(amount_cents),
               AVG(amount_cents)
        FROM orders WHERE order_id < 0
    """).fetchone()
    assert empty == (0, 0, None, None)
    first_filter = conn.execute("""
        SELECT AVG(amount_cents) FROM orders
        WHERE user_id=2 AND status='done' AND amount_cents > 10000
    """).fetchone()[0]
    last_filter = conn.execute("""
        SELECT AVG(amount_cents) FROM orders
        WHERE user_id=2 AND status='done'
        GROUP BY user_id
        HAVING AVG(amount_cents) > 10000
    """).fetchall()
    assert first_filter == 16000.0 and last_filter == []
    coverage = conn.execute("""
        SELECT COUNT(*),
               SUM(CASE WHEN status='done' THEN 1 ELSE 0 END),
               COUNT(CASE WHEN status='done' THEN amount_cents END),
               AVG(CASE WHEN status='done' THEN amount_cents END)
        FROM orders WHERE user_id=1
    """).fetchone()
    assert coverage == (3, 3, 2, 1500.0)
    fake_city = "甲城' OR 1=1 --"
    assert conn.execute("SELECT user_id FROM users WHERE city=?",
                        (fake_city,)).fetchall() == []
    dup = conn.execute("""
        WITH t(x) AS (VALUES (100), (100))
        SELECT SUM(x), SUM(DISTINCT x) FROM t
    """).fetchone()
    assert dup == (200, 100)
    groups = conn.execute("""
        WITH t(g,x) AS (VALUES ('A',10),('B',20),('B',20),('B',20))
        SELECT g, COUNT(x), SUM(x), AVG(x) FROM t GROUP BY g ORDER BY g
    """).fetchall()
    overall = sum(r[2] for r in groups) / sum(r[1] for r in groups)
    macro = sum(r[3] for r in groups) / len(groups)
    assert overall == 17.5 and macro == 15.0
    print("summary:", summary)
    print("empty:", empty, "coverage:", coverage)
    print("overall:", overall, "macro:", macro)
```

本例在组筛选查询中显式写出 `GROUP BY user_id`：虽然 `WHERE` 已限定单个用户，写出分组仍能清楚表达“对该用户的全部合格订单求均值，再筛组”的顺序，也兼容 Ubuntu 22.04 所带的较早 SQLite。SQLite 从 [3.39.0](https://www.sqlite.org/releaselog/3_39_0.html) 起才支持聚合查询在没有 `GROUP BY` 时使用 `HAVING`，不能只看宿主 Python 版本判断该语法是否可用。

三个输出依次包括用户摘要、空输入与覆盖率、整体均值与分组均值。用户一有三笔已完成订单，但只有两笔金额已知；用户二的取消订单不会进入摘要；二月第一刻的记录不会混入一月。断言不只是测试语法能执行，而是在检查统计契约的关键边界。任何断言失败，都应定位相应假设，不应先改期望值让程序通过。

这里故意捕获三种约束错误，但没有把整个实验当作复杂业务写入流程。正式修改数据应显式设计提交与回滚，而非从练习中的异常捕获推导事务策略。本例连接使用关闭上下文管理，保证资源释放；数据库连接自身的上下文主要管理事务结束行为，两者职责不能混淆。清楚说明资源所有权也有助于之后理解并发连接和快照。

<a id="database-1-detail-29"></a>

### 7.2 为断言构造能击败错误实现的输入

把金额已知数误写成总行数，用户一的均值分母会变成三；把月份上界改成包含二月第一刻，用户三就被错误纳入；删除取消状态筛选，用户二总额会增加；使用金额去重求和，相同金额但身份不同的订单会少算。这些反例应该在提交查询前设计，而不是上线后等待真实数据触发。

参数绑定测试使用含引号与逻辑片段的城市文本，结果仍按普通字符串匹配，不会成为新的查询条件。绑定解决值与语法边界，不自动验证城市是否存在，也不会把错误单位变正确。动态表名、列名和排序方向不能作为普通值参数随意传入，应从受控映射中选择；未知选项应给明确错误，而不是拼接到查询。

金额全部以整数输入，因此本例没有证明任意类型混入都能安全处理。完整验收还应依据真实驱动和模式，检查超范围、字符串、非有限数值与错误日期。玩具实验能证明明确输入下的行为，不能自动成为所有版本与类型组合的普遍定理。学习时既要观察成功路径，也要理解证据范围。

<a id="database-1-detail-30"></a>

### 7.3 手工推导与自动检查互相约束

先手工列出合格订单，再逐用户计算行数、已知数和金额和，能检查题目是否被正确理解；程序断言能检查实现是否保持理解。若手算和程序来自同一错误公式，二者相等仍会误导，因此还要检查独立性质，例如已知数不超过总行数、分组计数之和等于同一输入总体计数。

这些性质有条件。分组求和等于整体求和，需要每条输入只属于一个组、使用同一筛选，并避免溢出或显著舍入误差；分组不同用户数之和不一定等于全局不同用户数，因为同一用户可能跨组。检查旁边应写明前提，否则错误的通用断言可能逼迫正确查询作出错误修改。

<a id="database-1-detail-31"></a>

## 8. 研究与工程：从答案审查到不变量审查

<a id="database-1-detail-32"></a>

### 8.1 不只看最终数值是否合理

只看均值是否接近预期很脆弱。两处相反错误可能抵消，例如部分订单被重复加权，另一部分被误删，最终均值恰好不变。应检查键集合、每键重数、未知比例、时间边界与单位，再检查指标。对于机器学习，复制少数对象会改变优化权重，即使几个总体均值几乎不变，也可能造成明显模型偏差。

可以记录每一步的行数、不同业务键数和异常键示例。若原始粒度是一行一订单，纯筛选后行数不增加；按用户分组后行数不超过合格订单数；按合法外键连接唯一用户维表，订单行数保持。每个上界和等式应说明约束前提，失败时才能区分业务新情况、来源异常与查询错误。

金额还可做守恒检查：把同一总体按互斥城市分组，分组和的总和应等于总体和，缺失城市组也要包括。如果连接维表后总额变化，优先检查重复匹配与未匹配行被删除。守恒不能证明城市归属正确，因为错分城市可能保持总额，但它对放大和漏行敏感，适合作为第一层诊断。

<a id="database-1-detail-33"></a>

### 8.2 查询等价与变形测试

查询等价是对全部合法输入成立的命题，有限测试不能穷尽证明，但可迅速找到反例。应主动包含重复键、同额不同订单、空值、空表、并列值和边界时间。比较输出时要按多重集而非仅按集合，否则重复放大错误会被测试框架忽略。若涉及排序，再分别比较内容与顺序契约。

变形测试利用已知关系。复制全部输入时，在无去重且筛选不变的条件下，计数和求和翻倍，均值保持；给全部已知金额加同一常数，已知均值增加该常数，缺失数不变；打乱插入顺序，不带次序敏感语义的输出多重集不变。每条关系都有前提，不能对去重计数机械使用翻倍规则。

小规模参考实现可以用 Python 显式循环，刻意采用与 SQL 不同的表达路径。例如 SQL 条件聚合，参考实现先建立合格记录列表，再独立计算分子分母。独立实现有助于发现翻译错误，但不能替代业务定义；两个程序都可能忠实计算同一个错误问题。正确性证据应包含定义、推导与实验三个层次。

<a id="database-1-detail-34"></a>

### 8.3 数据版本与可重复导出

即使查询文本没变，来源数据补录、状态修订和模式演化也可能改变结果。保存查询文本不足以复现训练集，还需要数据版本或可重建快照、参数、时间范围、环境与输出键。对于重要结果，可保存每个阶段的计数及摘要，用来区分代码变化和数据变化，而不是发现分数波动后只能猜测原因。

结果散列也有边界。若导出没有稳定排序，相同多重集可能产生不同文件散列；若数值格式变化，文本散列也会变化。比较前先定义要验证逻辑内容还是逐字节文件。逻辑比较应尊重重复和类型，文件比较则需要统一编码、列顺序、行顺序和格式。复现要求越严格，数据契约就越应具体。

## 9. 进阶练习与逐题解析

<a id="sec-7-1"></a>

<a id="database-1-detail-36"></a>

### 9.1 题一：AVG 的分母为什么不是总行数

**题目：** 金额为十、空值、二十，报告分别给出十五与十，哪份一定正确？需要补充什么？

**解析：** 两者对应只平均已知金额和把缺失当零后平均，不能只凭数值判定。若空值是采集失败，十增加了零金额假设；若业务确定该行表示没有消费，零可能合理，但表是否应称订单也需审视。应补充缺失原因、统计总体和填补规则，同时报告三条记录、两条已知、已知和三十。还要检查缺失是否随金额、来源或状态变化，否则已知均值不一定代表完整总体。语法正确与统计估计合理是两层判断。

<a id="database-1-detail-37"></a>

### 9.2 题二：当前唯一是否足以成为键

**题目：** 一万名用户目前没有重名，能把姓名作为主键吗？新增随机编号能消除重复业务用户吗？

**解析：** 当前没有反例只支持样本事实，不能证明全部合法状态都唯一。姓名可重名也可变化，不适合该业务稳定标识。新增编号只使数据库行可区分，同一个真人仍可能得到多条记录。要分开讨论行身份、真实对象身份和导入事件身份；若上游有稳定编号，可将来源和编号组成业务唯一约束。跨来源身份合并需要另外的规则，不能期待主键自动完成实体解析。

<a id="database-1-detail-38"></a>

### 9.3 题三：不同金额为什么不能去重订单

**题目：** 两个真实订单都为一百，其中一个因连接出现两次。对金额去重后求和能恢复正确总额吗？

**解析：** 不能。金额去重只知道数值相同，不知道订单身份。它会同时合并同一订单的复制和另一笔合法订单，结果是一百，而正确金额为两百。应在仍保留订单键时解决连接基数，或先把明细聚合到订单粒度再连接。若只剩金额，身份信息已经丢失，一般无法恢复。这个反例说明，去重的位置与依据比是否写了去重更重要，修复应针对产生重复的机制。

<a id="database-1-detail-39"></a>

### 9.4 题四：否定筛选为何不能覆盖缺失

**题目：** 大于一百与不大于一百两组，为什么行数相加可能少于总行数？如何完整划分？

**解析：** 空值比较得到未知，未知的否定仍未知，两个筛选都不保留这些行。可以明确分成已知且大于、已知且不大于、缺失三组，并验证互斥且穷尽。若产品只需要两类，就必须另行定义缺失归属，不能以为逻辑否定已经做出业务选择。训练中派生二值特征也应保存缺失指示或清楚的填补规则，否则某个默认筛选会把可用样本悄悄排除，使总体发生变化。

<a id="database-1-detail-40"></a>

### 9.5 题五：空输入与不存在分组

**题目：** 无分组聚合返回一行零计数，按用户分组却没有结果。怎样为全部注册用户显示零单？

**解析：** 前者对整个空总体形成摘要，后者需要输入建立用户组，没有输入就没有组。应以注册用户为总体，先把合格订单按用户聚合，再左连接用户，并对缺失计数提供零展示。不要无条件把所有聚合值填零，因为没有金额观测时均值未定义。可以另外保留是否有观测与已知数，避免展示层缺省值被模型当作真实零。保持总体来源明确，才能正确保留从未产生订单的用户。

<a id="database-1-detail-41"></a>

### 9.6 题六：平均的平均何时正确

**题目：** 甲组一个十，乙组九个二十，十五和十九分别回答什么问题？

**解析：** 若每组等概率被选择，先看该组平均，十五对应组等权目标；若从全部十条记录等概率选择，十九对应记录等权目标。数值无须竞争谁绝对正确，关键是抽样单位。分片合并应保留和及有效个数，以恢复整体均值；若还需组等权均值，则保留组摘要。研究比较应在看结果前固定权重口径，否则在多个指标中选择有利值会让结论缺乏明确对象。

<a id="database-1-detail-42"></a>

### 9.7 题七：筛行与筛组的反例

**题目：** 同一用户订单四十和一百六十。先筛金额大于一百再平均，与先平均再筛均值大于一百，差别是什么？

**解析：** 前者只有一百六十进入聚合，用户出现且均值为一百六十；后者两笔都进入聚合，均值一百，不满足严格大于，所以不出现。即使条件改成大于等于，后者会出现但均值仍不同。反例应同时比较输出键集合与字段值，不能只检查行数。理解这个机制后，再面对更复杂状态条件或窗口查询，仍可追问哪些原始记录参与了每个统计量。

<a id="database-1-detail-43"></a>

### 9.8 题八：检查约束能否代替非空

**题目：** 金额只有非负检查，插入空值是否一定失败？必填金额怎样表达？

**解析：** 不能假定失败，常见检查规则允许未知结果，需以产品规定为准。必填且非负应同时表达存在性与范围限制。如果业务确实允许待结算金额未知，就不应为简化查询强行填零，而应保留状态与原因，并规定哪些状态允许缺失。数据约束忠实表示业务比表面完整更重要。否则所有行都有数值，却把未知假装成零，后续均值、标签与模型决策都会建立在错误事实之上。

<a id="database-1-detail-44"></a>

### 9.9 题九：文本日期为什么可能错序

**题目：** 日期字符串有的补零、有的不补零，有的带不同时区。直接做字符串范围筛选可靠吗？

**解析：** 不可靠，只有统一表示下字典序才可能对应时间序。不补零、不同分隔符、时区偏移和精度都可破坏这种关系。应在导入时解析为明确时间类型或统一规范表示，并定义时区与区间边界。此处只是基础表示问题，之后还需区分事件时间和可用时间。若最基础的时间序都不稳定，后续所有窗口、标签和特征合法性检查都可能建立在错误范围上。

<a id="database-1-detail-45"></a>

### 9.10 题十：集合并能否修复重复采集

**题目：** 每天合并两个来源，按整行去重，能保证真实事件仅出现一次吗？

**解析：** 不保证。同一事件的批次号和到达时间可能不同，整行去重不消除它；两个真实事件保留字段刚好相同，又可能被误合并。需要稳定事件键和版本冲突规则，必要时保留来源与原始编号。如果来源没有足够身份信息，就应承认无法无损判断，并补充采集或给出不确定性。集合操作只能比较当前表示，不能恢复已经缺失的身份，因此业务去重应有独立设计。

<a id="database-1-detail-46"></a>

### 9.11 题十一：参数绑定为何不能随意绑定列名

**题目：** 用户选择金额或数量排序，能把列名作为普通值参数传入吗？怎样控制动态语法？

**解析：** 普通参数通常表示数据值，不会成为列引用；按一个绑定常量排序也不会实现按所选列排序。应把有限用户选项映射到预先审查的固定列表达式，方向也从允许值选择，未知输入给明确错误。日期、状态和阈值仍作为普通值绑定。这样将语法选择与数据传入分开，每种可执行结构都能测试，而不是把不受控文本直接纳入程序。安全性与语义清楚在这里相互促进。

<a id="database-1-detail-47"></a>

### 9.12 题十二：随机验证能否证明等价

**题目：** 随机一千行上两个查询结果相同，是否足以确认改写正确？

**解析：** 只能说明该样本没找到差异。真实错误可能只出现在缺失、重复、无匹配用户或边界时刻，而随机数据很少包含这些结构。应主动设计空表、全部缺失组、相同金额不同键、重复键、无订单用户与并列值，并按多重集比较。关键改写还需给出代数解释和约束前提。测试能迅速找到反例，证明解释为何某些反例不可能，两者结合才能支撑可靠优化，而不是凭一次结果相同作决定。

<a id="database-1-detail-48"></a>

### 9.13 题十三：模式变化怎样造成目标泄漏

**题目：** 训练抽取选择全部列，来源新增最终退款结果后，模型大幅提升。应怎样调查？

**解析：** 首先比较字段清单，查看新列是否进入特征，并核查预测时点是否可见。若来自未来，提升可能是泄漏。应固定输入列与标签列，保存数据和模式版本，并明确时间可用规则。还需核查导出顺序、切分和缺失处理是否变化。模型分数只能提示现象，不能证明输入合法；只有在同一合法总体和信息条件下，比较才解释为模型改进，而不是使用了部署时不存在的答案。

<a id="database-1-detail-49"></a>

### 9.14 题十四：不知道真值怎样检查城市汇总

**题目：** 没有人工核定每城金额时，怎样发现部分漏行或复制？

**解析：** 在相同时间、状态范围内，独立计算总体金额和与城市分组金额和的总和，并把缺失城市也纳入。若每笔订单进入且只进入一组，两者应一致；同时比较行数和业务键唯一性。失败时检查连接放大、缺失过滤和范围差异。通过仍不代表城市归属正确，因为错分可能保持总额，因此另需抽查键到城市的映射。这个例子说明不同不变量覆盖不同错误类型，不能用一条总和相等宣称全部正确。

## 10. 自查与进一步追问

读完后，应能不看语法就解释每个输出列的单位，也能从查询反推出总体。若解释中出现“应该差不多”“反正已经去重”“空值就当零”，通常意味着某个假设尚未明确。重新构造三到五行反例，比直接在百万行观察结果更容易抓住概念问题；小表是查询设计中的精密实验工具，并非仅供入门。

进一步可研究约束如何支持连接消除、近似不同值计数怎样合并状态、模式演化怎样保持数据契约。每个方向都先给最小可执行例子，再列推广条件，避免只堆名词。身份决定事实属于谁，重数决定被使用多少次，分母决定指标怎样赋权；后续语法越强大，这三条线索越需要被持续追踪。

<a id="database-1-detail-51"></a>

### 10.1 将数据库语义连接到学习目标

训练过程常把每条导出行视作一个损失项。因此，数据库的重数会直接变成优化目标里的权重。假设用户甲因重复事件出现十次，用户乙出现一次，模型并非在两个用户上等权学习，而是在十一个行位置上等权学习。即使最终调用完全标准的训练函数，也不能修复此前定义错误的样本分布。去重、抽样和加权都应在数据契约中有可解释依据，而不只是模型调参选项。

缺失处理同样会改变学习问题。删除金额未知的记录相当于在“金额可观察”条件下训练，若部署对象包括不可观察人群，训练分布与部署分布可能不一致；填零则把观测过程折叠进数值，可能制造额外模式。选择方法时应把数据生成与采集机制纳入分析，用时间切分或来源切分检验稳定性，并将覆盖率和缺失比例列为模型旁边的质量指标。

还应区分数据库里真实保存的值与概念上想要的潜在值。查询只能操作已有记录，不能凭语法推断漏掉的订单，也不能从空值中恢复未知金额。若研究目标要求完整总体，可能需要补采、与其他来源匹配、使用明确假设下的估计方法，或收缩结论范围。承认信息限制是严谨建模的起点，不能用复杂查询把缺失信息包装成看似精确的结果。

<a id="database-1-detail-52"></a>

### 10.2 一个可复用的口头验收流程

向同伴解释查询时，先说最终一行代表什么，再说原始记录怎样进入总体，然后说明每个聚合量的分子、分母和未知规则，最后说明顺序与并列。让对方用一个没有订单的用户、一组全部空值和两个同额订单挑战它。如果能在纸上迅速写出预期输出，再用实验验证，说明语义已经足够清楚；如果无法回答，继续增加函数或优化索引通常只会掩盖问题。

<a id="database-1-detail-53"></a>

### 10.3 用失败记录改善模式

若某条新数据违反现有约束，不应立即删除它，也不应立即放宽约束。先判断它属于来源错误、规则变化，还是原模型遗漏了真实情况。例如金额为负可能是错误订单，也可能是退款事件被放进订单表。前者应纠正来源，后者可能需要事件类型和符号规则。约束失败是对业务模型的反馈，只有理解原因后才能决定修复数据还是演化模式。
