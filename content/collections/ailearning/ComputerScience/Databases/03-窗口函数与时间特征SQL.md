## 1. 窗口函数保留哪一层的行

窗口函数适合为每条结果记录附加排名、前后值和局部统计。它并不自动保证记录仍然代表原始事件，也不会替使用者判断某条历史在预测时是否可见。理解窗口的第一步，是写清进入窗口计算的关系是什么、每行代表什么，以及它已经经历了哪些连接、过滤和聚合。

本章以本地 SQLite 3.42.0 的可执行实验为基线，使用整数时间表示明确的业务时刻。涉及其他数据库时单独说明语法与行为不能直接照搬。目标是从集合定义推导 SQL，再用独立 Python 参考核对，而不是把一个能执行的查询当作正确特征的证明。

<a id="db-3-detail-2"></a>

### 1.1 GROUP BY 折叠，窗口附加结果

普通分组聚合把一组输入折叠成一行，例如按用户求总金额，每位用户只有一个结果。窗口聚合则对当前查询层保留的每行，计算与它对应的一个统计值。用户三笔金额十、二十、三十，分组得到六十，而包含当前行的前缀窗口可得到十、三十、六十这三条结果。

这里的“保留行”是相对于窗口所接收的查询层而言。如果先做分组，再对分组结果做窗口，窗口保留的是每组一行，而不是恢复原始事件。若先连接导致一条事件复制三次，窗口也会看到三份，不会识别它们本来来自同一笔订单。

因此应先验证窗口输入的键和粒度。每笔订单一行、每个订单明细一行、每位用户每天一行，是三个不同关系。即使最后都按用户分区，金额累计也可能不同。需要先决定原始重复是否代表业务明细，再用约束或预聚合建立正确输入。

<a id="db-3-detail-3"></a>

### 1.2 逻辑查询阶段决定窗口能看到什么

在一个普通查询层中，可以按逻辑理解为先形成来源和连接，再用 WHERE 过滤，随后分组和 HAVING，之后计算窗口结果，最后完成结果选择、去重、排序和限制等后续步骤。优化器可能采用不同物理执行方式，但必须保留相应语义。

这解释为什么在同一层 WHERE 中通常不能直接筛选新计算的窗口序号：序号在该逻辑阶段还没有产生。SQLite 可把窗口放在子查询或公共表表达式中，再由外层筛选。某些产品提供额外简写，但跨产品资料应明确方言，而不是把一个专用关键字当标准通用功能。

也不要把逻辑顺序误解为必须实际生成所有中间表。数据库可以合并、重排或流式执行某些操作。学习时先用逻辑关系证明结果，再用执行计划分析实现，避免反过来从某次计划猜出一个不稳定的语言规则。

<a id="db-3-detail-4"></a>

### 1.3 窗口排序不等于最终输出排序

窗口中的 ORDER BY 决定排名、偏移和 frame 的顺序；查询最外层 ORDER BY 决定返回给客户端的行顺序。前者存在，不保证客户端看到的记录必然按相同顺序排列。没有外层排序时，不能把某次扫描碰巧有序当作接口保证。

同样，多个窗口可以有不同排序，例如一列按时间累计，另一列按分数排名。它们共享输入关系，却代表不同顺序。阅读结果时应通过样本键对齐，而不是根据打印出来的位置推断窗口内部次序。

若结果要分页或生成稳定文件，应使用最终的确定全序，例如用户、时间、唯一事件号。若只按可能重复的时间排序，同值行的相对顺序仍可能变化。稳定输出与历史可见性是不同要求，后面还会分别讨论。

<a id="sec-1-1"></a>

<a id="db-3-detail-5"></a>

### 1.4 历史特征的空窗不是普通零值

若要求事件发生前的累计金额，三笔十、二十、三十应对应空历史、十、三十。空历史时 SUM 常返回 NULL，它表示没有可聚合的非空值，不自动代表真实消费为零。可以根据特征定义填零，但最好同时保留历史行数或有无历史标志。

如果历史有三笔记录但金额全部缺失，SUM 也可能为 NULL，与完全没有历史不同。COUNT(*)、COUNT(amount) 和 SUM(amount) 分别记录不同事实：历史记录数、金额非空数、已知金额之和。把它们过早压成一个零，会丢掉数据质量信息。

对模型而言，缺失模式可能有预测价值，也可能是来源或处理流程的捷径。是否保留标志应结合任务和部署信息条件判断。数据库表达式只负责实现规则，不能替研究者决定缺失究竟意味着什么。

## 2. 分区、排序、同级行与 frame

<a id="db-3-detail-7"></a>

### 2.1 分区是统计总体，不是物理分片

PARTITION BY 为每条行指定同组记录，例如同一用户或同一设备。它表达统计分组，不意味着数据一定被物理放在同一个文件，也不要求最终输出连续。一个用户可能在物理扫描中分散，数据库仍应按查询语义处理其窗口。

分区键若缺少租户、设备版本或业务域，可能把本不应合并的记录累计到一起。反过来，加入过细键会把历史割裂，例如按订单号分区导致每笔订单只看到自己。先写每个统计量应共享历史的实体，再选择分区字段。

NULL 分组键也要有明确策略。若很多未知用户都具有 NULL，按该字段分区可能把它们视作同一分区，形成跨实体历史。可以拒绝缺失身份、使用真正独立的事件级标识，或定义专门的未知总体，但不能默默把所有未知人当一个人。

<a id="db-3-detail-8"></a>

### 2.2 同级行由窗口排序表达式决定

对于按照排序值处理的 frame，同样排序值的行构成同级组。只按时间排序时，同一时间的不同事件是同级；加上唯一事件号后，可能每行各自成为一个同级组。因此添加次级键不只是让输出稳定，还可能改变 RANGE、GROUPS 及排除规则的统计含义。

例如同一时刻两笔金额五和七，按时间的前缀 RANGE 会让二者看到同一时间组，累计同时包含十二；按时间与唯一号的 ROWS 则可以逐行得到五和十二。哪一个正确取决于问题是否允许同时间记录存在有意义先后，不能根据哪种数值更平滑来选。

如果业务时间精度只有秒，而真实事件在秒内有先后，编号排序是否能代表真实可见顺序仍需要证据。一个任意自增主键可以保证计算可复现，却未必代表模型当时已看到前一事件。确定性与因果合法性不能混为一谈。

<a id="sec-2-1"></a>

<a id="db-3-detail-9"></a>

### 2.3 ROWS、RANGE 与 GROUPS 表达不同集合

ROWS 以排序后行位置计数，前两行就是两条记录，不考虑时间间隔。RANGE 按排序值及边界确定范围，同值记录通常一起进入；带数值偏移的用法需要核对产品限制，本章 SQLite 实验使用单一数值排序列。GROUPS 则以同级组数量移动边界。

因此最近七行、最近七个时间组和最近七个时间单位是三种目标。高频用户七行可能只覆盖几秒，低频用户则覆盖数月。GROUPS 的一个时间组可以包含很多行，并不等于一行，也不自动等于一天。

在 SQLite 的本章数值时间设置中，RANGE 的数值偏移按排序列数值单位解释。若时间保存为秒，偏移七表示七秒，不是七天。若使用文本日期或多个排序字段，不能机械复制同样写法，需要根据方言与表示重新推导。

<a id="deep-dive-2"></a>

<a id="db-3-detail-10"></a>

### 2.4 默认 frame、CURRENT ROW 与排除规则

缺省 frame 可能包含当前同级组，不能把写了 ORDER BY 就理解为只看过去。为了使教材结果可以核对，本章所有关键历史计算都显式写出 frame 或严格时间条件，并说明是否包括当前与同时间事件。

排除当前行只去掉当前这一条，不一定去掉同时间其他行；排除当前同级组则会去掉整个排序同值组。这两者在“严格早于当前时间”的特征中差别很大。若加了唯一键导致同级组变小，原来排除同时间组的含义也会变化。

frame 对不同函数并非统一生效。偏移函数、排名函数与 frame 敏感的聚合或首尾值函数，需要分别核对。不能看到一段 OVER 定义，就假定其中每个边界会以完全相同方式影响所有窗口函数。后面通过实验展示这种差异，而不是只依赖术语记忆。

### 3.1 四行记录同时观察多种窗口

构造同一用户四条事件，时间为十、十、二十、三十五，金额为五、七、NULL、十一。按照时间与编号的逐行累计得到五、十二、十二、二十三；按时间同级的累计则前两行都得到十二。金额缺失不增加和，但仍是一条历史记录。

若逐行排除当前行，前两行历史分别为空和五；严格排除当前时间组，前两行都为空。这个最小表证明，“前一行”不等于“严格早于当前时间”，也证明空金额与空窗口的计数行为不同。

还可以观察默认 LAST_VALUE：在一个截至当前同级组的 frame 中，它返回的是该 frame 尾部，而不一定是整个分区最后一条。如果需要分区尾部，应显式把结束边界扩到分区末尾，同时判断这是否在预测时可用。

<a id="db-3-detail-13"></a>

### 3.2 可运行 SQL 与独立参考

下面用 SQLite 内存连接运行，所有输入与预期都在代码中。SQL 结果按事件号输出，Python 参考独立计算逐行前缀与严格时间历史。LAG 的例子故意配一个仅含当前行的 frame，展示它取前行的偏移语义，而不是在该单行 frame 中寻找前行。

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.executescript('''
CREATE TABLE events(
  user_id TEXT NOT NULL, event_id INTEGER PRIMARY KEY,
  event_time INTEGER NOT NULL, amount INTEGER
);
''')
data = [("A", 1, 10, 5), ("A", 2, 10, 7),
        ("A", 3, 20, None), ("A", 4, 35, 11)]
con.executemany("INSERT INTO events VALUES(?,?,?,?)", data)
rows = con.execute('''
SELECT event_id,
 SUM(amount) OVER(
   PARTITION BY user_id ORDER BY event_time,event_id
   ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS row_total,
 SUM(amount) OVER(
   PARTITION BY user_id ORDER BY event_time
   RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS peer_total,
 SUM(amount) OVER(
   PARTITION BY user_id ORDER BY event_time
   RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW EXCLUDE GROUP) AS strict_total,
 COUNT(*) OVER(
   PARTITION BY user_id ORDER BY event_time,event_id
   ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) AS history_rows,
 COUNT(amount) OVER(
   PARTITION BY user_id ORDER BY event_time,event_id
   ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) AS known_rows,
 LAG(amount) OVER(
   PARTITION BY user_id ORDER BY event_time,event_id
   ROWS BETWEEN CURRENT ROW AND CURRENT ROW) AS lag_value
FROM events ORDER BY event_id
''').fetchall()
def sum_or_null(values):
    known = [value for value in values if value is not None]
    return sum(known) if known else None
for i, row in enumerate(rows):
    current = data[i]
    previous = data[:i]
    strict = [r[3] for r in data if r[2] < current[2]]
    assert row[1] == sum_or_null([r[3] for r in data[:i+1]])
    assert row[3] == sum_or_null(strict)
    assert row[4] == len(previous)
    assert row[5] == sum(r[3] is not None for r in previous)
    assert row[6] == (None if i == 0 else data[i-1][3])
assert [row[2] for row in rows] == [12, 12, 12, 23]
assert [row[3] for row in rows] == [None, None, 12, 12]
print("SQLite:", sqlite3.sqlite_version)
print("id / ROWS / RANGE / strict / n / known / lag:", rows)
con.close()
```

### 3.3 实验结论的范围

这个实验验证 SQLite 本地版本的具体语义，不代表所有数据库对所有窗口关键字都有同样支持。迁移时应保留这个小表，逐个核对 frame、NULL 与排除行为，必要时用相关子查询或聚合连接表达同一集合。

金额使用整数，避免把浮点累加顺序微差与集合边界错误混在一起。真实金额可采用明确精度的数值类型或最小货币单位整数，但还要处理溢出和币种。窗口正确性首先是选择了哪些记录，其次才是这些值怎样数值归约。

对时间特征，应把这些查询看成表达工具。严格早于事件时间仍不足以保证当时已入库，修订版本也可能来自未来。下一节将额外加入可用时间与版本，展示仅靠一个顺序窗口无法解决的情形。

<a id="db-3-detail-15"></a>

## 4. 按预测时点重建真正可用的历史

<a id="db-3-detail-16"></a>

### 4.1 三种时间分别回答什么

事件时间描述业务发生，入库或可用时间描述系统何时能读取该信息，预测时间描述模型作出决策。三者可能不同。一笔昨天发生、今天才入库的交易，在今天的数据库中存在，但不能自动进入昨天已完成预测的特征。

版本修订进一步增加复杂性。某事件金额先记为十，后来更正为三十；历史重放应使用预测时点之前已可用的最新版本，而不是今天的最终正确值。最终真相可以用于某些标签定义，却不能未经说明回填为过去特征。

还要定义同一时刻的可见边界。本章约定可用时间不晚于预测时间的版本可读，事件本身必须严格早于预测时间。这个约定只是一种协议；若真实系统在同一时间戳内还有提交顺序，应加入更精细游标，不能靠任意编号假造可见性。

<a id="db-3-detail-17"></a>

### 4.2 先选可见版本，再判断事件是否落窗

为每个样本，先保留可用时间合法的版本，再在每个逻辑事件内选最新可见版本，最后检查该版本的事件时间和删除状态。如果先按事件时间过滤，再选版本，可能把被修订移出窗口的事件旧版本重新选回。

例如一条事件原时间为七，后来被更正为十五；预测时点为十五，历史要求严格早于十五。最新可见版本已在边界外，应不计入。若先删掉事件时间十五的版本，旧版本七还在，排名后它反而成了第一，产生错误“复活”。

删除标记同理。先过滤删除版本，再排名，可能把已被删除的旧值带回结果。版本选择的对象是逻辑事件当前可见状态，资格过滤应在这个状态上执行；不能把事件版本当成彼此独立的普通历史行。

<a id="db-3-detail-18"></a>

### 4.3 样本键必须进入版本排名分区

不同样本预测时点不同，同一事件对它们的最新可见版本可能不同。因此排名分区需要样本键加事件键，而不能在全表只给每事件排一次最新，再连接全部样本。

如果样本只有用户和日期但一天有多次预测，应保留真正唯一样本身份。用用户分区会把多个预测时点混成一个版本选择，或者连接后产生重复。特征表应能保证每个样本键恰好一行，而非靠最终 DISTINCT 掩盖选择逻辑错误。

这种按样本重放的查询可能产生较大中间关系。可以通过索引、预计算或版本区间优化，但必须先保留一个清楚的参考查询，再证明改写等价。查询慢是优化问题，不能通过先取今天最新版本来“提速”却改变历史含义。

<a id="db-3-detail-19"></a>

### 4.4 完整双时间版本实验

下面还假设事件的用户归属在各版本间不变，逻辑事件键为用户与事件号的组合，因此可以先按样本用户连接候选。如果业务允许同一全局事件从用户甲修订为用户乙，用户归属就属于版本化属性：必须先按全局事件身份选出该样本时点的最新可见版本，再判断它是否归属目标用户。若先筛甲的记录，最新版本已移给乙却被过滤，甲的旧记录又会被错误选回。事件身份与可变业务属性应在模式中分清，不能因为都叫编号就当成相同层次。

下例使用四个预测时点与五个逻辑事件，覆盖延迟入库、金额修订、事件时间移动和删除标记。Python 参考先逐样本筛可用版本，再按事件选最新，最后应用历史窗。SQL 与参考逐键比较，避免只核对总行数。

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.executescript('''
CREATE TABLE samples(
 sample_id INTEGER PRIMARY KEY, user_id TEXT NOT NULL, cutoff INTEGER NOT NULL
);
CREATE TABLE versions(
 user_id TEXT NOT NULL, event_id INTEGER NOT NULL, version_id INTEGER NOT NULL,
 event_time INTEGER NOT NULL, available_time INTEGER NOT NULL,
 amount INTEGER, deleted INTEGER NOT NULL CHECK(deleted IN (0,1)),
 PRIMARY KEY(user_id,event_id,version_id)
);
''')
samples = [(1, "A", 12), (2, "A", 15), (3, "A", 16), (4, "A", 21)]
versions = [
 ("A", 1, 1, 8, 9, 10, 0), ("A", 1, 2, 8, 15, 30, 0),
 ("A", 2, 1, 10, 10, 5, 0), ("A", 3, 1, 9, 20, 100, 0),
 ("A", 4, 1, 7, 7, 4, 0), ("A", 4, 2, 15, 14, 4, 0),
 ("A", 5, 1, 6, 6, 50, 0), ("A", 5, 2, 6, 13, None, 1)
]
con.executemany("INSERT INTO samples VALUES(?,?,?)", samples)
con.executemany("INSERT INTO versions VALUES(?,?,?,?,?,?,?)", versions)
query = '''
WITH eligible AS (
 SELECT s.sample_id,s.cutoff,v.*,
  ROW_NUMBER() OVER(
   PARTITION BY s.sample_id,v.user_id,v.event_id
   ORDER BY v.available_time DESC,v.version_id DESC
  ) AS rn
 FROM samples s JOIN versions v
  ON v.user_id=s.user_id AND v.available_time<=s.cutoff
), history AS (
 SELECT * FROM eligible
 WHERE rn=1 AND deleted=0
  AND event_time>=cutoff-? AND event_time<cutoff
), summary AS (
 SELECT sample_id,COUNT(*) AS n,COUNT(amount) AS known,SUM(amount) AS total
 FROM history GROUP BY sample_id
)
SELECT s.sample_id,COALESCE(h.n,0),COALESCE(h.known,0),COALESCE(h.total,0)
FROM samples s LEFT JOIN summary h USING(sample_id)
ORDER BY s.sample_id
'''
actual = con.execute(query, (10,)).fetchall()
reference = []
for sample_id, user, cutoff in samples:
    latest = {}
    for row in versions:
        uid, event, version, event_time, available, amount, deleted = row
        if uid != user or available > cutoff:
            continue
        key = (available, version)
        if event not in latest or key > (latest[event][4], latest[event][2]):
            latest[event] = row
    selected = [row for row in latest.values()
                if not row[6] and cutoff-10 <= row[3] < cutoff]
    known = [row[5] for row in selected if row[5] is not None]
    reference.append((sample_id, len(selected), len(known), sum(known)))
assert actual == reference
assert actual == [(1, 4, 4, 69), (2, 2, 2, 35),
                  (3, 3, 3, 39), (4, 1, 1, 4)]
print("sample / historical count / known count / sum:", actual)
con.close()
```

本例将金额和中的空值填为零，同时保留历史记录数与已知金额数。这个零只表示按既定缺失规则汇总的已知贡献；当历史记录数大于零、已知数为零时，不能据此宣称真实金额为零。若模型接口需要直接区分这两类状态，可以让金额和继续保留空值，或另设金额全部未知的标志，再在训练折内确定后续处理。

<a id="db-3-detail-20"></a>

### 4.5 什么条件下追加未来数据不应改变旧特征

若只追加可用时间严格晚于所有旧预测时点的新版本，且旧记录与查询规则不变，那么它们在可见性筛选中全部被排除，旧特征应保持相同。这是可用来验证实现的重要不变量。

但若后续写入记录被回填了较早可用时间，或者历史版本本身被覆盖，条件就不成立。重跑结果改变可能来自数据协议没有保留真实可用历史，而不是 SQL 窗口失效。应区分“当时系统确实知道什么”和“今天认为当时应该知道什么”。

这种区分也说明一致快照不足以证明无泄漏。快照可以让整个查询读取同一数据库状态，但如果该状态包含未来修订，而查询没有按样本时点约束，历史特征仍然非法。下一章会把快照一致性与业务时间合法性进一步分开。

## 5. 排名、去重与首尾值的精确含义

<a id="db-3-detail-22"></a>

### 5.1 三种排名回答不同同分问题

分数九、九、七时，RANK 对应一、一、三，DENSE_RANK 对应一、一、二，ROW_NUMBER 对应三个不同编号。前两种保留同分关系，后一种必须在并列时有额外规则才能确定谁获得哪个编号。

如果目标是保留所有第一名，RANK 等于一与 ROW_NUMBER 等于一不同：前者可能多行，后者最多一行。若目标恰取一条，就应增加稳定次级键，同时说明为何该键符合保留规则。不能把“去重”当成无须业务定义的通用操作。

排名排序列也会影响同分本身。给 RANK 加唯一事件号，会让原本同分的分数被拆开，可能不再有并列名次。为了确定 ROW_NUMBER 添加唯一键是合理的，但不能把相同做法机械复制到本来要保留分数并列的排名。

<a id="db-3-detail-23"></a>

### 5.2 LAG、LEAD 与标签可见性

LAG 可以取排序前一条记录，适合差分与间隔计算；LEAD 取后一条，常用于离线标签或区间结束标记。使用后一条不必然错误，关键是它属于特征还是未来结果，以及预测时是否允许读取。

例如用下一次购买时间定义回访标签，需要一个足够成熟的观察区间；用下一次购买金额作为当前预测特征则通常泄漏。两者可以出现在同一数据准备项目，却应该在不同阶段和清楚的数据角色下使用。

偏移量是行数量，不是时间长度。前一条记录可能在一秒前，也可能在一年之前，应该同时计算时间差或可见性标志。缺少前行与前行某字段为 NULL 也不同，可以保留前行身份与字段值，避免一个 NULL 隐藏两种来源。

<a id="db-3-detail-24"></a>

### 5.3 LAST_VALUE 不一定是分区最后一行

首尾函数依赖 frame。默认截至当前同级组时，LAST_VALUE 常看起来像当前值，原因不是函数失效，而是它在当前 frame 中取尾。若要取整个分区末尾，需要相应结束边界；若用于在线历史，还要防止该末尾来自未来。

要取最后一个非空值，则又是另一个目标。产品对忽略 NULL 的专用语法支持不同，不能默认某个选项处处可用。可用相关子查询、分组键传播或版本选择表达，但应在有连续 NULL 和同时间记录的最小表中验证。

同时保留“最后事件时间”和“最后非空测量时间”往往更清楚。前者表示活动间隔，后者表示数值新鲜度。只填补一个值而不保留其年龄，可能让模型把很久以前的测量误认为当前可靠信息。

<a id="db-3-detail-25"></a>

## 6. 会话切分与间隔结构

<a id="db-3-detail-26"></a>

### 6.1 从相邻时间差定义会话

一个常见规则是同一用户相邻事件间隔严格超过阈值时开启新会话。先用 LAG 得到前一时间，再生成开始标志，最后对标志做前缀和获得会话编号。需要两层窗口计算，因为后一步依赖前一步产物。

阈值等于时归哪边必须明确。本章实验约定超过十才新开，因此间隔恰十仍在同一会话。若业务改成至少十就断开，需要改变比较符。会话边界不是一个自然唯一事实，而是应用定义的分组。

同时间多个事件应使用稳定键以保证行序，但时间差仍为零。若先过滤某些事件，再计算 LAG，会改变相邻关系，可能把原本同一会话切开；如果这些事件只是“不输出”但仍算活动，应先在完整活动集合计算，再在外层筛结果。

<a id="db-3-detail-27"></a>

### 6.2 会话实验与 Python 状态机

下面每个用户独立维护前一时间和会话号，作为 SQL 的独立参考。输入故意不是按时间排列，核对最终排序与窗口排序。这个实验也展示没有必要让调用方预先排好数据，SQL 应明确自己的顺序定义。

```python
import sqlite3

data = [("A", 4, 32), ("A", 1, 0), ("B", 7, 9),
        ("A", 3, 11), ("A", 2, 10), ("B", 6, 0)]
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE activity(user_id TEXT,event_id INTEGER PRIMARY KEY,t INTEGER)")
con.executemany("INSERT INTO activity VALUES(?,?,?)", data)
actual = con.execute('''
WITH previous AS (
 SELECT *,LAG(t) OVER(PARTITION BY user_id ORDER BY t,event_id) AS prev_t
 FROM activity
), marked AS (
 SELECT *,CASE WHEN prev_t IS NULL OR t-prev_t>10 THEN 1 ELSE 0 END AS starts
 FROM previous
)
SELECT user_id,event_id,t,
 SUM(starts) OVER(
  PARTITION BY user_id ORDER BY t,event_id
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
 ) AS session_id
FROM marked ORDER BY user_id,t,event_id
''').fetchall()
reference = []
last = {}
sessions = {}
for user, event, time in sorted(data, key=lambda r:(r[0],r[2],r[1])):
    if user not in last or time-last[user] > 10:
        sessions[user] = sessions.get(user, 0)+1
    last[user] = time
    reference.append((user,event,time,sessions[user]))
assert actual == reference
assert [r[3] for r in actual if r[0]=="A"] == [1,1,1,2]
print("sessions:", actual)
con.close()
```

## 7. 窗口改写的等价条件

<a id="db-3-detail-29"></a>

### 7.1 外层过滤与内层过滤不总可交换

如果先只保留当月记录，再求累计，月初看不到上月历史；如果先在完整历史上累计，再在外层选当月样本，就保留了之前贡献。这是不同输入集合导致的确定性差异，不是优化器偶然选择的问题。

一个容易证明安全的情形是过滤条件对整个分区恒定，例如只选择一组完整用户，且窗口分区也恰好按用户。被保留用户的所有输入行未改变，其窗口结果就不变。反过来，按金额、日期或状态删掉分区内部部分行，一般会改变前后关系和统计。

实际优化器能下推哪些条件，需要遵守这种语义约束。用户手动把一个外层条件挪到窗口输入前，不等于数据库承诺该改写安全。应先写出保留行的依赖集合，再证明被删行从未参与这些结果，否则保留原参考查询。

<a id="db-3-detail-30"></a>

### 7.2 排名前过滤决定选的是哪种第一名

若任务是“合格候选中分数最高的一条”，应先筛合格，再排名；若任务是“全体最高者是否合格”，应先排名，再检查资格。两者的结果在最高者不合格但第二名合格时不同。

版本选择则要判断资格针对版本还是逻辑事件状态。前文删除标记和事件时间移动要求先选最新可见版本，再过滤该状态；若任务明确定义为“历史上任何符合条件的版本”，又是不同目标。没有脱离业务定义的统一先筛或后筛口诀。

查询审阅中应让自然语言需求与 SQL 阶段一一对应。看到 ROW_NUMBER 等于一，不能只问排序是否稳定，还要问排的是哪个候选集合，以及同一个逻辑实体为什么可能有多行。这样才能发现看似合理的错误去重。

<a id="db-3-detail-31"></a>

### 7.3 窗口之前的连接会改变重复次数

假设每笔订单与多个标签、商品或活动记录连接，一条订单金额可能复制多次。之后按订单时间累计，求的是复制后的行总额，而不是原始订单总额。窗口保留行的性质并不会抵消连接基数膨胀。

可以在连接前把右侧聚合到所需键、用存在性查询避免展开，或在适当位置建立唯一事件关系。不能简单给 SUM 加 DISTINCT，因为两笔不同订单金额相同也应各贡献一次，去重数值会误删真实重复金额。

若确实需要明细级统计，就应把粒度和权重改为明细定义。优化与正确性都应围绕目标行身份，而不是通过看到重复后任意 DISTINCT 来让行数接近期望。下一章会进一步讨论多重集等价验收。

<a id="db-3-detail-32"></a>

### 7.4 逻辑阶段实验

本例在一月有十、二月有二十和三十，比较先筛二月和后筛二月的累计；同时核对三种排名。所有差异都有手算答案，用来防止重构时把合法 SQL 改成另一统计任务。

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.executescript('''
CREATE TABLE orders(id INTEGER PRIMARY KEY,month INTEGER,amount INTEGER);
INSERT INTO orders VALUES(1,1,10),(2,2,20),(3,2,30);
CREATE TABLE scores(id INTEGER PRIMARY KEY,score INTEGER);
INSERT INTO scores VALUES(1,9),(2,9),(3,7);
''')
before = con.execute('''
SELECT id,SUM(amount) OVER(
 ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
FROM orders WHERE month=2 ORDER BY id
''').fetchall()
after = con.execute('''
WITH totals AS(
 SELECT *,SUM(amount) OVER(
  ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS total
 FROM orders
)
SELECT id,total FROM totals WHERE month=2 ORDER BY id
''').fetchall()
ranks = con.execute('''
SELECT id,
 ROW_NUMBER() OVER(ORDER BY score DESC,id),
 RANK() OVER(ORDER BY score DESC),
 DENSE_RANK() OVER(ORDER BY score DESC)
FROM scores ORDER BY id
''').fetchall()
assert before == [(2,20),(3,50)]
assert after == [(2,30),(3,60)]
assert ranks == [(1,1,1,1),(2,2,1,1),(3,3,3,2)]
print("filter before / after:", before, after)
print("row_number / rank / dense_rank:", ranks)
con.close()
```

## 8. 时间单位、时区和窗口端点

<a id="db-3-detail-34"></a>

### 8.1 时间数值必须有统一单位与原点

把时间存成整数有利于清楚表达范围，但仍要约定单位、原点与时区。秒、毫秒和微秒混用会让窗口宽度差三个或六个数量级，SQL 语法却完全合法。字段名称可以标明单位，加载时还应检查合理范围。

UTC 时间点与当地日历日期回答不同问题。过去二十四小时不总等于当地前一个日历日，夏令时切换附近尤其明显；自然月长度也不同。若目标是当地日历窗口，应先定义地区与日历边界，再转换成可比较的时间点，而不是把每月固定当三十天。

文本时间还需确认排序与时间先后是否一致。不同偏移格式、精度或非统一补零的字符串，字典序不必等于绝对时刻序。不能把 ISO 风格外观当作任何文本都可直接比较的保证，应规范化表示并保留原始时区语义。

<a id="db-3-detail-35"></a>

### 8.2 闭开区间帮助避免边界双算

历史窗常定义为起点包含、预测时点不包含，便于连续区间拼接且排除当前事件。未来标签窗可以定义为预测时点开始到结束不包含，但是否包括同时间事件需结合业务可用顺序。用清楚不等式比“前七天”“未来一月”更容易验收。

如果每天批量预测一次，预测时间是批次生成时点还是业务日开始，会影响当天已发生数据是否可用。训练回放应采用与服务相同规则，不能在离线查询中读取全天数据，却声称模拟当天早上的决策。

时间精度转换还可能把本来不同的时刻合并为同级组。毫秒截成秒之后，严格先后关系变成并列，ROWS 次级键虽能重新排序，也不能恢复被丢掉的真实时间信息。应保留足够精度，或明确选择保守可见规则。

<a id="db-3-detail-36"></a>

### 8.3 标签成熟与特征可用分开定义

预测未来七天是否购买，需要观察到标签窗结束并考虑入库延迟。今天提取最近三天样本时，很多负标签尚未成熟，把未观察到购买直接当零会产生删失偏差。特征截至时间合法，并不意味着标签已完整。

可以保存标签窗口终点、观察截止时间和成熟标记。只用成熟样本训练时，还要注意成熟规则是否与结果或来源有关。正例可能更早被确认，负例必须等完整窗口，若简单只保留已确认记录，样本组成会偏移。

窗口 SQL 可以用 LEAD 或范围连接构造标签，但最终需要统一的成熟协议。特征与标签最好在逻辑上分开构建，再按样本键连接，以减少一条查询同时混合过去与未来的机会。即使放在同一工程，也应保持角色与时间界限清楚。

<a id="db-3-detail-37"></a>

## 9. 不同统计量需要不同窗口状态

<a id="db-3-detail-38"></a>

### 9.1 加权均值的分子分母必须来自同一集合

如果每条历史有权重，窗口均值可以由加权值之和除以有效权重和。金额缺失或权重无效时，分子与分母应按同一个资格掩码处理；只让 SUM(amount*weight) 忽略 NULL，却让分母包含所有权重，会把缺失金额隐式当零。

权重和为零时结果未定义，应给 NULL 或明确缺失规则，不能任意除一。权重可能表示频次、部署组成或可靠性，其统计含义不同；SQL 能计算同一个比值，不代表相同置信区间或有效样本数解释。

同样，AVG 忽略 NULL，COUNT(*) 不忽略行，二者搭配时需要知道缺失从哪里来。可以额外保存总历史数、有效测量数和权重和，让模型与审阅者区分样本量不足和数值本来较小。

<a id="db-3-detail-39"></a>

### 9.2 滑动去重计数不能总用首次标志求和

对完整前缀，给每个键的首次出现记一，再做前缀和，可以得到截至该位置的不同键数。在滑动窗口中，这个方法一般失效，因为某键的全局首次出现可能已经滑出，但它在当前窗中仍有后续出现。

例如序列甲、乙、甲，最近两条在第三位置包含乙和甲，不同键数为二；全局首次标志为一、一、零，最近两标志之和却为一。问题来自过期状态，不能用更稳定的排序修复。

有些数据库不支持在窗口聚合中直接使用 DISTINCT，本章 SQLite 就不能把普通 COUNT(DISTINCT) 机械加 OVER。可以用相关范围查询、适合的聚合连接或维护键频数状态，实现取决于产品与规模。应先用精确小表验证，再讨论性能或近似摘要。

<a id="db-3-detail-40"></a>

### 9.3 滑动分位数比滑动和需要更多信息

和与计数可以在窗口移入移出时加减，分位数需要有序分布状态，不能只保留上一个中位数。用每小时中位数再求日中位数通常不精确，因为小时样本量与尾部分布不同。

数据库是否提供分位数聚合或窗口接口，以及是否精确、怎样插值，都要按产品核对。没有相应功能时，可以用排序和排名构造参考，但成本与并列定义需要分析。一个函数名看起来相同，不代表各产品返回完全相同估计。

若接受近似，应说明秩误差或数值误差目标，并保证训练与服务采用相容定义。对于有长尾和大量同值的数据，这两种误差可能差异很大。窗口大小与摘要精度也是模型特征协议的一部分，不能只记录 SQL 文本而省略参数。

<a id="db-3-detail-41"></a>

## 10. 性能、验证和迁移边界

<a id="db-3-detail-42"></a>

### 10.1 窗口常需要排序与分区工作集

按分区与排序键建立合适索引，可能帮助有序读取，但不保证所有窗口都不再排序。多个不同排序、连接后顺序变化或复杂 frame，都可能需要临时结构。应看实际执行计划和工作负载，不把出现窗口函数直接等同线性流式算法。

前缀累计在合适顺序下可以只保存少量状态，含未来行或分区末尾的函数可能需要等待更多输入，精确分位数又需要不同状态。窗口声明相似不意味着内存需求相同，应该结合具体函数与执行实现分析。

分区极不均匀时，大用户可能主导排序与缓冲，平均每用户记录数无法描述峰值。可以检查最大分区、长尾和外部排序情况。分块执行也不能随意在用户中间截断，否则 LAG、排名和历史和会缺少前一块状态。

<a id="db-3-detail-43"></a>

### 10.2 测试应覆盖集合身份，而非只覆盖聚合数字

两个错误历史集合可能碰巧总金额相同，单看 SUM 无法发现。小规模参考最好同时返回参与事件身份、选中版本和边界条件，再核对计数、缺失与总量。正式大规模流程可用抽样回溯和结构摘要，但应保留调查路径。

有用的不变量包括每个样本一行、空历史不丢样本、分区不互相污染、同一时间组按预定规则处理，以及追加未来可用版本不改变旧特征。再加入删除、修订移动、NULL 与同分案例，通常比随机正常数据更能暴露逻辑错误。

如果优化后结果不同，应先定位哪一个样本、哪一条历史发生变化，再判断是精度、同分规则还是集合语义。不要只因为差异比例小就自动接受；一条边界记录可能正好决定标签或业务动作。

<a id="db-3-detail-44"></a>

### 10.3 迁移时重跑语义契约

数据库之间可能在 NULL 排序、日期运算、frame 支持、数值类型和公共表表达式优化方面不同。可以用显式 NULL 次序和统一时间表示减少歧义，但仍需要目标环境中的小表测试。SQL 标准概念与产品实现范围应分开说明。

本章代码实际运行在本地 SQLite 内存连接，不需要安装数据库服务；PostgreSQL 文档用于比较概念与方言，不意味着在本机执行了 PostgreSQL 计划。读者迁移时应记录版本，运行相同反例，核对结果后再进行大规模提取。

这些验证不是为每条查询增加繁琐流程，而是在特征影响模型结论前明确契约。一旦定义和最小反例固定，后续索引与排版变化就有稳定参考，能够更快判断变化是否仍在解决同一任务。

<a id="db-3-detail-45"></a>

## 11. 进阶：增量维护与研究中的时间协议

<a id="db-3-detail-46"></a>

### 11.1 增量更新不只是把新记录加进去

对于固定实体、只追加且无修订的前缀和，新记录可以直接加入状态；滑动窗还需要移除过期项。若有修订，应先移除旧可见版本的贡献，再判断新版本是否进入当前窗。若有删除，则需要撤销相应贡献，不能仅忽略删除行。

因此在线特征状态应知道每个逻辑事件目前贡献了什么，以及何时过期。只保存一个累计总数，可能无法在修订到来时正确撤销。对于均值，需要计数与和共同维护；对于不同值数，还需键频数；对于分位数，需要更丰富分布状态。SQL 窗口与流式程序应实现同一个数学集合，状态组织可以不同。

乱序到达使维护更复杂。事件时间很早但现在才可见的新记录，可以影响现在之后的预测，不应反向改变已经真实输出的过去预测记录。若研究选择事后重算修订真值，应另建明确的数据版本，而不是覆盖当时特征并继续称它为当时观测。

<a id="db-3-detail-47"></a>

### 11.2 水位是处理协议，不是时间真相

流式水位常表达系统认为某个时间之前事件已足够完整，但它依赖延迟模型与允许迟到政策。超过水位仍可能有真实迟到记录，系统需要决定丢弃、旁路、修订或重算。水位不能自动证明所有历史完整。

离线数据库包含全部迟到事件时，若直接按事件时间窗口聚合，得到的可能是事后完整历史，而非当时可用历史。要与线上对齐，应记录可用时间与迟到处理方式。所谓离线线上一致，不只是两个系统都写了过去七天，而是对迟到、修订和边界有同样协议。

重放实验可以故意延迟某些记录，观察线上状态与离线 as-of 查询是否一致。把时间戳、版本选择与状态更新顺序固定，可以把问题缩小为可验证状态机，而不是在模型分数下降后才猜测是否发生泄漏。

<a id="db-3-detail-48"></a>

### 11.3 窗口结果的单调性需要额外条件

在固定数据上，非负金额的包含当前前缀和随顺序不下降，这是来自集合扩张与非负贡献的性质。若金额可负，数值可能下降；若窗口滑动，旧记录会退出，也不单调；若版本修订或删除改变状态，即使原始金额都非负，累计也可能回落。

因此测试断言必须与目标条件匹配。不能把“用户历史越来越多”当作所有窗口计数必然增长的理由；同样，某个特征下降不自动说明数据损坏。先判断当前计算的是固定前缀、有限时间窗还是可修订状态，再选择不变量。

相对稳定的不变量通常是身份守恒、可见性与边界。例如同一预测样本只能使用一个逻辑事件版本、所有贡献都满足两个时间条件、空历史样本仍保留。这些不依赖金额符号，更适合用来保护通用提取流程。

<a id="db-3-detail-49"></a>

### 11.4 目标编码还要约束标签何时已知

按历史类别计算目标均值，看起来只使用过去行，仍可能泄漏。如果一条历史事件的标签需要未来七天才确定，事件发生在当前预测之前，并不表示标签当时已知。应对标签可用时间独立过滤，必要时只使用成熟结果。

同时，训练验证划分也会影响允许的信息。随机交叉验证中，若用全数据标签先算类别均值，再划分训练验证，验证标签已进入特征；时间划分中，若用未来成熟的历史标签回填过去，也会泄漏。时间约束与折内拟合是不同维度，都要满足相应实验设计。

可把特征定义写成“预测时允许信息的函数”，再逐字段审查来源。日期早于预测只是一个必要检查，版本、标签成熟和外部来源同样属于信息条件。窗口语法表达的是一部分约束，不能凭一个 PRECEDING 关键字宣布整个流程因果合法。


<a id="db-3-detail-50"></a>

### 11.5 按日预聚合何时与原始窗口等价

若窗口只覆盖完整自然日，事件版本和可用状态已固定，且目标是可加统计量，可以先按用户与日保存计数、有效值数与总和，再在日级表上累计。理由是原始历史集合恰好分成互不重叠的完整日桶，求和与计数可先桶内再桶间合并。均值应由全窗总和除有效数，不能等权平均各日均值。

如果左边界或右边界切过某个日桶，完整桶汇总就不足以恢复被切开的部分。可以让中间完整桶使用摘要，边界桶仍查明细，或者选择与业务完全对齐的桶定义。若每个样本截止时点不同，同一个日桶也可能对不同样本包含不同的可用版本，今天计算的最终日总额不能直接当成过去任何时点都已知的摘要。

这个等价条件同样适用于预聚合连接优化。必须先证明桶内记录的资格不再依赖后续样本，且摘要保存了最终统计需要的充分量。若后续还要按事件属性过滤、选最后非空值或做精确不同值计数，只有日总和与计数通常不够。性能优化应从可合并性证明出发，而不是看到明细大就先随意分组。

<a id="db-3-detail-51"></a>

### 11.6 时间维表连接需要区间唯一性

有些版本表将每个状态展开为有效起止区间，方便按样本时间连接。这个表示可以减少重复排名，但应保证同一实体在同一查询时点至多命中一个合法区间；区间重叠会复制样本，间隙则产生缺失。结束与开始端点若都包含，相邻版本边界还可能双重命中。

业务有效区间与系统可用区间仍然不同。一个今天补录、业务生效于上月的版本，可以覆盖上月业务日期，却不应进入上月当时的预测。若需要完整双时间重放，应同时维护相应维度，或使用清楚的版本选择参考。把一个更新时间字段改名为生效时间，并不能创造缺失的历史信息。

验收可以先枚举少量样本时点，计算每个时点匹配数，再对照逐版本参考。特别检查版本切换精确时刻、删除状态和补录记录。若预计算区间与参考逐样本选择不一致，应先修复版本转换，再讨论索引和吞吐；否则快查询只会更稳定地输出错误特征。

## 12. 进阶练习与详细解析

<a id="db-3-detail-53"></a>

### 12.1 练习一：窗口之后究竟有几行

**题目。** 六条订单先按用户与月份分成三组，再对分组金额按用户计算前缀和。窗口阶段保留六行还是三行？为什么“窗口不折叠行”不能给出六行？

**解析。** 窗口接收的是分组后的三行，所以保留三行。它不撤销上一阶段的聚合，也不认识原订单身份。检查行粒度应从整个查询的数据流开始，而不是只观察是否出现 OVER。若希望每订单一行，应在明细关系上计算相应窗口，并避免前面先折叠为月统计。

<a id="db-3-detail-54"></a>

### 12.2 练习二：同时间前一行是否可见

**题目。** 两个事件时间都为十，编号为一与二。按时间、编号排序并用 ROWS 到前一行，第二行会读到第一行吗？这是否证明业务上它可见？

**解析。** 会，因为行顺序明确把第一行放在前面。但编号可能只是数据库写入或任意身份，不一定代表真实观测先后。若业务要求严格早于时间十，两行都不应读取同时间事件，应使用相应集合条件或同级组排除。确定计算顺序不等于获得真实信息可见性。

<a id="db-3-detail-55"></a>

### 12.3 练习三：COUNT 与 SUM 的空值

**题目。** 一个窗口有三条历史，金额全为 NULL；另一个窗口完全为空。COUNT(*)、COUNT(amount) 与 SUM(amount) 分别如何区分两者？

**解析。** 前者记录数三、已知金额数零、和为 NULL；后者记录数零、已知数零、和同为 NULL。若仅保留填零后的和，两种情况无法区分。应根据特征需要保留历史存在性与有效值计数，而不是让一个 NULL 或零承担所有缺失原因。

<a id="db-3-detail-56"></a>

### 12.4 练习四：当月过滤的差异

**题目。** 一月金额十，二月二十与三十。要求只输出二月，但累计含全部过去。WHERE 放在窗口同一层与外层，各得到什么？

**解析。** 同层先删一月，二月累计为二十、五十；外层保留完整累计后筛选，为三十、六十。后者符合题目。优化时移动条件可能改变统计总体，应保留手算小表作为参考。只有能证明删除行不参与保留结果时，过滤与窗口才可以交换。

<a id="db-3-detail-57"></a>

### 12.5 练习五：给排名加唯一键的副作用

**题目。** 分数九、九、七，要保留所有最高分者。把 RANK 的排序写为分数降序、唯一编号升序，是否仍保留前两条并列第一？

**解析。** 不一定，唯一编号让完整排序元组不同，前两条不再同级，名次被分开。要保留分数并列，应只按分数定义相应排名；若只想取一条，用 ROW_NUMBER 加稳定编号更合适。排名表达式不是单纯显示顺序，它定义同分等价关系。

<a id="db-3-detail-58"></a>

### 12.6 练习六：LAST_VALUE 的范围

**题目。** 按时间排序的三个值十、二十、三十，默认截至当前范围时，第一行 LAST_VALUE 为什么可能是十而非三十？用于过去预测时能否直接改成整个分区末尾？

**解析。** 函数取当前 frame 尾部，不是名字里隐含全分区尾。扩到整个分区可以得到三十，但若第三条发生在预测之后，就泄漏。先确定要查询的是历史最后值还是离线全序列最后值，再写边界；函数名不能代替信息条件。

<a id="db-3-detail-59"></a>

### 12.7 练习七：窗口单位

**题目。** 时间列以毫秒存储，RANGE 偏移写七，能否表示过去七天？正确数值是否一经换算就解决所有时区问题？

**解析。** 它只表示七毫秒。若目标是连续七乘二十四小时，应按同一单位换算；若目标是当地七个日历日，还需时区与日历边界。夏令时、自然日切换和时间精度可能改变集合，不能仅把一个常数乘大就声称语义完全相同。

<a id="sec-7-1"></a>

<a id="db-3-detail-60"></a>

### 12.8 练习八：最近十行与十天

**题目。** 高频用户一天有一百条，低频用户一个月一条，最近十行是否具有可比的时间覆盖？如果模型确实需要最近十次行为，应强行改成十天吗？

**解析。** 时间覆盖不可比，但不代表行窗口本身错误。若任务关注最近十次交互，按行正是目标；若关注固定时间活动强度，应按时间范围。要选择符合问题的集合，并可额外保存覆盖时长与历史计数，不能把两种窗口按名称相近视为等价。

<a id="db-3-detail-61"></a>

### 12.9 练习九：版本先筛还是先排

**题目。** 一事件旧版本时间七，新版本时间十五且在预测十五之前已可用，历史要求事件时间小于十五。先按时间删新版本再排名会怎样？

**解析。** 会让旧版本七成为剩余第一，错误复活事件。应先选最新可见状态，再应用时间范围和删除条件。若新版本是删除标记，先删标记同样会复活旧值。排名对象是逻辑事件的状态，不能把每个版本当成可独立任选的候选历史。

<a id="db-3-detail-62"></a>

### 12.10 练习十：迟到事件的两种历史

**题目。** 事件发生在周一，周三入库，模型在周二预测。今天回放时能否把它计入周二特征？事后完整事件分析是否也必须排除？

**解析。** 模拟周二真实预测时应排除，因为当时不可读。事后完整事件分析可以计入，但它回答的是修订后的事实历史，不能冒充当时观测。两种数据产品都可能有价值，应独立版本化并写清目标，避免为追求完整而抹掉可用时间。

<a id="db-3-detail-63"></a>

### 12.11 练习十一：滑动不同值数

**题目。** 序列甲、乙、甲，最近两条的不同值数为多少？用全局首次标志的一、一、零做最近两条和会得到什么？

**解析。** 正确为二，首次标志法给一。甲首次出现已退出，但最新甲仍在窗内，说明全局首次信息不足以维护滑动去重。可以维护窗内键频数，或用准确范围去重查询。一个在完整前缀成立的技巧，不必在滑动集合中成立。

<a id="db-3-detail-64"></a>

### 12.12 练习十二：权重分母的缺失掩码

**题目。** 两行权重各一，金额分别十与 NULL，若分子只累计已知金额乘权重，分母却是二，会把缺失解释为什么？已知值加权均值应是多少？

**解析。** 得五相当于把缺失金额按零贡献且仍占权重。若目标是已知金额均值，分母也应仅包含已知有效行，为一，结果十。两种目标可以定义，但应明确，最好保留有效权重和。NULL 自动忽略规则不能替使用者确定缺失模型。

<a id="db-3-detail-65"></a>

### 12.13 练习十三：会话边界

**题目。** 阈值十，时间为零、十、十一、三十二，约定严格超过十才新会话，会话号为何是一、一、一、二？改成至少十时会怎样？

**解析。** 相邻间隔为十、一、二十一，只有最后超过十；改为至少十时，第二条也开新会话，结果一、二、二、三。应比较相邻间隔，而不是从会话起点计算总跨度，除非业务明确选择另一种定义。边界与状态机需要一致。

<a id="db-3-detail-66"></a>

### 12.14 练习十四：快照不能代替历史版本

**题目。** 今天用同一个事务快照读取所有表，为去年预测连接今天会员等级。数据库一致性正确能否保证无泄漏？

**解析。** 不能。快照约束读取的数据库时刻，会员等级还可能来自去年之后的升级。需要按历史预测时点选择当时有效且已可用的版本。事务、业务有效时间与可用时间是三个维度，正确其中一个不能替代另外两个。

<a id="db-3-detail-67"></a>

### 12.15 练习十五：可交换过滤的证明

**题目。** 窗口按用户分区，只保留用户甲的全部记录，能否先筛用户再算窗口？若只保留甲的本月记录，证明为什么不同？

**解析。** 第一种对甲分区没有删任何行，所有依赖集合不变，结果可交换；第二种删除了甲分区内部历史，可能改变累计、排名与前行。这个证明依赖完整分区保留，不是 WHERE 条件越简单就一定能下推。应根据窗口依赖判断。

<a id="db-3-detail-68"></a>

### 12.16 练习十六：时间目标编码

**题目。** 一条过去事件的标签需要七天后才成熟，当前预测只晚两天。用它的最终标签算历史类别均值，虽然事件时间在过去，为什么仍可能泄漏？

**解析。** 事件已发生不等于结果已知。最终标签包含未来五天信息，应该按标签可用或成熟时点过滤。还需确保目标编码在相应训练折内拟合，避免验证标签进入统计。时间先后、标签成熟和折内信息边界应分别核对。

<a id="db-3-detail-69"></a>

## 13. 综合研究与验收

<a id="db-3-detail-70"></a>

### 13.1 从参考集合走向增量系统

选择一份含修订、删除和迟到的小事件日志，先用本章逐样本查询生成精确参考，再实现在线状态维护。按可用时间驱动输入，在每个预测点比较事件身份、版本、计数和总量，记录何时需要撤销旧贡献或移除过期项。

随后改变事件到达顺序但保留真实可用协议，检查哪些变化应影响结果，哪些只影响执行。若使用水位或允许迟到上限，应明确超限记录政策，并用专门反例检验。验收不是平均误差足够小，而是每一种业务边界都有一致解释。

<a id="db-3-detail-71"></a>

### 13.2 设计最小回归表而非巨大随机表

一个高质量回归表可以只有少量行，但应覆盖首次事件、同时间组、空金额、未知身份、未来可用版本、删除和时间移动。每个反例应有手算答案与失败原因，这比只用百万条正常数据看总量是否接近更有辨别力。

优化后若更换窗口、相关子查询或预聚合方案，就在同一表上核对。然后再做代表规模性能实验。通过把语义正确性与资源测量分开，可以避免把少算历史、错误去重或漏样本当成查询优化收益。
