# 第 2 章 进程日志远程与环境管理

本章围绕一个具体目标组织知识：把一次可能运行很久的研究实验，变成能够定位、观察、停止、恢复和验收的任务。进程管理不是记住几个查看命令；你需要区分程序、进程、线程、会话和产物，理解退出状态与日志的不同含义，也要知道远程登录和环境继承怎样改变实际运行条件。

## 1. 从一段程序到一个可管理任务

<a id="linux-2-detail-2"></a>
### 1.1 程序、进程和线程不是同一个对象

程序是可执行代码与相关资源的静态表示；进程是一次执行实例，拥有地址空间、描述符、身份与调度等状态。同一个程序可以启动多个进程，每个进程有不同输入和输出。线程共享所属进程中的许多资源，但具有自己的执行上下文；多个线程访问共享数据时，还需要应用层同步。只知道可执行文件名字，不能唯一识别一项实验。

研究任务又比进程更大。一次训练可能包含启动器、主进程、数据加载子进程、评估进程和日志收集器；某个阶段结束后，另一个阶段可能继续运行。任务身份应该由稳定的运行标识表示，而不是永久绑定某个进程号。进程号会复用，某个数字今天属于训练，稍后可能属于完全不同的任务。对旧日志里的数字直接发送信号，有误伤的可能。

最小任务记录应包括运行标识、启动时间、父子关系、实际命令参数、工作目录、代码和数据版本、输出目录。若由调度器管理，还应记录调度器作业标识。它们共同回答“这是谁”，而资源指标回答“它现在怎样”。缺少任务身份的监控截图，往往无法与最终结果建立可靠关联。

进程状态只描述某个瞬间。一个处于睡眠状态的进程可能正在正常等待输入，一个占满处理器的进程也可能只是错误地循环。解释状态必须结合预期阶段和时间变化。模型下载、数据解压、首轮编译和正式训练具有不同资源模式，不能用同一个静态阈值判断所有阶段是否健康。

<a id="sec-1-1"></a>
<a id="linux-2-detail-3"></a>
### 1.2 启动成功、退出正常与产物完成

启动器成功创建进程，只证明操作系统接受了启动请求，不证明依赖加载成功，更不证明训练完成。进程正常退出，说明它按自己的退出约定结束；如果程序捕获异常后错误地返回零，调用者仍可能得到虚假的成功。产物完成则是业务层结论，需要验证文件集合、格式、维度、记录数和实验标识等约定。

可以把任务状态设计成“已创建、已启动、输入已验证、计算中、输出待验收、已发布、失败或中断”。每个状态都应有明确进入条件，不能仅靠一个存在的目录推断。输出目录在任务开始就创建非常常见，因此“目录存在”几乎不能证明任何后续阶段完成。完成标记宜在验证通过之后发布，并包含可核对的版本信息。

退出码也应有文档。非零一般表示程序未按正常成功路径完成，但具体数值的含义由接口约定；被信号终止的状态在不同启动层中又可能被重新编码。Python 子进程接口在 POSIX 环境通常用负数表示导致结束的信号，而 Shell 观察到的状态表达可能不同。比较日志时应注明来自哪一层，不要把同一个数字解释成跨工具的通用错误类型。

产物验收不应过度依赖日志中的最后一句话。缓冲可能让它延迟出现，写入失败可能发生在它之后，日志复制也可能不完整。更可靠的方式是让产物携带自己的模式版本、输入标识和必要摘要，并让独立验证步骤检查。日志解释过程，产物证明结果，两者相互补充。

<a id="linux-2-detail-4"></a>
### 1.3 父子关系、等待和僵尸状态

一个常见的进程创建模型是先创建子进程，再在子进程中执行目标程序。执行新程序并不必然改变进程号；它替换的是执行映像。父进程通常通过等待接口取得子进程退出状态，并让系统回收保留的退出信息。这一过程说明“子进程已经结束”和“父进程已经处理其结束状态”并不是同一时刻。

僵尸进程是已经结束、但退出信息尚未被合适的父级等待回收的进程状态。它不再执行原业务代码，因此不是继续占满处理器的训练任务；但大量未回收条目仍会消耗进程管理资源，反映父进程管理缺陷。向一个已经结束的僵尸发送强制终止信号，不能替代父进程正确等待。

父进程先退出时，存活的子进程通常会被其他合适的进程接管，具体可涉及初始化进程或子收割者机制。不能据此假设“父进程死了，所有子进程一定死”，也不能反向假设“所有子进程一定会继续”。终端挂断、进程组信号、服务管理器和容器生命周期，都可能另外影响它们。

对研究程序，明确负责管理整组子进程的主体尤其重要。异常时若只结束主进程，数据加载器和辅助进程可能继续持有文件或设备资源；若不加辨别地匹配进程名批量结束，又可能影响其他实验。推荐从创建开始保存自己拥有的子进程对象或作业标识，并在清理路径中逐个等待确认。

## 2. 会话、进程组和信号

<a id="sec-6"></a>
<a id="linux-2-detail-6"></a>
### 2.1 终端按键为什么会影响一组进程

交互终端通常有一个前台进程组，终端产生的中断等信号可发往这个进程组，而不是只发给看起来最显眼的那个进程。流水线包含多个进程时，它们可能作为一组参与前台作业控制。这解释了为什么按中断键可能同时影响多个流水线阶段，也解释了为什么程序放到后台后行为会改变。

会话组织进程组及控制终端关系；进程组提供向一组进程发送信号的管理边界。它们与应用层任务身份并不完全重合。一个复杂启动器可以创建新的会话或进程组，服务管理器也可能采用更强的资源归属边界。因此，管理方案应根据实际启动结构设计，而不是由“这个任务只有一个终端窗口”推断进程归属。

把命令放到后台，通常只改变 Shell 等待和作业控制方式，并不会自动创建可靠的持久任务。关闭登录会话后，终端关联、信号和描述符都可能影响后台程序。可靠运行需要明确终端依赖、输入输出位置和监督机制；长任务宜交给现有且获授权的任务管理设施，而不是靠一个后台符号表达所有需求。

<a id="linux-2-detail-7"></a>
### 2.2 信号是请求与通知，不是远程函数调用

信号可以用于终止请求、挂断通知、停止与继续等机制。某些信号可由程序捕获或忽略，某些不能被捕获。温和终止给程序机会结束当前步骤、刷新状态和关闭资源；强制终止不提供用户态清理机会。发送调用成功只说明信号请求被内核接受，不能立即证明目标已退出或产物完整。

标准信号通常不是可靠计数队列。同一种信号在阻塞期间多次产生，可能合并为一个待处理状态；不能用“每来一次信号就处理一个样本”的方式建立通用任务队列。需要明确计数、顺序和负载的通知，应使用适当的队列、管道或其他通信机制，并处理容量与背压。

信号处理程序还存在安全边界。底层异步信号处理上下文中，许多普通库函数不能随意调用；Python 则由解释器提供自己的处理机制，通常在主线程执行 Python 级处理器，响应时机可能受到执行状态影响。教学示例中设置一个停止标志，再在正常主循环里保存和退出，是容易解释的模式；它不等于证明任意复杂框架都能瞬时响应。

停止请求也需要期限。如果程序在一个无法很快返回的步骤中，温和退出可能延迟。监督者应先发请求，在合理期限内等待，再按任务协议决定进一步措施；强制结束之后必须检查并隔离未完成产物。对于不可中断等待等内核状态，信号也不保证立刻让进程消失。正确诊断应依据实际状态，而不是连续重复发送同一个信号。

<a id="sec-2-1"></a>
<a id="linux-2-detail-8"></a>
### 2.3 停止、暂停和检查点具有不同语义

暂停进程会阻止它继续获得正常执行机会，但不等于保存了可跨机器恢复的状态。内存仍属于原进程，打开资源也可能继续占用；依赖的远程服务或锁可能在暂停期间超时。检查点则把应用认为必要的状态序列化到持久介质，恢复时重新构建执行。因此“先暂停，再关机”不能自动成为可靠恢复方案。

训练检查点除了模型参数，还可能需要优化器状态、步数、学习率调度器、随机数状态、采样位置和数据版本。遗漏其中一些内容，仍可能可以继续训练，但轨迹与原任务不完全一致。恢复目标应说清楚：只恢复一个可用模型、近似延续训练，还是尽力保持逐步相同的轨迹；不同目标需要不同保存范围。

保存本身也会失败。磁盘满、共享存储中断和序列化异常，都可能留下一个名字正常却内容不完整的文件。采用临时对象写入、关闭验证后发布，可以减少半成品被误认为正式检查点。多文件检查点还需集合级发布协议。信号处理器只设置停止请求，主循环在一致状态点保存，是避免随意打断复杂更新过程的重要方法。

### 图解：进程、父子关系与进程组是不同结构

![进程、父子关系与进程组是不同结构](images/02-advanced.svg)

左图先固定创建关系：100 创建 101，101 创建 102 与 103；102 在满足条件时调用 `setsid`，再创建 104。设 100 已是会话 100、进程组 100 的首进程；101、103 留在原组，102 建立会话及组 102，104 继承它们。图中的 ID 是教学设定，不是要求在机器上寻找或终止这些真实 PID。

右图按当前 PGID 重新分组：组 100 的成员为 100、101、103，组 102 的成员为 102、104。分组不会改写“102 曾由 101 创建”这一亲缘关系；创建树中相邻的节点，后来可以属于不同会话和组。只沿父子树找任务与只向一个组广播，因此回答不同问题。

假设目标仍存活且调用者有权限，向 PID 100 发送信号只针对该进程；向 PGID 100 发送则选择三个原组成员，不包含已经离开的 102，也不包含它后来创建的 104。[Linux kill 手册](https://man7.org/linux/man-pages/man2/kill.2.html)规定，负且小于 −1 的目标参数按对应进程组解释，而非递归遍历后代；[setsid 手册](https://man7.org/linux/man-pages/man2/setsid.2.html)说明建立新会话与新组的条件。因此不能把一次组发送概括为“所有子孙都已取消”。

Python 的 `start_new_session` 在 POSIX 上对应这类会话安排，但 Windows 具有不同的进程管理接口。即便组成员选择正确，信号还可能被捕获、延迟或按其性质忽略，发送成功也不是清理完成的证据。可靠作业管理应在创建时记录所有权、组或作业边界，在取消后等待并确认退出；如果任务允许自行离组，原组 ID 就不能继续当作完整的生命周期清单。

## 3. 日志是具有代价的数据流

<a id="linux-2-detail-10"></a>
### 3.1 缓冲改变可见时间

程序输出到终端时和输出到普通文件或管道时，运行库可能采用不同缓冲策略。于是交互运行每步都有进度，重定向后却长时间看不到内容，并不一定说明进程卡住。数据可能仍在用户态缓冲区里。显式刷新、选择适当的日志库或采用行缓冲，可以改善可见性，但频繁刷新也会增加系统调用和存储压力。

用户态刷新只把内容继续交给更下层，并不自动等于落到稳定介质。日志被日志收集器接收、被操作系统接受和在崩溃后仍能恢复，是不同保证。多数训练进度日志不需要每条都同步落盘；关键审计事件和最终清单可能有不同要求。应按用途设计，而不是用同一个“立即写”概念混合所有层次。

进度条还可能使用回车覆盖同一行，捕获到文件后会出现看似重复或缺少换行的记录。机器日志最好每条是独立、可解析的记录，把交互显示与结构化事件分开。解析时不要假设终端上每次看见的变化都对应文件中的完整新行。

<a id="linux-2-detail-11"></a>
### 3.2 日志字段怎样支持因果推理

一条有用日志应说明运行标识、阶段、事件、必要的计数和上下文。时间戳帮助定位外部事件，单调时间间隔帮助衡量持续时长，步数或序号帮助判断是否前进。墙上时间可能被同步调整，因此测量耗时宜使用单调时钟；跨机器比较还需要承认时钟偏差，不能只按数字排序就断言先后因果。

错误记录应保存异常类别和调用上下文，同时避免把凭据、访问令牌或整份敏感数据作为调试便利打印出来。可复现性并不要求公开所有环境变量的值。记录需要的配置键、非敏感值和版本即可；秘密引用可以用标识代替明文。日志的研究价值来自能解释决策和状态，而不是越多越好。

阶段日志宜区分“开始”“成功”“失败”“耗时”和“处理数量”。例如数据加载阶段只打印开始，后续无记录，诊断范围仍然很大；若记录文件枚举完成、解码完成和批次构建完成，就能更准确定位停顿。指标过密也会产生噪声，应围绕可能失败的边界建立少而清楚的事件。

<a id="linux-2-detail-12"></a>
### 3.3 日志轮转、并发与收集失败

长任务不能假设日志永远增长而不影响系统。写满磁盘会进一步影响检查点和缓存。可以选择适当的轮转、压缩与保留策略，但要结合应用对描述符的持有方式；第一章已经说明，改名后原进程可能继续向旧对象写入。日志策略应与写入程序共同验证。

多进程直接写同一个普通文件，记录可能交错，不能轻易把一次高级日志调用当作跨进程原子事务。可以由单独收集进程序列化事件，或者每个工作进程写自己的日志并在记录中携带关联标识。收集器自身也会失败或阻塞，因此关键产物验证不能完全依赖它。

“没有新日志”需要结合其他证据。可能是缓冲、计算阶段很长、输出路径改变、日志收集器故障，也可能是死锁。先查看阶段预期，再观察进程资源和输出计数的时间变化，最后设计有针对性的最小测试。仅靠反复刷新日志窗口，不能区分这些假设。

## 4. 环境是进程输入的一部分

<a id="linux-2-detail-14"></a>
### 4.1 环境变量、搜索路径和继承方向

进程通常在创建时获得一份环境变量映射，子进程可以继承并修改自己的副本。子进程改环境，不会自动回写父进程；一个脚本在子 Shell 中设置变量，结束后也不会神奇地改变启动它的终端。理解继承方向，就能解释为什么“运行了激活脚本”与“在当前 Shell 中执行激活操作”可能产生不同结果。

命令搜索路径决定输入一个简单命令名时找到哪个程序。两个终端都能运行同名解释器，并不证明用的是同一个文件或相同版本。应同时记录可执行文件的真实位置、解释器版本和所需库的版本。若通过完整路径调用解释器，可以降低搜索歧义，但仍要检查它加载的动态库、模块路径和配置。

环境里还有区域设置、时区、线程数、设备可见性、缓存目录和代理等输入。只记录依赖包清单，会漏掉其中影响结果或运行行为的部分。记录应该围绕实验实际依赖，而不是盲目倾倒全部环境。运行前可以输出一份经过筛选的配置清单，既降低噪声，也避免暴露不必要的秘密值。

修改环境后必须确保目标进程确实重新启动。已经运行的进程不会因为另一个终端激活了新环境，就自动切换解释器或替换加载中的库。热更新还可能引入新旧代码混用，应按应用支持的方式处理。诊断时把“磁盘上现在是什么”“新终端会找到什么”“已有进程实际加载了什么”分别检查。

<a id="linux-2-detail-15"></a>
### 4.2 虚拟环境与锁定依赖能保证到哪里

语言虚拟环境通常隔离一部分解释器与包搜索路径，不等于隔离操作系统内核、设备驱动和全部系统库。把依赖包列表复制到另一台机器，可以改善重建条件，却不能证明数值结果逐位一致。硬件、底层数学库、并行归约顺序和非确定性算子，仍然可能改变结果。

依赖锁定应记录解析后的具体版本和来源，而不是只有宽泛版本范围。若使用可编辑安装或本地修改，包版本号可能不反映实际代码，应记录代码提交和工作区状态。依赖中有编译扩展时，还应说明与运行平台相关的构建条件。可复现环境是一组条件，不是一条安装命令的名字。

配置的优先级也要固定。默认值、配置文件、环境变量和命令行参数同时存在时，应明示谁覆盖谁，并记录最终解析值。只保存原始配置文件，会漏掉命令行覆盖；只保存命令字符串，又可能漏掉环境变量。实验产物宜包含最终有效配置，再链接到原始来源，以便解释一个值为什么这样取。

有些环境变量只在库导入或运行时初始化时读取。把线程数在初始化之后再改变，可能没有预期效果。研究性能时，应在启动入口设置并记录，使用小型验证确定实际行为。不要以“变量已经打印出来”为依据，就声称底层库一定采用了该值。

<a id="linux-2-detail-16"></a>
### 4.3 随机种子与数值复现的层次

固定一个随机种子，只约束对应随机数生成器的状态。程序可能同时使用语言标准库、数值库、框架和数据加载工作进程中的多个生成器；它们各自需要受控。子进程继承状态还可能使多个工作进程意外生成相关序列，因此种子分配应与工作单元身份对应，并记录分配策略。

即使随机序列一致，执行顺序变化也可能改变浮点结果。浮点加法不满足任意重排下的结合律，多线程归约、设备内核选择和异步执行都可能影响次序。要求逐位一致时，需要检查框架与硬件支持的确定性路径；要求统计复现时，则应使用多次运行和合理误差范围。两种目标都可以有价值，但不能混用完成标准。

记录环境也不是为了把一切差异都归咎于系统。若不同种子下结果变化很大，应先研究模型、数据和评估方差，而不是把唯一一次最佳结果当作稳定结论。环境管理与统计设计互相配合，前者固定已知条件，后者衡量即使条件合理仍存在的变化。

<a id="visual-02-mechanism"></a>

### 图解：环境继承是创建子进程时的一次传递

![环境继承是创建子进程时的一次传递](images/02-mechanism.svg)

图中每条竖线属于一份不同的环境状态，弯箭头只出现在明确的启动事件；子进程二的生命线直到最后一次启动才开始。独立验证用标准输出确认子进程一已取得 A，再将父级映射改为 B，并经标准输入释放旧进程继续读取。这样观察到“旧进程仍是 A”不依赖固定睡眠时长，也不会把尚未启动误当作继承失败。子进程随后改成 C，父级映射仍保持 B，新启动的第二个进程取得 B。

图把“继承一次”拆成四个可复算状态。为避免改变父进程的真实全局环境，设启动器持有一份独立环境映射 `env`，并通过 `subprocess.Popen(..., env=env)` 显式传入。起初变量为 A，子进程一取得 A；父级随后把映射改为 B，已启动子进程一仍为 A；子进程一在自己的环境中改为 C，也不会回写父级。此后用当前映射创建子进程二，它取得 B，而不是 A 或 C。

关键是每个箭头都对应一次明确启动，不存在一个把三份环境自动同步的共享变量。第 6.1 节实验已经验证子进程修改不会回写映射；图增加第二次启动，帮助解释“新任务用新配置，旧任务仍在旧配置上运行”的常见现象。若希望旧任务更新配置，需要它显式读取配置文件、接收消息或重新启动，不能仅修改另一个终端或启动器的值。

[Python subprocess 的 env 文档](https://docs.python.org/3.11/library/subprocess.html#subprocess.run)说明，显式映射定义新进程的环境，替代默认的当前进程环境继承。图中的 `env` 因而是一份启动配置，而不是所有进程可共同写入的环境服务；真实配置热更新通道应另行定义。

## 5. 远程会话中的身份和边界

<a id="linux-2-detail-18"></a>
### 5.1 登录、命令执行和文件传输分开理解

SSH 提供经过认证和加密的连接机制，但“能登录”只验证了连接与身份认证中的一部分条件。远程进程的工作目录、环境和权限仍然由远端设置及启动方式决定。交互登录与直接执行远程命令，可能经过不同的 Shell 初始化路径，所以本地终端中有效的激活操作，不能自动移植为远程非交互任务的环境。

远程执行还有两层解析问题：本地 Shell 先处理一遍参数，远端的命令文本又可能由远端 Shell 解释。路径中有空格或特殊字符时，必须明确每一层收到什么。对复杂流程，优先把经过审查的脚本和配置放在远端固定位置，再通过清楚的参数入口启动；不要靠不断增加反斜杠来维持不可理解的多层拼接。

远程文件传输与远程命令执行也有独立的成功条件。传输工具退出成功，说明它按自己的协议完成，并不证明数据版本与目标任务要求一致。大型数据可以结合大小、摘要和版本清单验证；多个文件构成一个数据集时，还需要确认集合完整。不要因为目录里已经出现文件名，就让训练进程立即开始读可能尚在传输的对象。

<a id="linux-2-detail-19"></a>
### 5.2 主机身份、凭据与最小暴露

连接加密不自动证明连接的是预期主机。主机密钥验证用于确认远端身份，首次建立信任时需要通过可靠渠道核对，而不是为了省事永久关闭检查。主机密钥发生变化可能有合理运维原因，也可能意味着连接目标或信任关系发生了变化；应按组织提供的流程核验，不要把告警机械忽略。

认证密钥与远端主机密钥承担不同角色。用户认证证明你有权以某身份访问，主机验证证明远端是谁；把二者混为“有密钥就安全”会漏掉另一半。私钥、访问令牌和转发的认证能力也不应出现在学习笔记、代码仓库或运行日志中。环境清单需要记录使用的认证方式和必要标识，而不需要复制秘密材料。

代理转发和端口转发会扩展连接所能访问的边界。它们有正当用途，但在没有明确任务需求时不应随意开启。研究者首先要能画出哪些进程在哪台机器上、哪个端口由谁监听、哪些凭据可被哪一侧使用。图画不清时，连接“能用”并不等于行为可解释。

本章没有发起远程连接，也没有修改认证配置。这里的机制说明应在获授权的实际服务器上按其管理规范应用。学习实验完全可以先用本地子进程验证参数、环境和日志继承，再把真正需要网络条件的部分单独验证，而不把两类证据混在一起。

<a id="linux-2-detail-20"></a>
### 5.3 会话断开后，任务究竟依靠谁存活

远程连接断开可以影响终端、Shell、标准流和相关信号。某些工具通过忽略挂断信号并重定向输出来降低影响，终端复用器则通过保持一个独立会话提供继续查看能力；服务管理器和作业调度器还提供更明确的生命周期管理。不同机制解决的问题范围不同，没有一种短命令能自动承担全部监督、恢复和验收职责。

如果任务标准输入仍连着断开的会话，程序可能等待或收到文件结束；标准输出连接断开的通道，也可能遇到写入错误。即使挂断信号被忽略，这些输入输出依赖仍需要处理。长任务宜明确把输入设为已知来源、日志写到受控位置，并让监督者能够取得最终退出状态。

可靠恢复还要求保存任务信息。连接断开后，操作者需要知道运行标识、输出目录、启动环境与监督系统里的作业位置，而不是依赖一个已消失终端的滚屏。启动后立即生成运行清单、阶段性状态和可验证产物，能让会话成为查看入口，而不是唯一的任务记忆。

## 6. 三组隔离机制实验

<a id="linux-2-detail-22"></a>
### 6.1 参数、工作目录与环境继承

这个实验只创建一个短命子进程，分别传入工作目录和环境映射。它证明子进程可以看到受控环境，而父进程不会被子进程修改。直接使用参数数组，不通过 Shell 解释路径，可以把参数边界问题从环境实验中移开。

```python
import json
import os
import subprocess
import sys
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory(prefix="linux-env-") as raw:
    env = os.environ.copy()
    env["AI_LEARNING_CASE"] = "parent-selected"
    code = (
        "import json,os,sys;"
        "before=os.environ['AI_LEARNING_CASE'];"
        "os.environ['AI_LEARNING_CASE']='child-changed';"
        "print(json.dumps({'before':before,'cwd':os.getcwd(),"
        "'args':sys.argv[1:]}))"
    )
    p = subprocess.run(
        [sys.executable, "-c", code, "one argument", ""],
        cwd=raw, env=env, capture_output=True, text=True,
        timeout=5, check=True,
    )
    result = json.loads(p.stdout)
    assert result["before"] == "parent-selected"
    assert Path(result["cwd"]).resolve() == Path(raw).resolve()
    assert result["args"] == ["one argument", ""]
    assert env["AI_LEARNING_CASE"] == "parent-selected"
print("environment and argv assertions passed")
```

父进程传给子进程的是一份配置好的映射，子进程内部改变自己的值，不会改变父进程保存的映射。现实中的环境激活与调度系统配置也遵循这个方向。需要当前 Shell 改状态时，应使用该 Shell 支持的相应机制；需要程序可复现时，则可以直接把受控环境作为启动参数交给子进程。

<a id="linux-2-detail-23"></a>
### 6.2 温和停止与强制结束的产物差异

下面的子进程启动后打印就绪，收到温和终止请求时只设置标志，在主循环中写出完成说明后退出。第二次运行被强制终止，不会经过这条用户态清理路径。测试会等待并回收自己创建的所有子进程，异常时也执行清理。产物只是教学说明，不是完整训练检查点。

```python
import signal
import subprocess
import sys
import tempfile
from pathlib import Path

child = r'''
import pathlib, signal, sys, time
stop = False
def request_stop(signum, frame):
    global stop
    stop = True
signal.signal(signal.SIGTERM, request_stop)
print("READY", flush=True)
while not stop:
    time.sleep(0.01)
pathlib.Path(sys.argv[1]).write_text("clean-stop\n", encoding="utf-8")
'''

with tempfile.TemporaryDirectory(prefix="linux-signal-") as raw:
    root = Path(raw)
    for graceful in (True, False):
        result = root / ("graceful.txt" if graceful else "forced.txt")
        p = subprocess.Popen(
            [sys.executable, "-u", "-c", child, str(result)],
            stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True,
        )
        try:
            assert p.stdout.readline().strip() == "READY"
            if graceful:
                p.send_signal(signal.SIGTERM)
            else:
                p.kill()
            out, err = p.communicate(timeout=5)
            if graceful:
                assert p.returncode == 0
                assert result.read_text(encoding="utf-8") == "clean-stop\n"
            else:
                assert p.returncode == -signal.SIGKILL
                assert not result.exists()
        finally:
            if p.poll() is None:
                p.kill()
                p.communicate(timeout=5)
print("signal and cleanup assertions passed")
```

就绪行避免了“处理器尚未安装就发送信号”的常见测试竞态。该实验只能证明这个受控程序的两条退出路径，不保证所有应用都能在五秒内保存，也不证明强制结束后任何文件都不存在。真实程序可能早已写下部分结果，所以强制结束后仍必须按产物协议验证，不能用文件是否存在代替完成判断。

<a id="linux-2-detail-24"></a>
### 6.3 发布标记应落在验证之后

第三个实验模拟三个不同子任务：返回非零、返回零但产物错误、返回零且产物正确。监督者把退出码和独立内容验证结合，只有最后一种状态才生成完成标记。任务目录彼此隔离，不会把前一次成功的旧标记误认作新任务成功。

```python
import json
import subprocess
import sys
import tempfile
from pathlib import Path

child = r'''
import pathlib, sys
root = pathlib.Path(sys.argv[1])
mode = sys.argv[2]
(root / "result.json").write_text(
    '{"count": 3}' if mode == "valid" else '{"count": 1}',
    encoding="utf-8",
)
raise SystemExit(7 if mode == "failed" else 0)
'''

with tempfile.TemporaryDirectory(prefix="linux-complete-") as raw:
    for mode in ("failed", "invalid", "valid"):
        root = Path(raw) / mode
        root.mkdir()
        p = subprocess.run(
            [sys.executable, "-c", child, str(root), mode],
            capture_output=True, text=True, timeout=5,
        )
        payload = json.loads((root / "result.json").read_text(encoding="utf-8"))
        valid = payload.get("count") == 3
        if p.returncode == 0 and valid:
            (root / "COMPLETE").write_text("verified\n", encoding="utf-8")
        assert (root / "COMPLETE").exists() == (mode == "valid")
print("completion protocol assertions passed")
```

真实验收通常还应包含数据与代码版本、模式版本、输出维度以及必要摘要。这里使用一个简单计数字段，是为了把逻辑关系展示清楚，而不是建议所有实验都用三个样本验收。独立验证应尽量针对真正会损害结论的失败模式，不能只验证“文件不是空的”这种过弱条件。

## 7. 把任务的生命周期变成证据链

<a id="sec-6-1"></a>
<a id="linux-2-detail-26"></a>
### 7.1 进程存活不等于任务前进

判断任务是否前进，需要一个与业务阶段相符的进度量。训练可以观察已完成更新步数、有效样本数和最近一次检查点；数据预处理可以观察已验证记录数和输出分片数。计数必须代表真正完成的工作，而不是刚刚加入队列的请求。队列长度下降不一定说明成功，也可能是任务被丢弃。

心跳只证明某个发送心跳的执行路径仍然活着。如果专门的心跳线程继续运行，而主计算线程死锁，心跳依然会出现。设计时可以让心跳携带阶段和最近进度序号，监督者同时检查“还在响应”和“业务是否在合理时间内前进”。具体阈值应参考历史和阶段复杂度，不要给所有任务套同一个分钟数。

资源利用也需要结合进度解释。高处理器占用配合稳定步数增长，可能是正常计算；高占用但计数不变，可能处于单个很长步骤，也可能是忙等。低占用配合磁盘读取，可能是输入瓶颈；低占用且所有相关指标不动，则需要检查等待关系。每个假设应提出下一项能够区分它的证据，而不是看到一个百分比就下结论。

监督逻辑最好显式区分“未知”“正常”“可疑”和“已失败”。暂时没有数据不等于失败，证据不足时标为未知比伪装成绿色健康更诚实。另一方面，可疑状态不能无限延长，应该有采样、诊断和升级处理的流程。研究任务的可靠性来自可追踪决策，而不是从不出现红色状态。

<a id="linux-2-detail-27"></a>
### 7.2 时间、超时与取消协议

超时必须说明作用范围：只限制启动、限制某一阶段，还是限制整个任务。下载阶段正常的时间分布可能与一次小矩阵运算完全不同；全局超时若没有阶段信息，失败时很难解释。最好同时记录总耗时和关键阶段耗时，使用单调时钟计算持续时长，用墙上时间关联外部事件。

取消请求应具有清楚的所有权。由本程序创建并拥有的子进程，可以在清理路径中停止并等待；对共享服务或其他人的进程，则不能因为超时就随意结束。进程树里还可能存在已经脱离原父进程的成员，需要由适当作业管理边界追踪。第三章将进一步讨论并行作业管理中的失败传播。

重复发送取消请求，也要考虑程序是否具备幂等清理。关闭已经关闭的资源、删除本任务的临时文件、写入终止状态，都应有可重复执行的合理行为。清理失败应保留诊断，不能用一个新的异常完全覆盖原始失败原因。一个常见设计是保存主失败，再尽力清理，最后同时报告主失败与清理结果。

超时后继续等待并不是实现缺陷本身。某些资源释放需要额外时间，强制杀死也可能留下外部副作用。完成条件应区分“取消请求已经发出”“本地进程已退出”“子进程已回收”“外部资源已确认释放”和“产物已隔离”。只有把这些状态分开，才不会在界面显示停止后误以为整个系统已经恢复。

<a id="linux-2-detail-28"></a>
### 7.3 重启与恢复不应复用含糊目录

同一个输出目录被多次尝试复用，很容易混入旧的成功标记和新的半成品。推荐把逻辑实验标识与每次执行尝试标识分开：同一配置可以重试多次，但每次尝试都有独立日志、状态和中间产物，最终再明确哪次尝试被验收发布。这样既能追踪恢复过程，也不会把旧结果错误归属到新运行。

恢复入口先验证检查点版本和所需环境，再决定继续方式。若配置变化影响模型结构、优化器或数据顺序，应明确哪些状态仍可加载，哪些必须重新初始化。程序可以支持部分恢复，但必须把这种行为记入新运行清单。把“能成功读取文件”当作“恢复完全一致”，是研究结果不可解释的常见来源。

检查点选择也应有规则。最新修改时间的文件未必是最新完整检查点，文件名中的步数也可能与内容不符。应根据已验证的清单、内部步数和发布状态选择，并保留失败候选以供诊断。清理历史文件之前，先确认至少有满足恢复目标的有效版本，不能单靠排序后删除就决定唯一的恢复依据。

<a id="linux-2-detail-29"></a>
### 7.4 一份可以被另一个人使用的运行清单

运行清单的核心不是漂亮格式，而是回答另一个人在没有原终端的情况下如何核验和复现。它至少应提供输入身份、有效配置、代码身份、环境条件、启动方式、输出模式和验收规则。若某一步依赖外部资源，应记录可访问的版本标识或快照，不要只留一个会变化的网页地址或临时下载路径。

资源配置也属于运行条件。例如工作进程数、每个进程的线程上限、设备分配和内存约束，可能影响性能乃至数值轨迹。记录它们并不保证环境完全相同，却能让差异讨论有依据。若论文主要结论来自性能比较，还需要说明硬件、负载干扰、预热、计时同步和重复次数；单个结束时间不能代表通用速度。

完成报告宜把失败和中断也纳入可查询状态。只保存成功尝试，会让人看不到选择过程和稳定性问题。对研究而言，失败次数、无效超参数和恢复策略有时直接影响结论。把不成功的运行清单保留在适当位置，可以减少后来重复踩坑，也避免只展示最佳结果造成的偏差。

<a id="linux-2-buffer-extra"></a>
### 7.5 用握手区分“尚未生成”与“尚未刷新”

若只在父进程中睡一小会儿，再看看有没有输出，测试结果会依赖调度快慢；子进程也许根本还没运行到打印位置。更好的实验使用另一个已刷新通道发出就绪确认。父进程收到确认后，已经知道普通打印调用执行过，此时标准输出仍不可读，就能把原因缩小到已知的缓冲设置，而不是启动延迟。

下面显式采用带缓冲的文本输出，并用标准错误完成握手。所有通信内容很小，两个管道不会因容量耗尽而互相阻塞；父进程会在异常时结束并回收自己创建的子进程。这是缓冲机制实验，不是依据某个固定等待秒数测性能，也不把一次测试扩展为任意语言运行库的通用默认行为。

```python
import select
import subprocess
import sys

code = r'''
import sys
sys.stdout.reconfigure(line_buffering=False, write_through=False)
print("BUFFERED")
print("READY", file=sys.stderr, flush=True)
sys.stdin.readline()
sys.stdout.flush()
'''
p = subprocess.Popen(
    [sys.executable, "-I", "-c", code],
    stdin=subprocess.PIPE, stdout=subprocess.PIPE,
    stderr=subprocess.PIPE, text=True,
)
try:
    assert p.stderr.readline().strip() == "READY"
    readable, _, _ = select.select([p.stdout], [], [], 0)
    assert not readable
    out, err = p.communicate(input="release\n", timeout=5)
    assert p.returncode == 0
    assert out == "BUFFERED\n"
finally:
    if p.poll() is None:
        p.kill()
        p.communicate(timeout=5)
print("buffer visibility assertions passed")
```

观察到刷新后内容出现，只能证明这段程序的文本缓冲造成了可见性延迟；它不证明真实训练的静默也必然来自缓冲。实际排障可以把这个机制作为一个候选假设，再结合进度计数和资源证据验证。相反，如果握手消息也没有到达，首先要查子进程是否启动、代码是否执行到相应阶段，以及错误流是否连到了预期位置。

这种利用独立证据约束状态的方法，比不断延长等待更可靠。它同样适用于模型加载、设备初始化和服务就绪测试：让被测对象在完成明确条件后发出可验证确认，再进行下一步断言，而不是把“过了几秒”当作“前置条件已满足”。

## 8. 练习与详细解析

<a id="linux-2-detail-31"></a>
### 8.1 进程、退出和信号：五道机制题

**题一：程序已经返回零，但输出只包含预期记录的一半。任务应该标记成功吗？请给出最少的判定步骤。**

**解析：** 不应该仅按退出码标成功。先确认这个退出码属于目标程序本身，而不是外层启动器；再对照运行清单验证输出集合、记录数和格式；接着确认输出携带正确输入与配置身份；全部符合后才发布完成状态。若记录数不足，要把尝试标记为验收失败，并保留日志和半成品用于诊断。修复不能只改成“非空文件即成功”，因为那仍然无法表达完整结果契约。

**题二：一个进程结束以后仍显示为僵尸，向它发送强制结束信号为什么不能解决根因？**

**解析：** 僵尸已经停止执行，系统保留的是供父级取得的退出状态。根因通常是负责等待的主体没有回收，而不是业务代码仍在运行。需要检查父进程的等待逻辑或进程监督结构。大量僵尸可能消耗管理资源，但不应把它们误解成仍在进行高强度计算的工作者。诊断时应把状态、父子关系和资源数据结合，而不是只看名称还出现在进程列表里。

**题三：主进程退出了，为什么数据加载子进程可能仍存在？如何避免用进程名批量结束带来的错误？**

**解析：** 父子关系不自动等于共同生命周期，子进程可能被接管，启动器还可能创建独立会话。应在启动时保存本任务的子进程对象、进程组或调度器作业身份，并在正常与异常路径中停止和等待自己拥有的成员。按进程名模糊匹配可能误伤同名实验；旧进程号也可能被复用。可靠管理需要从创建开始建立所有权，而不是失败后临时猜谁属于谁。

**题四：连续发送十次标准信号，能保证目标执行十次业务处理吗？**

**解析：** 不能。标准信号在某些等待和阻塞条件下可能合并，不是通用的计数消息队列。它适合通知某类事件发生、请求重新检查状态或请求停止，不适合承担任意负载、顺序和准确次数。需要十个任务时，应使用有确认和容量设计的队列，或其他能够表示十个独立消息的机制。把信号处理器计数当成可靠分布式任务协议，会漏掉重要保证。

**题五：温和停止实验出现“请求已发送”，但进程还在。有哪些合理解释，下一步证据是什么？**

**解析：** 程序可能正在完成当前一致性步骤、处理器尚未到执行点、信号被阻塞，或者目标处在内核等待状态；也可能代码忽略了请求。先确认目标身份与信号发送结果，再检查阶段、进程状态和近期进度，按照既定期限等待。若需要升级措施，应先说明对产物完整性的影响并在结束后验收。反复发送同一请求不增加诊断信息，也不能证明程序一定能立即停止。

<a id="linux-2-detail-32"></a>
### 8.2 日志与观察：四道推理题

**题六：交互运行每秒显示进度，重定向到文件后几分钟没有新行，怎样区分缓冲与真正停顿？**

**解析：** 先确认程序所处阶段和日志目的地，再观察业务计数、资源变化与输出文件进展。用小型受控程序比较显式刷新与默认缓冲，可以验证日志机制，但不要据此直接证明大任务健康。若启用适当刷新后仍无进度，再沿阶段依赖排查。刷新只能改善可见性，不能修复主线程死锁，也不等于每条记录已经稳定落盘。

**题七：心跳线程每秒发消息，为什么主任务仍可能已经死锁？怎样改进健康信号？**

**解析：** 心跳证明的只是发送路径能够运行，主计算线程可能完全不前进。改进办法让心跳包含最近完成的业务序号、当前阶段和最后进度时间，监督者同时检查响应与进度。还应允许阶段特定的合理静默期，避免把单个长步骤误判死锁。如果进度指标只统计已排队任务，也会虚假增长，因此计数定义必须对应真正完成的工作。

**题八：两个进程的日志时间戳相差一毫秒，能否据此证明哪个业务事件先发生？**

**解析：** 不能无条件证明。机器时钟可能有偏差，日志生成和写入之间有缓冲，多个线程还可能延迟提交记录。可以用进程内单调序号、明确消息关联和因果标识补充。墙上时间适合粗粒度关联，单调时钟适合本进程耗时测量，跨进程严格顺序需要额外协议。若结论依赖微小时差，就必须先给出足够的同步和观测误差证据。

**题九：为了调试，把所有环境变量全部写入公开日志有什么问题？是否会更利于复现？**

**解析：** 全量日志可能泄露访问令牌、私钥路径和服务凭据，也会增加大量无关噪声。复现需要与实验有关的有效配置、版本和条件，并不需要秘密本身。应筛选允许记录的键，遮蔽秘密值，记录必要的认证方式或资源标识。日志契约既要让研究可解释，也要让记录可安全保存；这不是放弃复现，而是精确区分配置知识与访问能力。

<a id="linux-2-detail-33"></a>
### 8.3 环境与远程：五道设计题

**题十：一个子脚本设置了环境变量，退出后父终端没有变化，是继承机制失败了吗？**

**解析：** 不是。通常是父进程把环境副本交给子进程，子进程修改自己的副本，不会自动回写父级。若需要当前 Shell 改变自身状态，应采用该 Shell 的明确机制；若仅需要启动目标程序，可以在子进程启动时传入环境。两种需求不能混用。实验清单记录目标进程实际得到的值，比只记录“曾经执行过一个设置脚本”更有解释力。

**题十一：包版本完全相同、随机种子相同，模型结果仍有微小差异，是否足以判定程序有错误？**

**解析：** 不足以。需要检查硬件、底层库、并行归约顺序、非确定性算子和多个随机数生成器。先确定目标是逐位复现还是统计复现，再采用相应检查。若差异明显超过预期范围，也不能轻易全归因于浮点误差，应比较输入、配置和训练轨迹。版本与种子是必要控制的一部分，不是对所有执行细节的完整约束。

**题十二：远程交互登录后能运行，直接通过 SSH 执行同名命令失败，最先检查什么？**

**解析：** 检查远端实际解释器位置、搜索路径、工作目录、必要变量和初始化脚本路径。交互与非交互 Shell 可能读取不同启动文件，环境激活未必发生。用最小、固定的入口记录有效环境并直接调用明确解释器，可以降低歧义。不要一开始就重新安装全部依赖，因为现象很可能是启动上下文不同，而不是包损坏。远程还有额外解析层，参数边界也应单独验证。

**题十三：忽略挂断信号后，任务是否一定能在 SSH 断开后可靠完成？**

**解析：** 不能。标准输入输出仍可能依赖断开的连接，程序可能在读取或写入时出错；子进程归属和监督者退出也可能改变生命周期。还要定义日志位置、输入来源、最终状态取得方式和恢复协议。长任务应采用符合服务器管理方式的监督机制。忽略一个信号只处理一个机制，不自动提供重启、验收、资源清理和多进程管理。

**题十四：主机密钥校验与用户认证有什么不同？首次连接告警能否为了方便永远忽略？**

**解析：** 主机校验确认你连接的是哪个远端，用户认证确认你是否有权以某身份访问。加密连接如果连错目标，仍然不能满足正确访问的要求。首次信任应通过可靠渠道核对，后续变化按管理流程确认。永久关闭检查会丢失远端身份验证的重要环节。学习时只需理解边界，不应自行改变共享服务器的认证策略或在笔记中保存秘密材料。

## 9. 综合练习：设计一个可恢复的两阶段实验

<a id="linux-2-detail-35"></a>
### 9.1 题目与状态建模

设一个实验先做预处理，再训练；训练可能因会话断开、用户取消、磁盘满或程序异常而停止。要求另一个人在不查看原终端的情况下，能够知道尝试状态、判断产物是否可信，并从合适位置恢复。请给出目录组织、状态转换、日志字段和验收条件，不要求把所有机制写进一个大脚本。

一种合理组织是为逻辑实验建立稳定标识，为每次尝试建立独立目录；目录中保存有效配置、环境清单、输入身份、阶段日志、检查点清单和最终验收结果。预处理输出采用不可变版本，训练明确引用其版本。这样预处理是否重做由输入和规则身份决定，而不是由一个同名目录碰巧存在决定。

状态可以分为输入待验证、预处理中、预处理已发布、训练中、输出待验收、已完成、失败和已取消。每次转换记录事件与必要证据；异常不会自动倒回“未开始”，也不会覆盖历史成功。恢复作为新的尝试记录它依赖的检查点和原尝试身份，避免把恢复后的表现伪装成一次从未中断的运行。

<a id="linux-2-detail-36"></a>
### 9.2 故障注入与验收解析

至少设计四种小规模故障注入：输入格式无效、训练程序非零退出、输出数量不足但退出零、温和取消后检查点保存失败。每种测试都要给出预期状态和保留产物。这样才能验证状态机是否真正区分了进程错误、业务验收错误和清理错误，而不是只有正常路径好看。

预处理验收检查输入版本、记录数与模式，并确认所有分片已发布；训练验收检查模型结构、配置身份和必需文件集合，必要时做一个轻量加载与预测验证。完成标记只在全部验收通过后生成。若输出是多文件集合，发布协议要确保读取方不会混读不同版本。仅把最后一行日志写成完成，并没有表达这些条件。

恢复测试应比较“不间断运行”和“中断后恢复”的目标是否一致。若追求统计复现，可以比较多次重复的指标分布；若追求逐步一致，则要核对随机状态、采样位置和底层确定性条件。检查点可加载，只证明文件与接口兼容的一部分，不直接证明实验轨迹或结论相同。

<a id="sec-7-1"></a>
<a id="linux-2-detail-37"></a>
### 9.3 边界追问：后台进程存在是否意味着任务可靠完成

答案需要按时间和层次展开。后台进程在某一时刻存在，最多说明该进程当时尚未被完全结束；它可能还没加载依赖，可能阻塞，可能只是监督线程还活着。即使它后来正常退出，也要依据产物契约验收。可靠完成是一组事件和证据，不是一个瞬间的存在性判断。

同样，会话保留工具能让人继续查看终端，但不能替应用保存检查点；任务调度器能跟踪作业状态，却不能知道你的输出维度是否正确；日志收集器能记录异常，也不能自动补齐缺失数据。各层职责明确，才能组合成可靠系统。把某个工具当作万能保证，反而会让真正的缺口长期不被发现。

最后为任务写一段可以交接的说明：从哪里查运行清单、怎样识别当前尝试、哪些状态允许恢复、哪些产物需要隔离、如何验证完成，以及出现未知状态时先收集什么证据。若另一个人能凭这些说明判断，而不必问原作者“你当时在哪个终端敲的命令”，这套组织才真正支持持续研究。

<a id="linux-2-detail-38"></a>
## 10. 继续深入的研究问题

进一步可以比较三类管理机制：Shell 作业控制、服务监督和集群作业调度。它们对生命周期、资源归属、重启和日志提供不同抽象，适用于不同任务规模。比较时要围绕可证伪问题，例如“监督者异常退出后谁负责子进程”“退出码怎样保留”“重试是否产生重复副作用”，而不是只比较命令是否简短。

也可以研究观测本身的扰动。高频日志、性能采样和同步写入会改变运行开销；调试器还会改变线程时序。可靠实验需要在可见性与扰动之间选择合适粒度，并说明测量条件。一个没有任何监控的快任务可能无法解释，一个每一步都同步写大量日志的任务又可能不代表真实运行性能。

最后，把可恢复性作为研究对象本身：检查点间隔怎样影响平均损失工作量，保存开销与故障频率怎样权衡，外部数据变化怎样破坏恢复。这些问题连接到概率、优化和系统设计，但前提仍是本章建立的身份、状态和证据边界。先确保知道一次任务究竟做了什么，再讨论怎样让它更快和更大。



**延伸算例：信号送达、进程结束与资源回收不是同一时点。** 向一个任务发送终止信号成功，说明请求已被相应接口接受，不等于目标已经完成清理或产物发布。目标可能稍后处理、按策略忽略可忽略信号，或在当前等待阶段尚未结束；子进程退出后，父进程还需通过等待接口收集其退出状态。因而关闭协议通常先请求停止，再等待明确结束，最后验收产物和残留资源。若超过截止时间采取更强终止，必须把这次任务记录为中断情形，而不能因主控程序终于退出就标成正常完成。进程组范围、身份复用与子孙进程策略也应先明确，避免把同一个数值 PID 当作跨生命周期的永久身份。
