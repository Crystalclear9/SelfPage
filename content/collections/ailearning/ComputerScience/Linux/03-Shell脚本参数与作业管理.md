# 第 3 章 Shell脚本参数与作业管理

脚本不是把交互命令排成一列，而是为输入、状态变化、失败传播和重复执行规定契约。一个合格的研究脚本，应当能解释每个参数怎样生效、哪一步失败后还允许继续、谁负责等待后台工作，以及中断后留下的文件能否被信任。本章以 Bash 为具体语言，但强调的状态和副作用分析，同样适用于其他自动化工具。

本章行为实验在既有 Ubuntu 22.04.5 LTS、Bash 5.1.16、Python 3.10.12 中核验。所有 Bash 程序通过固定脚本文本与位置参数调用，实验目录由临时目录机制管理，不修改项目数据，不安装依赖，不启动服务。严格选项和等待语义同时核对本机 Bash 的内置帮助。不同 Shell 不共享全部语义；不要把本章的 Bash 数组和选项直接粘贴到其他解释器。

## 1. 脚本入口应当像一个小型接口

<a id="linux-3-detail-2"></a>
### 1.1 输入、输出和副作用分别建模

在写命令之前，先列出脚本接受什么、输出什么，以及会改变哪些外部状态。输入不只有位置参数，还包括工作目录、环境变量、文件内容和工具版本；输出不只有标准输出，还有产物、日志、退出状态和可能的远程操作。副作用则包括覆盖文件、追加记录、创建任务和更新数据库。把这些信息写清楚，才能判断重试是否安全。

脚本入口最好只负责解析、验证和编排，让复杂数据变换交给具有明确接口的程序。否则，一份脚本同时承担格式解析、数值运算、进程监督和外部事务，会很快超出 Shell 易于推理的范围。选择 Shell 是因为它擅长连接程序与文件，不意味着每个循环和每个字符串问题都应该在 Shell 中解决。

还要说明执行策略：遇到已有输出是拒绝、覆盖、创建新尝试还是恢复；出现某类非零状态是失败、正常空结果还是需要重试；取消后保留哪些诊断。没有这些规定，脚本虽然能执行，却无法让第二个人预测它会怎样改变目录。这种不可预测性在多次实验和共享环境中尤其危险。

<a id="sec-1-1"></a>
<a id="linux-3-detail-3"></a>
### 1.2 参数验证不应等到高成本步骤之后

验证可以分成语法、取值范围和资源条件。语法检查确认必需选项、选项值和额外参数；范围检查确认并行度为允许的整数、阈值落在合理区间；资源检查确认输入类型、输出父目录和依赖命令。尽量在启动长任务前完成便宜检查，但不要把所有可能变化的条件都误认为能永久预先确认。

路径存在性检查尤其如此。先检查输入存在，之后仍可能被另一个进程修改；因此关键验证宜作用于实际打开和读取的对象。输出目录可写也不证明后面一定不会磁盘满。预检减少可预见错误，运行时错误处理和产物验收仍然不可省略。

对缺失参数，要报告缺的是哪个选项以及正确用法，而不是让一个后续命令报出难懂的空路径错误。对未知选项要尽早拒绝，避免拼写错误被当作额外文件名。对重复选项也要明确选择：最后一次覆盖、首次生效或者直接拒绝。接口可以采用不同约定，但必须稳定并写进说明。

数字字符串的解释值得小心。一个看似整数的值可能含前导符号、空格、前导零或算术表达式。若接口只允许正十进制整数，应先按该语法验证，再进行运算；不要把任意用户字符串直接放入 Shell 算术上下文。过大的并行度还需要范围上限，不能因为语法正确就自动接受无限资源请求。

<a id="linux-3-detail-4"></a>
### 1.3 使用数组表达命令，而不是重建代码

需要调用一个程序及一组动态参数时，Bash 数组可以保留每个参数的边界。数组元素可以包含空格、中文和空字符串，引用数组展开时仍然是独立参数。相反，把命令和参数拼成一个大字符串，再交给重新解释的机制，不仅难以保留边界，还把数据重新提升成代码。

如果只是为了打印日志，可以打印经过清楚编码的参数列表，但打印形式不应反过来成为执行依据。人类可读的命令展示，未必能无损表达所有字符；需要机器重放时，应保存结构化参数和有效环境。最容易解释的执行方式，是命令数组原样交给执行接口，同时把同一份结构化信息记入清单。

函数接口也应明确返回值与输出。若函数通过标准输出返回数据，诊断应放到标准错误，以免调用者捕获到混杂内容。若函数通过退出状态表达真假，调用者必须按条件接口使用，不能又把非零一律当异常。一个函数同时用输出、全局变量和隐式当前目录返回多种状态，会使组合推理非常困难。

### 图解：后台作业需要逐个等待

![后台作业需要逐个等待](images/03-concept.svg)

**图解。** 图中三条任务按共同起点表示，时长三、一、二是为解释完成次序指定的教学量，不是实际调度测量。B 最先结束但退出码为七；若只等待最后启动的 C，就只取得 C 的零。右侧另列按启动次序进行的等待 A、B、C：即使 B 已经先结束，之后等待仍需收集其保存的失败结果，不能被 C 的成功覆盖。实际进程创建和调度存在时间差，但逐项取得退出状态的要求不依赖这组示意时长。

每个后台作业有独立退出结果，监督者需要保存身份、逐个等待并汇总。示例中最后作业成功，不能覆盖中间作业失败的事实。

等待顺序不等于完成顺序。真正的脚本还要处理中断、清理和重试幂等；set -e 的例外上下文很多，不能把打开一个选项当作完整监督协议。

## 2. 严格选项解决什么，又留下什么

<a id="linux-3-detail-6"></a>
### 2.1 非零状态是一个值，不总是异常

Shell 中每个命令都有退出状态，零通常表示成功，非零的具体含义由命令定义。查找工具没有匹配时可能用某个非零值表示正常空结果，而读取失败又是另一个值。因此“任何非零都必须停止”与“非零都忽略”同样粗糙；脚本应依据步骤契约解释状态。

在条件中调用命令，是表达预期真假结果的自然方式。但命令兼有正常无结果与真正错误时，还应区分对应状态。一个空结果分支可以产生空集合，真正的读取错误则必须使任务失败。为了让脚本继续而在后面统一追加“或真”，会把这两类情况抹平，留下看似成功的错误数据。

状态还容易被覆盖。命令失败后先打印一条日志，再读取上一条状态，读到的可能已经是日志命令的结果。应立即保存需要的状态，或者在明确条件分支中处理。函数最后一条命令也常决定函数返回值；在失败函数末尾添加一条成功的提示，可能意外把失败变成成功。

<a id="linux-3-detail-7"></a>
### 2.2 set -e 受语法上下文影响

开启遇错退出有助于发现某些未处理失败，但它不是通用异常系统。位于条件测试、某些逻辑列表、被否定的流水线以及其他特定上下文中的失败，具有专门规则。理解时应看完整语法结构，而不是只盯着失败命令那一行。

一个反直觉例子是把函数作为条件调用。如果函数执行处于遇错退出被忽略的上下文，函数体内的失败也可能不会按你平时想象的方式中止，随后命令仍会运行，最后成功命令还可能让整个函数返回零。于是一个本来被作者当作“有错误就自动停”的函数，换个调用位置就失去该假设。

可靠做法是在函数内部对关键步骤显式检查，并明确返回失败；调用者再按函数契约处理。严格选项作为辅助防线，而不是替代局部错误逻辑。阅读脚本时也应检查调用上下文，不能因为文件顶部有一个选项，就跳过所有错误分支审查。

命令替换和子 Shell 还有继承细节。Bash 的某些模式或选项会改变命令替换是否继承遇错退出。研究脚本应该显式设定需要的模式，并用最小反例验证实际版本，而不是把别处看到的行为当作所有环境的必然规则。下面的实验会把这些差异直接变成可执行断言。

<a id="linux-3-detail-8"></a>
### 2.3 pipefail 把哪个失败带回父级

默认情况下，流水线的状态通常取最后一个命令的状态；前面步骤失败，最后的统计命令仍然可能成功。启用管道失败传播后，流水线会在有失败成员时给出相应非零状态。需要注意，它通常采用最右侧非零成员的状态，并不表示最早发生或最根本的错误。

若需要知道每个成员的结果，应及时读取 Bash 提供的流水线状态数组，并避免后续命令覆盖它。即使取得全部状态，诊断仍需结合错误流，因为下游提前退出可能让上游遇到断管道，这未必是原始数据损坏。失败传播能避免静默成功，却不会自动完成根因归因。

管道中的每个阶段也可能处于子进程上下文，变量修改未必回到父 Shell。把统计计数放进管道中的循环，再在外面读取变量，可能得到意外值。Bash 的特定选项和作业控制设置又会影响某些情形，因此最好避免依赖含糊的变量传播，或者明确选择输入重定向、进程替换及其各自状态处理方式。

<a id="linux-3-pipeline-status"></a>

#### 同时捕获汇总状态与成员状态，避免被下一条命令覆盖

![两种管道成员结果及立即保存PIPESTATUS的区别](images/03-pipeline-status.svg)

第一行成员状态为 $`[7,0,0]`$，默认汇总为最后成员的零，开启 `pipefail` 后才变为七。第二行为 $`[7,0,3]`$，两种模式的汇总都为三；此时仅看总状态仍不知道左侧另有一个七。所谓“最右侧非零”按语法位置选择，不是按失败时刻选择，也不能直接解释为根因。

需要同时保留两种信息，可以在流水线紧后用同一次赋值展开：`states=("$?" "${PIPESTATUS[@]}")`。对第二行且已开启 `pipefail` 的 Bash，所得依次是总状态三、各成员七零三。展开取到的是赋值执行前的状态；赋值本身结束以后，当前 `$?` 和 `PIPESTATUS` 又会变化，因此后续诊断应使用已保存数组。

例如，在不启用 `set -e`、以便主动检查状态的隔离 Bash 中，执行 `bash -c 'exit 7' | bash -c 'exit 0' | bash -c 'exit 3'` 后，立即快照即可得到上述结果。若先插入一个成功的 `printf`，再访问状态，得到的已是打印命令对应的零，而不是原流水线。只增加日志却改变了所读取证据，是脚本调试中尤其需要防止的问题。具体管道汇总规则可对照 [GNU Bash 管道说明](https://www.gnu.org/software/bash/manual/html_node/Pipelines.html)，也可用目标 Bash 的内置 `help set` 和最小反例核对。

<a id="linux-3-detail-9"></a>
### 2.4 nounset、错误陷阱和跟踪的边界

未设置变量检查能够暴露拼写错误，但可选参数仍需明确默认值和缺失语义。空字符串与未设置是不同状态；默认展开形式是否同时把空串视为缺失，取决于写法。接口如果允许空字符串，应使用符合该契约的展开形式，不能为了消除告警而统一补空值。

错误陷阱受到与遇错退出相关的上下文规则影响，继承范围也有选项控制。它适合补充诊断，但不能作为保证捕获所有失败的全局异常处理器。退出陷阱更适合做已拥有资源的清理；清理逻辑应保存原始退出状态，避免最后一个清理命令把主失败掩盖。

执行跟踪可以显示展开后的命令，帮助定位实际参数，但也可能把秘密值输出到日志。需要调试时局部启用，并考虑哪些参数会暴露。跟踪文本也不自动包含业务状态、数据版本和产物验证结果，仍需结构化日志补充。任何工具都应按它实际提供的观察层使用。

## 3. 清理、取消和等待应组成一个协议

<a id="sec-2"></a>
<a id="linux-3-detail-11"></a>
### 3.1 后台启动只是开始，不是监督完成

在命令末尾放后台符号，Shell 可以继续执行，但子任务的失败不会自动变成主脚本失败。启动成功返回的状态，通常只表明后台任务被启动；必须等待实际子任务，才能取得它的结束结果。一个主脚本启动十个训练后直接返回零，调度器看到的并不是十个训练都完成。

每个子任务应有稳定标识、独立日志与明确结果位置。保存启动时得到的子进程标识，并把它和业务标识关联。等待时逐个记录状态，或者使用适当版本支持的等待任意任务机制。无参数等待可以用于等全部结束，但其返回约定不能自动替代你需要的逐项失败汇总。

并发上限还必须与真实资源一致。四个工作进程，每个内部再开许多线程，可能远超预期计算负载；多个任务共享内存或设备时，也可能互相挤压。并行度不是越高越好，应通过受控实验比较吞吐、延迟和资源峰值，避免把任务数当作有效计算能力的直接比例。

<a id="sec-2-1"></a>
<a id="linux-3-detail-12"></a>
### 3.2 先定义失败策略，再写并发循环

至少有三种常见策略：任何一个失败就尽快取消剩余任务，允许全部结束后汇总，或者按独立性继续可用部分。它们分别适合不同依赖结构。彼此独立的参数实验可以全部跑完再汇总；需要全部分片才能发布的数据处理，任何失败都必须阻止最终完成；有外部副作用的步骤还要考虑取消后的补偿。

尽快失败也不是“第一个非零出现就主脚本立刻退出”。那样可能留下未管理的子进程。真正的流程是记录失败、停止启动新任务、请求已有任务结束、等待回收、隔离未完成产物，再返回清楚状态。清理本身失败时也要报告，不能假装所有资源都已释放。

按启动顺序等待比较简单，但可能延迟发现后启动任务的失败；等待任意完成更及时，却需要准确维护活跃集合和业务映射。应按任务规模选择，不必为了一个小批量引入复杂调度器，也不能在大规模长任务中忽略失败发现延迟。两种实现都应有可验证的不变量：活跃任务数有上限，每个已启动任务最终被等待，每个结果都被分类。

<a id="linux-3-detail-13"></a>
### 3.3 trap 的时机、引用和状态保存

设置陷阱时，命令文本可能在设置阶段或触发阶段发生不同的展开，取决于引用写法。过早展开一个尚未赋值的临时路径，会让清理时得到错误目标；过晚依赖一个已经被修改的变量，也会指向错误对象。更容易审查的方式是让陷阱调用命名清理函数，函数只操作明确初始化、由本任务拥有的资源。

退出陷阱通常先保存进入时的退出状态，再执行尽力清理，最后返回原主状态或按文档表达清理失败。若清理再次触发退出逻辑，还要避免递归和重复副作用。温和信号的处理可以设置取消状态或者转为明确退出，再让统一清理路径处理；强制结束和系统崩溃则不会给用户态陷阱机会。

清理范围必须窄。临时目录由安全创建机制生成并由脚本持有，删除前确认它是本任务创建的对象；不要把用户提供的大目录当作“失败时全部清空”的范围。重跑能力来自识别和隔离半成品，而不是为了方便把未知数据一起删掉。

## 4. 幂等性来自状态设计

<a id="linux-3-detail-15"></a>
### 4.1 先区分相同请求与重复尝试

幂等性不是“脚本运行两遍都没报错”，而是在约定观察范围内，重复执行同一个逻辑请求不会制造额外错误副作用。读取同一个不可变文件可以自然重复，向计数器加一则不具备这种性质；覆盖同名结果也不一定幂等，因为两次计算可能使用变化的数据或随机状态。必须先确定请求身份和预期最终状态。

逻辑请求可以由代码版本、数据版本和有效配置共同标识，每次实际执行再有单独尝试标识。这样同一请求的多次失败不会相互覆盖日志，也能判断某个已完成结果是否真的对应当前需求。只把输出目录名字当作请求身份，容易把旧数据的新配置或新代码的旧结果混在一起。

哈希可以压缩标识，但被哈希的信息必须完整且有规范编码。配置键顺序、默认值是否展开、浮点字符串表示、外部文件是否只记录路径，都会影响身份设计。一个只对命令字符串取摘要的键，可能遗漏环境覆盖和实际数据变化。先定义身份，再选择编码与摘要工具，顺序不能反过来。

<a id="sec-5"></a>
<a id="linux-3-detail-16"></a>
### 4.2 临时产物、验证与发布

典型文件阶段可以采用四步协议：生成独立临时对象，关闭写入，验证内容，发布正式版本。只有发布后的对象允许下游消费；临时对象即使名字存在也不能触发跳过。验证应覆盖业务契约，例如模式、记录数、维度和输入身份，而不是仅检查非空。

发布通过同文件系统名称替换实现时，可以改善单个入口的原子可见性，但不自动提供多文件事务和断电持久性。多个文件组成结果时，先组织成独立版本集合，再切换清单或入口；读者也要遵循这一协议。生产者正确而消费者绕过发布标记直接读取临时目录，整体仍然不可靠。

重试时可以删除或隔离本尝试的临时对象，然后重新生成；已经发布且验证身份相同的版本可以复用。身份不同则拒绝或创建新版本，不应静默覆盖。若验证逻辑升级，还需要明确旧完成标记是否仍被信任，不能让一个过时的空标记永久绕过新增检查。

<a id="linux-3-detail-17"></a>
### 4.3 外部副作用不能靠文件标记包住

向远程服务提交请求时，可能出现“服务已完成操作，但本地还没来得及写完成标记就断开”。重试若再次提交，会产生重复副作用；不重试又无法判断是否缺失。这是通信失败下的典型不确定状态，不能仅凭本地文件不存在断言远端未执行。

可行方案包括服务端幂等键、唯一业务键、事务、查询状态和适当补偿。幂等键必须绑定同一个逻辑请求，不能每次重试生成新键；也要明确保存期限与冲突行为。若服务不提供任何去重或事务能力，脚本就不能凭空承诺恰好一次，只能给出更弱保证并设计人工核对或补偿流程。

“先写本地标记再调用服务”也不能解决问题，因为可能标记已写而服务未执行。调整两步顺序只改变哪一种失败会发生，没有让两步自动原子化。理解这种边界，有助于选择正确的系统接口，而不是把重试循环写得更复杂却仍然无法证明结果。

<a id="linux-3-detail-18"></a>
### 4.4 锁解决互斥，不自动证明结果正确

两个相同请求同时执行，可能争抢输出或重复消耗资源。锁能在适用范围内建立互斥，但要说明锁的主体、生命周期和失效方式。基于进程持有的锁与基于文件存在的标志不同：后者在异常结束后可能残留，需要额外判断；随意根据“文件很旧”删除，又可能打断仍在运行的慢任务。

锁也不能代替产物验证。持锁进程完全可能写出错误结果；锁只限制并发进入，不保证步骤本身正确。若使用共享或网络文件系统，还要核对锁机制的实际支持与失败语义。单机实验通过不能自动证明分布式环境中的相同行为。

若任务可以把结果写到彼此独立的尝试目录，最后按版本发布，有时可以减少锁范围。允许多个尝试并行计算，但只让一个合格结果成为正式版本；代价是可能重复计算。选择严格互斥还是竞争发布，应结合计算成本、外部副作用和一致性要求，而不是一概增加锁。

## 5. 三组 Bash 行为实验

<a id="linux-3-detail-20"></a>
### 5.1 严格选项的可执行反例表

下面用 Python 启动多个独立 Bash，每个案例都有明确期望。固定最小环境可以减少启动文件和继承选项干扰；每个子进程都有超时。实验不接触文件，只比较退出状态和输出。它展示的是 Bash 的具体规则，不是建议为了通过测试而删掉严格选项。

```python
import subprocess

cases = [
    ("plain", "set -e; false; printf survived", 1, ""),
    ("condition", "set -e; if false; then :; fi; printf survived", 0, "survived"),
    ("and-list", "set -e; false && printf no; printf survived", 0, "survived"),
    ("pipeline-default", "set -e; false | true; printf survived", 0, "survived"),
    ("pipeline-checked", "set -eo pipefail; false | true; printf survived", 1, ""),
    ("function-condition",
     "set -e; f(){ false; printf after; }; if f; then printf branch; fi",
     0, "afterbranch"),
    ("substitution-default",
     "set -e; value=$(false; printf text); printf '%s' \"$value\"",
     0, "text"),
    ("substitution-inherit",
     "set -e; shopt -s inherit_errexit; value=$(false; printf text); printf '%s' \"$value\"",
     1, ""),
]
for name, script, status, output in cases:
    p = subprocess.run(
        ["bash", "--noprofile", "--norc", "-c", script],
        env={"PATH": "/usr/bin:/bin", "LC_ALL": "C"},
        capture_output=True, text=True, timeout=5,
    )
    assert (p.returncode, p.stdout) == (status, output), (name, p.returncode, p.stdout)
    print(name, "passed")
```

最值得反复分析的是函数条件案例：函数里的失败之后仍打印内容，最后条件也进入成功分支。若函数负责数据生成，这种结构可能把不完整输出误认为成功。修复应让关键步骤显式返回失败，并避免依赖调用位置决定函数内部正确性，而不只是把文件顶部的选项写得更长。

命令替换的两个案例则说明，隐含模式是环境契约的一部分。脚本可以选择显式继承，也可以在子结构中对关键命令检查；无论选择哪种，都应该通过最小案例理解。只记住“严格模式很安全”或“严格模式没有用”都过于笼统，真正需要的是具体规则与局部契约。

<a id="linux-3-detail-21"></a>
### 5.2 一个拒绝含糊输入的参数入口

这个入口接受输入文件、输出目录和有限并行度，拒绝重复选项、未知选项与未说明的位置参数。示例使用 Bash 数组保存后续命令参数，但为了不启动真实训练，只把解析后的值交给 Python 进行结构化展示。可用脚本应把展示部分替换为经过审查的实际程序入口。

```python
import json
import subprocess
import sys
import tempfile
from pathlib import Path

script = r'''
set -u
die(){ printf '%s\n' "$1" >&2; exit 2; }
input=''; output=''; jobs='1'
seen_input=0; seen_output=0; seen_jobs=0
while (( $# )); do
  case "$1" in
    --input)
      (( $# >= 2 )) || die 'missing input value'
      (( seen_input == 0 )) || die 'duplicate input'
      input=$2; seen_input=1; shift 2 ;;
    --output)
      (( $# >= 2 )) || die 'missing output value'
      (( seen_output == 0 )) || die 'duplicate output'
      output=$2; seen_output=1; shift 2 ;;
    --jobs)
      (( $# >= 2 )) || die 'missing jobs value'
      (( seen_jobs == 0 )) || die 'duplicate jobs'
      jobs=$2; seen_jobs=1; shift 2 ;;
    --) shift; break ;;
    *) die "unknown option: $1" ;;
  esac
done
(( $# == 0 )) || die 'unexpected positional argument'
(( seen_input && seen_output )) || die 'input and output required'
[[ -f "$input" ]] || die 'input is not a regular file'
[[ -n "$output" ]] || die 'output must not be empty'
[[ "$jobs" =~ ^[1-9][0-9]?$ ]] || die 'jobs must be decimal 1..99'
command=("$PYTHON_BIN" -c 'import json,sys;print(json.dumps(sys.argv[1:]))')
"${command[@]}" "$input" "$output" "$jobs"
'''
with tempfile.TemporaryDirectory(prefix="linux args ") as raw:
    root = Path(raw)
    source = root / "输入 数据.txt"
    source.write_text("sample\n", encoding="utf-8")
    env = {"PATH": "/usr/bin:/bin", "LC_ALL": "C.UTF-8", "PYTHON_BIN": sys.executable}
    base = ["--input", str(source), "--output", str(root / "result dir")]
    good = subprocess.run(
        ["bash", "--noprofile", "--norc", "-c", script, "entry", *base, "--jobs", "2"],
        env=env, capture_output=True, text=True, timeout=5,
    )
    assert good.returncode == 0, good.stderr
    assert json.loads(good.stdout) == [str(source), str(root / "result dir"), "2"]
    for extra in (["--jobs", "0"], ["--jobs"], ["--unknown"], ["--jobs", "2", "--jobs", "3"]):
        bad = subprocess.run(
            ["bash", "--noprofile", "--norc", "-c", script, "entry", *base, *extra],
            env=env, capture_output=True, text=True, timeout=5,
        )
        assert bad.returncode == 2, (extra, bad.stdout, bad.stderr)
print("argument contract assertions passed")
```

范围限制写成简单的一到九十九，是这个教学接口自己的资源策略，不代表所有服务器都适合九十九个任务。真实入口应结合资源配额给出更合适上限，并在启动时记录有效值。示例也没有把输入类型检查冒充完整数据验证；数据格式与版本仍需后续阶段检查。

重复参数被拒绝，使配置来源更容易解释。另一种合法设计是最后一次覆盖，但应测试并记录实际规则。重要的是调用者能预测行为，而不是某种解析风格天然更高级。路径中包含空格与中文的成功案例，则验证参数边界在入口到执行链上没有丢失。

<a id="linux-3-detail-22"></a>
### 5.3 等待每个后台任务并汇总失败

下面固定启动三个短任务，保存各自进程标识，并逐个等待记录状态。它采用“全部结束后汇总”策略，演示非零状态必须显式取得。实验子任务只短暂等待后退出，没有后台孙进程；因此清理拥有的直接子进程足以覆盖本例范围。真实启动器若再创建后代，需要更合适的进程组或监督边界。

```python
import subprocess

script = r'''
set -u
pids=()
cleanup(){
  for pid in "${pids[@]}"; do
    [[ -n "$pid" ]] || continue
    kill "$pid" 2>/dev/null || :
  done
  for pid in "${pids[@]}"; do
    [[ -n "$pid" ]] || continue
    wait "$pid" 2>/dev/null || :
  done
}
trap cleanup EXIT
for code in 0 7 0; do
  bash --noprofile --norc -c 'sleep 0.01; exit "$1"' child "$code" &
  pids+=("$!")
done
failed=0
for i in "${!pids[@]}"; do
  if wait "${pids[$i]}"; then
    status=0
  else
    status=$?
    failed=1
  fi
  pids[$i]=''
  printf '%s:%s\n' "$i" "$status"
done
exit "$failed"
'''
p = subprocess.run(
    ["bash", "--noprofile", "--norc", "-c", script],
    env={"PATH": "/usr/bin:/bin", "LC_ALL": "C"},
    capture_output=True, text=True, timeout=5,
)
assert p.returncode == 1
assert p.stdout.splitlines() == ["0:0", "1:7", "2:0"]
print("wait and aggregate-status assertions passed")
```

清理列表在任务等待完成后立即清空对应元素，避免清理时继续对已经完成并回收的旧标识操作。例子没有无条件对系统中同名进程发信号，也没有使用模糊匹配。若主实验在外层被超时结束，外层监督者同样应按自己的所有权协议回收整个任务，而不是依赖本例所有情况下都能执行退出陷阱。

主脚本最终返回非零，但三个子任务各自状态仍保留在输出中。实际任务还应把它们写入结构化结果清单，与日志和业务标识关联。一个汇总布尔值适合告诉调度器“整体未成功”，却不够解释哪个分片为何失败，两层信息都需要保存。

<a id="linux-3-detail-23"></a>
## 6. 并发与恢复的正确性如何验证

<a id="linux-3-detail-24"></a>
### 6.1 用不变量审查任务池

任务池最重要的不是循环写法，而是能够始终成立的关系。第一，已启动任务集合应当能被明确枚举；第二，正在执行的数量不能超过上限；第三，每个任务从未启动、运行中到结束应只有清楚的转移；第四，每个已启动任务最终都取得一个结束分类；第五，整体完成只能由符合策略的子结果集合导出。这些关系比“终端上看起来三个任务同时运行”更有验证价值。

若实现采用批次方式，每次启动有限数量，再全部等待，结构较简单，但慢任务会拖住下一批。若采用动态补位，某个任务完成后立即启动下一个，资源利用可能更平滑，但需要准确维护活跃集合。两种方案并没有脱离条件的优劣；任务耗时差异很大时，动态补位更可能有价值，而规模很小的离线流程可能优先选择易审查结构。

资源上限不只有任务数量。每个任务的内存峰值可能随输入变化，单个并行度限制无法保证总内存不会超标。可以采用按资源权重的准入策略，或者利用现有调度器提供的资源限制；脚本层至少要记录实际配置并在失败时保留证据。不能从“最多四个任务”推导“内存一定安全”，除非每个任务都有可信上界并计入共享开销。

测试任务池可以使用一组刻意设计的小任务：立刻成功、短暂等待后失败、较慢成功，以及收到停止请求后才结束。记录每个任务开始和结束事件，检查任何时刻活跃数是否超限、失败后是否仍启动了不该启动的新任务、每个标识是否恰好出现一个最终状态。测试应验证调度策略，而不是只检查最后返回零。

<a id="linux-3-detail-25"></a>
### 6.2 从正常路径扩展到失败矩阵

一个流程至少有输入、执行、输出验证、发布和清理几个阶段，每个阶段都可以失败。用表格组织故障注入时，行可以表示阶段，列可以表示缺失资源、无效数据、非零退出、取消和已有状态。并非每个组合都必须单独写程序，但每一类真实风险都应有对应的处理规则和代表性测试。

例如，输入缺失应该在高成本启动前失败；生成器失败后不应发布完成标记；验证失败应保留诊断并隔离半成品；发布失败不能宣称成功；清理失败不能掩盖原始生成错误。所有错误还应该归属于正确尝试，而不是写到共享的最后状态文件里，让并发任务互相覆盖。

故障注入应限定在自有临时范围。无需真的写满服务器磁盘，可以让受控写入函数抛出相应错误；无需破坏共享数据库，可以用测试接口模拟确认前断开；无需结束其他人任务，可以向自己创建的子进程发送信号。模拟能验证控制流，但涉及真实文件系统持久性、网络重传或调度器策略时，还需要对应环境的集成测试，不能把模拟证据夸大。

<a id="linux-3-detail-26"></a>
### 6.3 假成功比明显失败更需要针对性测试

非零退出通常容易被注意，最危险的反而是返回零但结果不符合要求。可能原因包括程序忽略一部分输入、写入旧路径、恢复了错误版本、过滤条件过严或把异常转成空结果。测试必须包含这些“表面成功”情况，否则错误处理再复杂，也只覆盖了最容易看见的一类失败。

可以给每个产物设置少量与任务相关的交叉检查。例如样本计数应与输入清单和过滤统计守恒，模型输出维度应与标签空间一致，分片集合的索引不应缺失或重复，恢复步数不应倒退。检查应独立于生成逻辑的关键假设，否则同一个错误可能同时污染生成与验证。

验收太弱会放过坏结果，验收太强又可能误拒合理差异。浮点结果不宜随意用逐位相等代替容差和统计标准；随机训练也不应要求每次指标完全相同。先定义业务正确性，再选择验证规则。脚本的角色是诚实执行规则并记录证据，不能用一个统一的“文件存在”规则处理所有研究产物。

<a id="linux-3-detail-27"></a>
### 6.4 重试需要分类、限额和停止条件

适合重试的错误通常具有暂时性，并且操作具备可接受的重复语义。输入格式错误、缺少必需参数和确定的模型结构不兼容，反复重试不会自然恢复；网络暂时不可用可能恢复，但也需要考虑服务端是否已经完成请求。把所有非零都重试，只会延迟暴露真正问题并制造重复副作用。

重试策略应规定最大尝试次数或总时限、等待方式、哪些状态可重试，以及最终失败如何表达。逐渐增加等待可以减轻瞬时压力，加入适当随机扰动可降低大量任务同步重试；但具体参数需要按系统负载和服务契约决定，不应在教材里捏造一个适用于所有场景的最佳秒数。

每次重试保留独立诊断，同时与同一逻辑请求关联。成功后也不应抹去之前的失败历史，因为稳定性和总成本可能影响研究结论。若错误类别发生变化，要重新判断策略，而不是把新的确定性错误继续当作旧的暂时故障。

<a id="linux-3-publication-extra"></a>
### 6.5 实验：在发布前失败，再重跑同一请求

下面用标准库模拟一个文件阶段，核心是观察状态协议，而不是重新演示 Bash 语法。输入内容与规则版本共同决定请求身份；每次尝试有独立目录，只有验收通过的清单才成为正式结果。第一次故意在发布前失败，留下临时产物但没有正式版本；第二次重新计算并发布；第三次识别身份一致的已发布版本并复用。

这个设计不覆盖远程事务，也不声称具备断电持久性。它在单进程、同一文件系统的教学条件下，验证“存在半成品不等于可以跳过”和“相同请求复用必须检查身份”两个关键不变量。故障通过受控异常注入，不写满磁盘，也不破坏外部资源。

```python
import hashlib
import json
import os
import tempfile
from pathlib import Path

def request_key(source):
    payload = b"sum-v1\n" + source.read_bytes()
    return hashlib.sha256(payload).hexdigest()

def stage(root, source, fail_before_publish=False):
    key = request_key(source)
    published = root / "published.json"
    if published.exists():
        saved = json.loads(published.read_text(encoding="utf-8"))
        if saved["request"] != key:
            raise ValueError("published result belongs to another request")
        if not isinstance(saved["sum"], int):
            raise ValueError("invalid published schema")
        return saved["sum"], "reused"
    attempt = root / ("attempt-" + str(len(list(root.glob("attempt-*")))))
    attempt.mkdir()
    values = [int(x) for x in source.read_text(encoding="utf-8").split()]
    result = {"request": key, "sum": sum(values), "count": len(values)}
    temp = attempt / "result.tmp"
    temp.write_text(json.dumps(result), encoding="utf-8")
    checked = json.loads(temp.read_text(encoding="utf-8"))
    assert checked["count"] == 3 and checked["sum"] == 6
    if fail_before_publish:
        raise RuntimeError("injected failure before publication")
    os.replace(temp, published)
    return checked["sum"], "created"

with tempfile.TemporaryDirectory(prefix="linux-publish-") as raw:
    root = Path(raw)
    source = root / "input.txt"
    source.write_text("1 2 3\n", encoding="utf-8")
    try:
        stage(root, source, fail_before_publish=True)
    except RuntimeError:
        pass
    else:
        raise AssertionError("failure injection did not happen")
    assert not (root / "published.json").exists()
    assert list(root.glob("attempt-*/result.tmp"))
    assert stage(root, source) == (6, "created")
    assert stage(root, source) == (6, "reused")
    source.write_text("1 2 4\n", encoding="utf-8")
    try:
        stage(root, source)
    except ValueError:
        pass
    else:
        raise AssertionError("changed request must not reuse old output")
print("retry and publication assertions passed")
```

这里的业务验收使用三个已知整数，是为了让错误路径完全可解释；真实数据需要换成实际契约。复用检查也可以更强，例如同时验证计数、摘要和结果清单模式。读者可以故意篡改正式清单，观察当前检查能发现哪些问题，再补充必要验证。目标不是用更多断言装饰代码，而是让每项检查对应一个确实可能损害结论的失败模式。

还应注意请求键计算与实际读取之间的时间间隔。本例输入受控不变，所以两次读取指向相同内容；若输入可以并发修改，键与计算可能不一致。改进方式包括先读取稳定快照并同时用于摘要和计算，或要求生产者发布不可变版本。这一限制说明幂等协议依赖输入身份稳定，不能只因为出现了哈希函数就宣称所有竞态消失。

正式结果已经存在时，示例选择对不同请求直接拒绝，而不是覆盖。另一种设计可以用请求键划分不同版本目录，让多个请求共存；也可以在明确授权下替换某个发布入口。任何选择都应写进接口，尤其不能在复用失败时悄悄回退到旧结果，否则程序可能“为了可用”而改变了科学问题。

<a id="linux-3-trace-extra"></a>
### 6.6 把失败时间线写成可审查记录

对一次复杂失败，建议按事件顺序整理四列信息：已经确认完成的动作、尚未确认的动作、可能发生的副作用，以及下一步能够消除不确定性的证据。例如外部提交返回连接错误时，已确认的是请求曾发出，未确认的是服务是否提交成功，可能副作用是远端已有记录，下一证据应该是按请求键查询状态，而不是立即换新键再次提交。

这个时间线方法也适用于本地文件。生成器返回错误时，临时文件可能已经存在，但正式入口尚未切换；可以保留临时对象用于诊断，重跑时重新生成。若正式入口切换成功而日志写入失败，不能因为日志没有成功行就重复执行整个不可逆流程，应直接核验正式版本。状态证据有优先级，不能把最后一条日志当作唯一真相。

时间线还应标明观察来源。退出状态来自进程接口，文件内容来自产物验证，远端确认来自服务协议，操作者记忆只能作为待核对线索。不同来源互相矛盾时，先解释是否观察了不同尝试、不同路径或不同时间点，再怀疑系统违反语义。很多“偶发神秘故障”其实是多个尝试共享名字造成的证据混淆。

如果你能为每个失败窗口写出这样的时间线，就已经具备把脚本提升为可恢复工作流的核心能力。下一步应根据真实需求选择工具，而不是急于把所有场景压进更多陷阱和循环。清楚表达未知状态，也是一种正确性；强行把未知涂成成功或失败，才会给恢复制造更大风险。

## 7. 从脚本走向更大工作流的边界

<a id="linux-3-detail-29"></a>
### 7.1 阶段依赖可以表达成有向无环图

当步骤越来越多，可以把每一步视为节点，把必须先完成的关系视为有向边。只有所有前置条件已满足的节点才允许启动；失败策略决定下游是否取消，独立分支是否继续。这个模型比一段越来越长的串行脚本更容易揭示哪些步骤可以并行，以及哪些输出需要共同发布。

缓存则需要把节点身份绑定到输入和规则版本。仅根据输出修改时间决定是否重算，可能漏掉配置变化、依赖代码变化和外部数据更新。内容与配置感知的缓存更可靠，但成本和实现也更高。小型流程可以采用明确版本目录和人工清单，大型流程可以使用已有工作流工具；无论采用哪种，都要理解它的缓存与失败语义。

任务依赖图没有自动解决外部副作用。一个节点重复执行仍可能重复提交服务请求，分布式调度还会带来执行确认不确定性。节点接口应尽量设计为读取不可变输入、生成独立输出、验证后发布；不能避免副作用时，用服务端契约明确去重与恢复。

<a id="linux-3-detail-30"></a>
### 7.2 何时应把逻辑移出 Shell

出现复杂数据结构、正式格式解析、大量数值运算或难以测试的状态机时，把核心逻辑放到普通编程语言通常更清楚。Shell 保留少量环境设置和程序连接，复杂部分采用可单独测试的函数和数据类型。迁移的理由应是可读性与正确性，而不是某种语言身份上的优越感。

当需要跨机器调度、资源配额、依赖图和历史追踪时，现有任务系统可能比自写后台循环更合适。但引入系统后仍要核对退出状态传播、重试策略、日志保留和产物验收。调度器知道进程结束，并不知道你的科学结论是否成立；工作流工具知道缓存命中，也未必知道外部数据有没有悄悄变化。

脚本作为研究接口应保持可交接。另一个人应能在小输入上运行验证、看到有效参数、定位失败阶段和找到最终产物。若运行必须依赖作者记忆中的终端状态，即使脚本有几百行也不算成熟自动化。减少隐含状态，比增加更多神秘选项更有价值。

<a id="linux-3-subshell-extra"></a>
### 7.3 当前 Shell 与子 Shell 的状态边界

把一组命令放在子 Shell 中执行，可以限制工作目录和变量等状态改变的传播；在当前 Shell 中组织的命令组则可能保留这些变化。这个差别对可组合脚本很重要：一个辅助函数若悄悄改变当前目录，后续所有相对路径都可能改指向。将需要临时切换目录的步骤隔离，可以减少隐含耦合，但子 Shell 的失败仍需由调用者明确处理。

下面用一个临时目录验证目录和变量的边界，不依赖用户当前目录内容。它没有把子 Shell 当作完整安全沙箱；子 Shell 仍然可以写文件、访问网络和产生其他外部副作用。隔离进程内状态，不等于隔离所有外部世界。

```python
import subprocess
import tempfile

script = r'''
set -eu
start=$PWD
marker=parent
( cd "$1"; marker=child; [[ "$PWD" == "$1" ]] )
[[ "$PWD" == "$start" ]]
[[ "$marker" == parent ]]
{ marker=changed; }
[[ "$marker" == changed ]]
printf 'state-boundary-ok\n'
'''
with tempfile.TemporaryDirectory(prefix="linux-subshell-") as raw:
    p = subprocess.run(
        ["bash", "--noprofile", "--norc", "-c", script, "state", raw],
        env={"PATH": "/usr/bin:/bin", "LC_ALL": "C"},
        capture_output=True, text=True, timeout=5,
    )
    assert p.returncode == 0, p.stderr
    assert p.stdout == "state-boundary-ok\n"
print("subshell boundary assertions passed")
```

结果说明工作目录和普通变量变化没有从子 Shell 回传，而当前 Shell 命令组中的变量变化会保留。若需要子步骤返回数据，可以使用清楚编码的输出、文件或其他接口；若需要返回成功与否，可以使用退出状态。不要让调用者猜测某个变量是否因为运行位置不同而被修改。

研究脚本重构时尤其应检查这一层。把原来的串行块移到后台或管道中，可能改变它是否在父级状态里执行；代码文本看起来没变，变量传播却变了。反过来，把隔离块改成当前执行，也可能让目录和选项泄漏到后续步骤。每次结构调整都应重新核对状态所有权，而不能仅凭已有命令本身已经测试过就认为组合必然正确。

## 8. 练习与详细解析

<a id="linux-3-detail-32"></a>
### 8.1 入口与状态：四道基础进阶题

**题一：某脚本允许同一输出参数出现两次，但文档没有说明。为什么这会损害可复现性？**

**解析：** 调用者无法判断是首次生效、末次覆盖还是两者都使用，日志也可能只显示其中一个。应明确重复策略，并在解析后输出最终有效配置。若选择拒绝，就在高成本任务前返回用法错误；若选择覆盖，则保存参数来源和覆盖关系。可复现性依赖实际生效值，而不是命令行中曾出现过某个字符串。测试应包含重复参数，防止重构解析器时行为悄悄改变。

**题二：为什么不能把“输入文件存在”当作输入验证完成？**

**解析：** 它没有证明对象类型、可读性、格式、版本和内容完整，也不能保证检查之后名称不变。应在实际读取中验证数据契约，并记录输入身份。存在性检查适合快速发现明显错误，不能代替业务验收。如果输入可能并发变化，使用不可变版本或受控快照；如果只在完全受控目录运行，也应把这一前提写清楚，避免后续迁移时误以为已经具有更强保证。

**题三：在失败命令后先打印日志，再保存上一条退出状态，会发生什么？**

**解析：** 上一条状态已经变成日志命令的状态，原失败可能被覆盖。应立即保存状态，或使用条件分支直接取得失败结果。函数末尾也有同样问题：失败后加一个成功打印，可能让函数最终返回零。退出状态是随执行不断更新的值，不是永久记住最近一次重要错误的全局异常对象。代码审阅应特别检查这些看似无害的提示语句。

**题四：数组调用为何比字符串加重新解释更容易证明参数正确？**

**解析：** 数组保存每个参数的边界，引用展开后空格、星号和空字符串仍是各自元素里的数据。字符串拼接会丢失边界，重新解释又让数据中的语法字符获得执行含义。数组不能自动证明路径合法或选项含义正确，但它消除了一个重要混淆层。调用者还需按目标工具契约处理以减号开头的值，并验证输出和退出状态。

<a id="linux-3-detail-33"></a>
### 8.2 严格选项：四道反例分析题

**题五：函数内部第一步失败，第二步打印成功，而函数被放在条件位置。为什么开启遇错退出仍可能进入成功分支？**

**解析：** 条件上下文会影响遇错退出规则，函数体中的失败可能不自动中止；后面的成功命令使函数最终返回零。应在关键步骤后显式返回失败，并让函数契约不依赖调用位置。可以用本章实验修改成“失败后立即返回”，再确认第二步不执行且条件进入失败路径。修复目标是局部正确性，而不是寻找另一个全局开关掩盖问题。

**题六：启用管道失败传播后，能否仅凭整个流水线的状态判断最初根因？**

**解析：** 不能。汇总状态按规则来自某个非零成员，不表示时间上最先失败或逻辑上最根本的错误。下游提前退出可能让上游出现断管道，多个成员也可能同时失败。需要及时保存各成员状态并结合错误日志和数据流协议。该选项改善失败可见性，但不自动完成因果分析，更不能代替产物验证。

**题七：为什么给每条命令后面都加“或成功”不是健壮性？**

**解析：** 它把预期空结果、暂时故障和真正损坏全部压成成功，使后续阶段在无效前提下继续。健壮性应依据命令契约区分状态，对允许的空结果形成明确数据，对真正失败停止依赖步骤并保留诊断。只有在清理等尽力操作中，某些失败才可能被容忍，而且仍应考虑记录。无条件忽略不是恢复，而是失去证据。

**题八：未设置变量检查能否取代必需参数检查？**

**解析：** 不能。变量可能已经设置为空字符串、无效路径或越界数字，这些都不会被简单的未设置检查完整识别。接口需要明确缺失与空值是否等价，并按语法、范围和资源条件验证。严格选项适合暴露一类拼写和状态错误；参数契约则解释什么值是合法输入。两者互补，不能因为开启选项就省略清楚的用法错误。

<a id="linux-3-detail-34"></a>
### 8.3 并发、清理与重试：六道设计题

**题九：主脚本启动五个后台任务后立即返回零，为什么调度器可能错误显示成功？**

**解析：** 主脚本的成功只描述启动和自身结束，没有取得子任务最终状态。必须等待每个任务，按策略汇总，阻止不合格结果发布，并在退出前完成归属清理。任务日志还应与业务标识关联，不能只有一个总布尔值。若任务被故意转交给更长期监督者，则要把所有权转移和状态查询接口明确记录，不能靠后台符号暗示转移已经成立。

**题十：任何一个并行分片失败后立刻退出主脚本，为什么不一定叫“尽快失败”？**

**解析：** 它只是尽快放弃监督，可能留下其他子任务继续占资源和写产物。真正策略应停止启动新任务、请求活动成员结束、等待回收并隔离不完整输出，最后返回整体失败。若允许独立任务继续，也应有另一个明确监督主体。完成条件包括资源与状态收尾，而不是主进程消失得足够快。

**题十一：退出陷阱能保证任何情况下都清理成功吗？**

**解析：** 不能。强制终止和系统崩溃不会给用户态清理机会，清理操作本身也可能失败。陷阱应作为正常和可处理异常路径的辅助，把持久状态设计成能够识别半成品和安全重跑。保留原始退出状态，限定清理范围，记录失败，不要把未知目录全部删除。可靠恢复来自协议，而不是假设清理一定执行。

**题十二：某次远程插入已成功，但本地在写标记前中断。重跑怎样避免重复插入？**

**解析：** 需要服务端支持稳定幂等键、唯一业务键、事务或状态查询等机制。本地标记不存在不能证明远端未执行，把标记移到调用前又会产生标记存在但操作未执行的失败窗口。重试使用同一逻辑请求身份，查询或重复提交时由服务端契约去重。若服务没有这种能力，就不能承诺恰好一次，只能说明较弱保证并安排核对或补偿。

**题十三：四个任务并发为何仍可能造成处理器过度争用？**

**解析：** 每个任务内部可能再创建多个线程或子进程，真正可运行执行单元远多于四个。应记录任务数与内部线程设置，结合机器和配额测试吞吐与延迟。还要考虑内存带宽、磁盘和设备共享，处理器不是唯一瓶颈。不能根据任务数线性外推速度，也不应在教材里给没有实测条件的通用性能倍数。

**题十四：给输出目录加锁以后，为什么仍需验证结果和设计重试？**

**解析：** 锁只限制并发进入，持锁进程仍可能失败、写错内容或在发布前崩溃。还需版本身份、临时产物、验收与发布协议，以及锁失效后的恢复规则。网络文件系统和多机环境要核对实际锁语义。一个锁文件存在也不一定说明持有者仍活着，随意删除残留标志又可能干扰慢任务。互斥与正确性是不同层次的保证。

## 9. 综合追问：重试会不会重复副作用

设一个流程按顺序执行提取特征、写外部索引、发布模型三个阶段，第二阶段可能在服务已写入后连接断开。请分别给出三阶段的重跑规则，并说明一个总完成文件为何不足以解决问题。

特征提取可以引用不可变输入版本和有效配置，输出到独立临时对象，验证后发布；重跑复用身份一致的已发布版本，不复用半成品。外部索引必须使用服务支持的幂等键或唯一业务键，连接断开后查询状态或用同一键重试；没有服务契约就要保留未知状态并核对。模型发布需要验证权重、配置与索引版本的兼容关系，再切换集合入口。

总完成文件只说明整个流程曾走到某个末端，不能表达中间远端操作是否已经发生。它不存在时，前两步可能都没做，也可能已经做完；它存在时，又可能对应旧配置。需要阶段状态、请求身份和产物清单共同支持恢复。状态粒度应覆盖真实副作用边界，而不是随便每十行脚本写一个标记。

进一步，设计故障测试时要覆盖每个确认窗口：操作前失败、操作已完成但确认丢失、确认已收到但本地记录失败。分别检查是否会漏执行、重复执行或误发布。对于无法原子协调的系统，承认并处理不确定状态，比在脚本里写一个永远重试循环更接近正确工程。

<a id="visual-03-mechanism"></a>

### 图解：重试不是幂等：重复追加会重复副作用

![重试不是幂等：重复追加会重复副作用](images/03-mechanism.svg)

两条时间线都先让服务方完成写入，再故意丢掉返回确认；调用方因此无法区分“未执行”与“已执行但未收到答复”。普通追加在重试后产生两份 k；具有约定去重能力的服务按同一调用者与请求键识别重复，再返回已有结果，仍只有一份业务写入。它不是简单把本地日志改写成成功，也不是发现相同参数就一律拒绝用户创建第二份合法资源。

[Amazon Builders’ Library 的幂等 API 教学文章](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)用同类请求／响应图区分重试和新意图，并强调去重记录与变更必须一致提交。图中右侧只是受控服务模型；实现还要规定键的作用域、保留时间、相同键却不同负载时的错误，以及重试如何取得语义等价结果。这里没有发起远程调用，也不从一次本地模型推导真实服务的故障保证。

任务超时只意味着调用方没有得到确认，不意味着副作用没有发生。盲目重试追加操作可能重复写入；用稳定任务键发布同一结果，可以让重复执行落在同一个逻辑身份上。

按键覆盖也不天然安全：不同输入若错误共用一个键，会覆盖有效结果。外部扣费或消息发送需要接收方支持的幂等协议，不能靠本地文件规则直接推广。

## 10. 继续研究与学习检查

能够独立解释本章反例之后，可以研究工作流系统怎样存储节点状态、调度器怎样处理重试与抢占、服务怎样实现幂等请求，以及文件系统怎样提供不同持久性保证。每个方向都从一个明确接口开始：它接受什么输入，成功意味着什么，确认丢失后怎样查证，哪些状态允许重跑。

也可以尝试把本章入口迁移到普通编程语言，并比较两种实现的可测试性。不要只比较行数；比较未知参数、空值、含空格路径、子任务失败、取消和恢复是否都有清楚行为。一个更短但隐含状态更多的实现，不一定更容易维护；一个类型更丰富的实现，也仍可能忽略外部副作用。

最后做一次交接演练：让另一个人在全新终端中，仅根据文档运行小输入，故意制造一次失败，再从记录中解释原因与恢复位置。若他必须依赖原作者回忆临时环境，说明契约还不完整。研究脚本的成熟度体现在别人能否理解和验证它，而不只是作者自己是否已经习惯那套操作顺序。



**延伸算例：重试上限改变的是负载与等待预算。** 若每次尝试独立以一半概率成功，最多尝试三次，则至少成功一次的概率为 $`1-(\frac12)^3=\frac78`$，期望尝试数为 $`1+\frac12+\frac14=\frac74`$。这只是独立、固定成功率的模型，不是实际故障恢复保证。服务持续不可用时，多次尝试可能完全相关；相同时间大量客户端重试还会增加负载，改变成功概率。退避与抖动可用于分散请求，但不能替代幂等键与总截止时间。把最多三次写成循环只是实施尝试预算，仍需在每次重试前确认错误可重试、剩余时间足够且请求身份未改变。
