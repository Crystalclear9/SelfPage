## 1. 诊断对象：先定义什么叫失败

<a id="linux-4-detail-2"></a>
### 1.1 从模糊现象到可检验陈述

“服务器不行”没有明确观察对象，无法指导下一步。一个可操作的现象至少包含运行标识、时间范围、工作量、预期行为和实际行为。例如，同一数据快照、相同批大小的训练，前一千批每批约二百毫秒，随后连续五十批超过两秒；进程仍在，检查点没有更新。这个陈述允许分别检查输入长度、加载等待、计算时间、保存耗时和资源压力。若只记录“今天训练很慢”，第二天即使速度恢复，也不知道原因是否消失。

失败可分为正确性失败、终止性失败、性能失败和交付失败。正确性失败是计算出了不符合定义的结果，如样本重复或损失成为非数；终止性失败是任务异常退出、死锁或长期没有进度；性能失败是结果仍正确，但耗时或成本超出预算；交付失败则是进程退出正常，却没有可验证的完整产物。四类可以同时发生，定位顺序通常先保证结果含义与数据安全，再改善速度，否则可能更快地产生错误文件。

性能目标必须和工作量绑定。每秒处理多少样本比单独的设备利用率更接近训练目标，但不同长度样本每秒数量也不可直接比较。语言模型可同时报告有效词元吞吐、批延迟和序列长度分布；数据库提取可报告满足同一筛选条件的行数、字节量和快照标识。把工作量定义清楚，才能区分实现变慢与任务变难。压低输入质量、少处理样本或跳过校验得到的加速，不属于同一任务的性能改进。

<a id="linux-4-detail-3"></a>
### 1.2 四类资源与跨层限制

CPU 提供可调度的计算时间，内存承载工作集及缓存，存储负责持久化和读写，网络连接远程数据与协同计算。GPU 还具有自己的显存、执行单元、传输路径和异步队列。一个训练步骤从远端取文件，经主机解码、拼批和复制后才能计算，最后还可能同步指标与写入检查点。任何一段都能限制最终吞吐，不能因为模型在 GPU 上执行就只监控 GPU。

资源“有剩余”也必须问剩余属于谁。主机拥有许多核，作业却可能只获配两个；主机空闲内存很多，容器可能达到内存上限；文件系统有空间，用户配额仍可能耗尽；GPU 总显存未满，连续块分配或设备上下文仍可能失败。命名空间、调度器和控制组改变进程所见边界。查看全机指标后，还应查看本作业实际允许的 CPU、内存、文件描述符和进程数量限制。

<a id="deep-dive-1"></a>
<a id="linux-4-detail-4"></a>
### 1.3 证据链与反事实实验

证据链由现象、候选解释、区分观察、最小干预和结果组成。“GPU 空闲，所以换显卡”跳过了中间三步。“加载器等待占批耗时的大半；固定预处理后的同一输入使等待显著下降；结果校验不变”，才支持数据路径是重要瓶颈。结论仍应限定在这套数据、并发和硬件条件下，因为增加工作进程后瓶颈可能转移到共享存储。

反事实实验要改变能够区分假设的因素。怀疑解码慢，可在内存中重放已经解码的同一小批，保持模型和批次内容固定；怀疑网络慢，可比较同一文件的受控本地副本，同时记录复制本身的成本；怀疑数值异常，可保存触发异常的输入与随机状态，缩小到单步。若一口气改数据、依赖、模型和设备，成功只能说明新组合可运行，不能证明任何一个旧组件是根因。

诊断不是要求每次都证明唯一原因。生产环境常有多个共同原因，权限也未必允许完整实验。此时应明确证据等级：直接观察到的事实、受到实验支持的解释，以及尚未排除的可能性。把“未观察到”写成“没有发生”会夸大采样能力；把一次相关写成必然因果，会让后续维护者重复错误处置。

## 2. 时间、吞吐与等待：建立统一计量语言

<a id="linux-4-detail-6"></a>
### 2.1 墙钟时间与 CPU 时间

墙钟时间描述外界经过多久，CPU 时间描述线程真正占用处理器多久。等待磁盘、锁、网络或者调度时，墙钟仍前进，线程 CPU 时间通常不增加。对于一个单线程进程，若墙钟十秒而用户态加内核态 CPU 时间仅一秒，其余时间需要从等待和未获调度解释；对于多线程或子进程总和，累计 CPU 时间可以大于墙钟时间，因此不能把两者的比值无条件当成零到百分之百的利用率。

测量持续时间使用单调时钟，记录跨机器事件使用带时区的墙钟时间。系统校时可能让日期时间跳变，直接相减会得到负耗时；单调时钟适合本机同一次运行内计算间隔，却不是全球统一时间戳。分布式日志还受时钟偏移影响，不能仅凭两台机器各自打印的毫秒时间断言严格先后。最好同时保留运行内序号、请求标识和阶段关系。

定义时间区间内完成的工作量为 $`N`$，墙钟间隔为 $`T`$，平均吞吐为 $`X=\frac{N}{T}`$。批次平均延迟可写为总批延迟除以批数，但只有批次工作量相同时才容易比较。若存在并发，一个请求的等待时间可以与另一个请求的计算重叠，不能把所有请求延迟相加就称作整体运行时间。先画资源与请求两种时间线，再判断哪些成本能够重叠。

<a id="linux-4-detail-7"></a>
### 2.2 串行比例与流水线的边界

假设总耗时中比例 $`s`$ 永远串行，其余部分理想地获得 $`p`$ 倍加速，则整体加速上界为 $`\frac{1}{(s+\frac{(1-s)}{p})}`$。这个表达式来自把旧时间归一为一，而不是硬件保证。若串行比例为四分之一，即使其余计算无限快，也最多加速四倍。训练中每步都同步的日志、单进程数据转换和串行检查点可能成为这部分成本，继续增加计算设备并不能消除它们。

稳定流水线的吞吐由最慢阶段的服务率约束。加载每批八十毫秒、计算每批二十毫秒，若阶段不能重叠，约一百毫秒完成一批；理想充分重叠后，稳态间隔仍至少八十毫秒，首批启动和末批排空另算。把计算加速到十毫秒，稳态吞吐仍没有翻倍。反过来，增加加载并发可能增加内存副本和存储争用，所以不能只依据阶段算式无限增加工作进程。

平均在系统中的任务数、平均到达率和平均停留时间之间，可在稳定且边界一致的条件下使用 $`L=\lambda W`$。这里的停留时间包含服务和排队，到达与离开统计也要覆盖同一系统。若队列持续增长，有限窗口的均值未必代表稳定状态；若把加载队列长度和整个训练作业耗时混用，公式没有解释力。排队变长常是需求接近服务能力的信号，但还要检查突发到达与下游阻塞。

<a id="linux-4-detail-8"></a>
### 2.3 分位数、采样和测量扰动

平均延迟隐藏少量长停顿。百个批次中九十九个耗时一百毫秒、一个耗时十秒，平均约一百九十九毫秒，而尾部体验很差。应同时记录中位数、较高分位数、最大值与样本数，并保留异常批次对应的数据规模和阶段。样本太少时高分位数近似最大值，不适合解释细微差别；比较不同运行时，也应使用相同统计窗口与相同异常处理规则。

采样周期决定能看见什么。每分钟记录一次内存，可能错过几十毫秒的分配峰值；每毫秒打印完整堆栈，又可能让日志本身成为瓶颈。先使用低开销阶段计时和资源计数，确认异常时间段，再短时启用更精细的分析。监控应该回答问题，而非无限收集数据。日志过密还会放大磁盘占用，并把程序等待输出误判成业务计算慢。

异步设备让计时更加微妙。主机提交 GPU 工作后很快返回，只测函数返回可能得到排队时间而非设备完成时间。需要按框架官方语义选择设备事件或同步边界，并说明测的是核执行、数据传输还是端到端步骤。同步会破坏原本重叠，所以局部剖析结果不能直接代替正常运行吞吐。没有 GPU 的机器可以学习这一区别，但不能据此伪造设备性能数字。

## 3. CPU、调度与控制组：忙碌不等于有效计算

<a id="linux-4-detail-10"></a>
### 3.1 百分比的分母与负载含义

监控工具显示百分之百，可能表示一个逻辑 CPU 被占满，也可能表示整机总能力被占满。比较数字前必须确认工具的归一化约定、采样窗口与线程范围。一个四线程进程累计三点二秒 CPU、墙钟一秒，可称平均使用三点二个 CPU；若整机三十二核，主机平均利用率仍可能只有一成。用全机低利用率来否定该进程已经受到两核配额限制，是层级混淆。

Linux 的负载平均值与 CPU 利用率不同，它反映一定时间尺度内可运行任务以及处于不可中断等待的任务数量的平滑统计，不是百分比。大量存储等待也可能抬高负载。负载十在两核配额作业与六十四核专用机器上的含义不同，更不能直接除以宿主核数得出本作业拥塞程度。应结合允许的 CPU、运行队列、任务状态和资源压力解释。

用户态 CPU 时间高可能来自有效数值计算，也可能来自重复解码、忙等待或意外的纯 Python 循环。内核态时间高可能来自大量小读写、页错误、网络协议处理或系统调用频繁，不能仅凭比例认定内核有缺陷。先找阶段，再缩小到线程或调用栈。多个底层数学库各自创建线程，还会产生嵌套并行和调度争用，线程数多于核数不保证更快。

<a id="linux-4-detail-11"></a>
### 3.2 配额、亲和性与压力信息

控制组第二版中，`cpu.max`可表达周期内允许的 CPU 时间预算。若内容为`200000 100000`，意味着在一百毫秒周期内允许合计二百毫秒 CPU 时间，直观上相当于约两个 CPU 的持续预算；这不指定固定的两个核，也不保证瞬时并行严格为二。`cpu.stat`的节流相关累计计数增量可支持配额约束假设，读取时仍要考虑祖先控制组施加的限制。[内核控制组文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)定义了这些字段的边界。

CPU 亲和性限制允许运行的位置，配额限制时间预算，两者不是同一机制。允许八个核但预算两核的程序可能短时在多个核上运行后被节流；只允许一个核的程序，即使预算宽松也不能自动同时使用八核。调度器提交参数、容器配置和进程状态应相互核对，不能从处理器型号或系统总核数推断实际可用能力。本章只读解释相关接口，不修改共享机器的资源控制设置。

压力阻塞信息描述任务由于 CPU、内存或 I/O 资源而被延迟的时间比例及累计量，通常可从`/proc/pressure`获取，具体字段与支持能力依内核配置而定。它能提示“任务在等资源”，却不能直接指出哪个函数该优化。全机压力和控制组压力范围不同；统计的部分任务受阻与全部任务受阻也不同，尤其不能把系统级 CPU 的全部受阻字段机械地套用到其他资源。[内核 PSI 文档](https://www.kernel.org/doc/html/v6.6/accounting/psi.html)应与运行内核版本一起阅读。

<a id="linux-4-detail-12"></a>
### 3.3 一个受控计时实验

下面对比等待与计算，不制造长时高负载，也不宣称任何机器上的固定性能。测试只断言等待阶段确实经过合理的墙钟时间、计算阶段消耗了正的 CPU 时间，以及计算结果正确。不同调度和虚拟化环境会改变比值，因此不设置“CPU 利用率一定达到某值”的脆弱断言。`process_time`在此只统计当前进程；若工作被分派给子进程，就应另行收集子进程数据。

```python
import time

start_wall = time.monotonic()
start_cpu = time.process_time()
time.sleep(0.08)
sleep_wall = time.monotonic() - start_wall
sleep_cpu = time.process_time() - start_cpu

start_wall = time.monotonic()
start_cpu = time.process_time()
checksum = sum((i * i) % 997 for i in range(300000))
compute_wall = time.monotonic() - start_wall
compute_cpu = time.process_time() - start_cpu
assert checksum == 149406557
assert sleep_wall >= 0.06
assert compute_cpu > 0 and compute_wall > 0
print({"sleep_wall": round(sleep_wall, 5),
       "sleep_cpu": round(sleep_cpu, 5),
       "compute_wall": round(compute_wall, 5),
       "compute_cpu": round(compute_cpu, 5)})
```

实验说明“经过时间”和“使用处理器时间”是不同观察量。若等待时间远高于预期，可检查调度暂停和虚拟机负载，不能仅根据一次测试宣布系统时钟坏了。若计算 CPU 时间为正但墙钟很长，也可能是计算期间多次被调度出去。要定位生产作业，仍需把同样的计量放进实际阶段，并记录工作量，不能把这个小循环的表现外推到模型训练。

<a id="linux-4-detail-13"></a>
## 4. 主机内存、缓存与 OOM：先辨认计数范围

<a id="linux-4-detail-14"></a>
### 4.1 虚拟地址、驻留集与比例分摊

虚拟内存大小描述进程地址空间中映射区域的规模，不等于已经占用同样数量的物理内存。映射大文件、保留尚未触碰的地址范围和共享库都会扩大这个数字。驻留集描述当前驻留物理内存的映射页面，但共享页可能在多个进程的驻留集中重复计算。把八个工作进程的驻留集直接相加，可能高估实际物理占用；只看主进程，又会低估子进程私有缓冲与预取批次。

比例分摊驻留集把共享页面按映射者数量分摊，可用于估算多个进程共同承担的占用，但读取这类统计有成本，也受权限和内核接口影响。`/proc/PID/smaps_rollup`在支持的系统上提供汇总；分析时保留匿名页、文件页和交换等分类比只看一个总数更有帮助。某些运行时的分配器保留已释放内存，业务对象消失后驻留集不立刻下降，这不自动证明泄漏；不过无界增长也不能都解释为缓存。

应把三个问题分开：程序请求了多少空间、当前驻留了多少空间、再增长是否会触发资源边界。一个大地址空间但很少驻留的进程可能稳定运行；一个驻留集不大但所在控制组已被其他成员占满的进程可能分配失败；一个峰值很短的进程可能在低频监控中看起来始终不高。诊断必须同时覆盖作业整体、时间峰值和有效限制，而非只截取主进程某一时刻的数字。

<a id="linux-4-detail-15"></a>
### 4.2 页缓存、可用内存与换页

Linux 会利用空闲物理内存缓存文件内容，以减少后续存储访问。看到空闲内存很少，并不等于系统已经没有可供应用使用的内存。`MemAvailable`是内核对在不引起交换的情况下可供新应用使用空间的估计，其中考虑部分可回收缓存；它也不是未来分配成功的承诺，因为碎片、限制、并发和不同内存类型仍可能影响分配。实际字段语义以运行内核的接口文档为准。

换页不是只有“有或没有”两个状态。长期未访问的匿名页曾被换出，交换使用量仍不为零，但当前任务可能没有显著交换开销；相反，持续换入换出并伴随内存压力和业务停顿，才支持工作集超过可承受范围的解释。对比累计计数的时间增量，并把它对齐到性能异常窗口。仅看到交换区用了两吉字节就立刻认定当前训练在抖动，会把历史状态误当成实时行为。

文件映射与普通读取都可能受到页缓存影响，重复运行比第一次快并不必然是算法优化成功。冷启动、预热后稳定运行和真实线上混合访问是不同实验条件。不要在共享服务器上随意清空全机缓存来追求“公平”；更可取的是报告预热策略、交替比较、隔离测试输入以及明确缓存状态。研究结论应指出结果适用于哪种访问模式，而不是把一次热缓存读取当成存储的持续能力。

<a id="linux-4-detail-16"></a>
### 4.3 泄漏、预取与工作集模型

估算加载器内存可从并发工作进程数、每进程预取批数、单批解码后大小和复制次数出发。假设八个进程各预取两批，每批解码后约六十四兆字节，仅这些批次就可能达到约一吉字节，尚未计入主进程队列、原始压缩数据、固定页缓冲和运行时开销。压缩文件体积无法直接代表解码后的工作集，图像像素、音频长度和词元填充都会显著改变大小。

若内存每处理一个样本都持续增加，且在多个完整周期后仍不回落，可检查保存所有预测、把带计算图的损失追加到列表、无界缓存、日志队列和未关闭对象。若增长主要发生在前几轮随后平台化，则可能是预热缓存或分配器扩张。区分实验应保持数据顺序，减少预取、关闭特定缓存或只保留聚合统计，观察增长斜率而非仅比较初始与末尾两个数。

“降低批大小”能减少某些激活和批缓冲，却不会按比例减少模型参数、优化器状态和固定数据索引。若主要问题是每步永久保留计算图，降低批大小只是推迟失败。把总内存分为固定项、随批量变化项、随序列长度变化项和随历史步数增长项，才能提出有针对性的修复。诊断记录最好包含步数、批量、有效长度与工作进程数量，使不同运行具备可比较的自变量。

<a id="linux-4-detail-17"></a>
### 4.4 OOM、终止信号与控制组事件

进程消失且没有 Python 异常，不足以证明内存不足。它可能被用户终止、调度器回收、父进程取消、节点重启或 OOM 机制结束。Shell 中常见的状态一百三十七通常对应一百二十八加终止信号九，但程序也能主动以相同数值退出，管道和包装器还可能改变最终状态。Python 的直接子进程返回负信号编号与 Shell 的编码规则也不同。因此退出数字只是线索，必须核对作业记录和相关系统事件。

在控制组第二版中，应结合`memory.current`、`memory.max`、`memory.high`和`memory.events`的增量理解内存约束。达到较高压力边界可能发生回收与节流，达到最大限制也不意味着每一次尝试都会立即杀进程；事件计数区分接近限制、进入 OOM 状态和实际杀进程等情况。事件范围可能包含子控制组，读取当前路径还不够时要检查祖先限制。详细解释见[控制组内存接口](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)。

没有权限读取内核日志时，应明确证据缺口，请管理员提供对应时间和作业范围的记录，而非运行破坏性压力测试试图“重现一次”。本章实验不会耗尽系统内存。对真实任务的第一步通常是收集最后进度、退出状态、有效限制和峰值记录，随后在小输入上验证内存随批量或历史步数的变化。只有证据支持后，才选择减少预取、修正保留引用、调整数据结构或申请更多资源。

<a id="linux-4-detail-18"></a>
## 5. 存储与 I/O：容量、元数据和访问模式

<a id="linux-4-detail-19"></a>
### 5.1 吞吐、操作频率与延迟

存储吞吐描述每秒字节数，操作频率描述每秒请求数，延迟描述请求从提交到完成的时间。大块顺序读可能产生高吞吐而请求数不多；大量小文件随机访问可能吞吐很低，却已受限于元数据和单次请求延迟。故“只读了几兆字节，磁盘不可能忙”并不成立。还要考虑请求是否被合并、文件是否在缓存、底层是否为网络存储，以及监控观察的是文件系统、块设备还是远端服务。

队列中并发未完成请求数与延迟、完成率在稳定边界下有数量关系，但设备队列和应用队列不是同一个系统。应用单线程串行打开文件，即使设备还有并行能力，也可能受往返延迟限制；增加并发能隐藏一部分等待，却可能让共享设备排队更深，尾延迟上升。应同时报告端到端吞吐、批等待和设备请求指标，不能仅追求某个工具显示的队列深度更大。

CPU 的 I/O 等待字段也不能直接理解成某进程实际等盘的精确时长。处理器可能在某任务等待时执行其他任务，多核统计与归属存在限制，内核文档还指出该计数并非所有条件下都可靠。高等待比例可作为进一步查看存储的线索，低等待也不能排除单个作业被慢存储拖住。应结合进程状态、实际读写速率、业务阶段和压力信息。[`/proc/stat` 文档](https://www.man7.org/linux/man-pages/man5/proc_stat.5.html)说明了这些计数的含义与限制。

<a id="linux-4-detail-20"></a>
### 5.2 容量不足不只有块空间

`df`观察挂载文件系统层面的空间统计，`du`根据可遍历的目录树累加文件占用。二者的范围和机制不同，不能期待永远相等。检查路径时先确认它属于哪个挂载点：看根分区有空间，不能证明输出目录所在的数据盘有空间。符号链接、挂载覆盖、快照、配额、文件系统保留空间和稀疏文件也都会改变直观解释。

inode 是文件系统对象的元数据资源。许多很小的文件可能耗尽 inode，即使数据块仍有剩余。相反，少量巨大文件可能先用完块空间。若保存失败，应区分空间不足、inode 不足、用户配额、只读挂载、权限和远端服务错误，记录系统调用错误信息。每次检查点完整复制模型、每步生成独立小日志、缓存从不淘汰，分别会形成不同的耗尽模式，修复策略也应不同。

稀疏文件逻辑长度可以远大于实际分配块数，因此文件大小字段与磁盘占用不是同一量。某些压缩或写时复制文件系统又有进一步差异。估算训练产物预算时，应考虑检查点最大同时存在数量：旧正式文件、新临时文件和保留版本在替换过程中可能并存。剩余空间只比一个检查点稍大，不一定足以完成下一次安全发布。

<a id="linux-4-detail-21"></a>
### 5.3 为什么删除文件后空间可能不下降

路径名是找到文件对象的一种入口，已打开的文件描述符也持有引用。移除最后一个目录项后，只要进程仍持有打开引用，文件内容仍可能占用空间，直到相应引用释放。于是`du`找不到该文件，文件系统空间却尚未回收。日志轮转中删除当前日志但进程继续向旧描述符写入，就是常见情形。解决要依据写入进程的正常重新打开或退出协议，不能只反复删除更多目录。

下面实验仅创建一个小临时文件，证明解除路径名后仍可读写已打开对象，并通过`/proc/self/fd`观察当前进程自己的描述符。不对真实日志操作，不要求管理员权限，也不依赖文件系统空闲块恰好减少多少。目录退出时自动清理；观察链接字符串只是 Linux 上的机制示例，不将其当成跨系统稳定的业务接口。

```python
import os
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory(prefix="learning-open-file-") as directory:
    path = Path(directory) / "trace.log"
    with path.open("w+b") as stream:
        stream.write(b"first\n")
        stream.flush()
        descriptor = stream.fileno()
        path.unlink()
        assert not path.exists()
        assert os.fstat(descriptor).st_nlink == 0
        stream.write(b"second\n")
        stream.flush()
        stream.seek(0)
        assert stream.read() == b"first\nsecond\n"
        fd_target = os.readlink(f"/proc/self/fd/{descriptor}")
        print({"name_removed": True, "still_readable": True,
               "fd_target": fd_target})
    assert not Path(f"/proc/self/fd/{descriptor}").exists()
assert not Path(directory).exists()
```

最后关于描述符路径的断言只适用于本段没有额外并发开关描述符的微型实验；在多线程程序中相同编号可能立即被重用，不能靠编号存在与否追踪原对象。真实排查还需要进程标识和对象信息，并考虑进程退出与标识重用的竞争。这里真正稳定的结论来自打开流的读回结果和链接计数，而不是某次列表截图。

<a id="linux-4-detail-22"></a>
### 5.4 数据访问的区分实验

怀疑小文件开销时，先记录每批打开的文件数与字节数，再比较保持同一记录集合的顺序容器或分片读取；验证样本标识和顺序契约没有改变。怀疑压缩解码时，用同一小批预解码输入隔离 CPU 成本；怀疑存储吞吐时，观察批等待与实际读取是否同时上升。不能把“把全部数据复制进内存”直接当生产修复，因为它可能越过内存预算或改变缓存条件。

网络文件系统增加了服务端负载、客户端缓存、网络重传和一致性等层次。客户端看到的打开成功不代表所有远端访问都会低延迟；主机网卡吞吐不高，也可能是大量串行元数据往返受限。先检查是否所有作业同时变慢、是否仅一个目录或文件异常，并把证据交给负责对应层的人员。短期使用受控本地副本可以验证路径假设，但应保留源快照、校验值与复制成本，避免把数据版本差异误认为性能改善。

<a id="linux-4-detail-23"></a>
## 6. GPU 与分布式：设备指标必须连回工作流

<a id="linux-4-detail-24"></a>
### 6.1 显存组成与批量的关系

训练显存通常包含参数、梯度、优化器状态、激活、临时工作区和运行时保留内存。不同精度、优化器和实现会改变各项大小，不能用一个固定倍数概括所有模型。批量和序列长度主要影响部分激活与输入，参数状态通常不随批量同比缩小；注意力等运算的某些中间量还可能随长度出现非线性增长。因此“昨天同样批量能跑”并不能排除今天长序列批次触发峰值。

框架统计的已分配、已保留与设备工具观察的进程占用范围不同。分配器可保留暂时不用的块供后续复用，其他设备上下文也可能占用空间。释放业务对象或请求清理缓存，不保证所有显示数字立刻归零；反过来，不能用“都是缓存”解释持续增长。应记录相同阶段的峰值与当前值，并检查对象引用、计算图生命周期及操作工作区。具体接口和同步语义依框架版本查询官方文档。

混合精度、激活重计算和梯度累积是不同取舍。混合精度可能降低部分存储和计算成本，但有数值范围与状态精度条件；重计算减少保存的激活，却增加前向计算；累积允许较小微批量近似较大总批量的梯度求和，但含批统计、随机性、损失归一化和优化器步频时不保证逐位等价。做内存修复时，应同时验证训练含义和数值稳定性，不能只记录“不再报错”。

<a id="linux-4-detail-25"></a>
### 6.2 低利用率的多个竞争解释

GPU 利用率低可来自输入饥饿、模型太小、主机频繁同步、CPU 侧串行控制、设备间通信或任务已经失败。区分方法不是立刻增大模型，而是对齐数据等待、传输、计算和同步阶段。若缓存一批输入并重复执行后吞吐显著改善，支持输入路径假设；若设备上存在大量很短的工作片段且主机间隔长，可能需要检查提交开销；若只有保存时出现周期性空闲，重点应转向检查点路径。

设备利用率是采样窗内的活动指标，不是模型质量、资源效率或理论峰值达到程度。通过添加无意义计算可以让利用率变高，却让目标任务更慢。应以固定正确性要求下的端到端吞吐、总成本和尾延迟评价改进，并报告设备型号、精度、输入形状、预热和同步方式。跨版本内核选择、自动调优和编译缓存也可能影响前几步，所以首次迭代不宜直接代表稳态。

本章未在 GPU 上执行实验，因此不提供伪造的显存或利用率结果。学习时可先画时间线并提出能够区分解释的实验，再在具备相应设备和权限的环境运行。工具名称不是结论：即使能够显示很多曲线，如果没有批次标识和阶段时间，也可能无法判断哪一条变化发生在问题之前。

<a id="linux-4-detail-26"></a>
### 6.3 分布式挂起与最慢参与者

同步训练的一步通常受到最慢参与者影响。一台节点读取数据慢，其他节点可能停在集合通信处，看起来像通信故障；一个进程因坏样本退出，其余进程可能等待而不再产生新日志。诊断应收集每个参与者最后进入和完成的阶段、退出状态与样本标识，并区分谁先异常。只看主进程最后打印的通信超时，可能错过更早的远端内存错误。

分布式日志需要共享运行标识和参与者标识，且避免无限制重复输出同一错误。检查所有参与者是否使用同一模型结构、相同通信步骤和兼容配置；条件分支若让部分参与者跳过集合操作，会产生协议不一致。网络可达性只是必要条件之一，连接成功不证明数据路径、消息大小和长期负载都正常。微型通信测试也不能取代完整训练的数据与计算行为验证。

超时用于约束等待并产生诊断信息，不会自动恢复一致状态。简单延长超时可能掩盖持续堵塞，过短超时又会把正常波动误判为失败。恢复要回到明确的检查点与参与者集合，并核对已执行的外部副作用。本文不连接远端、不启动通信服务；这些机制说明是后续设备与集群实践的准备，不代表已经测试某个集群。

## 7. 环境故障：从实际执行对象缩小范围

<a id="sec-2-1"></a>
<a id="linux-4-detail-28"></a>
### 7.1 解释器、模块与动态依赖

终端提示显示某个环境名，不保证实际运行了该环境中的解释器。记录`sys.executable`、Python 版本、工作目录和关键模块的实际位置，比只保存环境名称更具体。通过同一解释器调用包管理工具，可以减少安装到另一解释器的风险，但仍需考虑用户目录、环境变量和当前路径中同名模块的遮蔽。一个叫`numpy.py`的本地文件就可能让导入行为偏离预期，不应先认定第三方包损坏。

导入纯 Python 包成功，只说明相应导入路径可用；包含本机扩展的包还涉及动态库、架构、系统运行库和设备驱动。设备框架的构建版本、驱动支持和实际设备能力是不同层次，不能只依据一个“CUDA 版本”标签决定所有兼容性。先保留原错误堆栈，识别缺失模块、找不到共享库、符号不匹配还是设备初始化失败，再查询相应版本官方兼容信息。

最低限度复现应从同一解释器的最小导入开始，随后是固定输入的 CPU 计算、设备计算、单步训练和短任务。每一层通过才能有依据继续扩大范围。若最小导入已经失败，调节批量没有针对性；若只有特定样本失败，重装所有依赖会丢失线索。隔离环境便于比较，但建立新环境成功不自动证明旧环境错误在哪，仍应记录最小差异和修复验证。

<a id="linux-4-detail-29"></a>
### 7.2 路径、权限、配额与工作目录

相对路径根据进程工作目录解析，不根据脚本文件位置自动解析。交互终端能读取配置，作业调度后却找不到，可能只是启动目录不同。应在运行记录中保存解析后的输入和输出路径，并在启动前验证输入清单和输出父目录。权限检查要涉及祖先目录的搜索权限、文件类型、挂载状态与有效用户；“文件存在”不代表本进程可以读写。

预先判断“目录可写”到真正写入之间仍有竞争，最终操作的返回值才是直接证据。短暂文件测试能发现常见配置错误，却不能保证几小时后仍有空间、权限不变或网络始终可用。应把错误处理放在实际写入路径，并记录失败对象和阶段。安全预检减少早期浪费，不能取代运行时检查和最终验收。

环境变量应只记录影响复现的必要键，避免把令牌、密码和完整连接串写入共享日志。复现清单可以保存变量是否设置、非敏感参数或经过脱敏的来源标识。遇到认证失败时核对身份与授权范围，不能把“换一个更大权限的账号能运行”当成充分修复说明。最小可用权限和明确的数据归属有助于维持可解释的运行边界。

## 8. 有组织的排错：保留竞争假设

<a id="linux-4-detail-31"></a>
### 8.1 一次改变一个条件的正确含义

一次改变一个条件是一种局部因果定位策略，适合减少变量混杂，并不是禁止研究因素交互。若缓存策略和工作进程数量共同决定性能，只比较一个设置可能漏掉交互作用。可先用单因素实验找主要范围，再进行小规模受控组合比较；每组保持相同输入、预算与验收规则，随机或交替安排运行次序以减轻缓存和时间漂移的偏差。

必须先建立基线。基线包括代码版本、配置、数据快照、工作量、环境、资源限制、观测窗口和结果校验。没有这些，所谓“快了一倍”可能来自第二次命中缓存或样本变短。性能实验还应重复到能够看见自然波动，报告中位数与离散程度。并非所有小差异都值得追求；如果改善小于运行波动，结论应保留不确定性，而不是挑选最好一次结果。

<a id="linux-4-detail-32"></a>
### 8.2 案例：训练周期性停顿

某作业平时每批约二百毫秒，每隔五百批停顿数秒。第一组解释是数据长度周期变化，第二组解释是检查点保存，第三组解释是共享存储竞争。先对齐批次长度、保存开始结束和数据等待日志，发现停顿与保存阶段完全重合，批次长度稳定。这个观察支持保存路径，但仍未区分序列化、传输同步和磁盘持久化。

接着在受控短运行中分别记录准备状态、序列化、写入和发布耗时，同时保持保存内容和检查点频率。若序列化快、写入慢，重点调查输出文件系统；若准备状态耗时高，可能需要设备同步与数据迁移。减少保存频率会降低停顿次数，但改变恢复成本，应明确最多允许损失多少步骤。异步保存则需要稳定快照和有界队列，不能让后台线程读取正被训练更新的状态而产生不一致文件。

修复后不仅比较训练吞吐，还要故意中断短任务，验证最近检查点能加载、配置匹配、恢复步骤明确。否则可能只是把阻塞保存改成了更快的错误保存。保存耗时与恢复可靠性是一组共同约束，不应在验收中只保留前者。

<a id="linux-4-detail-33"></a>
### 8.3 案例：任务消失而日志没有报错

某训练在第六千步停止，最后日志是正常损失值，终端没有异常堆栈。先记录直接子进程退出状态及调度器事件，确定是被信号终止还是程序自行报错。然后核对对应时间的控制组内存事件、节点事件和取消记录。如果存在作业范围的 OOM 杀进程增量，且内存曲线持续攀升，才有较强证据调查内存增长；若同时节点重启，则须保留另一条解释。

在缩短运行中记录每隔固定步数的作业内存、预测保存数量和缓存条目。发现列表长度与步数一致增长，列表元素保留了训练图，修复为只保存必要的标量或有界样本后，增长趋势消失。这里“减少批量后多跑了一会儿”只是延迟故障，不是根因修复。最终还应验证损失统计和需要保留的结果没有被误删，避免资源问题转化为交付缺失。

<a id="linux-4-detail-34"></a>
### 8.4 案例：主机空闲而作业仍很慢

主机 CPU 总体占用不到两成，单个任务却比预期慢。竞争解释包括线程未并行、作业配额、亲和性、锁等待和串行 I/O。检查线程状态和任务 CPU 时间，发现大量可运行线程、控制组节流计数在异常窗口增长，而允许的 CPU 时间预算只有两个核当量。此时全机空闲与作业受限完全可以同时成立，调整模型算法之前应确认资源分配是否符合申请。

若配额足够而只有一个线程忙，需判断工作是否本来串行，或是否受解释器与底层库的并行策略影响；若线程大多睡眠，转向锁、队列和 I/O。不能用统一的“增加线程数”应对这三种情况。真正有效的结论必须连接线程状态、阶段时间和资源边界，而不是给所有慢任务套相同参数。

## 9. 证据采集设计：从日志到短时剖析

<a id="linux-4-detail-36"></a>
### 9.1 最小结构化事件

一条阶段事件宜包含运行标识、进程或参与者标识、阶段名、运行内序号、墙钟时间、单调间隔、已完成工作量及状态。错误事件还应包含可定位的异常类型和对象标识，避免只写“失败”。批次标识与输入清单连接后，可以从一条慢日志回到具体数据；只有耗时数字却无法定位输入，往往不足以解释长尾。

不要在每条事件里重复整个配置，也不要把大张量直接格式化到日志。配置可通过不可变标识关联，指标按合适周期汇总，关键异常保留上下文。输出缓冲意味着程序内部发生事件与外部看见日志之间有延迟；在阶段边界显式提交重要记录有助于诊断，但每步强制刷盘会增加开销。可见性、持久性和性能需要分别约定，打印成功不保证突然断电后还能找回。

<a id="linux-4-detail-37"></a>
### 9.2 计数器增量与边界变化

许多系统文件给的是启动以来或控制组建立以来的累计计数。速率需要用两个样本之差除以时间差，并确认对象未重启、计数未重置。若第二次值更小，不能直接得到负吞吐，应检查重置、溢出、对象替换或读取范围变化。进程标识会重用，控制组路径也可能被重建；只保存一个数字标识不足以证明两个样本属于同一生命周期。

阶段边界同样重要。把初始化、编译和缓存预热混进一小段平均值，可能错误比较稳态；只挑运行最快部分，又会隐藏真实启动成本。按用户目标报告两套指标：从开始到交付的总耗时，以及明确排除哪些阶段后的稳定吞吐。这样既能评价一次性任务，也能评价长服务，不必为了一个漂亮数字抹去必要工作。

<a id="linux-4-detail-38"></a>
### 9.3 从低开销观察升级到剖析

先确认卡在哪个阶段，再决定需要函数剖析、系统调用跟踪、锁分析还是设备时间线。系统调用跟踪能揭示反复打开不存在路径或大量小写入，但也会改变执行速度；采样剖析能估计热点分布，却可能漏掉短暂稀有路径。任何工具都应注明采样方式、持续时间、权限和扰动，不把剖析期间的绝对吞吐直接当作正常运行性能。

共享机器上尤其要限定进程范围与持续时间，避免采集无关用户数据。已经有足够证据支持下一步实验时，应停止扩大观测范围。分析报告的价值来自解释“哪一项观察排除了哪一种解释”，不是附上最多工具截图。能够被其他人按相同步骤复核的微型证据，通常比一张没有时间与对象信息的综合大屏更有用。

## 10. 长任务交付：完成必须可以被验证

<a id="linux-4-detail-40"></a>
### 10.1 运行身份、检查点与最终产物

最小运行清单应关联代码版本、配置、数据快照、环境、启动命令、资源申请和产物契约。进程标识用于临时观测，不能作为永久运行身份，因为进程结束后编号可复用。随机生成或由任务系统分配的运行标识更适合关联日志和产物；如果同一配置重复运行，也要区分每次尝试，避免新日志覆盖旧失败记录。

检查点是恢复状态，最终产物是交付结果，二者的验收不完全相同。训练恢复可能需要模型、优化器、调度器、随机状态、数据位置和梯度累积边界；只保存权重通常足以某些推理用途，却不保证按原训练轨迹恢复。数据位置也不能仅用“第几批”描述，若数据顺序、采样种子或分片方式改变，同一批号可能对应另一批记录。

完成协议至少验证正常退出、最终记录存在、结构可解析、数量与范围正确、配置和输入标识匹配，以及必要的重新加载。正常退出只是其中一个条件：程序可能吞掉异常后返回零，也可能在失败后留下旧文件。另一方面，任务被取消前已经安全发布的阶段产物可以仍然有效，不应把进程最终非零退出机械地解释成所有历史结果都损坏。

<a id="linux-4-detail-41"></a>
### 10.2 原子可见性与崩溃持久性

先写临时文件、完整校验、再替换正式路径，可以在适用文件系统语义下避免读者看到半写文件。临时文件与正式目标应位于允许原子替换的同一文件系统，跨文件系统移动通常不具备相同保证。写入完成并不等于断电后持久存在；文件内容同步与目录项同步分别处理不同层次，底层存储和挂载语义还影响最终承诺。不能把一个重命名调用概括为任何环境下都绝对不丢数据。

若产物包含多个文件，分别替换模型和清单会出现新模型配旧清单的中间状态。可将不可变文件放入一个带版本的发布单元，完整验证后只切换一个入口，并让读者固定该版本；也可以把足够小的状态封装为单文件。多写者需要额外的独占或版本比较协议，否则每个写者内部都原子发布，仍可能互相覆盖。原子操作解决单次可见性，不自动解决所有并发正确性。

恢复时检查点应先被验证，再决定从哪里继续。文件名里带有“完成”二字没有证明力；文件存在也不能证明来自本次配置。校验和可以检测传输或内容变化，但不能证明算法结果正确，且非可信写者可以同时修改数据与校验和。契约中应明确防范的是误截断、误配版本、意外重复，还是更强的对抗修改，避免把一种校验夸大成所有保证。

<a id="linux-4-detail-42"></a>
### 10.3 自包含实验：失败不应覆盖已发布结果

下面实验把配置标识、数据和内容摘要封装到一个 JSON 文件。先发布有效结果，再在新临时文件校验完成之后、替换之前注入异常，验证旧结果仍可加载。最后成功替换并读回新版本，且临时目录自动清理。它实测的是应用异常下的发布协议，不模拟机器断电，也没有证明某个远端文件系统的持久化语义。

```python
import hashlib
import json
import os
from pathlib import Path
from tempfile import TemporaryDirectory

def encode_payload(payload):
    return json.dumps(payload, sort_keys=True,
                      separators=(",", ":")).encode("utf-8")

def load_valid(path):
    envelope = json.loads(path.read_text(encoding="utf-8"))
    payload = envelope["payload"]
    actual = hashlib.sha256(encode_payload(payload)).hexdigest()
    assert actual == envelope["sha256"]
    assert payload["config"] == "square-v1"
    assert all(row["y"] == row["x"] ** 2 for row in payload["rows"])
    return payload

def publish(target, rows, fail_before_replace=False):
    temporary = target.with_name(target.name + ".pending")
    assert not temporary.exists()
    payload = {"config": "square-v1", "rows": rows}
    envelope = {"payload": payload,
                "sha256": hashlib.sha256(encode_payload(payload)).hexdigest()}
    try:
        with temporary.open("x", encoding="utf-8") as stream:
            json.dump(envelope, stream, sort_keys=True)
            stream.flush()
            os.fsync(stream.fileno())
        assert load_valid(temporary) == payload
        if fail_before_replace:
            raise RuntimeError("injected before publication")
        os.replace(temporary, target)
        directory_fd = os.open(target.parent, os.O_RDONLY | os.O_DIRECTORY)
        try:
            os.fsync(directory_fd)
        finally:
            os.close(directory_fd)
    finally:
        temporary.unlink(missing_ok=True)

with TemporaryDirectory(prefix="learning-publish-") as directory:
    target = Path(directory) / "result.json"
    old = [{"x": 1, "y": 1}]
    new = [{"x": 1, "y": 1}, {"x": 2, "y": 4}]
    publish(target, old)
    try:
        publish(target, new, fail_before_replace=True)
    except RuntimeError:
        pass
    else:
        raise AssertionError("failure injection did not run")
    assert load_valid(target)["rows"] == old
    assert not target.with_name("result.json.pending").exists()
    publish(target, new)
    assert load_valid(target)["rows"] == new
    assert sorted(p.name for p in target.parent.iterdir()) == ["result.json"]
    print("publication checks passed: old survives failure, new validates")
assert not Path(directory).exists()
```

此实现假定单写者，固定临时名便于观察，不能直接供并发作业共享。它没有把“替换已成功但目录同步失败”伪装成全部回滚：若该阶段抛错，正式路径可能已经指向新内容，调用方应读回并依据运行身份判断状态。实际恢复设计需要明确这个不确定窗口。最终清理只删除本次约定的临时路径；不使用通配符扫描目录，也不把未知文件自动视为可删除垃圾。

<a id="linux-4-detail-43"></a>
### 10.4 重跑、幂等与外部副作用

可重跑不等于可以重复执行任何副作用。读取同一不可变输入并生成版本化结果通常容易设计；发送通知、追加远程记录或扣减额度则需要对方支持幂等键或事务机制。若进程在外部写成功后、记录本地进度前崩溃，重试可能重复写；若先记录进度再写外部，崩溃又可能漏写。单机文件替换不能解决两个独立系统之间的原子提交问题。

对数据处理可定义稳定记录标识、处理版本和明确的输出主键，使重试写入能够检查或覆盖同一逻辑结果，再把输出与进度放在能够原子更新的范围。若无法做到，应承认至少一次或至多一次的具体语义，设计去重与对账。不要只在日志里写“完成一批”就宣布准确一次，日志缓冲和崩溃窗口都可能让它与实际外部状态不一致。

<a id="linux-4-detail-44"></a>
## 11. 研究式验证：让诊断结论可复核

<a id="linux-4-detail-45"></a>
### 11.1 构建最小故障矩阵

可以按输入异常、资源边界、进程中断、输出损坏和环境漂移建立测试矩阵。每一行写出触发方式、预期可观察信号、应该保持的旧状态和恢复入口。例如坏输入应产生具体记录标识而非悄悄跳过；保存前中断应留下上一版可加载结果；清单配置不匹配应拒绝复用。测试规模保持很小，目标是验证协议而非制造真实系统事故。

资源极限测试应优先使用受限的微型模型或模拟错误返回，不通过填满共享磁盘、耗尽内存或杀死未知进程获得“真实感”。对真实 Linux 机制的验证可以像本章那样限制为短时计算、小临时文件和自身进程对象。对无法安全复现的硬件和集群条件，记录需要管理员或专用环境验证的假设，既保留研究问题，也不编造已获得的证据。

<a id="linux-4-detail-46"></a>
### 11.2 比较方案时保留正确性不变量

优化数据读取应保持记录集合、标签、必要顺序和快照一致；改变并发时检查重复与遗漏；改变精度时检查数值误差和收敛；改变保存协议时检查可加载性与恢复点。相同吞吐目标必须附带这些不变量，否则“优化”可能只是减少了实际工作。比较表应把输入条件、资源预算、完成时间、峰值内存、尾延迟和验收结果放在一起，让取舍能够被审阅。

一次性能改进未必是永久最优。数据规模变大、存储延迟变化、模型计算增加后，瓶颈可能迁移。可复核的报告应该说清适用范围和下一种可能瓶颈，例如加载优化后设备计算成为主耗时，而不是宣称从此解决所有性能问题。好的诊断知识能够指导下一次观察，而不仅记录某次碰巧有效的参数。

## 12. 进阶练习与逐步解析

<a id="linux-4-detail-48"></a>
### 12.1 十秒墙钟只累计一秒 CPU，能否认定磁盘慢

**题目：** 一个单线程任务运行十秒，CPU 时间约一秒，其余是否必定是磁盘等待？

**解析：** 先由两种时钟的定义得出大量时间没有在本线程执行处理器指令，但等待来源尚未确定。它可能睡眠、等锁、等网络、等子进程，或受调度与配额限制。应按业务阶段查看阻塞对象，并比较控制组节流、线程状态和 I/O 证据。如果 CPU 时间只统计主进程，子进程计算还可能被漏算。验收答案应明确“支持存在等待”与“证明等待磁盘”之间缺少哪项区分观察。

<a id="linux-4-detail-49"></a>
### 12.2 主机有三十二核而作业只能用两核

**题目：** 主机 CPU 利用率很低，是否可直接增加数据加载工作进程到三十二个？

**解析：** 先核对作业允许的 CPU、配额和祖先限制。若持续预算仅两个核，增加工作进程可能加剧调度与内存争用，并不能获得三十二核持续计算。再分别测量加载与计算阶段，确认加载是否真是瓶颈。可在相同输入下比较少量并发设置，保留吞吐、尾延迟与峰值内存。合格结论应说明全机剩余能力不等于本作业授权和实际可用能力。

<a id="linux-4-detail-50"></a>
### 12.3 虚拟内存巨大是否表示即将 OOM

**题目：** 一个进程虚拟地址空间两百吉字节、驻留集两吉字节，是否应立即终止？

**解析：** 地址空间规模不等于物理占用，可能来自映射和保留区域。应检查驻留组成、增长趋势、工作集、控制组当前占用与有效限制，判断是否存在真实压力。还应考虑其他成员占用以及未来触碰保留地址的行为。单个数字不足以作出资源耗尽结论。若只看驻留集也不够，因为短峰值可能被漏采样，答案需给出时间范围与限制范围。

<a id="linux-4-detail-51"></a>
### 12.4 多进程驻留集相加为何高于主机使用量

**题目：** 多个工作进程共享大文件映射，直接相加驻留集是否准确？

**解析：** 同一物理页可能在多个进程驻留集中分别出现，相加发生重复计数。可结合比例分摊统计、私有页、共享页和作业级内存观察，但这些接口的计数范围也要说明。反过来，忽略工作进程只看主进程会漏掉私有解码缓冲。验收不要求所有工具数字恰好相等，而要求能解释共享、缓存、采样时刻和层级差异。

<a id="linux-4-detail-52"></a>
### 12.5 交换使用量不为零是否说明正在抖动

**题目：** 交换区有历史占用，但训练吞吐稳定，是否必须先停任务？

**解析：** 历史换出的页面可能暂时没有再次访问，静态占用不能证明当前持续交换。应观察异常窗口内换入换出增量、内存压力和业务延迟是否对应，再判断工作集是否超过有效预算。若存在持续高交换与停顿，可减少预取或修正增长；若无明显活动，则应继续保留观测，避免把历史状态误判为正在发生的瓶颈。

<a id="linux-4-detail-53"></a>
### 12.6 退出码一百三十七是否足以证明 OOM

**题目：** 作业没有堆栈，只留下状态一百三十七，应怎样报告？

**解析：** 在常见 Shell 编码中它可能对应信号九，但主动退出、包装器和管道也能产生相同数字。先说明观测来自哪个层次，核对调度器、节点和作业范围的 OOM 事件。只有时间与范围对齐的证据才支持 OOM 判断。若无权限访问关键记录，应写“疑似被强制终止，原因待核实”，并保留最后进度、内存峰值与运行身份，而非确定地归因模型太大。

<a id="linux-4-detail-54"></a>
### 12.7 目录占用不大而文件系统已满

**题目：** `du`看不到大文件，`df`却显示满了，是否工具错误？

**解析：** 先确认同一挂载点和权限范围，再调查已删除但仍打开的文件、挂载覆盖、快照、保留空间与配额。目录遍历与文件系统统计观察对象不同，差异可能有机制解释。对已删除日志应定位持有描述符的写入进程，按其正常重新打开或退出协议处理。不能为了让数字下降，盲目删除其他作业文件。微型实验中解除路径后仍可读回内容就是直接反例。

<a id="linux-4-detail-55"></a>
### 12.8 小文件读写为何低吞吐也很慢

**题目：** 每秒只读几兆字节，是否证明存储不是瓶颈？

**解析：** 若每条记录要串行打开许多小文件，时间可能消耗在元数据操作和往返延迟，而不是传输字节。统计文件打开次数、请求大小、端到端等待和缓存条件，再用保持同一记录集合的分片格式做区分比较。若改成预解码内存输入才变快，则解码也可能是共同因素。答案需提出能够区分字节吞吐、操作频率与 CPU 解码的实验，而不是只重复“磁盘慢”。

<a id="linux-4-detail-56"></a>
### 12.9 GPU 利用率提高而吞吐下降

**题目：** 增加额外计算后 GPU 更忙，却更晚完成任务，是否优化成功？

**解析：** 目标是相同工作和正确性条件下的完成效率，利用率只是中间观察。额外计算提高活动比例同时增加总成本，不能称为性能改进。应比较端到端吞吐、延迟、结果校验和资源预算，并核对批次长度及预热条件。若真正瓶颈是加载，改模型可能只掩盖空闲；应使用固定输入重放区分输入饥饿和设备计算限制。

<a id="linux-4-detail-57"></a>
### 12.10 缩小批量后不再报错是否说明完成修复

**题目：** 原任务六千步消失，批量减半后运行到一万步，能否结束排查？

**解析：** 这只能说明新配置在当前预算内运行更久。若保留历史张量造成无界增长，较小批量可能只是延迟失败。观察内存相对步数的增长斜率、缓存条目和对象保留，再验证固定项与批量相关项。还要检查梯度归一化、优化器步频与结果质量是否符合目标。最终通过标准应覆盖完整计划工作量和产物验证，而不是比旧运行多撑一段时间。

<a id="sec-7-2"></a>
<a id="linux-4-detail-58"></a>
### 12.11 同时升级依赖后成功能否证明根因

**题目：** 重装多个包、改数据目录并降低批量后任务成功，修复记录应怎样写？

**解析：** 应如实记为新组合通过验证，不能把其中某项指定为已证实根因。若需要定位，应保留原最小失败，在隔离环境逐项比较解释器、模块位置与动态依赖。多因素交互可设计受控组合，但必须记录每项变化和同一验收标准。若原环境已无法恢复，也应标注证据限制，避免后来者以为某个升级具有经过验证的必要性。

<a id="linux-4-detail-59"></a>
### 12.12 检查点停顿应该直接异步化吗

**题目：** 保存阶段占用大量时间，是否启动一个后台线程就能安全解决？

**解析：** 后台保存需要一致状态快照、有界队列、错误传播和退出等待。如果训练同时修改参数，保存可能读到不同步骤混合状态；如果后台速度长期低于生产速度，队列会无界增长。先分解准备、序列化和写入成本，再选择降低频率、改存储或异步协议。验收必须加载检查点并模拟中断，不能只以主线程不再阻塞作为成功标准。

<a id="linux-4-detail-60"></a>
### 12.13 单调时钟能否合并跨机器事件

**题目：** 两台机器的单调时钟数值谁大，是否就代表事件发生更晚？

**解析：** 不同机器的单调时钟没有统一起点，直接比较绝对值通常无意义。它适合各自运行内计算持续时间。跨机事件需要带时区的墙钟、同步误差说明和请求或阶段关系；即便墙钟有校时，也不应忽略偏差推断严格先后。答案应分别说明持续时间测量与跨机事件排序的需求，并指出共享运行标识提供关联而非消除时间误差。

<a id="linux-4-detail-61"></a>
### 12.14 两次性能结果应如何公平比较

**题目：** 第一次冷启动十分钟，第二次热缓存五分钟，能否宣布新代码两倍加速？

**解析：** 当前比较混合了代码变化与缓存状态。应明确用户关心冷启动还是稳态，固定输入与资源，交替或随机安排多个重复运行，报告启动成本、稳态吞吐和自然波动。不要在共享机器上擅自清空全机缓存。若无法控制缓存，只能把它列为限制；结果校验还应确认样本数和内容不变，避免实际工作减少造成虚假加速。

## 13. 综合研究练习：设计可交付的故障报告

<a id="sec-7-1"></a>
<a id="linux-4-detail-63"></a>
### 13.1 输出文件存在，失败重跑能否跳过

**题目：** 数据处理进程失败，但正式路径已有文件。请设计判断与恢复流程。

**解析：** 先确认文件对应的运行、配置和输入快照，再验证结构、记录数量、标识范围、内容摘要及必要业务约束。若只是临时半成品，不作为完成依据；若旧版本已完整发布，则保留其身份，不冒充本次结果。恢复从经过验证的检查点开始，外部写入使用稳定主键或幂等键处理重试。最后检查退出状态、正式入口和可加载结果三者是否一致。故障注入应至少覆盖发布前失败、发布后确认前失败，以及检查点配置不匹配，分别说明可能留下的状态。

**验收：** 小规模运行首先发布旧结果，再注入一次发布前异常，确认旧结果仍可读且临时文件可识别；随后成功重跑得到完整新结果。对发布后确认前的情况，允许调用方不确定，但读回时必须能识别具体版本。不能要求所有异常都表现成“什么也没发生”，因为真正的提交动作可能已经完成。

<a id="linux-4-detail-64"></a>
### 13.2 为一次慢任务构造竞争假设矩阵

**题目：** 某训练吞吐下降、GPU 空闲、主机内存增长，请给出至少三种解释和区分证据。

**解析：** 解释一是加载器预取过多，引起内存压力和读取停顿，可比较作业级内存、压力、加载等待与预取设置；解释二是保存历史计算图，内存随训练步数无界增长，可检查对象数量和简化统计保存；解释三是样本长度增加，同时推高解码、填充和激活成本，可对齐长度分布与阶段时间；解释四是共享存储拥塞，内存增长可能只是积压结果，应核对写入队列和其他任务的异常时间。多个解释可以共存，不能要求一条曲线唯一决定答案。

**验收：** 选择最能区分当前候选的微型实验，固定数据与模型，只修改一个针对性条件；记录观察、排除与尚未排除的解释。修复后同时验证完整工作量、吞吐、峰值资源和产物正确性，再给出适用范围。报告应让另一位学习者知道下一步怎样复核，而不是只留下“增加工作进程后好了”。
