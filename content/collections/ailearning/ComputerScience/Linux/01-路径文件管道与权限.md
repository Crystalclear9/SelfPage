# 第 1 章 路径文件管道与权限

[主题目录](README.md) · [分类目录](../README.md) · [总目录](../../README.md) · [下一章](02-进程日志远程与环境管理.md)

本章把“会敲命令”推进到“能解释命令为什么这样执行”。研究任务常见的路径错误、日志混乱、文件丢失、共享权限失效，并不需要更复杂的框架才能解释；它们通常来自名称、对象、参数、字节流和权限检查这几层的混淆。读完以后，你应能逐层回答：程序到底收到了几个参数，内核从哪个目录开始查找，文件描述符指向哪个打开对象，权限在哪里被拒绝，以及一次重命名究竟保证了什么。

本章的 Linux 实验在既有 WSL Ubuntu 22.04.5 LTS 中核验，使用 Bash 5.1.16 与 Python 3.10.12；WSL 的 Linux 内核并不等于 Windows PowerShell。涉及 inode、符号链接、权限位的实验使用 Linux 临时目录，避免把 Windows 挂载目录的权限映射误当成本地 Linux 文件系统语义。所有示例只创建并清理自己的临时目录；高级权限、网络文件系统和断电持久性另行说明适用范围。

## 1. 路径首先是一场查找

<a id="sec-1-1"></a>
<a id="linux-1-detail-2"></a>
### 1.1 工作目录决定相对路径的起点

路径不是文件本身，而是让内核找到对象的一串查找指令。绝对路径从调用进程所见的根目录开始；相对路径一般从该进程的当前工作目录开始。进程启动时通常继承父进程的工作目录，之后可以独立改变。因此，同一个程序、同一个配置字符串，在不同目录启动，可能读取完全不同的数据。这不是程序“不稳定”，而是它的输入里隐含了工作目录。

假设项目有原始数据目录、训练目录和评估目录，配置写着相对路径“数据集”。从项目根启动时，它指向根目录下的数据集；进入训练目录再启动时，它转而指向训练目录中的同名条目。解释器能够找到脚本，不意味着脚本中的相对路径会自动相对于脚本位置。脚本位置、工作目录、配置文件位置，是三个需要明确选择的基准，任何一个都不能靠习惯猜测。

稳健的设计先规定路径契约：命令行传入的相对路径相对调用目录解释，配置文件中的相对路径相对配置文件所在目录解释，程序内置资源相对安装包定位。契约也可以采用另一套规则，但应在入口统一转换，并在运行清单中记录实际采用的绝对路径。这样迁移目录时只需调整入口，而不是让每个函数自行寻找一个“看起来正确”的目录。

环境变量中的项目根目录不是万能答案。如果变量缺失，程序应该给出明确诊断；如果变量指向旧副本，绝对路径仍然会稳定地读错数据。进一步记录数据标识、版本和摘要，才能验证“找到了某个文件”与“找到了预期文件”两件不同的事情。绝对路径提高定位的明确性，内容标识提高对象身份的明确性。

<a id="linux-1-detail-3"></a>
### 1.2 名称、目录项和 inode 分别承担什么

普通目录可以理解为名称到文件对象标识的映射；具体实现和缓存策略由文件系统决定。inode 保存某个文件系统内对象的元数据，包括类型、权限、所有者、大小和数据定位等信息。目录项中的名字不属于普通文件内容，也不是 inode 的唯一名字。文件对象可以有多个目录项指向它，这正是硬链接能够存在的原因。

因此“修改文件名”与“修改文件内容”沿着不同的路径发生。重命名主要改变目录中的名称关联；通过一个名字打开文件并写入内容，改变的则是同一个对象的数据。两个硬链接名称看起来像两份文件，但它们共享对象。反过来，复制出来的两个文件即使字节完全相同，也通常是两个独立对象，修改其中一个不会自动改变另一个。

设备标识和 inode 编号应一起用于同一观察时刻的身份比较。inode 编号只在所属文件系统中有意义，删除后还可能被重新使用。仅把一个编号写进永久实验清单，不能作为永不冲突的全局对象身份。需要长期识别内容时，可以使用内容摘要并保留数据版本；需要跟踪正在使用的对象时，应保留已打开的描述符，而不是不断重新解析一个名字。

目录名也参与查找。路径的中间分量必须能够继续作为目录访问；一个普通文件即使名字像目录，也不能在其后继续拼接子路径。错误“没有这个文件”可能来自任何中间分量，不一定只说明最后的名字不存在。遇到路径错误，逐级检查目录和类型，比反复改最后一个文件名更有效。

<a id="linux-1-detail-4"></a>
### 1.3 软链接、硬链接与相对目标

硬链接增加另一个指向同一对象的目录项，通常不能跨文件系统创建，普通用户也不能随意对目录创建硬链接。它不保存“原文件路径”，所以删除其中一个名称，并不会让另一个名称失效。对共享对象进行原地写入，两边都会看到新内容；若先生成新对象再替换其中一个名字，另一个名字仍然指向旧对象，这个区别对检查点轮换非常重要。

符号链接自身是一个独立对象，其内容是一个目标路径字符串。访问时通常继续解析目标，某些接口则专门操作链接本身。相对符号链接的目标以链接所在目录为基准解释，通常不是以访问进程的工作目录解释。因此把整个目录树一起搬走时，相对链接可能保持有效；把链接单独搬走时，它也可能指向另一个地方或者失效。

软链接允许目标暂时不存在，这叫悬空链接。检查“名称是否存在”与检查“解析后的目标是否存在”会得到不同答案。对一个悬空链接，检查链接自身的接口仍然能取得元数据，而跟随链接的打开操作失败。故障排查要明确正在询问哪一层；如果安装脚本把悬空链接误判为“这里什么也没有”，可能覆盖本来需要保留的配置关系。

软链接还会改变路径中的父目录直觉。在含链接的路径上，“先把字符串中的上一级抵消掉”与“让内核逐级解析”可能走到不同对象。纯词法归一化只处理字符串，物理解析会访问文件系统并跟随链接。两者都能有合理用途，但验证一个文件是否位于授权目录内时，不能只依赖简单字符串前缀或机械删除上一级分量。

<a id="linux-1-detail-5"></a>
### 1.4 打开之后删除：名称消失为什么仍能读

打开文件后，进程得到文件描述符，它引用一个内核维护的打开状态。删除普通文件名称，实质上是解除目录项关联；已经打开的对象仍可能继续被读取和写入。直到有关名称关联与打开引用等条件都满足释放要求，文件系统才可以回收相应存储。因此“目录里看不见了”并不等于“所有进程都不再使用”。

日志轮转能直接体现这一点。若把当前日志改名，再新建同名日志，原进程已经打开的描述符仍然可能写向改名后的旧对象。管理员只查看新名字会误以为程序停止输出。正确的轮转协议必须让应用重新打开日志，或者采用应用支持的轮转机制；截断原文件虽然保留对象，却存在与并发写入配合不当而丢记录的风险。

同样，删除一个被大进程打开的大文件，有时不会立刻释放你期待的磁盘空间。先判断哪个进程持有引用，再选择合适的关闭或重开流程，才能解释空间变化。不能由“删除命令成功”直接推导“空间一定马上回来了”，也不能为了腾空间随意结束不属于本实验的任务。

## 2. Shell 把文字变成参数

<a id="sec-4"></a>
<a id="linux-1-detail-7"></a>
### 2.1 先区分命令文本和参数数组

Shell 读取的是具有语法的命令文本；外部程序通常接收的是已经解析好的参数数组。空格、引号、通配符、重定向符号首先由 Shell 解释，外部程序不一定见得到它们。学习命令最有价值的练习之一，是用一个打印参数的程序替代真正操作数据的程序，观察每个参数的边界，而不是仅凭终端显示猜测。

变量赋值为“实验 一”，未引用地展开时，在默认设置下可能经历字段拆分，变成两个参数。双引号围住变量展开，则保留一个参数，其中的空格只是数据。若变量内容含星号，未引用展开还可能匹配当前目录的多个文件。后果不是“字符串稍微不一样”，而是程序的输入个数、输入顺序乃至选项解释都可能改变。

单引号通常保留内部字符的字面意义；双引号允许参数展开、命令替换等操作，同时抑制常见的字段拆分和路径名展开。引号是 Shell 语法，完成分词后通常会被移除，不是自动作为字符传入程序。要在数据中传入一个真正的引号，需要让 Shell 产生那个字符，而不是认为终端上看到引号就一定存在于参数里。

最直接的工程规则是：把路径当作一个参数传递时，引用变量；需要多个参数时，使用 Bash 数组并引用数组展开。不要先把一组参数拼成字符串，再希望 Shell 恰好按原意拆回去，因为一旦字符串中含空参数、空格或特殊字符，原始边界信息就已经丢失。数组表达结构，字符串表达一个值，两者并不等价。

<a id="linux-1-detail-8"></a>
### 2.2 展开顺序及其可观测后果

理解 Bash 展开，不必死背所有细节，但必须区分源代码结构与运行时数据。花括号展开发生得较早，变量的值不一定会重新触发你以为的花括号语法。算术展开用于整数表达式，命令替换用于获取另一个命令的输出，路径名展开用于匹配目录中的名称。把这些操作混成“Shell 会自动替我处理”，就很难解释空格和星号为什么产生不同后果。

命令替换会删除末尾的换行，这意味着它不是任意字节数据的无损容器。Shell 变量也不能可靠保存包含零字节的任意二进制内容。处理模型权重、压缩档案和数据块时，应通过文件或管道传递字节，而不是把所有内容塞进变量。即使一段文本肉眼看起来一样，末尾换行是否保留也可能影响摘要、协议和测试。

路径名匹配不是正则表达式。星号与问号的含义由 Shell 的匹配规则决定；隐藏名称是否匹配、无匹配时保留字面模式还是变成空结果，也受 Shell 选项影响。脚本应明确需要的行为，例如在独立子 Shell 中启用相应选项，或者把查找交给具有明确筛选条件的工具。运行环境改变选项后，不能假设同一模式永远产生同一组参数。

通配符匹配到多少文件，还受命令行总长度限制影响。一个在几十个文件上正常的命令，未必能直接用于几十万个文件。此时应使用流式遍历、分批调用或者程序内部读取清单。需要稳定实验顺序时，还应说明排序规则；文件系统枚举顺序不是你设计的样本顺序，字符排序又可能受到区域设置影响。

<a id="linux-1-detail-9"></a>
### 2.3 参数边界不是安全性之外的附加问题

路径以减号开头时，某些工具会把它当作选项。引用只保证它是一个参数，不会自动阻止选项解释。支持双减号选项终止符的工具，可以在位置参数前使用它；也可以在合适的相对路径前加当前目录分量。这个细节与引用解决的是两个不同问题，不能互相替代。

绝不要把不可信的数据拼接进待执行的 Shell 文本，再调用重新解释的机制。比如用户输入本来只应成为一个数据集路径，经过文本拼接后，其中的分号和命令替换可能变成执行语法。使用直接参数数组调用程序，可以让这些字符保持数据身份。确实需要 Shell 功能时，也应把不可信值作为位置参数传入固定的脚本文本，而不是拼进脚本文本内部。

这里的主要目标仍然是可解释性：你能指出哪些字符被当作语法，哪些字符只是值。如果所有输入都来自自己，错误引用仍然会造成错读数据、漏处理文件和覆盖结果；它并不是只有面向陌生用户的服务才需要考虑的议题。路径中有空格、中文和换行，是合法性问题而不是使用者“命名不规范”的证据。

## 3. 描述符、重定向与管道

<a id="linux-1-detail-11"></a>
### 3.1 三个标准流分别表达什么

一个进程通常约定描述符零为标准输入、一为标准输出、二为标准错误。它们是三个接口位置，不等于三个固定的终端窗口。父进程可以把它们连接到终端、普通文件、管道或者其他对象。程序把预测结果写到标准输出，把诊断信息写到标准错误，就能让下游解析结果而不被进度条污染；但这种划分是程序遵守的约定，不是内核理解内容后自动分配。

退出状态另有一条传递渠道。空的标准错误不能证明成功；某些程序失败时只返回非零状态。大量标准错误也不能证明失败；进度提示和告警可能都出现在那里。判断一次运行，需要同时看退出状态、预期产物、内容验证与必要的诊断证据，而不是把任何一个信号当作全部事实。

多个进程写进同一文件时，日志顺序也不等于真实因果顺序。用户态缓冲、线程调度和不同描述符会让输出晚到。给记录加入任务标识、阶段标识、时间与序号，能帮助重建过程；但不同机器的墙上时钟仍有偏移，不能直接把极接近的时间戳当作严格全序。跨进程记录需要额外的关联关系。

<a id="linux-1-detail-12"></a>
### 3.2 重定向从左到右改变连接

重定向的顺序决定文件描述符最终指向哪里。先把标准输出指向文件，再把标准错误复制为当前标准输出，两个流会进入同一目的地。先复制标准错误，再改变标准输出，则标准错误可能仍留在原来的终端。这种“复制”描述的是当时的引用关系，不是建立一个以后永远自动跟随另一个编号的变量关系。

大于号打开文件时通常会截断已有内容，追加重定向则通常以追加方式打开。即使即将执行的程序因为参数错误马上退出，Shell 也可能已经完成了打开和截断。因此不能用“程序应该还没开始”来推断原结果没被影响。重要结果宜写入新的运行目录或临时产物，验证通过后再发布。

一个尤其容易踩到的例子，是让读取某文件的命令把输出重定向回同一个文件。Shell 先截断目的地，读取程序再打开它时已经没有原内容。这里不需要并发，也不需要系统崩溃，单靠执行顺序就能造成数据丢失。使用临时文件后重命名，或者使用支持原地修改且语义明确的工具，才能避免这种结构性问题。

<a id="linux-1-detail-13"></a>
### 3.3 管道是有容量的字节通道

管道把一个进程的输出连接到另一个进程的输入。它传输字节，不会自动识别“每行一个样本”，也不会把一次写入永久保存成一条应用消息。读取端一次读取可能得到半条记录，也可能得到几条记录；应用层必须用换行、长度前缀或正式格式定义记录边界。处理文本时，行缓冲只是常见约定，不是管道内置的表格结构。

管道容量有限，生产者比消费者快时，写入可能阻塞。这叫背压，它使内存使用受控，但也可能揭示死锁：父进程等待子进程结束，却一直不读取子进程填满的标准输出，双方都无法前进。同时捕获标准输出和标准错误时，也不能只读一个流而永久忽略另一个；子进程可能恰好把另一个管道写满。

读取端提前退出后，继续写入的一方可能遇到断开的管道，体现为相关错误或信号。某些只取前几行的流水线故意提前结束，这时生产者异常状态可能只是协议结果。另一方面，若管道中间的转换失败，而最后一个命令照常退出，默认流水线状态未必能表达整个流程失败。第三章将通过失败策略讨论如何明确这种边界。

<a id="deep-dive-2"></a>
<a id="linux-1-detail-14"></a>
### 3.4 文件描述符共享的是哪一层状态

复制描述符常常让它们引用同一个打开文件描述，从而共享文件偏移等状态。两个独立打开操作则通常有各自的偏移。这个差别解释了为什么复制后的两个句柄交替读取，会像共同推进一个游标；而分别打开同一路径，可以各自从头读取。名称相同，不足以推断打开状态相同。

子进程继承哪些描述符，也影响管道何时出现文件结束。只要还有写端引用没有关闭，读取端就可能一直等待。即使“负责生产数据的那个子进程”已经退出，另一个意外继承写端的进程仍可能让读取方等不到结束标记。排查流水线挂住时，要查整个描述符生命周期，而不只看核心计算进程的存活状态。

这也给程序设计一个原则：谁创建资源，谁说明所有权和关闭时机；把句柄传给别的组件时，说明是借用还是转移。垃圾回收有时能最终释放对象，但它不应成为控制管道结束时刻的唯一机制。使用上下文管理器和明确的关闭动作，能把资源生命周期变成可审查的程序结构。

## 4. 权限约束的是具体操作

<a id="linux-1-detail-16"></a>
### 4.1 文件与目录的同一个字母含义不同

普通文件的读权限允许读取内容，写权限允许修改内容，执行权限参与把文件作为程序执行的检查。目录的读权限允许枚举名称，写权限参与增加、删除和重命名目录项，执行权限通常表示搜索或穿越目录的能力。因此“能够列出名字”“能够通过已知名字打开对象”“能够修改对象内容”，可以是三个不同答案。

例如，一个目录只有搜索权限而没有读取权限，使用者可能无法列出里面的名字，却仍能在知道完整文件名、且文件权限允许的情况下访问该文件。反过来，一个能列出名字但没有搜索权限的目录，也未必允许继续打开其中对象。不要用能否列目录作为唯一访问测试，应按真正需要的操作进行最小验证。

删除文件主要涉及父目录中名称关联的改变，而不是修改该文件的数据内容。文件本身只读，并不必然阻止有权修改父目录的人删除其名字。共享目录还可能设置粘滞位，进一步限制谁能删除或重命名条目。理解这一点，就不会用“把结果文件设为只读”来代替完整的目录保护策略。

路径中每一级目录都可能需要搜索权限。最终文件权限看起来正确，但上层目录不允许穿越，仍然无法访问。诊断时应按路径分量逐层检查，而不是只对最后一个文件反复执行修改权限。跨容器、挂载和远程文件系统时，还应把实际执行身份、映射规则和访问控制层一起纳入证据。

<a id="linux-1-detail-17"></a>
### 4.2 所有者、组与其他用户怎样选择

传统权限把使用者分成所有者、文件所属组以及其他用户三类。检查不是把所有适用类别的允许位随意相加；一个以所有者身份匹配的进程，不能因为所有者权限较少就自动改用“其他用户”中更宽松的位。组匹配还要考虑进程的附加组，不能只看当前默认组名。

权限检查依据的是进程实际使用的身份与凭据，而不是人类觉得“我登录的是谁”。通过不同启动器、服务管理器或容器运行后，进程可能拥有不同的用户、组和能力。终端上手工读取成功，不足以证明同一程序在服务环境中也能读取。复现故障时，要在相同身份、相同挂载和相同目录上下文里验证。

文件访问控制列表会扩展传统三类权限，能力机制、强制访问控制和挂载选项还可能施加额外限制。于是九位权限字符串正确，不一定意味着操作必然成功。遇到拒绝时，先记录实际错误与适用控制层，再查相应机制；不要从第一眼看到的传统权限位就宣布“系统有问题”。

本章的基础实验不创建额外用户，不修改系统访问策略，也不尝试绕过限制。如果实验身份具有管理能力，单纯去掉文件读位后仍然读到内容，并不能否定权限机制；那说明你的测试主体不满足“普通无特权进程”的前提。权限实验必须报告主体条件，不能只展示一个成功或失败的终端截图。

<a id="linux-1-detail-18"></a>
### 4.3 umask 的位运算及其边界

创建文件时，程序请求一个权限模式，系统再按创建规则处理。传统情况下，没有目录默认访问控制列表参与时，可以用“请求模式与掩码取反后逐位相与”理解初始权限。它不是十进制减法，也不会凭空增加程序没有请求的权限。普通文件常请求不含执行位的模式，因此把掩码设得很宽松，也不会自动变成可执行文件。

举例说，程序请求所有人可读写的普通文件模式，掩码禁止组和其他人的写位，得到所有者可读写、其他可读的结果。若程序请求只有所有者读写，掩码无法把组读权限补回来。目录通常需要搜索位才能正常使用，所以目录的常见请求模式与普通文件不同，不能混用同一个记忆口诀而忽略对象类型。

掩码是进程状态的一部分，子进程通常继承它。某个终端会话改过掩码，之后启动的实验可能生成与另一个会话不同的权限。建议在受控的子 Shell 或创建进程内设置实验所需掩码，并记录其值；在共享的长寿命父进程里随意改掩码，容易影响后续不相关任务。

默认访问控制列表存在时，创建权限的推导需要按访问控制列表继承规则分析，不能机械套用简化公式。此外，文件创建之后再修改权限会有一个时间窗口：对象可能先以较宽权限出现，随后才收紧。需要保密的临时数据，应在创建时就请求合适权限，避免依赖“生成完再统一修改”来补救。

<a id="linux-1-detail-19"></a>
### 4.4 执行位、解释器与挂载条件

一个文本脚本可以通过解释器读取运行，也可以在具备执行权限且有合适解释器声明时直接执行。前一种方式主要要求解释器能读取脚本；后一种方式还涉及执行权限、文件系统是否允许执行以及解释器定位。于是“用解释器运行成功”和“直接执行成功”并不是同一个测试。

解释器声明中的路径如果在另一台机器不存在，脚本即使内容和权限都正确，也可能无法直接运行。用环境搜索解释器提高了可移植性，却又把搜索路径与当前环境带进了解释器选择。研究实验应该记录最终使用的解释器版本和真实位置，而不只记录声明行。

执行权限也不保证运行成功。动态库缺失、架构不匹配、加载器路径错误、容器挂载限制，都可能在真正的业务逻辑开始前导致失败。这些情形应通过错误类型与最小依赖验证区分。不断增加权限无法修复二进制架构错误，也不能替代正确安装依赖。

<a id="linux-1-detail-20"></a>
## 5. 文本流必须有明确的数据契约

<a id="linux-1-detail-21"></a>
### 5.1 文件名列表与记录列表需要不同分隔协议

Linux 文件名可以包含换行，但不能包含路径分隔用的斜杠和字符串终止用的零字节。因此，把每个文件名后面加一个换行，再按行读取，不足以无损表示所有合法文件名。专门的文件名遍历流程可以使用零字节分隔，并让上下游都明确支持这种协议；只改一端不够。

不要解析面向人类显示的目录列表来获取文件名。显示工具可能对特殊字符转义、加颜色、按终端宽度排版，输出不等于一个稳定的机器接口。使用文件系统遍历接口，或者具有明确机器输出选项的工具，才能把名称本身与显示样式分开。程序处理路径时，也应尽可能一直保留结构化的路径对象或参数数组。

文本记录则要规定编码、字段分隔、引号和换行约定。简单按逗号切分可以处理某个受限格式，却不能自动成为正式的逗号分隔数据解析器。字段内部包含逗号、双引号或换行时，需要遵循格式规则的解析器。如果训练数据来自正式格式，应按它的语法解析，而不是因为一份样本恰好简单就降低整个数据契约。

<a id="linux-1-detail-22"></a>
### 5.2 编码、换行和末尾空行会改变观察

字节是文件系统和管道传输的基本材料，字符则需要通过编码解释。一个中文字符不一定对应一个字节，按字节截取可能切断编码序列。读取失败应明确是编码不匹配、文件截断还是二进制误当文本；直接忽略解码错误可能悄悄删除内容，改变训练样本和标签。

不同平台的换行约定会在脚本、哈希和解析中产生差异。交互显示通常把这些差异隐藏起来，而某些解释器声明或严格协议会直接受到影响。需要跨平台共享文本时，可以在版本管理和文件写入处约定换行；需要验证原始字节一致时，必须对字节做摘要，不能先经过可能归一化换行的文本读取再比较。

“按行统计”也应给出定义。某些工具统计的是换行符数量，最后一条记录没有末尾换行时，显示数字未必等于你以为的记录数。空行是不是样本、表头要不要计入、嵌入字段中的换行是否构成新记录，都属于数据格式层的问题。指标定义不清时，一个很快的流水线仍然可能稳定地产生错误样本量。

<a id="linux-1-detail-23"></a>
### 5.3 排序、去重和抽样会悄悄改变实验

排序工具对字符的比较通常受区域设置影响。相同数据在不同环境下排序结果改变，可能进一步改变数据划分、批次顺序和最终训练轨迹。若需要按字节稳定排序，可以在局部命令环境指定相应区域设置；若需要自然语言排序，应明确采用的语言规则，并接受不同实现版本可能带来的差异。

相邻去重与全局去重是不同操作。只合并连续相同记录的工具，要求输入已经按合适规则聚集；为了让它工作而先排序，又会改变原顺序。若原顺序具有时间意义，排序可能引入数据泄漏或破坏时间切分。需要保序去重时，应使用专门保留首次出现顺序的方法，并说明内存需求和键的定义。

抽取前若干行适合检查格式，却不一定形成有代表性的样本。文件按标签、时间或来源排序时，前缀样本会系统偏向某些群体。要做统计评估，需要明确抽样单位和随机机制；要做调试，则可以有意选小而可解释的样本。区分目的，才能避免把一个调试命令产生的子集当成可靠基准。

## 6. 可复现实验：从名称到字节流

<a id="sec-6-1"></a>
<a id="linux-1-detail-25"></a>
### 6.1 用一个隔离实验观察链接和打开对象

下面的实验只使用 Python 标准库，但实际运行位置应是 Linux 文件系统中的临时目录。它把“名称被删”“内容被替换”“句柄仍指向旧对象”拆成独立断言。不要在权限映射不同的 Windows 挂载目录里运行后，拿结果替代 Linux 本地文件系统的判断。

```python
import os
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory(prefix="linux-path-") as raw:
    root = Path(raw)
    source = root / "data.txt"
    hard = root / "hard.txt"
    soft = root / "soft.txt"
    source.write_text("old\n", encoding="utf-8")
    os.link(source, hard)
    soft.symlink_to("data.txt")
    assert source.stat().st_ino == hard.stat().st_ino
    assert soft.lstat().st_ino != source.stat().st_ino
    with source.open("r", encoding="utf-8") as opened:
        replacement = root / "new.tmp"
        replacement.write_text("new\n", encoding="utf-8")
        os.replace(replacement, source)
        assert source.read_text(encoding="utf-8") == "new\n"
        assert soft.read_text(encoding="utf-8") == "new\n"
        assert hard.read_text(encoding="utf-8") == "old\n"
        assert opened.read() == "old\n"
    hard.unlink()
    with source.open("r", encoding="utf-8") as opened:
        source.unlink()
        assert not source.exists()
        assert soft.is_symlink() and not soft.exists()
        assert opened.read() == "new\n"
print("link and open-object assertions passed")
```

逐步解释比只看最后的成功消息更重要。第一次创建硬链接后，两个名称具有相同对象标识；创建软链接则增加了一个保存目标字符串的对象。之后替换原始名称，软链接在下一次解析时跟随新名称指向新对象；硬链接仍保留旧对象的另一个名称，已经打开的句柄也仍引用旧对象。最后删除新对象的名字，已经打开的句柄仍能读完内容，而软链接变成悬空链接。

这个实验没有证明所有文件系统在断电后都能恢复出相同结果，也没有测试网络文件系统上的缓存一致性。它验证的是当前条件下的名称和打开引用关系。若要研究持久性，必须另外设计写入、同步、崩溃和恢复协议，不能由这里的运行结果直接外推。

<a id="linux-1-detail-26"></a>
### 6.2 观察参数数组、空参数和重定向顺序

这个实验让 Bash 启动 Python 打印收到的参数，并把两个重定向顺序的结果分别捕获。程序传给 Bash 的值通过位置参数进入，固定脚本文本没有拼入路径内容。即使临时目录名字含空格，也不会因此改变脚本的语法。

```python
import json
import subprocess
import sys
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory(prefix="linux argv ") as raw:
    root = Path(raw)
    (root / "one.txt").write_text("x", encoding="utf-8")
    script = r'''
set -eu
name='alpha beta'
"$1" -c 'import json,sys;print(json.dumps(sys.argv[1:]))' "$name" "" "*.txt"
printf '%s\n' "$name" > "$2"
{ printf 'OUT\n'; printf 'ERR\n' >&2; } > "$3" 2>&1
{ printf 'OUT\n'; printf 'ERR\n' >&2; } 2>&1 > "$4"
'''
    p = subprocess.run(
        ["bash", "--noprofile", "--norc", "-c", script, "demo",
         sys.executable, str(root / "value.txt"),
         str(root / "both.txt"), str(root / "out.txt")],
        cwd=root, text=True, capture_output=True, check=True,
    )
    lines = p.stdout.splitlines()
    assert json.loads(lines[0]) == ["alpha beta", "", "*.txt"]
    assert lines[1:] == ["ERR"]
    assert (root / "both.txt").read_text() == "OUT\nERR\n"
    assert (root / "out.txt").read_text() == "OUT\n"
    assert (root / "value.txt").read_text() == "alpha beta\n"
print("argv and descriptor assertions passed")
```

这里保留了一个空参数和一个字面星号模式，证明引用保护的是参数结构，而不是简单让字符串“显得整齐”。两个重定向块的输出差异，则直接证明复制发生在当时：第二个块先把错误流复制到捕获管道，再改变输出流，因此错误内容进入了父进程捕获的标准输出，而没有进入普通输出文件。

实验使用受控的小输出，避免产生大规模管道阻塞。真实服务若持续输出大量内容，应采用流式读取、合理缓冲和完整超时清理。不能把适合教学的捕获方式不加分析地套到数小时训练日志上。

<a id="linux-1-detail-27"></a>
### 6.3 验证掩码公式与正式格式解析

下面把权限位验证与数据解析放在同一个自清理实验中，但两部分没有隐含的业务依赖。程序会恢复原掩码，不把实验状态留给后续代码。权限断言仅适用于本实验新建、无默认访问控制列表干预的普通临时目录；是否有读取权限则还取决于进程身份，因此本实验不通过“读失败”断言来推断所有权限控制。

```python
import csv
import io
import os
import stat
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory(prefix="linux-mode-") as raw:
    root = Path(raw)
    old_mask = os.umask(0o027)
    try:
        fd = os.open(root / "record.txt", os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o666)
        os.close(fd)
        (root / "work").mkdir(mode=0o777)
    finally:
        os.umask(old_mask)
    assert stat.S_IMODE((root / "record.txt").stat().st_mode) == 0o640
    assert stat.S_IMODE((root / "work").stat().st_mode) == 0o750
    data = 'name,note\nsample,"line one\nline two, quoted"\n'
    rows = list(csv.reader(io.StringIO(data, newline="")))
    assert len(rows) == 2
    assert rows[1] == ["sample", "line one\nline two, quoted"]
    assert len(data.splitlines()) == 3
print("mode and format assertions passed")
```

正式解析产生两条记录，而简单按文本换行得到三行。这不是某个工具“计数不准”，而是你询问的对象不同：物理文本行、格式记录和业务样本可能有不同数量。实验报告应注明采用哪个单位，否则即使所有计算都没有程序错误，结论也可能互相矛盾。

<a id="linux-1-detail-28"></a>
## 7. 进阶边界：原子性、身份与并发变化

<a id="linux-1-detail-29"></a>
### 7.1 重命名保证名称切换，不自动保证持久化

在适用的同一文件系统和操作条件下，重命名可以使名称切换具有原子性：观察者通常看到旧关联或新关联，而不会看到把文件逐字节复制到一半的中间内容。这是发布配置和模型检查点时常用的基本机制。但若临时文件位于另一个文件系统，重命名可能失败；某些上层工具为了完成跨文件系统移动而退化为复制，再删除，整体就不再是同一种原子切换。

原子性也不同于持久性。程序写入后，数据可能仍在用户态缓冲或内核缓存中。要求崩溃恢复语义时，需要按文件系统和平台约定处理刷新、同步文件数据、名称替换以及相关目录同步；还要考虑存储设备的实际保证。仅凭“替换调用返回成功”不能证明断电后一定保留新结果，更不能证明应用层的多文件事务完整。

多个输出文件一起构成一个实验结果时，应把它们视作一个版本集合。把权重和配置分别覆盖成新文件，会让读者在中间时刻读到新权重配旧配置。更稳妥的组织是先生成独立版本目录，验证文件集合，再切换一个版本入口或者发布清单。入口切换的粒度与读取方协议共同决定一致性，不能只关注某一个文件的原子写入。

<a id="linux-1-detail-30"></a>
### 7.2 先检查再使用会遇到竞态

程序先检查路径“存在且是普通文件”，再过一会儿打开它，中间名称关联可能已经变化。这叫检查与使用之间的时间竞争。即使没有恶意行为，另一个训练进程的清理和发布也足以触发它。单纯增加更多路径检查，无法消除检查与实际操作之间的间隙。

实际策略是尽量把验证作用于已经打开的对象，或者使用能在一个接口中表达约束的操作。例如以排他创建方式生成新文件，避免“先检查不存在，再创建”之间被别人抢先；打开后检查对象元数据，再据此执行后续步骤。面对不可信目录树时，还需要目录描述符相对操作、链接解析限制等更严格机制，其适用条件应查阅系统接口文档。

路径前缀检查也可能误判。字符串以某个目录名开头，不代表它实际位于该目录内；同名前缀的兄弟目录、上一级分量和符号链接都能改变结果。即使先完成真实路径解析，后续仍可能发生目录变化。根据威胁和并发条件选择适当接口，才是可靠设计；没有并发对手的小型离线脚本，可以采用较简化的契约，但应清楚它没有提供什么保证。

<a id="linux-1-detail-31"></a>
### 7.3 内容摘要、元数据和打开句柄互补

文件大小和修改时间适合快速发现变化，却不能证明内容相同。两个不同文件可能大小相同，时间戳也可能被复制或具有有限精度。内容摘要对识别字节版本更有力，但必须在稳定快照或受控读取条件下计算；若文件边读边被改，得到的摘要可能不对应任何一个完整发布版本。

打开句柄可以固定正在读取的对象引用，却不会自动阻止其他进程修改同一个对象内容。只读打开限制的是本句柄操作，不是对全系统的冻结。要让训练看到稳定数据，可以使用不可变版本目录、写入完成后的发布协议、适用的锁或者文件系统快照。选择哪一种，要结合数据规模、并发写入方式和存储能力。

版本管理中的提交标识也不能自动覆盖外部大数据、环境和未提交配置。实验清单需要把代码版本、数据版本、配置与环境联系起来。Linux 基础之所以与研究可信度直接相关，正因为所有高级框架最终仍然通过这些名称、字节、权限和进程状态访问世界。

## 8. 练习与详细解析

<a id="linux-1-detail-33"></a>
### 8.1 路径和链接：四道推理题

**题一：同一脚本从两个目录启动，为什么可能读到不同数据？** 假设参数中没有明确指定数据位置，脚本内部直接打开一个相对文件名。请写出定位链，并提出同时适用于命令行和配置文件的契约。

**解析：** 定位链从启动进程的工作目录开始，经过每个相对路径分量，到达最终对象；脚本文件所在目录不会自动替代这个起点。命令行相对路径可以明确相对调用目录，配置文件中的相对路径可以明确相对配置目录，两者在入口统一解析为实际路径。日志记录解析后的路径和数据摘要，才能同时排查定位错误与版本错误。仅在脚本开头切换目录会影响所有相对输出，必须在采用前评估它是否符合整个接口契约。

**题二：一个文件有两个硬链接名称，先通过第一个名称原地写入，再用新对象替换第一个名称，第二个名称分别看到什么？**

**解析：** 原地写入时，两个名称仍指向同一个对象，所以第二个名称读到被修改的内容。替换时，第一个名称改为指向新对象，第二个名称仍引用旧对象，所以它不会跟随新内容。关键不是“文件名有没有变”，而是目录项关联是否改向另一个对象。备份系统若用硬链接节省空间，后续原地修改就可能破坏原本以为独立的历史版本，应采用符合其共享模型的写入策略。

**题三：相对软链接保存目标“数据目录/样本”，把链接移动到另一个目录，会发生什么？**

**解析：** 相对目标从链接所在目录开始解释，所以移动链接本身可能改变最终目标。把整个目录树连同链接及相对目标一起按相同结构移动，通常更容易保持关系。还要检查移动操作是否跨文件系统、目标是否仍存在以及路径中的权限。不能因为软链接的内容字符串没变，就断定其指向对象没变；名称解释依赖上下文。

**题四：日志文件已经删除，为什么磁盘空间仍未明显下降？能否直接推断删除失败？**

**解析：** 不能。进程可能仍持有打开引用，或文件还有其他硬链接名称。应检查相关对象的引用和链接关系，结合文件系统空间统计判断。还可能有快照、保留空间和延迟回收等机制，但要按具体文件系统验证。处理时先识别拥有该对象的任务，再选择应用支持的关闭或重开流程，不能把结束任意进程当作常规腾空间方法。

<a id="linux-1-detail-34"></a>
### 8.2 参数、流与格式：五道诊断题

**题五：把路径放在双引号里，为什么仍可能被命令当作选项？**

**解析：** 引号主要保护参数边界和展开行为，完成解析后通常被移除。一个以减号开头的单个参数，仍可能符合工具的选项语法。支持选项终止符的工具可在路径前放双减号，或者用明确的相对路径形式避免首字符被当作选项。需要分别验证“传了几个参数”与“工具怎样解释参数”，不能把两个解析层混成一个问题。

**题六：为什么把一个参数列表存进普通字符串，再不引用地展开，无法保证恢复原列表？**

**解析：** 字符串没有保留每个参数原来的边界，也无法区分“一个含空格的参数”和“两个参数”。空参数可能消失，星号可能匹配目录，字段拆分规则还会受到环境影响。使用数组保存结构，再引用整个数组展开，才能保留每个元素。如果跨进程或跨文件传递列表，应使用有明确定义的编码，例如正式序列化格式或者零字节分隔，不能靠目测空格猜测边界。

**题七：某程序打印了“完成”，退出状态也是零，为什么结果仍可能不能使用？**

**解析：** 程序的完成标志可能只覆盖计算阶段，输出可能仍未通过完整性验证，或者产物路径与调用者预期不同。退出零表示该程序按自身约定认为成功，不自动证明业务契约。需要验证文件集合、形状、记录数、格式、摘要以及任务标识。对多文件结果还要防止新旧版本混合，并把验证通过后发布与中间生成明确分开。

**题八：一个流水线只统计换行符，得到一千行，为什么不能直接宣布有一千条训练样本？**

**解析：** 文件可能有表头、空行、跨行字段，最后一条记录也可能缺少末尾换行；样本还可能由多条记录组成。先定义业务样本，再选择符合格式的解析器统计。若格式明确规定每行一条独立记录、没有表头和空行、末尾规则也固定，那么行统计才可能成为有效实现。工具输出正确与指标定义正确，是两个需要分别证明的条件。

**题九：为什么不应把任意二进制文件读进 Shell 变量后再写回，作为可靠复制方法？**

**解析：** Shell 变量无法可靠表示任意包含零字节的数据，命令替换还会删除末尾换行，未引用展开可能继续改变参数。把字符变量当通用字节容器，会违反数据表示假设。应使用字节复制工具、文件描述符或二进制读写接口，并通过摘要确认复制结果。对于大文件，还要考虑内存与流式处理，而不是把整个文件一次装入变量。

<a id="linux-1-detail-35"></a>
### 8.3 权限和并发：五道设计题

**题十：文件只读却被别人删除，是否说明权限位无效？**

**解析：** 不说明。删除名称主要受父目录的写入和搜索权限以及粘滞位等规则约束；文件读写权限控制内容访问。防止不合适的删除，需要合理安排目录所有权和目录权限，并结合共享协作需求。简单禁止所有目录写入可能又阻止合法发布，因此设计应该从谁需要创建、替换、读取和删除分别出发，而不是寻找一个万能权限数字。

**题十一：请求普通文件模式为六六六，掩码为零二七，为什么结果是六四零而不是算术减法得到的数字？**

**解析：** 三组数字分别是三个权限位的八进制编码，系统逐位清除掩码中指定的权限。所有者没有被禁止，组的写位被清除，其他用户的读写位都被清除，得到六四零。目录若请求七七七，则相同掩码得到七五零。若有默认访问控制列表，必须重新分析继承规则，不能机械采用本题的简化前提。

**题十二：用管理员身份测试文件权限，读取成功，能证明普通用户也能读取吗？**

**解析：** 不能。测试主体不同，适用能力和身份不同。权限结论必须在与目标进程相同的凭据和控制层下验证。先记录进程身份、组和挂载上下文，再检查最小实际操作。研究实验里也一样：交互终端中的成功，不足以证明计划任务或服务账户中的成功，因为它们可能处于不同环境和命名空间。

**题十三：临时结果文件与最终文件位于不同文件系统，能否依靠移动命令保证原子发布？**

**解析：** 不能直接依靠。底层重命名可能不支持跨文件系统，上层移动命令可能变成复制再删除。应把临时文件创建在最终目标所在文件系统，并验证适用操作语义；多文件结果则用版本目录和发布入口协议。原子可见性仍不等于断电持久性，后者需要独立的同步和恢复设计。本题的判断依据是操作边界，而不是命令名字叫“移动”。

**题十四：先检查路径位于指定目录内，再打开，为什么仍可能访问到变化后的对象？如何改进？**

**解析：** 检查与打开之间，目录项或链接可能变化。字符串前缀还会误判兄弟目录和上一级路径。根据需要可使用基于目录描述符的相对访问、排他创建、限制链接解析的接口，或者先打开再对实际对象验证。对于完全受控的离线输入，也可以使用简化协议，但必须承认它依赖目录不被并发改动的前提。改进不是堆叠更多相同检查，而是缩小或消除检查与使用的间隙。

<a id="sec-7-1"></a>
<a id="linux-1-detail-36"></a>
### 8.4 综合追问：管道分隔字段能否替代正式格式解析

给定包含带逗号名称、跨行备注和重复标识的数据文件，要求筛选某类样本、保留输入顺序、输出一份新版本，并记录样本数。请解释仅靠按行切分、逗号切字段、排序去重和覆盖原文件会分别破坏什么。

先按行切分可能把一个跨行字段拆成多条伪记录；再按逗号切字段可能把带分隔符的名称拆成多个列。为了去重而排序，会改变原顺序，如果顺序具有时间或采样意义，还会改变后续实验；直接覆盖原文件则可能在输入打开前被重定向截断，或者让失败时留下半成品。这四种问题分别发生在格式语法、字段语法、业务语义和发布协议层，不能只修一个分隔符。

合理方案先用正式解析器读取，明确唯一键、空值和重复冲突处理，按输入顺序进行筛选和保序去重；输出写入同文件系统中的新临时对象，关闭并验证记录数、必要字段和内容摘要，再发布到新版本位置。运行清单记录源版本、筛选条件和输出版本。若输入非常大，保序全局去重需要外部状态或分区策略，应把内存上界和顺序恢复方案纳入设计，而不是假装一个短命令自动解决所有规模。

进一步的研究问题是：源数据在读取期间发生变化，怎样保证输出对应一个稳定输入版本？可以要求源文件不可变、从快照读取，或通过生产者发布协议固定版本。仅计算读取前后的文件大小不足以证明中间没有变化；摘要也需要与稳定读取对象结合。这个问题把本章所有层次连在一起：名称决定找谁，句柄决定读哪个对象，格式决定怎样理解字节，发布协议决定别人何时能信任结果。

<a id="linux-1-detail-37"></a>
## 9. 继续研究的方向

如果你已经能解释本章实验，可以沿三个方向深入。第一是系统调用层：阅读打开、链接、重命名与目录相对操作的接口，研究哪些检查可以被原子表达。第二是文件系统层：比较本地日志文件系统、网络文件系统和对象存储的可见性与持久性契约，理解“路径存在”并不是所有存储都共有的抽象。第三是数据工程层：为每种输入格式规定编码、模式、版本和损坏处理，把字节正确性一路连接到样本正确性。

深入时应始终保留一个可证伪的问题。例如“替换名称会不会改变已打开读者看到的对象”，比“学习文件系统”更适合设计实验。先给出条件、预期和反例，再做隔离验证；观察到结果后，只把它推广到已经说明的范围。这样学到的 Linux 不只是命令清单，而是一套能支持可靠研究的推理方法。
