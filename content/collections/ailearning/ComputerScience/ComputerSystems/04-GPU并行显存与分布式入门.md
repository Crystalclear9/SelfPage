## 1. GPU 为什么适合某些并行工作

<a id="gpu-detail-2"></a>

### 1.1 从吞吐导向到 SIMT 执行

CPU 往往擅长低延迟地推进少量复杂控制流，GPU 通过大量并行工作和线程调度追求总体吞吐。这个区分不是“CPU 串行、GPU 并行”：现代 CPU 也有多核与向量单元，GPU 也会执行顺序依赖。真正要问的是工作中有多少独立操作、访存是否规则、控制路径是否一致，以及规模能否摊薄启动和传输成本。

CUDA 把工作组织成线程、线程块和网格，线程块内可以协作并使用共享存储。硬件把线程以执行组调度，在相近控制路径上执行指令，通常称为 SIMT。概念上每个线程有自己的索引与状态；实现上多个线程共享执行资源。编写内核时既要保留每个元素的独立语义，也要考虑同组线程怎样共同占用带宽和执行单元。

分支发散是同一执行组内线程走不同路径，导致资源利用下降的一种机制。如果一半线程执行代价很高的分支，另一半执行轻分支，不能简单按平均分支成本估计总时间。具体调度能力因架构而异，但“语义独立不等于成本独立”是稳定原则。把相似任务分组可能改善执行一致性，却可能增加排序和恢复原序的成本。

还要区分并行度与占用率。启动很多线程只是提供可调度工作；寄存器、共享内存、线程块限制和依赖链决定多少工作能同时驻留。过多寄存器可能减少驻留块数，强行减少寄存器又可能让变量溢出到较慢存储。占用率更高不保证更快，因为已有足够线程隐藏延迟后，减少数据搬运或增加复用通常更重要。

<a id="gpu-detail-3"></a>

### 1.2 访存合并、复用和工作粒度

连续线程访问相邻地址时，硬件更容易把访问合并成较少事务；随机散布则可能为很少的有效字节发起许多事务。这与 CPU 缓存局部性有联系，却不能用同一套缓存行直觉解释所有设备。转置、切片和稀疏索引可能让逻辑形状不变但物理访问变差，因此算子形状、步幅和实际布局都应进入性能说明。

矩阵乘法有较高复用潜力：一个输入元素可以参与许多乘加。分块把部分输入载入较近存储，再反复使用，从而减少外部显存访问。向量逐元素加法则几乎每次读取只产生少量计算，更容易受带宽限制。两者都能并行，但适合优化的方向不同。只比较浮点运算数量，容易误判哪个算子需要更长时间。

大量很小的算子可能由启动和调度开销主导。算子融合把几个连续变换合并，可以减少中间结果写回与额外启动；但融合后寄存器压力可能增加，也可能阻碍其他并行。融合应保持数学语义和数值容差，并在代表性形状上测量。不能仅凭“少一个 Python 调用”就证明设备工作减少。

[NVIDIA CUDA 编程指南](https://docs.nvidia.com/cuda/cuda-programming-guide/)提供硬件与编程模型的正式入口；[最佳实践指南](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/)讨论访问与执行优化。本章采用这些机制建立简化账本，不给出跨设备通用的线程块大小、占用率阈值或峰值数字。具体架构参数必须从对应设备与版本核对。

<a id="gpu-detail-4"></a>

### 1.3 Roofline：把计算量和搬运量放到同一尺度

设某工作需要 $F$ 次浮点操作，跨选定内存层级搬运 $Q$ 字节，可持续计算能力为 $P$，可持续带宽为 $B$。忽略其他开销，下界为 $T\ge\max(F/P,Q/B)$，于是可达吞吐至多为 $\min(P,BI)$，其中算术强度 $I=F/Q$。这是由计算和字节各自不能超过资源服务能力推出的界，不是实际时间的精确预测。

转折点为 $I_\ast=P/B$。若 $I<I_\ast$，带宽界更紧；若 $I>I_\ast$，计算界更紧。这里的字节必须与带宽所属层级一致：把芯片内缓存流量除以外部显存带宽没有意义。有效复用能降低外部字节，但编译器、缓存命中和布局会使实际流量与理想最少流量不同，应明确是估计值还是测量值。

以矩阵乘法 $C=AB$ 为例，$A$ 为 $m\times k$，$B$ 为 $k\times n$，按一次乘加计两次操作，有 $F\approx2mkn$。若每个输入只读一次、输出只写一次、元素占 $s$ 字节，则理想最少字节约为 $Q=s(mk+kn+mn)$。真实实现还可能读旧输出、写临时结果或重复取数，因此这个强度是理想化估计，不能直接当计数器读数。

Roofline 也没有覆盖所有瓶颈。内核启动、同步、指令依赖、非浮点计算、低并行度和通信都可能让性能低于两条界。发现算子位于界下方，是继续诊断的起点；不能直接推断程序有错。对小张量，固定启动成本甚至可能比全部计算与搬运下界都大。

<a id="gpu-detail-5"></a>

## 2. 显存账本：容量问题必须按生命周期拆开

<a id="gpu-detail-6"></a>

### 2.1 参数、梯度、优化器与激活

显存峰值账本可以列出参数、梯度、优化器状态、激活、临时工作空间与通信缓冲等活跃分配，再另列分配器已保留但未被活跃分配使用的额外空间。reserved 通常已经包含活跃 allocated，不能把全部 reserved 再加到活跃张量上；还需单列框架分配器之外的上下文或其他占用。各部分是否同时存在，取决于阶段和实现。不能简单把模型文件大小当训练显存，因为文件通常不包含训练中保存的激活与全部优化器状态；也不能把各阶段独立峰值直接相加，因为它们未必同时发生。

设有 $N$ 个可训练参数，参数与梯度均为四字节，优化器保存两个四字节动量状态，则持久状态粗略为 $16N$ 字节。这里没有额外主参数副本，没有压缩状态，没有分片，也没有冻结参数。若某种混合精度实现保留低精度权重和高精度主副本，应逐项增加，不能套用一个“每参数固定多少字节”的万能常数。

激活通常随批大小、序列长度、层数和中间特征宽度增长。某些注意力实现会显式保存与序列长度平方相关的矩阵，另一些实现通过分块重算避免存储该矩阵。相同数学模型不意味着相同激活账本。排查长序列显存问题时，先弄清实际算子保存了什么，再决定减批量、缩短序列还是采用不同实现。

临时工作空间可能在某个卷积或矩阵算法中突然增大；通信桶和参数展开也会制造短暂双份存储。参数、梯度和激活谁是主项，需要分别估算，并用阶段峰值验证。只有识别占比之后，才知道重算、分片、低精度或更小微批哪一种有希望解决容量约束。

<a id="gpu-detail-7"></a>

### 2.2 分配、保留、碎片与泄漏是不同问题

框架分配器可能保留已经不再被活跃张量使用的设备内存，以便后续复用。驱动看到的占用因此可能高于当前活跃张量字节。保留空间不自动等于内存泄漏；反过来，活跃张量持续增加才可能来自仍被引用的计算图、日志列表或缓存。应同时看活跃分配、保留量和阶段峰值，不只看单个外部工具数字。

碎片指空闲空间分散到无法满足所需大块的程度，具体表现依分配器机制而异。总空闲字节足够并不必然保证任意分配成功。不过在没有证据时把所有内存不足归为碎片，也会掩盖真正的激活增长。先用形状和生命周期解释主占用，再检查动态形状、反复变化的临时块与分配策略。

释放缓存不能释放仍被张量引用的内存，也不会让一个本质超过容量的训练步骤突然可行。频繁清理还可能破坏复用并增加分配开销。更有价值的做法是找到哪些对象跨步骤被持有、何处保存了不必要的图、是否可以及时结束生命周期。内存优化本质上是所有权与时间的问题，不只是调用某个清理接口。

CPU 与 GPU 内存也要分开。把状态卸载到主机可以减少设备容量压力，却消耗主机内存和传输带宽；若主机因此换页，端到端性能可能严重下降。容量转移不是容量消失，应在完整资源账本里报告新的驻留位置、搬运次数和同步依赖。

## 3. 流、传输与同步：异步提交需要依赖证明

<a id="gpu-detail-9"></a>

### 3.1 顺序执行与跨流依赖

一个设备流可以理解为有序工作队列，同一流中的操作通常按所需顺序执行。不同流之间没有因为主机代码相邻就自动建立全部依赖。若流甲生成张量，流乙消费它，必须使用正确事件或框架等待机制表达“生成完成之后才能消费”。同时还要保证张量存储在消费结束前没有被回收或复用。

数据依赖和存储生命周期是两件事。事件保证消费者不会读到尚未完成的结果；生命周期跟踪保证分配器不会把同一块存储提前交给别的工作。只解决其中一个仍可能出错。框架提供的跨流记录机制应按当前文档使用，而不是把普通 Python 引用存在与设备侧执行完成混为一谈。

多流也不承诺实际并行。设备可能没有足够空闲执行资源，两个内核可能都占满带宽，或者存在隐式同步。即使时间轴显示重叠，总完成时间也未必明显改善，因为二者竞争同一资源。合理实验要比较完整窗口，而不是只看图上两条彩色条带交叠。

[PyTorch CUDA 语义文档](https://docs.pytorch.org/docs/2.10/notes/cuda.html)说明了异步执行、流与内存管理的接口约束。由于本章在 CPU 上验证代数，不给出未经 GPU 实测的流优化成绩。迁移到实际设备时，应先构造一个最小依赖测试，再用事件与端到端同步边界核对正确性和性能。

<a id="gpu-detail-10"></a>

### 3.2 主机到设备传输何时可能被隐藏

假设每批主机到设备传输需 $H$，计算需 $C$，各自独立且依赖正确，双缓冲理想稳态间隔可接近 $\max(H,C)$，首批仍需 $H+C$。若传输和计算串行，间隔为 $H+C$。但能否接近重叠下界，还受硬件复制引擎、源内存条件、流安排、传输粒度与共享带宽影响。

锁页主机内存与合适异步接口可以帮助某些传输路径，但不能把任何带有“非阻塞”参数的调用都理解为已经获得重叠。接口返回仅表示提交语义，结果在何时可安全读取仍由依赖决定。设备到主机的异步拷贝后立刻读取主机数组，也可能读取尚未完成的数据，必须建立完成条件。

双缓冲意味着当前批计算时，下一批传输；至少需要两份合适的输入驻留空间，并保证旧批不再被使用后才能复用。若下一批还在 CPU 解码，设备侧空出缓冲并不能提前得到数据。把整条路径组合起来，加载、传输、计算的最慢资源才决定最终节奏，与上一章的流水线模型一致。

每批过小会让固定提交成本占比上升，过大又增加显存与响应延迟。可以先固定目标统计批，再在不改变目标的前提下调整传输粒度或微批，但要核对跨样本算子和更新边界。对于在线服务，批量等待本身也是延迟；吞吐最优配置未必满足请求时限。

## 4. 数据并行：从共同目标推导每个进程的损失

<a id="sec-1-1"></a>

<a id="gpu-detail-12"></a>

### 4.1 基础算例：全局批大小与有效更新频率

普通数据并行让每个设备保留模型副本，各处理一部分数据，再通过归约让梯度形成共同更新。设设备数为 $p$，每设备微批有 $b$ 个样本，累计 $a$ 次再更新，名义样本数是 $pba$。例如四个设备、每次八条、累积三次，名义上一次更新覆盖九十六条。这里默认每次实际数量相同、没有重复与掩码差异。

“名义”一词不能省略。分布式采样器可能为对齐补齐记录，有些位置被忽略，最后一个微批可能较小；不同设备还可能具有不同有效 token 数。目标若按 token 平均，样本条数就不是正确分母。应先定义损失分子与有效质量，再把执行拓扑映射到同一目标。

保持每设备批不变而增加设备，会增大全局批，减少每轮优化步数，改变梯度噪声与调度进度。保持全局批不变则每设备工作减少，通信占比可能上升。这是弱扩展与强扩展的不同设置，比较时应分别声明。只说训练相同轮数，既不能保证相同优化预算，也不能保证相同硬件工作量。

<a id="sec-2-1"></a>

<a id="gpu-detail-13"></a>

### 4.2 机制展开：全局分母和梯度平均必须配套

设进程 $r$ 的损失和为 $S_r(\theta)=\sum_i w_{ri}\ell_{ri}(\theta)$，有效权重和为 $N_r=\sum_iw_{ri}$，总权重 $N=\sum_rN_r>0$。如果权重不依赖参数，目标为 $L=\sum_rS_r/N$，梯度为 $\nabla L=\sum_r\nabla S_r/N$。分母通常可以通过标量归约获得，不能用局部平均分母代替。

若分布式机制最终把各进程梯度取算术平均，即输出 $\frac1p\sum_rg_r$，让每个进程反传 $\widetilde L_r=pS_r/N$，就得到正确全局梯度。若已经计算局部均值 $\bar L_r=S_r/N_r$，则需乘 $pN_r/N$。这就是“本地损失怎样缩放”必须与“通信是求和还是平均”一起说明的原因。

当 $N_r=0$ 时局部均值没有定义，但局部损失和可以为零。该进程仍可能必须参与相同的通信序列，并产生与模型图一致的零梯度。若全局 $N=0$，则整个平均目标未定义，应按统一协议跳过更新，而不是各进程自行决定是否继续。零有效数据边界既是数值问题，也是通信一致性问题。

若权重依赖参数，分母也随参数变化，直接把 $N$ 当常数会漏掉商法则项。训练中的有效 token 掩码通常与参数无关，而可学习重要性权重不一定如此。使用上述缩放前应明确这一条件；“按数量加权”的简洁公式有适用边界，不能覆盖所有自归一化目标。

<a id="deep-dive-2"></a>

<a id="gpu-detail-14"></a>

### 4.3 深入讲解：累积窗口才是一个完整归一化单元

设每个进程还执行多个微批，目标分子应对所有进程和全部微批求和，分母也应覆盖同一窗口。每个微批直接取均值再除以累计次数，仅在微批有效权重相等时等价。变长 token 任务常常不满足条件，因此更稳妥的推导是累计损失和对应的梯度，再在整个窗口统一归一化。

如果反向前已知道全局窗口分母，可在每个微批使用对应缩放；如果不知道，可以先累计未归一化梯度，在完成同步后按正确系数缩放。后一种方式要结合框架的梯度平均、混合精度缩放与梯度裁剪顺序：应先恢复真正目标的梯度，再按既定规则裁剪与更新。把裁剪放在错误缩放前，会改变有效阈值。

正则项还需要单独处理。目标若为数据平均损失加 $\lambda R(\theta)$，不应让每个微批都完整累加一次正则项，导致系数随累计次数放大。可以在窗口中加入一次，或按已知权重分配到微批，确保总系数恰好为 $\lambda$。优化器中的解耦权重衰减又具有不同更新语义，应与显式正则梯度区分。

局部不同数据量也影响动态批策略。若每卡按相同 token 预算组批，样本条数不同是正常的；若训练目标按样本平均，不能改用 token 总数做分母。数据流水线要把正确权重和传给训练循环，通信层要合并这些标量，优化器才有可能实现原目标。系统设计和统计目标在这里直接相接。

<a id="sec-4"></a>

<a id="gpu-detail-15"></a>

### 4.4 多卡梯度平均的含义：等价条件比批大小更多

代数正确只是第一步。要让分布式一次更新与串行一次大批一致，前向函数也必须可按样本拆分，初始状态相同，随机性处理符合比较目标，优化器只在相同边界更新。BatchNorm 的局部统计、批内对比损失、跨样本排序与负样本采样，都可能使分拆后的前向目标发生变化。

例如对比学习的负样本集合只在本卡内构造，多卡每卡八条并不等于单卡三十二条，因为每条样本看到的负样本不同。把梯度分母乘对，不能补回缺失的交互项。需要全局特征交换或重新定义目标，再讨论通信与梯度传播。系统层的“同一全局批”不能替代对前向数学定义的检查。

浮点加法非结合，即使所有数学条件成立，规约顺序不同也可能产生小差异。先用双精度 CPU 小例子和容差比较验证代数，再在真实精度下判断误差是否符合数值预期。位级一致是更强目标，可能需要限制算法与规约顺序；不能因为两个结果不完全相同就断言并行归约错误，也不能忽略系统性的尺度差异。

[PyTorch DDP 官方接口](https://docs.pytorch.org/docs/2.10/generated/torch.nn.parallel.DistributedDataParallel.html)应作为具体行为的依据；自定义通信钩子、特殊参与模式或其他框架可能改变缩放语义。本章推导使用“最终等权平均梯度”的明确假设，迁移到任何实现前都应先验证该假设。

## 5. 集合通信、反向重叠与故障协议

<a id="sec-5-1"></a>

<a id="gpu-detail-17"></a>

### 5.1 数据并行的全局批大小与通信代价

梯度聚合可以用不同集合通信实现。All-reduce 让各参与者获得规约结果；reduce-scatter 让各参与者获得结果的不同片段；all-gather 交换片段得到完整集合。它们不是同义词，容量与数据所有权不同。普通副本数据并行需要最终各副本形成一致更新；分片方案可能只让某个进程负责一段优化器状态，因而采用不同通信组合。

一个理想环形 all-reduce 可分为规约分散和全收集两阶段，每个阶段有 $p-1$ 步，每步传输总消息的 $1/p$。若梯度总字节为 $G$，每步启动成本为 $\alpha$、有效链路带宽为 $\beta$，粗略通信时间为 $2(p-1)\alpha+2(p-1)G/(p\beta)$。这是特定算法与理想均衡链路的模型，不是所有拓扑的实际时延。

模型揭示两个方向：大消息由带宽项主导，小消息由启动项主导。把梯度拆成无数小消息，虽然可能更早发送，却增加启动成本；合成一个大消息又可能等到反向全部结束才通信。分桶是在启动摊销和提早重叠之间选择。桶大小的最佳值依模型层次、反向就绪顺序、链路与设备资源竞争而变。

反向重叠意味着某些层的梯度已经就绪时开始通信，同时继续计算其他层。可隐藏的时间受依赖和资源限制：最后就绪的桶通常有无法隐藏的通信尾部；通信内核和反向也可能争用设备带宽。把全部反向时间与全部通信时间直接取最大值，是理想下界，需要进一步验证实际关键路径。

<a id="gpu-detail-18"></a>

### 5.2 所有进程必须对同一通信序列达成一致

集合通信是群体协议。若一部分进程进入第一个梯度归约，另一部分因本地分支跳过它，后续调用可能不匹配而等待或报错。数据相关控制流、某卡损失异常后提前返回、不同卡用不同次数的累积，都会破坏一致参与。不能把分布式训练当成若干互不相关的单卡循环，只在末尾加一次平均。

本地遇到全掩码批、坏样本或非有限损失时，应先通过共同协议决定如何继续。例如对错误标志做全局规约，全部进程一致跳过该优化步，并确保必要的通信与状态处理一致。具体框架对未使用参数和不均匀输入有专门机制，但使用它们仍需要理解其假设，不能用无限等待替代错误处理。

故障检测也不是精确证明。超时可能来自进程崩溃、网络故障或某个进程极慢；设置很短会误判，设置很长会延迟恢复。应让日志带有运行身份、进程编号、步骤和通信阶段，便于区分“某卡没进入调用”与“所有卡都进入但链路慢”。错误消息只是观察点，真正根因可能在更早的数据加载阶段。

恢复通常回到最近一致检查点，而不是从某个幸存进程的当前参数继续。因为部分进程可能完成了更新、部分尚未完成，副本已不再代表同一逻辑步。弹性改变设备数还会改变分片、采样和全局批设计，需要重新定义预算与恢复映射。高可用机制不能自动保证原训练轨迹逐步不变。

<a id="gpu-detail-19"></a>

### 5.3 评估指标也需要全局可合并统计

准确率可以累计正确数与样本数，再相除；均方误差可以累计误差平方和与权重和。直接平均各卡指标，只有各卡有效分母相同时才等价。分布式采样器若为整齐分配重复了验证样本，还会改变样本权重，必须避免重复或按唯一身份去重，而不是仅把总数除以设备数。

不是所有指标都能用几个局部均值合并。全局 AUC 依赖跨卡样本排序，平均局部 AUC 一般不等于全局 AUC；分位数也不能简单平均。可以收集所需预测与标签，或者采用有明确误差界的分布式近似摘要。选择聚合方法要从指标定义推导，不能从“所有指标都是一个数”推断同样规约有效。

日志记录也可能触发同步和主机传输。每步把设备标量取回主机，可能把原先异步流水线变成同步路径。应在不影响诊断的前提下批量记录或减少频率，并把日志开销纳入真实端到端性能。减少日志若掩盖错误和不可复现，也不是无代价收益，需要在可观测性与成本之间做明确选择。

<a id="gpu-detail-20"></a>

## 6. 容量扩展：重算、低精度、分片与卸载

<a id="gpu-detail-21"></a>

### 6.1 激活重算改变的是存储时间表

反向传播需要某些前向中间量。常规做法保存它们，重算则只保存部分边界，在反向需要时重新执行一段前向。它主要减少激活驻留，用额外计算和可能的状态管理换容量。参数与优化器若是主项，单靠重算不会解决根本限制；先建立账本，再决定是否适合。

对一条含 $L$ 个等大层的理想顺序链，按每段 $k$ 层设边界，粗略需要保存约 $L/k$ 个边界以及反向重算时最多约 $k$ 层的局部激活。空间主项形如 $A(L/k+k)$，在 $k\approx\sqrt L$ 时达到该简化模型的折中。真实网络有跳连、不同层大小和算子工作空间，不能把这个平方根关系当任意模型的精确公式。

重算必须复现足以得到正确梯度的前向行为。随机层状态、可变缓冲、计数器和外部副作用都可能破坏等价。若重算时再次更新某个运行统计，就可能把原本一次前向的状态变化执行两次。框架检查点接口对随机状态和不同模式有具体规定，应按[官方文档](https://docs.pytorch.org/docs/2.10/checkpoint.html)核对，而不是假定所有函数都可透明重跑。

所谓检查点还可能指持久化恢复文件，与激活检查点是两个不同机制。前者把模型与优化器等状态写入存储以应对中断，后者在一次训练步骤内部重排计算与存储。二者都涉及时间和空间交换，却解决不同问题。讨论系统配置时用“激活重算”和“恢复检查点”区分，可以减少误解。

<a id="gpu-detail-22"></a>

### 6.2 低精度要分清存储、计算与累加

参数存储类型、乘法输入类型、累加类型、梯度类型和优化器状态类型可以不同。说“用了半精度”不足以推断每参数字节，也不足以判断数值稳定性。某些算子在较高精度累加，某些状态仍保持高精度，部分敏感操作可能需要更高精度路径。性能与误差应按实际配置记录。

较小指数范围可能产生溢出或下溢；损失缩放试图让梯度落入更合适范围，但不能修复前向已经溢出的值，也不能增加低精度尾数的相对精度。动态缩放可能跳过某些更新，因此训练样本已被读取但优化步未推进。比较达到某个质量的时间时，应记录成功更新数和溢出行为，不能只统计循环次数。

不同数值格式的指数与尾数折中不同，不能统一说“位数相同所以稳定性相同”。量化还可能引入尺度、零点和反量化成本。训练、推理、优化器状态压缩又有不同误差机制。系统层应把字节收益、支持算子和质量验证连在一起讨论，不把理论字节减半等同于端到端时间减半。

<a id="gpu-detail-23"></a>

### 6.3 分片与模型并行把哪一项分出去

普通数据并行复制参数及大部分训练状态，设备增加后单卡持久状态不自动除以设备数。优化器状态分片只分摊优化器项；进一步分片梯度和参数可以继续省容量，却需要在相应阶段交换或重建数据。峰值要计入临时聚合的完整参数、通信缓冲和预取，不是把总账本简单除以 $p$。

张量并行拆分某层运算，往往需要层内通信；流水线并行按层段分配设备，需要调度微批并承受流水线气泡。前者的通信频率与算子结构有关，后者的负载均衡与微批数有关。它们既可为容量服务，也可为吞吐服务，但不是普通数据并行的不同名字。实际大模型系统可能组合多种并行，必须分别描述维度与所有权。

卸载把状态迁移到主机或其他存储，容量受益取决于搬运是否能与计算重叠。若每步都要穿过低带宽链路搬运大量状态，训练可能由传输主导。应比较总字节与可用带宽下界，提前判断是否有可行窗口。容量可行是第一道门槛，达到质量所需时间和稳定恢复是后续门槛，不能只看“终于能启动”。

<a id="gpu-detail-24"></a>

### 6.4 非线性操作的顺序：裁剪、缩放与跳步

梯度的线性求和可以分布执行，但梯度裁剪是非线性的，先在各卡分别裁剪再平均，通常不等于先求全局目标梯度再裁剪。设两卡标量梯度分别为一百与负九十，平均为五；阈值十时先全局平均不触发裁剪，局部分别裁剪后平均却为零。两个实现不仅数值不同，还可能把本来有效的更新方向完全抹去。选择哪种规则应由算法定义决定，不能当成通信实现细节。

全局范数的“全局”也容易歧义。副本数据并行中每卡若已持有完整一致梯度，单卡对全部参数计算范数即可得到目标范数，无需再按设备数重复求和。参数分片时，每卡只有一部分梯度，才需要把各分片的平方和合并后开方。若把完整副本的范数平方再跨卡相加，会额外乘上设备数，导致阈值被无意改变。

混合精度损失缩放与裁剪的顺序同样重要。若反向得到的是放大后的梯度，应该先恢复真实目标尺度，再计算目标规则中的范数；否则固定阈值实际随缩放因子变化。累计窗口中不同微批若使用不一致缩放，还需要证明它们能在共同尺度下相加。实际框架通常提供既定流程，使用者仍应理解其每一步处理的是哪一种梯度。

非有限梯度的跳步必须在相关进程间一致。如果部分副本更新、部分副本跳过，参数立即分叉，下一步再平均梯度也不能自动修复，因为各卡已在不同参数点计算。应将溢出或错误判定纳入全局一致协议，同时处理缩放器、优化器步数、学习率调度与日志计数。某个进程打印“跳过一步”不代表整组副本已经保持一致。

这也解释为何单看损失曲线不足以验证训练系统：分母错可能只是改变有效学习率，局部裁剪可能悄悄改变方向，跳步不同步可能逐步产生偏差。可以在小任务记录每个阶段的梯度范数、参数摘要和成功更新计数，先检查一致性，再减少日志以控制成本。诊断信息应围绕算法状态，而不是只围绕设备利用率。

## 7. 实验可比性与 CPU 验证

<a id="gpu-detail-26"></a>

### 7.1 实验一：显存账本与 Roofline 估算

下面不申请 GPU 显存，而是按明确假设计算字节。第一项采用全精度参数、梯度和两份优化器状态；第二项只把优化器状态均分到四个设备，仍保留完整参数与梯度。激活和临时空间相同，说明局部峰值不会简单变为四分之一。所有数值都是模型输入，不对应特定产品规格。

```python
def memory_ledger(n, batch, width, layers, shards=1):
    param = 4 * n
    grad = 4 * n
    optimizer = 8 * n / shards
    activation = 4 * batch * width * layers
    temporary = 32 * 1024**2
    return {"parameter": param, "gradient": grad, "optimizer": optimizer,
            "activation": activation, "temporary": temporary}

one = memory_ledger(10_000_000, 16, 512, 24)
four = memory_ledger(10_000_000, 16, 512, 24, shards=4)
assert one["parameter"] == four["parameter"]
assert one["optimizer"] == 4 * four["optimizer"]
assert sum(four.values()) > sum(one.values()) / 4
print("MiB full / optimizer-sharded:",
      round(sum(one.values())/1024**2, 3),
      round(sum(four.values())/1024**2, 3))

m = n = k = 256
flops = 2 * m * n * k
bytes_min = 4 * (m*k + k*n + m*n)
intensity = flops / bytes_min
peak = 10e12
bandwidth = 100e9
bound_seconds = max(flops/peak, bytes_min/bandwidth)
assert intensity < peak / bandwidth
print("intensity, lower-bound seconds:", intensity, bound_seconds)
```

输出账本约为一百八十五点三三八与一百二十八点一一七 MiB；理想算术强度约四十二点六七操作每字节，低于假设硬件的转折点一百，带宽下界更紧。这并不说明真实矩阵乘一定带宽受限，因为实际硬件、缓存层级和算子实现可能不同。实验的验收是单位一致、项分得清、模型结论与输入假设匹配。

<a id="gpu-detail-27"></a>

### 7.2 实验二：不等本地数量的梯度归约

用一维线性模型和平方损失，分别计算全批梯度、局部均值的错误等权平均、按全局分母缩放后的正确平均。所有运算采用 CPU 双精度，不启动通信。它能验证应发送的梯度数值，但不能证明真实多进程程序没有死锁、采样重复或设备映射错误，后者需要在实际环境另做协议测试。

```python
import torch
torch.set_default_dtype(torch.float64)
x = torch.tensor([1., 2., 3., 4., 5.])
y = torch.tensor([0., 1., 0., 1., 0.])
splits = [slice(0, 2), slice(2, 5)]
world = len(splits)

def gradient(xs, ys, scale, reduction):
    w = torch.tensor(0.7, requires_grad=True)
    values = (w*xs - ys).square()
    loss = values.sum() if reduction == "sum" else values.mean()
    return torch.autograd.grad(scale*loss, w)[0]

reference = gradient(x, y, 1., "mean")
wrong = sum(gradient(x[s], y[s], 1., "mean") for s in splits)/world
correct = sum(gradient(x[s], y[s], world/len(x), "sum")
              for s in splits)/world
assert not torch.allclose(wrong, reference)
torch.testing.assert_close(correct, reference)
print("full, equal-local-means, corrected:",
      reference.item(), wrong.item(), correct.item())
```

参考梯度为十三，错误平均约十一点零八三，正确缩放仍为十三。数量较少的第一卡在错误版本里被赋予过大权重。误差不是随机浮点噪声，而是目标函数改变。手算可得全局梯度为 $2(0.7\sum x_i^2-\sum x_iy_i)/5=2(38.5-6)/5=13$，因此实验具有独立解析参照。

### 7.3 实验三：微批分母、正则项和一次更新边界

下面让三个微批大小分别为一、三、二，证明累加损失和再除总数等于全批，而简单平均微批均值一般错误。正则项只加一次。最后验证若把微批每次更新参数，结果会不同，因为后续微批的梯度在新参数上计算，已经不再是同一个大批梯度。

```python
import torch
torch.set_default_dtype(torch.float64)
x = torch.tensor([1., 2., 3., 4., 5., 6.])
y = torch.tensor([0., 1., 1., 0., 1., 0.])
chunks = [slice(0, 1), slice(1, 4), slice(4, 6)]
lam = 0.2

def full_grad():
    w = torch.tensor(0.4, requires_grad=True)
    loss = (w*x-y).square().mean() + lam*w.square()/2
    return torch.autograd.grad(loss, w)[0]

w = torch.tensor(0.4, requires_grad=True)
for s in chunks:
    ((w*x[s]-y[s]).square().sum()/len(x)).backward()
(lam*w.square()/2).backward()
reference = full_grad()
torch.testing.assert_close(w.grad, reference)
v = torch.tensor(0.4, requires_grad=True)
wrong = sum((v*x[s]-y[s]).square().mean()
            for s in chunks)/len(chunks) + lam*v.square()/2
wrong_grad = torch.autograd.grad(wrong, v)[0]
assert not torch.allclose(wrong_grad, reference)
lr = 0.01
large_update = 0.4 - lr*reference.item()
sequential = 0.4
for s in chunks:
    grad = (2*x[s]*(sequential*x[s]-y[s])).sum().item()/len(x)
    grad += lam*sequential/len(chunks)
    sequential -= lr*grad
assert abs(sequential-large_update) > 1e-5
print("gradient correct / wrong:", w.grad.item(), wrong_grad.item())
print("one large / three sequential updates:", large_update, sequential)
```

本实验把目标的归一化单元和优化器更新边界显式分开。累积时不更新参数，因此各微批梯度在同一参数点相加；连续小步训练则在不同点求梯度。连续分支保留同一总样本分母，并把同一正则项均分到各次贡献；若参数冻结，其贡献总和等于大批参考，差异由提前更新导致的求导点变化引入。本例只是展示边界改变足以破坏等价，不把它作为对某个训练方案的质量判断。

### 7.4 实验四：通信模型和重算梯度一致性

先计算理想环形模型，观察消息小到一定程度后启动项不可忽略。再用无随机层、无可变缓冲的简单网络，对照常规前向与激活重算的梯度。这里验证的是相同数学函数的梯度，不测 GPU 显存节省；CPU 分配器统计也不能拿来代替设备峰值。

```python
import torch
from torch.utils.checkpoint import checkpoint

def ring_seconds(p, size_bytes, latency, bandwidth):
    if p == 1:
        return 0.0
    return 2*(p-1)*latency + 2*(p-1)/p*size_bytes/bandwidth

assert ring_seconds(1, 1024, 1e-5, 1e9) == 0
small = ring_seconds(4, 1024, 1e-5, 1e9)
large = ring_seconds(4, 64*1024**2, 1e-5, 1e9)
assert large > small > 0
print("ring model seconds small / large:", small, large)

torch.manual_seed(31)
net = torch.nn.Sequential(torch.nn.Linear(4, 8),
                          torch.nn.Tanh(), torch.nn.Linear(8, 2)).double()
x = torch.randn(5, 4, dtype=torch.float64, requires_grad=True)
params = tuple(net.parameters())
ordinary = net(x).square().mean()
g1 = torch.autograd.grad(ordinary, (x,) + params)
recomputed = checkpoint(net, x, use_reentrant=False).square().mean()
g2 = torch.autograd.grad(recomputed, (x,) + params)
for left, right in zip(g1, g2):
    torch.testing.assert_close(left, right)
print("checkpoint gradients matched:", len(g1))
```

四个设备、一千零二十四字节消息的模型结果约六十一点五四微秒，其中绝大部分来自六次启动；六十四 MiB 则约零点一秒，带宽项占主导。重算实验核对一个输入梯度与四个参数梯度，共五项。若把网络换成含随机状态或副作用的模块，应先明确重算如何恢复状态，再使用同样的一致性检验。

## 8. 进阶练习与详细解析

<a id="gpu-detail-31"></a>

### 8.1 十八个问题：显存、归约与故障边界

**题一：** 某算子需要十亿次操作，至少搬运两亿字节，设备可持续能力为每秒十万亿操作、每秒一千亿字节，哪个下界更紧？**解析：** 计算下界为零点一毫秒，搬运下界为二毫秒，理想带宽界更紧。即使计算能力翻倍，该带宽下界不变。这里说的是选定内存层级上的必要时间，不包含启动、同步与低并行度，真实时间可以更大。若两亿字节只是理想最小量，应避免把结论写成已测得的硬件瓶颈。

**题二：** 参数一亿个，参数和梯度各四字节、优化器两份四字节状态，持久状态有多大？**解析：** 共十六亿字节，约一点四九 GiB，尚未加入激活、临时空间、通信桶、分配器保留但未使用的额外空间，以及框架分配器之外的占用；不能把完整 reserved 重复相加。若只按权重文件四亿字节估计训练容量，会少算四倍左右的持久状态。这个倍数来自题设而非通用法则，换成无动量优化器、冻结部分参数或额外主参数副本，应重新逐项计算。

**题三：** 上题在四个设备上做普通副本数据并行，单卡持久状态是否变成四亿字节？**解析：** 不会，普通副本数据并行仍让每卡保留完整状态，容量不会自动四等分。若只把八亿字节优化器状态均分，单卡为参数四亿、梯度四亿、优化器两亿，共十亿字节，还没有激活等项。讨论分片收益时必须指出分的是哪一项，以及临时聚合是否制造新峰值。

**题四：** 每批传输八毫秒、计算二十毫秒，十批双缓冲理想总时间是多少？**解析：** 首批二十八毫秒，后续每二十毫秒完成一批，总计二百零八毫秒；串行为二百八十毫秒。结果要求独立资源、正确依赖和足够缓冲。如果传输与计算争用带宽或复制无法重叠，实际收益会更小。不能因为主机调用立即返回，就把传输时间视为零，也不能遗漏最后一批的完成等待。

**题五：** 两流中先生产后消费，主机代码先提交生产就安全了吗？**解析：** 不一定。跨流需明确依赖，主机提交次序不自动建立全部设备执行顺序。还应保证源存储在消费者结束前不被回收或复用，数据完成条件与存储生命周期分别核对。一个最小正确性测试应使用容易检查的输入，重复运行并启用适当检查工具，再测性能；偶尔得到正确结果不是依赖已经充分表达的证明。

**题六：** 两卡有效数量为二与六，局部平均梯度为一与五，全局平均应为多少？**解析：** 权重为数量，故结果 $(2\times1+6\times5)/8=4$，等权卡平均为三。若框架最终平均两卡梯度，可让本地均值分别乘零点五与一点五，再平均得到四。这里有效数量必须对应目标单位：按样本损失用样本数，按 token 损失用有效 token 数，不能随意互换。

**题七：** 三卡中一张卡全是掩码位置，能否让该进程直接跳过反向？**解析：** 不能仅凭本地决定。其他进程可能正在等待相同通信序列。应让所有进程一致确定全局分母与参与协议；本地损失和可以为零，但局部均值没有定义。实现需保证零梯度与图参与满足框架要求。若全局分母也为零，全部进程统一跳过更新，并一致处理调度与日志，避免状态分叉。

**题八：** 两个微批有效数量为一与九，各自平均后再除以二，等价全批均值吗？**解析：** 一般不等价，它给两个微批各一半权重，单个第一批样本相当于第二批每样本九倍权重。应累计各微批损失和并除以总数十，或用数量占比缩放局部均值。梯度裁剪要在恢复目标尺度后进行，否则阈值对应另一种尺度，可能把原本正确的线性缩放变成不同非线性更新。

**题九：** 累积四个微批，每次都加完整的 $\lambda R$，会发生什么？**解析：** 如果数据项按窗口正确累计而正则未缩放，正则梯度累加成四倍。可只在窗口加入一次，或每次加四分之一，确保目标系数为 $\lambda$。解耦权重衰减则由优化步边界控制，不能直接把它当作同一损失项来处理。应分别检查数据归约、显式正则与优化器更新三条路径。

**题十：** 相同全局批和归约系数，为什么局部 BatchNorm 仍可能不同？**解析：** 前向使用的均值和方差来自本地子批，而单卡大批使用全局统计，输出与梯度函数已经不同。数值尺度修正不能恢复缺失的跨卡统计。同步统计机制可以解决特定问题，但仍要核对训练与评估模式、运行状态和通信范围；对比学习的负样本集合等其他跨样本操作也有类似但不完全相同的依赖。

**题十一：** 四卡梯度分成一千个小桶是否一定比十个大桶快？**解析：** 不一定。小桶更早就绪，可能增加重叠，却增加集合通信启动与调度次数。理想环形模型中的时延项会按消息数累加。大桶减少启动，但最后桶可能延后。应根据真实梯度就绪时间和通信尾部测量，比较端到端窗口，而不是只看总字节相同就认为性能相同。

**题十二：** 为什么平均各卡 AUC 通常错误？**解析：** AUC 依赖全局正负样本的相对排序，跨卡正负对在局部指标里根本没有计算。两个局部 AUC 之平均缺少这些交互信息，无法通过按样本量加权普遍恢复。需要合并预测与标签，或使用明确近似性质的全局摘要。能否合并应从统计定义推导，准确率可合并并不意味着所有指标都可合并。

**题十三：** 激活重算让理论激活减半，为什么峰值显存只下降一点？**解析：** 峰值可能由参数、优化器或临时工作空间主导，激活本来只占小部分；也可能重算阶段同时产生较大临时块。先分解原峰值的生命周期，再预测可消除的部分。若设备分配器继续保留已释放块，外部占用工具也未必立即下降，应区分活跃分配与保留量，不能据此断言重算无效。

**题十四：** 低精度存储使权重字节减半，训练一定快一倍吗？**解析：** 不一定。工作可能受启动、通信或解码限制；敏感算子仍用高精度；转换与缩放产生额外成本；优化器状态也可能没有减半。需要在相同质量要求下测达到目标的时间，并记录成功更新、溢出和误差。理论权重字节是资源账本的一项，不是端到端速度的充分预测。

**题十五：** 一个进程发现坏样本便直接继续下一批，其他进程会怎样？**解析：** 它们可能进入当前步的集合通信，而该进程已经前进到下一步，产生通信顺序不一致。应先统一错误标志，再让所有进程按同一协议重试或跳过。日志包含进程编号和逻辑步，可帮助定位第一个偏离点。单纯延长超时只推迟暴露问题，无法修复协议分歧。

**题十六：** 恢复时设备数从四变八，只重载参数是否足够？**解析：** 不足以恢复相同训练状态。优化器分片需要重新映射，数据采样和全局批可能变化，随机状态与调度进度也要定义。若目标是继续有效训练而非逐步复现，可以制定新的批量与预算规则，但应记录这一变化。恢复文件还必须来自一致提交点，不能混合不同步骤的参数与优化器状态。

### 8.2 边界追问：同全局 batch 是否保证同轨迹

**题十七：** 四设备小批加梯度累积与单设备大批，在什么条件下可以比较一次更新？**解析：** 至少要初始参数和优化器状态相同，前向目标可按样本拆分，数据身份与权重相同，随机性满足约定，所有梯度在同一参数点计算，归约正确，正则和裁剪位置一致，优化器只更新一次。满足数学条件后，浮点顺序仍可造成容差内差异；要追求位级一致还需更严格的算法和规约控制。

条件不满足时，应指出具体改变。例如局部 BatchNorm 改变前向，微批内负样本改变目标，连续小步更新改变求导点，简单平均微批改变权重。把差异统称为“多卡不稳定”会丢失诊断信息。最有力的验证是先建立一个无随机、无跨样本操作的解析小例子，逐步加入机制，每次检查第一次产生差异的位置。

**题十八：** 混合精度训练发现非有限梯度并跳过参数更新，本轮能否仍按一次成功优化步推进学习率、指数移动平均和训练预算？**解析：** 先区分数据已经消费、反向已经尝试和参数实际更新三个计数。若调度器与指数移动平均按成功更新定义，跳步时就不应机械推进，否则学习率轨迹与平均权重衰减次数会脱离实际优化步；若预算明确按已消费样本或尝试次数定义，则相应计数可以推进，但必须独立记录跳步比例。动态缩放状态通常仍需根据溢出调整，不能因为参数未更新就把全部训练状态冻结。多进程还要保证各参与者遵循一致的有限性和更新协议，不能让部分副本更新、部分副本跳过。恢复检查点应一起保存参数、优化器、缩放器及各类进度身份；仅加载模型权重不能重建原来的跳步历史。验证可人为制造一次溢出，逐项核对参数是否变化、缩放状态是否变化、成功步与尝试步是否分离，再恢复运行比较后续调度。

## 9. 综合研究：把局部优化放回端到端系统

<a id="sec-7-1"></a>

<a id="gpu-detail-34"></a>

### 9.1 综合练习：局部提速能否推算整体提速

**综合题：** 原系统八成时间用于可加速计算，计算快四倍，其他不变，整体理想加速是多少？**解析：** 归一化新时间为 $0.2+0.8/4=0.4$，整体二点五倍。若计算快四倍还引入占原总时间十分之一的通信，新时间为零点五，加速变为两倍。若通信与部分计算重叠，不能机械把它全部相加，应画依赖图求关键路径，再实测完整窗口。

这个练习使用串行时间分解，不能未经说明套用到本来就重叠的流水线。对于加载、传输、计算并行的系统，局部计算变快后可能立刻暴露加载瓶颈。应分别说明是阶段服务工作量还是不可重叠的墙钟占比。数学公式只有在分解的语义成立时才有预测力，漂亮的百分比本身不构成系统模型。

<a id="gpu-detail-35"></a>

### 9.2 从小例子到真实分布式实验的阶梯

第一层验证数学目标：用本章 CPU 双精度实验检查全局分母、微批权重、正则项与更新边界。第二层验证数据：固定身份序列，记录各进程收到哪些样本和有效计数，确认没有意外重复或遗漏。第三层验证协议：在最小多进程环境检查通信顺序、错误标志与一致退出，故意注入一条全掩码或坏记录，观察是否按设计处理。

第四层才是性能：用代表性形状与精度预热，在窗口边界确保所有设备完成，记录真实样本吞吐、设备数、主机线程、网络拓扑、峰值内存和通信尾部。分别做强扩展与弱扩展，保持相关预算可比。若只有设备端算子加速而端到端没有改善，应回到加载、传输、同步和保存路径解释，而不是删除慢阶段后报告新数字。

第五层验证恢复：在已知步骤主动中断，恢复后检查参数与优化器状态、数据消费位置、随机任务键和全局预算。先在确定性小任务验证，再扩展到大任务。真正的故障通常发生在最不方便的时间，一套从未演练过的检查点流程只是一种希望。恢复不一定要逐位相同，但允许差异和正确性标准应事先定义。

每一层失败都应停止向更大规模扩展并定位原因，因为规模增加会把简单错误变成昂贵、难复现的问题。这个阶梯不是额外手续，而是把目标、数据、协议和性能分开，使每次实验能回答一个明确问题。五层都混在一次大训练里，最终即使结果好，也很难知道它为什么好、是否可重复。

<a id="gpu-detail-36"></a>

### 9.3 研究方向：通信、容量与统计效率的联合优化

一个更有价值的研究目标是“在固定质量约束下缩短训练时间”，而不是单独最大化设备利用率。增加全局批可以提高吞吐，却可能需要更多样本达到相同质量；分片可以容纳更大模型，却可能增大通信；重算可以支持更长序列，却增加每步计算。系统效率与统计效率需要共同计入，不能把每秒样本数直接当最终学习收益。

可把一次完整实验写成三份账：资源账记录操作、字节、峰值与同步；统计账记录样本、有效权重、优化步与质量；恢复账记录提交点、状态所有权与可重放路径。某个方案若在资源账上更优、统计账上却改变目标，就不能归因为同任务系统加速；若恢复账缺失，则长期任务的实际完成时间可能被故障重跑吞掉。

还可研究通信压缩与局部更新，但它们可能改变梯度估计，不再只是精确归约的高效实现。需要分析误差反馈、偏差、陈旧度与收敛条件，再评估实际带宽收益。压缩后字节减少，却增加编码解码和额外状态；弱网络下可能有利，高带宽小模型下则可能不值。研究结论应给出有效区域与反例，而不是把某种技术写成普遍推荐。

调度也是可研究对象。若层的反向就绪时间不同，通信桶可以按依赖更合理地组织；若设备速度不同，静态均分样本可能造成慢设备拖尾。动态分配能改善负载，却改变各进程分母与数据恢复协议，需要重新证明归约正确。系统里的优化常常把一个简单假设换成更复杂的协议，收益要大到足以抵偿这种复杂性。

<a id="gpu-detail-37"></a>

### 9.4 阅读本章后应能独立回答的问题

看到显存不足，能够先指出参数、梯度、优化器、激活和临时块谁占主导，再选择减少哪一项。看到多卡吞吐差，能够区分全局批变化、链路带宽、消息启动、反向尾部、数据供给与进程分歧。看到“等价大批”，能够追问前向交互、有效分母、正则、裁剪和更新边界，而不是只核对一个乘法。

看到某个异步接口，能够追问结果何时可消费、源存储何时可复用、谁建立跨流依赖。看到分片后理论容量，能够追问临时全聚合和通信缓冲的峰值。看到硬件峰值数字，能够使用算术强度与服务下界解释它与任务表现的距离。这些追问帮助你从框架参数使用者走向能够验证系统设计的人。

本章的 CPU 实验只是论证链中的一环。它们已经验证代数和简化模型，但 GPU 架构、网络拓扑、驱动、算子实现和真实故障仍需实际环境证据。把“证明了什么”与“还没有测什么”清楚分开，既能避免过度结论，也能让后续实验有明确方向。下一章将继续讨论如何设计基准、辨别瓶颈和形成可信性能证据。
