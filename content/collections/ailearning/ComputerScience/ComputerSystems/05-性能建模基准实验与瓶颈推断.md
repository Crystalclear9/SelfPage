# 第 5 章 性能建模、基准实验与瓶颈推断

[主题目录](README.md) · [分类目录](../README.md) · [总目录](../../README.md) · [上一章](04-GPU并行显存与分布式入门.md)

优化一个机器学习程序，最容易犯的错误是先看到一个显眼的耗时，再急于更换实现。本章建立另一种做法：先确定要优化的目标，构造可以被实验否定的性能模型，再用公平测量判断瓶颈究竟来自计算、内存、排队、同步还是任务定义本身。我们将从单位和计时边界开始，推导整体加速与流水线模型，设计完整的基准协议，并分析训练、批处理和在线服务中不同的性能目标。

先修内容是前四章的存储层次、并发、数据流水线和设备执行。这里不要求实际拥有 GPU；核心算例和两个可运行实验只使用 Python 标准库与 NumPy。涉及设备异步执行的部分会说明计时原则，而不把未运行的设备专用代码包装为已经验证的实验。

## 1. 先定义被优化的工作，而不是先选择一个计时器

<a id="performance-section-1-1"></a>
### 1.1 性能指标应当对应任务价值

离线训练关心达到指定质量需要多少时间、资源和费用；批处理关心给定时间内处理多少有效样本；交互服务还关心用户等待多久以及最慢的一部分请求有多慢。一个实现每秒处理更多输入，却需要更多训练步才能达到同样质量，不一定更好。反过来，单步更慢但收敛更快的算法，可能缩短真正的交付时间。

因此应先声明工作单位。样本每秒、有效词元每秒、更新每秒和请求每秒不是可互换的数字。不同长度序列按条计数可能高估短序列实现的效率；包含填充位置的词元吞吐又可能奖励无效计算。评价时最好同时保留原始处理量和与任务有关的有效处理量，解释分母与分子的具体含义。

训练中的一个 epoch 也不是固定成本单位。数据增强、重复采样、动态长度和梯度累积会改变每轮实际运算。若比较两套系统，应说明样本集合、有效更新次数、精度策略和停止准则。只固定一个看起来相同的轮数，却改变了数据量或质量目标，得到的性能排名无法回答原来的问题。

<a id="performance-detail-1"></a>

### 1.2 延迟与吞吐之间没有一个永远成立的倒数关系

对于严格串行、没有重叠的单请求处理，单位请求平均服务时间的倒数对应理想吞吐。但在并发或批处理系统中，多个请求同时进行，用户延迟包含排队时间，整体吞吐由资源和调度共同限制，两者不能简单互取倒数。

例如一个批次包含三十二个样本，执行时间为八毫秒，批内单样本摊销执行成本是四分之一毫秒；但每个样本要等到整个批次完成，至少仍经历八毫秒的执行等待，还可能额外等待凑批。把摊销成本写成用户请求延迟，就会给出一个物理上不成立的数字。

如果系统每秒完成一千个请求，平均有二十个请求处于系统中，那么在适合使用长期流量守恒关系的稳定条件下，平均停留时间应为二十毫秒。这里的请求数应包括等待和执行中的请求，进入率与离开率要在稳定区间一致；持续过载、请求大量丢弃或只截取瞬态窗口时，不能未经说明照搬这个计算。

<a id="performance-detail-2"></a>

### 1.3 明确计时边界、冷启动与质量约束

一次完整预测可能包括输入解析、数据复制、模型执行、后处理和序列化。只测模型核心可以帮助定位算子瓶颈，但不能直接当作端到端用户体验。反过来，只测端到端也可能掩盖局部变化，所以两种边界都应保留，名称必须清楚。

首次调用可能包含模块导入、内存分配、动态编译、算法选择和缓存构建。预热后的稳定性能与冷启动性能回答不同问题。对长期训练，稳态通常很重要；对频繁启停的短任务，初始化可能占主要部分。不能因为冷启动很慢就把它从所有报告中删除，也不能拿一次初始化时间代表持续服务速度。

优化前还必须固定正确性标准。若把双精度改为低精度、缩小图像或减少生成长度，工作本身已经改变。允许这种变化时，应报告质量与性能的权衡曲线；若任务要求同等结果，则先检查误差、指标和输出契约，再接受速度比较。性能优化是受约束的问题，约束不清楚时，任何“快了几倍”的结论都不完整。

<a id="visual-05-concept"></a>

### 图解：局部加速受串行部分限制

![局部加速受串行部分限制](images/05-concept.svg)

上半部把单个数字推广为一族可复算曲线。设基线总时间为一，其中可被局部优化的比例为 $`p`$，该部分加速 $`k`$ 倍；其他工作及任务量不变且各部分串行相加，则新时间为 $`1-p+\frac pk`$，整体加速为 $`S(k)=\frac1{1-p+\frac pk}`$。图上横轴为局部加速，纵轴为整体加速，两轴都采用对数刻度；读数看刻度值，不把屏幕上的等距离误当等量增加。

当 $`p=0.25,0.75,0.95`$ 时，即使局部成本趋零，整体上界也分别只有 $`\frac43,4,20`$。三条曲线从 $`k=1,S=1`$ 出发，之后的弯曲体现剩余成本逐渐主导。例如局部快十倍，$`p=0.25`$ 时整体约 1.29 倍，$`p=0.95`$ 时才约 6.90 倍；不能只看到同一个“十倍内核”就预期相同端到端收益。

下半部固定 $`p=0.25`$ 展开时间账本：原来 75 个单位的其他工作与 25 个单位的可优化工作，变为 75 加 2.5，总时间 77.5。局部节省了 22.5，却仍留下 75；进一步优化已经很小的部分，收益会饱和。这种固定工作量下的剩余约束来自 [Amdahl 的原始讨论](https://www3.cs.stonybrook.edu/~rezaul/Spring-2019/CSE613/reading/Amdahl-1967.pdf)，图中的具体曲线则由这里明确的模型计算。

比例 $`p`$ 应来自所研究基线的时间边界，不能直接用 GPU 利用率、代码行数或各阶段分别测量的比例代替。若阶段可以重叠，优化改变了关键路径；若引入搬运、同步、质量退化或任务规模变化，也不再只是把原来的 $`p`$ 除以 $`k`$。先用曲线提出上界和瓶颈假设，再回到同任务、同负载的端到端实测；本图不是处理器数量扩展或某台设备速度的实测结果。

<a id="sec-2"></a>
## 2. 用工作量、字节量与时间构造量纲一致的模型

<a id="performance-section-2-1"></a>
### 2.1 把三个不同的资源问题分开

计算吞吐描述每秒能执行多少算术操作，带宽描述每秒能搬运多少字节，容量描述最多能同时放下多少字节。它们分别回答算得多快、搬得多快和装不装得下。容量足够不说明带宽足够，理论算力高也不说明当前工作能够使用这些计算单元。

最基本的时间下界来自工作守恒。若需要 $`F`$ 次运算，持续计算吞吐上限为 $`P`$，计算时间至少为 $`\frac{F}{P}`$；若需要穿过某个存储边界搬运 $`Q`$ 字节，持续带宽上限为 $`B`$，搬运时间至少为 $`\frac{Q}{B}`$。即便两者能够充分重叠，完成时间仍不小于两者的最大值。

注意上限应当与所计工作一致。把某种低精度矩阵指令峰值用于估计普通双精度标量代码，或把设备内部带宽用于估计主机到设备拷贝，都会混淆资源边界。一个模型的数值再精确，只要单位对应错误，推断仍然无效。

<a id="performance-detail-3"></a>

### 2.2 算术强度与一个可复算的例子

定义某个指定存储边界上的算术强度 $`I=\frac{F}{Q}`$，单位是每字节运算数。由前面的时间下界，持续性能满足理想化上界

$$
\frac F T\le\min(P,BI).
$$

这就是常见的屋顶线视角：强度较低时带宽项较小，强度较高时才可能触及计算上限。它是一种限制模型，实际代码还可能被并行度、依赖链、指令调度和启动成本进一步限制，并不保证能够达到屋顶。

设设备持续带宽为每秒二百 GB（本例按十进制 $`1\,\mathrm{GB}=10^9`$ 字节），适用计算吞吐为每秒十万亿次运算。某工作需要两百亿次运算、搬运四十 GB，则强度为每字节二分之一次运算，带宽限制性能为每秒一千亿次运算；计算下界为两毫秒，搬运下界为二百毫秒。因此仅升级计算单元、维持同样带宽，模型预测的收益非常有限。

若通过融合把同样数学工作所需流量减少为十 GB，带宽下界变为五十毫秒，理想情况下有四倍改善空间。这个四倍来自流量模型，不是已经测出的加速。还要检查融合是否增加寄存器压力、是否改变数值顺序，以及真实实现是否确实减少了跨边界访问。

<a id="performance-detail-4"></a>

### 2.3 字节量要按实际边界计算

一个数组在源代码中被引用三次，不一定真的从主存读取三次，因为它可能留在缓存；一个表达式看起来只读取一次，也可能因缓存不足、布局不佳或重复调度产生额外流量。因此算术强度要明确是算法最小流量、估计流量还是计数器测得流量，不能把它们混作同一个量。

对于双精度逐元素运算 $`z=x+y`$，忽略缓存写策略和其他开销时，每个元素至少涉及两个八字节输入和一个八字节输出，而算术仅一次加法。矩阵乘法则能够复用输入块，使同一字节参与多次乘加。为什么两者在同一设备上的利用率差异很大，可以先从这种数据复用结构理解。

如果计算融合后不再产生中间数组，减少的是跨存储层次的读写和分配，但并不一定减少数学运算数。若重计算替代保存，则可能增加算术却减少内存压力。性能比较必须说明优化动的是哪个资源，而不是把所有变化都笼统叫作“计算更高效”。

<a id="visual-05-mechanism"></a>

### 图解：算术强度决定 Roofline 模型中的上限

![算术强度决定 Roofline 模型中的上限](images/05-mechanism.svg)

假设内存带宽为 20 GB/s、峰值算力为 100 GFLOP/s。带宽约束给出吞吐上限等于 20 乘算术强度，直到强度 5 时碰到算力上限。左侧提高数据复用可能有效，右侧则不能仅靠减少字节量突破峰值算力。

这是简化上界，不是保证达到的性能。延迟、并发不足、同步与实际带宽都可能让测量点落在折线之下，FLOP 和字节必须采用一致计数口径。

<a id="sec-3"></a>
## 3. 整体加速：从串行分解到关键路径

<a id="performance-section-3-1"></a>
### 3.1 完整推导局部优化对整体的影响

设原时间为 $`T`$，其中比例 $`p`$ 的部分可以加速 $`s`$ 倍，其他部分不变且没有新的开销。优化后时间为 $`T[(1-p)+\frac{p}{s}]`$，所以整体加速比是

$$
S=\frac1{(1-p)+\frac{p}{s}}.
$$

若 $`p=0.8`$、$`s=4`$，整体加速为二点五，而不是四。即便把该部分变得无限快，极限也只是 $`\frac{1}{(1-p)}=5`$。这个上限依赖“剩余时间不变”和“分解互不重叠”的假设，不能把它机械套到存在强重叠或资源竞争的时间线上。

若优化额外引入时间 $`H`$，分母还要加 $`\frac{H}{T}`$。例如把原来占八成的计算加速四倍，却新增原时间一成的通信，整体变为两倍。这样写出代价后，某个局部技巧为何没有带来预期收益就不再神秘：它既减少了一部分，又增加了另一部分。

<a id="performance-detail-5"></a>

### 3.2 加速比不能简单相乘

假设原程序三成是加载、六成是计算、一成是保存。第一项改进把加载加速两倍，第二项把计算加速三倍。最终时间为 $`0.15+0.2+0.1=0.45`$ 倍原时间，整体加速约二点二二倍，并不是六倍。若先后报告每次相对前一版本的加速比，其乘积可以回到最终相对原版的比值，但不能把两个各自相对原版、作用于不同部分的局部倍数直接相乘。

同样，优化后的瓶颈会迁移。原先计算占主导，计算加速后加载可能成为最大项；再投入资源加速计算，边际收益下降。性能工程应不断重新测量剩余时间分解，而不能因为第一次定位到某个瓶颈，就长期围绕它优化。

<a id="performance-detail-6"></a>

### 3.3 重叠执行时看依赖图的最长完成路径

如果数据复制与计算可以并行，单次完成时间不是把两者持续时间简单相加，而要分析前后依赖。一个任务必须等待所需输入，后续阶段必须等待它的输出；独立部分可以重叠。完成时间至少是依赖图中最长路径的持续时间，同时还受共享资源容量限制。

例如复制耗时四毫秒、计算耗时六毫秒，若对同一批次必须先复制后计算，该批次最少十毫秒；若多个批次通过双缓冲交叠，稳态批次间隔可能接近六毫秒，但第一个批次延迟仍约十毫秒。把稳态间隔作为单批延迟，或把各阶段持续时间总和作为稳态间隔，都会得出错误结果。

关键路径也不是一个固定的函数名。一处同步可能迫使本来独立的工作串行，一次共享锁可能让多个线程互相等待；去掉同步后，瓶颈又可能转向带宽。因此观察时间线和等待关系，往往比只看每个函数累计时间更能解释端到端行为。

<a id="performance-detail-7"></a>

### 3.4 完整算例：决定下一次优化应该投入哪里

某训练迭代串行耗时为数据准备十二毫秒、复制四毫秒、计算二十四毫秒、统计与保存十毫秒，总计五十毫秒。方案甲把计算加速两倍，新总计三十八毫秒；方案乙把统计保存减为两毫秒，新总计四十二毫秒。就单一改动而言，甲的收益较大，但若甲需要昂贵硬件、乙只需减少不必要的日志，成本效率可能不同。

若先实施甲，再实施乙，总计三十毫秒。此时计算十二毫秒和数据准备十二毫秒并列最大项。进一步把计算减半，整体只能从三十降到二十四毫秒；若数据流水线能与计算交叠，可能获得另一种收益，但必须新增依赖与资源假设重新建模。正确比较应把实现成本、正确性风险和持续运行成本一并列出，而不只追逐局部最快数字。

<a id="sec-4"></a>
## 4. 流水线、排队与批处理中的容量约束

<a id="performance-section-4-1"></a>
### 4.1 有限批次数下的流水线时间

考虑三个阶段，每阶段一次处理一个批次，耗时分别为 $`a,b,c`$；不同阶段有独立资源和足够缓冲，同一阶段不能同时处理两个批次。第一批需要 $`a+b+c`$ 才能完成，进入稳定状态后，完成间隔至少受最慢阶段限制。对于这些理想条件，处理 $`N`$ 批的完成时间为

$$
T_N=a+b+c+(N-1)\max(a,b,c).
$$

这里忽略了调度、缓冲争用和耗时波动。若阶段时间分别为四、七、三毫秒，处理一百批的时间为十四加九十九乘七，即七百零七毫秒。完全串行则为一千四百毫秒。加速比接近两倍而非三倍，因为最慢阶段需要七毫秒，资源并不完全均衡。

若只有两批，总时间为二十一毫秒，对比串行二十八毫秒，收益就小得多。因此小规模测试可能主要观察流水线填充与排空，而长时间运行主要观察稳定节拍。报告时必须说明批次数量，不能把某个很短窗口的加速结果外推到长期吞吐，也不能把稳态模型用于估计单个请求响应。

<a id="performance-detail-8"></a>

### 4.2 增加预取深度为什么不能突破慢阶段

缓冲让上游在下游忙碌时先做准备，可以吸收短时波动，但不能让一个持续需要七毫秒的阶段平均每三毫秒完成一次。如果下游比上游慢，上游最终会被缓冲容量限制；如果上游比下游慢，下游会间歇空闲。无限增加队列只会使等待中的数据更多，甚至增加内存压力和数据陈旧程度。

预取深度应与波动尺度、任务时间和容量限制一起选择。若读取偶尔卡顿几十毫秒，适当缓冲可能掩盖停顿；若每次解码都比计算慢一倍，则需要改善解码、并行资源或数据格式，而不是单纯再增加几个缓冲槽位。真正的诊断要区分短时抖动和长期容量不足。

当上游与下游共享 CPU、内存带宽或存储设备时，阶段耗时还会互相影响。单独测得读取四毫秒、计算七毫秒，不保证同时运行后仍保持这两个时间；竞争可能把读取推到十毫秒。流水线模型应当先提出独立资源假设，再用并行运行测量验证，而不能把独立微基准数字直接拼成最终预测。

<a id="performance-detail-9"></a>

### 4.3 稳定流量、等待时间与平均在途数量

对一个长期稳定、边界明确的系统，平均在途任务数 $`L`$、完成率 $`\lambda`$ 与平均停留时间 $`W`$ 满足 $`L=\lambda W`$。可以把它理解为对任务在时间轴上占用的面积做两种计数：按时间看是在途数量的积分，按任务看是每个任务停留时间的总和。忽略足够长窗口两端的边界项，两种平均趋于一致。

例如服务每秒完成五百请求，平均停留时间四十毫秒，则平均有二十请求处于系统内部。若希望在同样吞吐下把平均停留时间减半，平均在途数量也要相应减小；但仅靠限制队列并不一定保持吞吐，还可能导致拒绝或转移等待。公式提供一致性检查，不会自动告诉你哪个调度策略能实现目标。

持续过载时，到达率大于处理能力，等待队列不断增长，不存在所需的稳定平均。短窗口里仍可以算出几个数，却不能直接将它们解释为稳态关系。若系统丢弃请求，还要区分进入系统的有效请求、被拒绝的请求和最终完成的请求，保持计数边界一致。

<a id="performance-detail-10"></a>

### 4.4 利用率很高为何可能让延迟急剧恶化

为理解趋势，可以研究一个简化的单服务台模型：到达为泊松过程、服务时间独立同分布且服从指数分布、服务时间与到达过程独立、先到先服务，平均服务率为 $`\mu`$，到达率为 $`\lambda<\mu`$。在这些特定假设下，平均系统停留时间为 $`\frac{1}{(\mu-\lambda)}`$。这个结果不是所有真实服务的通用公式，但清楚展示了接近容量上限时等待时间的非线性增长。

若平均服务能力为每秒一千请求，到达每秒五百时平均停留时间为两毫秒；到达每秒九百时为十毫秒；到达每秒九百九十时达到一百毫秒。单次平均服务时间始终是一毫秒，增长来自排队。把服务计算加快百分之十，或把负载减少一点，可能在高利用率区域带来很大的等待收益。

真实系统可能具有突发到达、重尾服务、批调度和多资源竞争，延迟形状会更复杂。因此本例的数字用于理解机制，不可代替实际容量测试。应测量不同到达率下的吞吐、错误和延迟分布，观察系统在何处进入排队或拒绝区域，再留出适合业务的容量余量。

<a id="visual-service-variance"></a>

### 图解：平均服务相同，波动怎样放大排队？

![相同利用率下服务时间波动改变平均等待](images/05-service-variance.svg)

上一节的指数服务假设很关键。现在只保留泊松到达、单服务台、先到先服务、无限等待空间和不主动闲置的条件，让服务时间 $`S`$ 服从任意给定分布，并要求各请求的服务时间独立同分布、与到达过程独立。记 $`\rho=\lambda\mathbb E[S]<1`$，且服务时间二阶矩有限。此时 M/G/1 的平均排队时间满足

$$
\mathbb E[W_q]
=\frac{\lambda\mathbb E[S^2]}{2(1-\rho)},
\qquad
\mathbb E[T]=\mathbb E[W_q]+\mathbb E[S].
$$

这是 Pollaczek–Khinchine 公式；模型条件、工作量积分证明及泊松到达与时间平均的关系，可参阅 [Stanford EE384X 排队讲义，第 19–21 页](https://web.stanford.edu/class/ee384x/EE384X/handouts/H10.pdf)。式中是二阶矩，不是方差；即使服务时间恒定，二阶矩也不为零，所以随机到达依然会产生排队。

图中构造两个均值完全相同的服务分布。蓝色每个请求固定服务十毫秒，$`\mathbb E[S^2]=100\,\mathrm{ms}^2`$；橙色以 $`0.9`$ 概率服务一毫秒、以 $`0.1`$ 概率服务九十一毫秒，平均仍为 $`0.9\cdot1+0.1\cdot91=10\,\mathrm{ms}`$，二阶矩却为 $`0.9\cdot1^2+0.1\cdot91^2=829\,\mathrm{ms}^2`$。因此在任意同样的正利用率下，橙色的平均排队时间都是蓝色的 $`8.29`$ 倍；总响应时间因两边都需加上十毫秒服务，并不保持这个倍数。

在每秒八十请求的到达率下，$`\lambda=0.08\,\mathrm{ms}^{-1}`$，利用率为 $`0.8`$。代入得到蓝色平均排队二十毫秒、平均响应三十毫秒；橙色平均排队 $`165.8`$ 毫秒、平均响应 $`175.8`$ 毫秒。两者稳定完成吞吐都是每秒八十请求，利用率也相同。由 Little 关系，总平均在途量分别为 $`80\cdot0.03=2.4`$ 和 $`80\cdot0.1758=14.064`$。因此只有吞吐与利用率两项监控，仍不足以判断用户实际等多久。

为何少量慢请求影响如此大？在服务器正在忙的时刻随机观察，长任务被观察到的机会更大。橙色分布中九十一毫秒的任务只占请求数的十分之一，却占忙碌时间的 $`\frac{0.1\cdot91}{10}=0.91`$。观察时遇到的未完成服务时间不能按请求频率直接平均。对每段服务画“剩余时间随时间递减”的三角形，长度为 $`s`$ 的任务贡献面积 $`\frac{s^2}{2}`$；这说明为什么二阶矩进入平均剩余工作，再经排队反馈放大。这个解释同时提醒我们：按请求抽样与按墙钟抽样观察到的任务分布可能不同。

本例曲线是解析模型值，不是设备压测结果，也不是第九十九分位预测。固定均值下减小方差会在上述模型中减小平均等待，但若优化同时改变均值、到达相关性、并行服务数或拒绝策略，就必须重新建模。特别是 $`\rho<1`$ 不代表平均等待必定有限：若服务分布的一阶矩有限而二阶矩无限，系统可存在稳态，却有无限平均等待。真实服务有超时、容量限制或截断时，也不能把无限队列结论直接移植过去。

<a id="performance-detail-11"></a>

### 4.5 动态批处理的收益与代价

批量通常能摊薄固定启动成本并提高数据复用。若一个批次时间近似为 $`t(b)=\alpha+\beta b`$，批内吞吐为 $`\frac{b}{(\alpha+\beta b)}`$，随批大小增加趋向 $`\frac{1}{\beta}`$。但请求还要等待凑批，批执行时间也随大小增加，因此最大吞吐批次不一定满足交互延迟约束。

取固定开销两毫秒、每条增量零点二毫秒，批大小一的执行吞吐约每秒四百五十五条，批大小十六约每秒三千零七十七条，批大小六十四约每秒四千三百二十四条。后两者的边际收益已经变小，而执行时间从五点二毫秒增加到十四点八毫秒，尚未包括凑批等待。

可以设置最大批大小与最大等待时间，形成吞吐和延迟的折中，但最佳值取决于到达过程、长度分布和质量约束。不同长度序列混批还可能增加填充浪费；按长度分桶有助于减少浪费，却可能延长少见长度请求的等待。研究这种系统时，应把调度与数据分布共同视为实验条件。

<a id="sec-5"></a>
## 5. 可信的测量：时钟、预热、重复与异步执行

<a id="performance-section-5-1"></a>
### 5.1 墙钟时间与 CPU 时间分别测到什么

墙钟时间描述现实经过多久，包括等待、休眠、调度和 I/O；进程 CPU 时间描述该进程消耗的处理器执行时间，通常不包括纯等待。对于单线程纯计算，两者可能接近；对于多线程或阻塞工作，它们可能显著不同。选择哪一个应由问题决定，不能把其中一个当作永远更真实的时间。

Python 的高分辨率性能计时器适合测经过时间，进程时间接口适合观察进程累计 CPU 消耗。具体分辨率、跨平台实现和线程行为应查看所用版本文档。计时器返回许多小数位，不代表测量就拥有同样多的可靠有效数字；时钟量化、调度抖动和环境波动都会限制精度。

若一次操作太快，单次计时会被调用与时钟开销污染。可以在一段计时区间里重复多次，再除以次数，但要保证重复没有改变问题，例如输入并未越来越大、缓存条件没有被错误解释、编译器或实现没有消除无用工作。微小时间差若与测量噪声同量级，就不应做出强结论。

<a id="performance-detail-12"></a>

### 5.2 预热不是删除不喜欢的数据

预热的目的，是把初始化状态与持续运行状态分开。应事先声明预热次数或停止规则，而不是看见某次慢就把它随意划为预热。若目标确实包含冷启动，应单独报告完整首次调用；若关注稳态，则在一致预热后测量，但保留初始化成本的说明。

重复测量可以观察波动，但连续循环并不总是独立重复。缓存、温度、功耗策略和后台任务可能造成时间相关性。对于严肃比较，可以分多个独立进程或多个时段运行，随机交替两个版本，记录环境变化。把同一进程里的十万次内循环当作十万个独立环境样本，会严重高估证据强度。

最小耗时通常接近较少干扰时的下限，适合研究某些内核潜力；中位数更能反映典型重复；高分位描述尾部。没有一种统计量天然适合所有问题。报告时应说明关注的量，以及采样窗口是否足以支持该量的估计。

<a id="performance-detail-13"></a>

### 5.3 异步设备：提交结束不等于计算完成

主机调用某些设备接口时，可能只是把工作放入队列后立即返回。若只在提交前后读取主机时钟，测得的是提交成本，不是设备执行时间。要测整个任务的完成时间，计时边界必须覆盖相关工作的真实完成；要测设备内部一段工作，可以使用设备支持的事件计时机制并明确流和依赖。

为了准确计时而增加同步，本身可能破坏原本存在的重叠。因此应区分诊断测量与最终吞吐测量：前者可以适当隔离阶段，后者应尽量保留真实执行结构。每个小算子前后都同步，会把原本可以排队与重叠的工作强制串行，得到一个与实际运行不同的系统。

同样，设备报错可能在后续同步点才浮现，错误位置与提交位置不一定相同。时间线上出现一个看似很慢的同步调用，可能是它等待了之前提交的工作，而不是该同步函数本身执行了大量计算。分析时要追踪依赖和队列，不能只凭函数表的累计时间给原因排序。

<a id="performance-detail-14"></a>

### 5.4 保持比较的输入、分配与结果使用一致

比较两个实现时，输入形状、布局、数据类型、随机种子和线程配置必须说明。一个版本在计时外准备了数组，另一个版本把准备包含在计时内，二者不是同一工作边界。一个版本复用输出缓冲，另一个每次重新分配，也应明确这是所比较的实现差异，还是无意引入的不公平。

输出必须真正被检查。计算更快却返回错误形状、改变排序语义或漏掉缺失值处理，不能算同任务优化。数值比较也要使用符合问题尺度的容差；浮点加法结合顺序改变可能造成小误差，但这不允许忽略明显的语义差异。对于随机算法，还要比较结果分布或质量，而不要求逐元素完全相等。

如果某项优化依赖一个新的前提，例如输入保证连续、标签保证无缺失、长度保证整除批大小，就应把前提写进接口契约并验证。把检查移除后变快，只有在调用者确实保证条件且错误行为可接受的情况下，才是一项合理的系统设计变化。

<a id="sec-6"></a>
## 6. 一个完整的 CPU 基准实验：融合、分配与公平比较

<a id="performance-section-6-1"></a>
### 6.1 明确数学目标和候选实现

目标是对一个双精度向量计算 $`y=(x-a)^2+b`$。表达式实现简洁，但通常会产生中间结果；显式复用缓冲可以控制分配。我们比较的是这两种 NumPy 实现，不把 Python 元素循环和向量化的差异混入同一实验，也不声称某个版本在所有设备和输入规模上必然更快。

第一版直接写表达式，第二版在预先分配的数组上依次减法、平方和加法。后者仍可能多次遍历数组，所以“减少分配”不等于真正将所有逐元素操作融合为一次内核。实验能够说明缓冲复用的影响，却不能仅凭语法证明底层流量减半。

```python
import time
import statistics
import numpy as np

rng = np.random.default_rng(7)
x = rng.normal(size=500_000).astype(np.float64)
a, b = 0.3, 0.7
buffer = np.empty_like(x)

def expression():
    return (x - a) ** 2 + b

def reused_buffer():
    np.subtract(x, a, out=buffer)
    np.square(buffer, out=buffer)
    np.add(buffer, b, out=buffer)
    return buffer

reference = expression()
np.testing.assert_allclose(reused_buffer(), reference, rtol=1e-14, atol=1e-14)
for _ in range(5):
    expression()
    reused_buffer()

records = {"expression": [], "buffer": []}
functions = {"expression": expression, "buffer": reused_buffer}
order_rng = np.random.default_rng(11)
checksum = 0.0
for _ in range(15):
    order = ["expression", "buffer"]
    order_rng.shuffle(order)
    for name in order:
        start = time.perf_counter()
        result = functions[name]()
        elapsed = time.perf_counter() - start
        records[name].append(elapsed)
        checksum += float(result[0])
        del result
for name, samples in records.items():
    print(name, "median_ms", 1000 * statistics.median(samples))
    print("range_ms", 1000 * min(samples), 1000 * max(samples))
print("checksum", checksum)
```

<a id="performance-detail-15"></a>

### 6.2 如何解释结果，哪些结论暂时不能下

两个版本在计时前都通过相同输入和容差验证，预热次数一致，测量顺序随机交替，输出在计时后被消费并解除本轮局部引用，避免上一轮返回数组的释放跨入下一轮计时。缓冲版本的预分配放在计时外，所以本实验比较持续重复调用场景；如果实际任务每次只调用一次，还应补充包含缓冲分配的冷调用比较。

打印结果随设备和负载改变，教材不预设一个固定倍数。若缓冲版本更快，可能来自减少分配和临时对象生命周期，也可能受缓存影响；若差异很小，说明在当前规模下分配可能不是主导成本。仅凭这一组时间，尚不足以区分底层带宽、缓存和分配器的具体贡献，需要规模扫描和额外观测。

这里两个函数返回值的所有权语义不同：表达式返回新数组，缓冲版每次返回同一个可变数组。若调用者保存多次输出，后续调用会覆盖先前缓冲结果。只有当接口允许复用，或者调用者及时复制时，才具有所需语义等价。复制的成本又可能抵消部分收益，必须计入真正的使用场景。

<a id="performance-detail-16"></a>

### 6.3 设计规模扫描，避免单点测量误导

将元素数分别设为几百、几万、几十万和几百万，观察时间随规模增长的趋势。很小规模可能由 Python 调用和函数调度主导；中等规模可能主要受缓存影响；更大规模才逐渐接近主存带宽限制。一个规模上的赢家不一定在另一个规模仍然获胜。

同时记录每次调用的分配量、有效字节估计和输入布局。如果把连续数组改成切片视图，步长访问可能改变缓存利用；如果改成另一种数据类型，字节量和向量化指令也会变化。每次实验只主动改变少量因素，才能把观察到的差异与候选机制建立可信联系。

完整报告应当包含目标公式、候选实现、等价条件、输入生成、计时边界、预热、重复和结果统计，再给出解释与尚未排除的原因。这样其他人才能复算或反驳你的结论，而不是只能相信某张没有上下文的速度截图。

<a id="sec-7"></a>
## 7. 从观测走向原因：剖析、干预与证据强度

<a id="performance-section-7-1"></a>
### 7.1 采样剖析与插桩剖析的差别

采样剖析周期性观察线程正在执行的位置，用样本分布估计时间分布；插桩则在函数、事件或算子边界记录进入和退出。前者通常开销相对可控，但短事件可能采不到，样本数量也限制分辨率；后者可以保留更明确的边界，却可能增加显著开销，甚至改变调度和缓存行为。

两者都需要理解统计口径。某个函数的自身时间只计其内部直接消耗，包含时间还计入被调用函数；递归和多线程汇总又可能产生看起来超过墙钟时间的数字。不要把不同口径的百分比直接相加，也不要因为累计 CPU 时间超过经过时间就认定工具错误，多核并行本来就可能发生这种情况。

选择工具之前先明确问题。如果想知道主线程为什么等待，应观察阻塞、队列和依赖；只采集正在 CPU 上执行的栈可能看不到主要等待原因。如果想分析设备空闲，应结合主机提交与设备时间线；单看某个算子的执行持续时间，无法解释两次算子之间为何存在长空隙。

<a id="performance-detail-17"></a>

### 7.2 高利用率、饱和与错误应分别检查

一个资源忙碌，不意味着它已经成为限制完成时间的瓶颈；一个资源利用率低，也不意味着它没有问题。设备可能因为上游断供而空闲，单线程可能占满一个核心而总体 CPU 利用率看起来不高，内存容量不足也可能体现为等待而不是高算术活动。

资源分析可以分别问：当前有多少容量在使用，是否有工作等待获得资源，是否发生分配失败或重试。这样的分解比只盯着一个百分比更有效。例如磁盘忙碌时间很高，但实际吞吐很低，可能是大量随机小请求；内存使用接近上限，但没有压力和换页，不必直接等同于故障。

这些观测仍是线索，因果判断需要干预。减少一个阶段的工作量后，若端到端时间按模型改善，且其他条件保持一致，说明这个阶段确实对完成时间有贡献。若局部变快而整体不变，可能存在重叠、瓶颈迁移或测量边界问题，需要修改模型。

<a id="performance-detail-18"></a>

### 7.3 用替代负载隔离数据与计算

训练很慢时，可以用形状相同、已经在内存中的合成输入替换真实读取路径，保持模型执行近似不变。若速度显著提高，数据路径值得进一步调查；若没有变化，主要瓶颈可能在其他位置。但合成输入会改变解码、数据布局和可能的数据依赖分支，因此这是一项诊断干预，不是最终训练性能报告。

还可以预先完成解码，只保留后续变换；或固定模型输出，只测数据路径。每次替代都应说明保留了什么、移除了什么，并检查是否引入新的缓存优势。把真实数据全部放进内存后变快，并不能单独证明磁盘硬件太慢，也可能是文件数量、压缩格式或预处理策略造成。

对于系统瓶颈，最好提出多个竞争假设。例如“CPU 解码不足”“主存带宽饱和”“频繁分配”“设备提交太碎”。为每个假设设计能够区分的改动，而不是只做一项大改然后把所有收益归给自己最初的猜想。一个好的实验不仅支持某种解释，也排除至少一部分替代解释。

<a id="performance-detail-19"></a>

### 7.4 容量问题与泄漏问题需要看生命周期

一次运行峰值很高，可能只是同时存活的对象很多；随着迭代无限增长的占用，才更值得调查不再需要的引用、计算图或缓冲是否被意外保留。分配器为了复用而保留内存，也可能使操作系统观察到的占用不立刻下降，这与对象仍然存活不是同一个事实。

可以按迭代记录活动对象量、进程驻留内存和框架分配指标，先观察是否达到平台。如果前几轮增加后稳定，可能是缓存或延迟初始化；如果每轮固定增加，检查日志是否保存了带依赖的输出、列表是否无限追加、数据缓存是否无上限。诊断应基于增长机制，而不是看到大数字就反复清空缓存。

减少批大小适合缓解随批增长的激活和输入占用，但不会同比减少参数和优化器状态。把对象移到其他设备会改变容量位置，也会引入传输和同步代价。每种处理都应对应已经定位的组成，不能把某个常见技巧当成所有内存问题的统一解法。

<a id="sec-8"></a>
## 8. 统计比较、尾部延迟与可复现结论

<a id="performance-section-8-1"></a>
### 8.1 配对比较比两个随意平均更有解释力

若两个实现使用同一输入，可以在相近环境下成对运行，并比较每对差值或比值，减少输入难度差异造成的干扰。顺序最好随机或交替，避免一套总在机器较冷时运行、另一套总在温度升高后运行。配对并不能消除所有噪声，但让实验结构更符合要比较的对象。

算术平均耗时适合估计固定工作集合的平均完成成本；不同任务的加速比直接平均可能产生奇怪权重。若任务有真实业务频率，应按频率加权总成本。若研究跨任务相对倍率，几何平均有其用途，但应明确每个任务的权重与解释，不能用一个汇总数字隐藏某些任务明显退化。

例如两个等频任务，原时间分别一毫秒和一百毫秒，优化后分别零点一毫秒和九十毫秒。局部倍数为十倍与约一点一一倍，算术平均倍数看起来很大，但总时间仅从一百零一降到九十点一毫秒，整体约一点一二倍。任务成本权重决定真正的端到端收益。

<a id="performance-detail-20"></a>

### 8.2 尾部分位数不能由几个样本可靠估计

九十九分位延迟描述约百分之一最慢区域的边界。只有几十次请求时，这个统计量几乎被一两个极端值决定，无法代表稳定尾部。即使样本很多，若请求之间高度相关，独立信息量也可能远低于请求数。报告尾部要保留采样时间、负载过程和置信程度，避免把一次偶发值写成系统固有属性。

一个简单思想是把“超过固定阈值”转为指示变量，再估计超标概率。若独立观察一千次都没有超标，只能说明在这组条件下未观察到事件，不能证明真实超标率为零。需要根据目标风险和置信水平决定样本规模；若线上请求存在时间相关性，还要使用合适的分块或独立时段分析。

服务测试还要防止负载生成器等待响应后才发送下一次请求，从而在系统变慢时自动减轻到达压力。这种闭环测试适合某些交互模型，却不能代表固定外部到达率下的排队。应按研究问题选择开放到达或闭环并发，并清楚报告，而不是只写“并发数若干”。

<a id="performance-detail-21"></a>

### 8.3 训练性能必须连同质量一起比较

若一套训练系统提高吞吐，却改变批量、数值精度或优化步边界，最终模型质量可能变化。为了比较达到目标质量的时间，应预先规定质量门槛、评价数据和停止规则，并在多个独立训练重复中观察是否稳定达到。不能只挑最快的一次，也不能训练后根据结果修改目标门槛。

如果某些运行根本没有达到门槛，其时间是未完成或删失结果，不能默默删掉后对成功运行取平均。可以报告成功率、固定预算下质量分布和达到门槛的时间分布。算法改动与系统改动混合时，还应区分单步实现收益和收敛行为变化，避免将其中一个的效果全部归因于另一个。

资源成本还可以包括总设备时间、能耗与人工维护。八台设备把墙钟时间缩短四倍，消耗的设备小时反而增加一倍；这可能符合紧急任务目标，却不一定节省成本。性能指标的选择要回到最初任务价值，而不是假定所有场景都只追求最短墙钟时间。

<a id="performance-detail-22"></a>

### 8.4 预先规定选择规则，避免从噪声中挑赢家

如果尝试二十种线程数、十种批大小和多个内存布局，再只报告其中最快的一项，最终数字包含调参带来的选择偏差。候选越多，越容易碰巧选中一次有利噪声。可以把调优与最终验证分开：先在开发负载上选择配置，再用未参与选择的独立重复与代表性任务复验。最终报告同时写明搜索范围和采用的选择指标。

这个原则与机器学习中的验证集选择非常相似。性能配置可以依赖开发环境，但若希望声称对另一台机器、另一种输入分布也有效，就必须在相应条件下验证。把一个局部最佳配置宣传为普遍最佳，往往比计时器误差造成更大的误导。若多个候选差异小于环境波动，可以优先选择结构简单、资源稳定且容易维护的实现，并明确当前证据不足以排序。

<a id="load-generation-boundary"></a>
### 8.5 负载生成器也属于实验系统

选择开放到达测试时，负载生成器按照预先安排的时间发送请求，不因为前一个请求尚未完成就停止产生后续需求。若系统变慢，等待队列或拒绝数会显现；若使用闭环客户端，客户端必须等到响应才发下一次，同样的并发数下系统变慢反而减少到达量。两者模拟不同交互机制，都可以合理，但不能用闭环结果直接证明固定外部到达率下仍具有同样尾部延迟。

一个具体例子是某客户端每次收到响应后立即发下一次，平时响应一毫秒，每秒可以发送约一千次；系统停顿一秒时，这个客户端只记录了一个很慢的请求，没有代表这一秒里本来可能到达的一千个外部请求。若业务真实需求持续到达，那些本应排队的工作被测试协议省略了。只查看已发送请求的延迟，会低估持续负载下的等待影响，这种遗漏来自实验生成机制，无法靠换一个更精确时钟修复。

受控测试应记录计划发送时间、实际发送时间、服务端接收和完成时间，并说明延迟从哪一刻起算。若负载生成器自身来不及按计划发送，实际发送时间已偏离目标流量，就应把这视为生成器容量限制，而不是把不足流量下的服务结果报告为目标吞吐。请求超时和被拒绝也必须保留在分母中，不能只对成功响应计算一个看起来很好的高分位。

为了判断原因，可以先测试生成器对一个极轻量处理器的能力，再逐步增加模型执行负载；也可以分离生成器与被测资源，避免两者争抢同一 CPU 或网络。隔离并不总是必要，但必须知道共享资源是否改变了结论。最终报告中，客户端数、到达过程、连接复用、超时、重试和目标长度分布都属于任务条件，而不是可以省略的测试细节。

<a id="load-generation-boundary-1"></a>

### 8.6 容量峰值应当画成生命周期问题

把每种对象大小相加只能给出某种静态总量，真实峰值取决于哪些对象同时存活。一个批次输出在下一个批次输入分配前释放，与两者重叠保留，峰值可能不同；异步执行还可能使主机已离开某段代码，设备仍在使用相关缓冲。观察占用时应对应时间线与所有权，而不是只按源代码上下顺序猜测释放点。

可以先画出参数、输入、激活、梯度、优化器状态和临时工作区的生存区间，再分析峰值处的交集。如果保存历史预测无意保留了大对象引用，增长来自生命周期错误；如果峰值始终稳定但太大，问题是容量设计。两类问题分别需要释放不再使用的状态，或采用分块、重计算与分片等资源交换。相同的“内存不足”错误消息，不代表相同的根因。

固定一百次构造请求：九十五次为 1 ms，五次为 100 ms，平均值为 5.95 ms。最近秩定义取第 ceil(100×0.95)=95 个有序值，所以 P95=1 ms；P99 取第 99 项，为 100 ms。图中把第 92 到 100 项展开，直接看到第 95、96 项之间的跳跃。

<a id="sec-9"></a>
## 9. 第二个可运行实验：用离散事件复算流水线

<a id="performance-section-9-1"></a>
### 9.1 从依赖关系构建模拟，而不是靠真实休眠凑时间

为了检查流水线模型，可以用离散事件计算每个阶段的开始与结束，不需要真的等待几百毫秒。第 $`i`$ 批在第 $`j`$ 阶段只能在两个条件都满足后开始：本批上一阶段完成、同阶段上一批完成。因此开始时间是两个完成时间的最大值，再加本阶段持续时间得到结束时间。

这个递推可以描述固定阶段耗时，也可以接收每批不同耗时，观察波动怎样传播。它没有模拟共享带宽、线程调度和有限队列，因此只验证明确给定的依赖模型，不是完整硬件模拟器。把模型范围写清楚，才能知道哪些差异来自实现错误，哪些来自现实超出假设。

实现限定实数时长，并要求所有累计完成时间在浮点范围内可表示。输入各项有限并不足以保证累加有限；例如两段时长均为 $`10^{308}`$，完成时间仍会溢出。复数坐标也不能通过丢弃虚部来解释成合法时长，以下接口显式拒绝这些情况。

```python
import numpy as np

def pipeline_finish(durations):
    if np.iscomplexobj(durations):
        raise ValueError("real durations required")
    durations = np.asarray(durations, dtype=float)
    if (durations.ndim != 2 or durations.shape[1] == 0
            or not np.all(np.isfinite(durations)) or np.any(durations < 0)):
        raise ValueError("expected finite nonnegative durations and at least one stage")
    batches, stages = durations.shape
    finish = np.zeros((batches, stages), dtype=float)
    for i in range(batches):
        for j in range(stages):
            input_ready = finish[i, j - 1] if j else 0.0
            stage_ready = finish[i - 1, j] if i else 0.0
            candidate = float(max(input_ready, stage_ready)) + float(durations[i, j])
            if not np.isfinite(candidate):
                raise ValueError("completion time is not representable as a finite float")
            finish[i, j] = candidate
    return finish

fixed = np.tile([4.0, 7.0, 3.0], (100, 1))
finish = pipeline_finish(fixed)
prediction = 4 + 7 + 3 + 99 * 7
assert finish[-1, -1] == prediction == 707
assert np.all(np.diff(finish[:, -1]) == 7)
print("fixed total_ms", finish[-1, -1])

variable = fixed.copy()
variable[20, 0] = 40.0
changed = pipeline_finish(variable)
print("one slow read total_ms", changed[-1, -1])
print("affected output intervals", np.diff(changed[:, -1])[18:24])

for invalid in ([[float("nan")]], [[float("inf")]], [[-1.0]], [[]],
                [[1e308, 1e308]], np.array([[1.0 + 2.0j]])):
    try:
        pipeline_finish(invalid)
    except ValueError:
        pass
    else:
        raise AssertionError("invalid durations must be rejected")
```

<a id="performance-detail-23"></a>

### 9.2 逐步解释一次慢读取如何影响输出

正常情况下，第十九批附近的输出间隔稳定为七毫秒。索引二十的读取从常规四毫秒变成四十毫秒，但上游此前比计算阶段快，已经形成一定提前量；在无限缓冲模型中，这个局部停顿可能被先前积累的输入掩盖，最终完成时间甚至保持不变。这个结果不是说慢读取永远无害，而是说明缓冲和已有余量会改变影响传播。

若把停顿放到最前几批，或把读取阶段改得接近七毫秒、缺乏余量，影响就可能显现。若限制缓冲大小，原先提前完成的读取不能无限积累，也会改变结论。实验应通过这些受控改动检验解释，不要只看到某次停顿没有影响就推出“数据加载无关紧要”。

模拟还能用来检查关键路径：记录每个阶段开始时间由输入就绪还是资源就绪决定，就能区分断供与资源忙碌。真实系统中的剖析也在做类似工作，只不过事件可能更多、资源可能共享、时间也带有测量误差。先在可完全理解的模型上练习，再分析复杂时间线，可以减少凭直觉猜测的次数。

<a id="performance-detail-24"></a>

### 9.3 延伸：有限队列为什么需要新的状态

上面的数组递推允许上游任意提前，隐含阶段间无限缓冲。若队列最多放两个批次，上游完成后可能因为队列满而阻塞，资源不能立即处理下一批。要准确建模，必须同时跟踪队列占用、下游取出事件和阻塞释放条件，不能简单把一个固定惩罚加到所有批次上。

这也提醒我们，增加模型复杂度应由实际问题推动。若无限缓冲模型已经准确预测主要趋势，不必为了“更真实”加入大量无法校准的参数；若真实曲线显示预取深度显著影响吞吐，就值得加入有限缓冲状态。一个可解释、可证伪的小模型，往往比一个参数很多却无法验证的大模型更有研究价值。

<a id="sec-10"></a>
## 10. 分层练习、详细解析与研究路线

<a id="performance-section-10-1"></a>
### 10.1 基础计算与口径辨析

**题一：** 一个程序每批处理一百条输入，批执行时间二十毫秒，平均凑批等待五毫秒。写出批内执行吞吐与请求平均等待下界，说明能否把吞吐倒数当作请求延迟。

**解析：** 批内执行吞吐是每秒五千条，摊销执行成本为每条零点二毫秒；但一条请求如果平均等待五毫秒凑批，再等待整批二十毫秒完成，平均经历至少二十五毫秒，尚未包括其他排队与传输。零点二毫秒是资源成本摊销，不是该请求真实经过时间。若批执行还能并行重叠，需要另外说明系统层吞吐，不能直接沿用单批比值。

**题二：** 工作需要六十亿次运算和三吉字节流量，适用计算吞吐每秒三万亿次、带宽每秒一百吉字节。求两个理想时间下界，并判断优先增加哪一种资源更可能有帮助。

**解析：** 计算下界为两毫秒，搬运下界为三十毫秒。当前模型明显由搬运限制，单纯把计算吞吐翻倍只把较小下界变为一毫秒，整体主要下界仍为三十毫秒。减少流量或提高实际可用带宽更有希望，但必须确认三吉字节确实跨越了所用带宽对应的边界，并检查是否还存在启动与并行度限制。

**题三：** 一项工作四分之一可加速十倍，整体加速是多少？若另增原耗时百分之五的调度开销呢？

**解析：** 没有新开销时，时间比例为 $`0.75+\frac{0.25}{10}=0.775`$，加速约一点二九倍；加入开销后比例为零点八二五，加速约一点二一倍。局部十倍并不代表整体接近十倍，尤其当可优化部分占比很小时。报告局部收益应同时给出其原始占比。

<a id="performance-detail-25"></a>

### 10.2 模型推导与条件检查

**题四：** 对本章简化单服务台模型，设利用率 $`\rho=\frac{\lambda}{\mu}<1`$，从稳态人数分布推导平均停留时间，并指出哪些前提不应省略。

**解析：** 泊松到达和指数服务构成的出生死亡模型满足相邻状态流量平衡 $`\pi_{n+1}\mu=\pi_n\lambda`$，所以 $`\pi_n=(1-\rho)\rho^n`$。几何级数求导得到平均系统人数 $`L=\frac{\rho}{(1-\rho)}`$，再用稳定流量关系 $`W=\frac{L}{\lambda}`$ 得 $`W=\frac{1}{(\mu-\lambda)}`$。需要单服务台、先到先服务的相应系统设定、无限等待空间、稳定负载与相应随机过程假设；改变服务分布后，不能继续直接使用同一人数分布推导。

**题五：** 三阶段耗时为二、五、四毫秒，处理十批，在独立资源与无限缓冲模型下需要多久？如果把第一阶段加速两倍，会发生什么？

**解析：** 原时间为十一加九乘五，即五十六毫秒。第一阶段降为一毫秒后，时间为十加九乘五，即五十五毫秒，只改善一个毫秒。稳态节拍仍由五毫秒阶段控制，第一阶段改进主要减少填充时间。若任务只有一批，改善占比会更大；若第一阶段存在波动，变快还可能增加吸收波动的余量，但那是另一个需要实际检验的收益。

<a id="performance-detail-26"></a>

### 10.3 实验批判与接口语义

**题六：** 某人只保留两个版本各自最快的一次，发现版本乙快百分之三，于是宣布稳定改善。你会要求补充哪些证据？

**解析：** 应先确认结果等价、计时边界一致、输入和线程配置一致，再查看重复分布与随机交替结果。百分之三若落在环境波动范围内，证据不足；若只关心最少干扰时的内核潜力，可以报告最小值，但不能将其解释为典型或尾部性能。还应检查冷启动、缓存与预热规则，确认不是某个版本总在更有利的状态运行。

**题七：** 本章缓冲版每次返回同一个数组，表达式版每次返回新数组。给出一个二者数值公式相同、应用行为却不同的调用场景，并设计修复。

**解析：** 调用者把第一次输出加入历史列表，改变输入后再次调用缓冲版，列表中的旧数组也被覆盖，历史结果不再可信。可以规定返回值只在下一次调用前有效，由调用者及时消费；或在需要保存时显式复制；或由调用者提供多个输出缓冲。不同修复具有不同内存和复制成本，因此公平基准应采用满足真实调用契约的版本。

<a id="performance-detail-27"></a>

### 10.4 研究任务与完成标准

选择一个实际学习项目，建立不少于三个竞争瓶颈假设，各写一项能够支持或反驳它的受控实验。例如固定合成输入检验数据路径、复用缓冲检验分配、扩大工作单元检验调度摊销。先预测改动应该影响哪个指标，再执行测量，记录没有符合预测的结果及修正后的模型。

完成标准是能够重建任务定义、正确性约束、资源边界和依赖关系；能从工作量推导量级，并知道哪些数字只是下界；能用同条件基准得到可复核结果；能把观察、解释和未排除原因分别陈述。没有达到这些标准时，应继续完善证据，而不是用更多小数位替代更清楚的实验设计。
