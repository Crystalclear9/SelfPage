## 1. 进程与线程：执行单位和资源边界

<a id="systems-2-detail-2"></a>
### 1.1 并发、并行与异步分别回答什么

并发描述多个活动在一段时间内都能推进，并行描述多个活动在同一时刻实际执行，异步接口则通常把“提交操作”和“等待完成”分离。一个单线程事件循环可以并发处理许多等待中的请求，却不代表同时执行多个纯计算片段；多个操作系统线程也可能因为只有一个可用执行单元而轮流运行。学习系统时，首先要明确是在讨论组织方式、硬件执行，还是接口完成语义。

并发的主要价值并不限于速度。它还能把交互、后台工作和资源管理组织成独立活动，使一个任务等待时另一个任务继续。这样的结构可能改善响应性，却增加共享状态和取消逻辑的复杂度。如果任务量很小，串行实现可能更简单且更快。因此不能把“使用并发”作为进阶的标志，应该根据任务依赖和资源等待决定是否需要。

并行必须有可同时执行的工作。若下一步输入依赖上一步结果，再多线程也无法越过依赖。算法的任务图先决定潜在并行度，运行时和硬件再决定能兑现多少。把一个串行依赖链拆成很多函数，不会自动增加并行性；相反，可能仅增加调度和传递成本。

<a id="systems-2-detail-3"></a>
### 1.2 进程隔离与线程共享

进程通常拥有独立地址空间及相关系统资源，线程共享所属进程的许多资源，同时各自拥有执行上下文与调用栈。线程间传递一个对象引用往往比较直接，但双方也可能意外访问同一可变对象。进程间普通语言对象则通常不会因为变量名字相同就共享，需要显式通信、共享映射或其他接口。

隔离是一种错误边界，不是完美安全或永不影响。一个进程失败可能不直接破坏另一个进程的私有对象，但它们仍可能共享文件、设备、内存段或外部服务。一个线程失败也未必立即结束整个进程，却可能留下不完整共享状态。因此设计时要明确哪些故障由谁观察，哪些资源由谁释放，以及谁负责决定任务整体成功。

线程切换和进程切换都需要保存恢复执行状态，具体成本取决于系统、地址空间变化和缓存等因素。不能把一个固定纳秒值当作普遍常数，也不能只凭“线程轻量”忽略每个线程的栈、调度和同步成本。对于数千个短任务，复用有限工作线程通常比为每个任务创建新线程更合适，但池也需要容量限制和退出协议。

<a id="sec-1-1"></a>
<a id="systems-2-detail-4"></a>
### 1.3 基础算例：计算与等待分开决定并发方案

设每条记录需要两毫秒可执行计算和八毫秒外部等待，串行服务时间为十毫秒。在理想无争用条件下，重叠等待可能提高吞吐，但不能保证每条记录低于其自身依赖路径。若所有记录都需要同一个独占资源八毫秒，该资源吞吐仍形成瓶颈。把等待标注为可重叠，不等于它占用的外部资源拥有无限容量。

另一个任务每条需要十毫秒纯 Python 计算。在本章实测环境的传统 CPython 3.11.5 中，多个线程不能简单靠同时执行 Python 字节码获得多核线性加速。换用多进程可能利用多个核心，但要计入启动、序列化和合并；若计算进入释放解释器锁的原生库，线程行为又可能不同。应根据具体代码路径分类，而不是仅根据函数用 Python 编写就下结论。

<a id="deep-dive-1"></a>
<a id="systems-2-detail-5"></a>
### 1.4 深入讲解：共享资源决定可用并行度

一个任务需要计算、文件访问和共享状态更新，每种资源都有自己的容量限制。即便计算可以充分并行，共享锁也可能让更新串行，存储也可能因并发随机请求而降低效率。合理的并发结构应把共享阶段缩小，并尽量让任务在私有数据上完成较大粒度计算，再以较少次数合并。

局部聚合是一种典型变换。若每处理一个元素都获取全局锁，锁次数与元素数成比例；若每个工作线程在局部累计一批结果，再合并一次，锁次数与批数成比例。但这种变换要求合并满足业务语义。例如计数求和容易分块，依赖严格先后顺序的状态机则不能随意重排。优化前必须确认可交换性、结合性和异常时的状态规则。

<a id="systems-2-detail-6"></a>
## 2. 运行时边界：GIL、原生库与进程启动

<a id="systems-2-detail-7"></a>
### 2.1 GIL 不是业务不变量的锁

传统 CPython 的全局解释器锁是运行时管理机制，不应当作用户程序所有复合操作的事务保证。一次“读取、检查、修改、写回”可能由多个执行步骤组成，中间允许其他线程推进。即便某个版本的某个简单操作表现为不可分割，也不能由此推出围绕它的业务条件天然正确。

例如“如果字典中没有某键，就创建一项并发送一次请求”，即便单次字典访问安全，检查与创建之间仍可能出现交错。两个线程都看到缺失，随后各自执行外部操作，最后字典只留下一个结果，却已经产生两次请求。正确同步必须保护完整不变量，或者使用具备明确原子语义的协议，而不是只盯某一条赋值语句。

本章不假设其他 Python 实现或其他构建采用相同锁机制。描述版本条件时，应写清解释器、版本和构建方式；对于原生扩展，也要查明是否释放相关锁、内部是否另有线程池，以及数据访问是否线程安全。不能把一个运行时限制扩展成所有语言、所有 Python 或所有数值计算的定律。

<a id="systems-2-detail-8"></a>
### 2.2 原生线程池与过度订阅

数值算子可能在内部启动或使用线程池。如果外层又开多个任务，每个任务各自调用多线程算子，活跃线程数可能远超可用核心。结果可能是上下文切换、缓存争用和内存带宽竞争，吞吐反而下降。这种过度订阅往往被误解为“系统没有真正多核”或“进程不如线程”，实际上需要协调两个层次的并行配置。

不能只数语言层创建的线程。数据库驱动、解码器和数学库都可能拥有后台线程。实验应记录外层并发数与底层线程配置，并观察整个任务的 CPU 与内存资源。如果只在外层调整一个参数而忽略内部变化，便无法判断收益来自何处。

对于以带宽为主的运算，增加计算线程到一定程度后可能只让同一内存系统更拥挤。对于等待型任务，适度超出核心数却可能有效。线程数与核心数没有一条普遍最佳比例，选择应依赖任务的计算、等待和共享资源结构，并通过代表性负载验证。

<a id="systems-2-detail-9"></a>
### 2.3 Windows 的 spawn 与可导入入口

在 Windows 的常见多进程路径中，新的解释器进程通过启动协议建立工作环境，而不是直接假定复制父进程当前执行状态。可提交给子进程的函数与参数必须满足所用序列化机制的要求，工作函数通常应位于可导入模块的顶层。闭包、交互环境中的临时函数和携带不可序列化资源的对象，常会造成问题。

入口保护的作用是防止子进程导入主模块时再次无条件启动新的进程。它不只是固定格式，背后是“模块导入会执行顶层代码”的语义。若创建进程的语句放在顶层，导入过程可能递归创建；若只定义函数并在主入口中启动，则能够把定义和执行分开。具体启动方式和默认值应以目标平台与版本文档为准。

序列化还影响性能和所有权。把一个大列表作为任务参数反复传递，可能导致重复编码、复制和内存占用。共享内存可以减少某些复制，但需要处理布局、生命周期与同步。进程隔离并不自动意味着低通信成本；多进程方案必须把数据如何进入和离开工作进程纳入设计。

## 3. 从任务图理解瓶颈与测量边界

<a id="systems-2-detail-11"></a>
### 3.1 工作量与关键路径

把任务表示为有向无环图，节点为工作，边为必须先完成的依赖。所有节点工作总和记为 $W$，关键路径长度记为 $D$。在简化相同处理单元模型下，使用 $p$ 个执行单元的时间至少为 $\max(W/p,D)$。前者来自总工作量，后者来自依赖链，二者都只是下界，尚未包括调度和通信。

例如有四个互相独立的十毫秒任务，之后必须执行一个五毫秒合并。总工作量四十五毫秒，关键路径十五毫秒。四个执行单元在理想条件下可以接近十五毫秒；增加到八个也不能缩短这个任务图中的前置任务长度或合并时间。若合并必须等待所有任务，任何一个长尾都会延迟整体完成。

任务图有助于避免盲目拆分。若把一个十毫秒任务拆成一百个零点一毫秒任务，却每个都需要较大调度成本，总工作量可能增加。粒度应足够大以摊销开销，又足够小以平衡负载。粒度选择是调度成本与负载不均之间的折中，不存在脱离工作负载的固定最佳任务大小。

<a id="systems-2-detail-12"></a>
### 3.2 墙钟时间、CPU 时间与等待

墙钟时间是用户从开始到结束经历的时间；CPU 时间描述处理器实际为相关执行消耗的时间。一个进程等待外部事件时墙钟继续增长，CPU 时间可能增加很少。多个核心并行工作时，总 CPU 时间又可能超过墙钟时间。把这两者混淆，会使等待型任务看起来“没有耗时”，或把多核任务误读为计时错误。

Python 的进程 CPU 时间接口通常不自动覆盖所有子进程，因此多进程基准不能只测父进程 CPU 时间就宣称总计算成本降低。需要采用与目标一致的测量范围，例如整个进程组或系统工具。单个线程的 CPU 时间又是另一种范围。每张表都应明确统计实体，不能让同名“CPU 时间”在不同实验中悄悄变换含义。

外部等待也可能嵌套。程序看似等待锁，持锁线程其实在等待磁盘；只优化锁原语未必解决根因。应先识别谁在等待谁，再沿依赖追踪到真正占用资源的活动。这种等待关系分析比只按函数累计耗时更能解释并发程序卡顿。

<a id="sec-2-1"></a>
<a id="systems-2-detail-13"></a>
### 3.3 机制展开：一次性成本与稳态分开

启动解释器、导入模块、创建线程池、初始化连接和分配缓冲可能主导短任务。若线上请求复用已启动的池，稳态指标有意义；若实际每次都启动新进程，排除启动成本就会低估用户时间。应分别报告冷启动和复用条件，而不是任意选择更漂亮的数字。

重复实验需要保持相同任务数量与结果语义。一个版本丢弃了失败任务，可能看起来更快，却没有完成同样工作；一个版本只等待提交而不等待所有结果，也不具备可比性。计时结束点应建立在完成条件上，例如所有任务结果已经验证并合并，而不只是所有任务已进入队列。

实验中应包含异常路径与资源回收。正常路径退出很快，不表示发生错误时工作线程能及时停止。对于长时间运行服务，取消响应、队列清空和线程退出也属于可观察行为。性能测试若从不覆盖这些情形，容易留下在真实环境中才出现的悬挂问题。

<a id="systems-2-detail-14"></a>
## 4. 正确性：竞态、不变量与同步协议

<a id="systems-2-detail-15"></a>
### 4.1 数据竞争与逻辑竞态

在不同语言和内存模型中，“数据竞争”可能具有严格定义；本章用逻辑竞态指结果依赖不受控制的事件先后，且这种依赖违反业务要求。即使底层单个读写都有安全保证，先检查后执行仍可能出错。应从业务不变量出发，例如余额总和不变、任务只完成一次、样本与标签一一对应，而不是只检查程序是否崩溃。

并发错误常表现为低概率，所以普通重复运行没有发现问题不能证明正确。更好的测试是人为安排危险交错，让两个线程在读取之后、写入之前汇合，从而稳定复现丢失更新。这样的测试验证某种交错存在，不说明每次调度都会产生同样结果，也不等同于测量实际故障概率。

同步协议的目标是给相关操作建立必要顺序。锁保护临界区，消息队列转移工作或结果，事件表达某个状态已经发生，条件变量则把等待与受保护谓词关联。选择原语之前先写清状态机：哪些状态合法，谁可以改变状态，改变后应唤醒谁。没有状态模型的同步代码很容易堆出锁而仍然错误。

<a id="systems-2-detail-16"></a>
### 4.2 锁保护的是不变量

若两个账户转账，需要同时维护扣款、入账和资金约束，锁必须覆盖这些相关状态的检查与更新。分别锁住单次读和单次写，仍可能在中间暴露不一致状态。临界区应足够大以维持不变量，又尽量避免不必要计算与外部等待；这是一项基于语义的边界选择，不是越短越好。

锁不是免费资源，但正确性不能靠删除锁换取。减少争用的方法包括局部聚合、减少共享、明确所有者以及分区。细粒度锁可能增加并发，也可能增加获取次数、锁次序复杂度和死锁风险。粗粒度锁可能足够高效，特别是临界区很短、请求不密集时。先测竞争再决定拆锁，避免把复杂度当成果。

异常处理必须保证释放。上下文管理能够让正常返回和异常路径都经过释放步骤，但它不会自动撤销临界区内已经部分完成的业务更新。若操作可能失败，需要先计算再提交、补偿或采用更明确的事务设计。互斥保证的是访问协调，不等于业务操作天然具有回滚能力。

<a id="systems-2-detail-17"></a>
### 4.3 条件变量：等待的是谓词

条件变量适合“当共享状态满足条件时继续”的场景。正确结构是在关联锁保护下检查谓词，不满足则等待，醒来后再次检查。等待动作需要以约定方式释放锁并阻塞，返回前重新获得锁。唤醒只表示值得重新检查，不是保证条件一定满足，也不是给某个线程预留资源。

为什么必须循环？多个消费者可能同时被唤醒，但第一个获得锁的消费者已取走唯一项目，其他线程再次检查时队列已空。即使没有这种交错，接口也可能允许其他原因的返回。用一次 `if` 检查后就直接消费，会把唤醒误当成资源凭证。正确性来自谓词和锁，不来自通知数量与任务数量看起来相等。

通知本身不保存一个永久的“消息”。如果先通知，之后等待者才进入等待，不能假设等待者一定会收到那次通知。应把“已有结果”“已关闭”等事实保存在共享状态中，等待者通过谓词观察。通知只是推动已等待的线程重新竞争锁，状态才是协议的记忆。

<a id="systems-2-detail-18"></a>
### 4.4 死锁、活锁与饥饿

死锁常见于多个活动互相等待对方持有的资源。若线程一先锁甲再锁乙，线程二先锁乙再锁甲，就可能形成等待环。统一锁次序能够排除这种具体的循环获取模式，但不自动解决程序中所有死锁，例如持锁等待任务，而任务也需要该锁，仍然可能卡住。

活锁是活动仍在运行却持续互相让步或重试，无法完成实际工作；饥饿是某个活动长期得不到需要的资源。没有死锁并不保证公平，也不保证有界等待。锁接口的公平性若没有明确承诺，就不能依赖“先等待者必定先获得”。业务若要求顺序，应使用具备相应协议的队列或调度设计。

超时可以让等待最终返回，却不自动修复状态。获取资源失败后，应明确是重试、取消还是返回错误，并保证已经取得的其他资源被释放。盲目循环短超时可能造成忙等和活锁。设计退出路径时，要同样认真地维护不变量。

<a id="sec-3"></a>
<a id="systems-2-detail-19"></a>
## 5. 从串行基线到受控并发

<a id="systems-2-detail-20"></a>
### 5.1 把任务改造成私有输入与显式结果

良好任务接口尽量接收明确输入并返回结果，减少对全局可变状态的隐式依赖。这样更容易在线程、进程或串行实现之间切换，也便于独立测试。对于读取共享只读模型的任务，还需要确认底层库确实允许并发读取且没有隐藏的可变缓存影响语义。

返回结果应带任务标识。并发完成顺序通常不同于提交顺序，如果只按完成列表的位置与原标签配对，可能产生安静的数据错配。可维护标识到结果的映射，再按所需顺序重组，或者使用明确保证有序返回的接口。吞吐提升若伴随样本错配，属于功能错误而不是可接受的随机性。

任务必须定义失败含义。是一个样本失败就使整批失败，还是允许记录失败并继续？重试是否可能重复副作用？若训练数据转换是纯函数，重试相对容易；若任务会写数据库或发送消息，则需要幂等键或其他协议。线程池只管理执行，不会替你决定业务上的恰好一次语义。

<a id="systems-2-detail-21"></a>
### 5.2 有界队列与背压

生产速度长期超过消费速度时，无界队列会把吞吐不匹配转化成内存增长。有界队列迫使生产者等待或按策略拒绝，从而形成背压。队列容量不应只根据“能装多少”设置，还要考虑单项大小、取消后如何清理，以及高峰流量下可以接受的等待时间。

队列里不仅有数据，还有排队延迟。把缓冲增加十倍，可能短期减少生产者阻塞，却使消费者处理到的任务更旧。对于交互请求或时效数据，这可能违反目标。正确配置应同时观察队列长度分布、完成吞吐和延迟，而不是把“生产者从不阻塞”视为成功。

背压还需要穿过系统边界。如果本地队列满了，但上游仍无限制接收请求，压力只是转移到其他缓冲。完整设计应明确每一层何时阻塞、拒绝或丢弃，并让调用方能够识别结果。训练管道的样本顺序和完整性尤其重要，不能悄悄丢样本换取漂亮吞吐。

<a id="systems-2-detail-22"></a>
### 5.3 关闭、取消与异常传播

线程通常需要协作式退出，例如检查停止事件或从队列读取结束标记。把线程设成守护线程只改变进程退出时的处理，不能代替资源清理。正式流程应停止生产、通知等待者、让消费者完成或取消已接收任务，最后等待所有工作线程退出。

取消尚未开始的任务，与终止已经运行的任务不同。某些执行器的取消方法无法打断正在执行的函数，因此函数自身应在合适边界检查停止信号。对阻塞外部调用，还需要接口本身支持超时或取消，否则主线程设置事件也不能立即让其返回。文档中应明确取消响应的实际边界。

异常必须进入主控流程。若后台线程打印了一条错误而主线程仍将结果标记成功，就会丢失失败。使用结果对象或错误通道可以让调用者逐项获取并检查；无论任务成功失败，都要保证计数、队列确认和资源释放逻辑一致。特别要避免一个工作线程异常退出后，其他线程永远等待本应由它产生的信号。

<a id="sec-4"></a>
<a id="systems-2-detail-23"></a>
## 6. 吞吐量、延迟与排队

<a id="systems-2-detail-24"></a>
### 6.1 服务时间不等于响应时间

服务时间是任务实际占用处理资源的时间，响应时间还包括排队和调度等等待。一个服务器单任务需要十毫秒服务，接近满负荷时请求可能等待远超过十毫秒。提高并发接收数量不意味着处理能力提高，可能只是让更多请求同时排队。

吞吐量是单位时间完成任务数，必须以完成而非提交计数。延迟应从定义好的到达点测到完成点，并报告分布，尤其在请求长短差异明显时，均值可能隐藏长尾。若只测已成功完成的任务而忽略超时或取消，还会引入选择偏差，使系统看起来比实际更快。

对于稳定系统，平均在途数量、平均完成速率和平均停留时间满足相应流量关系，但需要一致的系统边界和长期稳定条件。不能把瞬时队列长度代入长期平均公式，更不能在持续积压的系统中假定稳态存在。有关更完整的排队与性能模型，见第五章；本章只强调这些量必须共同解释。

可以用一个有明确假设的排队模型量化这种放大。假设到达为速率 $\lambda$ 的 Poisson 流、独立服务时间服从速率 $\mu$ 的指数分布、单个服务器先到先服务，队列容量无限，且 $\rho=\lambda/\mu<1$，这就是 M/M/1 模型。稳态详细平衡给出 $p_{n+1}\mu=p_n\lambda$，归一化后 $p_n=(1-\rho)\rho^n$，平均在途数量为 $L=\sum_n np_n=\rho/(1-\rho)$。再用同一边界的 Little 关系 $L=\lambda W$，得到平均响应时间 $W=1/(\mu-\lambda)$，平均排队时间为 $W_q=W-1/\mu$。

若平均服务时间十毫秒，$\mu=100$ 次每秒；到达五十次每秒时，平均响应二十毫秒，其中十毫秒在排队；到达九十次每秒时，响应增为一百毫秒，服务本身仍只占十毫秒。到达九十九次每秒时则达到一秒。资源利用率从九成走向接近满载，只增加少量吞吐，却可能放大等待。若 $\lambda\ge\mu$，这个无限队列模型不存在正常化稳态，不能继续代公式得负延迟或有限“稳定容量”。

真实训练加载器常有多服务器、有界队列、成批到达和长尾服务，上式不是直接预测器。它提供的是可检验机制：接近容量时应检查排队分量与到达率，增加接收线程可能只扩大在途工作；改善单任务服务或削峰才可能释放容量。有限队列还会通过阻塞、拒绝或丢弃控制积压，这些后果必须计入吞吐与失败率，不能只报告留下请求的低延迟。


<a id="systems-2-detail-25"></a>
### 6.2 批处理与公平性的折中

批处理可以摊销调用、调度和某些固定开销，但凑批需要等待。离线训练通常更关注完整作业吞吐，交互服务则可能同时约束尾延迟。某个批量在吞吐上最佳，并不保证满足交互目标。应把最大等待时间和最大批量共同作为策略，而不是无限等待凑满一批。

长任务还可能挡住短任务，造成队头阻塞。按长度分组、限制单任务资源或采用独立队列可以改善某些场景，但可能影响公平性和全局吞吐。任何调度策略都应说明优化目标，不能把某一类请求变快而另一类长期饥饿的结果称为无条件优化。

<a id="systems-2-detail-26"></a>
### 6.3 为什么更多工作线程会降低吞吐

增加线程可能使锁竞争、缓存失效和上下文切换加重；增加进程可能让序列化、内存复制与启动成本扩大；二者都可能争用同一存储或内存带宽。当资源已经饱和时，多余活动主要增加等待。性能曲线出现平台甚至回落，是资源约束的正常可能结果。

合理实验从小并发开始逐步增加，保持输入和结果校验一致，同时观察吞吐、延迟、内存和失败率。若吞吐提高但内存翻倍且尾延迟恶化，要根据目标判断是否值得。不能只选择单个速度数字，然后忽略系统其他维度的退化。

<a id="systems-2-detail-27"></a>
## 7. 可重复性与数值结果

<a id="systems-2-detail-28"></a>
### 7.1 无竞态不等于逐位相同

即使所有共享写入都正确同步，浮点规约顺序变化仍可能导致末位差异。加法在有限精度下通常不满足严格结合律，因此不同分块与合并树可能得到不同结果。这是数值执行顺序问题，不应仅凭末位差异就断言数据竞争；反过来，结果偶然相同也不能证明没有竞态。

验证应分层。业务不变量要求任务完整、样本对应正确和状态合法；数值比较可以采用与算法误差相符的容差；统计实验还要比较分布与置信范围。逐位确定性是更强要求，可能需要固定算法、调度、库版本和硬件相关条件，并付出性能代价。应先明确需求再选择机制。

<a id="systems-2-detail-29"></a>
### 7.2 随机数应绑定任务而非偶然调度

若所有线程争用一个随机数发生器，抽样顺序可能取决于调度，即使初始种子固定，每个任务得到的随机数也可能改变。更稳妥的设计是给任务分配确定的标识，再由明确规则生成各自随机流，或者预先生成任务输入。这样改变并发数时，任务内容不会悄悄变化。

独立种子并不自动证明数学上的独立随机流，具体生成器和派生方式仍需要依据库设计。对于教学实验，可以使用预先构造的确定输入，将并发调度与随机性分离；对于统计研究，应记录生成器类型和种子管理，并检查流之间的设计保证。不要把“用了不同整数种子”当作所有相关性问题已经解决。

<a id="systems-2-detail-30"></a>
## 8. 进阶：并行加速的串行与同步边界

<a id="sec-6-1"></a>
<a id="systems-2-detail-31"></a>
### 8.1 从 Amdahl 定律解释并行收益的上限

固定工作量中，设串行比例为 $s$，剩余部分能理想分给 $p$ 个执行单元，则相对于串行基线的加速为 $1/[s+(1-s)/p]$。当 $s=0.2,p=8$ 时约三点三三倍，执行单元无限多时也只趋近五倍。这个模型假定工作量与串行比例固定，并暂时忽略新增开销；实际并发方案还可能增加通信与同步。

如果扩大问题规模、改变批量或算法，已经不再是同一固定工作量比较，不能把新的结果直接代入旧比例解释。并行效率、吞吐扩展与单任务加速也不是同一个指标。本章保留这个基本边界，系统性建模和测量方法在第五章展开，以避免把一条理想公式当成实际预测器。

<a id="systems-2-detail-32"></a>
### 8.2 锁等待与临界路径可能互相强化

共享临界区若需要较长处理，增加并发会让更多任务在锁外排队。若持锁线程被调度出去，其他等待者也无法推进；若锁内还执行慢外部调用，系统就把外部等待传播给所有竞争者。一个重要改造是把无关计算和等待移出锁，仅在锁内检查并提交必要状态，但必须保证移出后不会破坏检查与提交之间的条件。

例如可以先在私有缓冲中准备新结果，再获取锁验证当前版本未变，最后一次性发布。如果版本变了，则重试或采取明确冲突处理。这比盲目缩短临界区更严谨，因为它显式承认“锁外计算期间共享状态可能变化”。这种乐观协议也有重试成本，在高冲突负载下不一定优于简单互斥。

<a id="systems-2-detail-33"></a>
### 8.3 线程池中的依赖等待

固定大小线程池里，一个任务若提交子任务并同步等待，而所有工作线程都被类似父任务占满，子任务便没有机会开始。这种死锁不需要两个显式锁，等待关系本身就足够形成资源循环。避免方式包括在主控线程组织依赖、使用不同执行层次，或把任务改造成不占用工作线程等待的调度结构。

不能简单把线程池开得很大作为根治。更大池可能暂时绕过某个例子，却保留同样结构缺陷，并带来资源消耗。应分析最坏依赖深度、阻塞任务数量和可用执行槽位，证明存在进展路径。任务图与资源分配图一起看，才能识别这类问题。

<a id="systems-2-detail-34"></a>
## 9. 标准库完整实验

<a id="systems-2-detail-35"></a>
### 9.1 人为安排交错，稳定展示丢失更新

下面用屏障让两个线程都先读到旧值，然后再写回。屏障不是错误修复，而是把危险交错变成可重复实验；随后另一个阶段用锁保护完整读改写。程序不依赖“多跑几次大概会出现”，也不把某版本字节码细节当作证明。所有线程最终都被等待结束。

```python
from threading import Barrier, Lock, Thread

state = {"value": 0}
after_read = Barrier(2)

def unsafe_once():
    old = state["value"]
    after_read.wait(timeout=5)
    state["value"] = old + 1

threads = [Thread(target=unsafe_once) for _ in range(2)]
for t in threads:
    t.start()
for t in threads:
    t.join()
assert state["value"] == 1

state["value"] = 0
lock = Lock()

def safe_many():
    for _ in range(1000):
        with lock:
            state["value"] += 1

threads = [Thread(target=safe_many) for _ in range(2)]
for t in threads:
    t.start()
for t in threads:
    t.join()
assert state["value"] == 2000
print("forced lost update: 1; protected result:", state["value"])
```

这个测试只证明特定读改写协议可以丢失更新，不证明所有整数操作都会以相同方式出错。同步后的版本把整个更新放进同一个临界区。若业务还有检查上限等条件，也必须一起放进受保护协议，不能因为计数更新本身已锁住就认为周围逻辑全部安全。

<a id="systems-2-detail-36"></a>
### 9.2 条件变量与完整关闭协议

共享状态包括结果列表和关闭标志。消费者在条件变量保护下循环等待“有数据或已关闭”，取到项目后在锁外处理。生产者完成后记录关闭并唤醒等待者。为避免教学实验中异常导致永久等待，等待操作带超时，并通过主线程收集错误；正常执行时会消费所有项目且顺利退出。

```python
from collections import deque
from threading import Condition, Thread

cv = Condition()
queue = deque()
status = {"closed": False}
received = []
errors = []

def consumer():
    try:
        while True:
            with cv:
                ready = cv.wait_for(
                    lambda: bool(queue) or status["closed"], timeout=5
                )
                if not ready:
                    raise TimeoutError("producer did not finish")
                if not queue:
                    assert status["closed"]
                    return
                item = queue.popleft()
            received.append(item * item)
    except BaseException as exc:
        errors.append(exc)

worker = Thread(target=consumer)
worker.start()
for item in range(20):
    with cv:
        queue.append(item)
        cv.notify()
with cv:
    status["closed"] = True
    cv.notify_all()
worker.join(timeout=6)
assert not worker.is_alive()
assert not errors, errors
assert received == [i * i for i in range(20)]
print("consumed:", len(received))
```

只有一个消费者负责写入结果列表，因此示例不需要对该列表再加一个独立锁；如果改为多个消费者，最终顺序也需要另行定义。主线程在消费者结束后检查结果，建立了明确完成边界。此示例没有有界容量，目的是突出条件谓词；真实长流水线应结合前文背压机制控制队列规模。

<a id="systems-2-detail-37"></a>
### 9.3 用等待型任务比较串行和线程池

实验以短暂休眠模拟外部等待，能够验证任务重叠与结果重组，但不是磁盘、网络或 GPU 实测。时间只打印，不设脆弱的加速比断言，因为共享机器负载和计时粒度会影响结果。真正断言的是两种方式完成相同任务并得到相同结果。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
from time import perf_counter, sleep

def waiting_task(task_id):
    sleep(0.01)
    return task_id, task_id * task_id

ids = list(range(12))
t0 = perf_counter()
serial = dict(waiting_task(i) for i in ids)
serial_seconds = perf_counter() - t0

t0 = perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(waiting_task, i) for i in ids]
    parallel = dict(f.result() for f in as_completed(futures))
threaded_seconds = perf_counter() - t0
assert serial == parallel == {i: i * i for i in ids}
print("serial seconds:", serial_seconds)
print("threaded seconds:", threaded_seconds)
```

线程池的上下文在退出时处理工作线程生命周期，逐个读取结果使任务异常能够传播。若去掉结果读取，并只计提交耗时，就不再是在测完成时间。本例也没有证明纯计算任务能靠线程获得同样收益，因为休眠期间没有持续执行 Python 算术。

<a id="systems-2-detail-38"></a>
### 9.4 不落地脚本的 spawn 验证

为使本章代码能够从交互执行器运行，并隔离主模块的导入状态，下面启动一个短命 Python 子解释器，在其中创建使用显式 `spawn` 上下文的进程池。工作函数采用可导入的内置 `abs`，不依赖主模块中的局部闭包。进程池与外层子解释器都正常等待结束，没有后台服务或持久文件。

```python
import subprocess
import sys

program = "\n".join([
    "import multiprocessing as mp",
    "from concurrent.futures import ProcessPoolExecutor",
    "def main():",
    "    context = mp.get_context('spawn')",
    "    with ProcessPoolExecutor(max_workers=2, mp_context=context) as pool:",
    "        values = list(pool.map(abs, [-3, -1, 2, -4]))",
    "    assert values == [3, 1, 2, 4]",
    "    print('spawn results:', values)",
    "if __name__ == '__main__':",
    "    main()",
])
completed = subprocess.run(
    [sys.executable, "-B", "-c", program],
    text=True, capture_output=True, timeout=30, check=True,
)
assert "[3, 1, 2, 4]" in completed.stdout
print(completed.stdout.strip())
```

这个例子验证启动协议、参数传递和结果合并，不是展示进程池加速：四个绝对值计算远不足以摊销启动成本。真正业务中应把自定义工作函数放在可导入模块顶层，使用主入口保护，并在相同完成语义下测量。若任务依赖某个不可序列化对象，需要重新设计资源创建位置，而不是仅仅换一个池接口。

<a id="systems-2-detail-39"></a>
### 9.5 浮点合并顺序与精确累计对照

下面三个数在常见二进制浮点环境中存在严重抵消，显式逐项累加的结果依赖顺序；`math.fsum` 提供更稳健的求和方式作为对照。这里自行写出逐项累加，而不把内置 `sum` 当作固定算法：Python 3.12 已改进浮点求和，不能要求所有版本的 `sum` 都重现旧版的抵消结果，见 [Python 的 sum 版本说明](https://docs.python.org/3/library/functions.html#sum)。我们没有启动线程，因为顺序差异本身已经足以解释问题。把确定的算术例子与并发调度分开，有助于辨认两类不同来源。

```python
import math

x = [1e16, 1.0, -1e16]
y = [1e16, -1e16, 1.0]
def left_fold(values):
    total = 0.0
    for value in values:
        total = total + value
    return total

ordinary_x = left_fold(x)
ordinary_y = left_fold(y)
assert ordinary_x == 0.0 and ordinary_y == 1.0
assert math.fsum(x) == math.fsum(y) == 1.0
print("ordinary:", ordinary_x, ordinary_y)
print("careful summation:", math.fsum(x))
```

实际并行数值库可能采用不同规约树和累加精度，因此不能假定这个三数例子的误差幅度就是训练误差。但它严格说明有限精度下重排可以改变结果。若需要研究对优化轨迹的影响，应进一步比较梯度、更新和最终统计表现，并控制随机输入，而不是仅凭一次末位变化作结论。

<a id="systems-2-detail-40"></a>
### 9.6 从操作历史推理线性化点

对一个并发容器，可以记录操作开始、结束与结果，问这些重叠操作是否能够解释为某个遵守实际先后约束的串行历史。对于某些对象，这种线性化视角比“内部用了锁”更接近接口承诺。若操作甲已经返回后乙才开始，解释历史应保留甲在乙前；若二者重叠，则可能允许任一合法顺序。每个操作看起来在某个瞬间生效的点，称为相关推理中的线性化点。

以一次受锁保护的取号为例，读取当前号码并递增可被视为在临界区中的某个点完成。两个调用可以在时间上重叠，但必须返回不同号码并对应某个顺序。若先在锁外读号、再在锁内递增，虽然递增部分互斥，两个调用仍可能返回同一旧号。由此可以看到，锁的位置必须匹配操作承诺，而不是只要出现锁就足够。

并不是所有应用都要求这种强语义。有些统计指标允许最终合并，有些状态则必须立即保持一致。选择一致性强度之前，应问调用者究竟依赖什么。例如进度展示允许短暂滞后，不代表资金扣减也可以使用同样规则。更弱语义可能带来更好伸缩性，但必须明确暴露给上层，不能在优化时悄悄改变。

<a id="systems-2-detail-41"></a>
### 9.7 发布数据与可见性的语言边界

在底层并发语言中，编译器和处理器对读写的重排、缓存与可见性由相应内存模型约束。一个线程先写数据再设置普通标志，另一个线程看到标志后是否能安全读取数据，不能脱离语言与同步规则讨论。应使用具有明确发布和获取语义的接口，而不是假定源代码顺序自动构成跨线程协议。

本章的 Python 示例通过锁、条件变量和完成等待建立顺序，不试图用普通变量忙等证明底层内存模型。这样的抽象边界也适用于扩展模块：原生代码若在运行时锁外访问共享缓冲，需要遵守其自身语言和库的线程安全规则。上层代码没有显式并发写，并不能证明底层内部状态没有冲突。

内存可见性与算法不变量还要分开。即使每次写入都及时可见，两个字段分步更新仍可能让读者看到业务上不合法组合；即使字段各自原子，也不代表整个组合原子。相反，通过不可变快照与受控发布，可以把复杂更新在私有空间完成后再整体交给读者。这种设计常比在每个字段周围分别加锁更容易推理。

<a id="systems-2-detail-42"></a>
### 9.8 取消竞争需要一个明确胜者

任务可能在“刚要完成”和“刚收到取消”之间交错，协议必须规定谁决定最终状态。可用状态机表示待处理、运行、成功、失败和已取消，并限制合法转换。不能让一个线程标记成功后，另一个线程又把同一任务改成取消，同时两边都向调用方报告最终结果。

一个常见做法是在受保护的提交阶段决定终态，只有第一个合法终态转换成功者负责发布结果。取消请求如果发生在不能撤销的外部副作用之后，还应区分“停止后续等待”和“操作没有发生”。用户按下取消并不自动回滚已经提交的数据，这一点应由业务协议明确，而不是交给线程调度偶然决定。

测试取消时，应人为安排取消发生在开始前、执行中、提交前和提交后等边界，检查资源和终态。只在随机时刻运行一次取消测试，往往覆盖不到真正危险的交错。对于教学任务，使用事件和屏障建立可控时间点，比依赖不同长度的休眠更稳定；休眠只能改变概率，不能证明某个先后关系已经发生。

<a id="systems-2-detail-43"></a>
### 9.9 失败聚合与部分结果的语义

并发批任务中，部分任务成功、部分失败是正常可能状态。主控逻辑需要决定是否返回部分结果、是否重试失败项，以及失败后已经完成的输出怎样保存。若接口声称整批成功，就应核对所有任务终态与结果数量；若允许部分成功，则应把失败标识作为结果的一部分，不能只丢弃异常。

重复执行是否安全取决于任务语义。纯数值转换通常可以重新计算；向外部系统写入、计费或发送消息则可能产生重复副作用。为任务设置稳定标识和幂等协议，有助于让重试可控，但“标识唯一”本身还不等于下游已经实现去重。应沿整个调用链核实重复请求的处理边界。

故障还可能发生在结果已经产生、但主控尚未收到确认时。这时调用方无法仅凭超时判断任务是否执行过。系统设计需要容纳这种不确定状态，或者通过查询和恢复协议消除它。这个认识能够防止把本地线程池中的简单异常处理，错误推广为分布式系统里的恰好一次保证。

<a id="systems-2-detail-44"></a>
### 9.10 把并发改造写成可审查的实验

一次可靠改造应同时保存任务定义、依赖、同步不变量、资源上界与完成条件。基线和新实现应读取相同输入，具有相同失败语义，并对任务标识做完整校验。计量时注明池是否复用、是否计入序列化、是否等待全部完成，以及有哪些底层线程配置。这样读者才能判断结果是否能够迁移到自己的负载。

对于没有收益的结果，也应保留其解释价值。它可能揭示任务粒度太小、共享资源已饱和或串行比例主导。下一步实验应有针对性地改变一个因素，检验这些候选解释，而不是不断增加线程数直到偶然出现较小时间。还应区分观测事实与原因假设。计时显示吞吐下降是一项事实，“锁竞争导致下降”则需要更多证据支持。可以通过减少共享更新次数、保持计算量不变的对照来检验，也可以收集等待和线程状态。若减少锁次数后仍无改善，就应考虑其他资源，而不是坚持原解释。记录这些反例能够帮助下一位学习者理解结论的边界，也让后续环境变化时更容易重新评估。并发学习的目标是能够证明进展、维持正确性并解释资源变化，而不是把所有程序改造成最多工作线程的形式。

## 10. 练习与详细解析

<a id="systems-2-detail-46"></a>
### 10.1 共享地址空间与对象复制

**问题。** 主线程修改一个列表，另一个线程和一个普通进程池任务是否一定都能看到新值？

**解析。** 线程若确实引用同一可变列表，存在共享关系，但何时读取、修改是否构成合法协议仍需同步。进程池任务通常接收经过传递机制得到的对象，不应假定它与父进程列表共享。若需要共享，必须使用明确定义的共享存储与协调方式。变量名称相同或初始内容相同都不能证明同一所有权关系。

<a id="systems-2-detail-47"></a>
### 10.2 线程适合等待的条件

**问题。** 一个任务九成时间等待外部资源，是否开十个线程必然十倍加速？

**解析。** 只有等待可以重叠、外部资源有足够容量、计算与调度成本不主导等条件同时较好满足时，才可能接近理想收益。如果所有等待都争用同一串行服务，线程只会增加排队。还应考虑连接限制、内存和延迟。先建立每任务资源需求，再用完成吞吐与结果完整性验证，不能仅从等待比例直接推出倍数。

<a id="systems-2-detail-48"></a>
### 10.3 GIL 为什么不能保护先检查后执行

**问题。** 某容器的单次操作在当前实现中安全，为什么“检查为空后插入”仍可能竞态？

**解析。** 业务操作由至少两个步骤组成，线程一检查后可能被切换，线程二也完成检查并插入，线程一恢复后又插入。单步安全没有给整个序列建立互斥。应将完整判断与修改放进同一保护范围，或使用明确提供所需原子语义的接口。若插入前还有外部副作用，更需要考虑重复执行与失败恢复。

<a id="systems-2-detail-49"></a>
### 10.4 条件变量为什么用循环

**问题。** 两个消费者被唤醒，但只有一项数据，为什么醒来后必须重新检查谓词？

**解析。** 第一个获得锁的消费者可以取走唯一数据，第二个重新获得锁时条件已不成立。通知并不为每个线程预留项目，也不应被当成计数票据。循环检查共享状态允许第二个继续等待；若收到关闭状态且队列为空，则退出。正确性由锁保护的谓词决定，而不是由通知次数决定。

<a id="systems-2-detail-50"></a>
### 10.5 统一锁次序的证明范围

**问题。** 所有代码都先锁甲再锁乙，是否证明程序不会发生任何死锁？

**解析。** 统一次序排除了这组锁以相反顺序形成的环，但程序还可能持锁等待线程结束、等待队列项目或等待线程池子任务，而被等待活动又需要该锁。应把所有等待资源纳入关系图，而不是只列显式锁。证明需要覆盖完整协议，也要考虑异常分支和关闭阶段。

<a id="systems-2-detail-51"></a>
### 10.6 有界队列为什么可能改善稳定性

**问题。** 生产每秒一百项，消费每秒八十项，无界队列会怎样？

**解析。** 若速率长期保持，积压平均每秒增加二十项，内存需求与等待时间都会持续增长，系统不处于稳定稳态。有界队列能够将压力传回生产者或触发拒绝策略，但它不会把消费能力自动提高到一百。还需决定上游如何处理阻塞或拒绝，确保没有把无限积压转移到另一个隐藏队列。

<a id="systems-2-detail-52"></a>
### 10.7 完成顺序与样本标签

**问题。** 使用按完成顺序返回的接口后，直接把第一个结果配给第一个标签有什么风险？

**解析。** 并发任务耗时可能不同，完成顺序不保证等于输入顺序。应把任务标识与结果一起传回，再按原标识重组；或明确使用保持提交顺序的接口。需要检查重复和缺失，不能仅比较结果总数，因为同样数量仍可能含重复项和遗漏项。结果完整性是性能比较成立的前提。

<a id="systems-2-detail-53"></a>
### 10.8 线程池内部等待为什么会卡住

**问题。** 两个工作线程都运行父任务，每个父任务提交子任务并等待，池大小也是二，会发生什么？

**解析。** 父任务占用全部执行槽位，子任务排队但没有槽位开始，父任务又不释放槽位，形成进展循环。应把依赖组织移到池外主控流程，或采用不会占槽等待的调度结构。增加池大小只对某些固定规模暂时有效，不能替代对最坏依赖结构的分析。

<a id="systems-2-detail-54"></a>
### 10.9 纯 Python 线程实验如何解释

**问题。** 在 CPython 3.11.5 上四线程算术循环没有变快，能否推断线程对所有 Python 程序都无用？

**解析。** 不能。结论只覆盖这个解释器构建和该代码路径。等待型任务可以重叠等待，释放相关运行时锁的原生计算也可能并行，其他实现与构建方式还可能不同。严谨报告应给出环境、负载与测量范围。也不能反过来从某个原生矩阵算子的线程收益推断纯 Python 循环同样收益。

<a id="sec-7-1"></a>
<a id="systems-2-detail-55"></a>
### 10.10 边界追问：局部四倍加速能否直接推整体四倍

**问题。** 原任务一半耗时被优化四倍，其余不变，整体加速多少？

**解析。** 新时间相对原时间为 $0.5+0.5/4=0.625$，加速为一点六倍。若优化还引入传递和同步开销，真实收益可能更低。这个推导假设原工作量和其他部分不变；若批量、算法或资源配置同时改变，则需要重新定义比较。应先把局部效果嵌入端到端路径，再作用户可见的性能声明。

<a id="systems-2-detail-56"></a>
### 10.11 八成计算四倍加速

**问题。** 原模型计算占八成，其余占两成，计算快四倍后整体如何变化？

**解析。** 相对耗时为 $0.2+0.8/4=0.4$，因此整体快二点五倍。此时原先的两成已经占新时间的一半，进一步只优化计算的边际收益下降。这说明瓶颈会随优化迁移。后续工作应重新测量，而不是继续依据最初比例无限投入同一阶段。

<a id="systems-2-detail-57"></a>
### 10.12 墙钟下降但 CPU 时间增加

**问题。** 并发版本墙钟从十秒降到六秒，但总 CPU 时间由十秒增到十四秒，是否矛盾？

**解析。** 不矛盾。多个核心可同时消耗 CPU，新增调度与通信也会增加总计算资源。用户可能更快得到结果，但资源成本更高。判断是否值得取决于目标，不能只看其中一个数。多进程测量还必须确认“总 CPU”确实包括工作进程，而不是只观察父进程。

<a id="systems-2-detail-58"></a>
### 10.13 有锁为什么浮点结果仍不同

**问题。** 每个局部和都正确生成，合并时也加锁，为什么不同运行仍有微小差异？

**解析。** 锁保证同一时刻合并互斥，却不保证各局部和的合并先后固定。有限精度加法随顺序变化，结果可能不同。若要求逐位一致，需要固定规约顺序或采用相应确定性算法，并确认底层库其他路径也符合要求。若只要求数值容差内一致，应按分析后的误差标准验证，而非把末位差异自动判错。

<a id="systems-2-detail-59"></a>
### 10.14 固定种子为什么不能固定任务随机输入

**问题。** 多线程共享一个随机发生器且初始种子相同，为什么某任务得到的样本仍会变化？

**解析。** 随机序列本身可以相同，但不同任务调用发生器的先后取决于调度，于是序列片段被分配给不同任务。可预生成输入，或按任务标识管理随机流，使任务内容不依赖调度顺序。同时需要遵守所用生成器的流管理设计，避免把任意种子派生当成已证明独立的随机流。

<a id="systems-2-detail-60"></a>
### 10.15 研究练习：优化共享计数器

**问题。** 每处理一个样本就加锁更新全局计数，如何设计改造和验证？

**解析。** 先保存串行基线和完整样本标识，再让工作线程局部计数，批末以较少次数合并。验证总数、重复和遗漏，覆盖任务失败与取消路径，确认计数语义是已接收还是已完成。随后在相同任务量和线程配置下测端到端，观察锁竞争与内存。若任务本身很重，合并优化可能收益很小；若计数主导，则可能明显改善。
