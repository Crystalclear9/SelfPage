## 1. 先定义一批数据的完整生命线

<a id="io-detail-2"></a>

### 1.1 以样本身份连接各阶段

设原始样本有稳定身份 $`i`$，数据版本为 $`v`$，当前训练轮次为 $`e`$，增强视图编号为 $`a`$。加载器最终应交付的不只是一个张量，而是可解释为 $`(i,v,e,a,x,y,m)`$ 的记录，其中 $`m`$ 是有效位置掩码。身份通常不必进入设备计算，却应在测试和抽样日志里保留。否则流水线再快，也难以回答重复样本、标签错位、数据泄漏和恢复后跳样的问题。

完整路径可以写成“生成索引—定位对象—读取字节—验证版本—解码—确定随机增强—组批—主机缓冲—传输—消费确认”。这些阶段并不一定各对应一个进程。一个 worker 可以同时承担读取、解码和增强；共享存储又可能把许多 worker 的读取串行化。先明确逻辑阶段，再映射物理资源，可以避免把进程数量当作实际并行能力。

训练端真正消费的是“已用于一次目标计算的批次”，不是已经读入内存的批次。已读取但尚未训练的数据称为在途工作；已经预取但因提前停止而丢弃的批次仍消耗资源，却没有增加训练预算。重启时若把生产游标误作消费游标，会把未训练的数据当作已经完成，造成静默遗漏。这一区分随后决定队列容量、检查点位置和失败重试策略。

统计契约先写清楚四件事：本轮应出现哪些样本；每个样本出现几次；样本进入哪些批次；增强如何由身份与轮次决定。性能契约再写清楚目标吞吐、可接受尾延迟、内存上限和错误处理。两套契约需要共同成立。只把解码失败的样本删除虽然可能减少等待，但优化后的训练分布已经改变，不能作为同一任务的纯加速结果。

<a id="sec-1-1"></a>

<a id="io-detail-3"></a>

### 1.2 基础算例：串行与流水线的时间账本

假设读取、变换和计算分别固定为每批 $`10,20,30`$ 毫秒，处理 $`N`$ 批。完全串行需要 $`60N`$ 毫秒。在各阶段使用独立资源、阶段之间能够充分重叠、没有额外争用的理想模型中，第一批仍需 $`60`$ 毫秒，其后每 $`30`$ 毫秒完成一批，因此总时间是 $`60+(N-1)30`$。当 $`N=1`$，没有流水线收益；当 $`N`$ 很大，平均每批趋近 $`30`$ 毫秒。

这个公式的证明来自依赖关系：第一个输出必须穿过全部阶段；稳态中最慢阶段每完成一批，才可能再释放一个输出。其他阶段只要及时供给，就不会降低该间隔。达到下界需要足够缓冲和独立资源，不能仅凭阶段名称不同就假设成立。读取和解压若争用同一核心，或者传输与计算争用带宽，理想间隔可能无法实现。

若把读取优化到 $`5`$ 毫秒，稳态仍由计算限制，收益主要出现在启动阶段和读取波动上。若计算优化到 $`15`$ 毫秒，变换的 $`20`$ 毫秒成为新瓶颈。性能优化因此具有阶段性：某次改动过去有用，瓶颈转移后重复同样改动可能不再有用。判断“无收益”不能只说实现失败，也可能是资源约束已经换了位置。

<a id="io-detail-4"></a>

### 1.3 深入讲解：路径、资源和依赖是三张不同的图

路径图描述数据先后经过什么，资源图描述谁共享核心、内存带宽、文件系统和网络，依赖图描述谁必须等谁。三者混在一起，会产生常见误判：看到三个 worker 就以为三倍读取；看到两条流就以为传输必然重叠；看到设备空闲就以为存储慢。设备空闲也可能是主进程组批、序列化、锁竞争或同步日志造成的。

设每批需要 $`r_j`$ 单位资源 $`j`$，该资源总服务能力为 $`C_j`$。不论如何排队，吞吐率 $`\lambda`$ 必须满足 $`\lambda r_j\le C_j`$，因此 $`\lambda\le\min_j\frac{C_j}{r_j}`$。这是资源守恒给出的必要上界。它比“最慢阶段”更一般，因为多个阶段可能共用同一资源；共享 CPU 的解码和增强必须先合并资源需求，再求上界。

例如每批读取占用半个核心毫秒、解码占用八个核心毫秒、增强占用四个核心毫秒，两核心机器的 CPU 上界约为每秒 $`\frac{2000}{12.5}=160`$ 批。即使把读取 worker 加到十六个，也无法突破这个 CPU 服务上界，还可能增加上下文切换。反过来，若 worker 大量阻塞在网络，增加少量并发可能使等待重叠，从而接近带宽上界。

端到端排查应先画出这一小账本，再用证据修正：记录等待位置、阶段服务量和共享资源利用情况。模型只是解释器，不是把经验数字包装成定律。真实系统中的预读、压缩、缓存、批量提交和动态频率会让服务量随并发改变，公式中的常数需要在代表性条件下重新测量。

### 图解：流水线首批延迟与稳态节拍

![流水线首批延迟与稳态节拍](images/03-concept.svg)

**图解。** 本图与前面的十、二十、三十毫秒主算例使用同一组数据。每个矩形是一个批次在一项独立资源上的服务；沿同一批号追踪阶段依赖，沿同一行检查资源是否同时处理两批。B0 从零开始，读取在十完成，变换在三十完成，计算在六十完成。B1 虽在二十已读好，仍要等变换资源到三十空闲；它的计算还要等 B0 到六十完成。

四批的计算完成时刻依次为六十、九十、一百二十、一百五十毫秒。因此首批延迟仍为六十，后续间隔为三十，四批流水总耗时一百五十，而完全串行为二百四十。首批、稳态间隔与有限任务总时长是三个量，不能用同一个“每批平均”混称。矩形之间的空白还可帮助定位等待：变换可能等输入或等自身资源，计算可能等变换产物。

图假定阶段资源独立、耗时固定、缓冲足够；它没有证明真实硬件必然按这个时刻表运行。接下来的有界队列图会明确“产出完成但无法入队”的额外状态，最后再用同一任务的有序与无序交付解释统计顺序。

## 2. 从文件字节到应用缓存：缓存命中到底省了什么

<a id="io-detail-6"></a>

### 2.1 三层缓存对应三种不同的成本

操作系统页缓存通常缓存文件内容的内存页；应用的原始字节缓存保存读取结果；解码缓存保存已经解析的数组或图像；最终张量缓存还可能包含归一化或增强结果。命中不同层，省下的工作不同。页缓存命中通常仍要经历文件接口和解码；解码缓存命中可以省解析，却可能占用远大于压缩文件的空间。

以压缩图像为例，文件平均二十千字节，解码成三通道浮点张量后可能超过一兆字节。把一万张图的最终张量全部保留，内存规模可能从数百兆上升到十余吉字节。不能用“数据集文件很小”推断解码缓存也小。对象头、索引、内存对齐、临时数组、进程副本和队列中的重复引用或复制都应进入账本。

Linux 内核的[内存概念文档](https://www.kernel.org/doc/html/latest/admin-guide/mm/concepts.html)说明了页缓存与文件访问的关系。具体操作系统、文件系统和访问方式会改变细节。本章只采用可移植的结论：文件再次读取可能命中系统维护的缓存，应用并没有因此跳过全部数据处理。下面的实验模拟应用缓存，不尝试从 Python 宣称清空系统缓存。

缓存也不是只有“命中率”一个指标。若命中的都是原本很快的记录，省下的时间可能很少；若少量大对象占满空间，命中率高也可能拖累其他工作。应同时报告命中次数、节省的读取与解码成本、占用字节、失效次数和驱逐成本。对训练而言，还要检查缓存是否冻结了本应随轮次变化的随机增强。

<a id="io-detail-7"></a>

### 2.2 缓存键是数据语义的一部分

安全缓存键至少能区分样本身份、原始内容版本和确定性预处理版本。若缓存最终增强结果，还必须把随机视图身份纳入键，或者明确承认重复使用同一增强。只用文件路径作为键，在原位替换文件后可能返回旧数据；只用样本编号，在两个数据集编号重叠时可能串读。缓存命中返回错误版本，比直接报错更难定位。

内容哈希有较强的身份含义，但计算哈希也要读取字节。文件大小和修改时间便宜，却不是内容绝对相等的证明。实践中可以由数据发布流程生成不可变清单，清单记录内容摘要与版本，运行时再使用清单身份构造缓存键。关键不是任何任务都必须完整哈希，而是把正确性依赖写出来，避免把弱启发式误当严格保证。

失效需要与读取一致。假设一个线程检查版本为一，另一个线程替换原始内容，第一个线程再读取新字节却用版本一缓存，缓存键和内容就不匹配。不可变对象名、版本化读取接口，或在一个受控事务内获取版本与内容，都可避免这种时间差。单纯在缓存字典外加锁，只保护字典结构，并不自动保护外部数据源的一致快照。

训练数据通常可以设计为不可变发布：新版本写到新位置，全部写完并验证后再原子切换清单。这样旧实验继续使用旧清单，新实验使用新清单，不必让每个 worker 猜测哪些缓存该失效。可变在线数据则需要更明确的一致性级别，例如允许多少陈旧、如何记录事件时间，以及重跑是否能取得同一快照。

<a id="io-detail-8"></a>

### 2.3 命中率、工作集与替换策略

设缓存容量能容纳 $`K`$ 个等大对象，工作集是某段时间内反复访问的对象集合。若访问循环长度为 $`K+1`$，最朴素的最近最少使用策略可能在每次访问前都恰好驱逐下一个要用的对象，命中率为零。这不是实现故障，而是访问顺序与容量共同造成的反例。顺序扫描一个远大于缓存的数据集，也不保证下一轮热启动。

相反，若每个大分片连续抽取多个样本，分片级缓存可以复用读取结果。代价是样本相邻性增强，批次可能更相关。可以用“先随机分片，再在分片内随机，配合跨分片缓冲”的折中，但它通常不等于全局均匀随机排列。正确描述是新的抽样过程，在统计效果可接受的条件下换取局部性，而不是宣称随机性完全不变。

多进程缓存还有放大问题。每个 worker 各缓存一份热门数据，总内存可能近似 worker 数乘单份缓存。共享内存可以减少副本，但需要管理生命周期、写入所有权与失效通知。只读数组共享较容易；可变对象若被增强函数原地修改，则可能污染其他任务。缓存返回值是否允许修改，是接口必须明确的契约。

<a id="io-detail-9"></a>

### 2.4 机制展开：小文件优化改变的是开销结构

设每次打开和元数据处理耗时为 $`h`$，平均文件字节为 $`s`$，有效顺序带宽为 $`B`$。读取 $`n`$ 个独立小文件的粗略时间是 $`nh+\frac{ns}{B}`$。把它们打包成 $`k`$ 个分片，理想可把第一项降至 $`kh`$，但增加索引查找、压缩块解码、读取放大以及分片更新成本。这个模型解释小文件为何慢，也解释“合并越大越好”为何不成立。

若只需要分片中一个短记录，却必须解压整个大块，读取放大系数可定义为实际读取字节除以有效载荷字节。文件数减少可能伴随放大系数上升。在随机访问任务里，小块索引压缩格式可能比单个巨大压缩流更合适；在顺序遍历任务里，较大分片又可减少请求与定位成本。选择应由访问模式决定，不由格式名字决定。

远程对象存储还要考虑每次请求往返时延、并发上限和限流。增加并发可以隐藏单次时延，直到带宽或服务配额饱和；超过饱和点后，重试与排队可能反而放大尾部。存储吞吐、请求数、有效样本数要同时统计，避免系统看起来每秒传了很多字节，实际上大部分是重复下载与读取放大。

压缩决策也可做账：未压缩每批 $`S`$ 字节，压缩比例 $`c`$，解压时间 $`D`$。不重叠时压缩有利需要 $`\frac{(1-c)S}{B}>D`$；若传输和解压能重叠，则应比较瓶颈而非简单相加。解压占用训练所需 CPU 时，减少网络耗时也可能增加设备饥饿，因此最终判断仍要回到端到端吞吐。

<a id="visual-03-advanced"></a>

### 图解：缓存命中不等于命中了正确的数据版本

![缓存命中不等于命中了正确的数据版本](images/03-advanced.svg)

若缓存键只有路径字符串，文件在原路径更新后仍可能命中旧结果。此时命中率很高，却没有正确反映输入版本；缓存正确性要求键和失效规则覆盖会影响结果的依赖。

图中的错误来自刻意缺失版本条件。可采用内容摘要、可信版本号或受约束的失效协议，但还要考虑配置、代码和外部表变化；只检查修改时间也有适用边界。

## 3. 有界队列、背压与尾部：吞吐不是平均耗时的倒数

<a id="io-detail-11"></a>

### 3.1 队列为什么必须有容量约束

生产端每秒产生 $`\lambda_p`$ 批，消费端最多每秒处理 $`\lambda_c`$ 批。若长期 $`\lambda_p>\lambda_c`$ 且不丢弃、不阻塞，积压大致以 $`(\lambda_p-\lambda_c)t`$ 增长。任何有限内存最终都会耗尽。因此稳定系统必须让生产速率受消费约束、明确丢弃策略，或把积压移到有容量管理的外部存储。多开几个生产 worker 无法消除这个守恒关系。

背压意味着下游容量用尽时，上游暂停接收新工作。一个有界阻塞队列可以实现最基本的背压，但容量的单位要说清楚：按批数限制不能控制变长批次的实际字节。长文本、视频和稀疏对象大小差别很大，十个批次可能相差十倍内存。更稳健的方案可以同时限制批次数、总字节与最大单样本大小。

队列上限还要覆盖“队列外在途对象”。若有四个 worker，每个正在解码一批，输出队列有两批，主进程正组批一批，设备传输还保留一批来源，内存并不只是两批。可以用保守账本 $`M_{\rm peak}\lesssim M_{\rm base}+(Q+W+H)M_{\rm batch}+M_{\rm scratch}`$ 表示，分别对应队列容量、生产并发、额外持有批次和临时工作空间。变长时应使用可解释的上界或实测分位。

阻塞不是坏现象。生产者被背压阻塞，可能恰好说明数据供给已经足够，下游计算成为瓶颈。如果只盯着“所有 worker 都很忙”，反而可能优化出不断制造无用积压的系统。指标应以有效训练吞吐和受控内存为中心，再检查必要的缓冲是否能吸收波动。

<a id="io-detail-12"></a>

### 3.2 Little 定律如何使用，何时不能乱用

在稳定、具有一致统计边界的系统里，平均在途数量 $`L`$、平均到达率 $`\lambda`$ 和平均停留时间 $`W`$ 满足 $`L=\lambda W`$。直觉是把一段足够长时间内每个任务占据系统的时长相加：按任务求和得到任务数乘平均停留，按时间求和得到平均在途数乘观察时长，再除以观察时长即可。边界上尚未完成的任务贡献在长窗口中需要可以忽略。

若每秒完成一百批，平均有二十批在途，平均从进入到完成约二百毫秒。它没有说明每批计算只需二百毫秒，也没有承诺第九十九分位同样小。停留时间包含排队、等待和服务；时间边界、任务单位与统计稳定性必须一致。把“每秒样本数”乘“每批耗时”会因单位混乱得到错误结果。

有限训练任务存在启动与收尾；负载持续增长的系统不稳定；任务被静默丢弃时到达数和完成数不一致。这些情形不能机械套稳态等式。可以仍做有限窗口的占用积分，但应保留未完成任务的边界项。排队论模型是诊断工具，不应拿一个公式代替对系统是否稳定的检查。

增加队列容量通常先帮助吸收生产波动，随后只增加等待。在平均吞吐固定时，如果平均在途量翻倍，Little 定律意味着平均停留时间也翻倍。对离线训练，较高停留未必直接影响目标，但会延长故障恢复时的重放距离，增加过期数据和内存；对在线训练，它还可能增加数据陈旧度，影响实际模型适应速度。

<a id="io-detail-13"></a>

### 3.3 平均、分位与队头阻塞

两个加载器平均都用十毫秒，不代表训练效果相同。一个每批稳定十毫秒，另一个九十九批一毫秒、一批九百零一毫秒，平均一样，但第二种需要更大预取才能掩盖长停顿。有限队列未必装得下这么多提前数据，设备仍会周期性断粮。要观察服务时间分布、消费者等待分布和相关性，而不只看均值。

有序消费可以保证按预先定义的索引顺序训练，但慢样本可能挡住后面已完成的样本，这叫队头阻塞。无序消费可以减少这类等待，却可能把读取耗时变成隐式抽样权重：若大图、长文本或某个类别解码更慢，训练前缀会偏向容易完成的样本。完整遍历时集合相同，也不意味着提前停止时看到的分布相同。

一个折中是允许内部并行乱序完成，再用序号重排；它保留训练顺序，却仍受队头阻塞和重排缓冲容量限制。另一个折中是按预先确定的批次分组，组内允许加载并行，组间固定顺序。无论采用哪种，都应明确顺序是统计契约还是可调整的性能参数，不能在不知情时让调度器代替采样器。

尾延迟还可能存在相关性。远程存储拥塞往往同时拖慢许多 worker，独立随机波动的直觉会失效。增加预取对短独立尖峰有效，对持续数秒的共同故障无能为力。需要在时间轴上查看排队和等待，而不是只画总体直方图；同样的延迟分布，集中成一段长停顿和分散在全程，对流水线的影响不同。

<a id="visual-03-mechanism"></a>

### 图解：背压：队列满后生产者需要等待

![背压：队列满后生产者需要等待](images/03-mechanism.svg)

本图把“队列满了”展开成可复算的调度，而不是只画容量折线。它采用一个单生产者、一个单消费者：每批生产十毫秒、消费三十毫秒、FIFO 队列容量两批，共七批。容量只算排队元素，不含消费者正在处理的一批，也不含生产者已经完成但尚未成功入队的一批。生产者在输出入队前一直占有自己的批次缓冲，采用**服务完成后阻塞**；若消费取队列与生产入队同刻发生，先释放队列位置。不同约定会改变中间状态，必须先写清楚。

沿图上半部分看 B4：它在四十毫秒开始、五十毫秒完成生产；此时消费者还在处理 B1，队列中的 B2、B3 已占满两个位置，所以 B4 只能留在生产者手中。七十毫秒消费者取走 B2，B4 才能入队，生产者才开始 B5。后面的两次阻塞完全同理，分别为八十到一百、一百一十到一百三十毫秒。三段等待合计六十毫秒，但消费者仍持续工作，总完工时刻为二百二十毫秒。

**为什么等待没有降低这个算例的吞吐？** 第一批十毫秒到达，消费者之后七次各用三十毫秒，最早也只能在 $`10+7\times30=220`$ 毫秒完成。图中的有界调度恰好没有让消费者断粮，所以达到这一下界。继续加大队列无法突破消费能力；它只会让生产者更早做完、更多批次提前占内存。反过来，如果生产本身有长停顿，缓冲可能帮助维持消费，本例没有据此断言小队列在所有输入上最优。

设第 $`i`$ 批的生产完成、成功入队、开始消费和完成消费分别为 $`f_i,a_i,c_i,e_i`$，编号从零开始，队列容量为 $`Q\ge1`$。生产者必须等前一批入队才能继续，所以 $`f_i=a_{i-1}+10`$，第一批从零生产。对于 $`i\ge Q`$，它还要等较早的第 $`i-Q`$ 批开始消费，才有队列空位：

$$
a_i=\max(f_i,c_{i-Q}),\qquad
c_i=\max(a_i,e_{i-1}),\qquad
e_i=c_i+30.
$$

最初不足 $`Q`$ 批时不需要等待释放位置；第一批之前消费者空闲。下面实现这些边界，返回完整时刻，而不是只返回总耗时。它是模型仿真，不调用睡眠，也不是机器性能基准。

```python
def bounded_schedule(produce=10, consume=30, batches=7, capacity=2):
    if any(type(v) is not int or v <= 0
           for v in (produce, consume, batches, capacity)):
        raise ValueError("all arguments must be positive integers")
    rows = []
    producer_free = 0
    consumer_free = 0
    for i in range(batches):
        start = producer_free
        finished = start + produce
        # A consumer takes from the queue before a simultaneous enqueue.
        slot_free = rows[i-capacity]["consume_start"] if i >= capacity else 0
        admitted = max(finished, slot_free)
        consume_start = max(admitted, consumer_free)
        consumer_free = consume_start + consume
        rows.append({
            "batch": i, "produce_start": start, "produce_end": finished,
            "admit": admitted, "consume_start": consume_start,
            "consume_end": consumer_free,
        })
        # A completed-but-blocked batch still occupies the producer.
        producer_free = admitted
    return rows

rows = bounded_schedule()
assert [r["produce_end"] for r in rows] == [10, 20, 30, 40, 50, 80, 110]
assert [r["admit"] for r in rows] == [10, 20, 30, 40, 70, 100, 130]
assert [r["consume_start"] for r in rows] == [10, 40, 70, 100, 130, 160, 190]
assert sum(r["admit"] - r["produce_end"] for r in rows) == 60
assert rows[-1]["consume_end"] == 220
print("bounded queue: 60 ms producer blocking, 220 ms total")
```

图下半部再固定五十毫秒这一瞬间：排队两批、消费一批、生产者持有一批，共有四份批对象。若每份负载为 $`M`$，这几项共需 $`4M`$ 的存储，而不是队列容量乘出的 $`2M`$；解码工作区、额外副本和框架状态仍需另算。这里假设每个角色独占一份批缓冲，不把实际共享存储重复记账。变长批次还必须按字节而不只按对象数限制。

有界生产者／消费者的等待条件和唤醒原则，可对照 [OSTEP 条件变量章的有界缓冲问题](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-cv.pdf)。上面的确定性调度解释时刻与容量，真实程序还需锁、条件谓词、关闭和异常传播协议，不能把这组整数递推视为一个线程安全队列的实现。

## 4. 测量阶段耗时：为每个数字声明边界

<a id="io-detail-15"></a>

### 4.1 服务时间、等待时间和端到端时间

服务时间是某阶段实际占用处理资源的时间，等待时间是任务已准备好却没有获得服务的时间，端到端时间包含路径上的二者。主进程调用迭代器直到返回的时间，测到的是它暴露给消费者的等待，可能已经被预取隐藏了大量读取与解码。不能据此断言数据加载本身几乎免费，只能说当时没有明显阻塞消费者。

同理，在后台线程中分别累加读取和增强时间，会得到工作量指标，不等于墙钟总时间。多线程重叠时各线程服务时间之和可以超过总耗时；CPU 时间与墙钟时间也有不同含义。测量表应把单位和边界写在列名里，例如“消费者等待毫秒”“每批解码核心毫秒”“窗口墙钟秒”，避免后续错误相加。

设备异步执行会进一步扩大差异。主机提交计算后返回，不代表设备完成。正式吞吐应在完整窗口边界建立正确完成条件，再计算总样本数除以墙钟时间；算子内部分析则用设备事件或合适剖析工具。每一步强制同步虽然便于理解，却会改变原先的重叠行为，适合定位依赖，不适合直接宣称原系统稳态性能。

数据等待与计算耗时还可能互相影响。CPU 过量解码占满内存带宽，会降低主机传输速度；后台压缩检查点会争用存储；日志序列化可能阻塞主线程。应先测一个尽量完整的系统，再用受控替换逐步去掉阶段。只把每段单独跑到最快再拼起来，会忽略同时运行时的资源竞争。

<a id="io-detail-16"></a>

### 4.2 分位数需要足够观测和一致定义

第九十五分位不是“最慢百分之五的平均”，而是按规定分位估计方法得到的阈值。样本很少时高分位不稳定；只测二十批就报告精确到小数点后两位的第九十九分位，没有相应信息量。可以报告原始次数、窗口数量、分位算法和重复实验范围，让读者知道尾部结论有多稳健。

批次大小不同也会让“每批延迟”难以比较。动态批次应同时记录有效样本数、有效 token 数或有效像素数；吞吐分母包含哪些被屏蔽位置要声明。长度分桶减少 padding 后，每秒张量元素可能下降，但每秒有效 token 上升，后者更贴近学习工作量。只看一个吞吐单位可能把真正收益隐藏掉。

热身不能任意删除所有慢样本。第一次打开文件、初始化 worker、建立缓存和分配内存可以单独作为冷启动指标；正式稳态窗口应覆盖具有代表性的慢记录，而不是挑选“看起来平稳”的一小段。如果周期性每千批出现一次停顿，测一百批恰好避开它，不足以说明长期训练没有问题。

重复测量应尽量保持输入身份和次序可比，交替执行候选方案，记录机器负载与缓存条件。若基线永远先跑、候选永远后跑，候选可能只是享用了页缓存。无法控制冷缓存时，可以诚实报告“同一热缓存协议下的结果”，而不是进行未经证实的冷盘性能比较。

## 5. 数据加载的统计契约与失败语义

<a id="io-detail-18"></a>

### 5.1 随机增强应由逻辑身份决定

用 worker 编号作为唯一随机种子，会使增强依赖样本被哪个 worker 处理。改变 worker 数、任务完成次序或恢复位置，可能改变增强轨迹。更可解释的做法是从全局种子、数据版本、轮次、样本身份和视图编号派生局部随机种子。此时调度改变不影响同一逻辑任务的增强，便于比较系统优化前后的数值结果。

派生方式不应依赖 Python 默认字符串哈希，因为不同进程或运行可能采用不同随机化盐。可以使用明确编码规则的稳定摘要，再从摘要取得随机种子。字符串拼接要避免歧义，例如身份“十二”和“二”不能因分隔不严密而与另一组字段碰撞；结构化编码或长度前缀能够清晰表达字段边界。

这一方案也有边界：同一个样本在同一轮可能被有放回抽样多次，若希望每次不同增强，就把抽样出现序号纳入键；若希望对比两种增强视图，就使用不同视图编号。仅靠样本编号会固定这些重复出现的增强。随机性是否独立不是一个函数参数能自动保证的，需要先定义“什么算一次新的随机试验”。

为每个样本构造局部随机数发生器会有开销，可以用批量派生、计数器式方案或预先生成的任务种子优化。优化时仍要保留可复现映射的含义。跨库随机源也要分别管理：Python、NumPy、框架和图像库可能维护独立状态，只设置其中一个并不保证所有增强受控。

<a id="io-detail-19"></a>

### 5.2 坏样本、重试和重复交付

读取失败可能是暂时网络错误，也可能是永久损坏或格式不支持。无限重试会把一个坏样本变成永不结束的队头阻塞；零重试直接跳过又可能改变类别比例。合理策略是区分错误类型，设置有限次数与退避，最终把失败身份、原因和处理策略纳入结果。训练是否允许跳过，要由数据契约决定，而不是让异常处理临时决定。

至少一次交付意味着任务失败后可能重放，容易产生重复；至多一次意味着避免重复但可能遗漏；恰好一次通常需要把任务身份、提交状态和消费确认放到一个一致的协议里。对本地训练，不一定需要复杂事务系统，但至少要明确“读取成功”和“优化器已更新”哪个事件算提交。两者之间的崩溃窗口不能靠一句保存游标消失。

若训练步骤已经更新参数，而消费确认未写入，恢复后重放该批会再更新一次；若先确认再更新，崩溃可能丢掉一次更新。把参数、优化器状态、随机状态和已消费游标在同一检查点边界恢复，通常比逐批外部确认更可控。代价是崩溃后回退到上个一致检查点，并重跑一段数据；这应作为恢复协议的一部分说明。

重试还应保持样本与增强语义。若第一次读取失败后重新抽一个样本代替，那么失败率高的对象进入训练的概率下降。若每次重试重新采增强，最终被接受的增强分布也可能与耗时相关。较清楚的做法是重试同一逻辑任务，把任务身份和随机键固定，让重试只改变传输行为。

<a id="io-detail-20"></a>

### 5.3 分片、最后一批和全局分母

多个 worker 读取流式数据时，必须把数据源显式分片，否则每个 worker 都可能从头遍历相同记录。简单按全局序号对 worker 数取模，能在静态流上避免重复，但要求每个 worker 看到相同顺序；远程流若各自有不同过滤结果或不同起点，该条件会失效。以不可变分片清单分配所有权通常更容易验证。

最后不足一批的数据是保留、丢弃还是补齐，会影响有效样本数。多 worker 分别丢弃自己的尾批，可能比全局合并后只丢一次丢得更多。使用可迭代数据集时，框架的具体尾批语义应核对当前版本文档，而不是从单进程经验类推。这里可以参照[PyTorch 2.10 数据加载说明](https://docs.pytorch.org/docs/2.10/data.html)确认接口行为。

变长序列尤其要把分母带到训练端。每批平均损失若按有效 token 数计算，再简单平均各批均值，会给小批更大权重。正确的全局统计通常先累加损失分子与有效数量，再相除。数据流水线不仅要交付输入，还要提供掩码和可合并计数，否则训练端无法恢复原本想优化的目标。

缓存、分片和过滤规则应共享同一个数据版本。若训练清单与标签缓存来自不同版本，样本数量对得上也可能标签错位。推荐用小型审计批检查身份、内容摘要、标签和掩码的联结，再扩大并发。速度优化前后的样本集合、重复次数和按身份派生的增强应能自动比较。

## 6. 可重复实验：版本缓存、调度与流水线守恒

<a id="io-detail-22"></a>

### 6.1 实验一：带版本键的有界解码缓存

下面用内存字节代替文件，用读取计数代替不稳定的墙钟耗时。实验目的不是证明某台磁盘有多快，而是验证缓存的正确性：同一版本第二次命中，新版本必须重新解码，容量用尽按最近最少使用顺序驱逐。缓存值是不可变元组，消费者不能原地修改它，从接口层避免共享缓存被增强污染。

```python
from collections import OrderedDict

class DecodeCache:
    def __init__(self, capacity=2):
        self.capacity = capacity
        self.items = OrderedDict()
        self.reads = 0
        self.hits = 0

    def get(self, source, sample_id, transform_version):
        # source 中的 (版本, 字节) 是本实验的原子快照。
        version, raw = source[sample_id]
        key = (sample_id, version, transform_version)
        if key in self.items:
            self.hits += 1
            self.items.move_to_end(key)
            return self.items[key]
        self.reads += 1
        value = tuple(int(x) for x in raw.decode("ascii").split(","))
        self.items[key] = value
        self.items.move_to_end(key)
        while len(self.items) > self.capacity:
            self.items.popitem(last=False)
        return value

source = {"a": (1, b"1,2"), "b": (1, b"3,4"),
          "c": (1, b"5,6")}
cache = DecodeCache(2)
assert cache.get(source, "a", "decode-v1") == (1, 2)
assert cache.get(source, "a", "decode-v1") == (1, 2)
assert (cache.reads, cache.hits) == (1, 1)
source["a"] = (2, b"8,9")
assert cache.get(source, "a", "decode-v1") == (8, 9)
cache.get(source, "b", "decode-v1")
cache.get(source, "c", "decode-v1")
assert len(cache.items) == 2
before = cache.reads
cache.get(source, "a", "decode-v1")
assert cache.reads == before + 1
print("reads, hits, resident:", cache.reads, cache.hits, len(cache.items))
```

执行结果为读取五次、命中一次、驻留两项。新版本一旦产生，旧缓存项不会错误命中，但它可能暂时占据容量，直到被驱逐。若版本更换频繁，可以主动移除同一身份的旧版本；若旧实验仍需旧快照，则应允许多版本共存。这里的替换策略服务于可解释的小实验，不是完整的线程安全缓存实现。

实验还有两个重要限制。第一，按对象个数限制容量，假设对象等大；真实图像大小不同，应以实际缓冲字节或保守估算控制。第二，数据源字典的取值被我们视为原子快照，真实文件系统中版本检查与读取可能分离。把小实验迁移到实际系统时，需要补齐这两条假设，而不是仅复制字典代码。

### 6.2 实验二：离散流水线验证首批与稳态

固定阶段时长的递推为 $`C_{j,i}=\max(C_{j-1,i},C_{j,i-1})+t_j`$，其中 $`C_{j,i}`$ 表示第 $`i`$ 批在第 $`j`$ 阶段的完成时刻。第一项确保上一阶段已产出，第二项确保本阶段已空闲。边界完成时刻为零。它模拟独立串行服务器与足够中间缓冲，不包含共享带宽和动态抖动。

```python
def pipeline(stage_times, batches):
    stages = len(stage_times)
    end = [[0.0] * (batches + 1) for _ in range(stages + 1)]
    for j, service in enumerate(stage_times, 1):
        for i in range(1, batches + 1):
            end[j][i] = max(end[j-1][i], end[j][i-1]) + service
    return end[-1][1:]

out = pipeline([10, 20, 30], 10)
assert out[0] == 60
assert out[-1] == 60 + 9 * 30
assert all(b-a == 30 for a, b in zip(out, out[1:]))
serial = 10 * sum([10, 20, 30])
print("serial, pipeline, first:", serial, out[-1], out[0])
# 提高已非瓶颈的读取速度，不改变稳态完成间隔。
faster_read = pipeline([5, 20, 30], 10)
assert faster_read[-1] - faster_read[-2] == 30
```

输出串行为六百时间单位，流水线为三百三十，首批为六十。这个确定性仿真允许我们逐项检查理论，不受操作系统调度噪声影响。不过它不能回答现实中开几个 worker 最合适，因为模型假设没有把 worker 管理、缓存和核心竞争计入。模型证明的是依赖约束下的时间结构，不是任何实现都必然达到的速度。

本章第 3 节的有界算例已经把“阶段产出但下游无空间”作为状态，使生产者保持占用或阻塞；如果希望研究共享 CPU，则应把多个逻辑阶段投影到同一资源队列。扩展模型时，每增加一个机制，都应找一个可手算的极小案例验证。未经校验的大模拟器也会制造精确却错误的数字。

### 6.3 实验三：完成顺序会改变训练前缀

以下使用两个 worker 的确定性调度模型。耗时四的样本设为类别一，耗时一的样本设为类别零。按完成时间直接消费，早期前缀会偏向快类别。我们比较同一任务集合的完成序与提交序，不使用真实睡眠，也不把仿真时间当成机器性能。

```python
import heapq
from collections import Counter

jobs = [(0, 1, 4), (1, 0, 1), (2, 0, 1),
        (3, 0, 1), (4, 1, 4), (5, 0, 1)]
workers = [(0, 0), (0, 1)]
heapq.heapify(workers)
events = []
for sample_id, label, cost in jobs:
    start, worker = heapq.heappop(workers)
    finish = start + cost
    events.append((finish, sample_id, label))
    heapq.heappush(workers, (finish, worker))
completion = sorted(events)
unordered = [sample_id for _, sample_id, _ in completion]
ordered = [sample_id for sample_id, _, _ in jobs]
labels = {sample_id: label for sample_id, label, _ in jobs}
assert set(unordered) == set(ordered)
assert Counter(unordered) == Counter(ordered)
print("submit:", ordered, "complete:", unordered)
print("positive in first 3:",
      sum(labels[i] for i in ordered[:3]),
      sum(labels[i] for i in unordered[:3]))
assert sum(labels[i] for i in ordered[:3]) == 1
assert sum(labels[i] for i in unordered[:3]) == 0
```

提交顺序前三条含一个正类，完成顺序前三条全为负类。两种方式完整遍历后的身份多重集合相同，前缀却不同。这直接解释为什么“没有少样本”不足以证明训练过程相同。固定训练步数、早停、学习率随步数变化和在线数据时效，都会让前缀顺序影响最终结果。

有序消费需要缓存提前完成的任务，并等待尚未完成的最小序号。缓冲受限时，后面的任务可能无法继续提交，这就是正确性、内存与吞吐的交换。若任务允许顺序变化，可以接受无序模式，但应把这种变化明确写进实验协议，并检查耗时是否与类别、长度、来源或难度相关。

<a id="io-visual-completion-prefix"></a>

#### 连续图解：沿实际任务追踪“完成”如何变成“被训练”

![同一六任务的两个worker调度、提交序与完成序及训练前三条的类别差异](images/03-completion-training-prefix.svg)

这张图直接展开上面的六条 `jobs`，颜色表示类别，矩形长度表示服务时间。worker 0 先处理耗时四的样本零，到时刻四后再处理样本五；worker 1 连续处理样本一、二、三，再从时刻三处理耗时四的样本四。于是完成序列精确为

$$
(1,2,3,0,5,4),
$$

相应完成时刻为 $`(1,2,3,4,5,7)`$。图中没有随机调度或同刻完成的并列选择，因此这个顺序完全由所给服务量和分派规则决定。它不同于提交顺序 $`(0,1,2,3,4,5)`$，但包含同一身份多重集合。

**按顺序消费需要在哪里等待？** 样本一在时刻一完成，仍不能越过序号零；到时刻三，已有一、二、三三条结果等待重排。零在四完成后，才能按零、一、二、三交付。五虽然五时就完成，仍要等四到时刻七才可按四、五交付。因此“worker 有结果”与“训练端按协议可以收到结果”是两种完成边界。若重排缓冲太小，后续提交还会受背压影响；本图假定容量足够。

图底虚线只划出前三条：按提交序读到的标签为 $`(1,0,0)`$，按完成序则为 $`(0,0,0)`$。如果预算只够三次更新，两个训练过程接收的经验分布已经不同；即使完整遍历，也不能仅凭集合相同断言逐步优化轨迹相同。用最小标量平方损失即可复算：

$$
\ell(\theta;y)=\frac12(\theta-y)^2,\qquad
\theta_{k+1}=\frac12\theta_k+\frac12y_k,\qquad \theta_0=0.
$$

提交序前三次更新得到 $`0.5,0.25,0.125`$，完成序前三次都为零。若六条全部更新完，提交序参数为 $`0.265625`$，完成序为 $`0.625`$。这里没有声称其中一个更能泛化；它只是隔离出“相同样本集合”不能消除的顺序效应。若训练规则改为在同一参数基点汇总全部梯度、最后只更新一次，则又是不同的计算协议。

[PyTorch DataLoader 文档](https://docs.pytorch.org/docs/2.10/data.html) 也提示无序交付可能影响可复现性，并在数据不均衡时扭曲交付分布。图中的分派是本章透明仿真，不等同于某版本 DataLoader 的全部预取实现。迁移时应记录样本身份、批次和交付顺序，依据任务决定是否允许顺序变化，再测量吞吐；不能把取消排序产生的统计变化归类为纯执行加速。

至此三张图形成一条连续检查路径：第一张确定每批的阶段依赖和最慢资源；第二张把排队、阻塞及内存持有位置展开；第三张追踪调度如何影响训练端的实际输入。只测其中一层，就可能把未被消费的预取量、排队驻留量或提前完成的快类别误当成训练收益。

### 6.4 实验四：调度无关的随机视图与身份审计

本实验使用稳定摘要派生种子，验证反向调度仍给同一身份相同视图，换轮次则获得另一组可复现值。增强只是给整数加入小扰动，便于逐条比较；实际任务应为每种随机变换传递受控随机源。断言核对的是逐身份映射，而不是平均值碰巧接近。

```python
import hashlib
import json
import random
from collections import Counter

def seed_for(global_seed, version, epoch, sample_id, occurrence=0):
    raw = json.dumps([global_seed, version, epoch, sample_id, occurrence],
                     ensure_ascii=False, separators=(",", ":")).encode("utf-8")
    return int.from_bytes(hashlib.blake2b(raw, digest_size=16).digest(), "big")

def view(sample_id, epoch):
    rng = random.Random(seed_for(17, "data-v2", epoch, sample_id))
    return sample_id + rng.uniform(-0.1, 0.1)

ids = list(range(10))
left = {i: view(i, 3) for i in ids}
right = {i: view(i, 3) for i in reversed(ids)}
assert left == right
assert any(view(i, 4) != left[i] for i in ids)
expected = Counter(ids)
delivered = Counter([0, 1, 2, 3, 4, 5, 6, 7, 8, 8])
assert delivered != expected
print("missing:", list((expected-delivered).elements()))
print("duplicate:", list((delivered-expected).elements()))
```

输出缺失身份九、重复身份八。仅检查交付条数等于十会完全漏掉这个错误。训练数据审计应该至少区分集合、重复次数与顺序；若存在合法重复抽样，就用预定任务序列的多重集合对照，而不是简单要求每个身份只出现一次。数据验证的判据必须与真正抽样设计一致。

此处种子摘要不是密码学安全需求，也不依赖样本内容保密；选择稳定摘要是为获得跨调度一致的映射。若更换摘要算法、字段编码或随机数实现，结果可能改变，版本信息应进入可复现实验说明。固定种子能控制特定随机路径，不能消除硬件规约、第三方非确定算子和外部数据变动。

## 7. 从模型走向真实加载器：一套可证伪的排查过程

<a id="sec-6-1"></a>

<a id="io-detail-27"></a>

### 7.1 数据流水线的吞吐由受约束资源决定

先用相同形状、精度和模型的合成输入确定计算侧基线；再使用已经在主机内存中的真实解码结果，加入组批与传输；随后加入增强、解码和实际读取。每次只改变一个主要路径，使性能差异能够对应到机制。合成张量不能替代真实任务评价，它只是排除一部分等待来源的对照。

若纯计算吞吐已低，继续增加 worker 大概率无助于根因；若读取加入后下降，要进一步区分字节供给、解码 CPU、随机访问和元数据。可以比较压缩字节缓存与解码缓存：前者改善很少、后者明显改善，说明解析或增强更值得关注；两者都无改善时，还应检查组批、序列化和线程竞争，而不是立刻归咎于设备。

预取深度从小到大做有限扫描，同时记录有效吞吐、消费者等待、首批延迟和峰值内存。看到吞吐进入平台而内存继续上升，就有理由停止增大。最优值往往不是一个永远通用的常数：数据尺寸、增强强度、CPU 配额、远程存储状态和设备计算速度改变后，平台位置也会变化。

每次性能实验都要附上质量约束。若降低图像分辨率、截断文本、减少随机增强或跳过长样本，速度变快是在减少任务工作量。它可能是合理产品选择，但应同时衡量目标质量与公平性。系统优化的更强证据是在相同逻辑任务上减少等待或搬运，而不是只对比两个来源不同的吞吐数字。

<a id="io-detail-28"></a>

### 7.2 持久 worker、锁页内存与嵌套并行

保留 worker 可以摊薄每轮创建和初始化成本，但 worker 内部的缓存、随机状态与数据对象也会持续存在。主进程更新一个普通对象字段，不代表已经启动的子进程立刻看见变化。若轮次参与增强种子，需要通过显式任务字段或可靠共享状态传递，不能依赖“我在主进程改过 epoch 了”的直觉。

锁页内存能参与某些高效主机到设备传输路径，但锁住的内存不易被操作系统换出，过量使用会挤压系统余量。它也不会消除磁盘读取、解压和布局变换。具体异步传输条件需结合设备、源内存和流依赖核对，下一章再讨论。CPU 环境中无须为了形式一致而强行启用设备相关选项。

嵌套并行常见于“多个加载 worker，每个解码库又开多个线程”。若八个 worker 各启用八线程，在八核心机器上形成六十四个活跃线程，实际可能增加争用。应同时控制外层进程数和内层库线程数，测有效工作与切换成本。CPU 利用率接近满载，既可能是高效工作，也可能是忙于调度与重复搬运。

批量解码和向量化增强有时比增加 worker 更有价值，因为它减少每样本解释器、分配和调用开销。代价可能是等待足够样本形成批次，影响首批延迟；变长记录还可能增加 padding。系统设计应在调用粒度、局部性和响应时间之间做具体取舍，不是把所有独立操作都改成最大批量。

<a id="io-detail-29"></a>

### 7.3 预取与恢复：游标到底在哪里提交

设消费者刚完成第百批，生产端已经取到第一百零八批。如果只保存生产端游标，恢复时从第一百零九批开始，八个在途批次被遗漏。若只保存最初游标又不保存模型状态，可能把已经更新过的数据重复训练。应把模型、优化器、调度器、随机状态和逻辑消费位置作为一个一致恢复点。

严格复现还可能需要保存抽样排列或可重建它的种子、轮次和出现序号。可恢复协议可以选择丢弃所有在途数据，恢复到最近已提交消费位置，再按稳定任务键重新生成。这样无需持久化大队列，但要求原始数据快照仍可访问，随机视图由逻辑身份决定，外部副作用可重试。

数据源若是在线流，重放能力依赖其保留策略和偏移语义。偏移不一定等于样本编号，同一记录可能被解析成多个训练片段。检查点需要记录到足以重建逻辑任务的粒度；否则“从同一个文件偏移恢复”仍可能改变切片边界与重复计数。研究级可重复性建立在这些具体协议上，而不只是一张配置表。

训练日志也需要区分“看到的样本”“产生梯度的样本”“完成优化步的样本”。遇到梯度溢出而跳过更新、全掩码批次或故障重放时，这些数字可能不同。对齐学习率预算和吞吐时选择哪个计数，要与目标保持一致；否则优化步更少的方案可能被误报为相同预算下更快。

## 8. 进阶练习与详细解析

<a id="io-detail-31"></a>

### 8.1 十六个问题：从账本推导到统计反例

**题一：** 读取、增强、计算分别为四十、二十、三十毫秒，共十批，求串行与理想流水线总时长。**解析：** 串行为九百毫秒。第一批九十毫秒，稳态间隔四十毫秒，流水线总时长为 $`90+9\times40=450`$ 毫秒。平均每批四十五毫秒而不是四十，因为启动没有被无限批次摊薄。若有人报告四百毫秒，检查其是否遗漏了前后边界，或测的是已预热窗口。

**题二：** 在上一题中把计算加速到十毫秒，吞吐上界怎样变化？**解析：** 瓶颈仍为读取四十毫秒，稳态吞吐上界不变；首批从九十变七十，总时长降到四百三十毫秒。局部计算三倍加速只让十批任务少二十毫秒。对长任务相对收益趋近零，说明必须分清启动延迟与稳态吞吐，不能直接把某阶段加速倍数作为系统倍数。

**题三：** 生产速率每秒十五批，消费速率每秒十批，一批五十兆字节，无界队列一分钟多占多少内存？**解析：** 忽略启动和波动，净积压三百批，约十五千兆字节，尚未计对象和临时副本。有限内存必然遇到问题。把队列容量限制为二十批可以约束一部分积压，但生产者随后会阻塞，长期有效产出只能匹配消费者。这不是背压降低了本可实现的训练吞吐，而是它阻止了无法被消费的超额生产。

**题四：** 稳态每秒五十批、平均三十批在途，平均停留是多少？能否推出第九十九分位？**解析：** 由同一边界下的 Little 定律，平均停留为零点六秒。分位无法推出：全部批次都接近零点六秒与少数批次极慢可以具有同样均值。若系统积压不断增长，稳态前提不成立；若五十实际是每秒样本而三十是批次，也不能使用这个除法。先统一单位与边界。

**题五：** 一个可容纳三个对象的最近最少使用缓存，循环访问四个对象，会发生什么？**解析：** 从空缓存开始依次访问甲乙丙丁，再循环甲乙丙丁。插入丁驱逐甲，随后访问甲又驱逐乙，每次都未命中。工作集仅比容量大一个对象也足以让命中率为零。把策略换成其他算法未必完全解决，根本因素是访问模式与容量；分片重排可能改善局部性，但须检查其对抽样顺序的影响。

**题六：** 文件原位替换但路径没变，路径缓存是否仍然正确？**解析：** 不保证。路径标识位置而不必标识内容版本。可将不可变版本或内容摘要纳入缓存键，并确保键与读取内容来自一致快照。仅在缓存字典上加互斥锁，只阻止两个线程同时改字典，不能防止外部发布者在版本检查与文件读取之间替换内容。需要把一致性问题放到数据发布协议中处理。

**题七：** 为什么缓存随机增强后的张量可能改变学习目标？**解析：** 原目标包含对随机变换的期望，若每个样本只缓存一次增强，训练实际反复访问有限固定视图，近似目标发生变化。它未必一定导致质量下降，但不能宣称与逐轮重新增强完全等价。可以缓存确定性解码结果，把随机增强放在缓存之后；若希望缓存多视图，应明确视图生成与抽样方案，并计入容量。

**题八：** 四个 worker 各缓存两吉字节，输出队列六批，每批二百兆字节，是否只需约九点二吉字节？**解析：** 这只是部分账本，而且十进制兆与二进制吉应统一单位。还缺每个 worker 正在构造的批次、主进程持有项、传输源、临时解码对象、运行时基础开销以及系统缓存。总内存应按所有权与生命周期估计，避免同一共享对象重复计数，也避免把实际复制误当共享。峰值往往发生在旧对象尚未释放而新对象已经分配时。

**题九：** 无序完成后完整样本集合一致，为什么仍可能改变结果？**解析：** 梯度更新一般不可交换，早期批次还受到较大学习率影响。若耗时与标签相关，训练前缀的类别比例会变化；提前停止时甚至总体已消费集合不同。验证应比较任务多重集合、顺序及增强映射，再决定哪些变化可以接受。只核对轮次末总数，无法证明中途优化过程保持一致。

**题十：** 坏样本失败后随机抽另一个替代，是否等价于原采样？**解析：** 若失败概率依样本而异，最终被消费的身份分布会偏向低失败概率对象。例如长文本更易超时，替代策略降低长文本权重。可以有限重试同一身份，最终显式报告失败并按预定策略处理。若选择允许排除，应发布新的数据清单和预算，而不是把排除隐藏在性能代码里。

**题十一：** 每个 worker 丢弃自己的尾批，与主进程合并后丢一次尾批有何不同？**解析：** 例如两个 worker 各有三条记录，批大小四，分别丢尾会得到零批；合并六条后可得到一批并丢两条。实际框架行为依数据集类型与实现而定，不能从直觉推断。测试时用可列举的小数据集记录交付身份，多 worker、尾批与分片的组合最好逐项核对。

**题十二：** 批甲有两个有效 token，平均损失一；批乙有八个有效 token，平均损失三。全局平均是多少？**解析：** 分子为 $`2\times1+8\times3=26`$，分母十，结果二点六。简单平均两个批均值为二，是批次等权目标。两者都可以定义，却是不同目标。数据加载器若不提供有效数量，训练端很难修正，因此掩码和计数属于数据接口，而不是可有可无的日志字段。

**题十三：** 提交到第一百零八批、只训练到第一百批，恢复应选哪个游标？**解析：** 必须与模型和优化器检查点的提交状态一致。若参数只包含前百批更新，恢复数据应重建其后的任务，预取的八批不能被当作已训练。把在途队列丢弃并从一致消费边界重放是可行方案，但需保证原始快照和随机任务键可恢复。保存单独生产游标不足以保证正确性。

**题十四：** 为什么给每个 worker 固定不同种子仍不能保证改变 worker 数后视图不变？**解析：** 样本到 worker 的映射变了，同一身份会使用不同随机状态，而且此前处理过多少任务也改变状态位置。按逻辑身份、轮次和出现序号派生种子，把增强从执行拓扑中分离。若某个增强库仍使用隐藏的全局随机源，还需显式接管该源；只构造一个 NumPy 发生器并不能控制其他库。

**题十五：** 第二遍格式乙快于第一遍格式甲，能否说乙更快？**解析：** 不能直接归因于格式。第二遍可能享有操作系统页缓存、已初始化 worker 或编译缓存。可交替执行顺序、使用相同可解释的热缓存协议、把冷启动另列，并保留重复窗口的分布。若无法稳定获得冷缓存，应该限制结论到已测条件，不要声称验证了冷磁盘优势。

### 8.2 边界追问：更多预取是否一定提高吞吐

**题十六：** 加载平均比计算快，但偶尔出现半秒停顿，如何选择预取深度？**解析：** 先测停顿是否独立和多长。若计算每批二十毫秒，理想地吸收半秒完全断供需要约二十五批可消费库存；这只是粗略覆盖量，不保证库存恰好在停顿前已填满。若主机内存只容纳五批，继续调一个预取参数无法突破容量约束，可能需要减少停顿来源、改变缓存层或降低每批内存。

如果停顿来自所有 worker 共同访问的存储故障，增加 worker 可能同时遭遇相同故障；如果来自单个慢样本，有序消费还会受队头阻塞影响。应先查时间相关性，再选择缓冲或并发。若加载已稳定且计算是瓶颈，额外预取通常不提高稳态吞吐，只增加在途工作与恢复负担。有效答案需要同时给出吞吐曲线、等待曲线、内存曲线和数据语义检查。

## 9. 进一步研究：把性能改动写成可以被推翻的命题

<a id="io-detail-34"></a>

### 9.1 一份小型研究设计

选择一个明确命题，例如“在固定样本与增强映射下，解码缓存减少消费者等待，并且不超过指定内存预算”。先定义对照组与候选组，保存相同身份序列，使用逻辑随机键固定增强，分别运行多个完整窗口。每个窗口记录有效样本吞吐、首批延迟、消费者等待分位、驻留与峰值内存、缓存命中和失败身份。机器负载与软件版本也进入记录。

然后明确可推翻条件：候选组身份多重集合不同，说明统计契约失败；吞吐提高但峰值超预算，说明资源约束失败；只有第一次基线慢而后续交替比较无差异，说明原结论可能来自热缓存；解码时间明显下降但端到端不变，说明它原本不是主瓶颈。这样的研究即使得到负结果，也能提供清楚知识，而不只是“调参没有成功”。

可进一步研究自适应预取，但控制器必须考虑滞后。短窗口看到消费者等待就立即翻倍队列，可能在存储恢复后产生大量无用积压；看到队列满就立即减少 worker，又可能对短暂计算抖动过度反应。可以采用有上下限、缓慢调整、保留安全余量的策略，再与固定配置比较。所有自适应逻辑仍受容量守恒和数据契约约束。

<a id="io-detail-35"></a>

### 9.2 本章应留下的判断能力

遇到“加载慢”，先问慢在哪里、以什么单位、在什么缓存状态下，以及结果是否包含真实消费。遇到“多开 worker 有用”，继续问其隐藏了等待还是增加了服务能力，是否触发嵌套并行。遇到“缓存命中率很高”，继续问命中了哪一层、节省多少工作、是否返回正确版本。每个追问都把抽象性能口号还原成可测机制。

更深一层，数据加载既是系统问题，也是统计问题。调度可能改变顺序，缓存可能冻结增强，重试可能改变分布，分片可能重复样本，尾批可能改变目标分母。只有同时理解数据身份、资源所有权与提交边界，才能设计既快又可解释的训练流水线。这些能力会在下一章的分布式采样、全局损失归约和故障恢复中继续使用。
