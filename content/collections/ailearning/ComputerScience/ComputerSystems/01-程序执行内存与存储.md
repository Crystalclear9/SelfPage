## 1. 程序如何运行：把抽象层分开

<a id="systems-1-detail-2"></a>
### 1.1 从源程序到硬件状态变化

理解程序运行，首先要问“哪一层的程序”。数学公式说明输入输出关系，源代码规定语言中的计算步骤，解释器或编译器把这些步骤落实为机器可执行的操作，操作系统负责进程、地址空间和设备访问，处理器最终执行其指令集定义的行为。

这些层次彼此关联，却不具有一一对应关系。一行矩阵乘法可能进入数千行经过优化的底层实现；一个源语言变量也不保证总有一个固定内存位置，它可能被优化掉、放进寄存器，或者与其他值共享存储。

从较低层观察，可把顺序执行近似写成状态转移 $`S_{t+1}=F(S_t,I_t)`$。状态包括程序计数器、寄存器以及可访问的存储，指令决定下一步变化。这个模型有助于推理正确性，但真实处理器可能同时处理多条指令、预测分支并改变内部执行顺序。只要最终可观察行为满足指令集和内存模型的约定，内部实现不必逐条按源程序顺序完成。因而“处理器每次只执行一行代码”不是可靠的性能模型。

指令集规定软件能够观察和使用的接口，例如某类指令的操作数、异常与寻址方式。微体系结构决定如何实现接口，例如流水线深度、缓存组织和执行端口。相同指令集的两种处理器可以运行同一机器代码，却有不同性能；相同源代码在不同编译参数下也可能产生不同机器代码。解释性能时，应同时说明语言、实现、编译方式、硬件与工作负载，不能只凭处理器名字预测耗时。

操作系统不需要参与每一次普通整数加法。用户态代码可以直接执行许多指令；当程序要求访问受保护资源、申请某类系统服务或处理异常时，才通过约定进入内核。系统调用通常比简单算术昂贵，但其成本取决于操作与环境。读取一个字节的源语言调用，可能首先由语言缓冲区满足，甚至不产生新系统调用。反过来，一次简单的数组访问若触发缺页，也可能引发远多于一次加载指令的工作。

学习 AI 系统时，这种分层尤其重要。Python 循环的每一步可能有解释、对象访问和类型判断成本，而一个数组算子能把许多元素的工作交给连续底层循环。向量化常减少解释开销，但并不自动减少总算术量或内存流量。一次生成巨大中间矩阵的向量化表达式，可能比按块执行更占内存，甚至更慢。因此，优化不能停留在“写得更短”或“调用了底层库”。

<a id="systems-1-detail-3"></a>
### 1.2 编译、解释与运行时不是互斥阵营

解释执行通常指运行时读取某种程序表示并推动计算，编译则把一种程序表示变换成另一种。一个系统可以先把源代码编译为字节码，再由解释器执行字节码；也可以在运行过程中把热点代码编译成机器代码。两者组合并不矛盾。CPython 的具体字节码和自适应解释机制是实现细节，不宜把某一版本的字节码数量当作所有 Python 的执行成本。

程序还依赖运行时服务，例如对象分配、垃圾回收、异常传播和动态加载。某段函数第一次调用较慢，可能来自导入、内存分配、算法选择或编译，不能直接归结为硬件缓存未热。区分一次性初始化和稳态执行后，才可能设计合理实验。例如把初始化时间单独报告，随后在相同输入规模下重复测量，并说明重复是否复用了已分配的缓冲区。

机器代码也不是整个执行环境。可执行文件包含代码和数据，还需要加载器建立映射，动态链接器解析依赖，运行时准备必要状态。函数调用约定描述参数如何传递、哪些寄存器由谁保存等接口。把这些约定混用会造成错误，即便双方都使用同一种处理器。这里需要建立的认识是：程序能够执行，依赖一系列彼此匹配的契约，而不是某个文件中“有代码”就足够。

<a id="systems-1-detail-4"></a>
### 1.3 栈、堆与对象所有权的关系

栈常用于保存调用相关的信息，堆常用于动态对象，但这些是实现组织方式，并不等于源语言变量的固定分类。局部变量可以引用堆上的对象；返回一个对象也不表示返回了已经失效的栈空间。对于 Python，名称绑定到对象，赋值通常建立引用关系；对于具有值语义、显式指针或借用规则的语言，相似语句可能有不同含义。

判断内存是否可以释放，关键是对象是否仍被拥有或引用，以及相关运行时采用什么规则。调用结束并不保证所有相关内存立刻还给操作系统，因为对象可能被返回、保存在容器中，或者分配器保留已释放的块供后续复用。更深一步，程序内部的空闲空间未必能够拼成一个可释放给系统的连续区域，所以“逻辑上已无用”和“系统监控下降”之间可能有距离。

<a id="sec-1-1"></a>
<a id="systems-1-detail-5"></a>
### 1.4 基础算例：先算模型状态的字节量级

假设一百万个参数使用每元素四字节的表示，权重净数据量为四百万字节，即四兆十进制字节，约三点八一 MiB。若梯度同精度且优化器维护两个同形状状态数组，则这四组数据约占一千六百万字节。这个算式计算的是明确列举的数组有效载荷，不含对象头、对齐、激活、输入、临时空间或分配器预留。

用符号表示，状态净量为 $`M=P(b_w+b_g+b_m+b_v)`$。只有在这四项均实际存在且同时存活时，才应把它们相加。某些推理路径没有梯度和优化器状态；某些混合精度训练还维护主权重副本；分片会改变单设备持有的份额。因此，“每参数十六字节”应被理解为特定配置的估计，不能作为所有训练系统的普遍常数。

这个估计仍然很有用。它能帮助分辨数量级错误：如果仅权重就超过设备容量，减小批量不可能消除这部分常驻开销；如果权重很小但批量略增就溢出，则应优先检查随批量变化的激活与工作区。先通过数量级排除不可能的解释，再进一步测量，比无目标地尝试清理缓存更有效。

## 2. 存储层次与局部性

<a id="systems-1-detail-7"></a>
### 2.1 为什么不能只有一种存储器

理想存储器应同时容量大、延迟低、吞吐高、能耗小且价格低，但实现中存在约束。靠近计算单元的小型存储适合快速访问，较大容量通常需要更复杂的寻址和更长的数据路径。由此形成寄存器、若干级缓存、主存和持久存储等层次。层次的具体数量、共享方式和包含关系因硬件而异，不应把某台机器的缓存容量当作定义。

延迟是一次操作从开始到得到结果的时间，带宽是持续传输时单位时间搬运的字节数。高带宽不意味着低延迟。例如很多独立请求可以同时在途，以较长单请求延迟换取高总吞吐；若程序每一步必须等待上一步给出下一个地址，则很难提供这种并行度。随机指针追踪和顺序扫描即使读取同样多的有效字节，也可能表现完全不同。

缓存通常按块搬运数据。程序读取一个很小的元素，硬件可能把包含它的一整块带入缓存；之后访问附近元素就可能复用这次搬运。缓存行的大小是硬件属性，本章实验不会假定所有系统都是同一个数值。如果一个访问模式只使用每块中的极少内容，就会浪费已传输的数据。但预取、合并访问、缓存命中和页面行为都可能改变实际流量，不能直接用源程序加载次数代替内存控制器流量。

<a id="systems-1-detail-8"></a>
### 2.2 时间局部性、空间局部性与工作集

时间局部性指一个值在不久之后还会被使用，空间局部性指附近地址也将被访问。工作集是在相关时间窗口内程序实际需要保持可用的数据集合。若工作集适合某层缓存，反复使用可能主要在该层完成；一旦跨过容量界限，性能曲线可能发生变化。然而容量不是唯一因素，映射冲突、替换策略、共享线程和预取同样重要。

考虑按行连续存储的二维矩阵。按行遍历通常在短时间内访问相邻元素，按列遍历则可能跨越较大步长。对于以指针组织的嵌套 Python 列表，“按行存储”还不等于一个紧凑数值矩阵：外层装的是引用，内层也可能装引用，数值对象可能分散。若用它演示低层缓存，应明确解释器与对象布局会干扰结果，不能把时差全部解释成缓存行效果。

局部性也不等于代码循环越少越好。把多个操作融合到一次扫描中，通常能够减少中间数组读写；但融合后若寄存器需求过大、向量化变差或出现依赖链，也可能产生新的成本。优化的本质是改变数据在层次间的移动与复用方式，而不是机械地减少循环结构。

<a id="sec-2-1"></a>
<a id="systems-1-detail-9"></a>
### 2.3 机制展开：用块流量而非只用元素数推理

假设某个简化系统每次搬运大小为 $`L`$ 字节的块，数组元素大小为 $`e`$，且 $`L`$ 是 $`e`$ 的整数倍、数组边界按块对齐。连续读取足够长的数组并用尽每块，流量约为元素有效载荷加少量边界浪费。若每隔一块只读取一个元素，流量可能接近每元素一整块，即有效利用率约 $`\frac{e}{L}`$。这是上界式直觉，前提包括冷数据、无其他命中和相关层确实按该块搬运。

写入也不能总按一个元素一次写回计算。某些缓存策略先把目标块读入，再修改并在以后写回；某些流式写入策略可改变这种行为。写合并、脏块淘汰和缓存一致性也会影响总流量。因此，理论估计应注明“最低必要流量”还是“某种缓存策略下的预计流量”，避免把二者当成相同测量对象。

用这种思路分析归一化操作，会发现均值、方差、标准化、仿射变换若分成多遍，可能多次扫描相同数组。改成适当融合可以减少读写，但方差的数值稳定性、并行归约和中间统计的存活又提出约束。系统优化与数值算法不能割裂：少一次内存访问的算法若在极端输入下严重丢精度，整体方案仍不正确。

<a id="deep-dive-2"></a>
<a id="systems-1-detail-10"></a>
### 2.4 深入讲解：分块为什么能提高复用

以 $`C=AB`$ 为例，每个输出元素都需要许多乘加。朴素循环若在每次输出更新中重新从慢层读取输入，会产生大量重复流量。分块把若干输入片段和输出片段留在快层，在它们被逐出前完成更多更新。此时同一输入字节服务于多个算术操作，算术强度提高。分块大小必须与快层容量、并行组织和布局匹配，过大可能溢出，过小又会增加管理成本。

这里的关键不是“矩阵乘法天然快”，而是矩阵乘法提供了可利用的数据复用结构。小矩阵可能还没来得及摊销调用与调度开销；非连续输入可能需要打包；某种数据类型可能没有同样优化的实现。理论操作数相同，不表示实现走相同路径。验证时应同时记录形状、步长、数据类型和是否包含转换成本。

将这一理解迁移到注意力计算，会发现显式保存巨大中间矩阵可能增加容量和流量需求，而分块与重计算可以改变二者。不过本章不从 CPU 小实验推断 GPU 内核性能；GPU 的片上存储、线程组织和访问合并需要设备专门分析。本章只建立分析问题的语言，具体加速应通过对应设备上的实验确认。

## 3. 虚拟内存：地址不等于物理驻留

<a id="systems-1-detail-12"></a>
### 3.1 地址空间、页面和映射

进程通常看到独立的虚拟地址空间。虚拟地址经过硬件与操作系统共同管理的映射，关联到物理内存或其他支持资源。两个进程出现相同数值的虚拟地址，并不意味着访问同一物理位置；同一个物理页面也可能被多个地址空间映射。地址空间提供隔离与灵活组织，不能据地址数值直接推断真实容量使用。

页面是常见的映射管理单位，页表保存相关关系和权限，地址转换缓存则减少反复查询成本。页面大小、支持的大页机制和具体转换层级依赖系统。大页可能减少转换项数量，但也可能带来分配、碎片和管理上的代价，不是无条件优化。对于初学者，先区分“数据访问未命中缓存”和“地址转换遇到问题”比记住某个页大小更重要。

一次访问可能遇到尚未建立的映射、尚未驻留的数据，或者权限不满足等情况。缺页异常并不都意味着从磁盘读数据；按需分配零页、写时复制和权限处理也可能产生相关事件。监控工具中不同类别的缺页统计含义可能不同，不能只看到计数上升就断言系统正在大量交换到磁盘。

<a id="systems-1-detail-13"></a>
### 3.2 保留、提交、驻留与释放

“申请了内存”可能指保留地址区间，可能指获得了可使用的提交承诺，也可能指实际触碰后页面进入物理内存。这些状态应分别理解。具体术语和承诺策略因操作系统而异；在 Windows 上，虚拟地址区间的保留与提交具有明确区分，但不应据此反推所有系统采用完全相同的策略。

驻留集合描述某个时刻处于物理内存中的页面范围或规模。程序只保留一个很大的地址区间，可能没有同样大的物理驻留；反过来，大量文件页进入缓存也会占用物理资源，哪怕不完全归到你所观察的某个私有堆指标。把总虚拟空间、私有提交量、工作集和共享页简单相加，容易重复计数或比较不同概念。

释放语言对象不保证工作集立即下降。一方面分配器可能保留块以供复用，另一方面操作系统可以按照压力和策略管理页面驻留。判断泄漏应观察重复等价工作后的稳定趋势、仍存活的对象与引用链，以及相关分配域的变化。只凭一次峰值之后没有回到初始数值就宣布泄漏，证据不足。

<a id="systems-1-detail-14"></a>
### 3.3 写时复制与共享页的边界

写时复制允许某些映射在尚未修改时共享底层页面，一旦需要写入再产生私有副本。这可以降低最初复制大量数据的成本，却不意味着后续修改免费。在支持相应进程创建方式的系统中，父子进程可能起初共享许多页面；一旦工作进程修改数据或运行时元数据，物理占用可能增加。Windows 的常见进程启动路径与这套行为不同，不能把其他平台的经验照搬。

共享映射还引出统计上的困难。把所有进程的驻留量直接相加，可能把同一共享页面重复计算；只看私有占用又可能忽略共享池的总需求。报告多进程内存时应说明采用何种指标和归属规则，必要时同时提供整个任务组的总资源数据。精确归因往往需要系统专门工具，本章标准库实验不假装提供跨平台统一的物理内存真值。

<a id="systems-1-detail-15"></a>
### 3.4 统一地址与统一物理资源并非一回事

有些系统能够让不同处理单元通过相近的编程接口访问数据，甚至在统一虚拟地址范围中表示指针。这不必然意味着所有处理单元具有相同访问延迟、带宽和一致性保证。某些设备使用独立显存，某些系统共享物理内存，还有迁移与映射机制。讨论“统一内存”之前，应先明确硬件架构、运行时语义和数据当前所在位置。

对于 AI 程序，主机可见、设备可见、页锁定、异步复制可用和设备执行完成是不同事实。一次返回的复制调用可能只完成提交；释放源缓冲区是否安全，需要遵守框架的生命周期约定。这里保留概念边界即可，具体同步、设备事件和性能建模在后续章节结合运行时展开。

<a id="systems-1-detail-16"></a>
## 4. 对象、缓冲区与训练内存

<a id="systems-1-detail-17"></a>
### 4.1 有效载荷、容器与间接引用

一个包含一百万个数值的 Python 列表，不能直接按一百万乘四字节估算。列表通常保存对象引用，数值对象可能单独分配，还存在容器头、容量预留和分配器成本。紧凑数值缓冲区则可以按元素类型的字节大小估算有效载荷。两种表示数学上容纳相同的数列，内存布局和访问路径却不同。

`sys.getsizeof`给出特定对象的浅层大小，不会自动递归统计所有被引用对象。把浅层大小相加也不总正确，因为多个容器可能指向同一对象，导致重复计算。深层统计需要按对象身份去重，还要明白某些原生扩展拥有的内存并不完整暴露给一般对象遍历。一个数字不能同时代表所有内存层次。

对象身份相同表示它们引用同一对象，但`id`在语言层面只承诺对象生命周期内的身份标识语义；不要把它普遍当成物理地址。对象销毁后标识值可以被复用，因而跨时间收集对象标识时也要注意归属。把这些实现细节与硬件地址区分开，能够避免形成“打印出地址就知道数据在哪里”的错觉。

<a id="systems-1-detail-18"></a>
### 4.2 视图、复制与别名分析

视图通过共享底层数据并改变解释方式来避免复制。它可能只需一个较小描述符，但对原存储的依赖仍然存在。一小段视图如果保留了一个大缓冲区的所有权链，可能使大缓冲区无法释放；反过来，主动复制小片段虽然增加当下流量，却可能允许释放大对象。是否复制应依据后续生命周期，而非一概认为“零复制最好”。

别名还影响正确性。两个变量看似不同，实际可能共享同一片数据，修改一方会改变另一方。对只读输入创建只读视图可减少误改，但只读视图不一定能阻止另一个可写别名修改底层数据。若需要不可变化的快照，必须依据接口保证选择真正独立的副本或受控所有权机制。

内存视图的形状和步长描述怎样从逻辑索引定位字节。形状乘元素字节给出逻辑有效载荷，但跨步视图所覆盖的地址跨度可能更大，连续切片与抽样切片也不同。比较内存占用时，要分清逻辑元素总量、底层分配大小和访问跨度。三者可能相等，也可能相差很多。

<a id="systems-1-detail-19"></a>
### 4.3 训练状态的生命周期表

把训练的一次迭代拆成输入准备、前向、损失、反向、更新和释放等事件，记录各对象何时创建、最后使用和可释放，才能估计峰值。参数跨迭代常驻，梯度可能在反向逐渐生成，激活可能在前向保留并在反向逐步释放，优化器临时空间则可能只在更新时出现。简单静态求和通常是保守估计，精确峰值取决于这些区间重叠。

设对象 $`i`$ 大小为 $`m_i`$，存活指示函数为 $`a_i(t)`$，理想有效载荷峰值为 $`\max_t\sum_i m_i a_i(t)`$。这里不含碎片、对齐、分配器缓存及设备工作区，因此真实分配峰值可能更高。这个表达式的价值在于提示我们优化时间关系：提前释放、原位复用和重计算改变存活区间，不一定改变每个数组本身的元素数。

梯度累积减少单次微批激活需求，但并不会按累积次数缩小参数和累计梯度。优化器状态通常也仍然存在。如果把每个微批的损失都保存为带图对象，累积过程中还可能意外保留整条计算图。正确的标量记录方式与数学上的梯度累积是两件事，前者应避免保留不再需要的反向依赖。

<a id="systems-1-detail-20"></a>
### 4.4 重计算、分片与低精度分别改变什么

激活重计算用额外计算换取少存一部分中间状态；分片把某些状态分布到多个设备或进程，但引入通信与协调；低精度减少每元素字节数，却影响表示范围和误差。三种方法作用的维度不同。一个参数状态主导的问题，不一定能靠只针对激活的重计算充分解决；一个带宽主导的问题，也可能因低精度获得速度收益而不只是节省容量。

低精度还要区分存储、计算和累加精度。权重以较低精度存储，并不保证所有中间或优化器状态都使用同样精度；某些操作出于稳定性需要更高精度的统计量。因此，应写出真实配置的状态清单，再计算字节数。混合精度作为一个名称并不足以决定整个系统的内存需求。

<a id="sec-5"></a>
<a id="systems-1-detail-21"></a>
## 5. 内存带宽、延迟与算力是不同约束

<a id="systems-1-detail-22"></a>
### 5.1 建立最小流量的下界

考虑对长度为 $`N`$ 的独立数组计算 $`y_i=a x_i+b`$，假定每元素四字节、输出另存且输入标量忽略不计。按算法有效载荷口径，需要读取约 $`4N`$ 字节并写入约 $`4N`$ 字节，完成约 $`2N`$ 个算术操作，因此按最低必要流量估算的算术强度约为四分之一操作每字节。它不是算术强度的下界：在同一计量边界上，额外写分配等流量会增大分母、降低强度；若输入已驻留更快缓存，则跨主存边界的流量又可能更少。算术操作计数也要说明乘加是否记两次。

若带宽为 $`B`$，仅这些必要搬运就给出时间下界 $`\frac{8N}{B}`$；若算术峰值为 $`F`$，计算下界为 $`\frac{2N}{F}`$。程序耗时至少不小于两者中较大者，但真实耗时还可能有调度、指令、依赖和资源冲突等成本。下界能够排除不现实期待，却不能直接保证某个实现达到该速度。

这里应特别区分“读取数组的大小”和“某一层实际搬运的字节”。如果输入已经位于缓存，主存带宽不一定是当前限制；当数组远大于缓存并完整扫描，主存流量模型通常更相关。任何性能图上的算术强度都应注明相对于哪一层。只写一个强度数而不说计量边界，会使解释失去依据。

<a id="systems-1-detail-23"></a>
### 5.2 延迟隐藏需要足够独立工作

如果一次访问的平均等待为 $`\ell`$，每次能提供 $`L`$ 字节，粗略饱和带宽需要在途字节量达到 $`B\ell`$，即需要足够多的独立请求。这是用“流量等于速率乘时间”的数量级关系解释并发需求，不保证某架构一定允许相应在途请求。依赖链、指令窗口和硬件队列都会限制可用并行度。

一个链表节点给出下一个节点地址时，后续访问依赖当前结果；连续数组的多个未来地址却可能提前计算。即使二者读取总字节相同，后者更可能隐藏等待。把所有慢访问都称为“带宽不足”，会遗漏这类延迟主导的情况。正确优化可能是改变表示和依赖关系，而不是增加传输通道峰值。

<a id="systems-1-detail-24"></a>
## 6. 进阶：把容量与性能放到同一张分析表

<a id="systems-1-detail-25"></a>
### 6.1 Roofline 关系的适用边界

令 $`I`$ 表示相对于指定存储层的算术强度，则简化吞吐上界为 $`P\le\min(F,BI)`$。它把计算峰值与搬运峰值两种约束组合起来。转折强度 $`\frac{F}{B}`$ 表示在该简化下何时由带宽约束转为计算约束。实际达不到上界不表示模型失效，而是说明还存在未建模限制，例如小任务、依赖、分支、同步或实现未充分使用硬件。

本章只用这一关系解释存储行为，不开展完整性能建模；系统性基线、资源上界、异步计时和端到端分析见同主题第五章。这里最重要的结论是：减少容量与减少流量不是同一个目标。原位计算可能降低峰值，却因依赖关系影响执行；重计算可能降低容量却增加算术；融合可能同时降低容量和流量，但要验证数值与调度代价。

<a id="sec-6-1"></a>
<a id="systems-1-detail-26"></a>
### 6.2 训练内存应按同时存活的对象估算

设常驻状态为一百六十 MiB，输入十 MiB，前向末尾保留激活三百 MiB，反向还需要四十 MiB 工作区。若这些同时存活，净量峰值至少五百一十 MiB；若更新阶段另需一百 MiB 临时量但激活已经全部释放，就不能把这一百再机械加到前一个峰值上。应比较不同阶段的和，而不是把整次迭代所有出现过的对象相加。

再假设框架为复用保留了一块已经空闲的设备缓冲区。它可能计入设备保留量，却不计入当前活跃张量有效载荷。两个数字都可以合理，但回答的问题不同。报告“峰值显存”应说明来自何种工具、是活跃分配还是保留、是否包括其他进程，以及计量窗口是否覆盖初始化和更新阶段。

<a id="systems-1-detail-27"></a>
### 6.3 从症状建立候选解释

若内存随批量近似线性增长，激活或批输入是优先候选，但算法工作区选择也可能造成非线性跳变。若每迭代后基线持续增加，应检查保存带图结果、容器累计和未释放资源，而不是直接把缓存机制判为泄漏。若工作集突然膨胀同时耗时增加，则可能存在驻留压力，但还需系统指标排除数据规模变化或任务并发。

一种可靠排查顺序是先固定输入与模型，再记录各阶段对象和峰值，随后一次只改变一个因素。若减半批量后常驻状态不变、激活峰值下降，便支持相应解释；若关闭记录列表后增长消失，则说明引用生命周期值得重点检查。每次改变都应能够区分至少两个候选原因，否则实验只是在碰运气。

<a id="systems-1-detail-28"></a>
## 7. 内存映射、缓冲与持久性的边界

<a id="systems-1-detail-29"></a>
### 7.1 内存映射省去了什么

内存映射把文件的某段内容放进地址空间，通过内存访问形式使用它。它可以避免应用一次性把整个文件复制成私有缓冲，并让操作系统按访问需求调入页面；但数据仍需从存储层进入可访问的内存层，首次触碰仍可能付出等待。对顺序扫描而言，映射也不保证优于良好缓冲读取，访问模式、文件大小和系统策略都会影响结果。

映射对象的长度、切片与视图生命周期需要仔细处理。有些切片操作产生新字节串而不是零复制视图；一个仍存在的缓冲视图也可能阻止映射关闭。跨进程共享映射更需要同步：看见相同字节并不保证复合数据结构更新具有原子性。写入一个“长度字段加记录内容”的协议时，读者可能观察到不完整状态，必须设计发布与一致性规则。

<a id="systems-1-detail-30"></a>
### 7.2 读到新值、刷新与断电持久性

写入语言缓冲、把数据交给操作系统、刷新映射或文件、以及在掉电后可靠恢复，属于不同阶段。一次函数成功返回通常只保证其文档承诺的边界；不能笼统推断数据已经处于所有故障场景下都安全的介质上。文件系统、设备缓存、控制器和实际电源保护共同影响最终持久性。

检查点写入更应以恢复协议为目标。需要知道文件是否完整、元数据是否匹配、写入失败会留下什么、读取端如何识别完成版本。仅仅把权重写到一个文件名并不自动构成可恢复检查点。原子替换、同步与目录处理的保证具有平台和文件系统条件，本章不提供假装跨所有平台通用的几行“绝对安全”代码。

<a id="systems-1-detail-31"></a>
### 7.3 容量受限时如何选择数据表示

当数据大于内存，可以考虑分块读取、紧凑表示、映射和可流式算法。选择取决于访问模式：顺序单遍算法适合流式读取，反复随机访问可能受页面调入影响，跨文件的小对象访问则可能被元数据和调用开销主导。应让存储表示服务于实际算法，而不是先选一个流行格式再强行适配。

还要考虑压缩。压缩减少存储和传输字节，却需要解压计算与工作区；如果原本受带宽限制且解压足够快，端到端可能变快，若原本 CPU 已饱和则可能更慢。压缩率也影响批量预取的内存预算。合理评估必须包括读取、解码、转换和消费的完整路径，不能只比较磁盘文件体积。

<a id="systems-1-detail-32"></a>
## 8. 可复现实验：只验证能够观察的事实

<a id="systems-1-detail-33"></a>
### 8.1 浅层大小、紧凑数组与共享引用

下面使用标准库紧凑数组与列表比较表示，并主动构造共享引用。输出大小依赖解释器与平台，本实验只断言关系和语义，不把某次对象头大小推广为硬件常数。列表中的所有引用指向同一个大整数，恰好说明“容器项数乘对象大小”可能重复统计。运行后对象随局部作用域结束而释放，无文件产生。

```python
import sys
from array import array

n = 2000
shared = int("100000000000000000000")
items = [shared] * n
packed = array("d", (float(i) for i in range(n)))
assert all(x is shared for x in items)
assert packed.itemsize * len(packed) == memoryview(packed).nbytes
print("list shallow bytes:", sys.getsizeof(items))
print("one shared integer:", sys.getsizeof(shared))
print("packed payload bytes:", len(packed) * packed.itemsize)
print("packed shallow bytes:", sys.getsizeof(packed))
```

结果中列表浅层大小不包含那一个大整数的完整所有权图，紧凑数组的浅层大小则可能包含其内部缓冲。不同类型的`getsizeof`数字不能简单当成同一口径。若真正要比较业务数据表示，应使用相同值域、相同精度和相同访问功能，并把构建、转换与后续运算成本一并考虑。

<a id="systems-1-detail-34"></a>
### 8.2 视图的共享与副本的独立

实验用字节数组避免依赖第三方数值库。视图切片保留共享关系，显式转换成`bytes`则保存独立值。我们通过可观察修改验证别名，而不把对象标识误当作物理内存证据。结束前释放视图是良好资源习惯，也避免后续调整底层大小时仍有导出缓冲。

```python
buf = bytearray(range(16))
view = memoryview(buf)[4:8]
snapshot = bytes(view)
buf[4] = 200
assert view[0] == 200
assert snapshot[0] == 4
assert view.nbytes == 4
print("view:", list(view), "snapshot:", list(snapshot))
view.release()
```

如果把`view`长期保存，仅四个逻辑字节的视图仍然关联到整个原始缓冲。对于一个数百 MiB 的缓冲，这种所有权链可能比视图自身的浅层大小重要得多。此时复制少量真正需要的数据反而有利于降低长期驻留。这是生命周期分析得出的结论，而不是“复制永远好”或“视图永远好”。

<a id="systems-1-detail-35"></a>
### 8.3 无磁盘文件的映射语义实验

匿名映射用于验证访问和视图释放，不涉及文件持久化。长度固定为一个很小的区间，使用上下文管理关闭资源。该示例不能测出磁盘读取速度，也不能证明文件刷新后已经达到断电持久性；它证明的只是当前进程中映射对象和缓冲视图的共享语义。

```python
import mmap

with mmap.mmap(-1, 4096) as region:
    region[:4] = b"ABCD"
    exported = memoryview(region)[:4]
    assert bytes(exported) == b"ABCD"
    region[0:1] = b"Z"
    assert exported[0] == ord("Z")
    exported.release()
    assert region[:4] == b"ZBCD"
print("anonymous mapping closed")
```

<a id="systems-1-detail-36"></a>
### 8.4 用事件表计算理想峰值

下面把存活区间定义为左闭右开，单位统一为 MiB，处理同一时刻事件时先累计所有增减再观察该时刻状态，因此等时刻释放和分配可以复用空间。若真实执行需要先分配再释放，这个模型必须细化事件顺序；不要让表格的隐含约定掩盖实际峰值。

```python
objects = [
    ("state", 0, 8, 160),
    ("input", 1, 5, 10),
    ("activation", 2, 5, 300),
    ("backward scratch", 4, 5, 40),
    ("update scratch", 6, 7, 100),
]
events = {}
for name, start, end, size in objects:
    assert start < end and size >= 0
    events[start] = events.get(start, 0) + size
    events[end] = events.get(end, 0) - size
live = peak = 0
for t in sorted(events):
    live += events[t]
    assert live >= 0
    peak = max(peak, live)
assert live == 0 and peak == 510
print("ideal peak MiB:", peak)
print("sum of all object sizes:", sum(x[3] for x in objects))
```

所有对象大小之和为六百一十 MiB，理想峰值为五百一十 MiB。两者之差来自不同时存活的区间，而不是压缩或神奇复用。真实分配器可能因为对齐、粒度和碎片需要更多空间，调度策略也可能改变区间。把这个小程序用作规划工具时，应先确保输入区间来自真实依赖关系。

<a id="systems-1-detail-37"></a>
### 8.5 访问顺序实验应怎样限制结论

若直接在 Python 中逐元素计时，得到的是解释循环、索引、对象和硬件行为的混合结果。本章不输出一个貌似精确的“缓存提升倍数”。更严谨的进一步实验应使用相同底层数值内核，控制数据量、访问步长、线程配置和是否预热，并通过对应硬件计数器检查实际未命中与流量。没有这些证据，可以报告时间差，却不应断言差异全部来自某一级缓存。

研究问题可以从几何增长的数据规模开始，观察时间每字节是否出现拐点；再改变步长和复用次数，检验容量与延迟的解释是否一致。若不同假设都能解释同一曲线，就需要新增对照，例如改变工作集而保持算术量，或改变算术量而保持流量。这种以反证为目标的设计，比只画一条时间曲线更有价值。

<a id="systems-1-detail-38"></a>
### 8.6 追踪分配器时究竟追踪了什么

标准库的分配追踪工具能够帮助定位由受追踪分配域产生的分配，并给出相关调用栈，但它不天然覆盖设备显存或所有第三方原生库申请的缓冲。使用这类工具时，应把“追踪到的当前字节”作为一个明确指标，而不是直接改名为“程序全部内存”。同一个进程内存在多个分配域，工具覆盖范围本身就是实验条件。

快照差分尤其容易误读。两个快照之间增长最多的调用位置，可能是合理缓存、输入规模变化，也可能是异常保留；差分提供线索，却没有自动判定所有权是否合理。应该在等价迭代边界采样，并区分仍存活分配与整个期间累计申请量。一个每轮申请又释放很多临时数组的程序，累计流量可以很大而稳定占用很小。

进一步可用“先增加负载，再重复同负载，最后降低负载”的序列观察分配行为。如果第二轮复用了先前空间，说明高水位可能服务于后续工作；如果每轮都留下新的同类对象，便需要追查保留链。即使确认复用，也应判断这个缓存规模是否符合业务预算，因为没有泄漏并不代表内存策略一定合理。

<a id="systems-1-detail-39"></a>
### 8.7 对齐、碎片和大对象分配的工程影响

理论有效载荷只需整数个元素，实际分配往往遵循对齐与粒度约束。许多很小的对象可能各自带有元数据与空隙，大对象之间的空闲块也未必能够拼成所需形状。外部碎片强调可用空间分散，内部碎片强调已经分配的块中存在未利用部分。不同分配器会采取不同策略，本章不将具体某种碎片比例设为固定常数。

设总空闲量超过一次申请大小，申请仍可能失败，原因可能包括地址区间连续性要求、分配域限制、设备策略或者真实可用量与监控口径不同。不能仅凭一个总数证明申请应当成功。诊断应查看失败的是哪一类分配，是否需要连续虚拟区间、是否有相关设备池上限，以及同时存活状态是否突然扩大。

预分配和复用能够减少反复申请成本并让预算可控，但过度预分配又会挤占其他任务。一个实用策略是先根据最大可信工作负载设置缓冲上界，再在多阶段之间复用不重叠的空间，同时保留必要的形状与类型检查。若把不同语义的数据装进同一缓冲，应确保前一阶段的所有使用已经完成，否则节省内存的优化会变成覆盖仍在读取数据的错误。

<a id="systems-1-detail-40"></a>
### 8.8 把推断写成可复核的资源说明

一份有用的内存说明应写出输入规模、数据表示、常驻状态、峰值阶段、计量工具和单位。例如“同一进程在固定批量下，前向末尾活跃数组净量约为某值，分配器保留量为另一值”，比单独写“用了两 GB”更容易复核。设备、操作系统与运行时也应记录，因为同样算法在不同环境中的管理开销可能不同。

资源预算需要给出合理余量，但余量应来自明确的不确定性，而不是随意乘一个倍数。可以分别为算法工作区选择、输入长度变化、分配粒度和并发任务留出空间，并标注最坏情况下是否可能同时发生。这样，当输入规模变化时能够更新预算，而不用重新猜测全部占用。

最后应把正确性纳入说明。原位复用是否改变仍被引用的结果，压缩或低精度是否满足误差要求，异步执行是否已经结束，映射文件是否仍有效，都是容量优化的前提。只有满足这些约束的节省才具有意义。在团队协作中，还应保存能够重复的输入构造与计量步骤，使他人能够区分事实、估计和尚待验证的解释。系统学习的进阶不在于记住更多优化名词，而在于能够从对象语义、生命周期与资源测量之间建立可检验的因果链。

<a id="systems-1-detail-41"></a>
## 9. 进阶练习与完整解析

<a id="systems-1-detail-42"></a>
### 9.1 输入体积与训练峰值

**问题。** 形状为 $`(64,3,224,224)`$ 的四字节输入有多大，为什么不能用它预测训练显存？

**解析。** 元素数为九百六十三万三千七百九十二，乘四得三千八百五十三万五千一百六十八字节，即三十六点七五 MiB。这只包括输入净数据，不包括标签、参数、梯度、优化器状态、保留激活或工作区。应继续列出各阶段同时存活的对象，若输入还有转换副本，还需判断两份是否重叠存在。输入体积提供预算的一项，并不提供整次训练上界。

<a id="sec-7-1"></a>
<a id="systems-1-detail-43"></a>
### 9.2 边界追问：权重体积能否直接当训练内存

**问题。** 权重四十 MB，训练却占数百 MB，是否一定泄漏？

**解析。** 不一定。先统一十进制与二进制单位，再核对是否存在梯度、两个优化器状态、高精度副本和激活。随后区分当前活跃分配与分配器保留。如果在同样迭代条件下稳定在某个高水位，这与持续增长不同；只有观察到本应结束的所有权仍被保留，或等价迭代中未释放量持续累积，才获得更具体的泄漏证据。数值大本身不能证明生命周期错误。

<a id="systems-1-detail-44"></a>
### 9.3 小视图为什么可能占住大内存

**问题。** 一个十六字节视图为什么可能阻止一 GiB 缓冲释放，何时应复制？

**解析。** 视图需要保证其访问期间底层存储有效，因此拥有相应引用关系。视图逻辑长度小，不意味着底层分配被拆成小块。若只需长期保存十六字节，并且其余缓冲没有其他用途，复制这十六字节可以让大缓冲失去最后引用。若大缓冲仍被其他对象使用，复制不会带来同样释放效果。决策需要完整所有权图，而非只看切片形状。

<a id="systems-1-detail-45"></a>
### 9.4 相同虚拟地址意味着共享吗

**问题。** 两个进程打印出相同地址值，是否说明它们正在共享同一个数组？

**解析。** 不能。虚拟地址要结合地址空间解释，不同进程中相同值可以映射到不同物理页。即便确认存在共享页，也还需要核对偏移、权限和同步协议。正确验证共享应通过明确的共享内存接口及受控读写实验，并确保没有把序列化副本误当共享对象。对象身份数字更不能跨进程直接作为内存共享证据。

<a id="systems-1-detail-46"></a>
### 9.5 缺页是否一定意味着磁盘读取

**问题。** 首次遍历新数组时缺页计数增加，是否说明操作系统把数组从交换区读回？

**解析。** 未必。首次触碰可能建立页面或执行零填充，写时复制也可能产生相关处理。需要查看平台区分的缺页类别，以及实际磁盘活动和提交状态。若只是按需建立新页面，解释为交换读回就是错误归因。进一步实验可对比首次写入、再次遍历和确实由文件支持的映射，但必须控制数据规模，避免主动制造系统内存压力。

<a id="systems-1-detail-47"></a>
### 9.6 带宽下界能否当预测时间

**问题。** 必要流量八百 MB，某层带宽一百 GB 每秒，能否承诺八毫秒完成？

**解析。** 这只给出理想搬运下界，前提是单位一致且该层确实承担八百 MB 流量。程序还可能受到算术、依赖、调用和其他资源限制，实际可持续带宽也未必达到标称值。若实测小于该下界，应先检查数据是否在更快缓存层、流量计算是否重复或单位是否混淆；若大于下界，则需要继续定位额外限制。

<a id="systems-1-detail-48"></a>
### 9.7 两次扫描融合一定更快吗

**问题。** 把两个逐元素操作合成一个函数，是否必然减半耗时？

**解析。** 必须先确认原实现是否确实产生两遍慢层读写，新的实现是否真正融合到底层循环。即使流量减半，也可能还有不变的调度和算术成本，甚至出现向量化或寄存器压力损失。可先建立最低流量变化，再测端到端，并核对数值一致性。把源代码函数合并不等于硬件数据流已经融合。

<a id="systems-1-detail-49"></a>
### 9.8 批量减半为何没有节省一半内存

**问题。** 原峰值十 GiB，批量减半后仍有七 GiB，怎样解释？

**解析。** 若用 $`M(B)=M_0+kB`$ 的简化模型，两个观测给出常驻项四 GiB，原批量相关项六 GiB，因此减半后为七 GiB。这个拟合只是候选解释，需更多批量点验证；实际工作区选择、填充与分片可能导致非线性。应先把模型状态与激活分开，避免以为所有内存都跟批量成比例。

<a id="systems-1-detail-50"></a>
### 9.9 用生命周期计算峰值

**问题。** 常驻二百 MiB，前向激活四百 MiB，反向工作区一百 MiB，更新临时量二百 MiB；更新前激活与反向工作区都释放，理想峰值多少？

**解析。** 反向阶段最多为二百加四百加一百，即七百 MiB，更新阶段为二百加二百，即四百 MiB，因此理想净峰值七百 MiB。不能把所有量求和得九百。若更新临时量提前分配，或激活引用延迟释放，峰值会改变。实际预算还需加上分配粒度、其他输入与实现工作区。

<a id="systems-1-detail-51"></a>
### 9.10 内存映射是否等于无需内存

**问题。** 映射一百 GB 文件后地址空间足够，是否意味着可以不考虑 RAM 随机访问？

**解析。** 映射避免一次性复制整个文件，并不消除实际页面驻留和存储读取。随机访问工作集超过可用物理资源时，可能反复调入页面，吞吐与延迟会受影响。还要考虑地址空间、映射限制和其他进程的资源竞争。合理做法是明确访问模式并评估局部工作集，而不是把文件大小与地址空间大小比较后宣布问题解决。

<a id="systems-1-detail-52"></a>
### 9.11 列表表示与紧凑表示如何公平比较

**问题。** 某整数列表比浮点紧凑数组大，能否宣称紧凑数组在任何任务中都更优？

**解析。** 不能。必须确认数值精度、范围、可变长度、对象语义和所需操作等价。任意精度整数与固定精度浮点承载不同信息，强行转换可能改变问题。即使表示等价，转换成本与访问模式也会影响总收益。公平实验应明确语义约束，再在同一工作负载下比较容量、构建成本和后续计算。

<a id="systems-1-detail-53"></a>
### 9.12 压缩后文件更小为什么读取更慢

**问题。** 压缩把读取字节减少一半，却让训练输入吞吐下降，可能是什么原因？

**解析。** 解压计算、分配与格式解析可能成为新的瓶颈，压缩块组织也可能放大随机读取。若原本存储并非主要限制，减少读取字节未必抵消解码开销。应测读取、解压、转换和消费各阶段，并关注峰值缓冲。不能只凭压缩率预测吞吐，也不能因为一次变慢就推断压缩在所有资源条件下无效。

<a id="systems-1-detail-54"></a>
### 9.13 从状态量推断优化策略

**问题。** 参数与优化器状态占九成峰值，激活只占一成，单靠激活重计算最多能节省多少？

**解析。** 在简化不变配置下，即使把全部激活净量消除，也只减少约一成，实际重计算还需要边界状态与临时量。因此优先考虑状态表示、优化器选择或分片可能更有针对性，但这些策略有数值、收敛和通信代价。分析应先给出潜在收益上界，再评估实现复杂度，避免在不主导的部分投入过多工作。

<a id="systems-1-detail-55"></a>
### 9.14 为什么释放对象后监控不下降

**问题。** 删除容器后对象不再可达，但进程监控值保持高位，应怎样进一步判断？

**解析。** 首先核实对象是否确实不再被其他引用持有，再确认监控指标是驻留、提交还是分配器保留。重复构建相同规模任务，观察后续是否复用已有空间；若高水位稳定，可能是复用缓存。若持续增长，则进一步追踪分配域和所有权。不能用强行触发垃圾回收后的单个数值作为所有运行时内存健康的充分证明。

<a id="systems-1-detail-56"></a>
### 9.15 研究练习：设计可以反驳自己的局部性实验

**问题。** 你发现顺序访问比跨步快，提出缓存解释，如何增强证据？

**解析。** 先保持元素数和运算一致，改变访问顺序；再改变总工作集，检验超过缓存容量后差异是否按预期变化；同时测相关硬件事件，确认慢层流量或未命中变化。对语言解释器、数组布局与向量化做控制，防止观察到的只是不同代码路径。若证据与解释冲突，应修正模型，而不是删去不符合预期的数据。
