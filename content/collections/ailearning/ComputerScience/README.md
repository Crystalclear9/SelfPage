## 五个主题怎样组成一条实验链

以“每天重建用户最近七天的消费特征”为例，先写结果契约：每个用户与预测时点只产生一行，金额未知与没有事件分别表示，窗口左闭右开，修订只使用预测时点已经可见的版本。数据库第 1、2 章用于证明行粒度、连接重数与分母，第 3 章确定同时间事件、版本选择和窗口边界，第 4 章在这些语义不变的前提下选择索引、快照及分页协议。先得到小数据上的可手算答案，再讨论提速。

当事件太多无法一次放入内存时，算法主题帮助列出状态规模与访问成本。可加性摘要能否合并，取决于摘要是否保留足够信息；金额的和与已知值计数可合并，直接合并局部平均通常不正确。需要取每个用户最近事件或最大金额时，先固定并列规则，再决定使用排序、堆还是数据库访问路径。这样算法选择服务于同一个结果定义。

系统主题把逻辑工作量接到实际执行成本：读盘、解码、连接、写出可以形成流水线，也可能受一个阶段限制。Linux 主题负责解释路径、参数、描述符、进程和日志，进而把提取任务组织成可观察、可取消、可恢复的作业。进程存在、退出码为零、输出可解析以及输出满足结果契约，是需要分别检查的状态。发现运行变慢时，先比较同一批输入下的吞吐、资源和等待证据，再决定改算法、索引或并发度。

Git 主题把这次运行与可读取的代码树联系起来。提交标识之外，清单还要记录查询与参数、数据快照、配置、解释器和依赖、输出摘要。恢复时应先确认源版本是否仍可重建，再恢复到明确的检查点；分页游标只表示读取位置，并不能单独保证源数据未变。若更换了查询语义或数据版本，应建立新的运行身份，避免把两个条件不同的结果拼在一起。

## 分类综合验收

1. 构造包含重复金额、空值、无事件用户、同时间事件、迟到修订和删除标记的小数据，先手算各预测时点的结果；用查询和独立参考计算相互核对。
2. 给查询加索引或改写连接，比较完整行及其重数；需要顺序时另外声明全序，不能把集合相同作为全部验收条件。
3. 在批次输出前、输出后但进度提交前、进度提交后分别注入失败，说明每种情况下哪些结果可见、重跑是否会重复或遗漏。涉及外部输出时，还要写明发布和去重机制。
4. 给同一任务记录代码、数据、配置和输出身份，设置明确的完成标记及验收程序。故意破坏一个前提，检查验收能否拒绝该结果。
5. 对一次性能变化提出两个竞争解释，设计只改变一个因素的短实验。报告实测范围、等待位置、正确性证据及仍不能下的结论。

这些任务可以先在自动清理的临时目录和小型内存数据库里完成。验收重点是你能否解释每条不变量怎样保持、哪种反例会使它失效，再逐步扩大规模与运行环境。
