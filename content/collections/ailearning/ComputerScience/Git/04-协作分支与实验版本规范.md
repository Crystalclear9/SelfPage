## 1. 一条清晰的实验分支从明确基线开始

实验分支的首要职责是承载一个可以回答的问题，例如样本权重归一化是否修复批量变化带来的尺度偏差。基线应明确到提交和相关实验条件，而不是含糊地说“从最新代码开始”。如果主线正在快速变化，两个研究者口中的最新可能相差多个提交。记录基线让后来的差异与结论有确定参照。

分支命名可以表达任务目的或假设，但名称不是内容证明。一个叫修复的分支仍可能包含不相关重构；一个叫实验的分支也可能已经形成稳定实现。审查应根据实际差异与承诺判断，而不是只看名字。命名规范的价值在于帮助发现与沟通，不能替代版本核对和范围控制。

一条分支中可以有多次合理演进：先加入最小失败例子，再修复机制，最后补充必要说明。每次提交都应尽可能构成可以解释的状态。如果探索过程需要临时失败或大幅重写，可以保留为研究记录，但正式交付时应整理成让新读者能够审查的变化。整理不是隐藏重要选择，而是区分代码交付与实验事实。

当多个假设同时展开，最好让代码变化与运行记录具有明确关系。不同参数组合不一定需要复制大量分支，可以由固定代码与配置集合表达；不同架构或协议变化则可能需要独立主题分支。过度使用分支管理参数会让历史难以比较，完全不分支又会把无关假设混在一个工作区。选择应服务于可解释性。

### 1.1 提交、运行与产物为什么不是一一对应

同一个提交可以运行多个数据划分、种子和超参数，因此产生许多运行；一次运行又可能输出多个检查点、日志和指标。产物文件名即使包含提交前缀，也不能唯一表示运行。完整身份需要把代码、配置、输入、环境、运行和产物分别命名，再记录它们之间的连接。

例如提交甲定义同一个模型，配置乙选择学习率，数据丙定义训练与验证集合，运行丁使用种子七，产物戊是第十轮检查点。若只保存甲和戊，就丢失了影响结果的乙、丙以及选择过程。一个可靠清单应让读者沿这些关系追溯，而不是依赖作者记得当时终端输入。

反过来，相同配置文件名不保证相同有效配置。命令行覆盖、环境变量、默认值和配置继承可能共同决定运行值。必须记录解析完成后的有效内容，必要时同时保存来源与覆盖顺序，才能解释为什么文件里写着一个值，实际训练却使用另一个值。

## 2. 本地分支、远程分支与跟踪引用

本地分支是本仓库中的引用；远程仓库里的分支属于另一份仓库；远程跟踪引用是本地对远程状态的记录。三者可以暂时指向相同提交，也可以因时间与操作不同而分离。把它们都叫“远程分支”容易造成误解，尤其会误以为本地界面随时显示服务器的最新状态。

远程名称只是本地别名，不强制某个名称一定代表官方主仓库。它可以指向网络地址，也可以指向本机路径。多个远程可以拥有同名分支，含义由仓库来源决定。自动化应明确使用哪个远程和哪条引用，不应依赖每位协作者的默认配置恰好相同。

跟踪关系帮助 Git 知道当前分支默认与哪条上游引用比较或整合，但它不等于实时订阅，也不自动保证推送目标与拉取来源相同。不同配置会影响默认行为。重要协作步骤中，显式检查上游与推送目标，能够避免把实验变化送到错误位置，或误解领先落后计数的含义。

领先与落后计数通常是相对本地已知引用计算的图关系。如果还没获取最新远程历史，这些数字可能过时。即使刚获取，远程也可能随后变化。因此它们是特定观察时刻的证据，不是永久共享事实。并发协作必须承认观察与更新之间存在时间窗口。

<a id="git-4-detail-4"></a>

### 2.1 获取、整合与推送应分别解释

获取主要把对象与引用观察带到本地；整合决定当前历史如何吸收另一条历史；推送请求远程接受某些引用更新。把三者分开，可以清楚检查每个阶段的前置状态和结果。拉取作为组合命令很方便，但其后半段行为依赖配置，学习与故障定位阶段应明确它采用合并还是变基。

普通快进推送要求远程旧值在新值的历史中，能够避免直接把别人新增历史从该分支引用中移走。被拒绝时，首先检查远程变化与自己的关系，而不是把拒绝当成需要绕过的障碍。拒绝可能正是在保护尚未理解的协作内容。是否改写共享引用，应有明确任务需求和协调依据。

仅用一个无条件强制更新会弱化这类保护。带租约的方式可以附加预期旧值检查，但它也不是自动判断协作意图的工具。若预期来自可能被后台获取更新的本地跟踪引用，其保护语义可能与你想象不同；显式指定预期对象能把条件讲得更清楚，但仍需要确认该对象是你有意审核过的状态。

<a id="git-4-detail-5"></a>

### 2.2 租约是比较条件，不是对内容正确性的证明

可以把显式租约理解为“只有远程引用仍等于我预期的旧身份，才接受这次更新”。它类似比较并交换的并发条件，能够检测推送时远程当前值与明确预期值不相等的情况。若引用曾从甲变到乙，随后又回到甲，单凭预期甲的相等检查不能识别中途发生过变化；这类条件检查比较当前状态，并不提供完整的引用变化历史。但如果你预期的状态本来就包含未审查内容，租约通过也不会证明你已经合理整合了它；如果更新本身错误，条件成立仍可能发布错误代码。

因此租约解决的是某类竞争窗口，而不是权限、审查和语义正确性全部问题。真实共享项目中还可能有受保护分支与服务端规则，即使客户端条件满足也可以拒绝更新。教材实验会在独立本地裸仓库演示陈旧预期如何被拒绝，不会把这种机制用于用户的真实历史。

对已发布结果，改写引用还会影响引用该分支名的人。即使对象仍存在，默认路径不再指向它，旧报告可能难以发现。长期结果应记录具体对象与保留位置，而不是依赖一个允许随意移动的共享分支。分支适合推进工作，发布标识需要额外稳定约定。

## 3. 实验一：远程跟踪引用是最近观察，不是实时状态

下面创建一个本地裸仓库和两个克隆，模拟两个协作者。第一位推送第二个提交后，第二位的远程跟踪引用仍停在第一提交；获取以后才更新，同时第二位当前工作区与本地分支保持原状。所有仓库都位于一个系统临时目录，退出后自动清理，不涉及网络。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_collaboration_") as root:
    base = Path(root)
    remote, alice, bob = base / "remote.git", base / "alice", base / "bob"
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(cwd, *args, check=True):
        return subprocess.run(["git", *args], cwd=cwd, env=env, text=True,
                              encoding="utf-8", capture_output=True, check=check)
    def out(cwd, *args):
        return git(cwd, *args).stdout.strip()
    def configure(repo):
        for key, value in [("user.name", "Example"),
                           ("user.email", "example@example.invalid"),
                           ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
            git(repo, "config", key, value)
    git(base, "init", "--bare", "-b", "main", str(remote))
    git(base, "clone", str(remote), str(alice))
    configure(alice)
    (alice / "state.txt").write_text("A\n", encoding="utf-8")
    git(alice, "add", "--", "state.txt")
    git(alice, "commit", "-m", "initial A")
    git(alice, "push", "-u", "origin", "main")
    first = out(alice, "rev-parse", "HEAD")
    git(base, "clone", str(remote), str(bob))
    configure(bob)
    assert out(bob, "rev-parse", "origin/main") == first
    (alice / "state.txt").write_text("B\n", encoding="utf-8")
    git(alice, "add", "--", "state.txt")
    git(alice, "commit", "-m", "advance to B")
    git(alice, "push", "origin", "main")
    second = out(alice, "rev-parse", "HEAD")
    assert out(bob, "rev-parse", "origin/main") == first
    git(bob, "fetch", "origin")
    assert out(bob, "rev-parse", "origin/main") == second
    assert out(bob, "rev-parse", "HEAD") == first
    assert (bob / "state.txt").read_text(encoding="utf-8").strip() == "A"
    git(bob, "merge", "--ff-only", "origin/main")
    assert out(bob, "rev-parse", "HEAD") == second
    print("fetch updated observation; explicit integration advanced local main")
```

实验通过分别读取远程跟踪引用、本地 HEAD 与工作区文件，把观察更新和内容整合区分开。两个克隆位于同一台机器，不改变它们作为独立仓库拥有各自引用与工作区的事实。现实网络系统加入延迟和权限后，状态层次仍然成立，只是故障来源更多。

## 4. 实验二：显式陈旧租约被拒绝

该实验再创建两个独立协作者。第二位观察到旧提交后，第一位继续推送新提交；第二位试图以旧提交为明确预期更新同一远程引用，推送过程检测到远程实际旧值与明确预期不一致，更新被拒绝。我们只验证拒绝与远程保留新值，不演示对真实共享分支强制覆盖，也不需要网络地址。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_explicit_lease_") as root:
    base = Path(root)
    remote, first_repo, second_repo = base / "remote.git", base / "one", base / "two"
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def run(cwd, *args, check=True):
        return subprocess.run(["git", *args], cwd=cwd, env=env, text=True,
                              encoding="utf-8", capture_output=True, check=check)
    def git(cwd, *args):
        return run(cwd, *args).stdout.strip()
    def config(repo):
        for key, value in [("user.name", "Example"),
                           ("user.email", "example@example.invalid"),
                           ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
            git(repo, "config", key, value)
    def commit(repo, name, text):
        (repo / name).write_text(text, encoding="utf-8")
        git(repo, "add", "--", name)
        git(repo, "commit", "-m", text.strip())
    git(base, "init", "--bare", "-b", "main", str(remote))
    git(base, "clone", str(remote), str(first_repo))
    config(first_repo)
    commit(first_repo, "base.txt", "base\n")
    git(first_repo, "push", "-u", "origin", "main")
    git(base, "clone", str(remote), str(second_repo))
    config(second_repo)
    expected = git(second_repo, "rev-parse", "origin/main")
    commit(first_repo, "new.txt", "remote advanced\n")
    git(first_repo, "push", "origin", "main")
    accepted = git(first_repo, "rev-parse", "HEAD")
    commit(second_repo, "experiment.txt", "local experiment\n")
    result = run(second_repo, "push",
                 f"--force-with-lease=refs/heads/main:{expected}",
                 "origin", "HEAD:refs/heads/main", check=False)
    assert result.returncode != 0
    assert git(remote, "rev-parse", "refs/heads/main") == accepted
    print("stale explicit lease rejected; newer remote commit preserved")
```

拒绝原因通过状态构造与远程最终身份共同验证，而不是依赖某个版本的英文错误句子。实验中没有尝试把预期改为最新值来强行成功，因为学习目标是理解竞争检测。真实协作还必须理解新提交的内容与他人依赖，单纯刷新预期不等于完成整合。

## 5. 实验清单应保存最终有效配置

运行配置往往由默认值、配置文件、环境变量和命令行覆盖共同形成。保存原始配置文件很有用，但不足以证明实际使用值。清单应记录解析后的有效配置，必要时另存来源与覆盖关系。这样既能重建行为，也能解释某个参数为何取到最终值，而不需要猜测作者当时的终端状态。

有效配置应避免隐藏动态默认值。例如设备数量影响批量大小，日期影响输出路径，检测到某库后自动启用另一精度模式。若这些选择影响结果，应把解析后的值显式记录。对于不能直接序列化的对象，可以记录可重建的规范描述和版本，不要把某个内存地址或不稳定字符串表示当成配置身份。

配置摘要必须基于明确规范化方式。字典键顺序、浮点表示、路径形式与 Unicode 处理都可能影响字节摘要。两个语义相同的配置若序列化方式不同，可以具有不同摘要；摘要相同则只说明被摘要的字节一致，不自动证明所有运行条件都被包含。因此清单格式应说明字段含义与编码规则。

<a id="git-4-detail-9"></a>

### 5.1 配置继承与覆盖需要可观察优先级

假设默认学习率为甲，配置文件改为乙，命令行又指定丙。若优先级定义为默认、文件、命令行依次覆盖，最终应记录丙。只保存文件乙会让别人复现另一实验。更隐蔽的情况是嵌套配置合并：浅覆盖与递归覆盖会保留不同子字段，必须明确采用哪种语义。

覆盖还可能涉及非法组合。例如启用某优化器后，旧配置中的另一个优化器专属参数应当报错或被显式排除，而不是静默保留为无效字段。清单记录无效参数会制造“看起来控制了，实际没使用”的错觉。配置解析应校验字段、范围和相互依赖，并能输出最终实际参与计算的内容。

对于扫描实验，应同时记录候选空间、实际运行配置和选择规则。最终最优配置只是搜索过程的一部分，无法体现尝试次数与失败成本。若把搜索后的最好结果当作预先固定方案的独立评估，统计解释会失真。版本与清单使过程可追踪，但选择偏差仍需实验设计处理。

<a id="git-4-detail-10"></a>

### 5.2 把代码谱系与实验谱系分开再连接

代码谱系由提交父关系组织，描述版本如何派生；实验谱系还包含数据变换、预训练来源、检查点继续训练、超参数搜索与模型选择。这些关系往往是多对多的。一个训练提交可以消费不同预训练模型，一个权重又可以由另一个权重继续训练，因此单条线性分支无法表达全部来源。

可以把运行视为连接输入与输出的节点。输入包括代码树、有效配置、数据、环境和起始权重，输出包括模型、日志和指标；继续训练再以旧产物作为新输入。每个节点记录实际身份与必要条件，就能沿图追溯。图中的箭头必须有语义，例如来源、转换或选择，不能只画一条没有说明的关联线。

这种建模也帮助发现遗漏：若结果依赖某个外部词表，图中却没有它，就是隐藏输入；若最佳权重没有选择指标，是隐藏选择；若同名数据路径可变，是身份不稳定。完整性检查应围绕这些依赖关系展开，而不只是统计清单字段数量。字段很多但连接错误，同样无法重建结果。

## 6. 数据、环境与产物身份怎样固定

数据身份不能只写文件夹名称。原始内容、预处理版本、样本顺序和划分清单都可能影响训练。对小型文件可以直接记录内容摘要；对大型集合可以采用分片清单及摘要树，但必须说明清单包含什么、排序如何确定、缺失文件如何处理。只对目录名字做摘要没有内容证明价值。

数据划分需要防止实体泄漏。同一用户或同一原始样本的近重复版本若跨训练与测试，随机行号划分可能高估性能。清单应记录划分单位、规则与身份，而不只是随机种子。若数据本身增加或顺序变化，同样种子也可能生成不同集合。因此固定划分通常需要保存实际成员或稳定可重建规则及对应数据版本。

环境身份包括解释器、依赖解析、系统库、设备与相关运行选项。一个依赖范围声明允许未来解析出不同版本，和精确锁定不是同一种承诺；容器镜像标签也可能移动，内容摘要通常更精确。即使镜像内容固定，宿主驱动、硬件与外部服务仍可能影响执行，因此环境边界需要清楚说明。

产物身份最好与可变展示名分离。可以有一个方便阅读的“最佳模型”别名，但其目标应是固定内容与完整元数据。选择指标、方向、候选范围、轮次、并列处理以及验证集版本都需要可查。若两个模型具有相同显示名但来自不同规则，读者不应被迫从文件时间猜测哪一个才是报告所用对象。

<a id="git-4-detail-12"></a>

### 6.1 摘要证明内容身份，但不自动证明来源

内容摘要可以检测意外变化，并把产物与清单关联起来。但如果攻击者能够同时替换文件和未受保护的摘要清单，单纯重新计算一致并不能证明来源可信。真实性还需要可信发布入口、签名或其他受控机制。课堂中使用摘要主要用于固定输入和发现不一致，不把它宣传成所有安全问题的答案。

摘要还不解释内容语义。两个数据文件字节不同，可能只是无关空白，也可能是标签改变；字节相同则仍可能被不同解析器赋予不同含义。需要同时记录格式、编码和解析协议。对于模型文件，加载代码与版本也影响解释，因此产物身份必须连接相应模型构造和预处理状态。

规范化可以建立某种语义身份，但规范化本身会丢信息。比如按键排序的配置摘要忽略原始顺序，适用于顺序无关映射，却不适用于有顺序语义的列表。应声明摘要覆盖的是原始字节还是规范化表示，以及这种选择为什么符合任务。不可把两种摘要混用而不说明。

## 7. 实验三：生成有效配置清单并检测被改变的输入

以下实验不需要 Git，目的是把版本控制之外的输入身份做成实际断言。我们按明确优先级形成有效配置，对固定数据字节求摘要，保存运行清单，再重新读取核对。随后故意改变数据内容，确认清单检查能够发现不一致。所有文件都放在系统临时目录，代码结束后自动清理。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import hashlib
import json


def canonical_bytes(value):
    return json.dumps(value, ensure_ascii=False, sort_keys=True,
                      separators=(",", ":"), allow_nan=False).encode("utf-8")


def sha256_bytes(value):
    return hashlib.sha256(value).hexdigest()


with TemporaryDirectory(prefix="experiment_manifest_") as root:
    folder = Path(root)
    defaults = {"learning_rate": 0.1, "batch_size": 8, "seed": 7}
    file_config = {"learning_rate": 0.01}
    command_overrides = {"batch_size": 4}
    effective = {**defaults, **file_config, **command_overrides}
    assert effective == {"learning_rate": 0.01, "batch_size": 4, "seed": 7}
    data = folder / "data.json"
    data.write_bytes(canonical_bytes({"x": [1, 2, 3], "y": [2, 4, 6]}))
    manifest = {
        "schema_version": 1,
        "run_id": "toy-run-001",
        "effective_config": effective,
        "config_sha256": sha256_bytes(canonical_bytes(effective)),
        "data": {"relative_path": "data.json",
                 "sha256": sha256_bytes(data.read_bytes())},
        "code": {"identity_kind": "fixed teaching example", "version": 1},
        "selection": {"rule": "single predefined run; no model selection"},
    }
    record = folder / "manifest.json"
    record.write_bytes(canonical_bytes(manifest))
    loaded = json.loads(record.read_text(encoding="utf-8"))
    assert sha256_bytes(canonical_bytes(loaded["effective_config"])) == loaded["config_sha256"]
    assert sha256_bytes(data.read_bytes()) == loaded["data"]["sha256"]
    data.write_bytes(canonical_bytes({"x": [1, 2, 3], "y": [2, 4, 7]}))
    assert sha256_bytes(data.read_bytes()) != loaded["data"]["sha256"]
    print("effective config reconstructed; changed data detected")
```

示例明确将代码身份标为固定教学例子，而没有伪造一个真实仓库提交。实际项目应把该字段替换为真正被运行的代码身份与工作区状态。清单格式只覆盖本例需要的层次，不是完整通用标准；它缺少硬件与依赖，是因为实验只使用标准库和确定性字节操作。扩展到训练时必须补上相关条件。

还应注意这里的覆盖是浅字典覆盖，嵌套结构若需要递归语义，必须另行定义并测试。规范序列化禁止非有限数值，是为了避免把非标准数值表示混入身份。摘要核对通过也不能证明数据正确，只能证明它与清单所指字节一致；真实性、标签质量与划分合理性仍需独立检查。

## 8. 可审查交付要让陌生读者理解行为

一份交付说明先讲具体问题和最终行为，再讲必要实现与验证。读者不应该必须阅读整段聊天，才能知道为什么修改。对训练归一化修复，可以用“不同批量时原先总损失改变梯度尺度，现在按有效权重归一化”这样的触发与结果表达，再给手算例子和测试范围。抽象写“优化训练效果”无法被审查。

范围整理也很重要。必要源码、配置、测试和导航应共同交付；无关缓存、个人路径和临时图不应混入。是否保留某个文件应依据它对最终使用的作用，而不是按扩展名机械判断。一个小型测试数据可能必要，一个庞大逐步日志则更适合专门产物存储，但后者仍需可追踪定位。

交付说明应描述最终方案，而不是按聊天顺序堆积所有尝试。被放弃方案只有在解释重要取舍时才需要出现。与此同时，影响科学结论的搜索预算与筛选不能因为代码整理而消失。代码说明追求清楚的最终实现，实验记录保存选择事实，这两种材料可以互相链接而不互相淹没。

审查应关注能否重现关键行为，而不是代码是否看起来复杂。若某个简单实现已经满足边界和性能要求，就没有必要为了显得进阶而引入抽象。反过来，隐藏条件很复杂时，也不能用短说明掩盖。合理详实意味着把决定结果的机制讲透，而不是让每个文件都同样长。

<a id="git-4-detail-15"></a>

### 8.1 审查单位与实验单位可以不同

一个代码变更可能支持许多实验配置，一次研究结论又可能依赖多个代码变更。审查单位应该围绕行为或接口组织，实验单位围绕固定条件下的一次运行组织。把二者强行设为一一对应，容易造成分支爆炸或结果混杂。清单与链接提供连接，不需要让历史结构承担全部实验数据库职责。

例如新增通用样本权重支持是一个可审查变更，随后可以用多个权重方案进行实验。每次运行记录具体配置与结果即可，不必为了每个权重数值重写代码。若实验发现实现缺陷，则产生新的修复提交，并明确哪些旧运行受影响。这种组织既保留代码可理解性，也保留结果来源。

## 9. 版本说明如何服务复现与发布

发布说明应告诉使用者入口、输入前提、预期行为和已知限制。对于模型，至少需要构造方式、权重身份、词表或特征协议、依赖条件和最小推理例子。对于学习资料，目录、相对链接、公式约定与代码块就是可使用接口。移动文件或改变概念顺序，需要同步更新这些连接。

标签可以为某个版本提供易读名称，附注标签还可以包含说明等信息。但标签本身并非天然不可移动，稳定性来自发布约定与权限控制。长期记录仍应保存标签所指的实际对象身份及来源。签名可以增加可验证来源证据，但不证明模型公平、算法正确或数据许可完备，这些是其他层的判断。

发布后的修正也应可追踪。若发现评价错误，不能只替换同名文件而不记录变化；否则旧报告与新文件无法区分。可以发布新版本并说明受影响范围，保留必要旧身份与更正关系。稳定发布不是永不犯错，而是错误发现后仍能准确解释哪些对象、条件与结论发生了变化。

<a id="git-4-detail-17"></a>

### 9.1 独立恢复演练能揭露隐藏状态

最有价值的复现检查之一，是在独立目录或进程按说明运行，而不依赖作者当前会话。它可以发现未提交配置、绝对路径、交互式变量、残留缓存和隐式下载。能在原终端再次运行，只能证明该会话仍保有足够状态；独立恢复才更接近交付给别人的真实使用方式。

恢复演练应从固定身份出发，核对输入与产物摘要，运行最小推理或训练闭环，并记录预期输出。对于非确定性结果，可以定义合理容差和统计标准，而不是要求不现实的逐位相同。若失败，应定位哪一层不一致：获取、解析、环境、随机性还是实现，而不是反复更换种子寻找偶然相同数字。

演练还需考虑离线与权限前提。某个受许可数据集无法随仓库分发，仍可提供合法获取方式、版本说明和小型公开替代测试，但必须承认完整复现需要额外权限。记录充分不等于所有读者都能取得全部输入，清楚表达可获得性边界才是诚实交付。

## 10. 实验四：在独立进程中重算固定产物

下面把最小计算写入临时程序，记录固定输入与输出摘要，再从独立进程执行。它演示清单如何把输入、配置、程序与结果连接起来，而不是展示复杂训练框架。计算使用整数，避免把浮点容差分散为主要话题；实际模型应根据数值性质设计误差标准。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import hashlib
import json
import subprocess
import sys

with TemporaryDirectory(prefix="independent_replay_") as root:
    folder = Path(root)
    program = (
        "from pathlib import Path\n"
        "import json\n"
        "values = json.loads(Path('input.json').read_text())\n"
        "result = {'score': sum(x*x for x in values['x']) * values['scale']}\n"
        "Path('output.json').write_text(json.dumps(result, sort_keys=True))\n"
    )
    script = folder / "compute.py"
    script.write_text(program, encoding="utf-8")
    (folder / "input.json").write_text(
        json.dumps({"x": [1, 2, 3], "scale": 2}), encoding="utf-8")
    def digest(path):
        return hashlib.sha256(path.read_bytes()).hexdigest()
    source_identity = digest(script)
    input_identity = digest(folder / "input.json")
    subprocess.run([sys.executable, "compute.py"], cwd=folder, check=True,
                   capture_output=True, text=True)
    result = json.loads((folder / "output.json").read_text(encoding="utf-8"))
    assert result == {"score": 28}
    output_identity = digest(folder / "output.json")
    (folder / "output.json").unlink()
    subprocess.run([sys.executable, "compute.py"], cwd=folder, check=True,
                   capture_output=True, text=True)
    assert digest(script) == source_identity
    assert digest(folder / "input.json") == input_identity
    assert digest(folder / "output.json") == output_identity
    print("independent replay score=28; source/input/output identities verified")
```

这里固定的是程序文件与输入字节，独立进程仍使用同一个解释器和同一机器。因此结论是同环境独立进程重算一致，不是跨平台完整复现证明。范围说清楚以后，这个小实验仍然很有价值：它排除了依赖交互式内存变量的可能，并建立了输入到输出的可检查映射。

## 11. 实验谱系中的选择、失败与统计解释

研究结果不是只有最后一条成功运行。候选方案数量、搜索预算、停止规则、失败与人工筛选都影响结论。若在同一验证集上反复尝试，再只报告最高值，就会产生选择乐观偏差。Git 可以保留全部代码历史，但即使历史完整，统计偏差仍然存在，因为问题来自选择过程与评价复用。

一个实用做法是把探索、选择和最终评估分开。探索阶段允许调整方案并记录预算；选择阶段依据预先说明的验证协议确定候选；最终评估使用未参与选择的信息，并说明重复与不确定性。并非所有研究都能完全做到，但偏离之处应透明，而不是把探索后的结果描述成事先固定的单次检验。

失败运行也应保留合适记录。资源不足、数值发散、数据错误和人工取消分别代表不同事实，不能全部从统计中悄悄删除。若方案经常失败，只报告幸存运行会夸大稳定性。可以在汇总表中区分有效完成、环境故障和目标失败，并说明纳入规则。记录应服务于理解，不必保存每一个无关调试字符。

模型选择的“最佳”必须有确定规则。使用哪个指标、最大化还是最小化、在哪个数据集、候选包含哪些轮次、并列如何处理，以及是否根据测试集改过规则，都应可查。文件名叫最佳只是一种别名，真正身份由选中产物与选择过程共同决定。没有规则的最佳，很容易成为作者记忆中的偶然状态。

<a id="git-4-detail-20"></a>

### 11.1 实验分支与可发布结果承担不同责任

探索分支可以快速试错，正式结果需要稳定身份、可获取输入和明确验收。不能为了保持探索自由，省略发布时的复核；也不必为了发布整洁，把所有探索操作逐条塞进说明。合理组织是让实现说明围绕最终行为，另以实验清单保留影响结论的选择与预算，并通过固定身份连接。

发布前可以做一次独立最小恢复，再核对报告中的指标是否确实来自声明产物。某些项目里，报告使用的是验证阶段模型，发布文件却是最后一轮模型；两者名称相近，但内容与性能不同。产物摘要和运行映射能够发现这种错配。不要只检查文件存在，还要检查它是否是那一个文件。

对后续继续训练，旧权重成为新运行输入，应记录父产物而不是只记父代码提交。否则相同代码与配置也可能从不同初始化出发，产生不同结果。谱系需要跨越代码、数据与模型对象，不能把所有来源压缩成一条分支名称。

## 12. 共享工作树、标签与保留策略的边界

独立工作树允许同一对象数据库关联多个工作目录，各自有索引与检出位置，适合同时检查不同版本。它避免频繁切换对同一目录的干扰，但并不提供完整机器隔离。共享仓库配置、外部缓存、端口、数据库与产物路径仍可能产生竞争。运行设计必须覆盖真正共享的资源。

工作树还需要遵守工具对分支同时检出的约束，不要通过强制选项随意绕过而不理解原因。多个工作目录同时修改同一分支引用，会使人难以理解某次操作之后哪个目录对应哪一状态。若只是只读检查某个提交，可以使用明确的分离检出；若需要持续开发，应分配清晰分支与负责人。

标签适合给发布状态命名，但名称本身仍可能被删除或移动。稳定约定、权限和实际对象身份共同构成发布保证。长期结果清单应记录完整目标身份及可获取位置，并保存必要外部产物。一个提交仍在远程历史中，不意味着对应数据或模型也被远程仓库保存了。

保留策略还要考虑成本。所有逐步检查点永久保存可能不现实，但只留最高分产物又可能丢失恢复与审计能力。可以按用途分层：保留发布产物、关键里程碑、运行清单和必要统计，按明确期限清理可重建缓存。清理的依据应是可替代性与保留需求，而不是文件名看起来临时。

<a id="git-4-detail-22"></a>

### 12.1 中间文件清理如何保持结果完整

整理实验项目时，应先明确可复现结果所依赖的文件：源代码、有效配置、数据身份、环境说明、必要模型与评价记录。失去这些依赖，单独的分数或图片通常不能重建结论。清理时逐项确认文件来源、引用关系和用途，仅删除已经失去用途的临时产物，并把清理范围限制在当前项目内。

本章示例采用系统临时目录上下文，实验结束自动回收，这比在正式资料目录先堆积辅助文件再猜测清理更简单。对于长期训练产物，自动清理则必须更谨慎，确保所选模型、必要日志与清单已经可靠保留。目录整洁不能以丢失结果来源为代价。

对于资料仓库，最终验收可以检查所有文件是否为预期格式、目录链接是否存在、代码块能否解析、独立例子是否运行、旧锚点是否保留。每个检查都有明确对象。不要仅以总字数或文件大小判断内容完整，也不要只看导航正确就认为推导详实。结构与内容需要各自核对。

<a id="git-4-detail-23"></a>

## 13. 练习与详细解析

<a id="git-4-detail-24"></a>

### 13.1 练习一：两次都写使用主分支为何不够

同一分支在两次运行之间可能前进，工作区还可能有不同补丁，因此名字无法唯一固定代码。至少需要记录实际提交与未提交变化，同时关联配置、数据和环境。若分支只是展示别名，可以保留，但不能把它当成唯一身份字段。

更完整的答案还应考虑可获取性：即使记录完整对象标识，未来仓库或对象可能不再可用。需要保留适当引用与副本，并确认外部输入也有固定身份。定位与保留是两项责任，缺一都会阻碍重建。

<a id="git-4-detail-25"></a>

### 13.2 练习二：获取后为什么本地文件没变

获取更新了对象和远程跟踪引用，但当前本地分支与工作区没有自动整合。这是预期边界，不是获取失败。可以检查目标引用身份，再按照约定执行快进、合并或其他整合。若分叉，应先理解两侧变化，不要直接覆盖。

这个问题也能用三份身份回答：实际远程、最近观察的远程跟踪引用、本地分支。它们在不同时间可以不同。把观察与整合拆开，能更容易解释当前看到的状态。

<a id="git-4-detail-26"></a>

### 13.3 练习三：领先落后计数是否实时可靠

计数通常相对本地已有引用计算。未获取时可能过期，获取之后远程仍可能继续变化。因此计数是观察时刻的证据，而不是锁。需要更新远程时，服务器还会核对实际引用与策略，拒绝可能反映并发变化。

不能把本地显示零落后当成覆盖远程的授权。协作需要理解内容和约定，工具计数只提供图关系信息。显式租约可以检测某些竞争窗口，但同样不替代内容审查。

<a id="git-4-detail-27"></a>

### 13.4 练习四：显式租约通过是否代表整合正确

不代表。它主要检查远程旧值是否等于预期。你可能预期了错误对象，或者新内容本身有缺陷，条件仍然成立。租约保护的是特定并发条件，不是完整语义正确性。真实共享项目还需要权限、审查与验证。

若预期来自会被后台刷新跟踪引用，保护范围还可能与操作者原本审核的状态不同。更清楚的做法是保存明确预期并理解其来源，但即便如此，也要确认更新目标符合协作目的。

<a id="git-4-detail-28"></a>

### 13.5 练习五：配置文件与运行值不一致如何复现

先明确覆盖顺序，把默认、文件、环境和命令行形成的最终有效配置记录下来，再保存必要来源解释。仅复制原文件可能重建另一个实验。对嵌套结构要说明浅合并还是递归合并，并校验无效字段。

验收可以重新解析并比较规范化有效配置，而不只是比较文件名。若某些值由设备检测动态生成，也应把实际选择写入记录。否则相同启动命令在不同机器上可能产生不同计算条件。

<a id="git-4-detail-29"></a>

### 13.6 练习六：同提交同种子是否必然相同结果

不必然。数据、预训练权重、依赖、硬件、精度与非确定算子都可能不同；随机种子也不一定覆盖全部随机源。需要声明复现层次，是逐位一致、数值容差一致还是统计结论一致，并记录对应条件。

如果结果不同，应先定位输入与环境层，而不是不断更换种子找接近数字。一个看起来相同的最终分数也不能证明过程相同，可能只是偶然抵消。复现关注条件与机制，不只是输出表面。

<a id="git-4-detail-30"></a>

### 13.7 练习七：数据目录名为何不是版本

同一目录可以被覆盖、增加文件或改变顺序，名字保持不变。应固定实际成员、内容摘要、格式与处理规则。划分还需要记录单位与成员，避免同种子在不同数据顺序下生成不同集合。

若数据很大，可以使用分片清单而非把全部字节塞入代码仓库，但必须保证清单能定位不可变内容。一个可变下载链接只是获取入口，不足以单独承担版本身份。

<a id="git-4-detail-31"></a>

### 13.8 练习八：最佳模型还缺什么信息

至少缺选择指标与方向、验证数据版本、候选范围、轮次和并列规则，还需要连接代码、配置与产物摘要。若根据测试集反复选择，统计解释也会受影响。名称最佳不是一个自解释的科学结论。

验收时应加载报告声明的确切产物重算关键指标，而不是随便找同名权重。若发布文件与报告模型不同，要明确说明差别并分别记录结果，不能靠相似文件名掩盖来源错配。

<a id="git-4-detail-32"></a>

### 13.9 练习九：失败运行可否全部删除不计

不能一概如此。环境中断与算法数值失败代表不同事实，纳入规则应预先说明。只保留成功且高分的运行可能高估稳定性，并隐藏搜索预算。可以清理无用大日志，但应保留足以解释运行状态和选择的记录。

例如某方案十次中八次发散，只报告两次成功平均值会误导。应同时报告成功率或失败条件，并说明指标汇总对象。代码历史完整也不会自动纠正这种统计筛选。

<a id="git-4-detail-33"></a>

### 13.10 练习十：内容摘要相同证明什么

在采用同一摘要算法与编码规则的条件下，它提供所摘要内容身份一致的强证据，但不解释来源可信、标签正确或使用协议合理。若摘要清单本身被不可信来源替换，文件与清单一致也不能证明真实性。

还要区分原始字节摘要与规范化摘要。后者可能有意忽略某些表示差异，因此需要解释规范化规则。不能用配置的规范化身份替代原始数据字节身份而不说明。

<a id="git-4-detail-34"></a>

### 13.11 练习十一：独立工作树是否隔离训练输出

不自动隔离。若两个工作树把产物写到同一绝对路径，仍会覆盖。缓存、数据库和端口也可能共享。应给每次运行独立身份与资源命名，明确哪些输入可共享、哪些输出必须独立。

工作树解决的是多个代码检出目录的问题，不是完整容器或虚拟机。正确选用它需要承认边界，而不是因为它方便就赋予其不存在的隔离能力。

<a id="git-4-detail-35"></a>

### 13.12 练习十二：代码整理能否隐藏搜索历史

正式交付说明可以围绕最终实现重写，省略无关聊天过程，但影响结论的尝试次数、预算与筛选不应消失。代码审查材料与实验记录承担不同责任，可以分开保存并通过身份连接。

如果一百次尝试后选出最高验证分数，却描述成固定方案的一次运行，版本历史再整齐也不能消除选择偏差。组织清楚与统计透明应同时实现，而不是互相牺牲。

<a id="git-4-detail-36"></a>

### 13.13 练习十三：发布标签天然不可变吗

不是。标签名称可以被移动或删除，稳定性来自约定、权限和保留策略。长期清单应保存实际对象身份与来源。附注或签名标签可以增加说明和来源证据，但不证明算法与实验结论正确。

发布更正时应给新内容明确版本与更正关系，避免无声覆盖同名产物。这样旧报告仍能定位其对象，新读者也能知道当前推荐版本及变化范围。

<a id="sec-7-2"></a>

<a id="git-4-detail-37"></a>

### 13.14 边界追问：固定分支名能否固定代码状态

不能，分支是可移动引用，且运行可能包含未提交内容。重建需要固定提交、实际补丁与必要未跟踪输入。若分支后来被变基，旧运行仍应关联旧身份，而不是把结果字段改成新版本。事实记录与当前工作分支应分开。

进一步说，即使固定代码树，也还没有固定数据与环境。完整实验身份是多个输入之间的关系，不是一个字符串。可以逐层加强证据，但不应把某一层的成功宣称为全部完成。

## 14. 进阶研究练习与解析

<a id="git-4-detail-39"></a>

### 14.1 研究题一：把运行清单建成依赖图

请设计一个最小数据模型，表达两次运行使用同一代码但不同数据，第三次运行从其中一个检查点继续训练。参考方案分别建立代码、数据、配置、运行与产物节点；运行连接其输入与输出，继续训练通过父产物连接，不把父代码提交误当成父权重。

验收时沿任一最终产物应能追到其全部必要输入与选择规则；沿任一输入应能列出受它影响的运行。若数据被更正，可以据此定位需要复评的结果。这个反向可查询性比单向写一份启动命令更有价值，也能帮助发现隐藏依赖。

<a id="git-4-detail-40"></a>

### 14.2 研究题二：设计一个能揭露隐藏状态的恢复演练

准备一个固定小实验，在新进程和新目录按说明恢复，禁止读取原工作区。先核对代码与输入身份，再执行最小闭环，比较预设输出或容差。若失败，按获取、环境、解析、计算和选择层定位，不要随意更改参数直到数字接近。

演练应刻意检测绝对路径、被忽略配置和缓存依赖。可以临时移走原目录或在受控环境中只提供声明输入，但需要确保不破坏重要资源。目标是证明说明足以支撑独立使用，而不是证明作者当前终端还能运行。

<a id="git-4-detail-41"></a>

### 14.3 研究题三：审查一张只报告最高分的结果表

假设表中每个模型只保留最好种子的测试分数。首先询问候选数量、选择发生在哪个数据集、失败是否删除、预算是否一致。若测试集参与反复选择，应重新界定结论，必要时使用独立评价或预先固定方案重测。Git 提交可以定位实现，却不能弥补选择协议的不足。

验收报告应把代码追踪与统计有效性分开评估。一个结果可以代码来源完整但选择偏差严重，也可以评价设计合理却缺少可恢复产物。两项都重要，不能因为其中一项优秀就自动授予另一项通过。

<a id="sec-7-1"></a>

<a id="git-4-detail-42"></a>

### 14.4 综合练习：重建结果需要哪些版本信息

只给分支名和最佳模型，无法可靠重建结果。应先找到实际代码身份与工作区补丁，再固定有效配置、数据与划分、预训练来源、依赖环境、随机性设置、运行状态和产物摘要，最后补上选择规则与最小验证入口。每个字段都要连接实际对象，不能只是填一个看起来正式的名称。

逐层验收可以先加载固定输入并核对前处理，再检查模型构造与权重匹配，随后验证最小推理输出，最后按协议重算指标。若要求重训，应另设预算与复现容差。完成这些之后，才能说明哪些层已重建，哪些层仍受权限、硬件或非确定性限制。可追踪不等于无选择偏差，独立可运行也不等于科学结论已经广泛成立。

<a id="git-4-detail-43"></a>

## 15. 进阶专题：协作规范如何成为可检验协议

<a id="git-4-detail-44"></a>

### 15.1 规范应表达不变量而不是仪式

一份有效规范首先说明希望保持什么，例如主线提交可独立检出、报告结果可定位到固定产物、共享历史改写有明确协调、每次运行保留有效配置。这些是不变量。具体使用合并还是变基、何时压缩提交，应服务于这些目标，而不是把某种历史外观当成唯一正确形式。

可以为不变量设计检查：主线用干净环境运行最小测试；结果表检查身份字段与产物摘要；配置解析输出最终值；资料仓库检查链接和代码块。检查失败应该指出缺少的具体证据，而不是只给一个模糊的“不符合流程”。规则越能连接实际使用风险，越容易被团队理解和维护。

规范也需要例外机制，但例外不等于没有责任。比如紧急修复可以先止损再补完整实验，说明中应区分已执行检查与后续验证。关键是让承诺与证据保持一致，而不是为了形式完整声称尚未完成的工作已经通过。透明的有限交付比虚假的全覆盖更可靠。

<a id="git-4-detail-45"></a>

### 15.2 可复现性具有层次，不能一概而论

逐字节恢复输入、重建同样计算图、得到容差内数值、重复统计趋势和复核科学结论，是逐步扩展的不同目标。某个层次失败不一定否定所有其他层，但每个结论都应有相应证据。跨硬件浮点变化可能破坏逐位一致，却仍保留统计结论；数据泄漏则可能让所有重跑数字一致却科学结论无效。

因此复现报告应该写清目标层次和判定标准。若只做固定权重最小推理，不应称为完整训练复现；若只恢复代码，不应称为完整实验恢复。清楚的层次帮助读者决定材料是否满足自己的用途，也帮助作者合理安排验证成本。

版本控制在这些层次中提供基础身份与历史关系。它非常有用，却不应被过度神化。研究者还需要良好的测量、统计、数据管理和科学推理。把工具边界讲清楚，反而能让工具发挥更稳定作用。

<a id="git-4-detail-46"></a>

### 15.3 从一次交付建立长期可维护的知识

每次重要变化都可以留下一个小而完整的知识单元：问题、触发条件、行为变化、验证与限制。若这些单元能够通过提交与运行身份连接，未来的人就能理解为什么某个接口存在、为什么某条测试重要、为什么某个结果不可直接比较。知识不必全部放在提交说明里，但必须能够被发现。

长期维护还需要处理失效。依赖下载源、外部数据和服务接口会变化，旧说明可能不再可执行。可以保留固定产物、记录获取失败原因并提供适当替代演示，但不能在未经验证时继续宣称完整复现。更新材料时应区分原历史事实与当前可执行入口，让读者同时理解过去和现在。

最终，协作规范的成功标准是别人能接手、能核对、能解释差异，而不是目录里有多少说明文件。一个简洁清单若准确连接全部关键对象，胜过冗长却含糊的过程日志；一份详细章节若把机制、边界与例子讲透，也比堆积命令更能培养独立判断。组织形式应服务于可理解和可验证的结果。

<a id="git-4-detail-47"></a>

### 15.4 清单格式演进需要版本与兼容规则

清单本身也是接口。今天只记录学习率与种子，明天增加数据转换和选择规则，如果没有格式版本，旧记录的字段缺失可能被误当成默认值。应给清单模式明确版本，并规定缺失、未知字段与迁移行为。旧记录不具备的信息不能通过填一个当前默认值伪装成当时事实，应标记未知或无法恢复。

字段类型也需要约束。种子写成整数还是字符串，学习率能否是非有限数，路径相对哪个根目录，摘要采用何种算法，都应清楚。一个能被 JSON 解析的文件，不一定满足实验语义。模式校验可以发现结构问题，内容身份核对可以发现对象不一致，独立运行可以发现执行问题；三种检查逐层增强，不能相互替代。

如果规范化配置改变，应保留规范化版本，因为同一语义对象可能在新算法下得到另一摘要。可以同时记录原始字节与规范化身份，并说明用途。长期系统里，身份规则的演进比一次性脚本更重要：只有规则可解释，未来的人才能判断不同标识究竟代表内容变化还是表示变化。

<a id="git-4-detail-48"></a>

### 15.5 搜索预算与资源记录怎样影响比较

两个模型在同一测试集上比较，若一方经过数百次搜索而另一方只运行一次，结果反映的是模型与搜索预算的联合效果。它仍可能具有实际价值，但不能简单归因于架构本身。清单应记录搜索空间、实际完成次数、训练预算和筛选规则，使读者能够理解比较对象。

资源统计也应声明单位和边界。墙钟时间受硬件、并行度与数据加载影响，设备时间与能耗又是其他指标；只报告最快一次可能隐藏失败重试。可以按任务需要选择合适统计，但应说明计入哪些运行和预处理。版本控制固定代码，不会自动让不同硬件上的时间具有同等含义。

对个人学习，完整记录每秒资源可能过度，但至少可以保存候选数量、重要失败原因与最终选择依据。记录粒度应匹配结论粒度：如果只总结一个例子的机制，无需伪装成全面基准；如果要声称方案普遍更好，就需要更充分比较。合适的详实程度来自问题，而不是机械填满模板。

<a id="git-4-detail-49"></a>

### 15.6 交接检查可以从一条结果反向走完

选择报告中的任意一行结果，先找到对应产物，再找到选择规则、运行、有效配置、数据和代码；随后按说明重算一个最小观察。这个反向过程能直接发现断链：产物被覆盖、清单只有分支名、配置未记录覆盖、数据版本不可取得。相比只检查每个目录是否存在，它更接近实际使用需求。

也可以让未参与原实验的人执行这项检查，观察说明在哪一步产生歧义。若需要作者不断补充口头提示，就把这些必要提示转化为正式输入或文档，而不是只为这次演练临时解决。独立使用者能否按材料完成固定任务，是对交付完整性很直接的检验。它不要求保存所有探索噪声，却要求保留真正决定结果的条件与解释。

如果反向追踪成功，还应确认失败与限制没有被隐藏。例如该结果只在特定语言、长度或设备上验证，就不应在交接时被描述为任意场景可用。交接的目标是传递准确能力边界，而不是把所有不确定性删掉。一个知道何时适用、何时需要复核的结果，比看起来无条件完美的结果更容易被可靠使用。
