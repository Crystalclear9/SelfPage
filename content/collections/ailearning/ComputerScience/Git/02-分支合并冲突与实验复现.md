## 1. 分支是提交指针，不是独立文件夹副本

一个本地分支通常是指向提交的可移动引用。新建分支主要增加一个名字与目标之间的关系，不需要复制全部文件内容，因此分支创建通常很轻量。当你在该分支上创建提交时，分支引用前进到新提交；原提交和从它派生的其他分支不会因为这个动作而自动改变。工作区呈现的是当前检出状态，和“仓库中一共存在多少分支”不是同一概念。

分支名是便于交流的可变标签，提交身份则用于定位具体历史对象。报告“在实验分支上训练”无法固定结果，因为该分支明天可以继续前进。更准确的记录是某个仓库中的完整提交标识，加上工作区是否存在补丁、配置和数据身份。分支名仍有意义，它表达工作流角色，但不能替代不可变的版本定位。

通常 HEAD 指向当前分支，分支再指向提交；在分离状态下，HEAD 可以直接指向某个提交。这不是仓库损坏，而是另一种检出状态。若在这种状态下创建新提交，应在切走前建立明确引用以便保留和发现。不要把“现在能看见提交”误解为“它已经属于一个长期维护的分支”。

切换分支也不是无条件清空再恢复工作区。Git 会在可能覆盖未提交修改等情况下拒绝或要求处理，而某些不冲突的未提交变化可能被带到新分支。因此不能把切分支当成隔离未提交实验的万能工具。真正需要并行运行不同版本时，独立工作树或独立检出通常更清楚，但仍要隔离输出目录与外部状态。

### 1.1 用祖先关系判断是否需要真正合并

假设主分支指向提交甲，实验分支从甲出发又产生乙和丙，主分支没有新增提交。此时把实验分支整合到主分支，可以直接把主分支引用移动到丙，这叫快进。没有必要创建额外合并提交，因为原有历史已经包含甲到丙的完整路径。快进改变引用，不会把乙、丙重写成新身份。

如果主分支从甲另行产生丁，两个分支已经分叉。此时不能把主分支简单向前移动到丙而同时保留丁的后代关系；通常需要创建一个同时具有丁和丙为父的合并提交，或者采用变基等其他整合策略。决定因素是提交图的可达关系，不是哪个分支文件更多或时间戳更晚。

还有一种情况是实验分支的所有提交已经是主分支的祖先，整合时可能报告已经包含。即使实验分支名称仍然存在，也不意味着有待整合内容。名称是否删除属于工作流清理，历史是否已经包含属于图关系判断。把这两个问题分开，能避免反复执行没有实际意义的合并。

### 1.2 为什么合并依据共同祖先而非简单覆盖

假设祖先配置中批量大小为三十二，主分支改成六十四，实验分支保持三十二但新增正则化。若直接用实验分支整份文件覆盖主分支，会错误地撤掉批量大小调整。三方合并利用祖先判断：批量大小只在主分支改变，正则化只在实验分支增加，因此在可自动组合的条件下应保留两项变化。

共同祖先使工具能够区分“一侧有意修改”和“另一侧只是沿用旧内容”。这比简单比较最终两份文件提供更多上下文。但算法仍只依据内容与结构规则推断组合，无法完整理解训练协议。两项文本上独立的变化可能在数学上互相影响，例如一侧改变损失归约方式，另一侧改变学习率标定，合并之后需要重新验证有效步长。

复杂提交图中可能存在多个同样合适的最佳共同祖先，不能永远假设唯一一条简单分叉。具体合并策略会处理这些情况，可能先形成虚拟基线。初学实验采用单共同祖先，是为了使推理透明；当真实仓库出现交叉合并时，应检查提交图和实际策略，而不是硬套一张直线示意图。

## 2. 三种整合结果与它们的承诺

快进、普通合并和压缩整合提供不同历史结构。快进保留已有提交并移动引用；普通分叉合并通常创建多父提交，记录两侧历史汇合；压缩整合把组合结果准备成相对当前历史的一份变化，后续普通提交通常只有一个父，不会在提交图中记录对方分支为已合并祖先。目录内容可能相近，历史语义却不同。

选择方式时应先问希望保留什么证据。研究性分支包含多个有价值的中间假设，保留原始历史可能帮助理解；临时试错包含大量无意义修正，压缩后形成一个清楚的行为单元可能更易审查。但压缩意味着提交图不能直接表达原分支全部祖先已经汇入，后续再整合同一长期分支时需要格外理解共同祖先与重复改动。

普通合并也不保证产生合并提交：允许快进时，满足祖先条件就可以只移动引用。若流程要求保留明确分支汇合节点，可以使用相应禁止快进选项；若要求只允许快进，则在分叉时让命令失败，以便人工选择策略。应把这些选项理解为历史结构约束，而不是好坏排序。

合并提交的父顺序通常有意义：第一父对应执行合并时所在的当前分支，其他父对应被整合的历史。沿第一父查看可以突出主线整合事件，但不会展示所有侧支细节。审查合并结果时，还应比较与不同父的差异，避免只看某一种界面而遗漏冲突解决时额外引入的变化。

<a id="git-2-detail-5"></a>

### 2.1 合并基线与最终树的独立身份

可以把三方合并写成一个依赖基线与两侧树的操作，但不要把它想成普遍满足交换律的简单集合并。冲突选择、路径重命名、模式变化和策略选项都可能影响结果；即使内容相同，合并提交的父顺序和元数据不同也会影响提交身份。数学记号可以帮助列出输入，却不能替代具体算法与语义判断。

一个重要不变量是：合并之前两侧已经存在的提交对象不会被普通合并原地修改。新合并提交只是增加新的树与关系。相比之下，变基会生成重放后的提交对象。理解这个差别，有助于解释为什么普通合并通常不会让同伴原先依赖的提交身份失效，而对共享分支进行历史改写需要协调。

## 3. 冲突是尚未决定的组合，不是损坏

文本冲突表示 Git 无法按照当前策略唯一决定某些内容如何组合。常见原因包括两侧重叠修改、同一路径一侧删除另一侧修改、两侧以不兼容方式新增同名文件，以及重命名与删除等结构变化。冲突不是“文件有两份所以任选一份”，而是有一组尚未满足的组合约束需要人来判断。

普通内容冲突中，工作区可能出现分隔标记，展示当前侧和另一侧的候选内容；采用包含祖先的显示风格时，还能直接看到基线。索引则保留未合并阶段：常见的阶段一是基线，阶段二是当前侧，阶段三是另一侧，并非每种冲突都必然具有所有阶段。删除与新增场景中某个阶段可能不存在。

解决冲突的基本过程是确认双方目的，编辑最终应有内容，运行相应验证，再把解决后的路径加入索引。暂存动作在这里不仅保存内容，也表示你确认该路径已解决。如果只删除标记却丢掉必要逻辑，Git 可能接受这个结果，因为它不能判定你的业务承诺。工具的接受不等于语义上的正确。

需要停止整合时，可以在理解当前状态后使用相应中止流程。合并开始前若带有复杂未提交修改，恢复原状态可能更困难，某些修改也可能无法可靠重建。因此教学与重要整合都优先采用已理解、已保留的起始状态。不要为了处理一个冲突，随手执行会覆盖更多工作区内容的命令。

<a id="git-2-detail-7"></a>

### 3.1 先写双方不变量，再决定最终代码

假设当前分支修复了空批次除零，另一分支新增样本权重。直接选择任一侧都可能丢失另一侧目标。更可靠的方法是写下两个必须保持的条件：有效权重总和为零时按接口定义处理；有效权重非零时使用正确归一化。然后设计同时覆盖两者的最终实现，并用可手算的样本验证。

这样做把冲突从文本选择题变成约束满足问题。你可以发现双方设计本身也许不兼容，例如一侧规定空批次跳过优化器步，另一侧规定所有批次都推进学习率调度。此时需要决定组合后的协议，并更新测试与说明。不存在一条通用的“保留较新代码”规则可以自动解决这类问题。

解决过程中最好保留问题与决策的解释。未来读者看到合并提交时，需要知道为什么最终结果不同于两侧原文。合并说明不必列出每个标记，但应解释重要语义取舍、兼容性变化及验证范围。对于接口迁移，这些解释往往比单纯保留两侧提交列表更有价值。

<a id="git-2-detail-8"></a>

### 3.2 ours 与 theirs 为什么必须带上下文理解

在普通合并中，当前侧与被合并侧通常分别对应正在检出的分支和指定的另一历史。变基期间，冲突发生在把旧提交重新应用到新基线的过程中，界面中的当前侧可能对应已重放的新基线，而另一侧对应正在重放的旧提交。这与“我的实验”和“同伴代码”的日常归属不一定一致。

因此，不要根据英语单词的直觉一键覆盖。先读取当前操作类型，查看正在应用的提交、基线和冲突阶段，直接比较实际内容。尤其在自动脚本中，不能把一个适用于普通合并的全局选择策略未经核对用于变基。命令行选项还可能区分整棵树策略与冲突块偏好，名称相近不意味着语义相同。

更一般的原则是：角色由当前操作定义，作者身份由历史定义，业务目的由任务定义。三者常常一致，却不是同一概念。解决冲突时同时确认这三个层面，可以避免把“保留我写的内容”误当成“保留正确行为”。

## 4. 无文本冲突的语义冲突

一侧把数据字段从旧名改成新名，另一侧在新文件中增加读取旧名的代码。由于改动位于不同文件，文本合并可能完全成功，运行却会报错。这是最容易识别的语义冲突。更隐蔽的情况是程序仍能运行，但使用了错误单位、不同标签顺序或不匹配的归一化，使结果悄悄偏离预期。

例如一侧把损失从样本均值改成总和，另一侧引入按批次调节学习率的规则。合并后梯度尺度可能随批量大小变化，训练过程不再等价。或者一侧调整类别编号，另一侧增加按旧编号解释混淆矩阵的脚本，最终图形数值合理却标签含义错误。这些问题不能仅靠冲突标记检测。

语义验证要围绕跨模块契约组织：输入模式、单位、形状、缺失值、输出含义、默认配置和错误处理。合并时应读取双方改变的契约，而不只搜索同一个函数是否被修改。必要时为组合后的场景补充测试，因为双方原有测试各自只覆盖自己所基于的祖先环境。

自动合并成功仍有价值，它节省文本整合工作；但它提供的证据范围必须准确。可以说“树构造完成，未出现需要人工解决的文本冲突”，不能直接说“两个实验可以科学地比较”或“合并结果保持所有行为”。后两种结论需要额外观察和推理。

<a id="sec-6-1"></a>

<a id="git-2-detail-10"></a>

### 4.1 构造一个能揭露接口错配的最小例子

把问题缩小为一条数据记录：基线提供字段甲，分支一把它改为乙，分支二新增读取甲并乘二的函数。合并后，旧测试只检查记录是否有一个数，新函数测试使用自己手写的甲字段，因此都可能通过；只有把真实加载器输出送入新函数的集成测试才会揭露错配。

这个例子说明测试数量多不等于覆盖组合关系。关键是让测试跨越发生变化的接口，并使用真实协议。最小例子应当小到可以手工算出期望输出，同时真实地连接双方改动。若采用兼容层，应测试旧名与新名同时存在、只存在其一和都不存在时的明确行为，避免默默取错值。

研究任务中还应检查评估端。训练与评估分别沿用不同预处理版本时，模型可能在不一致输入上被评分。合并代码后只重跑训练单元测试无法发现全部问题。一次完整的最小闭环应该包括数据读取、前处理、模型调用、指标计算以及结果标签解释。

## 5. 变基是重新表达历史中的变化

变基的常见用途，是把一系列本地提交重新应用到新的基线上。假设实验分支从甲产生乙、丙，主线从甲产生丁。变基后可以得到从丁出发的新提交乙新、丙新，原乙、丙通常仍是原对象，只是实验分支引用转而指向新的链。因为父关系改变，新的提交身份通常也改变。

“变化重新应用”不等于机械地保存每个文件最终字节。新基线可能已经包含某些改动，某些提交可能变成空变化或被识别为重复；遇到冲突时，人工解决也可能改变最终内容。默认流程也不必保留原有合并拓扑，保留合并结构需要理解专门选项及其边界。因此变基完成后应检查提交范围与最终树。

变基的好处是可以让一串待审查变化建立在当前主线上，便于按线性顺序理解；代价是对象身份与依赖关系改变。若其他人已经基于旧提交继续工作，改写共享分支会使他们需要重新协调。是否采用变基不是纯粹的审美问题，应结合协作约定、分支是否共享、审查与发布工具如何关联提交来决定。

在变基冲突期间，应先确认当前正在重放哪一条提交，再解决与继续。跳过提交意味着放弃该步的变化，而不是通用的“忽略错误”。如果不确定应保留什么，先读取原提交目的与差异。必要时中止并回到已知状态，重新设计整合计划，比在未知状态下连续尝试多个强制选项更可控。

<a id="git-2-detail-12"></a>

### 5.1 合并与变基可以产生相同树吗

可以构造两条不同历史，使最终根树相同：一条通过合并保留两侧父关系，另一条通过重放形成线性链。树相同说明 Git 记录的最终内容相同，不说明提交图相同，也不说明中间每个版本相同。对最终构建，两者可能具有相同源文件；对审计、归因和后续整合，区别可能很大。

这种区分有助于讨论工作流时避免空泛争论。若目标是证明最终代码一致，可以比较树；若目标是保留实验分叉如何汇合的证据，需要检查图；若目标是审查一组逻辑补丁，需要检查提交序列与范围。一个指标不能覆盖所有目标，选择策略应明确优先保留哪一种信息。

对变基后的实验记录，还要处理旧运行结果。旧结果仍然对应旧代码身份；即使你认为新树等价，也应明确记录等价依据与验证范围，不能直接把旧结果的提交字段改成新哈希。研究记录应保存事实发生时的状态，再添加新的映射或复核结果。

## 6. 实验一：快进与真正合并的父关系

下面的独立实验用临时仓库构造两种图。第一个整合要求只能快进，验证没有新增提交；第二次在两侧分别修改不同文件，验证真正合并的提交具有两个父。所有写入都发生在自动清理的临时目录，命令使用参数列表，不会操作用户现有仓库或连接远程。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_merge_graph_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(*args):
        return subprocess.run(["git", *args], cwd=repo, env=env, text=True,
                              encoding="utf-8", capture_output=True,
                              check=True).stdout.strip()
    def write(name, text):
        (repo / name).write_text(text, encoding="utf-8")
    git("init", "-b", "main")
    for key, value in [("user.name", "Example"),
                       ("user.email", "example@example.invalid"),
                       ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
        git("config", key, value)
    write("base.txt", "base\n")
    git("add", "--", "base.txt")
    git("commit", "-m", "base")
    git("switch", "-c", "topic")
    write("topic.txt", "topic\n")
    git("add", "--", "topic.txt")
    git("commit", "-m", "topic change")
    topic = git("rev-parse", "HEAD")
    count = git("rev-list", "--count", "--all")
    git("switch", "main")
    git("merge", "--ff-only", "topic")
    assert git("rev-parse", "HEAD") == topic
    assert git("rev-list", "--count", "--all") == count
    git("switch", "topic")
    write("topic.txt", "topic next\n")
    git("add", "--", "topic.txt")
    git("commit", "-m", "advance topic")
    topic_next = git("rev-parse", "HEAD")
    git("switch", "main")
    write("main.txt", "main next\n")
    git("add", "--", "main.txt")
    git("commit", "-m", "advance main")
    main_before = git("rev-parse", "HEAD")
    git("merge", "--no-edit", "topic")
    parents = git("rev-list", "--parents", "-n", "1", "HEAD").split()[1:]
    assert parents == [main_before, topic_next]
    assert git("show", "HEAD:main.txt") == "main next"
    assert git("show", "HEAD:topic.txt") == "topic next"
    print("fast-forward created no commit; true merge has two parents")
```

实验通过父列表而不是图形界面的外观检查结构，避免把显示布局当成提交关系。第二次合并中的不同文件没有文本冲突，只说明本例的结构变化可自动组合。若这两个文件在运行时彼此依赖，还需要额外集成测试。对象图断言与行为断言回答的是不同问题。

## 7. 实验二：读取冲突三个阶段并构造解决方案

本实验先让祖先配置使用红色，两侧分别改成蓝色与绿色，故意制造同一位置冲突。合并失败在这里是预期观察，因此不会使用要求成功退出的方式吞掉结果。我们检查未合并阶段的实际内容，再写入包含明确决策的最终值，暂存并完成合并。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_conflict_stages_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def run(*args, check=True):
        return subprocess.run(["git", *args], cwd=repo, env=env, text=True,
                              encoding="utf-8", capture_output=True, check=check)
    def git(*args):
        return run(*args).stdout.strip()
    def set_value(value):
        (repo / "config.txt").write_text(f"color={value}\n", encoding="utf-8")
    git("init", "-b", "main")
    for key, value in [("user.name", "Example"),
                       ("user.email", "example@example.invalid"),
                       ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
        git("config", key, value)
    set_value("red")
    git("add", "--", "config.txt")
    git("commit", "-m", "base red")
    git("switch", "-c", "topic")
    set_value("green")
    git("add", "--", "config.txt")
    git("commit", "-m", "topic green")
    git("switch", "main")
    set_value("blue")
    git("add", "--", "config.txt")
    git("commit", "-m", "main blue")
    result = run("merge", "--no-edit", "topic", check=False)
    assert result.returncode != 0
    assert git("show", ":1:config.txt") == "color=red"
    assert git("show", ":2:config.txt") == "color=blue"
    assert git("show", ":3:config.txt") == "color=green"
    assert git("ls-files", "--unmerged")
    set_value("blue-green")
    git("add", "--", "config.txt")
    assert not git("ls-files", "--unmerged")
    git("commit", "-m", "combine palette with explicit decision")
    assert git("show", "HEAD:config.txt") == "color=blue-green"
    assert len(git("rev-list", "--parents", "-n", "1", "HEAD").split()) == 3
    print("base/ours/theirs verified; resolution recorded as merge")
```

这里的蓝绿色只是课堂上预先规定的组合结果，不是通用配置合并算法。真实场景可能要求保留蓝色、保留绿色、引入选择参数或重新设计接口。实验要验证的是索引阶段和解决流程，而不是证明把两份字符串拼起来就总能解决冲突。

## 8. 实验三：自动合并成功但接口已经破坏

下面构造两份互不重叠的文本变化。主分支把生产者输出字段改成新名；实验分支新增消费者并继续读取旧名。合并能够成功，索引也没有冲突，但把生产者输出传给消费者会产生缺失字段错误。随后我们显式修复接口，并核对手工可算的输出。这里直接读取提交后的工作区文件，目的是验证组合行为而不是模拟完整训练框架。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_semantic_conflict_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(*args):
        return subprocess.run(["git", *args], cwd=repo, env=env, text=True,
                              encoding="utf-8", capture_output=True,
                              check=True).stdout.strip()
    def write(name, value):
        (repo / name).write_text(value, encoding="utf-8")
    git("init", "-b", "main")
    for key, value in [("user.name", "Example"),
                       ("user.email", "example@example.invalid"),
                       ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
        git("config", key, value)
    write("producer.py", "def make_row():\n    return {'price': 3}\n")
    git("add", "--", "producer.py")
    git("commit", "-m", "base field protocol")
    git("switch", "-c", "consumer")
    write("consumer.py", "def double(row):\n    return 2 * row['price']\n")
    git("add", "--", "consumer.py")
    git("commit", "-m", "add consumer of original protocol")
    git("switch", "main")
    write("producer.py", "def make_row():\n    return {'amount': 3}\n")
    git("add", "--", "producer.py")
    git("commit", "-m", "rename producer field")
    git("merge", "--no-edit", "consumer")
    assert not git("ls-files", "--unmerged")
    producer, consumer = {}, {}
    exec((repo / "producer.py").read_text(encoding="utf-8"), producer)
    exec((repo / "consumer.py").read_text(encoding="utf-8"), consumer)
    try:
        consumer["double"](producer["make_row"]())
    except KeyError as error:
        assert error.args == ("price",)
    else:
        raise AssertionError("semantic mismatch was not detected")
    write("consumer.py", "def double(row):\n    return 2 * row['amount']\n")
    fixed = {}
    exec((repo / "consumer.py").read_text(encoding="utf-8"), fixed)
    assert fixed["double"](producer["make_row"]()) == 6
    git("add", "--", "consumer.py")
    git("commit", "-m", "align consumer with merged field protocol")
    print("clean text merge failed integration; explicit repair returns 6")
```

实验中的执行字符串完全来自本例刚写入的固定教学内容，不是在建议执行任意来源的仓库文件。真实审查中，运行陌生项目代码本身具有权限和依赖边界，需要使用合适环境。本例不读取用户目录、不下载依赖，也不会启动训练。它仅把“文本整合成功不保证接口契约成立”变成可重复观察。

如果你希望把修复直接包含在合并提交，可以在完成合并前安排检查并编辑最终树；但要注意快进情形的行为，以及相关选项是否真正阻止提交创建。不要把“暂不提交”理解成一定会阻止引用快进。为了避免流程误判，应在独立仓库中验证所选命令的具体语义，再纳入项目规范。

## 9. 实验四：变基改变身份并重新建立基线

本实验让实验分支与主线分别新增不同文件，因此重放不需要人工解决文本冲突。我们验证变基后实验提交的父已经变为新主线，提交身份改变，而实验文件内容保持。这不证明任意变基都保持最终内容，只说明在本例的独立变化条件下，预期关系成立。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_rebase_identity_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(*args):
        return subprocess.run(["git", *args], cwd=repo, env=env, text=True,
                              encoding="utf-8", capture_output=True,
                              check=True).stdout.strip()
    def add_commit(name, value, message):
        (repo / name).write_text(value, encoding="utf-8")
        git("add", "--", name)
        git("commit", "-m", message)
    git("init", "-b", "main")
    for key, value in [("user.name", "Example"),
                       ("user.email", "example@example.invalid"),
                       ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
        git("config", key, value)
    add_commit("base.txt", "base\n", "base")
    git("switch", "-c", "experiment")
    add_commit("model.txt", "model v1\n", "experiment model")
    old_tip = git("rev-parse", "HEAD")
    old_model = git("rev-parse", "HEAD:model.txt")
    git("branch", "before-rebase")
    git("switch", "main")
    add_commit("protocol.txt", "protocol v2\n", "advance protocol")
    new_base = git("rev-parse", "HEAD")
    git("switch", "experiment")
    git("rebase", "main")
    assert git("rev-parse", "HEAD") != old_tip
    assert git("rev-parse", "HEAD^") == new_base
    assert git("rev-parse", "HEAD:model.txt") == old_model
    assert git("show", "HEAD:protocol.txt") == "protocol v2"
    assert git("rev-parse", "before-rebase") == old_tip
    print("new parent and commit identity verified; model blob preserved")
```

保留旧分支引用是为了让实验明确区分旧对象与新对象，也说明变基不会就地编辑旧提交。真实项目是否保留这样的引用取决于保留需求，但对正在运行的实验，旧提交身份与结果映射不应被随意抹去。完成新基线验证后，可以另外记录新版本结果，而不是篡改旧运行的事实。

## 10. 远程同步与本地整合的层次

远程仓库是另一个对象与引用集合，远程名称是本地配置中的别名。获取远程历史通常会下载缺少的对象并更新相应远程跟踪引用，不会自动把当前工作区替换为远程分支内容。远程跟踪引用是本地对远程状态的最近观察，若远程又发生变化，它可能暂时落后，不能当成随时实时同步的共享变量。

拉取通常包含获取与后续整合，而整合方式受配置和参数影响，可以是合并或变基等流程。因此在理解阶段，把获取和整合分开更容易观察每个动作改变什么。先获取，再检查当前分支与目标引用的祖先关系，最后选择符合约定的整合方式，比在未知状态下反复拉取更容易解释。

推送涉及向远程传输对象并请求更新引用。远程可能依据祖先关系、权限和服务器规则拒绝更新。被拒绝不一定是网络故障，也可能是远程已经有你本地未整合的提交。正确响应首先是理解差异和协作状态，不是立即强制覆盖。第四章会详细讨论共享引用、租约与实验分支规范。

本章实验不需要远程。这样能够把提交图和整合机制从网络、身份认证与服务端策略中分离出来。等本地图关系清楚后，再加入两个独立克隆和一个本地裸仓库模拟协作，可以更精确地观察远程跟踪引用与实际远程引用之间的时序差异。

<a id="git-2-detail-18"></a>

### 10.1 分支隔离代码，不隔离全部运行副作用

两个实验分支分别配置不同模型，却把权重输出到同一个绝对路径，后运行的实验可能覆盖先前结果。即使两条代码历史完全独立，外部输出仍发生竞争。分支不会为数据库、缓存、进程、对象存储或随机状态自动建立命名空间。因此实验隔离必须扩展到运行标识和产物路径。

同样，切换分支后残留的未跟踪缓存可能影响下一次运行。某些缓存有效性只依赖文件名而不依赖内容摘要，导致旧预处理结果被误用。应让缓存键覆盖影响结果的输入与处理版本，必要时在验证流程中使用干净缓存，并明确记录是否允许缓存复用。版本控制能保存缓存规则，却不会自动保证规则设计正确。

并行工作树也共享某些配置和对象，但工作区不同。若项目把所有输出都写回仓库外同一个目录，使用工作树仍然不能解决覆盖问题。应给每次运行独立身份，并在结果清单中连接代码状态、输入与输出摘要。代码隔离只是运行隔离的一个组成部分。

## 11. 版本控制与实验管理如何互补

版本控制回答代码如何变化、变化之间有什么历史关系；实验管理回答哪次运行使用了什么条件、产生了什么观测。一次提交可能对应多次不同种子的运行，一次运行也可能使用某个提交再加未提交补丁。两者不是简单的一对一表。合理的数据模型需要分别表示提交、配置、数据、运行和产物，再用明确关系连接。

一个实验分支可以围绕单一假设组织，例如改变归一化方式，保持数据、训练预算与评价协议固定。若同时换模型、数据、优化器和评估口径，即使成绩提高，也无法可靠归因于某一项变化。Git 分支允许保留不同代码版本，但控制变量与消融设计仍需研究者负责。提交图不会自动生成科学因果解释。

合并后也不能直接继承原分支成绩。原分支在祖先环境下运行，合并结果可能包含新的数据协议、默认值或依赖。若声称合并后保持指标，需要实际验证相应树与条件，或者给出足够严格的等价论证。即使文件改动不重叠，也不能仅凭文本独立就认定计算独立。

对未提交状态，有两种相对清晰的记录方式：在运行前形成可定位提交；或者保存完整补丁、未跟踪必要文件及相关输入清单，并标明基线。只记录当前提交加一个“脏工作区”布尔值不足以重建实际代码，因为这个标志没有包含变化内容。为了长期可恢复，通常更偏好明确对象和不可变产物，而不是依赖临时状态。

<a id="git-2-detail-20"></a>

### 11.1 结果比较需要先建立可比性

两次实验的指标能否直接比较，取决于任务定义、数据划分、样本权重、评价单位和训练预算是否一致。假设一侧合并后改变有效样本过滤，平均损失下降可能来自删除困难样本；若另一侧改变分词，逐词元困惑度的单位也改变。代码版本记录只是让这种变化可追踪，不会让数字自动可比。

可比性检查应先于显著性讨论。先确认评价对象相同，再检查随机性与统计不确定性，最后讨论差异大小与实际意义。若评价协议必须改变，应保留旧协议结果或在统一协议下重评模型，避免把两个定义不同的数放在同一列里排名。合并说明也应突出这类口径变化。

研究复现还要区别精确重跑、统计复现与结论复核。某些计算在固定环境下可逐位复现，另一些只能要求分布或结论在合理范围内一致。实验记录应说明目标层次及验收标准。分支与提交能够固定代码状态，但不能把统计过程强制变成确定性过程。

<a id="git-2-detail-21"></a>

## 12. 合并后的验证应覆盖哪些关系

第一层是仓库状态：是否还有未合并索引条目，是否遗留冲突标记，最终树是否包含预期路径。第二层是构建与接口：导入、类型、配置解析、数据模式以及调用关系是否一致。第三层是行为：关键边界和反例是否保持。第四层是研究协议：训练预算、数据版本、指标口径和产物映射是否符合比较目的。

这些层次不要求每次合并都运行同样昂贵的全套训练。应根据变化范围选择足够验证。只修改说明可以重点检查链接、公式和示例；修改标签映射则需要跨数据与评价的闭环检查；修改核心优化更新应验证数学例子、数值尺度和代表性训练。检查范围应与承诺范围匹配，而不是追求无差别地运行所有命令。

当合并包含冲突解决时，最终内容可能不是两侧任何一个已有版本。已有测试结果无法完整覆盖这个新树，因此冲突解决应当被视为需要审查的新实现。可以查看合并结果相对各父的差异，解释额外取舍，运行针对这些取舍的测试。把冲突解决看成纯机械操作，会低估这里引入新缺陷的可能。

对于资料仓库，语义验证也有对应形式。一侧改符号定义，另一侧增加使用旧符号的推导，即使文本无冲突，最终章节也可能自相矛盾。应检查定义先后、单位、假设和交叉引用，确保新读者按顺序阅读能建立一致模型。工程中的接口契约，在教材里对应概念与记号契约。

<a id="git-2-detail-22"></a>

### 12.1 合并完成的证据应该怎样表达

一种清楚的交付说明可以同时给出历史与行为证据：从哪个基线整合哪个提交，采用哪种方式，是否发生人工冲突解决，最终提交身份是什么，执行了哪些验证及观察到什么结果。无需罗列无关内部命令，但应让读者知道被验证对象和验证条件。

例如可以写“在固定小型数据集上，新的生产者与消费者闭环输出符合手算结果；未执行完整训练”。这支持接口组合的窄结论。若要声明完整训练结果保持，则必须补上运行身份、配置与指标。把结论限定到证据实际覆盖的层次，能让后续维护者更放心地复用验证。

## 13. 练习与详细解析

<a id="git-2-detail-24"></a>

### 13.1 练习一：快进到底创建了什么

主分支指向甲，实验分支为甲之后的乙、丙，主分支没有其他提交。采用只允许快进的整合后，主分支指向哪里，是否新增提交？答案是指向丙，通常不新增提交。因为甲已经是丙的祖先，引用可以沿既有历史前进，乙和丙的对象身份保持。

若希望保留一次显式汇合事件，可以采用禁止快进的方式创建合并节点，但这是历史表达选择，不是修复数据丢失。解题时应先画祖先关系，再讨论选项，不要根据“执行了合并命令”就断定一定出现双父提交。

<a id="git-2-detail-25"></a>

### 13.2 练习二：谁更新就保留谁是否合理

共同祖先的阈值为甲，一侧改成乙，另一侧改成丙，后者时间更晚。是否应该直接保留丙？不能只依据时间判断。需要理解两侧目的、适用条件和组合后的协议，时间戳也不提供可靠的语义优先级。可能最终保留乙、保留丙或改为参数化选择。

正确答案应给出决策依据与验证案例。例如乙修复异常输入，丙适配另一类数据，那么需要明确两类输入是否都属于目标范围。冲突处理的任务是满足最终承诺，而不是从两个候选文本里按日期选一个。

<a id="git-2-detail-26"></a>

### 13.3 练习三：阶段二是否永远是我的代码

在普通合并中阶段二通常对应当前侧，但在变基中，当前侧可能是新基线与已经重放的提交，正在重放的旧实验变化可能出现在另一侧。因此“阶段二就是我原先写的代码”不是普遍规则。应读取当前操作、提交与实际阶段内容确认。

这道题的要点是区分工具角色与作者归属。一个角色名称的意义由操作上下文决定，不由日常的“我的分支”决定。自动化中更应避免用含糊归属驱动全局覆盖策略，因为错误选择可能静默丢掉整组必要变化。

<a id="git-2-detail-27"></a>

### 13.4 练习四：没有冲突为什么仍然失败

一侧改变数据字段，另一侧新增使用旧字段的函数，合并无冲突却运行失败。文本修改互不重叠，工具可以组合；运行时接口不一致，程序无法满足契约。应该增加生产者到消费者的最小闭环测试，并对字段迁移形成一致方案。

仅为消费者手写一份旧模式输入可能让测试继续通过，所以测试必须覆盖真实接口。修复后还应检查文档、配置与评价代码是否同样使用新协议。语义冲突的调查范围由依赖关系决定，而不是由冲突标记所在行决定。

<a id="git-2-detail-28"></a>

### 13.5 练习五：合并提交的两个父能交换吗

对于一条已经存在的合并提交，其父顺序是对象内容的一部分，不能在不改变身份的情况下随意交换。通常第一父对应整合时当前分支的历史，这影响沿第一父观察主线的结果。交换后即使根树相同，提交对象仍不同。

因此讨论“同一个合并”时要说明比较层次：相同最终树、相同父集合、相同有序父列表或完全相同提交对象，都是不同强度的断言。精确表述能够减少历史审计中的误会。

<a id="git-2-detail-29"></a>

### 13.6 练习六：压缩整合是否保留祖先关系

把实验分支的结果压缩成主线上的一个普通提交，是否意味着实验分支原有提交已经成为主线祖先？通常不意味着。最终内容可以包含其效果，但提交图没有通过多父关系连接原分支。因此后续整合同一长期分支时，需要理解原共同祖先与重复变化处理。

这不是压缩整合必然错误，而是它表达了不同历史。对短期、用后删除的主题分支，压缩可能清楚；对长期反复汇合的分支，应更仔细设计流程。选择依据应包括后续协作方式，而不只看当前历史是否整齐。

<a id="git-2-detail-30"></a>

### 13.7 练习七：变基前后的实验结果可以改标签吗

实验在旧提交上运行，后来把分支变基到新主线。能否直接把旧结果的代码字段改为新提交？不能。结果应忠实对应实际运行状态。即使模型文件没有变化，新主线可能改变数据、依赖或评价协议。应保留旧运行记录，并追加新旧树关系与必要复核。

如果能够证明与实验相关的全部输入和计算等价，可以明确记录这种等价论证，但仍不要改写发生事实。研究记录的价值在于让别人追踪过程，不能为了历史整洁把未运行的新状态冒充已运行状态。

<a id="git-2-detail-31"></a>

### 13.8 练习八：分支为什么没有保护输出文件

两个分支把模型写到同一个仓库外路径，后一次覆盖前一次。分支只隔离代码引用，不会自动隔离外部文件系统副作用。应为运行分配独立身份与产物目录，记录产物摘要，并避免把可变的“最新模型”路径当成唯一证据。

即使使用独立工作树，只要输出路径仍然相同，问题依然存在。解决方案必须作用于真正共享的资源，而不是只增加代码分支。类似原则也适用于数据库表、缓存键和远程实验任务名称。

<a id="git-2-detail-32"></a>

### 13.9 练习九：获取是否会替换工作区

在常见配置下，获取远程历史会更新对象与远程跟踪引用，但不会直接把当前工作区变成远程分支。若随后拉取发生了文件变化，是因为拉取还执行了整合步骤。应把网络观察与本地整合分开分析，检查具体配置与参数。

还要注意远程跟踪引用只是最近一次观察，不保证实时反映远程。若另一个人之后推送，本地引用在下次获取前可能落后。协作决策应考虑这种时序，而不是把本地显示当成远程永恒事实。

<a id="git-2-detail-33"></a>

### 13.10 练习十：同样最终树能否得到不同历史

一条路径通过普通合并形成双父节点，另一条通过变基形成线性链，最终树是否可能相同？可能。树记录内容，提交图记录来源关系。若内容等价，可以比较树身份；若要证明分支祖先关系，应检查父链接，不能只看文件一致。

这种区别也决定后续工具行为：审查范围、二分候选、主线日志和撤销合并时的语义都可能不同。最终树一致不表示所有操作效果一致，因此工作流讨论应声明关注的是内容还是历史。

<a id="git-2-detail-34"></a>

### 13.11 练习十一：冲突标记消失是否足够

手动删除所有冲突分隔标记，并把文件暂存，是否完成正确解决？只完成了工具层确认，语义仍需验证。你可能误删边界检查、重复保留互斥分支或让配置与接口不一致。应先写双方必须保持的条件，再用最终实现和测试逐项核对。

此外，某些冲突涉及删除、重命名或二进制文件，本来就不一定表现为普通文本标记。只搜索标记无法发现全部未解决状态，应同时检查索引与仓库状态。工具状态和业务行为都需要证据。

<a id="git-2-detail-35"></a>

### 13.12 练习十二：为什么同一损失值不保证同一口径

一侧把平均损失改为总损失，另一侧改变有效样本过滤，两次输出恰好数值相同，能否认为行为等价？不能。分母、样本集合和单位改变后，数字含义已经不同。需要使用手算样例核对每个计数，并在统一协议下比较。

这类错误比接口报错更隐蔽，因为程序可能正常结束。合并验证应包含指标定义和聚合单位，而不仅是检查输出为有限数。研究判断必须建立在可比的测量对象上。

<a id="git-2-detail-36"></a>

### 13.13 练习十三：共享分支变基为什么影响别人

同伴已经基于旧提交继续开发，你把共享分支变基后替换其历史。即使最终文件接近，同伴的父链仍引用旧对象，新旧链可能表现为分叉或重复变化，需要重新协调。问题来自依赖的提交身份与祖先关系改变，不只是界面显示变乱。

合理做法是遵循共享约定，避免随意改写别人依赖的历史。若确实需要重写，应有明确协调与恢复计划，并保留必要旧引用。不能把个人偏好的线性历史视为压倒协作事实的理由。

<a id="git-2-detail-37"></a>

### 13.14 练习十四：多个最佳共同祖先意味着什么

在交叉合并历史中，两个分支可能具有多个最佳共同祖先，是否说明仓库坏了？不说明。它是有向无环提交图允许的结构。具体合并策略可以处理这种情况，可能构造虚拟基线。调查时应查看完整图与实际策略，而不是强行指定一张简单分叉图作为事实。

本章基础实验采用唯一基线，是一种教学简化，不是所有仓库的定理。辨别简化条件与普遍性质，是进阶学习的重要能力。遇到超出简化模型的现象，应扩展模型而不是先认定工具错误。

<a id="sec-7-1"></a>

<a id="git-2-detail-38"></a>

### 13.15 综合题：怎样验收一次数据接口合并

一侧修改列名与单位，另一侧新增统计特征和评估图，工具自动合并成功。请给出验收顺序。首先固定最终代码树与数据快照，明确列名、单位和缺失值协议；再用可手算的一两条记录连接加载、特征、模型与指标；随后检查图中标签、单位和样本计数；最后在代表性数据上评估性能与资源行为。

如果结果与旧版本不同，应区分预期口径变化与意外缺陷。需要在统一协议下重评，才能比较模型能力。交付说明应记录最终提交、关键决策和实际执行的验证，不应把“自动合并无冲突”作为唯一证据。这个方案把版本身份、接口契约和研究可比性连接成可复核链条。

<a id="git-2-detail-39"></a>

## 14. 进阶研究：合并正确性为何难以完全自动化

文本合并面对的是有限可观察表示，程序语义却依赖运行输入与环境。即使两个修改分别通过各自测试，组合后也可能破坏没有被测试覆盖的性质。一个普遍自动判断任意程序合并是否保持全部预期行为的工具，会遇到程序分析本身的深刻限制。因此现实系统通常采用近似分析、类型约束、契约测试和人工审查组合降低风险。

这不意味着研究只能依赖直觉。可以把范围限制到明确的领域：配置模式兼容、数据库迁移依赖、函数签名变化或数据流契约，针对这些结构建立自动检查。检查越具体，越容易说明其充分条件与盲区。例如字段兼容检查可以发现旧名读取，却不能自动判断把厘米误写成米的业务含义，除非单位本身被编码进类型或模式。

你可以设计一个小型研究实验：准备若干对分支，其中包含文本冲突、跨文件接口冲突和纯指标口径冲突；比较只检查标记、加入单元测试、加入闭环测试三种策略的检出率与成本。应报告样本构造方式与不能代表真实仓库的局限，避免把课堂样本的高检出率宣传成普遍保证。

另一个方向是维护可测试历史。若每次提交都能在固定最小环境中运行关键测试，二分定位和重放验证会更可靠。可是为保持每个提交可运行而引入过多兼容层，也可能提高维护成本。可以从审查时间、失败定位时间和接口迁移成本三个维度衡量，而不是把“所有提交都完美”当成没有代价的口号。

<a id="git-2-detail-40"></a>

### 14.1 拣选提交为何不等于合并分支

拣选通常把某个提交相对其父的变化应用到当前历史上，再创建新的提交。它适合把一个独立修复带到另一条维护线，但通常不会建立原分支整体已经合并的祖先关系。若修复依赖前面的接口迁移，只拣选最后一条可能产生能应用文本却不能运行的结果。选择范围前需要阅读依赖，而不只是找到标题最像修复的提交。

当目标是一个合并提交时，还要明确相对哪一个父来解释变化。因为合并提交具有多个父，不指定基准就无法唯一回答“这一条提交引入了什么补丁”。这与撤销合并时需要理解主线父的原因相通。初学者不应把所有提交都想成具有唯一上一个版本的线性节点。

重复拣选、后来再合并原分支，也会带来历史与内容之间的复杂关系。某个补丁的效果可能已经存在，但提交祖先关系尚未连接；工具可能检测到等价变化，也可能因上下文变化产生冲突。应该通过最终树与测试核对结果，而不是根据提交标题推断一定没有重复。对长期维护线，可以建立明确的修复来源记录，帮助后续整合者理解。

<a id="git-2-detail-41"></a>

### 14.2 复用冲突解决结果仍需重新验证

Git 可以记录某些冲突的解决方式，并在相似冲突再次出现时复用。这对于反复重放实验分支很有帮助，但复用的是过去某种冲突表示与解决内容之间的关系，不是对当前业务语义的新证明。周边接口、数据协议或测试目的变化后，旧解决方式可能不再正确。

因此启用自动复用时，应清楚区分“工作区已经得到候选解决”与“索引已经确认解决”，并核对相关配置是否自动暂存。一个曾经正确的决定，不会因为被工具记住就永久正确。仍应审查候选差异并运行当前场景的关键测试。复用减少重复劳动，不能取代本次整合的责任。

可以构造一个研究例子来理解边界：第一次冲突中把默认阈值选择为乙，是因为当时数据单位固定；第二次文本相似，但主线已经改变单位，直接沿用乙可能错一个数量级。文本相似并不意味着条件相同。若单位约束显式进入配置模式或测试，自动复用后的错误更容易被发现。

<a id="git-2-detail-42"></a>

### 14.3 合并结果的测试不具有简单传递性

设分支甲与主线分别通过测试，能否推出它们的合并也通过？不能。测试结果只对各自被测状态成立，组合产生一个新状态。即使双方没有修改相同行，也可能共享一个隐含资源或契约。形式上，性质对两个单独状态成立，不蕴含对某种组合运算的结果成立，除非已经证明该性质在这个运算下闭合。

在受限条件下可以建立更强结论。例如两个组件完全不共享状态，接口契约保持，测试输入覆盖各自承诺，组合只做独立并列，那么某些局部性质可以组合推导。但现实工程中，“完全独立”本身需要证据，不能由不同文件路径推出。数据加载与指标脚本虽然分处两端，仍然通过样本身份和标签定义相连。

测试还需要注意执行时刻。主线在你完成本地验证后继续前进，最终服务端整合得到的树可能不同于本地被测树。若流程只检查旧的实验分支而不检查实际整合结果，就可能把过期证据用于新状态。持续集成系统可以针对候选合并树运行测试，或者在基线变化后要求重新验证；具体实现不同，核心都是让证据对应最终交付对象。

同样，多个待合并变化单独通过候选测试，也不保证按另一顺序整合后仍然通过。接口迁移、资源分配和默认配置之间可能存在顺序依赖。一个清楚的合并队列应明确测试基线与更新策略，而不是把所有绿色标记视为独立永久证书。绿色状态只属于某个代码对象和某组条件，不是可以脱离对象随意转移的属性。

对于研究协作，可以把这一点扩展到结果表。每行指标都应关联实际运行的代码与输入身份；若最终合并改变相关条件，就新增验证行或注明尚未复评。这样即使历史继续发展，旧结论仍然有准确位置，新结论也有独立证据。良好的记录允许不确定性被看见，而不是靠整理历史把它遮住。

由此可以形成一个实用审查方法：先列共享契约，再检查每侧是否改变契约，最后为交叉影响安排验证。对于纯文档变化，共享契约可能是符号和链接；对于训练系统，是形状、单位、随机状态和产物路径。这样选择检查比无差别重跑所有测试更有针对性，也比仅运行双方原有测试更能覆盖新组合。
