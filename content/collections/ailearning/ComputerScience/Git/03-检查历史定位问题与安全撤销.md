## 1. 从变化范围开始查，而不是从命令开始试

发现训练分数突然下降时，最先需要确认的不是用哪条撤销命令，而是两次测量是否具有同一含义。数据划分、预处理、指标分母、随机种子和依赖版本都可能变化。只有建立一个可重复、可比较的症状，代码历史才成为有力的定位工具。若测量对象本身改变，历史二分可能只是在追踪评价协议差异。

检查可以从四个状态开始：当前工作区、当前索引、最近提交、已知参考提交。工作区差异回答未暂存内容；暂存差异回答待提交内容；两个提交之间的差异回答已记录历史中的变化。不要把这三种比较混成一个“看看改了什么”。尤其在脏工作区运行实验时，最近提交标识不完全代表实际运行代码。

随后缩小范围：问题是输入解析、模型前向、梯度更新、指标聚合还是结果展示？一个完整训练失败可能由非常小的局部条件触发。能够把它缩成两条样本和一个断言，就能显著降低重复判定成本，也更容易区分代码回归与随机噪声。定位工具的效率很大程度取决于判定器质量。

阅读历史时应形成可检验假设。例如“样本权重归一化改变导致有效学习率变化”比“最近几次提交可能有问题”更具体。寻找相关函数、配置与测试，比较变化前后行为，并用最小反例区分假设。时间接近只能提供线索，不能自动建立因果关系。

<a id="git-3-detail-2"></a>

### 1.1 先区分撤销对象，再选择动作

如果错误只存在工作区，你可能只想恢复某个文件，同时保留其他实验；如果错误已经暂存，你可能只想把它撤出下一次提交而保留编辑；如果错误已经提交并共享，你可能需要新增反向变化；如果只是本地未共享历史，也可以考虑重新组织提交。四种目标涉及不同状态，不应由一个笼统的“撤销”决定。

在执行之前，写出保留集合和改变集合。例如“保留工作区全部编辑，只让索引回到最近提交”就是撤暂存目标；“保留分支引用与其他路径，只把某文件工作区恢复为索引版本”是另一目标。这个表达比记忆某条命令看起来安全更可靠，因为同一命令的选项会改变读写范围。

重要操作前还应确认仓库根目录与当前分支。一个命令在错误目录中执行，可能影响完全不同的项目。自动化应固定工作目录并使用结构化参数，不要依靠前一条终端命令留下的隐含位置。所有本章写入实验都在独立临时仓库完成，不对用户现有历史操作。

<a id="visual-03-concept"></a>

### 图解：反向提交保留原有历史

![反向提交保留原有历史](images/03-concept.svg)

**图解。** 在无其他改动的简单历史中，B 把 x 从 0 改为 1，撤销提交 R 再应用反向补丁把它改回 0。虽然 A 与 R 的文件内容相同，R 仍是新的提交，B 也仍在祖先链中。

反向提交不会假装 B 从未存在，而是在现有历史后增加一次明确的相反修改。这使共享历史保持可追踪，并允许审阅撤销本身。

图中是没有后续依赖的最小情形。复杂撤销可能冲突或影响其他变更；撤销合并还需选择主线，不能把内容恢复与祖先关系删除当成同一件事。

## 2. 历史查询工具分别提供什么证据

日志用于浏览提交与关系，查看提交用于读取某个对象及其变化，差异用于比较指定状态，逐行追踪用于找到当前行最近关联的历史变化。它们各自是观察接口，不是根因推断器。看到某行最后被一个提交修改，只说明当前归因算法把它关联到该变化，不说明该作者制造了当前故障。

一个常用查询顺序是先查看图和提交摘要，再阅读目标提交说明与完整相关差异，最后沿调用链检查上下文。只读标题容易漏掉范围；只读补丁容易误解设计目的；只读当前文件又看不到为什么形成这样的接口。三者结合，才能把变化放回当时条件中理解。

```bash
git status --short
git log --oneline --graph --decorate -12
git show --stat HEAD
git diff GOOD_COMMIT BAD_COMMIT -- path/to/file.py
git log --oneline -- path/to/file.py
git blame -- path/to/file.py
```

其中占位提交名与路径需要替换为实际对象；这组命令是读取历史，不会修复任何问题。用于脚本时，应选择稳定输出格式和明确分隔，避免解析面向人类的装饰文本。若需要证明某个版本具体包含哪些字节，直接读取目标树中的路径，比凭界面上绿色或红色行数推断更精确。

<a id="git-3-detail-4"></a>

### 2.1 两点差异与祖先比较的不同问题

直接比较两个提交的树，回答它们最终状态有什么不同；从共同祖先比较一侧，回答这一侧相对分叉起点引入了什么变化。这两个问题都合理，但不能互换。一个审查界面常展示主题分支相对共同祖先的变化，而你在终端直接比较两端树时，可能同时看到主线新增内容的反向差异。

修订范围语法在日志集合与差异命令中还有各自解释，应阅读对应命令语义，而不是把相同标点当成统一的集合公式。最稳妥的学习方式是先画包含四五个节点的小图，手工写出希望比较的两棵树或希望枚举的提交集合，再核对命令输出。明确问题后，语法才有确定用途。

发生合并时，查看单个合并提交的差异也需要声明基准父。相对第一父的差异与相对第二父的差异不同，组合差异显示又有自己的筛选规则。若怀疑冲突解决引入缺陷，不应只看默认视图就认定没有额外变化。需要结合各父和最终树检查实际决策。

<a id="git-3-detail-5"></a>

### 2.2 搜索变化与逐行归因的边界

历史搜索可以寻找某个字符串数量变化，或寻找补丁文本匹配某种模式的提交。这比逐个打开提交快，但搜索条件本身会漏检：代码可能重命名、等价改写，或者缺陷来自配置而非目标字符串。一次没搜到只说明未发现满足该条件的变化，不证明历史中没有相关原因。

逐行追踪也会受格式化、移动和复制检测选项影响。某次统一格式化可能成为大量行的最近关联提交，而真实逻辑更早出现。可以沿该提交的父继续调查，或在有明确依据时使用忽略指定修订的机制改善阅读。无论显示如何调整，都应回到实际版本与行为验证，避免把归因界面当成人员责任判决。

## 3. restore：恢复指定内容而不移动历史

恢复命令首先需要两个明确问题：从哪里读取，写到哪里。常见默认工作区恢复从索引读取；指定暂存目标时，默认来源通常是最近提交。可以显式指定来源树，也可以同时选择工作区与索引目标。阅读命令时，始终把来源、目标和路径范围分开，否则很容易把“撤暂存保留编辑”误变成“覆盖工作区编辑”。

仅恢复索引意味着改变下一次提交计划，工作区内容可以保持。仅恢复工作区意味着把当前文件替换为指定来源，可能丢掉尚未记录的编辑。恢复到旧提交中的一个文件，并不会把整个项目、依赖环境或实验状态回到那个时期。它创建的是“当前其他文件加旧版目标文件”的新组合，需要检查兼容性。

来源树没有某路径时，恢复行为可能包含删除该路径以匹配来源，因此不能把恢复想成只复制存在文件的操作。路径范围越宽，影响越大。处理单个配置错误时，应先限定到该配置并审查差异，而不是无差别恢复整个工作区。工具能忠实实现范围，范围是否符合意图由操作者决定。

<a id="git-3-detail-7"></a>

### 3.1 恢复文件和恢复实验不是一回事

假设旧模型代码使用旧标签编号，当前评估代码已经迁移到新编号。只恢复旧模型文件可能让程序运行，却使输出解释错误。所谓回到旧实验，至少涉及相关代码、配置、数据与环境；只恢复一个路径通常只能承诺该路径内容与旧版本一致。不要把窄操作包装成广泛复现结论。

这也解释了为什么恢复旧文件之后仍需要提交：恢复命令改变工作区或索引，但不会自动新增一条表达你选择的历史记录。后续提交可以把“重新采用旧实现并兼容当前接口”保存为新的状态。这样历史中保留了撤回原因和当前适配，而不是假装中间变化从未发生。

<a id="git-3-detail-8"></a>

## 4. reset：移动引用与重设状态的不同形式

重设命令有不同形式。针对提交并使用不同模式时，可以移动当前分支引用，并选择是否同步索引和工作区；针对路径的形式主要调整索引，不能把它理解为移动整个分支。学习时必须先区分命令形式，再讨论模式。把所有重设都称为“回退一个版本”会掩盖最重要的状态差别。

常见软重设主要移动当前历史位置，保留索引与工作区，因此原先提交内容相对新位置表现为已暂存变化；常见混合重设还重设索引，工作区保留，因此变化通常表现为未暂存；硬重设进一步更新工作区中的已跟踪内容，并可能删除阻碍写入的未跟踪路径。这些是范围性质，不是安全等级标签。

尤其不要把硬重设误解为“只清理已跟踪文件，绝不影响未跟踪内容”。当未跟踪路径阻碍需要写入的已跟踪路径时，可能受到删除影响。反过来，它也不是清理所有未跟踪文件的通用命令。实际效果由目标树、当前路径结构和模式决定，不能用一句过度简化规则替代状态检查。

共享历史中移动本地分支并不自动移动远程；若随后尝试用非快进方式替换共享引用，又会涉及协作者依赖。局部修复提交组织与修改已发布历史具有不同协作后果。第三章解释机制，第四章讨论共享规范，二者应结合理解。

<a id="git-3-detail-9"></a>

### 4.1 用状态不变量推导三种模式

设当前提交为乙，其父为甲，索引和工作区都等于乙。软重设到甲后，分支指向甲，索引与工作区仍等于乙，因此乙相对甲的变化已暂存；混合重设到甲后，分支和索引为甲，工作区仍为乙，因此变化未暂存；硬重设到甲后，三者通常都回到甲的相应内容，未提交的工作区差异可能被覆盖。

这里特意采用干净起始状态，便于推导。如果开始时索引和工作区各有不同内容，需要分别计算，不能直接把上述结论照搬。选择命令前画出起始状态与目标状态，逐项检查要保留什么，比凭一个熟悉命令试探可靠。若存在重要未记录编辑，应先以明确方式保存内容，而不是赌恢复机制总能找回。

<a id="visual-03-advanced"></a>

### 图解：三种 reset 模式影响不同状态层

![三种 reset 模式影响不同状态层](images/03-advanced.svg)

## 5. revert：在当前历史上新增反向变化

反向提交通常根据某个已有提交引入的变化，在当前状态上应用其逆向效果，并创建新的提交。原提交仍然存在，历史继续向前，因此适合需要保留共享事实与审查线索的场景。但反向变化不等于时间机器：它不会自动恢复后来依赖被撤接口的代码，也不会撤销外部数据库、已上传模型或实际训练成本。

如果原提交把函数名由甲改为乙，后续提交增加对乙的调用，那么撤销最初改名可能使后续调用失效。工具可能产生文本冲突，也可能无冲突但语义错误。处理时要明确目标是撤销某个行为、恢复旧接口还是同时迁移后续依赖，必要时采用新的修复实现，而不是机械追求字面逆补丁。

对多个提交的撤销还需要考虑顺序与依赖。撤销后引入内容，再撤销其前提，通常更容易理解，但不能认为所有变化都满足简单交换律。数据结构、迁移脚本与配置可能相互依赖。审查最终树与验证行为，才是判定恢复成功的标准。

<a id="git-3-detail-11"></a>

### 5.1 为什么反向提交保留了事实却不保证可运行

反向提交的优点是历史清楚记录“曾经引入，后来撤回”，并且共享分支继续前进。这有利于协作同步和事故解释。但这个历史性质不自动推出代码性质。若撤销破坏当前依赖，仍需补充适配；若原变化触发了外部副作用，仍需处理外部系统。

例如一次评估脚本错误已经发布了指标表，撤销脚本并不会让外部报告自动更正。需要重新评估、更新产物与说明。版本控制只管理其范围内的状态，研究记录和发布流程要负责传播更正。正确使用工具意味着承认其边界，而不是把所有恢复责任交给一个命令。

<a id="git-3-detail-12"></a>

### 5.2 撤销合并为什么需要主线语义

合并提交有多个父。要把它视为某种变化来撤销，必须说明相对哪个父保留主线。选择主线父后，反向变化针对合并结果相对该父的效果，而不是把整个提交图中的另一分支从历史删除。原有祖先关系仍然存在，这会影响之后再次合并同一历史时的判断。

因此撤销一次合并后，再合并同一分支并不必然重新引入原有全部内容，因为 Git 仍知道原提交曾经成为祖先。后续恢复需求可能涉及撤销那个反向提交，或者引入新的明确修复，但具体方案依赖历史与目标。重要场景应在独立副本中构造与验证，不能仅凭“再合一次应该就回来”的直觉操作。

这个例子凸显内容图与提交图的区别。反向提交改变内容，却保留祖先事实；历史重写则可能改变引用可达关系。它们可以在某一时刻产生相似文件树，却为后续协作留下不同语义。

#### 图解与实验：为何再次合并只带来新增部分？

![撤销合并后的祖先图与文件存在状态逐项对照](images/03-reverted-merge-ancestry.svg)

把上一节的结论拆成两个能独立检查的不变量：**当前树里有哪些文件，以及某个提交是否仍在祖先集合中**。图中 A 只建立基线；主题分支的 B 增加 `feature.txt`，主线的 C 增加 `main.txt`。从 C 合并 B 得到 M，父提交按顺序为 C、B，所以 `git revert -m 1 M` 选择的是“以第一父 C 为参照撤销 M 的净变化”。这里的数字一是父提交序号，不是分支名称，也不是删除一条分支。

在这个没有冲突的构造中，M 相对 C 只增加功能文件。因此反向提交 R 删去 `feature.txt`，保留 `main.txt`。但是提交边 C、B 到 M，以及 M 到 R 都还存在，B 仍是 R 的祖先。此时再次合并仍指向 B 的主题分支，Git 能确认该提交已经可达，不会为了恢复文件而自动再应用 B 的补丁。判断依据是历史，而不是看到当前文件缺失便猜测“以前没合过”。

**继续开发后，为什么只引入新文件？** 从 B 再提交 D，只新增 `helper.txt`，不修改旧功能文件。把 D 合入 R 时，共同祖先为 B。对功能文件而言，基线 B 有、主线 R 删除、主题 D 相对 B 没动；正常三方合并保留主线删除。对帮助文件而言，只有 D 新增，故它进入新合并 N。于是 N 有帮助文件，却仍没有原功能文件。这个例子刻意使用独立新增文件，排除文本冲突的干扰；如果 D 修改了已经在主线删除的文件，可能出现修改／删除冲突，不能照搬这里的无冲突结果。

| 需要验证的事实 | 对应的只读证据 |
| --- | --- |
| M 的父提交顺序 | `git rev-list --parents -n 1 M` |
| B 在 R 中仍可达 | `git merge-base --is-ancestor B R` 的成功状态 |
| 合并 R 与 D 所用的基线 | `git merge-base R D` 得到 B |
| 恢复后实际保留哪些内容 | 读取文件，检查工作区与树，而非只看提交标题 |

下面程序只在自己创建的临时仓库运行，不操作当前教材仓库，也不改全局 Git 配置。它验证父顺序、重复合并不改变 HEAD、增量合并结果，以及最后再撤销 R 的内容变化；本例还禁用签名并使用一个空钩子目录，避免外部配置使教学实验额外运行其他程序。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import subprocess

with TemporaryDirectory(prefix="merge_revert_model_") as root:
    root = Path(root)
    hooks = root / "empty_hooks"
    hooks.mkdir()

    def git(*args):
        result = subprocess.run(
            ["git", "-c", "core.autocrlf=false",
             "-c", "core.hooksPath=" + str(hooks),
             "-c", "commit.gpgSign=false",
             "-c", "user.name=Textbook Example",
             "-c", "user.email=textbook@example.invalid", *args],
            cwd=root, check=True, capture_output=True, text=True,
        )
        return result.stdout.strip()

    def commit_file(name, body, label):
        (root / name).write_bytes(body.encode("utf-8"))
        git("add", "--", name)
        git("commit", "-m", label)
        return git("rev-parse", "HEAD")

    git("init", "-b", "main")
    a = commit_file("base.txt", "base\n", "A")
    git("switch", "-c", "topic")
    b = commit_file("feature.txt", "feature-v1\n", "B")
    git("switch", "main")
    c = commit_file("main.txt", "main-only\n", "C")
    git("merge", "--no-ff", "--no-edit", "topic")
    m = git("rev-parse", "HEAD")
    assert git("rev-list", "--parents", "-n", "1", m).split()[1:] == [c, b]

    git("revert", "-m", "1", "--no-edit", m)
    r = git("rev-parse", "HEAD")
    assert not (root / "feature.txt").exists()
    assert (root / "main.txt").read_text() == "main-only\n"
    git("merge-base", "--is-ancestor", b, r)
    assert git("merge-base", r, b) == b
    git("merge", "--no-edit", "topic")
    assert git("rev-parse", "HEAD") == r

    git("switch", "topic")
    d = commit_file("helper.txt", "new-helper\n", "D")
    git("switch", "main")
    git("merge", "--no-ff", "--no-edit", "topic")
    n = git("rev-parse", "HEAD")
    assert git("merge-base", r, d) == b
    assert not (root / "feature.txt").exists()
    assert (root / "helper.txt").read_text() == "new-helper\n"

    # On this conflict-free history, undoing R restores B's file.
    git("revert", "--no-edit", r)
    q = git("rev-parse", "HEAD")
    assert (root / "feature.txt").read_text() == "feature-v1\n"
    assert (root / "helper.txt").read_text() == "new-helper\n"
    for ancestor in (a, b, c, m, r, d, n):
        git("merge-base", "--is-ancestor", ancestor, q)
    assert git("status", "--porcelain") == ""
print("merge parents, repeated merge, incremental merge, and revert-of-revert: passed")
```

**为什么 Q 能恢复，而 N 不能？** Q 反向应用 R 对内容的变化，本例等价于重新加回功能文件；它没有要求 Git 把 B 当成没合过。帮助文件在 R 的逆补丁范围之外，因此保留。到 Q 时，B、M、R、D、N 全部仍是祖先；从“删文件”到“加回文件”，改变的一直是树，不是抹去历史。

这种构造说明一条可行恢复路径，但不是对任意历史的固定处方。若主题分支是在旧提交之上追加修复，应判断恢复原功能与引入修复的组合；若功能已经基于撤销后的主线重新实现，则应按新的提交图分析，盲目撤销 R 可能重复引入旧实现。Git 官方的 [撤销错误合并指南](https://github.com/git/git/blob/HEAD/Documentation/howto/revert-a-faulty-merge.adoc) 专门区分这两种情形，[revert 主线选项](https://git-scm.com/docs/git-revert#Documentation/git-revert.txt--mparent-number) 则定义父序号的含义。

练习时可以把 D 改为修改旧功能文件，先预测三方基线、主线和主题侧各有什么，再观察冲突；随后加入一项依赖功能文件的检查，区分“合并命令成功”和“当前项目可运行”。恢复操作的正确对象是明确的行为与文件状态，祖先关系只是其中一部分证据。

## 6. reflog 与恢复：有价值但有明确边界

引用日志记录本地引用或 HEAD 的一些移动，可帮助找到误切走、误重设或变基之前的位置。它不是所有文件编辑的日志，也不是自动同步的共享历史。一个从未提交、从未暂存且被覆盖的工作区版本，通常不能仅靠引用日志恢复。编辑器本地历史或文件系统备份可能是另一条线索。

引用日志的保留有时间与配置边界，相关对象也可能在清理后消失。不能承诺任何历史操作都能无限期撤回。看到旧提交仍存在时，可以先给它建立明确引用以稳定保留，再检查内容，而不是反复移动当前分支试错。恢复过程应尽量增加可观察性、减少进一步覆盖。

引用日志也具有本地性。别人机器上发生过某个移动，不意味着你的克隆也有对应记录；远程服务的内部保留策略又是另一回事。事故恢复需要知道证据来自哪台仓库、记录了哪些动作、哪些对象仍可获取。一个短哈希截图或聊天片段可能提供线索，但不等于对象已经在本地可读。

<a id="git-3-detail-14"></a>

### 6.1 先保留再调查的恢复原则

发现误操作后，首先停止继续清理和大范围覆盖，读取状态与相关日志，辨认可能的目标提交。如果找到旧提交，建立新的恢复分支通常比立刻让当前分支强行跳回更便于检查，因为它保留现状与候选状态，允许你逐路径比较。之后根据目标选择拣选、恢复文件或其他明确动作。

对于未提交数据，应该优先检查实际保留位置：补丁、暂存对象、编辑器历史、系统备份或实验产物存储。不要因为某些情况下可以从不可达对象中找到内容，就把它当成通用保证。恢复能力依赖曾经写入了什么、还保留多久，以及你是否能识别正确版本。

## 7. 实验一：撤暂存保留工作区，恢复工作区读取索引

该实验直接验证两个容易混淆的目标。先把乙暂存并继续编辑为丙，撤暂存后索引回到甲而工作区保留丙；随后重新暂存丙、编辑成丁，再恢复工作区，得到索引中的丙。每一步通过读取实际内容断言，所有写入都局限于自动清理的临时目录。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_restore_targets_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(*args):
        return subprocess.run(["git", *args], cwd=repo, env=env, text=True,
                              encoding="utf-8", capture_output=True,
                              check=True).stdout.strip()
    git("init", "-b", "main")
    for key, value in [("user.name", "Example"),
                       ("user.email", "example@example.invalid"),
                       ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
        git("config", key, value)
    path = repo / "state.txt"
    path.write_text("A\n", encoding="utf-8")
    git("add", "--", "state.txt")
    git("commit", "-m", "base A")
    head = git("rev-parse", "HEAD")
    path.write_text("B\n", encoding="utf-8")
    git("add", "--", "state.txt")
    path.write_text("C\n", encoding="utf-8")
    git("restore", "--staged", "--", "state.txt")
    assert git("show", ":state.txt") == "A"
    assert path.read_text(encoding="utf-8").strip() == "C"
    git("add", "--", "state.txt")
    path.write_text("D\n", encoding="utf-8")
    git("restore", "--worktree", "--", "state.txt")
    assert path.read_text(encoding="utf-8").strip() == "C"
    assert git("rev-parse", "HEAD") == head
    print("unstage kept C; worktree restore copied indexed C; HEAD unchanged")
```

实验中的丁被覆盖是有意验证的行为，因此只在临时文件上演示。真实项目中若丁包含重要探索，应先保存。程序断言明确说明了哪些内容被保留、哪些被替换，比把恢复命令简单称为安全或危险更准确。

## 8. 实验二：软重设、混合重设与反向提交

下面分别在两个全新临时仓库中观察软重设与混合重设，避免前一个实验的状态影响后一个。然后构造一条普通反向提交，检查旧提交仍为新历史的祖先，内容回到原值。实验只在自己创建的目录执行历史移动，不应把这些调用改成用户重要项目路径。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

for mode in ["--soft", "--mixed"]:
    with TemporaryDirectory(prefix="git_reset_mode_") as root:
        repo = Path(root)
        env = os.environ.copy()
        env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
        def git(*args):
            return subprocess.run(["git", *args], cwd=repo, env=env, text=True,
                                  encoding="utf-8", capture_output=True,
                                  check=True).stdout.strip()
        git("init", "-b", "main")
        for key, value in [("user.name", "Example"),
                           ("user.email", "example@example.invalid"),
                           ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
            git("config", key, value)
        path = repo / "state.txt"
        for value in ["A", "B"]:
            path.write_text(value + "\n", encoding="utf-8")
            git("add", "--", "state.txt")
            git("commit", "-m", "record " + value)
        old_tip = git("rev-parse", "HEAD")
        git("branch", "saved-B")
        git("reset", mode, "HEAD^")
        assert git("show", "HEAD:state.txt") == "A"
        assert path.read_text(encoding="utf-8").strip() == "B"
        assert git("show", ":state.txt") == ("B" if mode == "--soft" else "A")
        assert git("rev-parse", "saved-B") == old_tip
        print(mode, "preserved working B; index prediction verified")

with TemporaryDirectory(prefix="git_revert_history_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(*args):
        return subprocess.run(["git", *args], cwd=repo, env=env, text=True,
                              encoding="utf-8", capture_output=True,
                              check=True).stdout.strip()
    git("init", "-b", "main")
    for key, value in [("user.name", "Example"),
                       ("user.email", "example@example.invalid"),
                       ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
        git("config", key, value)
    path = repo / "state.txt"
    for value in ["A", "B"]:
        path.write_text(value + "\n", encoding="utf-8")
        git("add", "--", "state.txt")
        git("commit", "-m", "record " + value)
    bad = git("rev-parse", "HEAD")
    git("revert", "--no-edit", bad)
    assert git("show", "HEAD:state.txt") == "A"
    assert git("rev-parse", "HEAD^") == bad
    assert git("rev-list", "--count", "HEAD") == "3"
    print("revert restored A and retained B as parent")
```

这组实验刻意给重设前的提交建立保留引用，说明“移动当前分支”与“删除旧对象”不同。普通反向提交的验证也没有只检查文件回到甲，而是同时检查父关系与提交数量，证明内容恢复和历史保留两个目标同时成立。它不包含后续依赖，因此不能用于推断复杂撤销必然无冲突。

## 9. 二分定位需要什么数学前提

在线性提交序列中，假设某个确定性判定在已知好端点通过，在坏端点失败，并且目标区间满足从好到坏的一次性边界。每次选择中间候选并判定，可以保留含有边界的一半区间，所需判定次数随候选数量呈对数增长。这个结论依赖判定稳定与边界模型，不是对任意训练分数序列的保证。

真实历史是有向无环图，工具会根据已知好坏与祖先关系选择能够有效缩小候选集合的节点，而不只是按时间戳取中位数。合并、跳过和不可测试提交会影响候选分布。通常可以定位一个与当前标记相容的首个坏提交，但若中间行为多次坏了又好，或者端点不是同一症状，结论就需要更谨慎解释。

稳定判定意味着同一对象在相同条件下能够得到一致分类。若每次随机训练分数波动大，某个真实较好的版本可能被误标为坏，搜索便会排除真正边界。一次错误标记不只是增加噪声，而可能改变后续搜索路径，使最终结果看似精确却针对错误约束。先降低判定噪声，往往比增加搜索速度更重要。

还应固定失败定义。程序无法构建、缺依赖和业务断言失败不是同一种坏。一个旧版本因为新依赖接口不兼容而无法启动，不足以证明它具有目标算法缺陷。对于无法判断的版本，可以跳过；若跳过集中在边界附近，工具可能只能给出多个候选，而不是唯一提交。应如实报告不确定区间。

<a id="git-3-detail-18"></a>

### 9.1 自动判定的退出码是接口契约

自动二分运行器把检查命令的退出状态解释为分类信号，因此退出码必须经过设计。对本章使用的`git bisect run`，零表示好；一至一百二十七之间、除一百二十五以外的退出码表示坏；一百二十五表示当前版本不可测试并跳过；其他退出码会终止二分。不要让“测试脚本找不到解释器”恰好被误解为业务失败。运行器需要区分环境故障、不可测试和确切缺陷。

尤其要注意，Shell 常用一百二十六表示找到了命令但无法执行，一百二十七表示找不到命令；这两者仍落在二分认定为坏的范围。若某个历史版本没有可用的构建工具，直接透传该状态就会把环境问题标成代码回归。

包装器应先区分可预期的历史版本不可测试与整个实验环境损坏：前者可以按事先规则返回跳过，后者宜终止搜索并修复环境。不要把所有异常都改成跳过，否则搜索会失去必要证据，也不要把所有异常都改成坏。[Git 官方自动二分说明](https://git-scm.com/docs/git-bisect#_bisect_run)列出了这些状态约定。

一个稳健检查器先确认必要输入存在与版本适配，再执行确定性断言，最后输出可追踪日志。对于旧版本接口不同的情况，可以在仓库外维护兼容检查器，但应确保它测量同一个行为，且没有替旧版本悄悄修复缺陷。检查器自身也是实验输入，需要固定其身份和调用条件。

每次判定最好记录目标提交、环境、输入摘要、观察值与分类理由。这样即使后来发现阈值或环境有误，也能重现搜索并纠正标记。二分日志是操作证据，不是最终因果解释；找到候选后仍需阅读差异，构造变化前后对照并验证机制。

<a id="git-3-detail-19"></a>

### 9.2 随机指标如何转成可解释判定

如果必须使用随机训练结果，应预先设定重复次数、种子集合、阈值与不确定时的处理方式，而不是看到分数后临时修改规则。可以把差异缩小为确定性局部症状，例如固定批次梯度是否具有预期尺度，避免每个节点都做完整训练。只有确实无法局部化时，才承担更昂贵的统计判定。

统计分类也有误判概率。多次自适应查询可能累积风险，普通固定样本置信区间并不自动提供整个搜索过程的错误控制。可采用更保守的预设规则、独立复核或适合序贯分析的方法，并清楚声明保证范围。本章不把一次分数超过阈值当成确定真值，因为这会隐藏研究任务最关键的不确定性。

找到候选后，应在边界两侧重新进行独立验证，最好使用未参与搜索的重复或更直接机制测试。若结果不稳定，应报告无法唯一定位，而不是强行挑一个提交。可靠的不确定结论比建立在误标上的精确哈希更有价值。

## 10. 实验三：用确定性断言实际运行历史二分

这个实验创建八个版本，其中第四个版本开始把固定输出从二改为三，并一直保持。仓库中的检查器读取该输出，通过返回码把正确值二标为好。我们使用系统当前 Python 解释器运行检查器，避免依赖外壳对可执行权限或脚本首行的解释，并在结束后恢复二分前的位置。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess
import sys

with TemporaryDirectory(prefix="git_bisect_exact_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(*args):
        return subprocess.run(["git", *args], cwd=repo, env=env, text=True,
                              encoding="utf-8", capture_output=True,
                              check=True).stdout.strip()
    git("init", "-b", "main")
    for key, value in [("user.name", "Example"),
                       ("user.email", "example@example.invalid"),
                       ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
        git("config", key, value)
    checker = (
        "from pathlib import Path\n"
        "import sys\n"
        "value = int(Path('value.txt').read_text())\n"
        "sys.exit(0 if value == 2 else 1)\n"
    )
    (repo / "check.py").write_text(checker, encoding="utf-8")
    commits = []
    for index in range(8):
        (repo / "value.txt").write_text("2\n" if index < 3 else "3\n",
                                         encoding="utf-8")
        (repo / "step.txt").write_text(str(index) + "\n", encoding="utf-8")
        git("add", "--", "check.py", "value.txt", "step.txt")
        git("commit", "-m", f"version {index + 1}")
        commits.append(git("rev-parse", "HEAD"))
    before = git("rev-parse", "HEAD")
    git("bisect", "start", commits[-1], commits[0])
    output = git("bisect", "run", sys.executable, "check.py")
    assert git("rev-parse", "refs/bisect/bad") == commits[3]
    assert commits[3] in output
    git("bisect", "reset")
    assert git("rev-parse", "HEAD") == before
    assert git("symbolic-ref", "--short", "HEAD") == "main"
    print("bisect identified version 4 and restored main")
```

额外的步数文件确保即使输出值不变，每个版本仍形成不同快照，避免空提交处理分散注意。实验的单一好坏边界由构造明确保证，正是二分有效的条件。把值改为交替好坏，再运行同样流程，可以观察模型前提破坏后结论如何受端点与历史结构影响；但不要把这种探索误称为唯一首因定位。

## 11. 从历史定位走向机制解释

定位到首个坏提交，只说明在给定判定器和条件下，某个变化边界与症状出现相联系。它可能直接引入缺陷，也可能暴露早已存在的错误，或者改变默认输入使旧问题首次被触发。例如新增空批次支持，可能暴露损失函数长期存在的除零问题；把新增支持全部撤掉能消除症状，却未必是最合理修复。

因此需要进行机制复核：明确变化影响了哪些输入与状态，构造最小失败样例，观察中间量，确认哪条假设被破坏，再设计针对性修复。若只凭历史边界就把整个提交定为错误，可能连同正确功能一起撤销。事故处置可以先快速止损，但长期修复应解释为什么失败、为什么方案能避免重现。

比较时还可以采用反事实实验：在坏版本上只修复怀疑点，或在好版本上引入该点，看症状是否按预测改变。这比纯时间关联提供更强证据，但仍要注意改动之间的相互作用。若只有多个变化组合才触发，单独恢复某一项可能不足以揭露完整机制。结论应与实验设计一致。

<a id="sec-5-1"></a>

<a id="git-3-detail-22"></a>

### 11.1 证据链如何支持之后的撤销决策

一份简洁但充分的缺陷记录可以保存失败输入、预期行为、实际行为、好坏版本、环境条件、最小触发机制和修复验证。这样未来读者能判断是否遇到同一问题，也能知道当初撤回的是某个实现还是整个功能。只有“某提交有问题，已回滚”会丢失大量可复用知识。

对模型指标事故，还应保留受影响运行与产物清单，避免修复代码后继续引用错误结果。若数据泄漏或评估口径有误，重新运行与报告更正属于恢复的一部分。Git 历史可以关联这些记录，却不会自动更新外部论文、看板或模型发布说明。

## 12. 实验四：通过引用日志找到旧位置并建立保留引用

下面只在临时仓库演示一次软重设，然后从引用日志验证旧位置仍被记录，创建恢复分支并读取旧文件。我们不依赖某个固定的日志序号，而是在记录中查找已知旧提交身份；这比假定所有环境都有同样多的操作更稳健。实验展示的是当前条件下可恢复，不承诺无限期保留。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_reflog_recovery_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(*args):
        return subprocess.run(["git", *args], cwd=repo, env=env, text=True,
                              encoding="utf-8", capture_output=True,
                              check=True).stdout.strip()
    git("init", "-b", "main")
    for key, value in [("user.name", "Example"),
                       ("user.email", "example@example.invalid"),
                       ("core.autocrlf", "false"), ("commit.gpgsign", "false"),
                       ("core.logAllRefUpdates", "true")]:
        git("config", key, value)
    for value in ["A", "B"]:
        (repo / "state.txt").write_text(value + "\n", encoding="utf-8")
        git("add", "--", "state.txt")
        git("commit", "-m", "record " + value)
    old = git("rev-parse", "HEAD")
    git("reset", "--soft", "HEAD^")
    entries = git("reflog", "show", "--format=%H", "HEAD").splitlines()
    assert old in entries
    git("branch", "recovered", old)
    assert git("show", "recovered:state.txt") == "B"
    assert git("show", "HEAD:state.txt") == "A"
    print("old B found in local reflog and retained without moving main")
```

在真实恢复中，如果旧身份并不知道，可以结合日志说明、时间和内容逐步辨认，但时间仅是线索。找到候选后读取文件与差异，确认它确实是需要的状态。不要因为日志中某条看起来最接近事故时间，就直接覆盖当前工作区。先给候选建立保留位置，再比较与选择，更容易保持证据完整。

## 13. 练习与详细解析

<a id="git-3-detail-25"></a>

### 13.1 练习一：撤暂存为什么不丢编辑

最近提交为甲，索引为乙，工作区为丙。希望保留丙，但下次提交不再包含乙，应改变哪个状态？只把索引恢复到甲，工作区保留丙。此后丙相对甲表现为未暂存变化。若错误地恢复工作区，就可能把丙覆盖为索引乙或其他来源，目标完全不同。

解题时先写目标三元组：提交甲、索引甲、工作区丙，再选择能实现它的操作。这个方法可以推广到多路径情况：每条路径分别声明来源和目标，不必把整个仓库一刀切。

<a id="git-3-detail-26"></a>

### 13.2 练习二：软重设后为什么仍然有全部修改

干净状态下提交乙是甲的后代，软重设到甲后，索引与工作区仍为乙，因此修改表现为已暂存。它不是命令没有执行，而是命令主要改变历史引用。若目的是重新组织提交，这正是有用状态；若目的是丢弃编辑，就需要另一种明确目标，但不能在不保留重要内容时随意扩大范围。

还要区分分支引用移动与对象删除。乙可能仍被其他引用或日志保留，软重设不会原地把乙变成甲。理解对象不可变模型，可以解释为什么恢复引用有时能够找回旧提交。

<a id="git-3-detail-27"></a>

### 13.3 练习三：硬重设一定保留所有未跟踪文件吗

不能作这种保证。阻碍目标已跟踪路径写入的未跟踪文件或目录可能受到删除影响。同时它也不等于删除所有未跟踪文件。因此不能把它当作具有简单“只碰跟踪文件”边界的清理命令。执行前必须检查目标树与当前路径关系，并保存必要内容。

这道题提醒我们，教程中的简化描述应保留关键例外。一个会造成数据丢失的边界，不适合为了口号简洁而省略。真正清楚的说明应该让读者能够预测具体路径的命运。

<a id="git-3-detail-28"></a>

### 13.4 练习四：恢复旧文件等于回到旧实验吗

不等于。其他代码、数据、依赖和配置仍可能是当前版本，形成一个历史上从未实际运行的新组合。若旧文件使用旧接口，当前调用方可能不兼容。恢复后应核对相关契约，必要时用完整旧快照与固定条件重跑，才能声称复现旧实验。

精确说法是“某路径恢复为某提交中的内容”。这种窄而准确的结论有明确证据。只有补齐其他条件，才能扩展为更强的实验复现结论。

<a id="git-3-detail-29"></a>

### 13.5 练习五：反向提交会删除原提交吗

通常不会，它新增一条抵消相关效果的提交，原提交仍在历史中。这样共享分支继续向前，协作者能够看到引入与撤回的事实。但反向补丁仍可能冲突或破坏后续依赖，因此不能仅凭命令成功就断言系统恢复可用。

若原提交已经对外部系统造成影响，例如生成错误指标，版本撤销也不会自动撤销外部事实。需要在相应系统中执行独立更正，并关联代码修复记录。

<a id="git-3-detail-30"></a>

### 13.6 练习六：撤销接口引入为何可能破坏后来代码

后续提交可能依赖被撤接口。即使逆补丁成功应用，调用方仍然使用新接口，于是产生运行失败或更隐蔽错误。应以当前目标行为为标准设计恢复，必要时同步调整依赖或保留兼容层，而不是把字面逆补丁当成唯一正确答案。

这也说明撤销与修复不同。撤销是一种实现策略，修复是满足行为目标。某些事故适合先撤销止损，之后再做精确修复；另一些情况下，撤销会破坏更多依赖，需要直接修正。

<a id="git-3-detail-31"></a>

### 13.7 练习七：引用日志能找回所有工作区版本吗

不能。引用日志记录引用位置变化，不是逐次文件保存历史。未被写入对象或其他备份的编辑，覆盖后通常不能依靠它恢复。编辑器历史、系统备份和明确补丁可能提供其他线索，但都各有保留边界。

即使旧提交曾经存在，也要考虑日志过期与对象清理。恢复机制有用，但不能替代事前保存。把“有时能救回来”当成“永远不会丢”是危险的逻辑跳跃。

<a id="git-3-detail-32"></a>

### 13.8 练习八：首个坏提交就是唯一根因吗

不必然。它可能引入错误，也可能暴露已有错误，或改变输入使潜在问题首次触发。二分定位给出与判定器相容的边界，机制解释还需要最小例子、中间量与反事实验证。应保留失败输入与环境，避免把代码时间顺序直接当作因果链。

例如允许空批次的功能使旧损失函数除零。删除新功能能消除症状，但真正缺陷可能是损失函数没有定义空输入行为。合理修复需要根据任务承诺判断。

<a id="git-3-detail-33"></a>

### 13.9 练习九：旧版本构建失败应标坏吗

如果目标是某个算法回归，因依赖变化而无法构建的版本通常不能直接标为业务坏。应先确认检查器是否适配旧版本，必要时跳过并记录原因。若跳过集中在边界附近，最后可能只能报告一组候选，不能强行宣称唯一定位。

反之，如果研究目标本身就是某平台构建能力，那么构建失败可以是目标症状。分类取决于预先定义的问题，不能在搜索途中根据方便临时改变含义。

<a id="git-3-detail-34"></a>

### 13.10 练习十：一次随机分数能作为真值吗

若版本差异很小而随机波动大，一次分数会带来误标风险，并可能让搜索排除真正边界。应优先寻找确定性局部症状；若必须统计判定，应预设重复、阈值和不确定处理，并在候选边界两侧独立复核。

不能因为工具最终给出一个哈希，就认为随机性已经被解决。精确输出格式不等于精确科学结论。误差来自判定器，工具无法自动知道你标错了哪次结果。

<a id="git-3-detail-35"></a>

### 13.11 练习十一：blame 是否可以证明责任

逐行追踪提供当前行与某些提交的关联，不能直接证明故障根因或个人责任。格式化、移动、复制以及跨模块依赖都可能改变显示。应沿相关提交阅读目的与上下文，再通过行为实验验证机制。

把归因工具用于寻找知识来源和解释路径，比用于指责更符合它的技术能力。即使某人最后编辑该行，真正缺陷也可能来自需求变化、接口假设或另一模块。

<a id="git-3-detail-36"></a>

### 13.12 练习十二：为什么撤销合并后再合并可能不恢复内容

撤销合并改变内容，但原合并的祖先关系仍然存在。工具知道相关历史已经汇入，因此再次合并同一组旧提交，不一定把被反向撤回的全部效果重新引入。应结合具体图决定是撤销反向提交还是采用新的修复，而不是盲目重复整合。

这正是内容状态与图关系必须同时理解的例子。两个当前文件树看起来类似，未来操作语义却可能不同。重要历史恢复应先在独立仓库模拟，再执行明确方案。

<a id="git-3-detail-37"></a>

### 13.13 练习十三：查到某个字符串变化就能锁定缺陷吗

不能。搜索结果是候选线索，字符串可能只在注释或无关路径变化，真正缺陷可能通过等价重写而没有相同文本。应检查差异如何影响实际执行，并用固定输入验证。搜索未命中也不能证明没有相关变化。

高效调查通常结合多种证据：提交说明提供目的，差异提供实现变化，调用图提供影响范围，测试提供观察。任何单个界面都很难独立承担完整解释。

<a id="git-3-detail-38"></a>

### 13.14 练习十四：恢复时为什么先建候选分支

如果已找到旧提交，给它建立新的保留引用通常可以在不移动当前分支的情况下检查内容，保留事故现状和候选版本。这样更方便比较与选择后续动作，也降低进一步覆盖的风险。它不是唯一方法，但体现“先保留、再调查、后改变”的原则。

仍需注意引用保留只覆盖仓库对象，不自动保存未跟踪文件与外部产物。恢复计划应按资源分别处理，明确哪些已经有可靠副本，哪些仍需从其他系统寻找。

<a id="sec-6-1"></a>

<a id="git-3-detail-39"></a>

### 13.15 综合题：如何定位随机训练中的细微回归

固定数据与评价协议后，发现新版本均值略差但种子波动明显。首先不要直接按一次完整训练分数二分；应比较损失定义、梯度尺度、标签映射和采样规则，寻找可确定性测量的局部差异。若找到固定批次上权重归一化不一致，就用该症状建立快速判定器，再进行历史定位。

如果无法局部化，预先确定统计设计与容忍区间，对不确定结果保留跳过或追加验证机制，并记录全部观察。找到候选后重新验证两侧、解释代码机制、检查外部条件。最终结论可以是“缩小到若干候选，证据尚不足以唯一归因”，不应为了给出一个哈希牺牲可靠性。

## 14. 进阶专题：为恢复操作建立状态证明

<a id="git-3-detail-41"></a>

### 14.1 把操作选择转成一个约束问题

假设当前提交树包含甲版本，索引包含乙版本，工作区包含丙版本。现在任务要求撤掉某项待提交功能，但保留修复与探索。仅知道三个版本不同还不足以选命令，因为乙和丙可能各自混合多种意图。需要先将差异分成逻辑单元，标记哪些必须保留、哪些需要撤回、哪些依赖其他单元，再决定是否能按路径或差异块操作。

如果功能与修复位于同一文件同一区域，整文件恢复通常过宽。可以重新构造目标内容，再审查索引与工作区的各自差异。交互操作节省编辑成本，但不会自动知道逻辑单元。一个可靠方法是在独立副本中先形成期望文件，比较它与当前状态，再将明确差异应用回目标位置。复杂时宁可多读几次内容，也不要把不可逆覆盖当成探索手段。

操作后的证明至少包含三项：需要保留的内容仍可读取，需要撤回的行为不再存在，其他无关路径未发生意外变化。第一项可以通过内容比较与引用保留证明；第二项需要行为测试；第三项需要范围差异检查。仅检查工作区状态干净无法同时证明这三点，因为干净状态也可能是错误内容被完整提交。

还要明确恢复来源是否完整。如果来源提交缺少当前必需的新配置，整树切回旧版本可能无法在新环境运行；若只恢复部分文件，又可能破坏旧接口。恢复计划应包含兼容性前提，而不是把旧版本天然视为正确。所谓“已知好版本”，始终是相对某个条件与判定器而言。

<a id="git-3-detail-42"></a>

### 14.2 单一边界假设为什么需要主动核验

考虑八个版本的判定序列依次为好、好、坏、坏、好、好、坏、坏。如果目标是寻找历史上第一次坏，单纯给工具最后一个坏和最早一个好，不足以表达中间修复又回归的全部结构。某些搜索路径可能把后一次边界识别为与当前症状相关的首个坏，而不满足你日常语言中的“最早出现”。应先明确要找哪次回归，并选择能隔离该区间的端点。

在提交图中，“第一个”也可能不是唯一时间点。不同侧支可以分别引入相关症状，合并后才暴露共同效果。若一个合并提交首次失败，原因可能是交互，而不是任一父独立失败。可以分别测试父节点，检查最终树相对各父的变化，再构造组合实验。不要强迫所有事故都具有一条线性单因故事。

主动核验可以包括：确认两个端点测量同一症状，抽查中间版本是否存在修复与再引入，检查合并父关系，以及在最终候选的父上运行相同判定。这样不能消除所有复杂性，但能发现明显违反模型的情形。一旦发现，应扩展调查范围并报告边界条件，而不是继续把算法输出当成绝对事实。

<a id="git-3-detail-43"></a>

### 14.3 用最小干预区分暴露缺陷与引入缺陷

假设某提交把批次采样改为允许空批次，训练从此出现非数值。二分定位该提交后，有两种假设：采样器不应产生空批次；或者损失接口承诺支持空批次但实现不完整。判断哪一种成立，需要回到设计契约，而不是只看失败发生时间。若空批次属于合法输入，修复损失函数可能比撤回采样功能更合适。

可以做两个最小干预。其一，在旧版本人为提供空批次，观察旧损失是否也失败；其二，在新版本保持采样器不变，只修复空输入处理，观察症状是否消失。若两者符合预测，证据支持“新变化暴露旧缺陷”。但仍需测试修复没有改变非空批次的梯度与计数，避免只为消除症状引入新的协议偏差。

再考虑标签编号迁移与模型输出顺序错配。单独恢复标签映射也许让分数恢复，却可能掩盖模型结构中另一个顺序假设。需要在极小样例中逐步跟踪样本身份、真值编号、输出列和指标解释，明确哪一条映射缺失。历史工具缩小代码范围，机制实验连接程序状态，二者结合才形成可解释结论。

<a id="git-3-detail-44"></a>

### 14.4 外部状态恢复需要独立事务设计

代码反向提交不会自动逆转已经执行的数据迁移。若新代码把旧字段合并并删除，恢复旧代码后可能无法再读取当前数据库；即使迁移有逆向脚本，也不一定能恢复被丢弃的信息。恢复方案需要数据备份、兼容窗口或可逆迁移设计，而不只是版本指针。代码状态与数据状态必须作为联合系统考虑。

训练产物也一样。错误运行覆盖了唯一模型文件，撤销代码不能凭空重建旧权重。应使用不可变产物身份、独立运行目录与保留策略，避免把覆盖式输出当成实验记录。恢复时需要检查产物是否与其声明的代码、配置和数据对应，不能只凭文件名包含“最佳”就认定它是正确候选。

对于外部报告，恢复还包括沟通与更正记录。这里的教材并不要求自动向任何人发送消息，而是强调工程事实：错误数字一旦进入报告或发布物，源代码修复并不改变已经传播的副本。负责任的交付应把受影响对象列清，并在授权流程中完成相应更新。版本历史只是整个更正链条的一部分。

<a id="git-3-detail-45"></a>

### 14.5 恢复演练比恢复口号更有价值

团队可以定期在无重要数据的练习仓库中模拟误暂存、误提交、分离状态提交和分支误移动，要求操作者先写目标状态再执行。评价标准不是背出多少命令，而是能否保留指定内容、准确解释影响、核对结果并清理临时资源。这样的演练能暴露对索引与引用的误解，而不需要真实事故来教学。

备份也应通过恢复验证。存在备份文件不意味着其中包含所需对象、依赖和产物；归档能够解压也不意味着项目可以重建。可以从一个固定实验身份出发，在干净目录恢复代码与必要输入，运行最小验证，记录缺失环节。演练发现的绝对路径依赖、失效下载和未记录配置，往往比增加一条抽象规范更有价值。

最后，恢复文档应写明前置条件和停止条件。比如“本步骤只在独立临时仓库运行”“若状态与示例不同先停止解释差异”“未确认保留内容前不执行覆盖”。这些条件帮助读者判断教程是否适用，而不是制造不必要审批。真正的安全来自对状态的理解与可验证保留，不来自给命令贴一个笼统标签。

<a id="git-3-detail-46"></a>

### 14.6 成本受限时怎样安排定位实验

假设完整训练需要数小时，而候选历史有几十个提交。直接对每个二分节点做完整训练虽然减少节点数，仍可能成本很高。可以先把失败定义拆成可观察的中间量：固定批次的预测、损失分子分母、梯度范数、参数更新和评价计数。若某个中间量已经能稳定区分好坏端点，就可以用它建立更便宜的判定器。

但代理判定器必须与原症状建立联系。某个梯度范数不同不一定就是缺陷，可能是正确改进。应解释为什么这个量违反契约，例如有效样本复制一倍后均值梯度不应翻倍；或者全掩码输入应按规定跳过更新，而不是产生非数值。基于不变量的判定比随意选择一个能区分端点的数字更可靠。

可以采用两阶段策略：先用快速检查缩小历史范围，再在候选边界进行昂贵端到端复核。快速阶段的结果是候选线索，最终阶段验证它是否解释真实事故。若快速检查与完整结果不一致，应修正假设，而不是只保留支持原观点的运行。成本优化应减少冗余计算，不应减少对关键机制的核对。

对于无法构建的旧版本，可以在隔离环境中恢复其依赖，但要权衡环境恢复成本与信息增益。若多个邻近版本都不可测试，诚实报告一个候选区间可能比花大量时间维持表面唯一性更合理。研究报告应区分“搜索到某节点”与“经过独立机制复核的根因”，避免把工具效率当成证据强度。

<a id="git-3-detail-47"></a>

### 14.7 把恢复成功写成可验收条件

“已经回滚”描述的是动作，不是结果。更好的验收条件包括：目标失败样例不再失败，原有合法输入行为保持，需要保留的未提交研究内容仍然可读，当前分支与共享状态可解释，相关产物和报告已经与代码身份对应。每一条都可以指定观察方法，而不是依赖操作者的主观感觉。

例如对错误归一化的恢复，可以检查复制样本后的均值不变、空有效集按协议处理、权重缩放符合预期，以及旧错误指标被标注为失效。对文档恢复，可以检查章节链接、公式约定和导航完整。相同恢复命令服务不同任务，验收自然不同，因此没有一条命令输出能够代替全部验收。

事故之后还应保留适量解释，避免未来重复同样试错。记录不需要冗长叙事，重点是触发条件、受影响范围、采取的状态变化、关键验证和保留边界。若有不确定部分，就明确写出还不能证明什么。清楚的限制能帮助后来的人正确使用结论，而不是削弱交付价值。

一个实用练习是让同伴只凭恢复记录重建你的判断，而不读取原始聊天。若他无法知道被测对象、需要保留的内容或失败定义，就说明记录还缺少必要连接。若他能够按固定输入复现原问题，再在修复树观察预期结果，证据链才具有可交接性。这个标准适用于个人学习：几周后的自己同样需要重新理解当时条件。

还可以把每次恢复总结成一条可以加入测试的不变量。这样事故知识不只留在叙述中，而是转化为未来变化的可执行约束。并非所有问题都适合自动测试，但输入模式、计数、边界和接口兼容通常值得保存最小例子。恢复工作的最终价值，不仅是让今天重新运行，也是让同类错误更容易在下一次被及时发现。

最后应清理练习产生的临时资源，但不要把恢复候选、唯一补丁或尚未核对的产物当成垃圾。清理应发生在保留与验收之后，且范围明确。本章实验借助临时目录上下文自动清理，读者项目中的长期文件则需要根据实际用途判断。简洁的工作目录是结果，不是以牺牲证据换来的外观。
