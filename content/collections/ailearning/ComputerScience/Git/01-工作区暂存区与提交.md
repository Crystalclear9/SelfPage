## 1. 三个区域分别解决什么

工作区是文件系统中供编辑器和程序访问的文件集合；暂存区通常称为索引，描述下一次提交准备采用的路径、模式和对象；仓库的对象数据库保存内容与提交之间的关系。三者解决三个不同时间尺度的问题：现在正在写什么，下一步准备交付什么，过去已经确认了什么。把这三个问题混在一起，便会误以为保存文件等于暂存、暂存等于提交、提交等于上传。

普通提交以暂存区构造快照。因此，一个文件可以同时有已提交版本、已暂存版本和尚未暂存版本。索引不是临时剪贴板，也不只是文件名清单：其中保存足够信息让 Git 构造下一棵目录树。在发生合并冲突时，索引还可以保存同一路径的多个阶段，此时它并不表示一份已经解决的普通快照，后续章节会展开这种状态。

为便于推理，暂时把普通已跟踪文件的三个内容记为最近提交中的版本、索引中的版本和工作区中的版本。正常编辑首先改变工作区；暂存把指定路径当时经过过滤后的内容写入对象数据库，并更新索引；普通提交把索引所描述的目录树连同父提交和元数据组成提交对象，随后移动当前分支引用。提交成功并不要求工作区与索引完全相同。

这里的“普通提交”指没有额外路径参数、没有自动暂存选项的常见调用。带路径的提交以及自动暂存已跟踪文件的提交会改变内容选择规则。初学阶段先固定一种明确流程：检查状态、审查差异、显式暂存、再次审查暂存差异、验证目标快照、提交。等能够解释这些动作后，再使用快捷方式。

### 1.1 暂存后继续编辑为什么会形成两个版本

假设最近提交中的学习率为十分之一，先把它改成百分之一并暂存，随后又改成千分之一。编辑器显示千分之一，索引仍保存百分之一。此时普通工作区差异比较的是千分之一与百分之一；暂存差异比较的是百分之一与十分之一。若直接提交，历史里记录百分之一。提交后，工作区仍保留千分之一，并继续表现为未暂存修改。

因此，提交成功之后仍有修改不是提交失败的证据。它可能精确反映了“先交付一部分，再继续编辑”的意图。真正需要核对的是：准备提交的版本是否符合目的，工作区剩余变化是否已被理解。如果本次任务要求交付千分之一，就必须再次暂存相应修改。如果本次只打算交付百分之一，保留后续试验也可以，但必须避免用后续试验的测试结果替前一版本背书。

把文件状态想成单一的“已修改”标签会丢失信息。短状态输出的两个位置分别描述索引相对提交的变化、工作区相对索引的变化。在普通非冲突状态下，同一个路径可能同时在两列出现修改标记。冲突状态还有独立编码规则，不能把这一解释机械套用于全部输出。机器解析还需要考虑路径引用、空格和特殊字符，应使用空字符分隔的稳定接口。

### 1.2 快照模型和补丁显示是两回事

Git 的数据模型以快照和父关系为中心，审查工具却常把相邻快照的区别显示为补丁。这两者并不矛盾。快照回答某个版本包含什么；差异回答两个选定状态之间什么发生了变化。看到提交页面只有几行修改，不意味着提交对象只保存这几行，也不意味着其他文件不属于该版本。

假设一个实验项目有训练程序、数据清单和配置三份文件。提交只修改配置时，新目录树仍指向训练程序和数据清单的对象。未变化的内容可以通过对象复用共享，而不必重复存储。底层打包时还可能使用增量压缩，但增量压缩属于存储实现，不会把逻辑快照变成只能按照补丁逐个恢复的链。分析恢复和完整性时，应先使用逻辑对象模型。

这个模型也解释了两个常见现象。第一，删除某个文件并提交，不会立即删除旧提交中引用的对象，所以以前的版本通常仍能读取它。第二，重命名在很多场景下是通过前后内容相似性推断出来的，而不是提交中保存了一条普遍适用的“文件改名命令”。修改检测参数可能影响显示出来的重命名关系，却不改变两棵树实际包含的路径和内容。

## 2. 最小本地工作流与读写边界

一个可靠的最小工作流首先确认当前位置和状态，再选择要交付的变化。查看状态与差异通常是读取操作；暂存会写索引及必要对象；提交会新增对象并更新引用；推送才涉及远程仓库。区分这些边界能帮助你知道失败后应该检查哪里，也能避免把本地实验误当成已经共享给同伴的结果。

```bash
git status --short
git diff -- train.py
git add -- train.py
git diff --staged -- train.py
git diff --staged --check
git commit -m "修正训练阶段的样本权重归一化"
git log -1 --stat
```

这里的双连字符用于分隔选项和路径，防止某些以连字符开头的文件名被误解为命令选项。它不等于禁用所有路径模式语义：Git 的路径参数还有路径规格规则。如果文件名包含通配字符，脚本应进一步明确是否使用字面路径规格，不能仅凭加引号就认定所有解释层都被消除。

这段流程也不是无条件保证正确性的咒语。差异检查通过只能说明补丁没有它所检测的空白错误，不能证明算法正确；提交说明清楚不代表测试充分；状态为空不代表实验可复现。每一个工具只提供特定证据。学习过程中最好在每步后写一句预测：它读取哪个状态、写入哪个状态、成功之后什么应当改变、什么不应改变。

### 2.1 提交前审查的对象必须明确

提交审查至少包含两个不同范围。索引相对最近提交的差异，描述默认提交将引入的变化；工作区相对索引的差异，描述当前运行文件与准备交付文件的区别。如果只查看前者，可能遗漏依赖尚未暂存内容的风险；如果只查看后者，又可能完全看不到已经暂存的错误。

例如，你暂存了新的损失函数实现，却没有暂存同时修复的除零保护。工作区训练可以顺利完成，因为程序读取的是两个修复都存在的文件；提交版本只包含损失函数变更，遇到空批次仍会失败。解决方法不是一律禁止部分暂存，而是确保测试覆盖的确实是要交付的树。独立检出或构建目标树能够把这个问题转化为可检验条件。

审查还应覆盖删除、模式和生成文件。只看文本中的加减行可能漏掉脚本执行位变化、符号链接变化或意外进入历史的二进制产物。对于训练项目，配置默认值、数据划分清单、评估脚本与文档的变化经常共同构成一个可解释单元。把它们放在一个提交中并不违背小提交原则，只要它们共同服务一个可以验证的目的。

<a id="git-1-detail-6"></a>

## 3. 索引是一份可构造的交付计划

索引允许你把“编辑时产生的全部变化”与“本次准备交付的变化”分开。一个文件可能同时混合格式清理、错误修复和探索性改动；部分暂存可以选择其中一组。这种能力的价值在于缩小审查与回滚范围，但前提是拆分后的每一份快照在语义上成立。机械地按行数切分可能得到无法运行或行为不一致的中间版本。

交互式暂存通常以差异块为单位选择。有时需要拆分块，有时两段相邻修改实际上互相依赖，不能为了凑小提交强行分离。例如函数参数增加了样本权重，而调用点也必须传入它，这两部分在一起才完成行为变化。索引让你表达依赖明确的交付计划，不会自动替你证明计划正确。

删除文件也需要进入索引。工作区删除只是当前文件系统不再有该路径；暂存删除以后，下一提交的树才会移除它。不同选项对新文件、修改文件和删除文件的覆盖范围不同，尤其在限定路径时应根据实际状态验证，而不是依赖“某个命令总能包办”的记忆。全仓库暂存方便，但在混合实验目录中可能把个人输出一并纳入。

索引中的路径不仅关联内容，还关联模式。常见普通文件、可执行文件和符号链接对应不同类型或模式表示；嵌套仓库还可能成为指向另一仓库提交的条目。索引不保存所有文件系统元数据，目录权限、任意扩展属性和文件时间不能指望通过普通提交完整恢复。因此“版本恢复了”与“原机器文件系统被完整克隆了”是不同断言。

<a id="git-1-detail-7"></a>

### 3.1 路径选择与命令执行的解释层

在命令行中，一个参数往往先经过外壳解释，再由 Git 解释。外壳可能展开通配符、变量或命令替换；Git 再按照选项、修订表达式和路径规格解析参数。因此自动化脚本应优先使用参数列表调用进程，而非把文件名拼成一整条命令字符串。即使文件名来源可信，空格和非英文字符也足以让脆弱的拼接方式出错。

研究项目的目录命名可能包含实验日期、模型版本以及括号。读取文件列表时，按换行拆分也不总安全，因为某些系统允许文件名包含换行。需要机器可靠处理的接口应选择空字符终止的输出，并按字节或明确编码解析。课堂中的短文件名是为了突出机制，不能让这些简化变成生产脚本的隐藏前提。

还有一种常见错误是把修订表达式与路径混在一起。例如某个分支名与目录名相同，命令可能产生歧义。显式分隔修订与路径，使用已经解析的提交标识，能够减少这种歧义。可重复实验中最好记录完整对象标识，而不是只抄一个在当前仓库恰好足够唯一的短前缀。短前缀的可辨识性依赖仓库对象集合。

## 4. 机器学习仓库应保存什么

机器学习代码仓库首先需要保存决定行为的源文件：模型定义、训练与评估入口、数据预处理规则、配置模式、依赖声明、测试以及解释实验协议的文档。它们应共同回答“这个结果如何产生”和“哪些条件发生变化”。只有训练脚本而没有划分规则，或者只有模型权重而没有词表与预处理版本，都可能使未来的读者无法重建同一计算。

大数据集和模型产物是否直接进入 Git，取决于体量、变更方式、访问权限与所用存储机制。对于大多数频繁变化的二进制产物，单纯放进普通历史会提高克隆与维护成本。合理替代是保存能够定位不可变产物的清单，记录内容摘要、来源、转换步骤、许可与可获得性。只有一个会被覆盖的下载地址不构成稳定版本标识。

训练日志同样要区分用途。用于审查的简洁指标、失败说明和运行清单可以是提交的一部分；庞大的逐步日志、缓存、临时检查点则可存放在专门产物系统。选择依据是它们如何被检索、验证和保留，而不是一律认为文本就应该入库、二进制就永远不能入库。小型固定测试夹具可以合理进入仓库，以支持无需联网的确定性测试。

仓库中也不应保存真实凭据和无关个人信息。忽略规则可以防止未跟踪文件被常规暂存，却不能撤回已经提交或已经分享的秘密。发生泄露时，首先处理凭据本身的有效性，再讨论历史清理与副本传播。把文件从最新目录删除，只改变最新快照，不会让已有克隆中的旧对象自动消失。

<a id="git-1-detail-9"></a>

### 4.1 代码版本只是实验身份的一部分

设两次训练使用完全相同的提交标识，却读取了不同的数据快照，或使用了不同的依赖解析结果。它们属于同一代码版本，却不是同一实验条件。相反，如果代码提交仅修改说明文档，训练行为可能相同，但仍需要说明如何判定这种等价。复现记录必须把代码身份与计算条件分开描述，再通过明确关系连接起来。

一个实用的实验身份至少包括代码提交、是否存在未提交补丁、配置内容、数据及划分标识、环境依赖、随机性控制、硬件与精度模式，以及输出产物摘要。随机种子不是万能复现开关：并行归约、非确定性算子、库版本差异和外部服务都可能影响结果。记录种子有价值，但只能覆盖随机性机制中的一部分。

提交身份的精确性也有边界。代码仓库引用了子模块、外部下载或运行时生成文件时，主仓库提交不一定包含完整输入。需要追踪每一条外部依赖的固定版本及可获取性。把某个版本号写进说明只是一个声明；能否拿到相同内容，还要靠锁定文件、内容摘要和实际恢复演练来验证。

<a id="git-1-detail-10"></a>

## 5. 提交信息如何承担解释责任

好的提交信息描述变化解决的问题和最终行为，并给出必要背景。标题应让读者不打开补丁也能理解目的，例如“按有效样本数归一化批次损失”比“修改代码”提供更多信息。正文适合说明触发条件、采用该设计的原因、替代方案为何不适用，以及验证结果。无需把每一行代码翻译成自然语言。

把提交当成可审查推理单元，会自然得到一个有用标准：这次变化是否能用一句明确的行为描述概括，相关修改是否都能支持这个描述，测试是否能区分修改前后的关键差别。如果标题只能写“整理各种东西”，往往意味着范围混杂；但如果一次接口迁移必须同时调整多个模块，文件很多也可能仍属于同一个清楚的变更。

提交信息不应宣称未经验证的结果。一次小型合成测试只能支持相应条件下的正确性，不能自动证明大规模训练稳定；修正统计口径也不等于模型能力提升。说明验证规模、数据范围和已知边界，使未来使用二分或回滚的人能够判断这个提交原本承诺了什么。诚实的窄结论比宽泛的成功宣言更利于长期维护。

时间与作者元数据也要正确理解。提交中通常存在作者和提交者两组信息，它们可能在转录、重放或协作中不同。时间戳不是严格拓扑顺序，也不是不可伪造的事实证明。判断祖先关系应依据提交图，判断真实性应结合受信任的签名与发布流程，不能仅凭某个界面展示的名字和时间。

<a id="git-1-detail-11"></a>

### 5.1 从缺陷报告写出可审查提交

设一个损失函数在空掩码批次上产生非数值。缺陷报告应说明空掩码如何出现、预期如何处理、当前错误如何表现。修复可能选择跳过该批次、返回显式状态，或把该情况视为输入错误；这些方案对应不同接口承诺。提交需要解释最终选择，测试则覆盖全有效、部分有效和全无效三种情况。

如果你顺便重命名了整个模块并重排所有函数，审查者会更难识别真正的行为修复。可以把纯重构与行为变化分开，前提是两个快照各自成立。若为了兼容接口必须一起调整调用方，就应一起交付，并在说明中强调依赖关系。小提交的目标是减少理解负担，不是让每次提交都只有一份文件。

对于教材或实验资料，提交也可以围绕一个认知变化组织。例如新增关于加权平均的反例时，应同时更新章节目录、示例输出和题解。只提交正文却漏掉导航，会使读者难以找到结果；只提交目录则会出现空链接。可审查性既包含算法正确，也包含交付对象在使用场景中是否完整。

## 6. 忽略规则、已跟踪文件与内容过滤

忽略规则主要影响未跟踪路径是否被常规扫描和添加。一个已经跟踪的日志文件，即使后来加入忽略模式，修改仍会出现在版本控制状态中。因为“是否跟踪”与“是否匹配忽略规则”是两个不同维度，不能把后者当成对前者的撤销命令。若决定不再跟踪，需要显式修改索引，并考虑该路径的历史与协作影响。

忽略文件通常应表达项目共同的生成产物，如缓存目录、构建输出和临时检查点。开发者个人编辑器设置可以使用本地排除机制，避免把个人偏好扩散成项目规则。规则越宽泛，误忽略重要输入的概率越高。例如一概忽略所有表格文件，可能把固定测试数据也隐藏。可以用例外规则恢复必要文件，但必须理解被排除父目录对重新包含的限制。

判断某个文件为什么被忽略，应使用能够显示匹配来源的检查命令。只凭状态中“没看到它”无法区分忽略、路径错误、位于另一个仓库或根本没有写入。对一个已跟踪文件执行忽略检查时，也要理解默认行为与相应选项。调查应该从文件是否存在、仓库根目录在哪里、是否已跟踪这几个独立问题开始。

内容过滤又引入另一个细节：工作区字节不总等于对象库中的字节。换行转换、属性设置和自定义过滤器都可能在加入索引或检出时作用于内容。因此“保存后没有修改任何字符”不能保证索引对象与原文件字节逐位相同。需要字节稳定的配置、数据和摘要实验应明确属性规则，避免跨平台隐式转换破坏证据链。

<a id="git-1-detail-13"></a>

### 6.1 换行、编码和可移植性

Windows 与类 Unix 系统常使用不同文本换行约定。仓库可以规定文本规范形式，并在检出时转换，但规则应由项目明确管理，不应只依赖每个人的全局设置。一次大规模换行重写会淹没真实改动，使审查和责任定位困难。对已有项目调整属性时，最好把规范化与行为变更分开，并检查二进制文件是否被错误当成文本处理。

Git 的内容对象保存字节，而不替所有文本文件统一语义编码。两份视觉上相同的字符串可能具有不同字节表示，例如 Unicode 组合方式不同。路径本身在不同文件系统上的大小写、规范化和保留名称规则也可能不同。跨平台仓库应避免只靠大小写区分重要文件，且不能假定一台机器能够忠实检出所有合法于另一台机器的路径集合。

这些问题在机器学习数据清单中尤其明显。样本路径的大小写变化、行尾空白、编码标记或路径分隔符，都可能改变加载器行为。提交能够保存这些字节，却不会告诉你哪一种语义正确。应通过输入校验和跨平台测试把约定显式化，并在评估清单中使用统一、可验证的路径解释规则。

## 7. 对象图、引用与提交身份

理解 Git 的底层对象不必从文件格式细节开始。先掌握四类主要对象：内容对象保存文件内容；树对象把路径名、模式与对象关联起来；提交对象关联根树、父提交和元数据；附注标签对象可以为另一对象附加说明与签名。普通轻量标签和分支主要表现为引用，不要把所有名称都当成独立内容对象。

文件名通常在树对象中，而不在内容对象中。因此两个不同路径保存完全相同的规范化字节，可以指向同一个内容对象。一个目录的内容、名称或模式变化会改变相应树，继而使引用该根树的新提交不同。提交对象还包含父关系与元数据，所以两次提交即使目录树完全一样，也可能得到不同身份。

对象标识来源于包含类型与长度等信息的对象表示的摘要。不同仓库可能使用不同对象格式，不应把固定长度的十六进制字符串当成永恒接口，也不能把对象摘要等同于作者签名。内容寻址擅长检测内容身份和建立链接关系；谁有权发布该内容、内容是否恶意、实验是否科学有效，是其他层面的判断。

分支可以理解为指向某个提交的可移动引用。当前分支上的新提交通常使该引用前进；历史提交本身不会就地改写。所谓修改历史，实际是创建新的对象关系并让引用指向新位置。旧对象在仍可达或尚未被清理时可能存在，但它们不会因为你希望恢复而永久保留。第二、三章将用这个模型解释合并与恢复。

<a id="sec-6-1"></a>

<a id="git-1-detail-15"></a>

### 7.1 用三个快照推导一次提交包含什么

考虑最近提交的根树包含训练文件甲、配置乙和说明丙。你将甲修改为甲二并暂存，将乙修改为乙二却没有暂存，最后删除丙并暂存删除。默认提交的树包含甲二和原乙，不再包含丙；工作区仍有乙二。判断结果只需要看索引，不需要猜测编辑顺序，也无需把工作区全部复制到脑中。

如果随后再次暂存乙，索引才变成甲二、乙二且无丙。若这两项变更需要共同成立，那么第二种树才是合适交付对象。反过来，如果甲二的实现仍兼容乙，第一种树也可能合理。Git 能准确构造你选择的树，但不会替你判断配置与实现是否匹配。把这种语义判断交给测试与审查，是工具和工程责任的明确分工。

树的比较还可以证明交付范围。若两个提交的树相同，它们在 Git 所记录的路径、模式和内容上相同；这不要求父提交或说明相同，也不证明外部数据与执行环境相同。相同树是比“看起来没改多少”更精确的代码状态证据，但仍不能替代完整实验身份。

<a id="visual-01-mechanism"></a>

### 图解：提交、树与内容对象承担不同角色

![提交、树与内容对象承担不同角色](images/01-mechanism.svg)

两个提交各自指向一棵树，树通过目录项关联内容对象。不同快照中相同文件内容可以复用同一个 blob，因此提交不是把所有文件简单复制成一套独立字节。

箭头表示对象引用方向。这里为突出内容复用省略父提交和其他文件；树对象还记录路径名、模式等信息，相同 blob 并不意味着整个项目快照相同。

<a id="visual-01-advanced"></a>

### 图解：相同文件树不代表相同提交

![相同文件树不代表相同提交](images/01-advanced.svg)

两个提交可以指向完全相同的文件树，却因父引用等提交元数据不同而具有不同身份。文件内容、树快照和提交历史是不同层次，不能用目录内容相同替代对提交身份的固定。

右侧结论框用于比较，不是树对象的真实引用；真正的对象引用只有两条提交到树的箭头。提交还包含作者、提交者等字段，相同文件树只固定了快照的一部分身份。

## 8. 实验一：直接观察三个区域

下面使用 Python 标准库创建临时仓库。每次 Git 调用都采用参数列表，并固定工作目录；没有命令字符串插值，也没有网络操作。局部配置只作用于临时仓库。实验主动禁止全局和系统配置对结果的部分干扰，并显式关闭换行转换与提交签名；这仍不是对任意恶意系统环境的沙箱承诺，而是为普通教学环境减少差异。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_three_states_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(*args):
        result = subprocess.run(
            ["git", *args], cwd=repo, env=env,
            text=True, encoding="utf-8", capture_output=True, check=True,
        )
        return result.stdout.strip()
    git("init", "-b", "main")
    git("config", "user.name", "Learning Example")
    git("config", "user.email", "example@example.invalid")
    git("config", "core.autocrlf", "false")
    git("config", "commit.gpgsign", "false")
    path = repo / "config.txt"
    path.write_text("rate=A\n", encoding="utf-8")
    git("add", "--", "config.txt")
    git("commit", "-m", "record A")
    path.write_text("rate=B\n", encoding="utf-8")
    git("add", "--", "config.txt")
    path.write_text("rate=C\n", encoding="utf-8")
    assert git("show", "HEAD:config.txt") == "rate=A"
    assert git("show", ":config.txt") == "rate=B"
    assert path.read_text(encoding="utf-8").strip() == "rate=C"
    assert "rate=B" in git("diff", "--staged", "--", "config.txt")
    assert "rate=C" in git("diff", "--", "config.txt")
    git("commit", "-m", "record staged B")
    assert git("show", "HEAD:config.txt") == "rate=B"
    assert path.read_text(encoding="utf-8").strip() == "rate=C"
    print("HEAD=B; working tree=C; unstaged change retained")
```

实验不依赖提交对象的具体标识，因此不会因运行时间不同而改变断言。它验证的是对象关系与内容关系，而不是某台机器恰好产生的一串哈希。输出中的工作区修改被保留，是流程的预期结果。临时目录退出后会自动删除，因此示例不会在你的原有项目目录留下仓库或辅助文件。

进一步观察时，可以在第二次提交之前查看索引条目和最近提交的树。你会看到索引中的对象身份对应暂存内容，而最近提交的树仍引用旧对象。不要直接修改索引二进制文件来“修复”状态；学习底层表示的目的是解释上层命令，不是绕开它们的约束随意编辑仓库内部结构。

## 9. 实验二：内容复用、树变化与忽略边界

第二个实验把相同内容放到两个路径，证明内容对象不依赖文件名；接着记录一个日志文件，再把它加入忽略规则，观察它仍然保持已跟踪状态。为了避免把示例误当成删除历史的方法，本实验只读取状态并创建普通提交，不执行任何历史重写。

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import os
import subprocess

with TemporaryDirectory(prefix="git_objects_") as root:
    repo = Path(root)
    env = os.environ.copy()
    env.update({"GIT_CONFIG_NOSYSTEM": "1", "GIT_CONFIG_GLOBAL": os.devnull})
    def git(*args):
        return subprocess.run(
            ["git", *args], cwd=repo, env=env, text=True,
            encoding="utf-8", capture_output=True, check=True,
        ).stdout.strip()
    git("init", "-b", "main")
    for key, value in [("user.name", "Example"),
                       ("user.email", "example@example.invalid"),
                       ("core.autocrlf", "false"), ("commit.gpgsign", "false")]:
        git("config", key, value)
    for name in ["left.txt", "right.txt"]:
        (repo / name).write_text("same bytes\n", encoding="utf-8")
    (repo / "run.log").write_text("first run\n", encoding="utf-8")
    git("add", "--", "left.txt", "right.txt", "run.log")
    git("commit", "-m", "record sample files")
    left = git("rev-parse", "HEAD:left.txt")
    right = git("rev-parse", "HEAD:right.txt")
    assert left == right
    assert git("cat-file", "-t", left) == "blob"
    tree_before = git("rev-parse", "HEAD^{tree}")
    (repo / ".gitignore").write_text("*.log\n", encoding="utf-8")
    (repo / "run.log").write_text("second run\n", encoding="utf-8")
    (repo / "scratch.log").write_text("temporary\n", encoding="utf-8")
    assert git("ls-files", "--", "run.log") == "run.log"
    assert "run.log" in git("status", "--short")
    assert "scratch.log" not in git("status", "--short")
    assert "scratch.log" in git("check-ignore", "--", "scratch.log")
    git("add", "--", ".gitignore")
    git("commit", "-m", "ignore future untracked logs")
    assert git("rev-parse", "HEAD^{tree}") != tree_before
    assert git("show", "HEAD:run.log") == "first run"
    print("shared blob verified; tracked log remains tracked")
```

这组断言同时展示了三个层次：相同字节可以共享内容对象；增加一个路径会改变根树；忽略新路径不改变已跟踪路径。最后一次提交只暂存忽略文件，因此日志虽然在工作区改变，提交仍保留第一版日志。若你能在运行前预测这些结果，就已经具备把索引视为交付计划的能力。

实验还提示不要把对象复用误解成文件之间的硬链接。两个工作区文件可以独立编辑，即使它们曾指向同一个内容对象，修改其中之一不会自动修改另一个。复用发生于版本存储层，而不是声明这两个路径在程序运行中永远具有联动关系。

<a id="git-1-detail-18"></a>

## 10. 证明测试对象等于交付对象

工作区中的测试通过，只能直接证明当时工作区及其可见外部条件下的表现。要证明准备提交的内容通过，就必须让测试读取该内容。最直接的方法是在提交后用独立检出验证该提交；如果必须提交前验证，可以先把索引导出到隔离目录，或构造临时提交再用独立工作树验证。不同方法的副作用不同，不应在不理解时用复杂脚本代替简单操作。

导出索引文件只给出 Git 跟踪的树，通常没有未跟踪的数据、依赖环境或生成产物。这恰好可以暴露隐含依赖，但也要求测试协议明确准备这些必要条件。把依赖配置为读取原工作区的绝对路径，会破坏隔离目的：测试表面上在新目录运行，实际上仍消费未提交文件。隔离验证应检查输入来源，而不只是检查当前目录。

在使用独立工作树时，还要理解工作树共享对象数据库与部分仓库配置，但拥有各自的工作区、索引和当前检出位置。因此“独立工作树”不是“完全独立的系统环境”。它适合验证代码快照差异，却不自动隔离全局依赖、数据库、缓存目录或网络服务。实验设计应按问题选择隔离范围，不要把一个工具提供的边界夸大成所有边界。

<a id="git-1-detail-19"></a>

### 10.1 最小可复核证据如何组织

对于一次可审查交付，可以记录被验证的完整提交标识、运行命令、输入身份、关键输出和退出状态。若测试发生在提交之前，还应记录被验证树的身份及随后提交是否引用该树。这样，即使提交元数据因为补充说明而变化，也能解释测试结果与实际代码内容的关系。

但树相同仍不意味着测试过程相同。测试可能受环境变量、当前时间、随机源或外部服务影响。因此证据需要按层累积：树身份说明源文件一致；依赖与输入说明计算条件；断言与结果说明观察到的行为。每一层都有作用范围。把所有条件压缩成“已经测过”会让后来的人无法判断结果能否迁移到自己的场景。

对于训练任务，完全重跑可能成本很高，可以使用分层验证：先进行配置解析和输入模式检查，再运行小型确定性样本验证关键公式，最后对代表性训练规模进行端到端测试。提交说明应清楚区分哪些层实际执行、哪些尚未执行。成本约束可以改变验证设计，不能把尚未执行的层描述成已经完成。

<a id="git-1-detail-20"></a>

## 11. 可达性、完整性与备份的区别

对象的存在与对象的可达性不是同一件事。一个内容对象可能因为曾被暂存而写入数据库，却没有进入任何当前引用可达的提交。它暂时存在不代表长期受到保留。分支、标签以及其他引用为提交图提供入口，而垃圾回收会依据规则处理不可达对象。因此，不应把“我曾经执行过暂存”当成永久备份保证。

版本控制也不等于备份。一个本地仓库能够保存丰富历史，但如果磁盘损坏且没有其他副本，所有对象可能一起丢失；远程副本如果只收到已推送引用，也不会自动包含工作区里尚未提交的研究记录。相反，文件系统备份可能保存未提交文件，却缺乏便捷的提交关系和审查语义。两者互补，承担不同恢复目标。

完整性检查主要检查对象结构、链接和可达性问题，不会验证模型训练结果是否合理，也不会保证所有外部产物仍能下载。一个结构健康的仓库可以包含错误算法或失效数据链接。工程上需要分别建立仓库完整性、数据可用性、产物校验和科学结论复核的证据，避免把任何一层的成功替代其他层。

当你需要长期保留某个实验版本时，应给它稳定可发现的引用，并确认代码、输入清单和产物均有适当副本。不能只在聊天记录中留一个短哈希，然后假设对象永远不会消失。版本身份解决“是哪一个”，保留策略解决“未来是否还拿得到”，两者缺一不可。

<a id="git-1-detail-21"></a>

## 12. 常见误解的机制性纠正

第一种误解是“保存了文件，提交就会包含它”。它忽略索引这一中间状态。纠正方法是在提交前直接查看暂存内容，而不是反复打开编辑器确认工作区。第二种误解是“状态干净，所以项目正确”。状态只比较 Git 管理的几个状态，不评价程序语义，也不保证忽略文件或外部环境一致。

第三种误解是“提交只保存修改过的文件”。从展示差异的角度，它突出这些文件；从版本模型的角度，提交指向整棵根树。第四种误解是“删除最新文件就删除了历史”。只要旧提交仍引用内容，它通常仍可读取。第五种误解是“哈希相同就证明实验完全一样”。哈希只能对所标识的对象及其结构提供身份信息，不能代替外部输入与环境说明。

第六种误解是“越小的提交越好”。过小而破坏语义完整性的提交会增加调试困难。第七种误解是“全局配置适用于所有项目”。不同项目可能需要不同身份、换行和签名规则，应该了解配置来源与覆盖顺序。第八种误解是“忽略规则是安全边界”。忽略规则既能被显式覆盖，也无法让已经分享的秘密失效。

最后一种值得特别注意的误解是“命令成功意味着目标达成”。命令成功只表示它按照参数和当前状态执行了相应操作。暂存成功可以暂存错误文件，提交成功可以记录不完整配置，推送成功可以共享错误结果。掌握 Git 的真正标志，是能把工具状态与任务意图逐项对齐，而不是只看退出码是否为零。

## 13. 练习与详细解析

<a id="git-1-detail-23"></a>

### 13.1 练习一：预测三份学习率

最近提交中的学习率为甲，修改为乙并暂存，再修改为丙而未暂存。此时普通提交后，各区域是什么？请同时说明普通差异和暂存差异的结果。答案是提交与索引都保存乙，工作区保存丙；普通差异显示丙相对乙的变化，暂存差异为空。暂存差异为空并不意味着工作区没有修改，而是索引已经与最新提交一致。

推理时不要从“最新编辑的应该进入提交”出发，而应沿着命令的数据流走：编辑只改工作区，暂存复制当时的内容身份到索引，普通提交读取索引。只要逐步更新这三份状态，就能处理任意多次编辑与暂存，不必为每种排列单独背答案。

<a id="git-1-detail-24"></a>

### 13.2 练习二：已删除文件为什么仍在历史中

某人删除一个模型权重文件并提交，却还能从以前的提交读取它，是否意味着删除失败？答案是否定的。删除成功意味着新树不再包含该路径；旧树仍然引用原内容对象，因此历史可读取。若文件包含秘密，最新目录删除不能完成秘密撤回。若文件只是大产物，是否清理旧历史应结合仓库共享与保留需求另行决定。

这里要区分路径删除、对象失去引用、对象实际被清理三个事件。它们通常不是同一时刻发生。只观察工作区已经没有文件，不能推断数据库里不再有相关对象；只观察对象暂时存在，也不能推断它未来永久存在。这个区分是学习撤销和恢复之前必须建立的基础。

<a id="git-1-detail-25"></a>

### 13.3 练习三：相同内容为什么可以有不同提交

两次提交保存完全相同的文件树，却具有不同标识，可能吗？可以。提交不仅包含根树身份，还包含父关系、作者与提交者信息、时间和说明等元数据。只要对象表示不同，提交身份就不同。这里无需假设发生摘要碰撞；正常元数据或父关系变化就足够解释现象。

反过来，两个路径的文件字节相同，在相同对象格式与相同规范化规则下可以共享内容对象，因为路径名不属于内容对象。文件身份、树身份和提交身份处于不同层。讨论“版本相同”时，应先声明比较的是哪个层次，否则很容易把源树一致与历史一致混为一谈。

<a id="git-1-detail-26"></a>

### 13.4 练习四：忽略规则为什么没有隐藏旧日志

一个日志文件已经提交，后来添加匹配所有日志的忽略规则，继续运行训练后它仍出现在状态中。原因是它已经被跟踪。忽略规则主要作用于未跟踪文件的默认发现与添加，不会自动把已跟踪路径从索引移除。正确调查应先确认该文件是否被跟踪，再决定是否改变跟踪策略。

如果只是为了本机少看一项修改，不应把项目共同需要的文件随意从历史中撤掉。还要问这个日志是否本来就应是版本输入，是否其他人依赖它，是否存在更合适的产物存储方式。工具层的答案解释现象，项目层的判断决定后续动作，两者不能互相替代。

<a id="git-1-detail-27"></a>

### 13.5 练习五：工作区测试通过能否证明提交可用

你暂存了模型接口变化，却没暂存调用方适配，工作区测试通过。能否据此断言默认提交通过？不能，因为测试读取包含调用方适配的工作区，提交读取不含适配的索引。需要在独立状态验证索引对应树，或者调整暂存范围使被测试树与提交树一致。

这道题也说明，部分暂存本身不是错误。错误是没有检查拆分后的语义闭合性。只要目标树独立成立、测试对应目标树，部分暂存可以提高审查质量。判断标准是可运行与可解释，而不是操作形式是否简洁。

<a id="git-1-detail-28"></a>

### 13.6 练习六：一个新配置为什么没有进入提交

研究者新增配置文件并修改训练程序，使用只自动暂存已跟踪路径变化的提交方式后，程序更新了，新配置却没有进入。原因是新文件尚未被跟踪，该快捷方式不会自动纳入所有未跟踪文件。解决思路是明确列出新配置并暂存，再检查暂存树中是否存在它，而不是依赖快捷选项的模糊印象。

验证时可以查看目标提交的文件列表或直接读取目标路径。当前工作区仍有配置，不能说明提交中也有。一个常见的持续集成失败模式正是本机保留未跟踪文件，而干净检出缺失该文件。独立检出测试能够把这种隐藏依赖暴露出来。

<a id="git-1-detail-29"></a>

### 13.7 练习七：是否应把依赖目录全部提交

为了避免未来安装失败，有人建议把当前虚拟环境全部提交。这个方案能否提供可靠复现？通常不能直接保证，因为环境中可能包含绝对路径、平台相关二进制、机器配置和缓存；体积也可能很大。更合理的方案需要明确依赖版本、解析结果、平台和可获取源，并通过干净环境恢复验证。

但也不能推出所有依赖文件永远不应保存。在受控发行或离线环境中，可以有经过设计的依赖归档与镜像策略。关键是采用能准确表达身份与平台约束的机制，并检查恢复过程。把某个目录直接复制进 Git，只是保存字节的一种选择，不自动建立可移植运行环境。

<a id="git-1-detail-30"></a>

### 13.8 练习八：短哈希什么时候会失去充分性

当前仓库中七位前缀能唯一识别一个提交，能否把这个前缀当成永久身份？不能保证。仓库对象数量增加后，相同前缀可能不再唯一；在另一仓库里也可能匹配不同对象或根本不存在。长期实验清单应保存完整标识，并说明仓库来源与对象格式，而展示界面可以使用便于阅读的短形式。

即使完整标识正确，未来仍需存在可获取对象的仓库或归档。身份与可用性是两个问题。只记录身份而不保留对象，等于知道一本书的精确版本却没有任何可获得副本。可复现流程必须同时维护定位信息和保留机制。

<a id="git-1-detail-31"></a>

### 13.9 练习九：时间较晚是否一定是后代

两个提交的时间戳一前一后，能否据此断定较晚者是较早者的后代？不能。提交时间可以由环境提供，也可能因时钟偏差、转录或显式设置而不符合拓扑直觉。判断祖先关系应检查提交图中的父链接，而不是按界面时间排序后推断。

这对事故分析尤其重要。日志中的事件时间、提交元数据时间与服务器接收时间可能分别描述不同事实。需要明确正在回答“什么时候被创作”“什么时候被提交”“什么时候被发布”还是“从哪个版本派生”。一个字段通常无法同时回答全部问题。

<a id="git-1-detail-32"></a>

### 13.10 练习十：树相同是否意味着行为相同

若两个提交的根树相同，训练结果是否必然相同？不必然。相同树只限定 Git 记录的文件内容与模式。训练还可能读取不同数据、使用不同依赖、硬件或随机状态。如果程序读取当前时间或网络响应，即使输入清单看似相同，实际执行条件也可能不同。

更精确的结论是：在树所覆盖的文件层面，两者相同。若想进一步声称行为相同，需要声明并核对运行条件，且在非确定性场景下给出统计意义上的复现标准。不要因为更强结论不成立，就否定树身份的价值；它是必要证据中的一层。

<a id="git-1-detail-33"></a>

### 13.11 练习十一：为什么纯重命名会显示删除和新增

你移动一个文件后，某个差异界面显示删除旧路径并新增新路径，另一个界面却显示重命名，是否仓库内容不同？未必。重命名经常由比较算法根据相似度推断，显示结果受阈值和选项影响。两棵树的实际路径与内容可以完全相同，只是工具对它们之间关系的解释不同。

这也说明不要用补丁显示的某个标签替代对象级核对。如果审查需要确认内容是否未改，可以比较相关内容对象，或使用适合的差异选项。显示层便利于理解，树层定义版本状态。二者相互补充，但职责不同。

<a id="git-1-detail-34"></a>

### 13.12 练习十二：什么时候一个大提交反而合理

一次模型输入接口迁移同时修改数据加载、模型前向、配置、测试和说明，涉及许多文件。必须拆成每个文件一个提交吗？不必须。如果这些变化共同实现一个接口协议，拆开反而导致中间版本不可运行。可以根据兼容层设计拆分，但每一步都应有可验证的承诺。

合理拆分通常先引入兼容接口，再迁移调用方，最后移除旧接口。若迁移规模很小，单次完成也可能更清楚。评价标准是读者能否理解目的、测试能否验证边界、回滚是否可控，而不是机械计数文件数量。

<a id="git-1-detail-35"></a>

### 13.13 练习十三：提交前检查空白能证明什么

某项目运行差异空白检查后没有输出，是否可以删除算法测试？不可以。空白检查主要捕捉其规则覆盖的格式问题，例如某些行尾空白或冲突相关异常；它不理解损失函数、样本权重和数据划分语义。静态格式证据与行为测试证据处于不同层。

同理，类型检查、单元测试、集成测试和训练评估也有各自盲区。一个合理的验证方案应该用最少而足够的检查覆盖实际风险，而不是把任何一次成功当成全局证明。提交说明可以明确“格式检查通过、合成例题通过、尚未运行完整训练”，这比笼统写“全部正常”更有信息。

<a id="git-1-detail-36"></a>

### 13.14 练习十四：没有远程的本地提交可靠吗

没有配置远程仓库，提交是否仍然有效？有效。本地提交的对象关系与引用更新不依赖网络。它能够提供历史、差异和分支能力。但是单机只有一个副本时，硬件故障仍可能导致丢失；尚未推送的本地提交也不会被同伴自动看见。

因此应分别回答“版本是否记录成功”“是否已经共享”“是否有独立备份”。这三个问题需要不同证据：本地历史与对象、远程引用与传输结果、备份恢复能力。把它们分开，既能正确使用离线工作流，也能避免误以为提交按钮等于云端备份按钮。

<a id="sec-7-1"></a>

<a id="git-1-detail-37"></a>

### 13.15 综合追问：如何证明已暂存提交可用

设工作区同时包含本次修复与下一项探索，索引只包含本次修复。请设计既不丢探索内容、又能核对交付树的方案。一个思路是先记录当前状态与未提交差异，再在隔离位置恢复索引描述的文件集合，准备相同的最小依赖和固定测试输入，在该位置运行验证；随后比较实际提交树与被验证树。另一思路是先创建本地提交，再在独立工作树验证该提交，失败则继续修复而不急于发布。

方案的关键不在于选用哪条复杂命令，而在于建立四个不变量：探索内容仍有明确保留位置，验证读取目标树，输入与环境符合测试协议，最终交付指向被验证内容。还要检查测试是否偷偷读取原目录中的配置或缓存。只把当前目录切换到临时位置，而保留绝对路径依赖，不构成真正的快照验证。

<a id="git-1-detail-38"></a>

## 14. 进阶研究：为提交建立可验证契约

可以把每个提交看作一个带上下文的状态转换契约：前置条件说明它适用的输入与环境，后置条件说明它承诺的行为，验证证据说明为何相信这些承诺。Git 保存状态与关系，却不原生理解这些契约。测试、文档和实验清单共同填补这部分语义。这个观点能把版本控制从“保存文件工具”提升为研究过程的证据组织工具。

例如，为一次评估口径变更建立契约时，前置条件包括固定数据划分与有效样本定义，后置条件包括指标按正确分母汇总，验证证据包括手工可算反例与完整评估结果。若只记录“指标变好了”，无法判断改进来自模型还是分母变化。把契约与提交树连接起来，可以更清楚地区分行为变化、报告变化和实验条件变化。

进一步可以研究提交粒度对缺陷定位的影响。过大的提交增加候选原因，过小但不完整的提交增加不可测试节点。理想粒度依赖项目结构，不存在一个普遍最佳行数。你可以在小型项目中设计两种历史，比较审查时间、二分时可测试节点比例和回滚时连带改动范围，从实际证据建立自己的工作规则。

另一个研究方向是内容寻址与信任的关系。对象身份使内容关系可验证，却不回答内容的来源是否可信。签名、受保护分支、构建证明与发布权限分别增加不同证据。不要把某一种机制想成万能安全保证；应该明确攻击者可以控制哪些层、验证者持有哪些可信入口，再判断整条链条是否闭合。

- [Git 官方 add 手册](https://git-scm.com/docs/git-add)：核对索引更新、部分暂存及选项边界。
- [Git 官方 diff 手册](https://git-scm.com/docs/git-diff)：区分工作区、索引与提交之间的比较。
- [Pro Git：Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)：从内容、树与提交对象继续阅读底层模型。

本章独立实验在 Git 2.45.1.windows.1 上实际运行；未依赖远程服务。阅读更新版本手册时，请区分版本无关的数据模型与新加入的具体选项。
